## 1. 页面概述

租户套餐页是**平台运营方的权益模板台账**：以表格列出全平台可售的套餐档位（名称 / 编码 / 购买类型 / 价格 / 最大用户数 / 状态），并提供「新增套餐 / 编辑 / 删除」三个写动作。它是 `61301 租户管理` 组的第 3 页（`sort=300`）。

**1.1 与相邻页的分工（`61301 租户管理` 组 5 页）**

| 页面 | 菜单ID | 回答的问题 | 后端前缀 | 与本页关系 |
|------|:-----:|-----------|---------|-----------|

| 模块授权 | 62004 | 某租户能开哪些模块 | `/api/tenant-menu` | **应由套餐驱动**（`sys_package_module`）—— **该表不存在**（§7.3） |

## 2. 页面截图

**N/A —— 本模块无对标系统截图。**

- ql361 中**不存在**「租户套餐」页面，**无可对标截图**；
- **不使用 Odoo / SAP / 金蝶 / 用友的界面截图**（口径见《系统模块/README.md》§5.3）；
- §8 只写**业界能力对标**，逐条标来源与可信度级别。

**本系统截图**：当前无本系统验收截图（`tools/` 与 `tools/acceptance/` 下不存在 `e2e-system-*.cjs` / `e2e-admin-*.cjs`）→ **P2 缺口**（README §7.3）。

**数据现状（devdb 实测 2026-09-18）——本页有真实数据，可以直接看到表格**：

```sql

       api_call_limit,status,deleted,tenant_id
  from sys_tenant_package order by id;
```

**列定义核查**：

| 项 | 实测结论 |
|----|---------|
| `formatter` | **全页无任何 `formatter`**；缺陷模式 `({row})=>` **未出现** |
| `type` / `defaultHidden` / `slotName` | **全部未指定**（`a-table` 原生 `#bodyCell` 按 `column.key` 分支，非 `BillDetailTable` 的 `type:'slot'` 体系）—— **无列配置能力** |
| `fixed` / `align` | **全部未指定**（无固定列、无右对齐） |
| 列 3/4/6 的 `dataIndex` | **刻意省略**（由槽位渲染）；这是可接受的 antd 写法，但**与「列配置」体系不兼容**（列配置依赖 `dataIndex`/`key` 稳定） |
| 原型链风险 | `{ monthly:…, yearly:…, perpetual:… }` 字面量对象做映射表，**键非原型链敏感键**（无 `toString` 等）→ **不触发 `js-prototype-key-trap`** ✅ |

**✅ 正确之处（价格单位换算）**：`price` 以「**分**」存储（后端字段注释「价格（分）」，`SysTenantPackage.java:31-32`；DB 实测 `9900`/`99900`/`499900`），前端展示**除以 100 并格式化为 2 位小数**（`:47`）→ **单位口径正确、无精度丢失**（`(9900/100).toFixed(2)` = `99.00`）。

**⚠️ 需注意（P2）**：价格空值显示 `-`（`:47` 的三元分支）；但 `0` 也会走 `-` 分支（`record.price ? … : '-'`，`0` 为 falsy）→ **价格为 0 的免费套餐会显示成 `-`**（这是真实缺陷，非理论风险）。

**双向换算 computed（本节是本页实现最精细的地方）**：

```ts

  set: (val: number) => { form.value.price = Math.round(val * 100) },

// 布尔 ↔ 1/0（:191-194）

  get: () => form.value.status === 1,
```

| 环节 | 单位 | 实现 | 行号 |
|------|:----:|------|------|

**✅ 正确之处**：写入方向用 `Math.round(val * 100)`（`:188`）→ **规避浮点误差**；读出方向 `.toFixed(2)` 保证两位小数。

### 5.4 取值口径（**套餐 → 租户：这一步不存在**，本页最核心的结构性缺口）

```
现状（断层）：
  sys_tenant_package（套餐定义，本页维护，3 行）
        ╳  无任何关联表 / 外键 / 端点 / 逻辑
  sys_tenant（租户，3 行）—— level 字段是自由字符串 basic/professional/enterprise
  sys_tenant_quota（租户配额，3 行，tenant_id = 1/2/3）—— 与套餐零连线
  sys_tenant_menu（模块授权，4 行，tenant_id 全 0）—— 与套餐零连线

业界模型（SAP，A 级）：
  Service → Service Plan（套餐档位）→ Entitlement（权利）→ Quota（配额）→ Assignment（分配）
```

| 观察 | 证据 |
|------|------|
| `sys_tenant` **无 `package_id` / `package_code` 列**（15 列实测），只有自由字符串 `level` | devdb `information_schema.columns` |
| `sys_tenant.level` 的三值与 `sys_tenant_package.package_code` 的三值**字面相同**（`basic`/`professional`/`enterprise`） | `list/index.vue:182-190` vs DB 实测 |
| 但**无任何唯一约束、无外键、无校验** → `level` 可填任意字符串（`POST /api/tenant` 不校验，`TenantController.java:84-88`） | 同上 |
| **无 `sys_package_module`、无 `sys_tenant_entitlement`** 表 | devdb 实测（§7.3） |
| → **改套餐价格 / 改配额 / 改模块清单，对任何租户都不产生效果** | 结构性结论 |

**结论**：本页当前是**一张孤立的价目表**。「套餐 = 模板，租户持有的是分配记录」这条业界口径（§8.2-①）在本系统**缺失了后半段**。

### 5.5 流转规则（本页动作）

```
（无）── POST /api/tenant-package ──▶ deleted=0、status 空则补 1、create_time/update_time=now
status=1 ⇄ status=0  ── 只能经「编辑」弹窗的 a-switch 改写（页面无独立启停按钮）
任意 ── DELETE /api/tenant-package/{id} ──▶ setDeleted(1)（逻辑删除，无引用保护）
```

| 动作 | 后端 | 前置校验 | 失败文案 | 副作用 | 行号 |
|------|------|:--------:|---------|--------|----|
| 新增 | `POST /api/tenant-package` | **无**（前端仅查名称/编码非空） | 无 | `setDeleted(0)` + 时间戳 + `status` 兜底 1 | `TenantPackageServiceImpl.java:37-46` |
| 编辑 | `PUT /api/tenant-package/{id}` | 先 `selectById`，`existing == null \|\| deleted == 1` → 返回 `null` | 后端返回 `code:200` + `message:"套餐不存在"`（**HTTP 仍是 200**） | `setCreateTime(原值)` / `setUpdateTime(now)` / `setDeleted(原值)` 后 `updateById` | `:49-58`；控制器 `:53-65` |
| 删除 | `DELETE /api/tenant-package/{id}` | 先 `selectById`，不存在或已删 → 返回 `false` | `message:"套餐不存在"`（HTTP 200） | `setDeleted(1)` + `setUpdateTime(now)` | `:61-69` |

**🔴 缺陷 P1-③：不存在时仍返回 HTTP 200 + `code:200`**
`GET /{id}`（`:39-42`）与 `PUT /{id}`（`:61-63`）在「套餐不存在」时返回 `ResponseEntity.ok(Map.of("code", 200, "data", null, "message", "套餐不存在"))` → **HTTP 200 成功壳**。前端若只判 HTTP 状态码，会**把失败当成功**。当前前端未接 `GET /{id}`（§6.3），`PUT` 路径的失败也因错误分支丢弃原文（§3.7）而**不可见**。

**🔴 缺陷 P1-④：`PUT` 不校验必填**
`update` 直接 `updateById(pkg)`（`:55`），**不校验 `packageName` / `packageCode` / `purchaseType` 非空**，也不做唯一性校验（编码可重复）。→ 可把套餐名改成空串（**这正好绕过 `updateById` 忽略 null 的限制**：空串非 null，会真的写入）。

**⚠️ 注意（P2）**：`create` 不校验 `packageCode` 唯一性（`SysTenantPackage` 无 `@TableField` 唯一约束、DB 无唯一索引）→ **可建同编码套餐**（对标《租户审批》注册链路的编码唯一校验，`:74-78`，口径不一致）。

### 5.6 多租户口径（本模块红线②，**本页是正面命中对象**）

| 事实 | 证据 |

### 8.2 业界做法要点（逐条给级）

1. **套餐 = 模板，租户持有的是「分配」** —— SAP 层级是「全局账户买权利 → **分配到**目录/子账户」；jeecg 是「系统管理员建套餐 → 给租户分配套餐 → 租户管理员再把套餐分配给租户下的用户」。**A**
2. **权限归属明确** —— jeecg 原文「**租户管理员没有权限新建和修改租户套餐**」，新建/修改**仅系统管理员可做** → **套餐的编辑权是平台级权限，不是租户级权限**。**A**（本页已经是平台侧页面，方向正确 ✅）
3. **必须有「默认套餐」** —— jeecg：新用户注册或被邀请加入租户时**系统自动把默认套餐给用户**；且有「自动分配用户」开关（默认开启）。**A**
4. **套餐与角色的分工** —— jeecg 的租户角色「只用于审批（类似职务），**不参与权限授权**」，「租户的个性化权限，可以通过租户下的套餐实现」。即**用套餐承载功能授权，用角色承载流程身份**。**A**
5. **同一功能可挂多个产品** —— Stripe 明确「同一功能可添加到多个产品」——避免为每个套餐复制一份功能定义。**B**
6. **套餐变更 = 分配记录的增删** —— SAP「**从目录或子账户中移除配额或分配时，配额或权利将在全局账户级别再次可用**」。**A**
7. **SAP 第 3 条关键原文（对「已有租户是否享受套餐改版」是明确答案）** —— 「将权利分配到目录时，会表达可在其子子账户中分配的权利和最大配额。您还可以选择将一定数量的配额自动分配给所有创建或移动到该目录的子账户。**选择该选项时，目录中已存在的子账户将不会自动分配配额**。」→ **不追朔存量**。**A**

### 8.4 明确不借鉴

| 不借鉴 | 理由 |
|--------|------|
| **SAP 的「全局账户 - 目录 - 子账户」三层分配模型** | 本系统无目录层（单层租户），也**没有一个「全局账户」对象** —— 引入目录层会导致「套餐分配给目录还是子账户」的二义性，投入产出比不成立 |
| **SAP 的配额「预留（reserved）」语义** | 需要「目录级配额池」前提；本系统无此对象 |
| **Stripe 的 webhook 驱动开通/撤销** | 本系统是**单体内应用**，模块开关是本地数据变更，无需外部事件驱动；引入 webhook 属过度设计 |
| **AWS 的 per-tier API Gateway usage plans** | 本系统无 API 网关层；限流应在应用内（若做） |
| **业界的界面样式**（Service Marketplace 磁贴 / jeecg 弹窗布局） | 本模块口径：只学能力模型，不照搬界面 |
| **把套餐字段冗余到租户表** | 底稿 §0.2 明确「**不要把套餐字段直接冗余到租户表**：套餐改版会污染存量租户」→ 本系统当前 `sys_tenant.level` 正是这种冗余（自由字符串），**应废弃或改为外键** |

### 10.1 接口验收（**22 项**）

**基线、红线与解包（①–⑤）**

① `GET /api/tenant-package/list`（带 `admin` 的 `Authorization: Bearer <token>`）→ **期望 200**，返回体含键 `records` / `total`（**裸 Map，无 `code`/`message`**，`TenantPackageController.java:29-31`）。
② **🔴 超管数据可见性专项**：断言 `records.length ≥ 3` **且 `total ≥ 3`**（直查 `select count(*) from sys_tenant_package where deleted=0` = **3**）；**若为 0，即红线②复发**（§5.6），须立即按 `@InterceptorIgnore(tenantLine="true")` 处置。
③ 断言返回的 3 行 `packageCode` 恰好为 `basic` / `professional` / `enterprise`，`status` 全为 `1`（与 §2 实测逐字对账）。
④ **字段完整性断言**：每行含 `id` / `packageName` / `packageCode` / `purchaseType` / `price` / `maxUsers` / `storageQuota` / `apiCallLimit` / `status` / `description` / `sortOrder` / `tenantId`；**断言 `tenantId` 全为 `0`**（现网事实）。
⑤ `GET /api/tenant-package/list` **不带 `Authorization`** → **期望 401/403**（方法级 `@SaCheckPermission`，`:27`）。

**金额与值域（⑥–⑨）**

⑥ **金额单位断言**：`GET /list` 返回的 `price` 是**分**（`basic=9900`、`professional=99900`、`enterprise=499900`）；**断言接口不做换算**（换算在前端，`package/index.vue:47`）。
⑦ **建单 → 回读的金额往返**：`POST` body `{"packageName":"E2E档","packageCode":"e2e_x","purchaseType":"monthly","price":12345}` → 200；**直查 DB 断言 `price = 12345`（分）**；再 `GET /list` 回读断言仍为 `12345` → **证明无双重换算**。
⑧ **前端换算正确性（黑盒对账）**：断言 §2 的三行在 UI 上分别显示 `¥99.00` / `¥999.00` / `¥4999.00`（`price/100` + `toFixed(2)`）。
⑨ **购买类型值域断言**：`POST` 传 `purchaseType` 为 `monthly` / `yearly` / `perpetual` 各一次 → 均 **200**；传 `"weekly"` → **当前期望 200（无枚举校验）** → 登记 P1 缺陷（应 400）。

**写链路（⑩–⑯）**

⑩ `POST /api/tenant-package`（`admin`）body 仅 `{packageName, packageCode}` → **期望 200**；断言 DB 新增 1 行且 `deleted=0`、**`status=1`**（兜底 `TenantPackageServiceImpl.java:42`）、`createTime`/`updateTime` 非空。
⑪ **编码重复缺口**：用同一 `packageCode` 再 `POST` → **当前期望 200（重复创建成功）** → 登记 P1 缺陷；修复后改断言 400/409。
⑫ `PUT /api/tenant-package/{id}` 改 `packageName` → 断言 200、`message="更新成功"`、DB 值已变、**`createTime` 未被改动**（`:52` 保留原值）、`updateTime` 已刷新。
⑬ **🔴 「不存在仍 200」专项**：`PUT /api/tenant-package/999999999` → **当前期望 HTTP 200 且 body `data=null`、`message="套餐不存在"`** → **这是 §9.2-P1 的可执行证据**；修复后改断言 404。
⑭ **`PUT` 不校验必填专项**：对已存在套餐 `PUT` 传 `{"packageName":"","packageCode":""}` → **当前期望 200 且空串被写入**（空串非 null，不被 `updateById` 忽略）→ 登记 P1；修复后改断言 400。
⑮ **`updateById` 忽略 null 对照断言**：对已存在套餐 `PUT` 只传 `{"packageName":"仅改名"}` → 断言 `packageCode` / `price` / `maxUsers` 等**未被清空**（保留原值）→ 确认 NOT_NULL 策略行为，并写清「这正是不能靠 `null` 清空的原因」。
⑯ **权限断言**：用**非超管账号**调 5 个端点（含只读 `/list`）→ **期望全部 403**（`platform:tenant-package:*` 在 `sys_permission` 中 **0 行**）。**并断言** `select count(*) from sys_permission where permission_code like 'platform:tenant%'` = **0**（当前事实）；补种子后改断言 ≥ 4 且返回 200。

**删除、详情与复原（⑰–㉒）**

⑰ `DELETE /api/tenant-package/{id}` → 断言 200、`data=true`；**直查断言 `deleted=1`（逻辑删除）**；`GET /list` 不再返回该行。
⑱ **删除幂等**：对同一 id 再 `DELETE` → 断言 `data=false`、`message="套餐不存在"`（HTTP 仍 200）。
⑲ **`getById` 不带 `deleted` 的怪相（P2 的可执行证据）**：对刚被逻辑删除的 id 调 `GET /api/tenant-package/{id}` → **当前期望 200 且 `data` 非空**（`TenantPackageServiceImpl.java:33` 未加 `deleted` 条件）→ 与 ⑰ 的「列表里查不到」**自相矛盾**。
⑳ **`getById` 不存在断言**：`GET /api/tenant-package/999999999` → 断言 HTTP 200 + `data=null` + `message="套餐不存在"`。
㉑ **「改库 → 回读 → 按原值复原」标准动作**：取 id=1（基础版），记录原 `packageName` / `price` / `status` / `sortOrder` → 经接口 `PUT` 改名与改价 → `GET /list` 回读断言新值 → 再经接口改回原值 → 回读断言**逐字段复原**（**全程不得直改 DB**）。
㉒ **清理与收口**：⑩–㉑ 造出的套餐必须**逐条清理**（删除或物理清除 `E2E_*` 行），完成后断言 `select count(*) from sys_tenant_package where deleted=0` 回到 **3**；并断言**本次验收未产生任何 `sys_audit_log` 行**（`select count(*) from sys_audit_log` 仍为 **0**）→ 这是 §9.2-P0 审计缺口的可执行证据。

| **平台级表多租户豁免清单** | **未落位（代码常量）** | `MyBatisPlusConfig.IGNORE_TENANT_TABLES`（`:32-93`，Java `Set<String>` 字面量）；**`sys_tenant_package` 不在其中** | **改代码 + 重启** | 漏登记 → 注入 `tenant_id` → **页面空白而非报错**（§5.6） |
| **超管角色码**（决定豁免与 `*` 通配） | **通道 2 core-api yml** | `system.super-admin.role-codes`（§5.6.3 登记） | 重启 | 用内置默认值 `SUPER_ADMIN` |

### 11.2 租户级参数（**本页无**）

| 结论 | 说明 |
|------|------|
| **本页不落位任何租户级参数** | 套餐是**平台级模板**，按定义对全平台一份；「某个租户实际拿到哪个套餐、能用多少」应落在**租户级**的 `sys_tenant_entitlement` / `sys_tenant_quota` —— **这两张表的写入侧（分配）当前不存在**（§5.4、§7.3） |
| **`tenant_id` 列的存在是个陷阱** | 该列**可空且现网全 0**；它给了「套餐可以按租户定制」的错觉，但**没有任何代码读写它**（Service 的 `getList` / `create` / `update` / `delete` **均未设置或过滤该列**，`TenantPackageServiceImpl.java:24-69`）。**建议：明确它到底是「自定义套餐的归属租户」还是「遗留空列」，并在文档/迁移中收口** |
| **将来若做「租户定制套餐」** | 应走 `sys_tenant_entitlement.source = 'override'`（**本系统设计，D 级**），**而不是**在 `sys_tenant_package` 里按 `tenant_id` 复制行 —— 复制行会导致套餐清单随租户数线性膨胀，且改价要改 N 份 |

### 11.3 落位缺口（登记）

| 缺口 | 建议 |
|------|------|
| **`sys_tenant_package.tenant_id` 语义未定义** | 裁定为「平台级共享」后，应**明确不使用该列**（或加注释/迁移移除）；**切勿**因红线②的空白问题而把它当租户维度用 |
| **套餐-模块 / 租户-分配 无落位** | 新增 `sys_package_module`（`package_id` / `module_code`）与 `sys_tenant_entitlement`（`tenant_id` / `module_code` / **`source`** / `expire_at`），**格式：逐字段列**（便于按租户/模块双向查询） |
| **默认套餐无落位** | `sys_tenant_package.is_default`（boolean，建议加唯一约束只允许一行为 true） |
| **套餐改版不追朔的开关** | 建议通道 3（配置中心），支持「改版立即生效 / 仅对新分配生效」两种策略；**该策略本身是 D 级设计，无业界明文**（§8.5） |
| **审计开关无落位** | 建议通道 2（yml）默认开启 |

## 12. 剩余缺口（P0 / P1 / P2）

> 口径与《系统模块/README.md》§7 对齐。README §7.1-P0-15（平台级表未豁免多租户 —— **本页表是典型对象**）、P0-17（平台侧无审计）、§7.2（30 页无列配置等）在本页的具体化见下。

### P0（4 条）

① **权限码 0 行 → 非超管 5 个端点全部 403**（含只读 `/list`）：`platform:tenant-package:list/create/update/delete` 在 `sys_permission`（264 行）中 **0 行**；前端又零 `v-permission` → 「按钮可见但点了 403」。**注意本页用 `platform:` 前缀，与同模块另两页的 `system:` 前缀不同域**，补种子时两套都要补。
② **平台侧写操作零审计**（README §7.1-P0-17 的具体化）：新增/编辑/删除套餐不留任何流水；`sys_audit_log` 实测 **0 行**。
③ **套餐与租户零关联（结构性）**：无 `sys_tenant_entitlement` 表、无外键、无端点、无 UI → **本页 3 行数据不影响任何租户的任何行为**；`sys_tenant.level` 只是自由字符串（可填任意值）。「套餐 = 模板，租户持有的是分配记录」这条业界口径（SAP/jeecg，A 级）的**后半段完全缺失**。
④ **套餐不含模块清单（结构性）**：无 `sys_package_module` 表 → 套餐**表达不了「含哪些功能/权限」**（jeecg：「套餐是**一种权限和功能的组合**」）。

### P1（10 条）

⑤ **错误分支丢弃后端原文**（`:252-254`、`:264-266`）→ 本组**唯一**丢原文的页（另两页都有 `e.message`）。
⑥ **`fetchData` 无 `catch`**（`:206-214`）→ 403/失败时页面恒空白无提示。
⑦ **不存在的记录仍返回 HTTP 200 + `code:200`**（`TenantPackageController.java:39-42`、`:61-63`）→ 前端无法区分失败。
⑧ **返回形态不一致**：`GET /list` 用裸 `{records,total}`，其余 4 个用 `{code,data,message}`（`:29-31` vs `:40/:50/:62/:72`）。
⑨ **`update` 不校验必填**（`TenantPackageServiceImpl.java:49-58`）→ 可把名称/编码/购买类型改成空串。
⑩ **`packageCode` 无唯一性校验**（`:37-46`）→ 可建同编码套餐（对照注册链路的编码唯一校验，`TenantRegistrationService.java:74-78`）。
⑪ **无引用保护**（`:61-69`）→ 删除在用套餐无任何提示（且因无分配表，**当前也无法判断是否在用**）。
⑫ **无查询条件 / 无分页**：`GET /list` 无入参、返全量；前端 `:pagination="false"`（`:29`、`:40`）。
⑬ **无独立启停按钮**（`:49-53` 只有 tag）→ 改状态要进弹窗。
⑭ **未达金标准路线 A** + **平台级表未豁免多租户插件（红线本体）**：`sys_tenant_package` **不在** `IGNORE_TENANT_TABLES`，3 行 `tenant_id=0`，而运营侧会话租户可非 0 → **非超管运营账号访问本页会空白**。**当前被超管整体豁免掩盖（`SysUserServiceImpl.java:88` + `AiReadyTenantLineInnerInterceptor.java:41-44`），但配置脆弱**。修法：`@InterceptorIgnore(tenantLine="true")`；**切勿把本表加进白名单**（该表**有 `tenant_id` 列**，白名单化会让**所有租户读到全平台套餐**）。**验收必须专门断言「超管登录后本表能查到 ≥3 行」**（§10.1-②）。

### P2（8 条）

⑮ **价格为 0 显示成 `-`**（`:47` 的 `record.price ? …` 对 0 判 falsy）→ 「免费」与「未定价」不可区分；且与弹窗 `?? 0` 的口径不一致（§5.3）。
⑯ **`required` 仅视觉星号**：`purchaseType` 标必填却无校验；无 `rules`/`validate()`（`:83/:93/:101` vs `:237-240`）。
⑰ **`sort_order` 列存在、Service 按它排序，但弹窗无此字段**（`TenantPackageServiceImpl.java:27`）。
⑱ **`getById` 不带 `deleted` 条件**，而 `update`/`delete` 都带 → 同服务内口径不一致（`:33` vs `:51`、`:63`）。
⑲ **`create_by` / `update_by` 列存在但无任何写入逻辑**（`SysTenantPackage.java:61-65`）。
⑳ **主键用 `IdType.AUTO`（自增）**，与本系统其余表的雪花 ID 不同（`SysTenantPackage.java:19`）。
㉑ **无统计卡 / 无页内 Tab / 无导出 / 无快捷键 / 无行选择 / 无批量**；**`GET /{id}` 前端未接**，编辑走本地回填（`api/tenant.ts:172-174`、`:219`）。
㉒ **无本系统验收截图、无模块级 E2E**（README §7.3 末条）。
