## 1. 页面概述

### 1.1 与相邻页的分工（`61301 租户管理` 5 页极易混淆，必须写清）

| 页面 | 菜单ID | 回答的问题 | 数据源 | 数据结构 |

| **配额与用量分离** | 配额是**授权数字**、用量是**计量数字**，两者必须分离并可对账（SAP + AWS，**A**） | 上游勉强分离（`max_*` vs `used_*`），但 **`used_*` 无任何采集路径** → 数字是**死的** | **P0** 补用量采集（见下「落地」） |
| **维度** | 多维度：存储（数据/文件）/ 流量 / 数据库专属容量 / 用户席位 / API 调用 / 并发（用友 C + AWS C + SAP A） | 库里有 3 组（用户/存储/API 调用），**页面只用 API 调用算「使用率」** | **P1** 改为**按维度分别显示使用率**（字段已具备，**无需新增列**） |
| **计量方式** | 周期汇总（SAP 月末，**A**）/ 准实时 + 周期（AWS CUR，**B**） | **无计量** | **P1** 见「落地」的「准实时累加 + 每日对账」口径 |
| **超限处置三档** | ①**软告警 + 局部降级**（用友：文件上传失败 + 登录提示，**C**）；②**硬性不再分配**（SAP，属**授权层面**硬性，**不是运行时阻断**，**A**）；③**限流**（AWS usage plans，**C**） | **一档都没有**：库中有数字、页面有红进度条，**系统层面无任何响应** | **P0/P1** 首版建议**只做软告警 + 局部降级**（对标用友），**不做硬阻断**——硬阻断会因计量误差误伤客户 |
| **周期与计费联动** | SAP 月末按使用单位计费（**A**）；Stripe 的 Entitlements **本身不含 quota 对象**（第三方说明，**C**） | 无周期字段、无计费 | **P2** 需新增列 |
| **审计** | SAP SAL 记录权限/配置变更（**B**：https://help.sap.com/docs/SAP_NETWEAVER_701/6f51f5216c4b10149358d088a0b7029c/c769bcb7f36611d3a6510000e835363f.html ，2026-09-18，B） | 配额变更**零审计**（`sys_audit_log` 0 行） | **P0**（README §7.1 P0-17） |

### 8.5 落地建议（**区分 D 级推论，不得称业界标准**）

| 建议 | 级别 | 取舍理由 |
|------|:----:|---------|
| 表结构：`sys_quota_definition`（配额项定义：编码/名称/单位/是否硬限制）+ `sys_tenant_quota`（上限/已用/周期）+ 用量采集 | **D 级（本系统设计）** | 底稿 §1.5「落地」明确为建议，**两条表均不存在**；本系统当前只有 `sys_tenant_quota` 一张 |
| 计量口径：**准实时累加 + 每日对账** | **D 级（本系统设计）** | 底稿 §8.3：「**未找到任何厂商官方文档推荐实时精确计数**（也未反对）」→ 底稿推论的实时计数会引入锁竞争；**不得写成「业界通行做法」** |
| 超限处置：**首版只做软告警 + 局部降级** | **D 级（本系统设计）** | 理由：**硬阻断会因计量误差误伤客户**；「软告警 + 局部降级」有**用友 C 级实证**支撑，但降级范围由本系统自定 |
| **降配时已超限数据的处理**：存量只读不删 + 新建硬阻断 + 宽限期 + 降配预览 | **D 级（本系统设计，不是业界标准）** | 底稿 §9.1-9 明确：**「未找到任何厂商官方文档明文规定」**；仅可参照 SAP「配额用完 → 新子账户不再自动获得配额（**不追朔**）」（**A**）与用友「超量 → 功能受限但不全停（**软降级**）」（**C**）。取舍理由：**存量数据是客户资产，不可因降配而删除**；但**新建应受控**，否则配额形同虚设 |
| 超限模式枚举 `hard / soft / throttle`、周期枚举 | **D 级（本系统设计）** | 底稿 §8.3 的「给本系统的口径建议（D 级）」，**须标注为本系统设计** |

**明确不借鉴**：
- ❌ SAP 的**全局账户 / 目录 / 配额预留**模型（本系统租户**单层**，无预留概念）；
- ❌ Cloud Foundry 的**空间配额计划**二次切分（本系统无「空间」这一层）；
- ❌ AWS 的 **usage plans 按 tier 限流**作为首版方案（需先有可信计量）；
- ❌ 用友/SAP 的界面样式（README §5.3）。

**不发明字段承诺**：本页所有「建议字段」（`period` / `quota_mode` / `unit` / `quota_definition`）**均需新增列或新表**，文档不预先承诺字段名；**能不动表就实现**的两项是：(a) 表单改租户选择器 + 显式 `tenantId`（`tenant_id` 列已存在）、(b) 使用率按维度分别展示（`max_*`/`used_*` 列已存在）。

⑪ **弹窗字段逐项断言**：5 个 label 依次为 `租户名称 / 租户编码 / 最大用户数 / 存储配额 / API调用限制/月`；默认值依次为 `空 / 空 / 10 / 10GB / 10000`（`:148-154`）。
⑫ **断言弹窗无「租户」选择器**（`租户名称` 是 `a-input` 自由文本框）→ **P0-② 的 UI 证据**；并断言**不存在 `tenantId` 输入项**。
⑬ 🔴 **提交归属的端到端断言**：在弹窗里把「租户名称」填成一个**与任何真实租户都不同的名字**（如 `不存在的租户XYZ`）→ 提交 → 断言提示 `创建成功`；**直查 DB 断言新增行的 `tenant_id` = 当前会话租户（1）**、`tenant_name` = `不存在的租户XYZ` → **P0-① 的端到端证据**；**最后物理删除该行复原**。
⑭ **必填校验断言**：清空「租户名称」直接点确定 → 断言提示 `请填写租户名称和编码`；填了名称但清空编码 → 同样提示（`:202-205`）；**断言此时不发请求**（Network 0 请求）。
⑮ **删除断言**：点行内 `删除` → `a-popconfirm` 文案逐字 `确定删除?`（`:55`）→ 确认后断言提示 `删除成功` 且**该行从表格消失、不出现「已删除」状态**（物理删除）→ 与 §5.2 对账。
⑯ 页面控制台**无 `error`（含 `TypeError` / `ReferenceError`）** —— 参见记忆中的「重构搬迁后必须做运行时验证」；**另断言列表请求失败时页面无任何提示**（可临时改一个错误路径或断网验证 `:174-182` 无 `catch`）→ 登记 P1-⑧。

### 11.1 平台级参数 vs 租户级参数（**本页的必答项**）

| 维度 | 本页 | 归属 |
|------|------|------|
| 菜单 / 路由 / 组件 | `sys_menu`：`client_type='system-admin'`、`tenant_id=0`（实测 62005） | **平台级** |
| 主数据表 | `sys_tenant_quota`：**每行按 `tenant_id` 归属一个租户** → **行级是租户维度** | **平台级表 / 租户级行** |
| 参数存储格式 | **纯列**（无 JSON、无键值表）：12 列实测 | — |
| 由谁维护 | **平台运营方**（`client_type='system-admin'`，租户登录看不到本页） | **平台级** |
| 影响谁 | **租户的运行资源**（用户数 / 存储 / API 调用）→ 属**跨租户治理参数** | **平台级（作用到租户）** |
| 租户可否自改 | **不可以**（无租户侧入口；设置模块无「我的配额」页） | — |
| 权限码 | `system:tenant:quota`（菜单码）+ `platform:tenant-quota:*`（接口码，**未落库**） | **平台级** |
| 与套餐的关系 | 套餐（`sys_tenant_package`，平台级模板）**与本表零连线** → 目前**没有任何「租户级参数」的写入口径**（既非套餐派生，也非租户自配） | **平台级（链路缺失）** |

> **结论一句话**：本页是**纯平台级治理页**，其数据行按 `tenant_id` 落到具体租户；**当前既没有「租户可自改」的通道，也没有「套餐派生」的链路** —— 三条已知的租户级参数来源（套餐 / 人工 / 租户自配）中，**只有「人工」被实现，且实现时归属是错的**。

## 12. 剩余缺口（P0 / P1 / P2）

> 口径与《系统模块/README.md》§7 保持一致。README §7.1 **P0-15**（平台级表未豁免多租户）、**P0-17**（平台侧无审计）在本页的具体化见下。

### P0（5 条）

① **新增/编辑的租户归属是错的（本页最严重）**：弹窗**无 `tenantId` 字段**、「租户名称/编码」是**自由文本**（`:148-154`、`:81-93`），而 `sys_tenant_quota.tenant_id` **NOT NULL**（`V6.17.0:32-44`）→ 落库归属由**多租户插件按会话租户注入**（`MyBatisPlusConfig.java:233-245`）→ 「给某租户配额」变成「**给自己会话租户配额**」（超管会话恒为 1）；表单文本与落库归属**无任何校验关系**。
   建议：表单改**租户选择器** + 显式 `tenantId` + 服务端校验存在性；写别的租户行前 `setTempTenantId(tid)`。
② **`used_*` 没有任何采集路径**：`used_users` / `used_storage` / `used_api_calls` 全后端零更新调用，3 行数字来自 Flyway 种子（`V6.17.0:80-85`）→ **「使用率」永远是种子老值**，配额治理形同虚设。
   建议：按 §8.5 的「**准实时累加 + 每日对账**」（**D 级，本系统设计**）补采集；首版可先做「按天汇总」表 + 定时任务。
③ **超限无任何系统级处置**：`usedApiCalls > maxApiCalls` 只在页面把进度条变红（`:47`），**后端不告警、不阻断、不降级**；`sys_audit_log` 0 行 → 连"超限发生过"都无迹可查。
   建议：首版只做**软告警 + 局部降级**（对标用友 C 级实证），**不做硬阻断**（会因计量误差误伤客户）。
④ **权限码 4 个全部 0 行**：`platform:tenant-quota:list/create/update/delete` 在 `sys_permission`（264 行）中**均不存在** → **非超管平台账号对 5 个端点全部 403**；叠加**前端零 `v-permission`** → 按钮可见可点但必然失败。
⑤ **配额变更零审计（README §7.1 P0-17 的具体化）**：增/改/删**都不写审计**；`sys_audit_log` 实测 **0 行** → 「谁在什么时候把哪个租户的配额改成了多少」**事后不可还原**。建议按「时间 + 主体 + 来源 IP + 目标租户 + 变更项 + 前后值 + 结果」落审计。

### P1（8 条）

⑥ **平台级表未豁免多租户（README §7.1 P0-15 的具体化）**：`sys_tenant_quota` 不在 `IGNORE_TENANT_TABLES`（`:32-93`）→ **非超管平台账号被注入 `tenant_id=<会话租户>` → 3 行只剩 1 行（页面空白而非报错）**。**当前被超管整体豁免掩盖**（`SysUserServiceImpl.java:88` ＋ `AiReadyTenantLineInnerInterceptor.java:41-44` ＋ `MyBatisPlusConfig.java:157-167`），**但配置脆弱、红线仍在**。
⑦ **列表请求无 `catch`**：`fetchData` 只有 `try/finally`（`:174-182`）→ 接口失败时页面**恒空白且无任何提示**（对比：模块列表页至少 `catch` 成空数组）。
⑧ **错误分支丢弃后端原文**：`catch { message.error('操作失败') }`（`:217-219`）、`catch { message.error('删除失败') }`（`:229-231`）→ 用户看不到「没有操作权限」这类关键原因。
⑨ **「使用率」只算一个维度**：`calcUsagePercent` 只读 `maxApiCalls/usedApiCalls`（`:167-172`），而库中还有用户数、存储两组可比数字（`used_users`/`used_storage` **根本不展示**）→ **同一行数据存在 3 个可能的使用率，页面只呈现 1 个**。
⑩ **失败仍返 HTTP 200**：`GET /{id}`、`PUT /{id}` 在记录不存在时返回 `200 + code:200 + data:null`（`:39-42`、`:61-63`）→ 前端无法据状态码区分成败。
⑪ **无查询条件**（页面上零筛选项）：3 行尚可，租户上百后不可用。
⑫ **无分页 + 无列配置 + 无 `PageConfigPanel` + 无 `storage-key`**（`:40` `:pagination="false"`）→ 与 README §7.2「30 页全部无 `PageConfigPanel` / 无 `storage-key` / 无经典分页 / 无列配置齿轮」一致。
⑬ **种子数据与真实租户表不一致（脏数据）**：`V6.17.0:80-85` 写入的「默认租户/演示租户/测试租户」（`tenant_id=1/2/3`）与 `sys_tenant`（`1=系统租户`、`2=E2E验收租户2`、**无 3**）**对不上**；页面把这两列当事实展示。

### P2（5 条）

⑭ **删除是物理删除**：`deleteById`（`TenantQuotaServiceImpl.java:55-56`），无 `deleted` 列、无回收站 → 误删不可恢复（对比：`sys_tenant_menu` 是软删、`sys_module` 是逻辑删）。
⑮ **`max_storage` / `used_storage` 是字符串**：无数值单位换算与校验（`'10GB'` vs `'3GB'` 直接展示），未来做「已用/上限」计算需先解析。
⑯ **配额周期语义缺失**：列标题写「API调用限制/月」（`:124`），库中无周期列 → 语义仅存在于 UI 文案里。
⑰ **`getById` 端点已封装但零调用**（`api/tenant.ts:218-220`）→ 编辑用的是整行 `{...record}` 回填（`:187`），若列表数据过期则会用陈旧值覆盖。
⑱ **无验收截图资产 / 无模块级 E2E**（`tools/` 下不存在 `e2e-system-*.cjs`）→ README §7.3 已登记。
