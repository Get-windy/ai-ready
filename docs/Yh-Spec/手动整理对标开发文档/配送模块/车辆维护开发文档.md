## 1. 页面概述

- **维保台账页**：记录车辆保养、维修、年检、保险、事故等**维保事件**，是车辆全生命周期成本与合规的基础数据。
- 与《车辆管理》的关系：车辆档案存"当前状态/当前里程/到期日"，维保记录存"历史事件流水"，保养后需**回写车辆里程**并重算下次到期。

## 2. 本系统现状（实测）

### 2.1 页面结构（双模式）

### 2.5 字段问题（**提交丢数据**）

| 问题 | 证据 | 影响 |
|------|------|------|
| **`maintDate` 不在 `MaintenanceCreateDTO`**（`DTO:18-51` 无该字段） | 提交时**被静默丢弃** | 维保日期存不进去 |

### 2.6 其他

- 模板 `@search="handleSearch"` 绑定到 `useCrud` 的 `handleSearch`（`:51 / :406`），**未接收 `SearchBar` 的 `formData`**，查询条件实际不生效；页面里真正处理筛选的 `onSearch` / `onReset`（`:481-489`）成了**死代码**。
- 从《车辆管理》"维保记录"跳转时携带 `query.vehicleId`（`:762`），但本组件只读 `props.vehicleId` —— 若路由未做 `query → props` 映射，则**按车辆过滤会失效**（待确认）。

### 3.1 页面结构（金标准）

`CategoryListLayout` + `BillTableList`（序号齿轮列配置，`storage-key` = `dms-vehicle-maintenance-columns`）+ `PageConfigPanel`。

- **列**：维保单号、**车辆（车牌号，非 ID）**、维保类型、维保日期、内容、**费用**、厂商/服务商、**维保前/后里程**、**下次到期（日期或里程）**、经办人、附件、备注、操作。
- **查询**：车辆（选择器）、维保类型（多选）、维保日期范围、费用区间、厂商、是否含附件。
- **功能按钮**：新增维保、批量导出、**到期提醒**、刷新。
- **弹窗**：维保类型、车辆（选择器带出车型/当前里程）、维保前里程（默认带出车辆当前里程）、维保后里程、日期、内容、费用、厂商、**附件上传（发票/记录单照片）**、下次到期（按保养间隔自动推算）。

### 3.2 业务联动（关键）

| 联动点 | 规则 |
|--------|------|
| 回写车辆里程 | 维保后里程 > 车辆当前里程时，**更新车辆 `current_mileage`** |
| 重算下次到期 | 保养 → 按 `maintenanceIntervalKm`（车辆档案）推算下次保养里程；年检/保险 → 更新车辆的对应到期日 |
| 到期提醒 | 维保到期与证件到期统一进 `/vehicle/expiring`（见《车辆管理》） |
| 成本归集 | 维保费用按车辆/部门/期间汇总，供配送成本分析 |

### 3.3 后端接口（金标准）

| 接口 | 说明 |
|------|------|
| `GET /api/dms/vehicle/maintenance/page` | 多条件分页（**补车辆车牌联查、日期/费用/厂商条件**） |

| `PUT /api/dms/vehicle/maintenance/{id}` | 修改（现状缺失，只能删了重建） |
| `DELETE /api/dms/vehicle/maintenance/{id}` | 删除 |
| `GET /api/dms/vehicle/maintenance/stat` | 费用统计（按车辆/类型/月份） |
| `POST /api/dms/vehicle/maintenance/upload` | 附件上传（发票/记录单） |

### 3.4 业界生产级实践要点

1. **预防性维护**：按里程/时间双阈值自动排保养计划（而非事后登记），到期未保养进预警。
2. **一车一档**：维保、年检、保险、事故、违章统一进车辆档案时间轴，便于二手处置与保险理赔。
3. **成本可视**：单公里维保成本 = 期间维保费用 / 期间行驶里程，用于车辆经济性评估（对照《车辆管理》里程）。
4. **厂商与质保**：记录服务商与质保期，同一故障重复维修可追溯。
5. **凭证留档**：发票与结算单必须留存（财务对账、税务合规）。

## 7. 厂商档案引用升级（2026-09-13）

### 7.1 为什么改：纯文本厂商在生产级系统里是缺陷

成熟车队/资产管理系统（SAP PM 工单供应商 `LIFNR`、用友/金蝶车辆管理的「维修厂商」）里，**维修厂商是往来单位/供应商主数据的引用**，不是自由文本。纯文本的三个硬伤：

| 硬伤 | 后果 |
|------|------|
| 同一厂商多种写法（`XX修理厂` / `XX汽修` / 带空格） | 服务商成本分析失真、无法按厂商汇总 |
| 无稳定锚点 | 厂商改名后历史记录无法归并；无法与应付/发票/质保索赔对账 |
| 无法精确过滤 | 「查这家厂修过哪些车」只能名称模糊，命中不可靠 |

### 7.2 落地口径（引用 + 快照，不建重复主数据）

- **不新建「厂商档案」表**：厂商与《资料 → 往来单位》**同一主数据**（`biz_party`），DMS 侧只读引用，遵循「功能/模块不重复开发」红线。
- **`dms_vehicle_maintenance.vendor_id`**（可空）引用 `biz_party.id`；**`maint_vendor` 保留为名称快照**（列表/导出/打印零改动，历史数据仍可读）。
- **候选范围**：`party_type ∈ {2 供应商, 4 其他往来单位}`（客户、物流公司不入候选）；`status=1` 已启用、未删除。支持按**名称 / 编码 / 助记码**模糊，默认返回 20 条（上限 50）。
- **保存规则**：
  - 选了往来单位 → 校验其确为供应商/其他往来单位（否则 400），并以**档案名称**回填名称快照 —— 名称以档案为准，杜绝手输变体；
  - 未选（vendorId 为空）→ 按手工填写的名称记账（路边快修等未建档厂商），`vendor_id` 留空据实标注「未建档」。
- **查询规则**：选档案 → 按 `vendor_id` 精确过滤（厂商改名不影响历史命中）；直接输入 → 按名称快照模糊过滤。
- **费用统计新增「按厂商」口径**：已建档按 `vendor_id` 归并（改名后仍是同一厂商）、未建档按名称归并，并标注来源（档案/手工）——即服务商成本分析。
- **不自动回填厂商联系人/电话**：维保单上的联系人是**当次接待/师傅**，与档案主联系人常常不同，自动填充反而失真（成熟系统同样不在工单层自动带出供应商联系人）。
