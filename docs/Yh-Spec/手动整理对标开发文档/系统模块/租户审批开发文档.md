## 1. 页面概述

租户审批页是**平台运营方的租户准入工作台**：列出所有「待审批」的自助注册申请（企业名称 / 编码 / 联系人 / 电话 / 注册时间 / 状态），并逐行提供「**通过**」「**驳回**」两个动作。它是 `61301 租户管理` 组的第 2 页（`sort=200`），与《租户列表》**共用 `sys_tenant` 同一张表**。

**数据现状（devdb 实测 2026-09-18）——本页最关键的「数据现状」**：

```sql
-- 后端待审筛选口径（TenantRegistrationService.java:253-261）
select count(*) from sys_tenant
 where status = 0 and deleted = 0 and admin_user_id is not null;   -- → 0    ★
```

| 口径 | 实测值 | 说明 |
|------|:-----:|------|
| 待审口径（三项 AND） | **0** | **本页表格恒为空**（即使把 404 路径修好也一样） |
| `status = 0` | **1** | 仅 id=0，但它 `deleted = 1`（已逻辑删除）→ 被 `deleted=0` 过滤 |
| `admin_user_id IS NOT NULL` | 0 行满足 | 3 行中该列**全为 NULL** |
| `sys_tenant` 全表 | **3** | id=0（deleted=1）/ id=1 系统租户 / id=2 E2E验收租户2 |

> **⚠️ 口径漂移声明**：《系统模块/README.md》与本任务书核实时记录的是「`status=0` 共 **2 行**（id=0 已逻辑删除、id=2 的 `admin_user_id` 为 NULL）」；**本轮实测 `status=0` 仅 1 行**（并行会话期间 id=2 的 `status` 已被改为 1）。**两种取值下 `pending` 计数均为 0**，结论不变。
> **→ 本页的验收必须先经 `POST /api/tenant-registration/register` 造一条真实注册申请，否则「通过 / 驳回」按钮在界面上不可触达**（§10.1-⑩）。

### 3.8 数据获取与错误处理（`fetchData`，`:79-87`）

```ts
async function fetchData() {
  loading.value = true
  try {
    const res = await tenantApprovalApi.getPending()
    list.value = res.data || []
  } finally {
    loading.value = false
  }
}
```

**🔴 缺陷 P0/P1：`fetchData` 无 `catch`**（`:79-87` 只有 `try/finally`）→ 接口 **404 时页面无任何自身提示**，`loading` 复位、表格保持空表；错误只能靠全局 `request` 拦截器。**本页的「路径 404」正是靠这条静默通道被掩盖的** —— 用户看到的是一张**空白表**，而不是「接口不存在」。

**响应解包**：后端 `GET /pending` 返回 `Result.ok(List<SysTenant>)`（`:80-82`）→ 前端取 `res.data`（`:83`）→ **解包口径正确 ✅**（若路径修好即可正常渲染）。

## 5. 业务规范

### 5.1 状态值域（**本页最严重的语义矛盾**）

| 场景 | 值域 | 位置 |
|------|------|------|
| **表格状态列（页面实际表现）** | **恒为文案「待审批」+ `color="orange"`，不随数据变化** | `approval/index.vue:31-35` |
| **待审列表筛选口径（后端真源）** | `sys_tenant.status = 0` **且** `deleted = 0` **且** `admin_user_id IS NOT NULL` | `TenantRegistrationService.java:253-261` |
| 注册时写入的状态 | 租户 `status = 0`（注释「暂未启用（待审批）」，`:117`）；管理员用户 `status = 0`（禁用，`:129`） | 同上 |
| 审批通过后 | 租户 `status = 1`（`:170`）；管理员用户 `status = 1` 且 `is_tenant_admin = true`（`:180-181`） | 同上 |
| 驳回后 | `remark = reason`（`:228`）后 **物理删除租户行**（`:244`） | 同上 |
| **后端常量（死代码）** | `AuditStatus.PENDING = 1` / `APPROVED = 2` / `REJECTED = 3` | `TenantRegistrationService.java:54-63` |

**🔴 缺陷 P2-①：僵尸常量与真实口径互相矛盾**
`AuditStatus` 定义「待审 = **1**」，而真实待审口径是 `status = **0**`（`:256`）。全后端检索 `AuditStatus` **只命中定义处与私有构造器**（`:54-63`）→ **无任何使用点**，是一段**死代码**。
**后果**：任何读这段常量的人都会把「待审」理解成 `status=1`，而 `status=1` 实际是「**正常/已启用**」→ **语义方向完全相反**。这是一个**极易引发错误实现的陷阱**，必须删或改。

**🔴 缺陷 P0-②：`status` 二值无法区分「未审批」与「已禁用」**
`sys_tenant.status` 只有 `0/1`（`SysTenant.java:50`），而「待审」被复用为 `0`（`:117`）。《租户列表》的「状态」列把 `0` 显示成「**禁用**」（`list/index.vue:91-93`）→ **同一个 `0`，在两页有两个相反的含义**：
- 《租户审批》：`0` = **还没审**
- 《租户列表》：`0` = **已禁用**

且 `GET /pending` 的筛选条件是三项 AND（`status=0` + `deleted=0` + `admin_user_id IS NOT NULL`）→ 一个被**人工禁用**的租户（`status=0`、`deleted=0`，若它曾有 `admin_user_id`）**会重新出现在待审列表里**。这是本页与《租户列表》**共用一张表却各自定义状态语义**的直接后果。

### 5.2 流转规则（**含一处破坏性语义，必须写清**）

```
（自助注册）POST /api/tenant-registration/register
   └─▶ sys_tenant.status=0 + sys_user.status=0（管理员禁用）+ sys_user_tenant 关联 + admin_user_id 回填
          │
          ├─（本页「通过」）POST /{id}/approve
          │     └─▶ 租户 status=1；管理员启用 + is_tenant_admin=true；建 TENANT_ADMIN 角色；套权限模板；清权限缓存
          │
          └─（本页「驳回」）POST /{id}/reject
                └─▶ remark=reason → 删除管理员用户 → 删除 user-tenant 关联 → ★ tenantMapper.deleteById(tenantId)
```

| 动作 | 后端 | 前置校验 | 失败文案 | 副作用 | 行号 |
|------|------|:--------:|---------|--------|----|
| 注册 | `POST /register` | 编码唯一 / 名称唯一 / 用户名全局唯一 / 邮箱全局唯一 / 密码复杂度 | 各自明确文案 | 建租户（`status=0`）+ 建禁用管理员 + 建关联 + 回填 `admin_user_id` | `:72-154`（校验 `:74-107`；建租户 `:110-119`；建用户 `:121-134`；关联 `:137-144`；回填 `:146-148`） |
| 通过 | `POST /{id}/approve` | 租户存在且 `deleted != 1` | `租户不存在` | 租户 `status=1`；`remark` 写入（若传）；管理员启用 + `is_tenant_admin=true`；创建/复用 `TENANT_ADMIN` 角色；套系统默认权限模板；清权限缓存 | `:162-216`（状态 `:170`；备注 `:171-173`；管理员 `:176-184`；角色 `:186-196`；模板 `:198-208`；清缓存 `:210-213`） |
| 驳回 | `POST /{id}/reject` | 租户存在且 `deleted != 1` | `租户不存在` | `remark=reason`（`:228`）→ **删除管理员用户**（`:233`）→ **删除 user-tenant 关联**（`:235-238`）→ **物理删除租户行**（`:244`） | `:221-248` |

**🔴 缺陷 P0-③：驳回 = 物理删除，且界面上没有任何破坏性提示**

`TenantRegistrationService.reject()` 的最后一步是 **`tenantMapper.deleteById(tenantId)`（`:244`）**。注意：

- `SysTenant.deleted` 带 **`@TableLogic`**（`SysTenant.java:60-61`），但 `TenantRegistrationService` 的注释明写「**物理删除租户记录（注册未通过不保留）**」（`:243`）—— 这是**刻意**的物理删除（走 `deleteById` 的 `@TableLogic` 语义时会走逻辑删除，此处注释与行为需在实施时复核；**无论哪种，"租户被删除"这一破坏性后果成立**）。
- 同方法还**级联删除管理员用户**（`:233`，`sysUserMapper.deleteById`）与该用户的**租户关联**（`:235-238`）。
- **一旦驳回，租户与其管理员账号都不复存在**，且**无回收站、无二次确认、无原因输入**（§3.7）。
- 对比业界：jeecg 的租户删除**可从「回收站」恢复**；SAP 的删除**是真删数据但走显式"删除租用"动作**（§8.2）。**本系统的驳回复用了"删除"语义却没有任何提示**，这是本页最危险的一处。

**⚠️ 缺陷 P1：驳回的 `remark` 写在一个即将被删除的行上** —— `:228` 先 `setRemark(dto.reason())` 并 `updateById`（`:229`），随后同一事务里 `:244` 删掉该行 → **这个 `remark` 对被驳回的申请人永远不可见**（它随行一起消失）。**驳回原因在系统中无任何留存点**。

### 8.2 业界做法要点（逐条给级）

1. **「开通」是一串带状态的异步动作，不是一条 INSERT** —— SAP 租用向导**可能有多个步骤**（「如果应用提供者提供了附加租用配置输入参数，则向导包含多个步骤」），提交后返回**确认弹窗 + 状态跟踪表**（在「**实例和租用**」页跟踪状态），**激活后「转到应用程序」链接才可用**。**A**
2. **审批的关键卡点是「主体身份」而不是「业务信息」** —— 用友对新企业要求**企业认证**（含对公打款认证），并存在「**已认证企业转让**」「**企业认证变更**」这类**主体变更**流程。**B**（目录标题级）
3. **开通失败要能闭环** —— 用友 FAQ 目录含「激活时提示：您正在激活的产品订单对应的企业 XX 与当前企业帐号绑定的企业 XX 不一致，该如何处理？」「激活产品一直显示激活文件生成中怎么办？」「当前加密绑定的特征码已超过规定次数」→ 说明**激活码/特征码绑定**是这类系统的常见机器绑定机制。**B**（目录标题级）
4. **激活状态影响登录** —— 用友 FAQ「登录时提示：用户未激活，如何激活账号？」，即**租户/用户激活状态是登录链路的前置校验**。**B**
5. **邀请制优于代建账号** —— jeecg 新版不再弹窗选租户，改为「邀请加入 / 一人多租户 / 员工离职移出」。**A**
6. **业界不存在「统一状态机」**（底稿 §8.1 结论）—— 取到的硬事实三条：①**开通是异步多步**（SAP）；②**删除是真删**（SAP）或**删了还能从回收站恢复**（jeecg）；③**超量是「功能受限」而非「全停」**（用友）。**A／B／C**

### 10.1 接口验收（**24 项**）

**注册造数与基线（①–④）**

① `POST /api/tenant-registration/register`（**不带 `Authorization`**，`:39-45` 无注解）body 为完整 8 字段 → **期望 200**；断言 DB 新增 `sys_tenant` 1 行且 `status=0`、`deleted=0`、`admin_user_id IS NOT NULL`。
② 断言同一请求在 DB 中同时产生：`sys_user` 1 行（`status=0`）、`sys_user_tenant` 1 行 → **记录注册链路的真实副作用行数**。
③ **重复注册断言**：同 `tenantCode` 再提交 → **期望 400**，文案含 `租户编码已被占用`（`TenantRegistrationService.java:76-78`）。
④ **正则与长度校验**：`contactPhone` 传 `1234` → **期望 400**（`请输入有效的手机号码`）；`adminPassword` 传 6 位 → **期望 400**（密码复杂度，`TenantRegistrationService.java:103-107`）。

**待审列表与分页（⑤–⑨）**

⑤ `GET /api/tenant/pending`（**按前端现状发**，带 `admin`）→ **当前期望 404** —— **这是 §9.2-P0-① 的第一条可执行证据**。
⑥ `GET /api/tenant-registration/pending`（**按后端真实路径发**）→ **期望 200**，返回数组长度 = 直查 `select count(*) from sys_tenant where status=0 and deleted=0 and admin_user_id is not null`。
⑦ **「待审恒空」的原始事实断言（修复路径前）**：在**未造数**时断言该 SQL = **0**，且 `GET /pending` 也返回 **0 行** —— **契约一致，说明「空表」是数据问题不是接口问题**。
⑧ **超管可见性专项**：`GET /api/tenant/page`（《租户列表》的端点，本页不调，但同表）→ 断言 `total ≥ 2`（直查 `deleted=0` = 2）→ **证明租户插件未误注入**（红线②）。
⑨ **分页缺口断言**：`GET /api/tenant-registration/pending?pageNum=1&pageSize=10` → **当前期望参数被忽略**（端点无入参，`:80`）→ 仍返回全量 → 登记 P1 缺陷。

**审批通过链路（⑩–⑯）**

⑩ `POST /api/tenant-registration/{id}/approve`（`admin`，body 空）→ **期望 200**，文案 `租户已审批通过`（`:57`）。
⑪ **通过后的库断言**：该租户 `status=1`；`admin_user_id` 对应用户 `status=1` 且 `is_tenant_admin=true`；`sys_role` 新增/复用了 `role_code='TENANT_ADMIN'` 的行；`sys_user_role` 新增 1 行（`:170/180-181/186-196/190-196`）。
⑫ **权限模板套用断言**：断言新建角色在权限关联表中有行（来源 `sys_permission_template` 第 1 条，`:202`）；**并断言当 `sys_permission_template` 为空时接口仍返回 200 但角色零权限**（`log.warn` 不阻断，`:206`）→ 登记 P1 缺陷。
⑬ **幂等缺口**：对**已通过**的租户再次 `approve` → **当前期望 200（重复更新不报错）** → 登记 P2 缺陷。
⑭ `POST /{id}/approve` **带 body `{"remark":"E2E通过备注"}`** → 断言 `sys_tenant.remark` = 该值（`:171-173`）。
⑮ **通过后登录可用性**：用注册时的 `adminUsername` / `adminPassword` 调登录接口 → **期望 200**（对照 ⑯ 的审批前 403）。
⑯ **异常与鉴权**：对不存在的 id 调 `approve` → **期望 404**，文案 `租户不存在`（`:165-167`）；**不带 `Authorization`** 调 `approve` → **期望 401/403**（`:51`）。

**审批驳回链路（⑰–㉑）**

⑰ 另造一条申请，`POST /api/tenant-registration/{id}/reject` body `{"reason":"E2E驳回原因"}` → **期望 200**，文案 `租户注册已驳回`（`:70`）。
⑱ **🔴 破坏性语义断言（必须截图/留证）**：驳回后直查 `select count(*) from sys_tenant where id = <该id>` → **断言为 0**（行已被删除，`:244`）；并断言 `sys_user` 中该管理员用户已不存在（`:233`）、`sys_user_tenant` 关联已不存在（`:235-238`）。
⑲ **🔴 驳回原因无留存断言**：全库检索字符串 `'E2E驳回原因'`（在 `sys_tenant.remark` / 其它表）→ **断言 0 命中**（原因随行删除消失）→ **这是 §9.2-P0-⑤ 的可执行证据**。
⑳ **驳回原因必填断言**：body 传 `{"reason":""}` → **期望 400**，文案 `驳回原因不能为空`（`TenantRegisterDTO.java:74`）；body 传 `{"reason": "<201 字符>"}` → **期望 400**（`@Size(max=200)`）。
㉑ **驳回前状态前置**：对**已通过**的租户调 `reject` → 记录实际行为（当前会直接删掉一个已启用的租户 → **登记为高危 P0**）。

**权限、审计与复原（㉒–㉔）**

㉒ **权限断言**：用**非超管账号**调 `GET /api/tenant-registration/pending` / `POST /{id}/approve` / `POST /{id}/reject` → **期望 403**（`system:tenant:approve` 在 `sys_permission` 中 **0 行**）。**并断言** `select count(*) from sys_permission where permission_code = 'system:tenant:approve'` = **0**（当前事实）；补种子后改断言 = 1 且返回 200。
㉓ **审计断言（当前为缺陷登记）**：审批前后对比 `select count(*) from sys_audit_log` → **断言两次均为 0**（`sys_audit_log` 实测 **0 行**）→ 登记 P0「平台侧无审计」。修复后改为：断言审批后新增 1 行且含主体/时间/IP/目标租户/动作。
㉔ **「改库 → 回读 → 按原值复原」+ 清理**：取 id=1（系统租户）行，记录原 `tenant_name` / `status` / `remark` → 经**真实接口**（`PUT /api/tenant/{id}`）改名 → `GET /api/tenant/page` 回读断言新值 → 再经接口改回原值 → 回读断言复原（**全程不得直改 DB**）；**⑩–㉑ 造出的测试租户/用户/角色/关联必须逐条清理**（用专用 `E2E_*` 前缀便于识别），完成后断言 `sys_tenant` 回到 `deleted=0` **2 行**。

### 10.2 UI 验收（**18 项**）

① 菜单 `系统 → 租户管理 → 租户审批`（`62002`）点开直达本页（**单入口**，无标签跳转、无 `list_path`）。
② 面包屑逐字为 `首页 / 系统管理 / 租户审批`（`:6-14`），页面标题逐字 `租户审批`（`:15-17`）。
③ **页头无按钮**（`:3-20` 无 `page-header-right` 块）→ 断言本页**没有**「新增 / 刷新 / 导出」入口。
④ **断言本页没有查询区**（`a-card` 内直接是表格，`:22-57`）→ 无法按企业名称筛选（登记 P1）。
⑤ 表格 **7 列**渲染，列头逐字为 `企业名称 / 企业编码 / 联系人 / 联系电话 / 注册时间 / 状态 / 操作`（`:69-77`）。
⑥ **🔴 状态列写死断言**：造一条真实待审数据后，该行显示橙色 tag「待审批」；**再经接口把该租户 `status` 改成 1（或 2）后刷新页面 → 该行仍显示「待审批」**（`:31-35` 不读 `record.status`）→ **这是 §9.2-P0-② 的可执行 UI 证据**。
⑦ **🔴 哨兵断言（路径 404）**：打开页面（现网待审 0 行）→ **直接断言表格为空且无错误提示**；此时打开浏览器控制台 → **断言 `GET /api/tenant/pending` 返回 404**，而**页面没有任何提示**（`fetchData` 无 `catch`，`:79-87`）→ §9.2-P0-① 与 P1-⑨ 的联合证据。
⑧ **🔴 通过按钮 404 断言**：先经接口造一条待审数据并**刷新页面**（数据来自 `GET /pending`，仍 404 → 需临时用浏览器 devtools 注入 mock 或直改前端 baseURL 以便触达按钮）→ 点「通过」→ **断言请求 `POST /api/tenant/{id}/approve` 返回 404**，页面 toast「操作失败」→ 与 §6.1 对账。
⑨ **无二次确认断言**：点「通过」/「驳回」**不出现任何确认框**（无 `a-popconfirm`，`:38-52`）→ 与《租户列表》的删除按钮（有 popconfirm）形成对照，登记 P1。
⑩ **无驳回原因输入断言**：点「驳回」**不出现弹窗**（全页无 `a-modal`）→ 断言 Network 里提交的 body 恒为 `{"reason":"驳回"}`（无论点哪一行）→ **这是 §9.2-P0-③ 的可执行证据**。
⑪ **无分页断言**：造 ≥ 21 条待审数据（`pageSize` 默认无关，因为 `:pagination="false"`）→ 断言**所有行一次性渲染、页面无分页控件**（`:28`）。
⑫ **「操作」列固定右侧**（`fixed:'right'`，`:76`）且仅含「通过」「驳回」两个 link 按钮。
⑬ **超管可见性专项（红线②）**：`admin` 登录 → 断言本页表格**渲染 0 行是正确的**（待审口径为 0，§2），**不得据此判红线②复发**；红线②的判断依据是 ⑧ 的 `GET /api/tenant/page` ≥ 2 行（§10.1-⑧）。
⑭ **审批前登录被拒断言**：用刚注册的 `adminUsername` / `adminPassword` 登录 → **断言失败**（管理员 `status=0` 被拒）；通过审批后再登录 → **断言成功**（`:129` vs `:180-181`）→ 证明「激活状态影响登录」这条**业界口径本系统已实现**。
⑮ **🔴 驳回破坏性 UI 证据**：造一条申请 → 点「驳回」→ 提示「已驳回」→ 到《租户列表》页查找该租户 → **断言已不存在**（物理删除）→ 截图并存证（§5.2）。
⑯ 断言页面**无统计卡 / 无 Tab / 无导出 / 无快捷键**（全文）。
⑰ **用另一账号（非超管）登录**，确认本页**仍然可见可点**（无 `v-permission`）→ 但点击后接口 **403**（`system:tenant:approve` 0 行）→ **「按钮可见但点了 403」是 §9.2-P0-⑥ 的可执行证据**。
⑱ **页面控制台无 `error`**（含 `TypeError` / `ReferenceError`）—— 参见记忆中的「重构搬迁后必须做运行时验证」；并用 Network 面板**逐个记录本页发出的 3 个请求的状态码**（当前预期全部 404）。

## 12. 剩余缺口（P0 / P1 / P2）

> 口径与《系统模块/README.md》§7 对齐。README §7.1-P0-15（平台级表未豁免）、P0-17（平台侧无审计）、**§7.2「租户审批 3 端点前缀不匹配 404」**在本页的具体化见下。

### P0（8 条）

① **3 个调用路径前缀不匹配 → 必然 404**（README §7.2 已登记）：前端 `/api/tenant/{pending,{id}/approve,{id}/reject}`，后端是 `/api/tenant-registration/*` → **通过/驳回两个按钮都不可能成功，列表恒空**。证据：`api/tenant.ts:114-126` vs `TenantRegistrationController.java:30/50/63/76`。**修法：改 3 处前缀。**
② **状态列写死「待审批」**：`:31-35` 不读 `record.status`、无分支；列定义 `:75` 的 `dataIndex` 被槽位覆盖失效。
③ **驳回原因是写死常量 `'驳回'`**：`:101`，且全页无弹窗、无输入 UI（后端 `Reject.reason` 却是 `@NotBlank`）。
④ **驳回 = 物理删除租户 + 级联删除管理员用户 + 删除用户-租户关联**（`:233`、`:235-238`、`:244`），**无二次确认、无破坏性提示、无回收站**；且对**已通过**的租户调 `reject` 也会走同一路径。
⑤ **驳回原因零留存**：`:228` 写入的 `remark` 随后被 `:244` 的删除一并抹去 → 被驳回的申请人**永远看不到理由**。
⑥ **零权限控制 + 权限码 0 行**：前端无 `v-permission`；`system:tenant:approve` 在 `sys_permission`（264 行）中 **0 行** → **非超管即使路径修好也 403**（404 与 403 双重不可用）。
⑦ **平台侧写操作零审计**（README §7.1-P0-17 的具体化）：通过/驳回均不写审计；`sys_audit_log` 实测 **0 行**。
⑧ **无审批流水载体**（无 `sys_tenant_approval`）：通过时 `remark` 只保留最后一次，驳回时零痕迹；**无审批历史可查、无审批人留痕**。

### P1（8 条）

⑨ **`fetchData` 无 `catch`**（`:79-87`）→ **404 被静默**，用户只看到空表，看不到「接口不存在」。
⑩ **无二次确认**（`:38-52` 直调）→ 误点即提交。
⑪ **无查询条件 / 无分页 / 无工具栏**（`:22-57`、`:28`）：`GET /pending` 也没有任何入参（`:80`）→ 大租户量下**全量返回**。
⑫ **审批通过不分配套餐 / 不授权模块 / 不写配额**（`:162-216`）→ 新租户**开箱即空**，需到 62003/62004/62005 手工补。
⑬ **权限模板只取第一条**（`:202`），模板为空时只 `log.warn`（`:206`）→ **「审批通过但零权限」**。
⑭ **无审批详情下钻**：注册时填 8 个字段，本页只显示 4 个（缺联系邮箱、管理员用户名、管理员邮箱、地址）。
