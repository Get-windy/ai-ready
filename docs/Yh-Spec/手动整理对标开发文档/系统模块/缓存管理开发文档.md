## 1. 页面概述

缓存管理页是平台运营方的**缓存看板与控制台**：展示缓存总大小 / 缓存键数量 / 命中率 / 过期键四个概览指标，按「缓存区域」列出键数量、内存占用、命中率、TTL，支持查看某区域的缓存键列表，并提供**三级清空能力**（清空全部缓存 / 清空单个区域 / 删除单个键）。

**一句话结论：本页是「假数据 + 真破坏」的危险组合** —— 概览与键列表**全部是后端硬编码常量或按公式现生成**（与真实 Redis 无任何关联），但三个**删除类**接口是**真实的 Redis 操作**，其中 `DELETE /api/cache/all` 会 `keys("*")` 整库清空，**连 sa-token 的登录会话一起删掉，把当前所有在线用户（含操作者自己）立即踢下线**。

**🔴 两个"操作后回显"缺陷（P1）**：

**① 删除键后键会「复活」**：`deleteKey` 成功分支（`:274-275`）重新调用 `viewCacheKeys` → `GET .../keys`，而后端 `getRegionKeys` 是**按公式现生成**的（`CacheManageController.java:152-160`），**生成规则固定** → **刚删掉的键原样再次出现**。
只有进入 `catch` 分支（`:277-278`）时才会在前端 `filter` 掉该键（**而那时显示的却是「已模拟删除缓存键」**）。

**② 清空后界面数值纹丝不动**：`clearRegion` / `clearAllCache` 成功后都调用 `fetchCacheStatus()`（`:237`、`:248`），但 `/api/cache/status` 返回的是**硬编码常量**（`CacheManageController.java:31-41`、`:58-66`）

（`CacheManageController.java:31-41` 的 `REGIONS` 是 `static final List.of(...)` **常量，无法被修改**。）
→ **后果**：用户以为"没生效"，**反复点击清空** → **每点一次都是真实的 Redis 删除**。

### 5.2 真实缓存里装的是什么（**决定了"清空全部"为什么危险**）

`redis-cli -n 0 KEYS "*"` 的实际内容（节选）：`Authorization:login:session:<雪花id>`、`Authorization:login:token:<uuid>`（**共 101 个**）、`Authorization:login:last-active:<uuid>`、`sys:config:history:expense.approval.level1.approverId`、`permission:user:1`、`role:user:1`、`rate_limit:ip:0:0:0:0:0:0:0:1`、`rate:limit:0:0:0:0:0:0:0:1:global`。

**⚠️ 同一 Redis DB 混装了两类数据**：

| # | 数据类 | 键前缀 | 来源 | 键数（实测） |
|:-:|-------|-------|------|:----------:|
| 1 | **sa-token 的登录会话** | `Authorization:login:*` | `core/base/core-base/pom.xml:66-69` 引入了 `sa-token-redis-jackson`（`:68`）→ sa-token 的 `SaTokenDao` 走 Redis，落点即 `application-dev.yml:24-28` 指定的 **db0**（`database: 0`） | **101**（`KEYS "Authorization:login:*"`） |
| 2 | **本系统业务缓存** | `sys:config:*`、`permission:user:*`、`role:user:*`、`rate:limit:*`、`rate_limit:*` | 系统自身缓存与限流 | 其余（117 − 101 = **16**） |

**🔴 因此 `DELETE /api/cache/all` 的完整后果链**：

```

```

> **⚠️ `keys("*")` 不是前缀匹配，是整库 glob** —— 这是本页最危险的三个字。

### 5.3 「缓存区域」的假名与真删除的错位

页面上 9 个「缓存区域」名（`user:info` / `user:perms` / `sys:config` / `dict:data` / `menu:data` / `dept:data` / `product:data` / `customer:data` / `order:data`，`:180`）**来自后端常量**；而「清空区域」走的是 `cacheService.deleteByPattern(name + ":*")`（`CacheManageController.java:91-95`）→ **用假名字去删真键**：

| 操作 | 传入的 pattern | 能否匹配到真实键 | 结果 |
|------|--------------|:--------------:|------|
| 清空 `sys:config` 区域 | `sys:config:*` | ✅ **能**（真实存在 `sys:config:history:*`） | **真删了业务缓存**（而这些键在页面上看不到） |
| 清空 `user:info` 区域 | `user:info:*` | ❌ 不能 | **什么都没删**，但界面报成功 |
| 清空 `dict:data` / `menu:data` / `dept:data` / `product:data` / `customer:data` / `order:data` | 对应 `:*` | ❌ 不能 | 同上 |
| 清空 `user:perms` | `user:perms:*` | ❌ 不能（真实是 `permission:user:*`） | 同上 |
| 查看键（9 个区域任一） | — | — | **显示按公式合成的假键名**（`:152-160`） |
| 删除某个「键」 | `delete(key)`（`:170-172`） | ❌ **几乎必然失败**（假键名在 Redis 里不存在） | 但**前端走 catch 弹「已模拟删除缓存键」**（`:276-279`） |

> **🔴 结论**：**「清空区域」在 9 个区域中有 8 个是"空动作"（假成功），1 个（`sys:config`）会真删业务缓存而用户不知情**；「删除键」**几乎全部失败但显示成功**；「清空全部」**真的会清空整库并踢人下线**。

## 8. 业界对标

> **本页在 ql361 无对应页**（§2）。本章只写**业界能力对标**，逐条标来源与可信度级别。**凡底稿标 D 级的方案，本文件一律写「本系统设计」而非「业界标准」。**

### 8.1 业界叫法

**Spring Boot Actuator `/actuator/caches`**（+ `/actuator/caches/{cache}` 可清空单个缓存）；**Redis `INFO` 命令的 `keyspace` 段**。

### 8.2 业界做法要点

1. **缓存清单与逐缓存清空是框架内置能力**：Actuator `caches`「暴露可用的缓存」—— **注意官方端点表里 `caches` 是"技术无关端点（默认可用）"，不需要额外依赖**。
2. **Redis 的 key 空间是分库统计的**：`INFO` 的 `keyspace` 段「提供主字典中每个数据库的统计。统计内容是**键的数量**与**带过期时间的键的数量**」，每个库一行：`dbXXX: keys=XXX,expires=XXX,avg_ttl=XXX,subexpiry=XXX`。
3. **内存指标要区分「数据集」与「开销」**：`used_memory_dataset`（数据集大小 = `used_memory` - `used_memory_overhead`）、`used_memory_dataset_perc`、`used_memory_overhead`、`used_memory_startup`、`total_system_memory`。
4. **命中率指标**：`keyspace_hits` / `keyspace_misses`（「主字典中成功/失败查找的次数」）—— **这是"缓存是否有效"的唯一原生依据**。
5. **淘汰与容量**：`evicted_clients`、`evicted_scripts`、`total_eviction_exceeded_time`、`current_eviction_exceeded_time`（「`used_memory` 超过 `maxmemory` 以来的毫秒数」）—— **超时时间非 0 就说明缓存在被挤压**。
6. **更多可用的信息段**：`INFO` 支持按段查询（`INFO [section [section ...]]`），段名包括 `latencystats`、`keysizes`（「按数据类型统计键大小分布」，基数 2 的对数直方图）、`errorstats`、`hotkeys`、`cluster`、`modules` 等。
   > **⚠️ 补充（官方 `MEMORY USAGE` 文档，A 级）**：单键的 `MEMORY USAGE key [SAMPLES count]`在 `SAMPLES 0` 时会给出精确值但**可能阻塞**；默认 5 个样本是**近似值**。**单键大小查询不是零成本操作。**
7. **`KEYS` 不是生产用法**：Redis 官方对 `KEYS` 的定位是"调试命令"，**生产应使用 `SCAN`** 做渐进式遍历（避免阻塞单线程）。本系统 `CacheService.deleteByPattern`（`:422-428`）用的正是 `redisTemplate.keys(pattern)` → **生产风险**。

> ③ **只做静态断言**（断言 `deleteByPattern("*")` 的调用路径存在，不实际触发）。
> **⚠️ 禁止在共享 dev 环境的 db0 上直接跑"清空全部"用例** —— 会误伤并行会话（参见记忆中的「按进程名杀进程会误杀并行会话」「共享环境端到端验证要点」两条教训）。

### 10.1 接口验收（24 项）

**可达性与响应形态（①–④）**

① `GET /api/cache/status`（带 `admin` Bearer）→ **期望 200**（包 `cn.aiedge.cache` 已装配，`AiReadyApplication.java:23`）。
② 断言返回体为 `{code: 200, data: {...}, message: "ok"}` 的**包装形态**（`CacheManageController.java:84`），且 `data` 含 `totalSize` / `totalKeys` / `hitRate` / `expiredKeys` / `regions`。
③ 断言不带 Authorization 调 `/status` → **期望 401/403**（全局登录拦截，`SaTokenConfig.java:70-71`）。
④ 同批断言 5 个端点**全部非 404**：`/status`、`/region/{name}`、`/all`、`/region/{name}/keys`、`/region/{region}/key/{key}`（**本页无 404 风险**，与本组《接口监控》相反）。

**🔴 假数据断言（⑤–⑩）—— 本页最重要的一组**

⑤ 🔴 **常量断言**：`GET /status` **连调 3 次（间隔 >5 秒）** → 断言 `totalKeys` / `totalSize` / `hitRate` / `expiredKeys` / `regions[]` **完全不变**（`:31-41`、`:58-66` 是 `static final` 常量）。
⑥ 🔴 **与 Redis 真值对账（核心证据）**：
   - 直连 Redis：`redis-cli -n 0 DBSIZE` → **117**；`INFO keyspace` → `db0:keys=117,expires=114,avg_ttl=4785760`；`INFO memory` → `used_memory_human:807.77K`；`INFO stats` → `keyspace_hits:4376460`、`keyspace_misses:6623`。
   - 断言 `/status` 的 `totalKeys` **不等于** 117（实测为 **2840**）；
   - 断言 `expiredKeys` **不等于** 114（实测为 **32**）；
   - 断言 `totalSize` **不等于** `807.77K`（实测为 **`"156.3 MB"`**）。
   → **三条不一致即证明 P0-1**。
⑦ 🔴 **命中率对账**：真实命中率 = `4376460 / (4376460 + 6623)` = **99.85%**；断言 `/status` 的 `hitRate` **不等于** 99.85（实测 **88.2**）。
⑧ 🔴 **区域名对账**：`redis-cli -n 0 KEYS "*"` 的真实前缀为 `Authorization:login:*`(101) / `sys:config:*` / `rate:limit:*` / `permission:user:*` / `role:user:*`；断言 `/status` 返回的 9 个 `regions[].name`（`user:info`/`user:perms`/`sys:config`/`dict:data`/`menu:data`/`dept:data`/`product:data`/`customer:data`/`order:data`）**至少 6 个在真实键空间里不存在**。
⑦ 🔴 **假键列表断言**：`GET /api/cache/region/user:info/keys` → 断言返回的键名形如 `user:info:1`、`user:info:2`…（`CacheManageController.java:155` 的 `name + ":" + i`），并在 Redis 中 `EXISTS user:info:1` → **断言返回 0（不存在）** → **证明列表是合成的**。
⑩ 🔴 **假类型/大小断言**：断言返回项的 `type` 只出现 `hash`/`string`/`set` 三种且按 `i % 3` 循环（`:156`）、`size` 恒为 `256 + (i*37) % 4096`（`:158`）、`ttl` 为 `ttl - (i*13) % ttl`（`:159`）→ **规律性即假数据证据**。

**🔴 危险操作（⑪–⑯，**慎执行**）**

⑪ **静态断言（安全）**：断言 `CacheManageController.java:114-116` 的 `cacheService.deleteByPattern("*")` 调用路径存在；断言 `CacheService.java:422-428` 用的是 `redisTemplate.keys(pattern)`（**整库 glob，非前缀匹配**）。

## 12. 剩余缺口（P0 / P1 / P2）

> 与《系统模块/README.md》§7 口径一致。README §3.4 P0-4、§7.1 P0-4（缓存管理后端返假数据，但 `DELETE /api/cache/all` 真清 Redis）在本页的具体化见下。

### P0（6 条）

① **读是假的（README §3.4 P0-4 之①）**：`/api/cache/status` 的缓存区域 / 键数量 / 内存 / 命中率 / TTL / 过期键**全部写死或按公式现生成**（`CacheManageController.java:28-41`、`:58-66`，注释逐字「模拟的缓存区域数据」），`/region/{name}/keys` 的键列表同样是公式合成（`:139-162`）。**与真实 Redis 全部对不上**（真值：**117 键 / 807.77K / 99.85% / 114 过期键**）。建议：改读 `INFO keyspace` / `memory` / `stats`。
② **写是真的且危险（README §3.4 P0-4 之②）**：`DELETE /api/cache/all` → `cacheService.deleteByPattern("*")`（`:111-122`）→ `redisTemplate.keys("*")` **整库 glob**（`CacheService.java:422-428`）→ **删掉全部 117 个键（含 101 个 sa-token 会话）→ 把当前所有在线用户（含操作者自己）立即踢下线**。建议：① 会话迁独立 DB / 加白名单前缀；② 清空前做影响面预览 + 确认串。
③ **5 端点零权限 + 未纳入注册表 + 无权限码**（`CacheManageController.java:20-22`；`PermissionInitializationConfig.java` grep 零命中；`sys_permission` 中 `system:monitor%` **0 行**）→ **任何已登录用户可清空整库**。建议：补权限种子 + `@SaCheckPermission` + `v-permission`。
④ **前端"失败也报成功"三连（绿色成功提示）**（`cache/index.vue:238-241`、`:249-252`、`:276-279`，含「已模拟…」文案与**本地伪造删除成功**）→ **用户永远不知道操作是否真的生效**。建议：删除"模拟"分支。
⑤ **前端 `Math.random()` 造假数据**（`:211-224`、`:262-267`，注释逐字「如果后端还未实现缓存管理API，使用默认显示数据」）→ **接口失败时页面显示随机数值，且每次刷新都不同**。建议：删除随机兜底，改错误态。
⑥ **破坏性操作无任何影响面保护**：`/all` 无 dry-run、无预览、无确认串、无白名单；popconfirm 文案「确定清空全部缓存?」**不告知会删除登录会话**（`.vue:88-97`）。建议：按 §8.4「本系统设计」补齐。

### P1（10 条）

⑦ **删除键后键会「复活」**（`.vue:274-275` 重拉 × `CacheManageController.java:152-160` 公式）。
⑧ **清空后界面数值纹丝不动**（`.vue:237`、`:248` 重拉 × `CacheManageController.java:31-41` 的 `static final` 常量）→ **用户误判"没生效"而反复点击**（每次都真删）。
⑨ **「清空区域」用假区域名删真键**：9 个区域中 **8 个是空动作**、**1 个（`sys:config`）会误删真实业务缓存**（`.vue:112-117` × `CacheManageController.java:93-95`）。
⑩ **「缓存总大小」卡的 `a-statistic` 字符串陷阱**：后端返回 `"156.3 MB"` 非数值串被 `:value` 直吃（`.vue:42-45`；`CacheManageController.java:78`）→ 可能显示 `NaN`/`0`。建议：改 `:formatter`。
⑪ **后端遍历用 `KEYS` 不是 `SCAN`**（`CacheService.java:422-428`）→ 生产阻塞风险。建议：`SCAN` + 分批 `DEL`/`UNLINK`。
⑫ **无 `INFO` / `SCAN` / 单键详情端点**：`keyspace_hits` / `keyspace_misses` / `used_memory_*` / `evicted_keys` / `maxmemory` / `TYPE` / `TTL` / `OBJECT ENCODING` / `MEMORY USAGE` 全部无出口（§6.4）。
⑬ **「区域存在性」查的是常量表**；不存在时返回 `"success", false` 但 **HTTP 仍是 200**（`CacheManageController.java:97-103`）。
⑭ **未达金标准路线 A**：无 `ErrorBoundary`、无布局组件、**两张裸 `a-table`**、无列配置齿轮、无 `PageConfigPanel`；键表是**前端分页**（`.vue:2-34`、`:100-121`、`:131-148`）—— 与 README §7.2 一致。
⑮ **无查询条件**：无按 key 前缀搜索、无按类型/TTL 筛选 → **实测 117 个真实键无从查找**（全页无 `a-form`）。
⑯ **无淘汰/容量水位预警**：`evicted_keys`（实测 **0**）/ `maxmemory` / `current_eviction_exceeded_time` 未读（§6.4 第 8 条）。

### P2（4 条）

⑰ **`@Autowired(required = false)` 的防御性写法实际失效**：`CacheService` Bean 确定存在（`CacheService.java:18` `@Service`）→ 三处 `if (cacheService != null)`（`:93-95`、`:114-116`、`:170-172`）恒真 → **给人"可能为 null 所以安全"的错觉**。
⑱ **无自动刷新**（无轮询，`:155`、`:282`）→ 缓存指标不自动更新。⚠️ **建议在修好真实数据之后再补**（当前加了会更困惑）。
⑲ **页面无任何 Actuator 能力**：`application.yml:136` 未暴露 `caches` → 业界"零成本"的缓存清单与逐缓存清空**当前不可用**。
⑳ **无本系统验收截图、无模块级 E2E**（README §7.3 末条）；且本页的 E2E **必须先解决"隔离环境"问题**（因为 §10.1-⑬ 会真清库并踢人），**这是本模块唯一一个"验收本身有环境风险"的页面**。
