## 1. 页面概述

本页管的是**末端收款**：配送员送货上门时向客户收取的钱，分两类且**科目不同**：

| 类型 | 含义 | 资金归属 |
|------|------|---------|
| **代收货款**（COD） | 代商家/平台向客户收取的商品款 | 代收 → 需**上交**企业/商家 |
| **配送费** | 向客户收取的配送服务费 | 企业**收入** |

## 2. 本系统现状（实测）

### 2.1 后端接口（`PaymentController`，`/api/dms/payment`）

| 方法 | 路径 | 参数 | 说明 |
|------|------|------|------|
| POST | `/qrcode` | `taskId`、`amount` | 生成收款二维码 |
| POST | `/confirm` | `taskId`、`paymentType`(1 微信/2 支付宝/3 现金/4 其他)、`amount`、`externalOrderNo` | 确认收款 |

| 操作 | 弹窗字段 | 调用 |
|------|---------|------|

| 确认收款 | 支付方式、收款金额、外部订单号 | `POST /confirm` |

## 3. 金标准目标设计

### 3.1 页面结构（金标准）

`CategoryListLayout` + Tab + `BillTableList`（`storage-key` = `dms-payment-columns`）：

1. **收款台账**（主）：任务编号、客户、配送员、收款类型（代收货款/配送费）、应收、实收、支付方式、支付状态、**收款时间**、外部流水号、**交款状态**（未交/已交）、操作。
2. **未付管理**：标记未付的单据 + 催收/核销记录。
3. **交款稽核**：按配送员/日期汇总"应上交 vs 已上交"，差异清单（资金安全核心）。
4. **支付流水**：支付平台流水导入与自动匹配。

工具栏：页面配置 / 刷新 / 导出 / 批量确认（线下）/ 流水导入。

### 3.2 收款方式与状态

| 项 | 取值 |
|----|------|
| 收款类型 | 1 代收货款 / 2 配送费（**与实体 `paymentType` 对齐**） |
| 支付方式 | 微信 / 支付宝 / 现金 / POS / 银行转账 / 其他 |
| 支付状态 | 0 待支付 → 1 已支付 ／ 3 未付（挂账） ／ 2 已退款 |
| 交款状态 | 未交 / 部分交 / 已交（现金与线下收款特有） |

### 3.3 后端接口（金标准）

| 接口 | 说明 |
|------|------|
| `GET /api/dms/payment/page` | 收款台账分页（多条件 + 联查任务/客户/配送员） |
| `POST /api/dms/payment/qrcode` | 生成收款码（**接真实支付渠道**） |
| `POST /api/dms/payment/callback` | **支付回调**（验签 + 幂等，自动置已支付） |
| `POST /api/dms/payment/confirm` | 线下收款确认（现金/POS） |
| `POST /api/dms/payment/mark-unpaid` | 标记未付（挂账） |
| `POST /api/dms/payment/{id}/handover` | **交款登记**（配送员上交企业） |
| `GET /api/dms/payment/handover/summary` | 交款稽核汇总（应上交 vs 已上交） |
| `POST /api/dms/payment/reconcile` | 与支付平台流水对账 |
| `POST /api/dms/payment/push-finance` | 推送财务生成收款单/核销应收 |

### 3.4 业务规范与注意事项（**重点**）

1. **代收货款必须与配送费分开记账**：前者是**负债（代收）**，后者是**收入**；ERP 科目不同，合并会做错账。
2. **资金安全（最容易出事的地方）**：
   - 配送员代收有**限额**（单笔/单日/累计）——超限需强制扫码支付或改由财务专户收款；
   - **交款时限**（如当日 24:00 前上交或次日 10:00 前），超时预警/停派单；
   - 现金收款必须**登记 + 稽核**，扫码收款走平台自动对账更安全。
3. **支付回调必须幂等**：以 `externalOrderNo` 或平台流水号做幂等键，避免重复置账。
4. **命名歧义要修**：接口的 `paymentType`（支付方式）建议改名 `payChannel`，与实体 `paymentType`（收款类型）区分；**前端已按此约定展示**（`PAY_CHANNEL_MAP`）。
5. **状态不可逆**：已支付 → 退款需走退款流程（生成退款单），不得直接改回待支付。
6. **未付（挂账）**：必须关联客户信用/后续催收，与《收款单》《按单收款》核销闭环。
7. **对账**：支付平台日终流水与系统记录**逐笔核对**，差异当日处理（时间差/掉单/重复）。
8. **凭证留存**：扫码支付保留平台交易号；现金保留签收凭证与配送员确认记录。
9. **隐私合规**：金额与客户信息属敏感数据，台账导出需权限控制与审计。

## 6. 本系统落地实现（✅ 2026-09-13）

### 6.1 名词口径（消除歧义）

| 概念 | 字段 | 取值 | 说明 |
|------|------|------|------|
| **收款类型** | `paymentType` | 1 代收货款 / 2 配送费 | **科目不同**：代收货款是负债（需上交），配送费是收入 |
| **支付方式** | `payChannel` | 1 微信 / 2 支付宝 / 3 现金 / 4 POS / 5 银行转账 / 9 其他 | 记录"客户怎么付的" |
| 支付状态 | `status` | 0 待支付 → 1 已支付 ／ 3 未付（挂账） ／ 2 已退款 | 状态不可逆（退款走退款流程） |
| 交款状态 | `handoverStatus` | 0 未交 / 1 部分交 / 2 已交 | 现金与线下收款特有 |

### 6.2 收款码（配置化，杜绝假二维码）

- 配置键 `dms.payment.qrcode.base-url`（`dms_config`，`tenant_id=0` 全局缺省）。
- **未配置** → `qrcodeUrl = null`，前端明确提示「未开通扫码收款，请使用现金/POS 等线下方式收款后点『确认收款』」；**不再返回任何示例域名**。
- **已配置** → 生成 `baseUrl?amount=<金额>&ref=<任务编号>` 的真实收款码地址。

### 6.3 收款与回调

- `POST /confirm`：线下收款确认（现金/POS/银行转账），记录支付方式、实收金额、外部单号；收款类型可按任务代收货款自动推断。
- `POST /callback`：线上支付回调，**幂等**（`tradeNo` 为幂等键）：重复回调直接返回既有记录（`idempotent=true`），不重复置账。

### 6.4 资金安全：交款与稽核

- `POST /{id}/handover`：交款登记（累计金额达应收 → 已交；否则部分交）；金额必须 > 0；仅已支付记录可交款。
- `GET /handover/summary`：按配送员汇总「应上交 / 已上交 / 未上交 / 未交清笔数」——稽核差异一目了然。
- 台账列「交款状态 / 已上交 / 交款人」，汇总条展示「待上交」金额（红字提示）。

### 7.2 未付管理（挂账闭环，§3.1-2 / §3.4-6）

- **挂账金额口径修正**（本轮修的真实缺陷）：`mark-unpaid` 新建记录时未写金额 → 挂账金额恒为 0；现按**任务应收 = 代收货款 + 配送费**补齐（`taskDue()`），`callback` 缺金额时同口径兜底。
- `POST /{id}/urge` 催收登记（说明必填，可带承诺付款日）；`POST /{id}/promise` 承诺付款日；动作全部落 `dms_payment_collection`（`action_type` 1 催收 / 2 核销 / 3 承诺付款）。
- `POST /{id}/write-off` 核销（挂账收回）：累计核销 **达到应收 → `status` 3 → 1（已支付）**；**超出应收被拒**；非挂账记录拒绝催收/核销。
- `GET /unpaid/page`（挂账台账 + 催收聚合）、`GET /unpaid/stat`（未付笔数/金额/已催收/承诺/已核销）、`GET /{id}/collections`（动作流水）。

### 7.3 支付流水对账（§3.1-4 / §3.3 `/reconcile`）

- 新表 `dms_payment_flow`：同一「租户 + 渠道 + 平台交易号」**唯一**（重复导入幂等跳过）；列含渠道/交易号/商户单号/金额/成交时间/付款人/导入批次/匹配状态/匹配收款记录/匹配方式/匹配时间。
- `POST /flow/import`：**逐行校验 + 逐行反馈**（缺交易号、金额非法返回行号与原因，不整批回滚）；**渠道编码 trim + 大写归一**（`wechat` 与 `WECHAT` 视为同一渠道，否则幂等判重会失效）。
- `POST /reconcile`：只对**线上渠道（微信/支付宝/POS/银行转账）已支付记录**逐笔核对，输出**五类结果**：
  `MATCHED`（交易号或商户单号一致且金额相符）、`FLOW_ONLY`（系统无此笔）、`AMOUNT_MISMATCH`（金额不符）、`DUPLICATE`（同一收款记录被两笔流水命中）、`SYSTEM_ONLY`（**掉单**：系统已支付、流水缺失）。
  已匹配流水不重复处理（对账幂等，**已人工忽略的流水也不改判**）；差异可反复重试；差异明细含任务编号，最多 200 条（`detailTruncated` 标记）。
- `POST /flow/{id}/match` 人工匹配、`POST /flow/{id}/ignore` 忽略差异（渠道测试单）；人工判定优先级高于自动对账。

### 7.4 财务打通（推送 ERP，幂等）

- `POST /push-finance?paymentId=`（单个）／`?paymentIds=1,2,3`（批量，**逐单反馈**）。
- 仅**已支付**可推；写入事件发件箱 `PAYMENT_PUSH_FINANCE`（`target=ERP`，payload 含 paymentId/taskNo/客户/科目/金额/支付方式/交易号），台账记 `finance_push_status` + `finance_trace_id`；**重复推送幂等**返回既有 traceId。
- 科目口径：代收货款冲减代收负债、配送费确认其他业务收入（消费方按 payload 的 `paymentType` 入账）。

### 7.5 资金安全（§3.4-2）

| 配置键（《配送参数》可改，`SETTLEMENT` 组） | 默认 | 行为 |
|---|---|---|
| `dms.payment.cash.limit.per.order` | 0（不限） | 超限**拒绝现金收款**并提示改用扫码/POS |

### 7.8 本轮修复的真实缺陷（4 处）

| # | 缺陷 | 现象 | 修复 |
|---|------|------|------|
| 1 | 挂账未写应收金额 | `mark-unpaid` 新建记录金额为空 → 挂账金额恒 0、催收/核销全链路失真 | 按任务口径补齐 `代收货款 + 配送费`（`taskDue()`），`callback` 缺金额时同口径兜底 |
| 2 | 复用的待支付记录未补收款类型 | 收款码/回调复用记录时 `paymentType` 为空 → 前端显示成「配送费」、推财务无法分科目记账 | `generateQrcode` 落定时按任务推断；`callback` 复用记录时补空（E2E 新增「科目完整性」断言） |
| 3 | 已忽略流水被再次对账改判 | `reconcile` 仅跳过「已匹配」，人工忽略的差异下次对账又被改回差异 | 跳过条件增加 `matchStatus=3`，尊重人工判定 |
| 4 | 渠道编码未归一 | `wechat` / `WECHAT` 被当成两个渠道 → 同交易号重复导入不被判重 | 导入与渠道统计统一 `trim().toUpperCase()` |

> **前端配套（UX 一致性）**：台账「仅看交款超时」与「支付状态/交款状态」互斥（勾选时自动清空并隐藏后两者），避免用户选出「已支付 + 未付」这类矛盾条件而得到空集；后端同时保证超时口径优先。
