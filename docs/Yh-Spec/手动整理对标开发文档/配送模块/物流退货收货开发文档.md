## 4. 业务规范

- **本页 = 销售退货申请的历史视图**（销售退货流程的入口与跟踪页），跟踪口径为**订货数量 / 已收数量 / 未收数量**（按单据）与**退货数量 / 已收数量 / 未收数量**（按明细）。
- **新增**：可从本页「新增」按钮进入退货申请表单（生成销售退货申请单）。
- **状态**：单据状态（待审核/已审核等）+ 结算状态分别跟踪。
- **仓储口径**：仓库、退货数量、（明细）单位/换算关系/包装；收货完成后进入销售退货单入库（见《销售退货单开发文档》）。
- **物流口径**：物流公司、运单号（隐藏列）、配送方式——本页亦称「物流退货收货」，即退货经物流回流后的收货确认。
- **商品扩展列**：按明细含 规格/型号/产地/货号/条码/大中小包装/换算关系等商品档案列（多数隐藏）。
- **自定义字段**：单据自定义 1–5、表体自定义 6–10（含往来单位/职员/部门类型）。

## 6. 落地实现（2026-09-13 · 金标准）

### 6.1 列表视图：入口直达复用（不重复造页面）

按《配送模块 README》§4「入口直达现象」，本页菜单打开的视图与《销售退货申请-历史》是**同一个视图**，直接复用其列表组件：

```vue
<!-- views/dispatch/return-receive/index.vue（薄壳） -->
<SalesReturnApplyList />   <!-- = views/sales/return-apply/index.vue -->
```

- 列配置 `storage-key` 沿用 `sale-return-apply-table-columns-{doc,detail}`，两入口口径天然一致；
- 新增/编辑走销售域表单 `/sales/return-apply/form`，与既有单据链路一致。

**本轮补强（原「默认全量展开」缺陷）**：目标视图的 47/62 列此前未标 `defaultHidden`，进入页面会把全部列铺开，与对标「默认 20 / 22 列」不符。已逐列标注默认显隐，两 Tab 默认表头与对标实测完全一致（E2E 精确集合断言）。

### 6.2 收货闭环：跟踪三列的真实数据来源（P0）

**改造前**：`erp_sale_return(_item).received_quantity` / `unreceived_quantity` **全仓无任何写入方**（恒为默认 0 / SQL 派生），且「退货申请」与「销售退货单」**两条链路各自入库 + 各自记账**，同一批退货会重复过账。

**改造后（职责唯一化）**：

| 环节 | 行为 |
|------|------|
| 退货申请审核（`SaleReturnServiceImpl#approve`） | 仅推进状态为 2（审核通过 = **待收货**），**不入库、不记账** |
| 退货单审核（`SaleReturnDocServiceImpl#approve`） | 入库 + 记账（保留原能力），并按 `returnApplyId` **汇总所有已审批退货单明细**回写申请 |
| 回写内容（`SaleReturnService#writebackReceivedProgress`） | 明细 `received_quantity`（按商品匹配）+ 主表 `ordered/received/unreceived_quantity`；全部收货 → 申请状态 3，部分收货保持 2 |
| 退货单取消 | 库存回冲 + 重新汇总回写（已收下修、未收回升） |
| 累计收货 > 申请数量 | 创建/更新退货单时即拦截（400），回写侧再做一次上限防御 |

这样本页的「订货数量 / 已收数量 / 未收数量」三列**只可能来自真实收货动作**，支持部分收货与取消回退。

### 6.3 其余去桩与补齐

- **列字段补齐**：`pageList` 增补派生列 `submitByName`（提交人姓名，`submit_by` → 昵称）与 `lineCount`（商品行数，分组计数、无 N+1）；
- **金额三列真实化**：迁移 `V11.311.0` 补 `erp_sale_return.discount_bill_amount`；`calculateTotals` 计算 折后金额（商品金额−优惠）与本单金额（折后+运费+其他费用），列表「金额 / 折后金额 / 本单金额」不再同源重复；
- **收货操作入口**：销售退货单表单新增「退货申请」源单选择器（仅列已审核待收货申请），选择后带出客户/仓库/经手人/销售类型与**待收商品明细**，形成「选中即收货」的闭环入口；
- **订单数量口径**：申请创建/编辑时即写入 `ordered_quantity`（= 明细退货数量合计），未收货时 `未收数量 = 订货数量`。

## 7. 验收（2026-09-13 · E2E 90/90）

### 7.1 二轮修复：按明细行键重复（Vue Duplicate keys）

**现象**：切到「按明细」Tab 时控制台报 `[Vue warn]: Duplicate keys found during update: "2099000000000000810"` —— 同一申请单的多行明细共用同一个行 key。

**根因**：明细查询 SQL 只返回主表 id（`erp_sale_return.id`），未返回明细行主键；而 `BillDetailTable` 行键取 `record.id`。主表与明细是**一对多**，一张单据的多行明细必然产生 N 个相同 key，会引发行复用错乱（勾选/展开/行内编辑串行）。

**修复（后端补字段 + 前端指定行键，`id` 语义保持不变）**

| 层 | 落点 | 改动 |
|----|------|------|
| 后端 | `SaleReturnMapper#selectPageDetail` | SELECT 增加 `i.id as "itemId"`（明细行主键）；`r.id` 仍作主表 id（页面行操作/跳转沿用，零破坏） |
| 后端 | `SaleReturnDocMapper#selectPageDetail` | 同上（销售退货单侧同源问题一并修） |
| 组件 | `BillDetailTable` | 新增 `rowKey` prop（默认 `id`）；行键改为 `record[rowKey] ?? record.id ?? rowIndex` |
| 组件 | `BillTableList` | 把既有 `rowKey` prop 透传给 `BillDetailTable`（此前只声明未下传） |
| 页面 | `views/sales/return-apply/index.vue` | `:row-key="activeTab === 'detail' ? 'itemId' : 'id'"`（按单据用主表 id，按明细用明细行主键） |

**验证**：接口 `/erp/sale/return/page-detail` 返回 4 行 → `itemId` 全非空且唯一、`id` 重复（符合主表语义）；实机切「按明细」**Duplicate keys 告警 0**；同期回归《采购订货收货》E2E 95/95、本页 E2E 89/89 均无回退。
