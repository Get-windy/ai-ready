## 1. 页面概述

- **调度工作台（列表操作页）**：对配送任务（`DmsTask`）执行**指派 / 改派 / 取消 / 异常标记 / 查看轨迹**，并支持一键**自动调度**待分配任务。
- 页面标题「调度任务」，数据源与《配送查询》《配送单》同源（`DmsTask`），但视角为**调度视角**（配送员维度）。

## 2. 页面结构（现状实测）

| 查询条件 | 控件 | 说明 |
|---------|------|------|

### 2.2 工具栏

- **自动调度**（页面右上，`header-extra`）：二次确认「对所有待分配任务执行自动调度？」→ 调调度服务。
- 导出（组件内置）。

### 2.3 数据表格列（11 列）

任务编号、订单号、类型、客户、配送员ID、数量、货品金额、优先级、状态、创建时间、操作。

- **类型**：1 销售配送 / 2 调拨 / 3 退货（标签色）。
- **优先级**：1 普通 / 2 紧急 / 3 加急（标签色）。
- **配送员ID** ⚠️ 显示 ID 而非姓名，应改配送员姓名。

### 2.4 行级操作

| 操作 | 显示条件 | 说明 |
|------|---------|------|
| 指派 | `status = 0`（待分配） | 打开「指派配送员」弹窗 |
| 改派 | `status ∈ {1,2}`（已分配/已接单） | 打开「改派配送员」弹窗（显示当前配送员） |
| 取消 | `status ∈ {0,1}` | 二次确认 → 取消任务 |
| 轨迹 | 有 `riderId` 且 `status ∈ {2,3,4}` | 跳转实时跟踪（`goTracking`） |
| 异常 | `status ∈ {2,3,4,5}` | 二次确认 → 标记异常 |

### 2.5 指派/改派弹窗

- 标题随模式切换：`指派配送员` / `改派配送员`。
- 头部信息：任务单号 + 订单号（改派时附当前配送员ID）。
- **候选配送员列表**（单选 radio，列：配送员ID、姓名、电话、评分、累计单量、车牌），未选配送员时「确定」禁用。

### 3.6 派单策略（业界生产级实践）

| 策略 | 说明 | 适用 |
|------|------|------|
| 最近可用 | 取距取货点最近且空闲的配送员 | 即时配送 |
| 负载均衡 | 在途单数最少优先 | 高峰期 |
| 评分优先 | 评分高优先 | 服务质量导向 |
| 区域分包 | 按配送区域/线路绑定固定配送员 | 路线型配送 |
| 抢单 / 竞价 | 任务入订单池，配送员抢单或报价 | 众包运力 |

**必须的工程约束**：

1. **配送员负载上限**：在途单数/载重/容积超限不可指派（指派前校验）。
2. **超时升级**：任务超时未接单/未完成 → 自动重新指派或升级告警（可配阈值，存《配送参数》）。
3. **调度审计**：每次指派/改派记录操作人、时间、原因（`dms_task_log`），支持追溯。
4. **批量与人工干预**：自动调度后允许人工微调；批量操作需二次确认与结果反馈（成功/跳过/失败原因）。
5. **地图联动**：地图上按区域圈选任务批量派单（业界常见），需地图 SDK（见《实时跟踪开发文档》）。

### 3.7 数据模型

- 主表 `dms_task`（已有）；关联 `dms_rider`、`dms_vehicle`。
- 建议补充：`dms_task_log`（指派/改派/取消/异常的操作日志）、配送员负载视图（`在途任务数`/`载重`）。

## 4. 业务规范

- **调度方式**（后端 `DispatchTypeEnum`）：1 自动 / 2 手动 / 3 抢单 / 4 竞价——手工指派属「手动」，工具栏「自动调度」属「自动」。
- **指派规则**：候选配送员应结合**在线状态、当前负载、评分、车辆**排序（现状为直接列表，排序/筛选规则待补）。
- **与订单池的关系**：待分配任务同时可从「订单池」（`DmsOrderPool` + `DmsBid`）以抢单/竞价方式消化；本页为**管理员指派视角**。
- **与司机端联动**：指派后任务进入配送员端（`frontend/apps/driver-delivery`），配送员接单 → 取货 → 配送 → 签收，状态回写。
- **异常处理**：标记异常后需人工介入（重新指派/取消），异常任务进入统计。

### 8.2 指派前校验（负载上限，§3.6 约束 1）

`DispatchService.assertAssignable(task, rider)` —— 人工指派与改派同样硬门控，不满足即拒绝并给出可读原因：

1. 配送员**休息中(3)** → 拒绝；
2. **并接上限**：在途（已分配/已接单/取货中/配送中）单数 ≥ `dms.dispatch.max.concurrent` → 拒绝；
3. **载重上限**：任务 `total_weight` > `dms.dispatch.max.load.kg` → 拒绝；
4. **容积上限**：任务 `total_volume` > `dms.dispatch.max.volume.m3` → 拒绝；
5. **资质**：`KycService.assertEligible`（受《配送参数》`verification.eligibility.enforce` 开关控制）。

> 距离与电子围栏属**自动派单的优化约束**（候选表标「不可派」并给原因），人工指派是调度员的显式决策，不做拦截——这与 §3.6「自动调度后允许人工微调」一致。

### 8.3 调度审计（§3.6 约束 3）

新表 `dms_task_log`（`V11.320.0`）：`action`(ASSIGN/REASSIGN/UNASSIGN/CANCEL/EXCEPTION/AUTO_ASSIGN/ESCALATE/BATCH_ASSIGN/BATCH_CANCEL) + 变更前后配送员（含姓名快照）+ 原因 + 操作人（姓名快照，系统动作为「系统」）+ 时间。写入点覆盖指派 / 改派 / 取消 / 异常 / 自动调度 / 超时升级 / 批量操作；**审计写入失败不打断主流程**（独立服务、异常吞掉并告警日志）。前端任务编号点开即时间线。

### 8.4 超时升级（§3.6 约束 2）

口径：在途任务「已过 `deadline_time`」或「已分配且超过 `dms.dispatch.timeout.escalate.minutes` 仍未接单」。
处理：**优先换人重派**（排除原配送员后再按策略评分选人）；确无他人可派时退回原配送员重新派单（重新计时）；配送中/取货中的已超时任务只记告警审计，等人工介入。结果同样逐单反馈。

触发方式（2026-09-14 补齐定时化）：
- **手动**：页面「超时升级」按钮 / `POST /api/dms/dispatch/escalate-overdue`；
- **定时**：定时任务处理器 `dms.dispatch.escalateOverdue`（默认**停用**；多实例 Redis 锁互斥；逐租户执行；`{"dryRun": true}` 只统计不落库）。详见 §8.8 与《配送模块 README》§8.4。
