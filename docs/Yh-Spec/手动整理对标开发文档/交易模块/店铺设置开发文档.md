## 业务规范说明

- **商城开关**：控制商城是否对外营业（关=买家端不可访问）。
- **营业时间**：起~止时间，控制商城下单时限展示。
- **买家注册/登录**：是否允许游客访问、游客显示价格、只允许微信登录、启用买家不显示客户级别、短信签名（注册/通知短信签名）。
- **价格规则**：价格跟踪、跟踪价格随单位联动、启用建议零售价（建议零售价来源）。
- **商品规则**：商品授权管理、分单位显示、显示销量、库存显示方式（可用库存）、商城分类、无货商品显示方式（补货中）。
- **订单规则**：N天自动收货（发货后 N 天未确认自动收货）。
- **支付方式**：在线支付（含 微信/支付宝/聚合/农业银行/建设银行/京东支付，需先在「支付方式」页启用）、欠款、货到付款三种支付场景，可按默认显示顺序排序、启用/停用、设置统一规则（如未付款自动取消订单时长、允许未付款发货）。

**布尔与 JSON 的前端转换方式（V11.361.7 起）**
- **布尔开关**：加载 `bitToBool(cfg?.xxx, false)`（库内 0/1 → `boolean`），提交 `boolToBit(params.xxx)`（`true→1 / false→0`）。转换函数定义在 `apps/pc-admin/src/api/erp/mall.ts`，**显式转换，不依赖隐式类型转换**。
- **支付场景矩阵**：加载 `JSON.parse` 后按 `sort` 重排行顺序；提交 `JSON.stringify` 为 `[{code,enabled,ruleEnabled,ruleValue,sort}]`。解析失败/为空时**保留由 `payment_methods` 推导的已回填值，不清零**（脏数据不把页面打崩）。

- **⚠️ 为什么 `reg_audit_required` 不能给默认值（2026-09-14 上级裁定并已改迁移）**：本列初稿写的是 `ADD COLUMN ... reg_audit_required INTEGER DEFAULT 0`。PostgreSQL 的 `ADD COLUMN ... DEFAULT` 会**把默认值回填到所有既有行**，于是「从未配置过」被静默填成 `0`＝「免审核」，而旧列 `enable_auto_audit` 的原语义下「需人工审核」对应的是 `0` —— 两者 `1` 的含义**恰好相反**，会导致存量租户注册审核行为被**翻转**。已改为「**无 DEFAULT 新增 + 按旧列反向映射订正存量行**」：
  ```sql
  ALTER TABLE tenant_shop_config ADD COLUMN IF NOT EXISTS reg_audit_required INTEGER;
  UPDATE tenant_shop_config
     SET reg_audit_required = CASE WHEN enable_auto_audit = 1 THEN 0 ELSE 1 END
   WHERE reg_audit_required IS NULL;
  ```
  - **映射依据**：`reg_audit_required == (enable_auto_audit == 1 ? 0 : 1)`（推理见缺口 #1(d)）。`enable_auto_audit IS NULL` 时 `ELSE 1` → 需审核，与原代码硬编码默认 `needAudit = true` 一致。
  - **真库事务内实测**（`tool-results/migcheck/MapProbe.java`，执行后 ROLLBACK，零持久化）：真库 `tenant_shop_config` 唯一行 `enable_auto_audit=0` → 迁移后 `reg_audit_required=1` → `newNeedAudit=true / oldNeedAudit=true` ⇒ **CONSISTENT OK（未翻转）**；列定义实测 `default=null / nullable=YES`；回滚后该列数=0。
  - **保持 NULL 的用意**：存量行已有确定值；后续新建行若未显式写值则保持 `NULL`，由运行时回落旧列（亦无值则按需审核），**不引入静默默认值**。⚠️ 后续任何人不许把本列改回 `DEFAULT 0/1`。
- **JSON 列的口径与理由（重要）**：`payment_scenes` 采用 **TEXT + JSON 字符串**，**不用 PG `jsonb`**。理由：
  1. 与既有 VARCHAR/TEXT 风格一致，实体侧直接映射 `String`，无需 TypeHandler；
  2. 本页是「整对象 PUT 一次保存」的模型，JSON 列与之一致，**无需为支付场景矩阵再开 CRUD 端点**；
  3. 对标文档本身给了「建议独立表 `shop_payment_scene` **或 JSON 存储**」两个选项；
  4. 支付场景矩阵的「统一规则值」口径**对标未完全实测**（如「允许未付款发货」是否独立布尔未验证），建独立表等于为未实测结构固化 schema。
  **存储结构（本实现口径）**：`[{code:'ONLINE'|'CREDIT'|'COD', enabled, ruleEnabled, ruleValue, sort}]` —— 含**启停 / 显示顺序 / 统一规则值**三项，完整覆盖对标矩阵的「商城默认显示顺序 / 支付方式启用 / 统一规则设置」三列。

  **这是本实现的存储口径**；后续如需按场景做查询/统计，可平滑迁移为独立表。

## 业界对标 / 跨模块 / 最终裁决

- **业界对标**：商城「店铺设置」为店铺级运行参数配置，同类系统以「店铺参数（开关/时间/注册登录/价格/商品/订单规则）+ 支付方式矩阵」组织。ql361 将店铺支付方式（在线支付/欠款/货到付款）放在店铺设置内，与独立「支付配置」的「支付方式×场景」矩阵（`PaymentConfig` 视图，含微信/支付宝/聚合/京东/农行/建行/微企付）区分——店铺设置控制支付场景启停，支付配置控制各支付渠道申请与费率。
- **跨模块**：支付设置联动「支付配置」（`PaymentConfig`）已启用的支付方式（未启用则本页置灰禁用）与「支付方式」页面；游客访问/微信登录联动「微信支付/微信公众号授权」；默认仓库联动 ERP 仓库主数据；价格跟踪/建议零售价联动 ERP 价格体系。
- **最终裁决**：本页不存在可配置列的数据表，**无列/页面配置弹窗**（配置/表单型；支付设置矩阵为业务表，非列可配置）。金标准应按「店铺参数/注册设置/支付设置」3 子项结构对齐；**已由 Flyway `V11.361.7` 补齐三页对标列并打通三子项真实读写**，**并由 `V11.365.0` 将「注册设置」子项按 2026-09-14 实测的 5 项重做**（原「注册协议」自造项已移除）；剩余为**注册设置默认分类选项字典未实测、三个跳转入口落地页未实现、营业执照门控未抓实、富文本组件缺失、预览 iframe 缺失**等缺口，见「剩余缺口」。
