## 页面概述

发货单用于出库发货复核（销售/调拨发货），承接拣货任务，记录发货数量、承运商与运单号，支持 PDA 扫码复核。模块含两个页面：

| 页面 | 地址 | 说明 |
|------|------|------|
| 发货单列表页 | `wh/shipping-order/index`（list_path 别名 `wms/ship`） | 双入口「历史」标签 |
| 新增/编辑发货单表单页 | `wh/shipping-order/form` | 编辑模式为新增模式加 id |

### 配置功能说明（每个页面都有）

- **页面配置**（页面顶部齿轮图标）：管理页面级字段的显示、隐藏和排序。
- **列配置**（数据表右上角表头单元格内齿轮图标）：管理数据表列字段的显示、隐藏、排序、宽度调整及左右冻结。
- ✅ **当前实现说明**：表单页已重构为生产级 `BillFormPage` + `BillDetailTable` 金标准（单据头 + 货位/商品/应发数量/批次/序列号明细）+ 配置三Tab（页面配置/录单默认值/打印设置，走 `userPageConfigApi`），支持 **远程搜索**（客户/承运商/拣货任务，`remoteSearch`）、扫码复核、拣货任务带出明细；列表页 `CategoryListLayout` + 双Tab(按单据/按明细) + 列/页面配置弹窗。

| 运单号 | a-input | 否 | trackingNo |
| 备注 | a-input | 否 | remark |

### 工作流按钮

| 状态 | 按钮 | 动作 |
|------|------|------|
| 任意 | 保存单据 / 保存修改 | `shipApi.save` / `update` |
| 任意 | 新建 | 重置表单 |
| status=0 | 开始发货 | `shipApi.startShip(id, userId, userName)` |
| status=1 | 确认发货（popconfirm） | `shipApi.confirmShip(id)`（不带用户参数） |

### 作业明细表格

明细仅**待复核（status=0）**可编辑，保存为**整体替换**（`shipApi.saveDetails`，先删后插）。

列：单号、来源单号、仓库、客户、承运商、进度（扫描/总）、状态、创建时间、操作（载入 / 开始 status=0 / 确认 status=1）。

## 业务规范说明

- 拣货 → 发货复核：发货单承接拣货任务（`pickTaskId`），复核扫描后确认发货，进入出库。
- 明细状态：待扫描 0 → 已扫描 1 → 已确认 2；确认发货后明细只读。
- 复核方式：`scanItem`（PDA `/wms/ship/scan`）逐行累加已扫描数，`confirmShip` 写 `shipTime`。
- 单号前缀 `SH`，前端 `genTaskNo` 生成（`SH-yyyyMMddHHmmss`），后端 `save` 原样落库；**后端无 next-no / 序列号自动生成**。
- **架构师红线**：对标 Odoo/SAP/金蝶/用友/管家婆等生产级系统的业务与交互逻辑；动手前过六关，仅最小可用闭环，防注入/容灾/安全防御代码不准省。
- **验收标准**：无桩（Stub）与模拟（mock|todo|fixme|占位|placeholder），确保真实数据。
- **对标系统**：ql361（`22stable.ql361.com`），仓储模块无发货页，本页为设计新增。

### 最终裁决方案（2026-09-02 · 严格按此执行，不得变通）

> 档案级决策，作为本页 P0/P1/P2 修复的唯一依据。来源=业务侧最终裁决。

**决策1 · 库存扣减（A 方案 · 红线）**
- 出库扣减统一走「冻结 + 扣减」A 方案：拣货/发货**前冻结**可用库存（`InventoryService.freeze`），出库确认时**统一扣减**（`InventoryService.decrease`）。
- **禁止 B 方案，严禁存在两条扣减链路**（不允许"ERP 销售域"与"WMS 发货"重复扣 `erp_stock`）。本次以 WMS 发货确认扣减为单一入口；ERP `sale/ship`、`sale-outbound/ship` 历史扣减路径收敛为**一条**（保留出库单级，订单级 `confirmShipment` 只建单不扣）。

**决策2 · 模块依赖（HTTP API 边界）**
- **禁止 WMS 直接依赖 erp-sales**。WMS 通过调用 ERP 暴露的 HTTP API 生成/推进出库单，**WMS 不持有出库单写入权限**。
- 发货确认后调 ERP：`POST /api/erp/sale-out/confirm`（后端在 ERP 侧暴露），WMS 仅 HTTP 调用。

**决策3 · 实施范围（先 P0+P2，P1 延后）**
- 本次发版只做 **P0（冻结+扣减库存安全）+ P2（批次/效期/序列强制校验）**，本周内稳定。
- **P1（波次生单/下推链）延后至下一迭代，前端入口先隐藏**，不阻塞发版。

**四个具体问题落地**
1. **出库单生成**：WMS 调 ERP HTTP API（`/api/erp/sale-out/confirm`）推进出库单；WMS 无写入权限。
2. **单据关联**：`WmsShipTask.sourceOrderId` 指向**销售订单（Sales Order）**；**一个销售订单可拆多个发货单**（1:N）。
3. **P1 数据源**（本次隐藏、下迭代实现）：拣货任务 → 调 **WMS 自身拣货任务 API**；销售出库单 → 调 **ERP 出库单查询 API**；客户主数据复用 **`md-customer.ts`**；承运商主数据暂缺，前端先用**默认值「其他」或留输入框**，后续对接。
4. **扫码复核**：**本次必做**，在发货表单集成 `scanItem` API（`POST /api/wms/ship/scan`）作为复核入口。

**执行指令**：立即以 P0（冻结+扣减）+ P2（强制校验）开工；P1 前端入口先隐藏；跨模块缺接口 → 提需让后端在 ERP 侧暴露 REST API，WMS 只做 HTTP 调用。

**✅ 库存双轨统一最终方案（2026-09-03 · 已落地，强一致单入口）**
- **底层事实**：`InventoryServiceImpl.decrease/increase` 已在**同一事务内双写**——扣减 `wms_inventory` 后经 `stockService.decreaseStock/increaseStock` **镜像同步到 ERP 轨 `erp_stock`**（源码 line 204 注释）。即双轨已被 `InventoryService` 作为**单一入口强一致统一**，并非物理隔离。
- **真正的双轨不一致**：第二条链路 `SaleOutboundServiceImpl.updateStock` 直接 `decreaseStock` 扣 `erp_stock`（绕过 wms、不写 `wms_inventory`）——**已屏蔽**（`TODO-ARCH` 注释），`erp_stock` 仅在 `InventoryService` 单入口侧同步。
- **confirmShip 现状**：`InventoryService.decrease`（**唯一扣减入口**，双写 `wms_inventory` + `erp_stock` 同事务强一致）+ P2 批次校验（`getByUniqueKey`）。**未引入 `InventoryChangedEvent` 事件总线**（否则 ERP 再 `decreaseStock` 会重复扣 `erp_stock`，违背单扣减链路红线）。
- **杜绝双向调用**：`InventoryService` 单向依赖注入 erp-stock 的 `stockService`，非反向耦合；`/api/erp/sale-out/confirm` 不实现不调用。
- **若未来改为异步最终一致**：需先让 `InventoryService` 只写 `wms_inventory`、再由事件单向同步 `erp_stock`（二者二选一不可并存），属架构权衡，本迭代**不采用**（采用更优的强一致镜像）。

## 开发原则（通用）

- **页面组件优先复用**：页面开发优先使用已有的页面组件，除非当前页面组件不满足业务需求；确无对应组件，则优先开发合适的通用组件。
- **功能/模块不重复开发**：已开发过的业务功能、单据、通用能力在全系统范围内只实现一次；其它模块直接复用，不重复开发。
- **Service 接口签名变更需同步测试**：修改 Service 接口签名（方法名/参数/返回值）时，必须同步更新对应测试类，否则会阻塞整模块的 `test-compile`。
- **阶段结束前回写开发文档**：当前阶段工作完成后、结束前，必须更新开发文档的「已完成」与「待完善」章节，使其反映当前代码的实际实现情况。
