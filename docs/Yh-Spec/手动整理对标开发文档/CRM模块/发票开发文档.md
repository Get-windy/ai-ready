### 1.2 三个相邻概念的边界（勿混）

- **发票（本页，`invoice`，85 列）**：**已开出的发票**（有票号、有开票人、有应收到期日）；由 `POST /create-from-application` 生成。
- **发票申请（`invoice_application`，69 列）**：**开票前的申请单**（待审批 → 批准 → 生成发票）；**前端无页面**（16 个端点零引用），而本页「新建发票」调的就是它的生成端点（传的却是一张裸表单，见 §5.4）。
- **ERP 销售订单（`erp_sale_order`）**：**已确认的交易**；本页「关联订单」下拉**硬编码 3 条假单号**（§4.1）。

> ① **分页参数键错（P0）**：后端是 `getInvoicesPage(Pageable pageable)`（`InvoiceController.java:76-80`）→ Spring 只识别 **`page`/`size`**，前端发的 `pageNum`/`pageSize` **被完全忽略** → 永远取 `page=0, size=20`。**翻页/改每页条数均无效果**（`result.totalElements` 仍能正确回读总数，所以症状是「总数对、内容恒为前 20 条」）。

## 5. 业务规范

### 5.1 状态值域：前端 5 个字符串 vs 后端 13 个英文枚举（**P0，本页最严重缺陷**）

| | 值域 | 证据 |
|---|------|------|
| **前端**（列表/筛选/详情/统计） | **字符串**：`draft 草稿 / issued 已开具 / sent 已发送 / received 已收到 / cancelled 已作废` | `index.vue:697-704` |
| **后端**（枚举 + 状态机） | **英文枚举 13 个**：`DRAFT 草稿 / SUBMITTED 已提交 / IN_APPROVAL 审批中 / APPROVED 已批准 / REJECTED 已拒绝 / GENERATED 已生成 / SENT 已发送 / PARTIALLY_PAID 部分支付 / PAID 已支付 / OVERDUE 逾期 / CANCELLED 已取消 / CREDITED 已冲红 / VOIDED 已作废` | `InvoiceStatus.java:6-70` |
| **DB 列** | `invoice_status` = `character varying`，`@Enumerated(EnumType.STRING)` → 存**枚举 name**（`GENERATED`/`SENT`/…） | `Invoice.java:49-51`；devdb 实测 |
| **前端表单初值** | `status: 'draft'`（字符串） | `form.vue:246` |

**三处必坏**：

1. **行操作按钮全不渲染（P0）**：`record.status === 'draft' / 'issued'`（`:273,288,303,318,328`）→ 后端返回的是 `invoiceStatus` 且值是 `GENERATED` 等 → **编辑/开具/发送/打印/作废 5 个入口恒隐藏**（只剩「查看」）。
2. **统计卡恒 0（P0）**：`statusCounts` 比 `'issued'`/`'sent'`/`'received'`（`:663-664`）→ 「已开具」「已收到」**两张卡恒 0**。
3. **状态列/详情 tag 空白**：`getStatusText(status) = statusTextMap[status]`（`:716`），查不到则 `|| status` → 列直出 **`GENERATED`** 英文原文；筛选面板发 `status=draft`（`:811`）→ 后端 `GET /page` **根本不收 `status` 参数** → 被忽略（`InvoiceController.java:76-80`）。

> **后端 13 个状态中前端只认 5 个**，且 `PARTIALLY_PAID`/`PAID`/`OVERDUE`/`CREDITED`/`IN_APPROVAL`/`SUBMITTED`/`APPROVED`/`REJECTED` 无中文映射。

### 5.5 单号规则（**P1：字符串切片错位 + 租户固定 1**）

`generateInvoiceNumber()`（`InvoiceServiceImpl.java:362-367`）：

```java
String number = bizNumberGeneratorService.nextInvoiceNo();     // 形如 INV-20260918-00001
return number.substring(0, 3) + "-" + number.substring(3, 11) + "-" + number.substring(11);
```

切片实得：`substring(0,3)` = `INV` ✅｜`substring(3,11)` = **`-2026091`** ❌（应 `20260918`）｜`substring(11)` = **`8-00001`** ❌（应 `00001`）→ **最终 `INV--2026091-8-00001`**（期望 `INV-20260918-00001`）。

`bizNumberGeneratorService.nextNumber()` 的格式是 `{prefix}-{yyyyMMdd}-{seq}`（`BizNumberGeneratorService.java:15-16,83-85`），devdb 实测 `INV` 行 = `prefix='INV'`, `seq_length=5`（`biz_number_sequence`）→ 原始串 18 位。**切片偏移应从 4 起、第二段 12 起**（或直接返回原串）。
另：`nextInvoiceNo()` → `nextNumber("INV")` → `nextNumber(bizType, **1L**, "zh_CN")`（`:114-116,40-42`）→ **号段永远取租户 1**，跨租户共用同一序列（P1）。

### 10.1 接口验收（建议 ≥ 32 项）

**基础查询**：① `GET /page` 默认 200，`totalElements` 与直查 DB（`is_deleted=false` + 租户）一致；② **`page`/`size`（0 基）生效，`pageSize=1` → `content.length===1`**；③ **传 `pageNum`/`pageSize` 时**断言「被忽略」（登记当前缺陷）；④ `GET /query?direction=sales|purchase` 的类型过滤与 `InvoiceType.getSalesTypes()/getPurchaseTypes()` 一致；⑤ `direction` 非法值 → 返回全部（当前实现行为）；⑥ `GET /search?keyword=` 命中票号/客户名/供应商名/备注；⑦ `GET /status/{s}` 用枚举 name 逐值可查；⑧ `GET /payment-status/{s}` 同理；⑨ `GET /date-range` / `/amount-range` 边界（含等值）正确；⑩ **无租户隔离断言**（跨租户造数 → 当前会串，登记缺陷）。

**创建与更新**：⑪ `POST /api/erp/invoice/application` 建申请 → `application_number` 匹配 `APP-*` 且 `status=DRAFT`；⑫ `POST /{id}/submit|approve|reject|cancel` 各前置校验与状态落库；⑬ `POST /application/{id}/generate-invoice?issuedBy=&issuedByName=` → `invoice` 新增行、`application_id` = 申请单 ID；⑭ **`invoice_number` 应匹配 `^INV-\d{8}-\d{5}$`（当前为 `INV--2026091-8-00001` → 断言缺陷）**；⑮ `POST /create-from-application` **不带 `issuedBy`/`issuedByName` → 断言 400**；⑯ **带 `invoiceType='special'` → 断言 400**（登记缺陷）；⑰ **`PUT /erp/invoice/{id}` → 断言当前 405/404**（修复后改 200）；⑱ `subtotal_amount`/`tax_amount`/`total_amount` 与构造值一致（**当前前端 `amount` 落不下去，断言为 0**）。

**状态机与动作**：⑲ `PUT /{id}/status?newStatus=GENERATED|SENT|VOIDED` 逐值成功且 DB 一致；⑳ **`newStatus=ISSUED` → 断言 400**（登记缺陷）；㉑ **改用例：不带前置校验时状态可任意跳（断言当前无不变量）**，修复后改断言 400；㉒ `POST /{id}/send?sendMethod=EMAIL` **不带 `sentBy` → 400**；带 `sentBy` + `status=GENERATED` → `send_status='SENT'`、`sent_at` 非空；㉓ `send` 对 `PARTIALLY_PAID`/`PAID`/红冲票 → 返回 `false`（`canSend()` 拦截）；㉔ `POST /{id}/void?reason=&voidedBy=` → `invoice_status=VOIDED`、`is_deleted=true`，**并断言它仍出现在 `/page`（当前缺陷）**；㉕ `POST /{id}/credit?reason=&creditedBy=` → 新增负额红票（`total_amount` 为负、`is_credit_note=true`、`original_invoice_id` 指向原票），原票置 `CREDITED`；㉖ `POST /{id}/payment?amount=` → `paid_amount`/`unpaid_amount`/`payment_status` 正确联动；㉗ `partial-refund`/`full-refund` 分别置 `PARTIALLY_REFUNDED`/`REFUNDED`；㉘ `GET /{id}/download` **当前返回 404/空**（登记缺陷）；㉙ `POST /batch-generate` **当前返回空数组**（登记缺陷）。

**统计与数据**：㉚ `GET /statistics` 的计数/金额与 `GROUP BY invoice_status` 一致；㉛ `GET /{id}` 返回体包含 `items`/`taxes`/`payments`（当前恒空数组）；㉜ `POST /create-from-application` **断言 `invoice_item` 无新增行**（登记缺陷）；㉝ **写库隔离**：所有写断言后**按原值复原**或使用专用测试单并清理。

### 10.2 UI 验收（建议 ≥ 26 项）

**入口与骨架**：① 菜单 `CRM → 发票管理 → 发票`（`70350`）点开**直接进录单页**；标签 `历史` 跳到**列表页** —— **双入口方向校验（与客户/线索/商机/合同相反）**；② 列表页 4 张统计卡渲染，**「已开具」「已收到」应有非零值**（当前恒 0）；③ 表格 9 列渲染，**状态列应显示中文标签**（当前直出 `GENERATED`）；④ **发票号码列应非空**（当前 `formatter` 失效 + 字段名不符）；⑤ **发票金额列应显示真实金额**（当前恒 `¥0.00`）。

## 12. 剩余缺口（不阻塞，如实登记）

1. **新建/保存必然失败（P0）** —— 三重原因（枚举值域 400 + 缺必填 query 400 + `application_id` NOT NULL 500）；**页面在架构上堵死**。
2. **字段契约全面错位（P0）** —— 列表 4 列 + 详情 8 项读的字段在实体里不存在或不同名。
3. **状态词表不匹配（P0）** —— 前端 5 字符串 vs 后端 13 枚举 → 5 个行操作入口恒定隐藏、2 张统计卡恒 0。
4. **`PUT /erp/invoice/{id}` 端点不存在（P0）** —— 表单页「编辑」必 404；列表弹窗「编辑」必新建。
