## 5. 业务规范

### 5.1 状态值域（前端 3 处 + 后端 6 处，**前后端不一致**）

**前端（`health/index.vue`）**

| 字段 | 值（逐字） | 语义 | 行号 |
|------|-----------|------|------|
| `healthStatus`（顶卡 `a-tag`） | `'UP'` → 绿「正常」；`'WARNING'` → 橙「警告」；**其它 → 红「异常」** | 三值 | `:46-47` |
| `record.status`（磁盘表） | `'UP'` → 绿「正常」；**否则 → 红「异常」** | 二值 | `:200-201` |
| `dep.status`（依赖卡） | `'UP'` → 绿边框 + `success` badge + 「正常运行」；否则红边框 + `error` badge + 「服务异常」 | 二值 | `:113`、`:121`、`:125` |

**后端（`HealthMonitorController.java`）**

| 字段 | 值域 | 产生规则 | 行号 |
|------|------|---------|------|
| `/jvm` 的 `status` | `UP` / `WARNING` / `CRITICAL` | 堆 >80% → `WARNING`；>90% **或存在死锁** → `CRITICAL` | `:157-172` |
| `/disk` 的 `status` | `UP` / `WARNING` / `CRITICAL` | 使用率 >90% → `WARNING`；>95% → `CRITICAL` | `:212-227` |
| `/dependencies` 内每项 `status` | `UP` / `DOWN` | `checkDependency(name, available)` | `:366-372` |
| `/dependencies` 汇总 `status` | `UP` / `DEGRADED` | 全 `UP` → `UP`，否则 `DEGRADED` | `:266` |
| `healthLevel`（分数档位） | `EXCELLENT`(≥90) / `GOOD`(≥70) / `FAIR`(≥50) / `POOR`(≥30) / `CRITICAL`(<30) | `getHealthLevel` | `:353-359` |
| `/status` 的 `status` | 来自 Actuator `HealthEndpoint#health()` 的 `Status` 字符串 | 透传 | `:50` |

**🔴 三处不一致（如实登记）**：

1. **`WARNING` 在磁盘表被判为「异常」**：后端磁盘 `status` 可能是 `WARNING`（`:212-227`），但前端磁盘表只认 `'UP'`，其余**一律显示红色「异常」**（`:200-201`）→ 90%~95% 使用率会显示成"异常"而非"警告"。
2. **`CRITICAL` 在前端无专属文案**：前端只画 `UP`/`WARNING`/其它三类，磁盘的 `UP`/`WARNING`/`CRITICAL` 落到顶卡时会**把 `CRITICAL` 显示成「异常」**（文案没错，但丢了严重度分级）。
3. **后端 `DEGRADED` 无前端出口**：`/dependencies` 汇总的 `DEGRADED`（`:266`）在前端依赖卡上没有对应文案（依赖卡按逐项 `dep.status` 渲染，不读汇总值）。

> **取值口径**：前端 `healthStatus` 与 `healthScore` **并非来自同一个字段** —— `res.status` 与 `res.healthScore`（`:253-255`），其中 `healthScore` 由后端 `calculateHealthScore`（`:339-351`）**按 Actuator 单一状态映射**（`UP→100 / DEGRADED→70 / DOWN→0 / else→50`），**不是加权评分**；且 Actuator 不产 `DEGRADED`，故实际取值只有 **100 或 0**（`healthLevel` 的五档因此永远只落在 `EXCELLENT` 或 `CRITICAL`）。

## 8. 业界对标

> **本页在 ql361 无对应页**（§2）。因此本章**不写 ql361 对标规格**，只写**业界能力对标**。所有来源按「标题 + URL + 章节 + 查阅日期 + 可信度级别」留痕；**凡底稿标 D 级的方案，本文件一律写「本系统设计」而非「业界标准」**。

### 8.1 业界叫法

**Spring Boot Actuator `/actuator/health`（含 liveness / readiness 健康组）**；SAP 侧对应 **SAP HANA Cockpit 的 Database Backups Card / 管理视图**；金蝶对应「执行服务器监控」。

### 8.2 业界做法要点（**本页几乎可以照抄 Spring Boot 官方文档**）

1. **健康是树形聚合，不是单一布尔**：健康信息来自 `HealthContributorRegistry`，`HealthIndicator` 提供叶子状态，`CompositeHealthContributor` 组合成树，最终由 `StatusAggregator` 汇总 —— 「按有序状态列表排序，取第一个作为整体状态；无已知状态则用 `UNKNOWN`」。
2. **HTTP 状态码映射**：`DOWN`、`OUT_OF_SERVICE` → **503**；`UP`、`UNKNOWN` → **200**。可自定义 `http-mapping`。
3. **默认不暴露细节**：`management.endpoint.health.show-details` / `show-components` 取值 `never`（默认）/`when-authorized`/`always`，授权角色由 `management.endpoint.health.roles` 配置。**平台级监控页应走 `when-authorized`。**
4. **liveness 与 readiness 语义必须分清（官方警告原文级）**：「**liveness 不应依赖外部系统**，否则外部（数据库/API/缓存）故障会触发 Kubernetes 重启全部实例，造成级联失败」；readiness 对外部依赖的取舍需谨慎，「共享的外部系统加入 readiness 会导致其宕机时应用被摘流」。
5. **两个探针组默认自动启用**：`/actuator/health/liveness`、`/actuator/health/readiness`（由 `LivenessStateHealthIndicator` / `ReadinessStateHealthIndicator` 提供），可用 `management.endpoint.health.probes.enabled` 关闭；**默认不会向这两个组添加其他健康指标**，需要时用 `management.endpoint.health.group.readiness.include=readinessState,customCheck` 追加。
6. **内置健康指标清单可直接当「服务状态」页面骨架**：`db`（DataSource 获取连接）、`diskspace`、`redis`、`mail`、`ssl`（含**证书到期预警**：`management.health.ssl.certificate-validity-warning-threshold`，状态 `WILL_EXPIRE_SOON`）、`ping`、`rabbit`、`elasticsearch`、`ldap`、`mongodb` 等；可用 `management.health.key.enabled` 单独启停。
7. **慢指标要能被发现**：「健康指标通常通过 HTTP 调用……超过 10 秒会记录警告日志」，阈值 `management.endpoint.health.logging.slow-indicator-threshold`。
8. **路由数据源**：`DataSource` 健康指标同时覆盖标准数据源与路由数据源，「路由数据源的健康包含各目标数据源的健康（以路由 key 命名）」，可 `management.health.db.ignore-routing-data-sources=true` 关闭。

**来源**：Spring Boot Reference《Endpoints》`https://docs.spring.io/spring-boot/reference/actuator/endpoints.html`（章节：**Health Groups / Kubernetes Probes / Auto-configured HealthIndicators**），查阅日期 **2026-09-18**，可信度 **A**（厂商官方产品文档）。

## 10. 验收标准

> **前置**：本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下无 `e2e-system-*.cjs`）。落地脚本建议命名 `tools/e2e-system.cjs`（接口 + 直连 DB 对账 + 写库后复原 + Playwright UI 截屏，参照 `tools/e2e-crm.cjs`）。
> **⚠️ 本页验收的最大前提**：**P0-1（包未装配）不修，§10.1 的①~⑦ 全部会得到 404**。因此建议的验收顺序是：**先修 `scanBasePackages` → 再跑接口断言 → 再跑 UI 断言**。
> **权限账号**：`admin`（id=1，`tenant_id=1`，SUPER_ADMIN）用作 200 基线；另需一个**非超管但持有 `SYSTEM_ADMIN` 角色**的账号做 403 对账（但注意：本页后端**无权限注解**，因此 §10.1-⑯ 的预期是 **200 而非 403**，这是**当前缺陷**的显式登记）。

### 10.1 接口验收（24 项）

**包装配与可达性（①–③）**

① 修复 `scanBasePackages` 后重启，`GET /api/monitor/health/status`（带 `admin` 的 Bearer）**期望 200**；未修复时**期望 404** —— **两种结果都要记录**，404 即证明 P0-1 未修。
② 同批断言 `GET /api/monitor/health/jvm`、`/disk`、`/dependencies`、`/database`、`/ready`、`/live` **7 个端点全部非 404**（存在性断言，逐个记录状态码）。
③ 断言 `GET /api/monitor/health/status` **不带 Authorization 时返回 401/403**（证明全局登录拦截生效，`SaTokenConfig.java:70-71`）。

**字段与口径（④–⑪）**

④ `/status` 返回体断言含键 `status`、`healthScore`、`serviceName`、`components`、`timestamp`；**并断言 `components` 当前为空 Map**（登记 P1-5 缺陷；修复后改断言非空）。
⑤ `/status` 的 HTTP 状态码：**当前恒 200**（即使 `status=DOWN`）→ **登记缺陷**（业界要求 `DOWN` → 503，§8.2-2）；修复后改断言 503。
⑥ `/jvm` 返回体断言含 `heapMemory{used,max,usagePercent}` 与 `threads{threadCount}`；`used <= max`；`usagePercent` 落在 `[0,100]`。
⑦ `/jvm` 的 `status` 断言三值域 `UP|WARNING|CRITICAL`（阈值 80/90，`HealthMonitorController.java:157-172`）；**构造或记录一次 >80% 的场景**（可用 `-Xmx` 极小值启动或直接断言逻辑分支）。
⑧ `/disk` 的 `disks[]` 至少 1 项（`File.listRoots()` 在 Windows 下返回盘符）；每项断言含 `path`/`totalSpace`/`usedSpace`/`freeSpace`/`usagePercent`，且 `totalSpace ≈ usedSpace + freeSpace`（允许 FS 保留块误差）。
⑨ `/disk` 的 `status` 断言三值域 `UP|WARNING|CRITICAL`（阈值 90/95，`:212-227`）。
⑩ 🔴 **`/dependencies` 常量断言**：`redis` 恒 `DOWN`、`messageQueue` 恒 `DOWN`、`externalApi` 恒 `UP`、`database` 随 `dataSource != null` —— **连调 3 次（间隔 >30s）断言四项取值完全不变**（`:250`、`:253`、`:256`）。**这是 P0-2 的可执行证据**。
⑪ `/dependencies` 汇总 `status`：全 `UP` 时为 `UP`，否则 `DEGRADED`（`:266`）；因 Redis/MQ 恒 `DOWN`，**当前应恒为 `DEGRADED`** —— 断言此事，即证明「依赖卡永远有 2 项红」。

**未接端点（⑫–⑭）**

⑫ `GET /api/monitor/health/database`（前端未调）返回体断言含数据库连接可用性与耗时；**断言前端网络面板中不存在对它的请求**（登记 P1-6）。
⑬ `GET /api/monitor/health/ready` 与 `/live` 返回值断言；**核查 `/live` 的实现是否引入外部依赖**（若引入，违反「liveness 不得依赖外部系统」，`§8.2-4`）—— **结论写入报告**。
⑭ 断言本页**不产生任何数据库读写**：调用前后对比 `sys_oper_log` 行数变化（本页无 Mapper，理论上无落库）。

**权限（⑮–⑰）**

⑮ 用 `admin`（SUPER_ADMIN，`tenant_id=1`）调 7 端点 → **当前期望 200**。
⑯ 用**非超管的 `SYSTEM_ADMIN` 角色账号**调 7 端点 → **当前期望仍为 200**（后端零权限注解）→ **登记 P0 越权缺陷**；修复后改为 **403**。
⑰ 断言 `sys_permission` 中 `permission_code LIKE 'system:monitor%'` **命中 0 行**（当前事实）—— 修复权限种子后改断言 ≥7 行（每个端点一个码）。

**轮询与静默失败（⑱–㉑）**

⑱ 打开页面后**静默等待 65 秒**，捕获网络请求：**期望 4 个端点各被调用 ≥3 次**（首屏 1 次 + 2 个 30 秒周期）→ 证明轮询真实运行（`:309`）。
⑲ 断言每次轮询的 4 个响应**全部为 404**（P0-1 未修时）→ 与 ⑱ 共同证明「持续假绿」。
⑳ 断言页面**未弹出任何错误提示**（因为 4 个 `catch` 均为 `{ /* ignore */ }`，`:256`、`:270`、`:285`、`:297`）→ **这才是缺陷的本质：404 不可见**。
㉑ 断言 `/api/monitor/**` 在 `SaTokenConfig.java` 的 `excludePathPatterns`（`:72-107`）中**零命中**（证明「必须登录」）。

**内存与生命周期（㉒–㉔）**

㉒ 路由切换到其它菜单再返回，断言**旧页面实例的定时器不再发包**（`onUnmounted` 清理有效，`:312-314`）—— 观察方式：切走后 60 秒内**不再出现** `/api/monitor/health/*` 请求。
㉓ 反复进入/离开本页 10 次，断言 `setInterval` 数量**不增长**（浏览器 Performance 面板或用 `window.__intervalCount` 探针）。
㉔ **断言本页无 `addEventListener` / 无 `setTimeout`**（grep 零命中）→ 排除了另外两类常见泄漏面。
