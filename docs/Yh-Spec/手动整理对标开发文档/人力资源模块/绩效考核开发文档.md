## 1. 页面概述

「绩效考核」承载**员工考核结果的登记与确认**：填写考核周期、考核类型、三个维度评分（工作态度 / 工作能力 / 工作业绩）与综合评语，提交后状态置「已考核」，再「确认」置「已确认」。

| 页面 | 地址 | 组件 | 行数 | 菜单挂载 | 说明 |
|------|------|------|:----:|:--------:|------|
| 绩效管理（列表） | `hr/performance` | `views/hr/performance/list.vue` | 75 | ✅ `90005` | **8 列 / 无查询区 / 无任何按钮 / 无操作列**（只读裸表） |
| 绩效管理（伴生页） | `hr/performance/index` | `views/hr/performance/index.vue` | 204 | ❌ **未挂菜单** | 9 列 + 查询区 2 项 + **新建考核弹窗** + **详情弹窗** + 确认按钮 |

> **⚠️ 伴生页提醒（全站 HR 模块共性）**：`index.vue` 已在 `router/dynamicRoutes.ts:511` 注册组件映射，**但 `sys_menu` 中没有任何一行把 `component` 指向 `views/hr/performance/index.vue`**（全迁移文件 grep 为空）。
> 路由表由菜单驱动（`transformMenuToRoutes`），故 `index.vue` **用户不可达** —— 只能由开发者在代码中直接 import。
> 后果：**功能更完整的那个页面用户看不到，用户看到的是功能最少的那个**。`list.vue` **既不能新建考核、也不能确认、也不能查询**，它是一个**纯只读裸表**；而能完成全部业务的 `index.vue` 藏在代码里。两页必须先**收敛为一页**（建议保留 `list.vue` 之名、吸收 `index.vue` 能力），再谈金标准升级。

### 1.2 本页与「薪资管理」的耦合（跨页一致性缺陷）

| 方向 | 现状 |
|------|------|
| 绩效 → 薪资 | ❌ **完全未接线**。薪资生成的 `performanceAmount` **直接取薪资结构里的固定基数 `performance_salary`**（`HrServiceImpls.java:307`），**从不读取** `hr_performance.score` / `level` |

### 3.2 查询条件

**`list.vue` 当前**：**无查询区**。`loadData()` 只传 `pageNum` / `pageSize`（`list.vue:60`）。
**`index.vue` 当前（2 项，`a-form layout="inline"`，`index.vue:10-29`）**：

| # | key | label | 控件 | 选项 | 后端是否接收 |
|:-:|-----|-------|------|------|:------------:|
| 1 | `reviewPeriod` | 考核周期 | input | placeholder `如：2026-Q1` | ✅ |
| 2 | `reviewType` | 考核类型 | select | `MONTHLY`=月度、`QUARTERLY`=季度、**`ANNUAL`**=年度 | ❌ **被静默丢弃** |

**后端 `GET /hr/performance/page` 实际支持的参数**（`HrController.java:242-252`）：`pageNum`、`pageSize`、`employeeId`(Long)、`reviewPeriod`(String)。

> **⚠️ 缺陷 1（P1）：`reviewType` 查询条件静默失效。**
> `index.vue:159` 用 `{ pageNum, pageSize, ...searchForm }` 展开提交，其中 `reviewType` **不在后端形参列表中**；Spring MVC 对未知 query 参数**不报错、直接忽略** → 用户选「季度考核」点查询，**结果完全不变**（《采购订货收货》「查询条件静默失效」同型）。

> **⚠️ 缺陷 2（P1）：`employeeId` 是后端唯一支持的员工维度过滤，两页都没有该控件。**
> 绩效考核最基本的用法是「**看某个人历次考核**」，而前端**没有任何员工筛选**；`list.vue` 连「员工」列都没有（见 §3.4）。

> **⚠️ 缺陷 3（P1）：考核周期是自由文本，无格式、无区间，且同时是唯一排序键。**
> `reviewPeriod` 是 `a-input`（`index.vue:13`，placeholder 只举季度例子），而考核类型可选「月度」（应写 `2026-01`）→ **一个字段承载三种格式且无校验**。
> 后端按该字符串排序：`orderByDesc(HrPerformance::getReviewPeriod)`（`HrServiceImpls.java:455`）→ 字符串降序，混用格式时与时间顺序**不一致**（`2026-Q1` > `2026-12` > `2026-01`），**列表顺序不可信**。

**目标规格（业界标准补充，★ 为本系统已有数据源但未上查询区；「业界建议」为本系统未实现项）**：

| 分组 | 查询项 | 说明 |
|------|--------|------|
| 基础 | 员工（`employeeId`，建议带搜索的下拉）、考核周期（建议改**区间**：周期起止日期）、考核类型 | `employeeId`/`reviewPeriod` 后端已支持、前端未接；`reviewType` 需后端补形参 |
| ★组织 | 部门（`deptId`）、岗位（`positionId`） | 需联 `hr_employee` |
| ★结果 | 考核等级（`level`：S/A/B/C/D）、评分区间（`score`）、是否已确认（`status`） | 需后端补形参 |
| ★流程 | 考核人（`reviewerId`）、考核时间区间（`reviewTime`）、待我评价 | 需后端补形参 |
| 业界建议 | 考核方案 / 模板（`templateId`）、考核阶段（自评 / 主管评 / 校准 / 面谈后确认）、是否纳入强制分布 | **业界建议、本系统未实现**（表无对应列，见 §7、§8） |

> 2. **考核类型列直出英文（P1）**：`list.vue:48` 与 `index.vue:146` 都是直出 `dataIndex`，而值域是 `MONTHLY/QUARTERLY/YEARLY(ANNUAL)` —— **页面上显示的是英文枚举原文**，而仓库里**存在**对应的中文映射能力（见 §5.1 的词表冲突），只是**没有为 `reviewType` 建映射表**。对照：`level` 列做了映射（`list.vue:26-28`）、`status` 列**没做**（两页都没有 status 列）。

> 4. **「考核人」列恒空（P1）**：`reviewerName` 实体有该字段（`HrPerformance.java:86`），但 `submitReview` **只填 `reviewerId`，从不填 `reviewerName`**（`HrServiceImpls.java:460-466`）；前端提交表单也不含该字段 → **列永远空白**。正确做法：后端按 `reviewerId` 反查姓名回填，或在 `submitReview` 里从登录态解析人名。

### 4.2 「新建考核」弹窗（`index.vue:58-98`）当前实现与缺陷

**字段（`index.vue:138`）**：

| 字段 | 控件 | 必填 | 校验 |
|------|------|:----:|------|
| `reviewPeriod` | `a-input`（自由文本） | ✅（`rules` L140） | 仅「非空」，**无格式校验** |
| `reviewType` | `a-select`（MONTHLY / QUARTERLY / **ANNUAL**） | ✅（L141） | 非空 |
| `attitudeScore` | `a-input-number` 0-100 | ❌ | 仅控件级 `min/max`，**无表单规则** |
| `abilityScore` | `a-input-number` 0-100 | ❌ | 同上 |
| `achievementScore` | `a-input-number` 0-100 | ❌ | 同上 |
| `comment` | `a-textarea` | ❌ | 无 |

默认值：三个维度分**均为 80**（`index.vue:138`、`:170` 重置时同值）。

> **⚠️ P0：提交必然失败 —— 表单缺少 `employeeId`。**
> `index.vue:138` 的 `form` 里**没有 `employeeId`**，`handleSave`（L174-184）直接把 `form` 整个丢给 `hrPerformanceApi.submit(...)`（→ `POST /hr/performance`，body 无 `employeeId`）。
> 而 `hr_performance.employee_id` 是 **`BIGINT NOT NULL`**（`V8.9.0:247`）→ **`save()` 必然抛非空约束异常 → 500**，前端 `catch` 后提示「提交失败」（`index.vue:182`）。
> 即：**「新建考核」按钮点了就报错，绩效考核根本创建不出来。**
> 修法：弹窗补「被考核员工」选择器（`hrEmployeeApi.page` 取人）并置 `employeeId`；同时补后端参数校验给出可读错误。

> **⚠️ P0：没有 `score` / `level` 的输入，也没有自动计算。**
> 三个维度分（态度 / 能力 / 业绩）提交后**原样落库**，`score` 与 `level` 无人赋值 → 恒 NULL。
> 也就是说：**即使用户绕过上面那个 500 成功建了记录，列表上的「考核评分」「考核等级」也是空白。**
> 缺的是**评分模型**：没有权重（三个维度各占多少）、没有 `score → level` 的映射阈值、没有任何校验（如三分为 60/60/60 时总分该是多少、等级该是 C 还是 B）。

> **⚠️ P1：考核类型词表与后端 / DB 不一致（`ANNUAL` vs `YEARLY`）。**
> - 前端下拉（`index.vue:17-19`）与提交的枚举值：`MONTHLY` / `QUARTERLY` / **`ANNUAL`**；
> - 实体注释（`HrPerformance.java:44`）与 DB 列注释（`V8.9.0:264`）：`MONTHLY-月度 QUARTERLY-季度` / **`YEARLY-年度`**。
> → 前端写入的是**字典外的值** `ANNUAL`。任何按 `YEARLY` 做的统计 / 筛选 / 报表都会**漏掉年度考核**。属《_开发指南-金标准》陷阱 18 同型的**双词表**缺陷，必须二选一收敛（建议统一为 `YEARLY`，与 DB 注释一致）。

> **⚠️ P1：`reviewPeriod` 与 `reviewType` 不联动、无格式约束。**
> 选「月度」时应引导 `2026-01`、选「季度」时应引导 `2026-Q1`、选「年度」时应引导 `2026`，但当前是**一个自由输入框**（placeholder 只举了季度例子）。用户可填入 `随便写`，系统照收 —— 而该字段**同时是唯一的排序键**（`HrServiceImpls.java:455`）→ **列表整体顺序随之失去意义**。

> **⚠️ P2：考核人不显示、不落姓名。**
> 后端把 `reviewerId` 设为 `SecurityUtils.getCurrentUserId()`（`HrController.java:258`），而 `reviewerName` 无人填（见 §3.4 第 4 条）。

> **⚠️ P2：`list.vue` 导入了未使用的 `message`（`list.vue:39`）**（无害，收敛时随手清）。

## 5. 业务规范

### 5.1 状态与值域

| 字段 | 值域 | 代码 / DB 口径 | 前端映射 | 问题 |
|------|------|---------------|---------|------|
| `review_type` | `MONTHLY` / `QUARTERLY` / **`YEARLY`** | 实体注释（`HrPerformance.java:44`）、DB 注释（`V8.9.0:264`） | `index.vue:17-19` 提供 `MONTHLY` / `QUARTERLY` / **`ANNUAL`** | ❌ **词表冲突**，见 §4.2 |
| `level` | `S / A / B / C / D` | 实体注释（`:54-56`）、DB 注释（`V8.9.0:265`） | `PERFORMANCE_LEVEL_MAP`（`api/hr/index.ts:282-288`）：S 优秀 / A 良好 / B 合格 / C 待改进 / D 不合格 | ⚠️ 映射只在**前端**，DB / 后端**无中文含义**；且**无 `score → level` 的映射规则**（不自动定级） |
| `status` | `0 待考核 / 1 已考核 / 2 已确认` | 实体注释（`:96`）、DB 默认 0（`V8.9.0:259`） | **无任何映射**；两页**都没有该列** | ❌ `0` 与 `2` **实际都不可达**（见 §3.3） |

> **⚠️ `level` 值域无落库口径**：`level` 是 `VARCHAR(10)`，可存任意字符串。既然**无自动定级**、**无字典表**、**无后端校验**，则该列的完整性完全依赖「调用方自觉」——而当前**调用方根本不传**。修法：`score → level` 映射规则应落在后端（配置化阈值），前端只展示。

### 5.2 当前「流程」的真实状态机

```
       ┌──────────────── POST /hr/performance ────────────────┐
       │  submitReview: status = 1, reviewTime = now          │
       ▼                                                       │
  [1 已考核]  ──── PUT /hr/performance/{id}/confirm ──▶  [2 已确认]
       ▲                                                       ▲
       │                                                       │
   （0 待考核 只存在于 DB 默认值，                       （无端点可回到 1）
     系统从不写入、界面也无处产生）                              （无驳回、无删除）
```

| 转移 | 端点 | 前置校验 | 问题 |
|------|------|---------|------|
| `(新) → 1` | `POST /hr/performance` | ❌ **无**（不校验员工是否存在、不校验是否重复考核、不校验周期格式） | 同一员工同一周期可**重复提交无限条**（表无唯一约束） |
| `1 → 2` | `PUT /hr/performance/{id}/confirm` | ❌ **无**（不校验原状态，可对已确认记录重复确认） | 界面按钮不出现（§3.3），端点**无 UI 可达路径** |
| `→ 0` | — | — | **不存在**（无「退回待考核」端点） |
| `→ 删除` | — | — | **不存在**（无删除端点，误建只能直接改库） |
| `2 → 1`（驳回重评） | — | — | **不存在** |

> **⚠️ 无流程、只有三态直改**：业界绩效是「**期初定目标 → 期中跟踪 → 期末评估（自评 / 主管评）→ 校准 → 面谈 → 确认归档**」的多阶段闭环（见 §8）。本系统把整个流程压缩成**两个状态位翻转**，且两次翻转**都不带任何校验与审计**。

### 5.3 关键业务规则

| 规则 | 当前 | 目标 |
|------|------|------|
| **评分模型（权重 / 自动定级）** | ❌ **无**：三个维度分直存，`score` / `level` 恒 NULL | 建评分模型：维度权重 → 加权总分 → 按阈值自动定级 |
| **考核模板 / 指标库（KPI / OKR）** | ❌ **无**：无模板表、无指标表、无权重、无评分标准 | 建 `hr_performance_template` + `hr_performance_item`（指标 / 权重 / 目标值 / 评分标准） |
| **同员工同周期唯一** | ❌ **无唯一约束**（`V8.9.0:267` 只有非唯一索引 `idx_hr_performance_employee`），提交时**不查重** | 加 `UNIQUE (tenant_id, employee_id, review_period, review_type)` 或提交时查重、已确认则拒绝 |
| **考核周期格式** | ❌ 自由文本，无校验、无区间 | 按 `review_type` 约束格式（`yyyy-MM` / `yyyy-Qn` / `yyyy`），或用起止日期建周期主数据 |
| **考核人** | ⚠️ 取 `SecurityUtils.getCurrentUserId()`（**`sys_user.id`**），且**不落姓名** | 与 `hr_employee` 建立映射；至少回填姓名 |
| **多评价人（360°）** | ❌ **无**：表只有**单个** `reviewer_id` / `reviewer_name` | 建评价人子表（自评 / 上级 / 同级 / 下属 / 客户） |
| **校准与强制分布** | ❌ **无**（无分位、无排名、无九宫格） | 补校准视图 + 强制分布规则 |
| **结果应用（调薪 / 晋升 / 奖金）** | ❌ **无**：与薪资**完全无联动**（§1.2） | 绩效等级 → 薪资调整 / 奖金系数 / 晋升资格 |
| **历史归档与版本** | ❌ **无**：改一次覆盖一次（`remark` 是唯一可写备注；且**无修改端点**，连"改"都做不到） | 版本化 / 快照，保留每次评分与校准轨迹 |
| **可解释性** | ❌ **无**：只有三个笼统维度分，说不出「为什么是 B」 | 指标级得分 + 权重 + 评语，可下钻 |
| **绩效申诉** | ❌ **无**（员工看不到自己的考核结果，也无申诉入口） | 结果公示 + 申诉流（接工作流模块） |
| **权限** | ❌ **绩效端点无任何权限码**（见 §6.3） | 员工看自己、主管看下属、HR 看全量 |

### 5.4 跨模块联动

| 方向 | 联动 | 状态 |
|------|------|------|
| 绩效 → 薪资 | 考核 `score` / `level` → 绩效工资实发额 | ❌ **完全未接线**（薪资侧取固定基数，`HrServiceImpls.java:307`） |
| 绩效 → 员工 | 读 `hr_employee` 取姓名 / 部门 / 岗位 | ❌ 前端连员工列都没有（§3.4） |
| 绩效 → 人事异动 | 等级 → 调岗 / 晋升 / 调薪建议 | ❌ 无（本系统亦无人事异动模块） |
| 绩效 → 工作流 | 考核审批 / 校准审批 / 申诉 | ❌ 无（本系统已有工作流模块，属未接线） |
| 员工 → 绩效 | 员工自助查看考核结果 | ❌ 无（`hr_employee` 与 `sys_user` 无关联，员工无法定位"我的考核"） |
| 考勤 / 请假 → 绩效 | 出勤率作为考核输入 | ❌ 无 |

> **⚠️ 缺考核方案 / 指标 / 权重（P0 业务）**：与业界对比，本表**没有** `template_id`（考核方案）、**没有**指标子表（KPI/OKR 项、目标值、权重、评分标准）、**没有** `calibrated_level`（校准后等级）、**没有** `final_score`（校准后得分）。三个笼统维度分**无法支撑**「为什么是这个等级」的解释，也无法支撑跨部门校准。

> **⚠️ 缺结果应用字段**：无 `salary_adjust_id` / `bonus_coefficient` 一类，绩效与薪酬之间**没有数据接口**。

> **参考来源：** Odoo 18 Appraisals `https://www.odoo.com/documentation/18.0/`（章节待补充）；SAP SuccessFactors Performance & Goals / S/4HANA HCM `https://help.sap.com/`（章节待补充）；金蝶 s-HR `https://vip.kingdee.com/`（章节待补充）；用友 DHR `https://success.yonyou.com/`（章节待补充）。

|:-:|------|---------|-----------|-----------|
| 1 | **考核单与阶段流转** | Odoo Appraisals：`hr.appraisal`（考核单）+ **`hr.appraisal.stage`（阶段，可配置流转）**；员工考核含**自评、主管评、最终评分** | 只有 `status` 三态**直改**（`0 → 1 → 2`），且 `0` / `2` 实际不可达（§3.3、§5.2）；**无阶段对象、无顺序、无流转规则** | **P0**：建阶段主数据（可配置）+ 流转规则；把 `status` 从「整数三态」升级为「阶段引用」 |

## 10. 验收标准（目标）

> 本模块**尚无 E2E 脚本**（`tools/` 目录下无任何 `e2e-hr*.cjs`）。以下为按金标准制定的验收清单。
> **前置条件（重要）**：所有 HR 表**当前 0 行**，故任何验收**必须先造数**（至少 2 个 `hr_employee`，用于验证按人筛选与「考核人 ≠ 被考核人」），并**在收尾时清理自产数据**（参见《共享db E2E 断言必须加作用域》）。

### 10.1 接口验收（11 项）

1. `GET /api/hr/performance/page` 200（**当前 404 → P0-1 回归断言**）；默认查询 `total` 与直查 DB（`deleted=0` + `tenant_id=当前租户`）**逐值一致**。
2. `pageNum` / `pageSize` 生效（`pageSize=1` → `records.length===1`）；`reviewPeriod` 与 `employeeId` 过滤各自生效（各造 2 条 / 2 人验证）；`reviewType` 过滤生效（目标；**当前后端无该形参 → 应失败**，P1 证据）。
3. **`POST /api/hr/performance` 带 `employeeId` → 成功且 DB 可查回**；**不带 `employeeId` → 返回可读 400 而非 500**（目标；**当前必然 500** → P0 回归断言）。
4. 提交后 `status = 1`、`reviewTime` 非空、`reviewerId` = 当前登录用户 id。
5. **`score` / `level` 由后端按规则算出**（目标）：造态度 90 / 能力 80 / 业绩 70 → `score` = 加权结果、`level` 落在 S/A/B/C/D；**当前两项应为 NULL**（P0 证据）。
6. `reviewType` 提交 `YEARLY` 后读出仍为 `YEARLY`（**词表一致性断言**；当前前端提交 `ANNUAL` → 应失败，P1 证据）。
7. `confirm` 后 `status = 2`；**对 `status = 2` 记录重复确认应被拒**（目标；当前会成功 → P1 证据）。
8. `PUT /{id}` 修改评分后三级回读一致（目标；**当前无该端点**）；`PUT /{id}/reject` 后回到可重评状态（目标；**当前无该端点**）。
9. **同员工同周期重复提交 → 应被拒绝**（目标：唯一约束或查重）；当前会成功插第 2 条 → P1 证据。
10. 权限：用**仅有普通角色**的账号提交 / 查看他人考核 → 应 403（**当前无权限注解 → 预期失败**，P0 业务证据）；未带 token → 401。
11. 收尾：清理自产 `hr_performance` / `hr_employee` 行，复核现场已复原。

### 10.2 UI 验收（10 项）

1. 菜单 `人力资源 → 薪资管理 → 绩效考核` 点开落在本页，**页面不空白**；**控制台无 error**（含 `ReferenceError` —— 参见《重构搬迁后必须做运行时验证》）。
2. **断言网络无 4xx**：`GET /api/hr/performance/page` 必须 200（当前 404）。
3. **「新建考核」可从已挂菜单的页面进入**（当前 `list.vue` 无任何按钮 —— 本条即 P0「裸表」的回归断言）；表单含**被考核员工**选择器且必填，提交后列表出现新行（**断言无 4xx**；当前必 500）。
4. 列表含**「员工姓名」列且有值**（当前两页都没有该列）；含**「状态」列**并显示中文，且 `2 已确认` 可从界面到达（当前**不可达**）。
5. 「考核类型」列显示**中文**（月度 / 季度 / 年度）而非 `MONTHLY` 原文。
6. 「考核评分」「考核等级」两列**有值**，且等级与该员工的三个维度分**符合既定映射规则**（当前两列恒空）；「考核人」列**有值**（当前恒空）。
7. 查询区为**横向自适应网格**（不得纵向单列）；2 项条件**逐个生效**（当前 `reviewType` 静默失效）。
8. 表头齿轮可改列显隐 / 顺序，刷新后**个人配置保留**（目标）。
9. 分页为**经典形态** `.classic-pagination`，页长选项 `[20,50,100]`（目标）；**当前两页默认 10 / 20，须统一**。
10. 收尾：所有验收造数已清理。

## 12. 剩余缺口（不阻塞，如实登记）

1. **整个 HR 模块端点 404**（P0-1）—— 最高优先，一行修复但影响 6 个菜单页。
2. **新建考核缺 `employeeId` → 提交必然 500**；**「确认」按钮永不渲染** → `status = 2` 不可达（三态值域实际只有 `1` 可用）。
3. **已挂菜单的 `list.vue` 是裸表**（无查询 / 无按钮 / 无操作列），能力全在不可达的 `index.vue` 里 —— 两页须先**收敛**。
4. **无评分模型**（`score` / `level` 恒 NULL）、**无考核方案 / 指标库 / 权重**、**无流程闭环**（无「下发 → 自评 → 主管评 → 校准 → 面谈 → 确认」）、**无 360° / 校准 / 强制分布 / 排名 / 归档** —— **业务根因级**缺失（§8 第 1-6、8 项）。
5. **绩效 → 薪资无联动** —— 本模块产出**无处使用**，须先定义结果应用接口（§8 第 7 项）。
6. **考核类型词表冲突**（`ANNUAL` vs `YEARLY`）须先收敛；**端点无权限码、无字段级脱敏**；`create_by` / `update_by` 恒 NULL。
7. **无修改 / 删除 / 驳回 / 详情端点**；`hr_performance` **无唯一约束**（同员工同周期可重复提交）；详情弹窗为纯前端取行数据。
8. **无导出、无 `/stat` 统计**；`sys_user ↔ hr_employee` 无映射；**无模块级 E2E、无验收截图**。
