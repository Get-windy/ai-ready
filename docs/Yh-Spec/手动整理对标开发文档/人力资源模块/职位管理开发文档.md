## 0. 🔴 命名裁定：本页是「岗位编制」，与「岗位权限」不是一回事（2026-09-20）

系统里曾有三套都带"岗位/职位"字样的概念，菜单名撞车导致使用者把本页与「职员管理 → 岗位权限」当成同一件事。实测（devdb 2026-09-19）后的完整辨析：

| 概念 | 载体 | 菜单 | 真实数据 | 职责 | ql361 对标 |
|---|---|---|---|---|---|
| **权限载体** | `sys_role` + `sys_role_permission` | 「岗位权限」80531（`V11.429.0` 已改指角色页） | 5 角色 / 490 权限关联 | **功能权限**：谁能用什么功能 | ✅ 对应它的「岗位」（ql361 的岗位即权限载体） |
| **编制单位** | `hr_position` | **本页 90006**（已更名为「**岗位编制**」，`V11.431.0`） | **0 行**（曾有的 1 行是 E2E 残留，已清） | **编制管控**：编制人数 / 在岗人数 / 空缺 / 是否超编 | ❌ ql361 **没有**这一层（它无人资模块，其"职务"只是职员档案里的自由文本） |
| 系统岗位（冗余） | `sys_position` + `sys_position_category` + `sys_user_position` | ❌ 无菜单（80531 已改指） | **0 行**（`sys_user_position` 0 行且**全代码库无任何读写入口**；`sys_user.post_id` 全为 NULL） | —（与上两行字段 80% 重叠，能力被 `hr_position` 覆盖） | ❌ 无 |

**裁定**：

1. **本页（90006）保留并已更名「岗位编制」** —— 它承担的是编制管控（对应 SAP `targetFTE + positionControlled`、用友/金蝶「控编方式」），是 ql361 没有的正当代价能力。
2. **`sys_position` 那套确认为冗余**：无菜单、无数据、无引用。按本仓孤儿表流程（**观察 → 改名 `zz_deprecated_*` → 再观察一个周期 → drop**）处理，**不与本轮代码改动同批执行**；`api/position.ts` 与 `views/system/position/index.vue`（1601 行，现无菜单）同步登记为待清理。
3. **改名只动 `menu_name`，不动 `menu_code`（`hr:position`）** —— 后者是权限码前缀（`hr:position:create/list/delete` 已注册且可能已授权），改它会直接断开授权。
4. ⚠️ **本页当前无任何真实数据**（`hr_position` 0 行）。"编制管控"是否需要保留属**产品决策**，不是技术决策 —— 若确认不做编制，本页应整体下线，而不是留着一个空页面。

## 1. 页面概述

「职位管理」承载**岗位（职位）主数据的建档与维护**：定义岗位编码 / 名称 / 级别 / 编制人数 / 职责，供员工档案（`hr_employee.position_id`）与其它 HR 子域引用。

| 页面 | 地址 | 组件 | 行数 | 菜单挂载 | 说明 |
|------|------|------|:----:|:--------:|------|
| 职位管理（列表 + 内嵌弹窗） | `hr/organization/position` | `frontend/apps/pc-admin/src/views/hr/organization/position-list.vue` | 222 | ✅ `90006` | 7 列 / **无查询区** / 无部门列 / 新增·编辑·删除 |
| 组织架构（伴生页，左树 + 右岗位表） | `hr/organization/index` | `views/hr/organization/index.vue` | 273 | ❌ **未挂菜单** | 左部门树 + 右岗位表；岗位弹窗**与上面同一套字段** |

> **⚠️ 菜单名与页面名不一致**：`sys_menu.menu_name` 是「**职位管理**」，而 `position-list.vue:6` 的页面标题与两种情况下的弹窗标题均写「**岗位管理**」/「新增岗位」。同一功能两个名字，建议统一为「职位管理」（业界 SAP 口径 `Position`＝职位，见 §8）。
>
> **⚠️ 伴生页提醒（全站 HR 共性）**：`hr/organization/index.vue` 已在 `router/dynamicRoutes.ts:514` 注册组件映射，**但 `sys_menu` 中不存在任何一行把 `component` 指向 `views/hr/organization/index.vue`**（devdb 实测 `select count(*) from sys_menu where component like '%organization/index%'` = **0**）。
> 路由表由菜单驱动（`transformMenuToRoutes`，`dynamicRoutes.ts:958`），故该页**用户不可达**，只能由开发者在代码中直接 import。详见《组织管理开发文档》。

### 1.2 与系统管理「岗位」的关系（红线，必须先读）

**同一概念在本系统存在两套互不相通的主数据**：

| | **HR 岗位（本页）** | **系统岗位（系统管理）** |
|---|---|---|
| 表 | `hr_position`（17 列） | `sys_position`（16 列）+ `sys_position_category`（14 列）+ `sys_user_position`（5 列） |
| 后端 | `HrController`（类级 `/hr`）→ `HrPositionServiceImpl` | `PositionController`（类级 `/api/position`，**路径正确**）→ `PositionServiceImpl` |
| 前端 api | `api/hr/index.ts` 的 `hrPositionApi` | `api/position.ts` |
| 「级别」语义 | `position_level`（1 高管 / 2 中层 / 3 基层 / 4 普通） | `level`（岗位职级，**与前者不是同一概念**） |
| 岗位分类 | ❌ **无** `category_id` | ✅ 有 `category_id` → `sys_position_category` |
| 与账号的关系 | ❌ **无任何关联表**（HR 岗位**不能分配给系统账号**） | ✅ `sys_user_position`（用户 ↔ 岗位，含 `is_primary`） |
| 谁在用 | `hr_employee.position_id` 指向它（员工档案的岗位） | 系统账号的岗位分配 / 菜单名「岗位权限」 |
| 行数 | 0 | 0 / 0 / 0 |

> **⚠️ P0**：**同一个「岗位」概念两套主数据**，且**没有任何映射表或同步逻辑**。系统管理里建的岗位，HR 下拉里选不到；HR 建的岗位，无法分配给系统账号。
> 菜单名叫「岗位权限」的功能实际走的是**角色 + 岗位分配**（`sys_user_position`），与 HR 的 `hr_position` **完全无关**（见 §8 第 6 行）。
> **收敛方向必须由业务先裁定**：① HR `hr_position` 增加 `category_id` 并**吸收** `sys_position`；或 ② `hr_position` 降级为「职务（Job）」、`sys_position` 保留为「职位（Position）」，按 SAP 三层模型拆分（见 §8 第 1 行）。**在裁定前不得再新增第三套岗位表**。

### 3.2 查询条件

**本页当前**：**无查询区**。`loadData()` 只传 `pageNum` / `pageSize`（`position-list.vue:158`）。
**伴生页当前**：**也无查询区**；仅通过左侧部门树点击触发 `loadPositions()`，并把 `selectedDeptId` 塞进 `params.deptId`（`index.vue:179`）。

> **⚠️ 静默失效 + 无入口（P1）**：后端支持的 `deptId` / `positionName` **本页一个都没接**；伴生页接了 `deptId`，但该页**用户不可达**。

> **⚠️ 缺陷（P1，四处）**
> ① 两页各自维护一份**完全相同语义的 7 列定义**，未抽公共配置，改一处必漏另一处（见《重构搬迁后必须做运行时验证》）。
> ② `POSITION_LEVEL_MAP` 未命中时兜底为 `'基层'` —— 与 DB 默认值 `position_level DEFAULT 3` 巧合一致，但语义上是"错值伪装成合法值"：返回 `null` 或未知级别（如 5）时显示「基层」而非「未知」，**无法察觉脏数据**。建议改 `POSITION_LEVEL_MAP[x] ?? '—'`。
> ③ `status` 只判 `=== 1`，其它值一律「禁用」；DB 允许 `status` 为 NULL（列无 NOT NULL）→ 不可区分"未设置"。
> ④ **无「所属部门」列**：`hr_position.dept_id` 存在且后端支持按 `deptId` 过滤，但列表既不显示部门 ID 也不显示部门名 → 用户**看不出岗位归属**（同型裁定见《员工列表开发文档》§3.4：**直接上 `dept_id` 列会显示雪花 ID，必须由后端 join 出 `deptName`**）。

## 5. 业务规范

### 5.1 状态与值域

| 字段 | 值域 | 当前实现 | 问题 |
|------|------|---------|------|
| `position_level` | `1 高管 / 2 中层 / 3 基层 / 4 普通`（DB 默认 `3`） | DB 注释（`V8.9.0:28`）、前端 `POSITION_LEVEL_MAP`（`api/hr/index.ts:268`）、弹窗选项（`position-list.vue:99-110`）**三处一致** | ✅ 词表一致（少见的一致项） |
| `status` | `0 禁用 / 1 启用`（DB 默认 `1`） | 列表 tag 只判 `=== 1`（`position-list.vue:40`） | ⚠️ 无写入入口；`null` 与 `0` 不可区分 |
| `quota_count` | 整数，DB 默认 `1` | 弹窗 `min=1 max=100` | ⚠️ 前后端约束不一致 |
| `current_count` | 整数，DB 默认 `0` | **全仓无任何写入方** | 🔴 见 §5.3 |

### 5.2 编码规则（当前：无）

- **无号段、无自动生成**：`position_code` 完全由用户手填，**可留空**（弹窗无 required）；`HrController.createPosition` / `updatePosition`（`:62-76`）**不检查编码重复**，`hr_position.position_code` **也无 UNIQUE 约束**（`V8.9.0:16` 仅 `VARCHAR(50)`）→ 可建出多个同编码岗位。
- **对比**：系统管理侧 `PositionServiceImpl.create`（`:100-103`）**有** `getByCode` 唯一性校验并抛「岗位编码已存在」；`sys_position` 同样**无 DB 唯一约束**（靠应用层）。
- **目标规格**：统一走**号段**（`next-no`，形如 `POS + 3 位序号`，租户内唯一）；或至少补应用层唯一校验 + DB 唯一索引 `UNIQUE (tenant_id, position_code) WHERE deleted = 0`。

### 5.3 关键业务规则

| 规则 | 当前 | 目标 |
|------|------|------|
| **编制（Headcount）管控** | 🔴 **形同虚设**：`quota_count`（编制人数）与 `current_count`（在岗人数）**两列都有**，但 `current_count` **在任何员工创建 / 更新 / 离职路径中都不被维护**（全仓 grep `currentCount` / `current_count` 在 `backend/**/*.java` 中**零命中写入方**），**超编也不拦截**（无任何校验代码） | 员工入职/调岗**占用**编制、离职**释放**编制；超编按「允许 / 警告 / 禁止」三档由**规则配置**决定（业界：SAP `positionControlled` + `targetFTE`；用友/金蝶「控编方式 = 允许超编 / 不允许超编」） |
| **删除保护** | 🔴 `removeById(id)` 直接逻辑删除（`HrController.java:78-83`），**不检查是否被 `hr_employee.position_id` 引用**；而系统管理侧 `PositionServiceImpl.delete` **有**引用检查（"该岗位下存在关联用户，无法删除"） | 删除前校验 `hr_employee` 引用；有引用时**改为「停用」**（业界通行做法） |
| **在岗人数统计** | ❌ 无；`current_count` 恒 0；**也无任何统计端点**（无 `/stat`） | 由 `hr_employee` 实时聚合或异步回写；提供 `GET /hr/positions/{id}/stat` |
| **排序** | ⚠️ 后端 `orderByAsc(HrPosition::getSort)`（`HrServiceImpls.java:40`），但 `sort` **无任何写入入口**（UI 无字段） → 全部为 0，**排序恒定失效** | 补排序字段或改为按编码/名称排序 |
| **编码唯一性** | ❌ 无（应用层 + DB 层都无） | 租户内唯一 |
| **岗位级别联动** | ❌ 无（`position_level` 是自由枚举，与薪级/职级序列无任何关联） | 关联职级序列 / 职等（业界建议、本系统未实现） |
| **租户隔离** | ✅ 分页查询显式 `eq(tenantId, ...)`（`HrServiceImpls.java:37`）；新增时 `position.setTenantId(SecurityUtils.getCurrentTenantId())`（`HrController.java:65`）；`PUT` / `DELETE` 依赖**多租户拦截器**自动注入 | 保持 |

> **⚠️ P0：编制两列都是"死列"**
> `quota_count` 由前端弹窗提交写入（Jackson 反序列化 `HrPosition.quotaCount`），**但没有任何代码读它做判断**；
> `current_count` **连写入都没有**，恒为 DB 默认 `0`。
> 结果：「编制人数 / 在岗人数」两列在列表上并排展示，**看起来像编制管理，实际两个数字互不相干、且第二个永远是 0** —— 这比"没有这两列"更危险（会给用户"编制已管控"的错觉）。

## 8. 业界对标（Odoo / SAP / 金蝶 / 用友）

> 本页在 ql361 **无对应页**（该对标系统**无人力资源模块**）。以下为业界标准做法与本系统的差距。
> **参考来源：** Odoo 18 HR `https://www.odoo.com/documentation/18.0/`（章节待补充）；SAP SuccessFactors / S/4HANA HCM `https://help.sap.com/`（章节待补充）；金蝶 s-HR / 金蝶云·星空 `https://vip.kingdee.com/`（章节待补充）；用友 DHR / YonSuite 人力云 `https://success.yonyou.com/`（章节待补充）。
> 详细的业界取证过程见同目录《人力资源-业界做法调研.md》§1.2 / §1.3 / §2.1 / §2.2 / §3.1 / §3.2 / §4.3 / §5.1。

| # | 能力 | 业界做法 | 本系统当前 | 差距与建议 |
|:-:|------|---------|-----------|-----------|
| 1 | **Job / Position / Employee 三层模型** | SAP / Workday 把「**职务 Job（职类）→ 职位 Position（编制单元）→ 员工 Employee（在编人）**」拆成三个对象；SAP 的 Position 是 MDF 独立对象（`code` / `externalName` / `effectiveStatus` / `targetFTE` / `positionControlled` / `parentPosition` 等 49 个标准字段）。Odoo **只有两层**：`hr.job` + `hr.employee`，**没有 Position 这一层** | `hr_position` **同时混了「职务」与「职位」两层语义**（`position_name` / `position_level` 是职务属性，`dept_id` / `quota_count` 是职位属性），**且与 `sys_position` 重复**（§1.2） | **P0**：先做**概念裁定** —— ① 收敛为一套（HR 吸收 `sys_position`，补 `category_id`）；或 ② 按 SAP 拆分 `hr_job`（职务）+ `hr_position`（职位）。**未裁定前不得再动 UI**（否则同时改错两处） |
| 2 | **编制（Headcount）管控** | SAP Position Control：**受管控职位上所有在任者 FTE 之和不得高于职位自身 FTE**，在 5 个时机校验（入职 / 改派职位 / 改 FTE / 改职位 FTE / 职位转移重分类）。金蝶：**强管控 / 弱管控**可选「允许 / 不允许超编」。用友：**事前**（招聘需求发起时校验余量，超编禁止提交）+ **事中**（入职占编、离职释放节点可配置）+ **预警**（满编率超 95% 告警） | 🔴 **编制形同虚设**：`quota_count` / `current_count` 两列都在，但 `current_count` **从不由任何异动维护**（零写入方），**超编不拦截**（无校验代码），**无满编率预警**，**无控编规则配置** | **P0（业务根因）**：① 员工入职/调岗/离职**真实占用与释放** `current_count`；② 增加**控编方式配置**（允许 / 警告 / 禁止）；③ 补满编率预警（可落调度任务）。**两列并排展示会造成"编制已管控"的错觉，比没有更危险** |
| 3 | **组织架构模型** | Odoo `hr.department`：`parent_id` + `child_ids` + **`parent_path`（物化路径，索引）** + `manager_id` + `member_ids` + `total_employee`（含下级总人数）；SAP OM 用 **O-S-P** 三对象模型 | 组织侧 `sys_department` 是最简 `parent_id + ancestors` 树，**无编制、无成本中心、无生效日期**；岗位侧跨部门引用 `dept_id` 但 **UI 无入口**（恒 NULL） | **P1**：`dept_id` 必须补 UI 写入；部门侧建议补 `total_employee` 与「岗位清单」下钻（金蝶「组织岗位联动」） |
| 4 | **组织变更的生效日期与历史版本** | SAP 全模块 **Effective Dating**：Position 带 `effectiveStartDate` / `effectiveEndDate` / `mdfSystemVersionId`，改组织/职位是**新增版本**，可回溯任意时点；金蝶有「岗位变更记录 / 岗位历史版本数据修订」与「组织变动明细查询」 | **完全无**：`hr_position` **只能覆盖式修改**（`updateById`），改完**查不到历史**（无版本、无生效日期、无审计人） | **P1**：引入 `effective_start_date` / `effective_end_date` 或岗位变更历史表；至少先让 `update_by` / `update_time` 真实落库 |
| 5 | **岗位职级体系** | 有「职级序列 / 职等职级 / 职务等级」主数据：SAP `Job Family` / `Job Level` / `payGrade` / `payRange`；金蝶「岗位的职级职等与职位的职级职等的关联关系」；Workday `job profile → job family → job family group` 三层 | `position_level` 只有 **4 个硬编码档位**（1 高管 / 2 中层 / 3 基层 / 4 普通），**无职级序列、无职等、无薪级关联** | **P1**：建职级序列主数据（`hr_job_grade` / `hr_job_family`）；并与薪资标准挂钩（当前 `hr_salary_structure` 只挂员工、不挂岗位） |
| 6 | **岗位与权限的关系** | SAP **RBP**：**不是**把权限挂在「岗位权限表」上，而是「**权限组（谁被授予）× 权限角色（一组权限）× 目标人群（对谁生效）**」的**三元授权**，「谁」可由**动态条件**（部门 / 国家 / 职务代码）自动圈定 | 菜单里确有「**岗位权限**」功能，但它走**系统管理的角色 / 岗位分配**（`sys_position` + `sys_user_position`），**与 `hr_position` 零关联** | ⚠️ **不要**为了「让岗位有用」而把 `hr_position` 直连权限表 —— 业界没有这种模型。若要打通，应让 HR 岗位**成为权限的「目标人群」条件之一**，而不是权限的宿主 |
| 7 | **部门与人员统计** | 组织架构页标配「**每部门人数、编制数、缺口数**」汇总并支持下钻（用友「超缺员统计 + 可视化看板 + 数据穿透」） | **无任何统计端点**（岗位 5 个端点里没有 `/stat`）；前端也无统计卡 | **P1**：补 `GET /api/hr/positions/stat`（编制 / 在岗 / 缺口）+ 页头统计卡 |
| 8 | **岗位空缺与招聘联动** | Odoo `hr.job.no_of_recruitment`（Target＝计划招聘人数），`expected_employees = 在岗 + 计划招聘`；用友「招聘需求发起时自动校验编制余量，超编禁止提交」 | **无**：`hr_position` 无「计划招聘数」列，**无空缺数计算**，与招聘模块**零联动** | **P1**：补 `planned_count`（计划招聘）列；`expected = current_count + planned_count`（照 Odoo 口径，注意这是「算得出但拦不下」的轻量替身，真正拦截在 §2 条） |

**明确不借鉴**：业界界面视觉样式；SAP 的多公司/多国职务矩阵（本系统无多公司场景）；SAP Position 的 30 个自定义字段额度机制（本系统无 MDF 元数据平台）。

## 10. 验收标准（目标）

> 本模块**尚无 E2E 脚本**（`tools/` 目录下无任何 `e2e-hr*.cjs`）。以下为按金标准制定的验收清单。
> **前置条件（重要）**：所有 HR 表**当前 0 行**（`hr_position` = 0；`sys_position` = 0），故任何验收**必须先造数**（至少 1 个 `sys_department` 行 + 1 个岗位），并**在收尾时清理自产数据**（参见《共享db E2E 断言必须加作用域》）。

### 10.1 接口验收（目标 ≥ 15 项）

1. `GET /api/hr/positions/page` 返回 200（**当前应为 404，修复 P0-1 后才成立**）—— 这一条本身就是 P0-1 的回归断言。
2. 默认查询 `total` 与直查 DB（`deleted = 0` + `tenant_id = 当前租户`）**逐值一致**；`pageNum` / `pageSize` 生效（`pageSize=1` 时 `records.length === 1`）。
3. `deptId` 与 `positionName` 过滤各自生效（造 2 个部门各 1 个岗位验证前者）。
4. `POST /api/hr/positions` 后 DB 新增 1 行，`tenant_id` 非空、`position_name` 与提交一致；`PUT /{id}` 改名后三级回读（DB / 详情 `GET /{id}` / 列表）一致；`DELETE /{id}` 后列表不出现（逻辑删 `deleted = 1`）。
5. **排序**：`ORDER BY sort ASC` 生效（当前因 `sort` 全 0 而无可观测效果 —— 此项在补 `sort` 写入后才有意义）。
6. **删除引用保护**：被 `hr_employee.position_id` 引用的岗位**不可删除**（目标行为；当前应允许删除，作为 P0 证据）。
7. `GET /api/hr/positions/{id}` 不存在时返回明确错误而非 200 空对象（当前 `getById` 返回 null 但 `Result.success(null)`）。
8. `PUT /api/hr/positions/{id}/status` 改状态后 DB 一致（**目标端点**，当前 404）。
9. `GET /api/hr/positions/stat` 返回编制 / 在岗 / 缺口（**目标端点**）。
10. **编制占用联动**：员工入职后 `current_count +1`；离职后 `-1`（**目标行为**，当前恒 0 —— 此项即 P0 编制缺陷的回归断言）。
11. `GET /api/hr/positions/dept/{deptId}` 返回该部门岗位（**接线 `getByDeptId` 后**，同时验证 P0-2 已修）。
12. 越权/未登录：未带 token 请求应 401（**当前 `HrController` 无鉴权注解，此项预期失败**，作为 P1 证据）。

### 10.2 UI 验收（目标 ≥ 10 项）

1. 菜单 `人力资源 → 组织管理 → 职位管理` 点开落在本页，**页面不空白**（目录节点透传组件已就位，见 `dynamicRoutes.ts:945-957` 同类机制）。
2. 页面**控制台无 error**（含 `ReferenceError` —— 参见《重构搬迁后必须做运行时验证》）；**断言网络无 4xx**（`GET /api/hr/positions/page` 必须 200）。
3. 表格 7 列渲染正确；「岗位级别」显示**中文标签**而非数字；「状态」显示启用/禁用 tag。
4. 查询区为**横向自适应网格**（不得纵向单列），`部门` / `岗位名称` 两项**逐个生效**。

## 12. 剩余缺口（不阻塞，如实登记）

1. **整个 HR 模块端点 404**（P0-1）—— 最高优先，一行修复但影响 5 个菜单页。
2. **`hr-base` 无 mapper XML**（P0-2）—— 10 个自定义方法全无绑定（含 `HrPositionMapper.selectByDeptId`）。
3. **`dept_id` 无 UI 写入入口**（P0）—— 岗位无法归属部门，是「组织管理」页树-表联动失效的根因。
4. **编制两列名存实亡**（P0）—— `current_count` 零写入、超编零拦截、无控编规则、无满编预警。
5. **两套岗位主数据**（P0）—— `hr_position` ↔ `sys_position` 零映射，须业务裁定收敛方向。
6. **无生效日期 / 无历史版本**（P1）—— 岗位覆盖式修改，改完查不到历史。
7. **无职级体系**（P1）—— `position_level` 4 个硬编码档位，无职级序列 / 职等 / 薪级关联。
8. **删除无引用保护**、**`sort` 写入入口缺失导致排序恒失效**、**`status` 无停用入口**（P1）。
9. **无统计端点**（编制 / 在岗 / 缺口 / 满编率）。
10. **HR 权限码 0 条**、`HrController` 无鉴权注解；**`create_by` / `update_by` 恒 NULL**；**无 DTO / VO / 参数校验**（17 列实体裸暴露，与系统管理侧 `PositionController` 形成鲜明对比）。
11. **整页未达金标准路线 A**；伴生页 `index.vue` 未挂菜单（孤儿页面，详见《组织管理开发文档》）；**无模块级 E2E、无验收截图**；菜单 `menu_level = 0` 未回填。
