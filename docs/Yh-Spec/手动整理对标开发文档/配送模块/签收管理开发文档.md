## 3. 金标准目标设计

### 3.1 页面结构（金标准）

`CategoryListLayout`（无分类树）+ `BillTableList`（序号齿轮列配置，`storage-key` = `dms-sign-columns`）+ `PageConfigPanel`。

```
工具栏：页面配置 | 批量审核 | 刷新 | 导出
├─ 签收台账（列表，默认按签收时间倒序）
└─ 行级：查看详情（照片/签名/位置对比图） | 审核（通过/驳回）
```

### 3.2 列表列配置（建议；★ = 默认显示）

| 列 | 说明 |
|----|------|
| ★ 任务编号 | `taskId` → 联查 `taskNo` |
| ★ 配送员 | 姓名 + 电话（非 ID） |
| ★ 客户 | 客户名称 |
| ★ 签收类型 | 正常 / 部分 / 拒收（标签色） |
| ★ 签收时间 | `signTime` |
| ★ 位置偏差 | `deviation` 米 + 超阈值红标 |
| ★ 凭证 | 照片数 / 有无签名（图标） |
| ★ 审核状态 | 待审核 / 通过 / 驳回 |
| 签收位置 | 经纬度 |
| 客户位置 | 经纬度 |
| 审核人/审核时间/审核备注 | 审计列 |

### 3.3 查询条件与功能按钮

- **查询条件**：任务编号、配送员（选择器）、客户、签收类型（多选）、审核状态（多选）、签收时间范围、**仅看超阈值**（勾选）、有无签名/照片。
- **功能按钮**：批量审核（通过/驳回）、刷新、导出、**超阈值清单导出**。

### 3.4 审核流转（关键缺口）

```
提交签收（配送员端） → 待审核(0) ──通过──> 已通过(1) ──> 触发结算/代收货款确认
                              └──驳回──> 已驳回(2) ──> 通知配送员重新签收
```

- **驳回原因必填**；驳回后可**重新签收**（同任务允许多条签收记录，取最新有效）。
- **审核通过后**：任务置「已签收」→ 触发《配送结算》《收款管理》。

### 3.5 后端接口（金标准）

| 接口 | 说明 |
|------|------|
| `GET /api/dms/sign/page` | **台账分页**（多条件 + 联查任务/配送员/客户） |
| `GET /api/dms/sign/{taskId}` | 按任务查（已有） |
| `POST /api/dms/sign/{id}/audit` | **审核**（`auditStatus` + `auditRemark`） |
| `POST /api/dms/sign/batch-audit` | 批量审核 |
| `GET /api/dms/sign/stat` | 签收统计（签收率、超阈值率、拒收率） |
| `GET /api/dms/sign/export` | 导出 xlsx |

### 3.6 业务规范与注意事项（**重点**）

1. **签收四要素**（业界标准，缺一不可）：**照片 + 手写签名 + 定位 + 时间戳**。本系统四要素字段齐全（`photoUrls/signatureUrl/signLat,signLng/signTime`），**产品需明确哪些场景强制**（如拒收必须拍照 + 备注）。
2. **位置偏差校验**：`deviationThresh` 默认 **100 米**，超阈值置 `deviationExceeded`。⚠️ **注意**：该值应为**可配置参数**（落《配送参数》），不同场景（园区/写字楼 GPS 漂移）阈值不同；超阈值**不应直接拒绝签收**，而是标记待人工复核（现状未明确）。
3. **签收类型语义**：正常 / **部分签收** / **拒收**——部分签收需记录**实际数量**（当前 `DmsSign` 无数量字段，⚠️ **缺口**，影响后续结算按实际数量计费）。
4. **拒收处理**：拒收后货物需回仓（联动《物流退货收货》），任务不应直接置"已完成"。
5. **与任务状态联动**：审核通过后 `DmsTask.status → 5 已签收 / 6 已完成`；**审核未通过前任务不得进入"已完成"**（避免未妥投就算完成）。
6. **代收货款联动**：签收类型=正常且任务有代收货款 → 触发《收款管理》待收；拒收 → 冲销。
7. **凭证合规**：签收照片/签名属**客户凭证**，需按保留期归档、可下载举证（纠纷处理）。
8. **双端一致性**：司机端提交的参数（`signType`、坐标、照片）与管理端展示**必须同一套枚举**，禁止两端各自定义。
9. **幂等**：同一任务重复提交签收（网络重试）应幂等，避免重复记录。

### 6.5 与运力池的联动：交付即释放（✅ 2026-09-14）

签收是**交付动作**，而审核是**后台动作（可能滞后数小时）**，两者不能绑在同一时刻决定运力占用：

| 时点 | 任务状态 | 配送员状态（`dms_rider.status`） |
|------|---------|--------------------------------|
| 提交签收 `POST /api/dms/sign/submit` | 配送中(4) → 已签收(5) | **释放**：名下无其它在途单 → 空闲(1)（`TaskService.releaseRiderIfIdle`） |
| 审核驳回 `POST /api/dms/sign/{id}/audit {auditStatus:2}` | 已签收(5) → 配送中(4) | **重新占用**：忙碌(2)（`TaskService.markRiderBusy`；休息中不覆盖） |
| 删除待审核签收 `DELETE /api/dms/sign/{id}` | 已签收(5) → 配送中(4) | **重新占用**：忙碌(2) |
| 审核通过 | 已签收(5) → 已完成(6) | 保持空闲（已在提交时释放） |

**Why**：自动派单候选池默认只取「空闲(1)」（`dms.dispatch.require.online=true`）。若把释放点放在「审核通过」，
未审核的签收会让配送员一直挂在「忙碌」→ 运力池被台账拖住（同一缺陷类的延迟版）。
**不变式**：`空闲 ⟺ 名下无在途任务(1/2/3/4)`；释放/占用都由 `TaskService` 单一出口负责，页面与其它模块不要各自 `set status`。
验收见《调度任务开发文档》§8.7（`e2e-dms-dispatch-task.cjs` 的「交付即释放运力」段：提交释放 / 驳回重占 / 重新签收 / 通过保持空闲 / 仍有余单不得误释放）。

### 7.3 后端配套改进（`SignService`）

1. **客户坐标回落任务快照**：司机端不掌握客户坐标（也不应自行回传），请求未带 `customerLat/Lng` 时回落到 `dms_task.customer_lat/lng` 再算偏差。

   首次提交后任务已置「已签收(5)」，原顺序会把重复提交报成「任务状态不允许签收」，掩盖真实原因（重复提交）。
