## 1. 页面概述

本页是外勤拜访的第二段（Do）：把一次实际拜访落成**执行记录**（签到打卡），可关联「拜访规划」里的计划，并在保存时**由后端把关联计划置为已完成**。

| 页面 | 地址 | 组件 | 行数 | 说明 |
|------|------|------|:----:|------|
| 拜访规划 | `sales/visit-plan` | `views/sales/visit-plan/index.vue` | 387 | 计划台账 + 新建/编辑弹窗 |
| **拜访执行（本页）** | `sales/visit-exec` | `views/sales/visit-exec/index.vue` | 442 | 10 列台账 + 签到打卡/编辑弹窗；**无统计卡** |
| 拜访检视 | `sales/visit-review` | `views/sales/visit-review/index.vue` | 140 | 只读检视 + 7 张统计卡 |

### 1.1 本页在闭环中的位置（亮点：真实回写）

```
[crm_visit_plan] ──① planId 选择──▶ [本页弹窗「签到打卡」]
   status 0/1                            │ ② POST /api/crm/visit/record
      ▲                                  ▼
      └── ④ 计划 status := 2 已完成 ◀── [crm_visit_record] ──▶ ③ 「拜访检视」聚合统计
                    (VisitRecordServiceImpl.java:50-56)
```

`VisitRecordServiceImpl.checkIn()`（`:43-58`）标注 `@Transactional(rollbackFor = Exception.class)`：同一事务内先 `insert` 记录，再（`planId` 非空时）`plan.setStatus(2)` + `updateById`；并有两个跳过分支 —— `plan == null`（`:51-52`）与 `plan.getDeleted() != 0`（`:52`）。`visitTime` 仅在为 `null` 时补 `LocalDateTime.now()`（`:45-47`）。

配套前端联动：选中「关联计划」后 `handlePlanChange`（`:330-337`）**自动带出** `customerId`/`salesPersonId`，并在计划有地址且表单未填地点时补 `location`。**这是本模块最值得肯定的实现。**

### 1.2 菜单归属「名实不符」（与另两页同源）

菜单挂载在 `CRM → 外勤拜访`，但 `menu_code = sales:visit-exec`、路由 `sales/visit-exec`、组件在 `views/sales/` 下，**接口却是 `/api/crm/visit/record/*`** —— 即「菜单在 CRM、代码在 sales、接口在 crm」。

> **收敛建议**：`menu_code` 改 `crm:visit-exec`。已核实（《拜访规划开发文档》§1.2）`menu_code` 仅用于唯一性检查与按码查询，**角色授权按 `menu_id`** 关联 `sys_role_menu` → 改码**不影响已下发权限**。

### 1.3 与 ERP「客户」的边界

「客户」下拉走 `crmCustomerApi.dropdown` → `GET /api/customer/dropdown`，即 **CRM 客户**（`crm_customer`，客户全量池），**不是** ERP 往来单位（`biz_party`）。外勤拜访属客户服务与维护环节，取 CRM 客户**正确**；本页不产出任何 ERP 单据，不写库存/应收。

| **计划 ↔ 客户一致性** | ❌ **不校验**：选计划后仍可**改客户**，保存时 `planId` 照传 → 记录挂客户乙、计划甲被置完成 | 🔴 见下 |
| **一计划多次打卡** | ❌ 无唯一约束、`checkIn` 不判重 | ⚠️ 覆盖率虚高、责任不清 |
| **删除记录回滚计划状态** | ❌ **不回滚** | 🔴 **单向门**：误打卡后删记录，计划**永久停在已完成**；而计划一旦为 `2` 就**无法取消**（`cancel` 拒绝），编辑又不写 `status` → **实际只能改库恢复** |
| 打卡时间可信度 | ❌ 用户手选 | 无法用于迟到/时长分析 |
| 结果/内容必填 | ✅ 前端必填；后端**不校验**（直连 API 可写 `null` 或 `9`） | ⚠️ 值域应收口到后端 |
| 客户必填 | ✅ 前端必填；DB `customer_id` **可空** | ⚠️ |
| 权限 / 数据权限 | ❌ **无 `v-permission`、后端无鉴权注解、无按登录人过滤** | ⚠️ 任何能打开本页者可对**任意客户/计划**打卡、删他人记录 |

> 🔴 **数据错位（P0 级风险）**：`handlePlanChange` 带出客户后，`customerId` 的 select **仍可编辑**（`:93-104` 无 `disabled`），保存时 `planId` 与 `customerId` **各自独立提交**，后端不做交叉校验 → 产生「计划甲已完成、记录挂客户乙」的**不一致数据**，而列表无 `planId` 列 → **两条数据都看不出问题**。
> **修法**：① 选定计划后把 `customerId`/`salesPersonId` 置 `disabled`（或改只读展示）；② 后端 `checkIn` 校验 `record.customerId == plan.customerId`，不一致 400。

### 5.3 计划完成是单向门（与配送模块同型缺陷）

| 动作 | 计划状态影响 |
|------|-------------|
| 打卡（`planId` 非空） | `0/1 → 2 已完成` |
| 删除该打卡记录 | **不变**（仍 2） |
| 编辑记录换 `planId` | **旧计划仍 2，新计划不被置 2**（`updateRecord` 仅 `updateById`，无联动） |
| 取消计划 | 仅 `status != 2` 才生效 → **已完成的无法取消** |

> 与《配送模块》「配送员忙碌是单向门」（`releaseRiderIfIdle`）属同类设计缺口：状态回写**只进不出**。建议 `DELETE /record/{id}` 与换绑 `planId` 时补「该计划已无其它有效记录 → 恢复 `0 待执行`」的释放逻辑。

### 5.4 跨模块联动

| 方向 | 联动 | 状态 |
|------|------|------|
| → 拜访规划 | 打卡置计划 `status = 2` | ✅ |
| → 拜访检视 | 检视页聚合本表（结果分布/按日计数/今日/本周） | ✅ |
| → CRM 客户 | `GET /api/customer/dropdown`（启用客户，LIMIT 200） | ⚠️ 上限 200 |
| → 跟进记录 | 无 | ❌ 见 §8 |
| → 商机/合同 | 无（「下一步行动」无处流转） | ❌ |

## 7. 数据模型

### 7.1 `crm_visit_record`（**20 列**，devdb 实测 2026-09-18）

```
id, tenant_id, plan_id, customer_id, customer_name, sales_person_id, sales_person_name,
visit_time, visit_type, location, longitude, latitude, content, result,
next_action, next_visit_date, attachments, create_time, update_time, deleted
```

| 列 | 类型 | 可空 | 默认 | 说明 |
|----|------|:----:|------|------|
| `id` | `bigint` | NO | `nextval('crm_visit_record_id_seq')` | **自增**（`@TableId(IdType.AUTO)`，`VisitRecord.java:19-20`）→ 前端 `number` 传 id 安全（**不涉及**雪花 ID 精度陷阱） |
| `tenant_id` | `bigint` | YES | null | 由 `MetaObjectHandler` 注入 |
| `plan_id` | `bigint` | YES | null | 关联计划；**无外键、无唯一约束** |

| `visit_type` / `result` | `integer` | YES | null | **可空且无 CHECK** → 可写任意整数 |
| `location` | `varchar` | YES | null | **自由文本**（无地理语义） |
| `longitude` / `latitude` | `numeric` | YES | null | 🔴 **全链路零读写**（§4.4） |
| `attachments` | `text` | YES | null | 🔴 **全链路零读写**（实体注释「附件URL json数组」） |
| `content` | **`text`** | YES | null | 长文本 ✅（对比 `location`/`next_action` 是 `varchar`） |
| `create_time` / `update_time` | `timestamp` | YES | `CURRENT_TIMESTAMP` | 见 §7.2 |
| `deleted` | `integer` | NO | 0 | `@TableLogic`（`VisitRecord.java:62-63`） |
| **无 `version`** | — | — | — | 🔴 本表**没有乐观锁列**（对比 `crm_visit_plan` 有），实体也未声明 `@Version` → `updateById` 为**后写覆盖** |

**索引（实测）**：`pkey(id)`、`idx_..._plan(plan_id)`、`idx_..._customer(customer_id)`、`idx_..._sales_person(sales_person_id)`、`idx_..._time(visit_time)`、`idx_..._result(result)` → 查询 3 个维度与时间列**均有索引** ✅。**无任何 UNIQUE 索引**（「一计划多打卡」在库层完全放行）。

### 7.2 审计列（本表比规划表健康）

| 列 | 填充机制 | 结论 |
|----|---------|------|
| `create_time` | 实体 `@TableField(fill = FieldFill.INSERT)`（`:56-57`）+ 填充器 `strictInsertFill("createTime", …)`（`MyBatisPlusConfig.java:171`） | ✅ **字段名命中** → 应用层写入 |
| `update_time` | 实体 `@TableField(fill = FieldFill.UPDATE)`（`:59-60`）+ `strictUpdateFill("updateTime", …)`（`:190`） | ✅ 每次 `updateById` **被正确刷新** |
| 操作人 | 无 `created_by`/`updated_by` 列 | ⚠️ 无法追溯「谁打的卡/谁改的」（只能靠 `sales_person_id` 间接推断） |

> **对照结论**：同模块 `crm_visit_plan` 用 `created_at`/`updated_at`（**不在填充器名单内**）→ `updated_at` 永不刷新；本表用 `create_time`/`update_time`（**在名单内**）→ 正常刷新。**这是"命名决定行为"的实证**（详见《拜访规划开发文档》§7.2）。新增实体务必用这两个字段名，或同步扩填充器。

### 7.3 当前数据现状

`crm_visit_record` → **0 行**；`crm_visit_plan` → **0 行**。本页当前呈现空态 `暂无拜访执行数据`（`:11`）。**验收前必须先造数据**（建议 ≥ 10 条，覆盖 `visitType 1/2/3` × `result 1/2/3` × 有/无 `planId` × 有/无 `nextVisitDate`）。

## 10. 验收标准（目标）

> 本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下**不存在** `e2e-crm*.cjs`）。落地脚本 `tools/e2e-crm.cjs`（界面 + 接口 + 直连 DB 对账 + 写库后复原）。

### 10.1 接口验收（建议 ≥ 16 项）

① `GET /record/page` 默认 200，`total` 与直查 DB（`deleted = 0` + 租户条件）一致；② `page`/`size` 生效（`size=1` → 1 条），`pageNum`/`pageSize` **同样生效**；③ `customerId`/`salesPersonId`/`result`/`visitDateStart`/`visitDateEnd` **逐参数生效**；④ **时间区间语义**：`start = end = 今天` 时今天 00:00~23:59 记录**全部命中**（`ge(start 00:00)` + `lt(end+1天 00:00)`，`VisitRecordServiceImpl.java:152-157`）；⑤ 排序 `visit_time DESC`（`:38`）；⑥ **不带** `visitTime` → DB 被后端补为当前时间（`:45-47`）；⑦ **带** `visitTime` → 后端**原样保存**（断言现状；修复后应改为服务端时间戳并改断言）；⑧ 带 `planId` → **同一事务**内 DB `crm_visit_plan.status = 2`（回读确认）；⑨ 带**不存在的** `planId` → 记录仍插入成功、计划不变（`plan == null` 分支，`:51-52`）；⑩ 带**已逻辑删**的计划 id → 计划**不被改动**（`deleted != 0` 分支）；⑪ **不一致校验（修复后断言）**：`planId` 的客户 ≠ `customerId` → 400；当前行为是**照常写入 + 计划被置完成**（先断言现状为缺陷）；⑫ `PUT /record/{id}` 改 `content` → DB 一致且 **`update_time` 被刷新**（填充器生效）；⑬ `PUT /record/{id}` 换 `planId` → 当前**旧计划仍为 2、新计划不被置 2**（断言现状）；⑭ `DELETE /record/{id}` → DB `deleted = 1`，列表与 `total` 不再出现，**关联计划状态不变**（断言现状）；⑮ 直连 API 写 `result = 9` / `visitType = 9` → 当前**能写进去**（断言值域未收口，修复后应 400）；⑯ **写库隔离**：所有写断言按原值**复原**（尤其 `crm_visit_plan.status`），或使用专用测试客户/计划。

> 2026-09-18 更新：⑦ 带 `visitTime` 仍**原样保存**（服务端时间戳未做）；⑪ 计划与客户的一致性校验**仍未做**（选计划后客户仍可改、后端不交叉校验）→ 这两条仍按「断言现状」执行。

### 10.2 UI 验收（建议 ≥ 19 项）

① 菜单 `CRM → 外勤拜访 → 拜访执行`（`70002`）点开落在 `sales/visit-exec`，**无配对标签页**；② 标题「拜访执行」，**无统计卡**；③ 查询区 4 项渲染（客户/负责人/结果 3 个 select **有可见 label**，拜访日期区间**无可见 label**）；④ 表格 10 列，拜访方式 tag（上门蓝/电话青/其他灰）、结果 tag（有意向绿/一般橙/无意向红）文案正确，非法值回退 `-` + 灰 tag；⑤ 「打卡时间」列显示 `YYYY-MM-DD HH:mm`，空值 `-`；⑥ 客户下拉有值、支持中文过滤；负责人 label = `nickname || username`；⑦ 查询 4 项**逐个生效**（含只填单边日期）；⑧ 重置清空 4 项并回第 1 页；分页参数为 **`page`/`size`**；⑨ 导出 `拜访执行_*.csv`、UTF-8 BOM、**表头 9 列**（不含「操作」）；⑩ `签到打卡` → 标题「签到打卡」→ 不填直接确定 → 五条校验文案**逐字**出现：`请选择客户`/`请选择负责人`/`请选择拜访方式`/`请输入拜访内容`/`请选择拜访结果`；⑪ 弹窗默认值：拜访方式 = **上门**；打卡时间 = **打开弹窗的当前时刻**（格式 `YYYY-MM-DDTHH:mm:ss`）；⑫ 「关联计划」下拉 label 格式 `计划号｜客户名｜计划日期`，**只列待执行/执行中的计划**；⑬ 选中计划 → **客户/负责人被自动带出**；计划有地址且地点为空 → **地点被自动填充**；地点已有值 → **不被覆盖**；⑭ 完整填写 → 确定 → 提示「打卡成功」→ 列表出现新行且客户/负责人显示**中文名称**，**断言网络无 4xx**；⑮ **闭环**：打卡（关联计划）→ 到「拜访规划」页该计划变「已完成」；再回本页，该记录的「编辑」弹窗中「关联计划」**当前显示为裸 ID**（登记为缺陷，修复后应显示 `计划号｜客户｜日期`）；⑯ 编辑 → 标题「编辑拜访记录」→ 10 个字段**逐字段回填正确** → 保存提示「拜访记录更新成功」；⑰ 「删除」确认框逐字为 `确认删除该拜访记录？`/ok `删除`/cancel `取消`，确认后行消失；⑱ 无计划的临时拜访（`planId` 留空）可正常打卡成功；⑲ 页面控制台**无 error**，**断言网络无 4xx**（4 个业务端点 + 3 个下拉依赖全部 200）。

> 2026-09-18 更新：③ 拜访日期区间**已有可见 label** → 改断言；⑨ 导出表头改为 **10 列（含「关联计划」）** 且套中文文案 → 改断言；⑮ 「编辑」弹窗的「关联计划」**已不再显示裸 ID**（`extraPlans` 并入下拉）→ 改断言；另需扩充断言集：弹窗「定位」行与「获取定位」按钮（拒绝授权时应提示且不留假坐标）、「定位坐标」列（默认隐藏）、表头齿轮、页面配置弹窗、经典分页栏、打印(F8)。

## 12. 剩余缺口（不阻塞，如实登记）

1. **无定位打卡 / 无地理围栏 / 无现场照片 / 时间戳不可信** —— **本模块最大能力缺口**；三项所需列（`longitude`/`latitude`/`attachments`）**均已存在**，补齐属「接线」而非「建模」。
2. **计划与客户的一致性无校验** —— 可产出「计划甲完成、记录挂客户乙」的错位数据，且列表无从察觉。
3. **计划完成是单向门** —— 删记录/换计划不回滚；已完成计划无法取消。同型问题在《配送模块》已有先例。
4. **一计划可多次打卡**（库层无唯一约束）。
5. **与跟进记录零联动** —— 客户 360 时间轴缺拜访事件。
6. **拜访时长无法计算** —— **无起止时间列、无 duration 列** → **无数据源，不得伪造**；如需须业务先裁定新增列。
7. **拜访方式/结果无字典表**，后端不校验值域。
8. **无数据权限、无权限码**。
9. **关联计划下拉漏项**（200 条上限 + 客户端过滤）；编辑时显示裸 ID。
10. **无「拜访方式」/「关联计划」筛选**。
11. **路线排程未复用配送模块能力** —— 建议复用，**不新建**。
12. **无异常打卡识别** —— 需先补定位，再配合《拜访检视开发文档》的异常口径。
13. **审计不足**：无操作人列；无 `version` 乐观锁。
14. **菜单名实不符**（`sales:*` 挂在 CRM 下）。
15. **外壳为路线 B**，整体未达金标准。
16. **后端值域收口缺失**：`result`/`visitType` 可写任意整数，`customer_id`/`visit_time` 可空。
17. **离线打卡判 N/A**（PC 管理端无此场景，APP 端能力不在本轮范围）。
18. **无模块级 E2E、无验收截图资产**。
