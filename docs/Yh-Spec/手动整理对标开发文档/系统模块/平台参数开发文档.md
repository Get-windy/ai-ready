## 1. 页面概述

平台参数页是**平台运营方的全局键值参数台账**：一张**前端切片分页的裸 `a-table`**（8 列）+ 3 个查询条件（其中 1 个是**纯前端过滤**）+ 4 个功能按钮（其中「刷新缓存」是**只打日志的空实现**）+ 2 个弹窗（「编辑参数」可改值、「变更日志」只读）。它属于 `61306 平台设置` 组的第 1 页（`sort=100`）。

> **一句话定性**：**页面之下是一层「看起来像配置中心、实际是内存 Map」的假实现** —— 后端 `SystemConfigServiceImpl` 用 `static final Map` `BUILTIN_CONFIGS`（**11 条**）实现全部读写，**全程不碰任何数据库表**；而 DB 里那张 17 列 / 8 行的 `sys_config` 是**孤儿表**（无任何 Java 实体/Mapper 映射它）→ **页面改的配置重启即失，DB 里那 8 行永远读不到**。这是本页的根级 P0。

> **⚠️ 跨模块重复（P0，README §4 已登记）**：**平台参数（62501）与设置模块的系统参数（80621）共用同一个「内存假实现」** —— 两侧最终都打到 `SystemConfigController` 的 `/api/config/*`（`SystemConfigController.java:21`）。
> - 本页走 `platformConfigApi`：`api/admin.ts:22/44/59` 的 `API_PREFIX='/api'` + **原生 axios**（不享受 `utils/request.ts` 拦截器）；
> - 系统参数页走 `configApi`：`api/config.ts:31/36/41/...` 的 `request.get('/config/page')` 等（**标准 `request` 实例**）；
> - **两条路径指向同一个内存 Map** → **同一条参数在「系统」和「设置」两个菜单里看到、改的都是同一份内存数据，且都重启即失**。
>
> **⚠️ 参数键两套、互不相干（本页第二个结构性问题）**：内存 `BUILTIN_CONFIGS` 的 11 个 key（如 `system.name`）与 DB `sys_config` 的 8 个 key（如 `system.title`）**完全不同**（对照见 §7.2 与 §7.3）→ 即使将来把表接上，也必须先做一次 key 对齐迁移。

## 10. 验收标准（目标）

> **前置**：本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下不存在 `e2e-system-*.cjs` / `e2e-admin-*.cjs`）。脚本建议命名 `tools/e2e-system.cjs`（接口 + 直连 DB 对账 + 写库后复原 + Playwright UI 截屏，参照 `tools/e2e-crm.cjs`）。
> **⚠️ 本页验收的四条前提**：
> 1. **本页的"写"不落库** → 写路径断言必须**同时断言「DB 未变化」**（否则会把桩行为误判为成功）；
> 2. **不得真的改坏共享环境里的参数值** —— 建议只改 `system.version`（无业务影响的展示参数），改前记录原值、改后**按原值复原**（复原方式：重跑/重启后端即回到内存初值 `1.0.0`）；
> 3. **不要发送任何测试邮件/短信**（本页无此动作，但 `notification.email.enabled` 之类的参数不要改成奇怪的值）；
> 4. **权限账号**：`admin`（`id=1`，`tenant_id=1`，SUPER_ADMIN）作 **200 基线**；另需一个**非超管账号**做 **403 / 空表 对账**（菜单 `system-admin` 域对非超管不可见）。

### 10.1 接口验收（**22 项**）

**可达性与超管豁免对照（①–⑤）**

① 用 `admin` 登录（**必须重新登录拿到新 token**，见 README §1.3 红线②）→ `GET /api/config/list` → **期望 200**；断言返回体是**数组**（非分页包装），**长度 = 11**（内存 11 条）。
② 🎯 **超管（重登后）能查到 ≥ 11 行的对照断言**：断言 ① 的数组长度 `≥ 11`，且其中**包含** `system.name` / `system.version` / `system.logo` / `security.login.maxAttempts` / `security.login.lockTime` / `security.password.minLength` / `security.session.timeout` / `upload.maxSize` / `upload.allowedTypes` / `notification.email.enabled` / `notification.sms.enabled` 这 11 个 `configKey`（逐一断言，顺序按 `LinkedHashMap` 插入序）。
③ 🎯 **非超管 / 旧 token 的对照断言（本模块最易误判处）**：
   - (a) 用**旧 token**（改动前签发、未重登）调 `GET /api/config/list` → **期望 200 但数组为空**（`tenantScopeExempt` 未写入 → 被收敛；本页虽不查表，但要断言「同一账号两种 token 的结果不同」这一现象**在本页是否出现**，以此确认豁免链的适用范围）；
   - (b) 用一个**非超管账号**调同一端点 → 断言**菜单树里没有 62501**（`GET /api/menu/user/mega/tenant-admin` 返回里不含平台设置组）→ 页面根本不可达。
   > **口径提醒**：本页**不读任何表**，因此「租户插件过滤导致 0 行」的经典症状在本页**理论上不出现**；本节的价值是**反向确证**——把「本页为什么不会 0 行」写成可执行断言，避免评审时与同组其余 4 页混为一谈。
④ 未带 `Authorization` 调任一端点 → **期望 401**。
⑤ 断言 `GET /api/config/list` 的**双路径等价**：分别用 `platformConfigApi`（`api/admin.ts`，原生 axios + `adminHeaders()`）与 `configApi`（`api/config.ts`，标准 `request`）调同一端点，**断言两次返回的 11 条 `configKey` 集合完全相同** → **确证「平台参数与系统参数共用同一内存实现」**（§1.1、§12 P0-⑥）。

**查询与过滤（⑥–⑨）**

⑥ `GET /api/config/list?configType=system` → 断言只返回 `configType='system'` 的 **5 条**（`system.name` / `system.version` / `system.logo` / `upload.maxSize` / `upload.allowedTypes`）。
⑦ `GET /api/config/list?configGroup=upload` → 断言返回 **2 条**（`upload.maxSize` / `upload.allowedTypes`）；`configType=system&configGroup=upload` → 同样 2 条（AND 语义）。
⑧ `GET /api/config/types` → 断言返回 **5 项**且 `value` 集合 = {`system`,`security`,`business`,`notification`,`integration`}（`SystemConfigController.java:172-178`）；`GET /api/config/groups` → **7 项**且 = {`basic`,`login`,`password`,`session`,`upload`,`email`,`sms`}（`:184-192`）。
⑨ **断言 `keyword` 不参与后端过滤**：`GET /api/config/list?keyword=system` → 断言返回**仍为 11 条**（后端不接收该参数）；再断言前端 `:224-231` 的过滤逻辑命中 2 条（`system.name` 与 `system.version` 含 `system`，`system.logo` 亦含）→ **以 UI 断言为准**（§10.2-⑤）。

**写路径（⑩–⑭，**本页最关键的接口断言**）**

⑩ 🎯 **"保存不落库"的核心断言（P0 的可执行证据）**：
   1. 直查 DB：`SELECT param_value FROM sys_config WHERE param_key='system.version'` → 记录现值（预期 `1.0.0`）；
   2. 调 `POST /api/config/save-value`，body `{ configKey: 'system.version', configValue: '9.9.9-e2e' }` → **期望 200**；
   3. `GET /api/config/list` → 断言内存中该条 `configValue` **已变为 `9.9.9-e2e`**（**证明写路径"看起来成功了"**）；
   4. 直查 DB 再读 `sys_config` → 断言 **`param_value` 未发生任何变化**（**证明没有落库**）；
   5. **复原**：`POST /api/config/save-value` 写回 `1.0.0`（或重启后端回到内存初值）；DB 无需复原（未被改动）。
⑪ **断言 `sys_config` 表与本页零连线（静态 + 动态双证）**：
   - 静态：`grep -rn '@TableName("sys_config")' backend/` → **0 命中**；`grep -rn 'param_key\|paramKey' backend/ --include=*.java --include=*.xml` → **0 命中**；

⑫ **断言 `POST /api/config/refresh-cache` 无实际效果**：调用前后各调一次 `GET /api/config/list` → 断言两次结果**完全相同**（后端只有 `log.info`，`:237-240`）；并断言**响应 200**（不是失败）。
⑬ **断言变更日志「操作人」恒为空**：调 ⑩ 的保存后 → `GET /api/config/logs/system.version` → 断言返回数组长度 **≥ 1**，且**每一条的 `operatorName` 均为 `null`/空**（`:157` 写入时传 null）。
⑭ **断言 `DELETE /api/config/{configKey}` 是假成功**：调 `DELETE /api/config/system.version` → 断言 **HTTP 200 且返回成功**；随后 `GET /api/config/list` → 断言 **`system.version` 仍在列表中**（未真删）→ **P0-⑥ 的可执行证据**；不产生 DB 变化，无需复原。

| **平台级读的租户豁免（落库后必做）** | ⚠️ **目标：代码级声明** | `sys_config` **不在** `MyBatisPlusConfig.IGNORE_TENANT_TABLES` → 落库后**必须**用 `@InterceptorIgnore(tenantLine = "true")` 读全局 | 改代码 + 重启 | 🔴 非超管会话下注入 `tenant_id=<会话租户>` → **全局参数查回 0 行且不报错**（README P0-15 的典型症状） |
| **写目标租户行（落库后必做）** | ⚠️ **目标：代码级** | 写 `tenant_id>0` 的覆盖行前调 `MyBatisPlusConfig.setTempTenantId(tid)` | 即时 | 覆盖行会被写成会话租户的行 |
| **前端 `VITE_*`（本页无）** | — | 本页不使用任何 `VITE_*` | — | — |

### 11.1 必须写清的「通道判别」事实（《对标开发技术参考文档》§5.6.2 硬规则）

1. **模块自带 yml 不生效**：若将来把平台参数写进 `config` 模块自带的 `src/main/resources/*.yml`，**core-api 启动时不会加载**（Spring Boot 只读 classpath 根那一份）→ **必须写到 core-api 的 `application.yml`**（或 `application-{profile}.yml`）。
   - **本页现状**：不走 yml（纯内存 + Redis）→ 本条目前**不适用**，但**落库改造后若引入「默认值 yml」，必须遵守**。
2. **前端 `VITE_*` 是构建期注入**：本页前端**未使用任何 `VITE_*`**（颜色表与页大小都在 `.vue` 里）→ 无需 CI 注入；代价是**改颜色/页大小必须重新构建**。
3. **密钥优先不入库**：本页的「参数值」可能承载敏感值 —— DB 里现存一条 `system.defaultPassword = 123456`（§2、§13）。**落库改造时必须补 `is_encrypted` 标记 + 出参脱敏 + 掩码回写保护**（参照 `dms_channel.config_json` 的 `ENCv1:` 做法）；⚠️ **数据源/属性加密的官方做法未取证**（底稿 §9.1 第 15 条）→ **实施前须另行取证**，本文档不称其为「业界标准」。
4. **必须有降级**：配置缺失时不得阻塞业务。本页当前无降级设计 —— 接口失败即空表（§3.1）。**目标**：参数读取失败时**用代码默认值并在响应中标注 `degraded=true`**（参照 `GET /api/dms/route/config` 的 `keySource` 口径），**绝不返回假数据**。
5. **换配置要能生效**：当前生效方式是「**重启后端**」（内存）→ **与"配置中心"的期望（页面保存即热生效）完全相反**。落库改造时必须定义生效方式；热生效实现 = 保存后发布领域事件 + 消费方失效本地缓存（多实例用 TTL 兜底）。
6. **多租户读全局默认**：落库后读 `tenant_id=0` 的全局行，**必须** `@InterceptorIgnore(tenantLine = "true")`；否则被租户插件注入条件 → **查回 0 行**（§11.1-上文表格、README §1.3 红线②）。

### 11.2 平台级参数 vs 租户级参数（**本页的必答项**）

| 维度 | 本页（平台参数 62501） | 系统参数（80621） | 归属判定 |
|------|----------------------|------------------|---------|
| 菜单 / 路由 / 组件 | `sys_menu`：`client_type='system-admin'`、`tenant_id=0`（实测 62501） | `client_type='tenant-admin'`、`tenant_id=0`（实测 80621） | **平台级菜单 / 租户级菜单** |
| 数据载体 | **同一份 JVM 内存**（无表） | **同一份 JVM 内存**（无表） | ⚠️ **无归属概念** |
| `tenant_id` 列 | `sys_config.tenant_id` 存在（8 行全 0）**但无人读** | 同左 | ⚠️ **字段在、语义未实现** |
| 由谁维护 | 平台运营方（超管） | 租户管理员 | 理论上是两级，**实现上是一级** |
| 影响谁 | 理论上是全平台；实际**无任何消费方被证实** | 同左 | ⚠️ **影响面未取证** |
| 租户可否自改 | 不可（无租户侧入口指向平台参数） | 可（80621 页面可改） | ⚠️ **但改的是同一份内存** |
| 权限码 | `system:config:*`（4 个，存在）+ 菜单码 `system:platform:params`（**未落库**） | `system:config:*`（同一套） | ⚠️ **两页共用同一套接口权限码** |
| 审计 | **应有而无**（平台侧写操作必须有审计，README §1.3 红线③） | 同左 | **P0** |

> **结论一句话**：**「平台参数」与「系统参数」目前不是两级参数体系，而是同一份内存的两个门**。判断一个参数属于哪一级，**在代码层无从判定**（没有 `scope` 字段、没有消费方登记）。这是本页在 `§11` 必须写明的最重要结论。

## 12. 剩余缺口（P0 / P1 / P2）

> 口径与《系统模块/README.md》§7 保持一致。README §7.1 **P0-1**（包未装配）、**P0-15**（平台级表未豁免）、**P0-17**（平台侧无审计）在本页的适用性逐条标注。

### P0（6 条）

① **后端全程不落库（本页最严重）**：`SystemConfigServiceImpl` 用 `static final Map` `BUILTIN_CONFIGS`（11 条）实现**全部读写**（`:26`、`:104-114`、`:128-143`），**无任何 insert/update/mapper 调用**；`sys_config` 表（**17 列 / 8 行**）是**孤儿表**（`@TableName("sys_config")` 与 `param_key` 的 grep **均 0 命中**）→ **页面改的配置重启即失，DB 里那 8 行永远读不到**。
    建议：① 补 `SystemConfig` 实体 + `@TableName("sys_config")` + Mapper；② **先做一次 key/语义对齐迁移**（内存 11 条 → DB 的 `param_key`，注意 `system.name` vs `system.title`、`upload.maxSize` 10485760 vs `system.uploadMaxSize` 104857600 **差 10 倍**）；③ 给 `param_key`（或 `(tenant_id, param_key)`）**加唯一约束**（对标 Odoo `unique (key)`，A 级）；④ 读全局用 `@InterceptorIgnore(tenantLine="true")`。
② **「刷新缓存」按钮无任何实际缓存操作**：后端 `refreshCache` 两个重载**都只 `log.info`**（`:237-240`、`:242-245`）→ 用户点按钮看到 `success`，**缓存纹丝不动**。
    建议：实现为「清 `config:` 前缀缓存 + 发布失效事件」，或**改名为「查看缓存状态」**避免误导。
③ **变更日志「操作人」恒为 null**：写入时 `logConfigChange(config, oldValue, "update", null, null, null, tenantId)`（`:157`）→ 前端第 4 列 `operatorName`（`:261`）永远空白；且日志**只进 Redis List、不落库**，无缓存服务时直接返回空数组（`:212`）。
    建议：写入时补 `StpUtil.getLoginIdAsLong()` + 用户名；日志落 DB（可复用 `sys_audit_log`，24 列 / 0 行）并补时间范围/操作人筛选。
④ **平台参数变更零审计（README §7.1 P0-17 在本页的具体化）**：改参数**不写任何审计**；`sys_audit_log` 实测 **0 行** → 「谁在什么时候把平台参数改成了什么」**事后不可还原**。
    建议：按「时间 + 主体 + 来源 IP + 目标 key + 前后值 + 结果」落审计（README §1.3 红线③）。
⑤ **「按租户区分」是空话**：`getConfigList` 的 `Long tenantId` 入参**方法体内零引用**（`:104`）→ 所有租户看到同一份数据；`sys_config.tenant_id` 8 行全 0，**从无一行被写过**。
    建议：落库时定义清楚「`tenant_id=0` 全局默认 / `>0` 租户覆盖」的读取优先级（**本系统设计，D 级**，见 §8.2-9），并写验收断言。
⑥ **跨模块重复实现（P0）**：本页（62501）与**设置模块的系统参数（80621）共用同一个内存假实现**，两侧都打 `/api/config/*`（`SystemConfigController.java:21`；本页 `params/index.vue:323` vs `set/sys-params/index.vue:307`），但**走两套前端 API 封装**（`platformConfigApi` 原生 axios vs `configApi` 标准 `request`）→ 同一份数据两个门、两套鉴权通道、两套类型定义（`PlatformConfigItem` vs `SystemConfig`）。
    建议：裁定**单一入口**（保留平台侧或租户侧其一），另一侧改为跳转；或明确「平台级参数只读 + 租户级参数可写」的分工并在两侧 UI 上标注。
⑦ **`/api/config/value/{configKey}` 无权限注解 + 明文返回**：`SystemConfigController.java:63-74` 仅 `@GetMapping` + `@Operation`，**无 `@SaCheckPermission`** → 任何登录用户（含租户侧用户）都能读平台参数值。
    建议：补权限注解；若确需匿名可读，改为白名单端点并在 `SaTokenConfig` 显式放行。

### P1（8 条）

⑧ **`getConfig(Long id)` 直接 `return null`（原文注释「简化实现」）**（`:63-66`）→ `/api/config/page` 的详情路径与任何按 id 的读取**恒为空**；「更新时间」列也因此恒空（内存对象未设 `createTime`/`updateTime`，`params/index.vue:253`）。
⑨ **`deleteConfig` / `batchDelete` 假成功**：`return true`（`:168-171`）、`log.info` + `return true`（`:187-194`）→ 若前端接上删除入口，会**谎报成功**。
⑩ **「参数值」无类型感知、无校验**：不论类型一律 `a-textarea :rows="4"`（`:150-155`），`a-form` 无 `:model`、无 `:rules` → 用户可以把 `security.login.maxAttempts` 写成 `abc`。
⑪ **查询失败静默吞异常**：`fetchData` 的 `catch { allRows.value = [] }`（`:329-331`）与 `onMounted` 的 `catch { console.warn(...) }`（`:342-344`）→ 接口挂了页面表现为「空表格」，**不提示用户**。
⑫ **前端零 `v-permission`**：4 个按钮对任何能看到本页的用户一律可见可点（`params/index.vue` 全文）；叠加菜单 `client_type='system-admin'` 的可见性收敛，实际风险被"看不到菜单"部分掩盖，但**不是权限控制**。
⑬ **无列配置 / 无 `PageConfigPanel` / 无 `storage-key` / 非经典分页**：`:233-244` 自算分页 + 前端切片；README §7.2 口径在本页的具体化。
⑭ **与安全策略页的重复建模（三组语义重复且值不一致）**：本页 `security.password.minLength = 8` vs `sys_security_policy.password_min_length = 8`（同值）；本页 `security.login.maxAttempts = 5` vs `lock_threshold = 5`（同值）；**本页 `security.session.timeout = 7200` vs `session_timeout = 60`（差 120 倍）** → 同一语义两处配置、两处都不生效。
    建议：收敛为**一处真源**；安全策略页的 `sys_security_policy` 已是结构化表，**更适合作为真源**，本页这三条应删除或改为只读引用。
⑮ **「参数是否为租户级」在代码层无从判定**：没有 `scope` 字段、没有消费方登记 → §11.2 的结论无法用代码回答；README §5.4 的专题 8 建议的「逐项配置清单」在本页**完全缺失**。
