## 1. 页面概述

安全策略页是**平台运营方的安全基线配置台账**：**双栏四卡片**布局（左栏 `a-card title="登录安全"` + `a-card title="密码策略"`；右栏 `a-card title="访问控制"` + `a-card title="审计日志"`），共 **17 个配置项**（数值 / 开关 / 文本混合）+ **1 个按钮**（页头右侧 `保存全部`，`type="primary"` + `SaveOutlined`）。它属于 `61306 平台设置` 组的第 5 页（`sort=500`）。

> **一句话定性**：本页是**全组 5 页里前后端路径唯一完全对得上的页面**（`GET /api/system/security/policy` + `POST /api/system/security/policy/save`，两端点**路径逐字符匹配**），**但**它仍然受同一条根因影响 —— `cn.aiedge.platform` **不在 `scanBasePackages`** → **2 个端点从未装配、运行期全部 404**。
> **更关键的是第二个问题**：**这 2 个端点就是全部**（该控制器只有 2 个端点）→ 修好装配后，**17 个字段里有 3 个存在硬冲突**（`rateLimit` 三方类型互不一致、`sessionTimeout` 单位差 60 倍、`ipWhitelist` 分隔符不兼容）→ **保存链路极可能直接 500**（详见 §5.1、§7.4）。
> **第三个问题（最隐蔽）**：**保存进 DB 的策略没有任何代码消费** —— 登录失败锁定、验证码、双因素、密码复杂度、会话超时、IP 白名单、限流**均未见读取 `sys_security_policy` 的证据**（取证范围见 §5.5）→ **用户以为加固了安全策略，实际可能完全未生效**。

### 1.2 与「平台参数」页的**重复建模**（**同一批安全语义两处配置，必须辨析**）

| 语义 | 本页（`sys_security_policy` 列） | 平台参数页（内存 `BUILTIN_CONFIGS` 的 key） | 两处的值 | 谁生效 |

| 密码最小长度 | `password_min_length` = **8** | `security.password.minLength` = **8** | **相同** | 🔴 **两处都不生效**（无消费方证据） |
| 登录失败锁定阈值 | `lock_threshold` = **5** | `security.login.maxAttempts` = **5** | **相同** | 🔴 同上 |

| 密码复杂度 | `require_upper` / `require_lower` / `require_digit` / `require_special`（4 个 boolean） | 无 | — | 仅本页有 |
| 密码有效期 | `password_expire_days` = **90** | 无（DB `sys_config.system.passwordPolicy` 里用字符串拼了 `minLength=8,...`） | — | 仅本页有 |
| 双因素认证 | `two_factor_enabled` = **false** | 无 | — | 仅本页有 |
| 验证码 | `captcha_enabled` = **true** | 无 | — | 仅本页有 |
| 单设备登录 | `single_device` = **true** | 无 | — | 仅本页有 |
| IP 白名单 | `ip_whitelist` = 空串 | 无 | — | 仅本页有 |
| 接口限流 | `rate_limit` = **1000**（integer） | 无 | — | 仅本页有 |
| 日志保留天数 | `audit_retention_days` = **180** | 无 | — | 仅本页有 |
| 敏感操作审计 | `log_sensitive_ops` = **true** | 无 | — | 仅本页有 |
| 登录日志开关 | `log_login` = **true** | 无 | — | 仅本页有 |

> **结论**：**3 组语义（最小长度 / 锁定阈值 / 会话超时）在两个页面各配一遍**，其中**会话超时的两处值相差 120 倍**，且**两处都无消费方被证实** → 这是 README §4「系统 → 设置」接线点之外、**`61306 平台设置` 组内部**的又一处重复建模（详见 §12 P1-⑧）。

### 5.2 取值口径（「策略是怎么读出来、写回去的」）

```text
【读】fetchPolicy(:203-228)  ← onMounted 调用
  ├─ GET /api/system/security/policy   → 404（cn.aiedge.platform 未装配；★路径本身是对的）
  └─ 失败 → catch { // 使用默认值 }(:225-227，原文注释，无任何提示)
       → 4 个 reactive 保留 :174-201 的硬编码默认值
       🔴 而这 4 组默认值与 DB 两行实测值【逐一相同】(§1.2/§5.1)：
          lockThreshold=5 / lockDuration=30 / captchaEnabled=true / twoFactorEnabled=false
          minLength=8 / requireUpper/Lower/Digit=true / requireSpecial=false / expireDays=90
          sessionTimeout=60 / singleDevice=true / ipWhitelist='' / rateLimit=1000
          retentionDays=180 / logSensitiveOps=true / logLogin=true
       → 用户【无法从界面上区分】"策略已加载"还是"接口失败退回默认值"
【写】saveAll(:230-257)
  ├─ message.loading('正在保存安全策略...', 0)(:231)   ← 🔴 duration=0 → 永不自动关闭
  ├─ POST /api/system/security/policy/save   body = 17 个字段(:233-251)  → 404
  ├─ 成功分支 → message.success('安全策略已保存')(:253)（【从不校验业务结果】）
  └─ 失败 → catch { message.error('保存失败') }(:255)
```

**「页面显示的是什么」**：由于读接口 404，**用户看到的永远是与 DB 无关的硬编码默认值** —— 而**这份默认值与 DB 恰好一样**，所以**界面上完全看不出异常**。这正是本页"误导性最强"的地方。

### 7.4 租户拦截器与 `Map.of` NPE 的耦合（**修好装配后立刻会遇到**）


### 7.5 `rate_limit` 三方冲突的运行时风险（**必须实测后再定级**）

| 层 | 声明 | 证据 |
|---|---|---|
| 前端 | `a-input-number`，number，默认 `1000`，语义「次/分钟」 | `security/index.vue:130-137`、`:194` |

本文档所有「建议字段」**均不预先承诺字段名**。已确认**可以不动表**就能落地的三项是：

## 10. 验收标准（目标）

> **前置**：本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下不存在 `e2e-system-*.cjs` / `e2e-admin-*.cjs`）。脚本建议命名 `tools/e2e-system.cjs`（接口 + 直连 DB 对账 + 写库后复原 + Playwright UI 截屏，参照 `tools/e2e-crm.cjs`）。
> **🔴 本页验收的四条硬纪律（务必先读）**：
> 1. **绝对不要真的修改任何安全策略**（会破坏共享环境：改 `single_device` / `session_timeout` / `lock_threshold` 可能把**正在跑的会话或 e2e 账号**锁死）→ **写断言只用 `id=1` 的"非行为性字段"**（建议只动 `audit_retention_days`，并**先记录原值**）；
> 2. **绝对不要在共享环境里把 `captcha_enabled` 改成 false、把 `two_factor_enabled` 改成 true、把 `lock_threshold` 改小、把 `ip_whitelist` 填值** —— 这四项**任一都可能直接锁死所有人**；

> 4. **不测试"策略是否生效"**（如尝试用错密码触发锁定）—— **绝不对共享环境的账号做登录失败实验**；§5.4 的"策略是否被消费"**只做静态取证**。

### 11.1 必须写清的「通道判别」事实（《对标开发技术参考文档》§5.6.2 硬规则）

1. **模块自带 yml 不生效**：若把 `password.policy.*` 写进某个**模块自带**的 `src/main/resources/*.yml`（位于嵌套 jar 内），**core-api 启动时不会加载**（Spring Boot 只读 classpath 根那一份）→ **必须写到 core-api 的 `application.yml`**。
   **本页现状**：`password.policy.max-age-days` 与 `system.super-admin.role-codes` **已在 core-api `application.yml` 声明**（§5.6.3 已登记）→ ✅ 这一点是对的；**但它们与 `sys_security_policy` 表的同名语义（`password_expire_days`）无任何连线** → **两条真源并存**（§1.2）。
2. **前端 `VITE_*` 是构建期注入**：本页**未使用** → 无需 CI 注入；代价是**任何前端改动（补校验、改单位文案、改按钮、loading 缺陷）都属前端改动 → 必须 rebuild 才生效**。
3. **密钥优先不入库**：本页**无凭据字段**（密码策略不等于密码本身）→ **本规则在本页不适用**；但**策略本身也是高敏数据**（改它等于改安全基线）→ 应按「**仅授权角色可见 + 必留审计**」处理（当前**两项都没做到**：前端零 `v-permission` + 审计人为 `"system"`）。
4. **必须有降级**：配置缺失时**不得阻塞业务**。当前 `password.policy.max-age-days` 缺失 → 用默认值（**属合理降级**）；**但本页的表不可作为兜底**（未接线）→ 表现为「用户在页面上配了也没用」。
   **⚠️ 本页反向的降级风险更高**：**策略"看起来配好了"但没生效**，会让管理员产生**虚假的安全感** —— 这比"配置项不存在"危险得多。
5. **换配置要能生效**：本页**当前无生效方式**（无消费方 + 404）。目标形态需**先裁定**：
   - **路线 A（推荐）**：保持 `password.policy.*` / `system.super-admin.role-codes` 为唯一真源 → 本页改成**只读诊断页**（显示当前生效的密码策略与超管角色来源，**不回显任何凭据**，参照 `GET /api/dms/route/config` 的 `keySource` 口径）；**并明确"哪些能在线改、哪些必须改 yml 重启"**。
   - **路线 B**：让认证链路改读 `sys_security_policy`（**热生效**）→ 需补**缓存失效机制**（保存后发领域事件 + 消费方失效本地缓存，多实例 TTL 兜底），并**显式豁免租户插件**（§11.1-6）；
   - **⚠️ 建议的生效方式（本系统设计）**：若走路线 B，**安全策略变更建议「下次登录生效」而非即时生效** —— 安全策略变更本就应谨慎、可预期，即时生效会让"正在登录的用户"遇到难以复现的异常。
6. **多租户读全局默认行**：`sys_security_policy` 的 2 行都是 `tenant_id=0` → 读它**必须** `@InterceptorIgnore(tenantLine = "true")`；否则被租户插件注入条件 → **查回 null → `Map.of` NPE → 500**（§7.4）。

### 11.2 平台级参数 vs 租户级参数（**本页的必答项**）

| 维度 | 本页（安全策略 62505） | 归属判定 |
|------|----------------------|---------|
| 菜单 / 路由 / 组件 | `sys_menu`：`client_type='system-admin'`、`tenant_id=0`（实测 62505） | **平台级菜单** |
| 主数据表 | `sys_security_policy`：`tenant_id` 列存在，**2 行全 0**（无租户行） | **平台级表**（当前无租户维度数据） |
| 参数存储格式 | **纯列**（无 JSON）：24 列实测 | — |
| 由谁维护 | **平台运营方**（超管） | **平台级** |
| 影响谁 | 理论上**全平台的登录 / 会话 / 密码基线**（实际由 yml 的 `password.policy.*` 决定） | **平台级** |
| 租户可否自改 | **不可以**（设置模块无"安全策略"页） | — |
| 权限码 | 菜单码 `system:platform:security`（**未落库**）+ 接口码 `platform:security:*`（**2 个均未落库**） | **平台级** |
| 审计 | **应有而无**（README §1.3 红线③）；**且本页是"改安全基线"，审计价值最高**（谁在什么时候把锁定阈值改成了多少） | **平台级** |

### P0（8 条）

① **`cn.aiedge.platform` 未列入 `scanBasePackages` → 2 个端点从未装配、运行期全 404**（README §7.1 **P0-1** 在本页的具体化；本组 4 页共 **11 个端点**受影响）：
   `AiReadyApplication.java:21-97` 的扫描列表**不含** `cn.aiedge.platform`（2026-09-18 `grep` **0 命中**）→ `SecurityPolicyController`（`:18`）永远不成为 Bean。
   **连带**：`@MapperScan("cn.aiedge.**.mapper")` 是**通配**的（`AiReadyApplication.java:117`）→ **Mapper 会注册，Service/Controller 不会** → 「**表能建、点不动**」。
   **✅ 本页的好消息**：**路径是对的**（§6.2）→ **只需补 `scanBasePackages` 即可让接口通**（不像存储配置页要修两处）。

② **策略保存后是否被消费未证实（"只写不读"）**：`SecurityPolicyServiceImpl`（`:20-61`）只做 DB 读写，**无任何事件发布 / 缓存刷新**；**在本页取证范围内未见登录链路读取 `sys_security_policy` 的证据**（登录失败锁定 / 验证码 / 双因素 / 密码复杂度 / 会话超时 / IP 白名单 / 限流的实现均未证实引用该表）。
   建议：**先立一个取证任务**（`grep -rn "sys_security_policy\|SysSecurityPolicy" backend/` 全量比对 + 走一遍登录链路），**确认后再决定"接线"还是"改只读诊断页"**；**在确认前不得宣称本页"已加固安全"**。
   > ⚠️ **证据边界（必须保留在文档里）**：本结论的取证范围**限于本页前后端链路**→ **不写成"已确认不生效"**，只写「**未在本页取证范围内找到消费方**」。
③ **`rateLimit` 三方类型互不一致（保存链路极可能 500）**：前端 `a-input-number`（number，默认 1000，语义「次/分钟」，`:130-137`）；后端 **`boolean rateLimit`**（`SecurityPolicy.java:61-62`，注释「是否限制请求频率」）；DB 列 **`integer`**（默认 `1000`）→ **中文语义 / Java 类型 / DB 类型三方全部对不上**；MyBatis-Plus 把 `boolean` 写回 `integer` 列时，PostgreSQL 极可能抛 `column "rate_limit" is of type integer but expression is of type boolean` → **保存 500**（**源码/DB 的冲突是确凿事实；"一定 500"是推断，须实测**）。
   建议：**统一为 `Integer`**（前端已是 number、DB 已是 integer，**改 Java 字段代价最小**）；语义统一为「次/分钟」；并补一条迁移把存量 `1000` 按新语义解释。
④ **`sessionTimeout` 单位冲突（三方不一致，差 60 倍）**：前端 label 后缀「**分钟**」（`:118`）且 `min=5/max=1440`；后端 Schema 注释「**秒**」（`SecurityPolicy.java:52-53`）；DB 默认 `60`。
   建议：**统一为「分钟」或「秒」并同时改三处**（前端文案 + 后端 Schema + DB 列注释），必要时补迁移；**在没统一之前，不要接任何消费方**（否则会把 60 秒当成 60 分钟）。
⑤ **每次保存把 `enabled` 写成 `false`**：`SecurityPolicy.java:73-74` 的 `enabled` 存在、DB 有列有默认值 `true`，但**前端 17 个字段里没有它**（`:233-251`）→ 反序列化缺省即 `false`（**原始 boolean，非 null**）→ `savePolicy` 的 `updateById` **不会跳过** → 一保存即"未启用"。
   建议：① 前端补 `enabled` 开关（**最小改动，列已存在**）；② 后端改用 `Boolean` 包装类型或显式判空。
⑥ **审计人写死为字符串 `"system"`**：`SecurityPolicyServiceImpl.java:47-48`（`setCreateBy("system")` / `setUpdateBy("system")`）与 `:55`（`setUpdateBy("system")`）→ **不取当前登录用户** → `create_by` / `update_by` 列的审计信息**无意义**；**叠加本页是"改安全基线"的高敏操作** → 「谁把锁定阈值从 5 改成 100」**无从回答**。
   建议：改为取 `StpUtil.getLoginIdAsLong()` + 用户名；**并同步接入 `sys_audit_log`**（见 P0-⑧）。
⑦ **`Map.of` 传 null value → 空策略时 NPE（500）**：`SecurityPolicyController.java:31`（另 `:41` 同款）。「无策略行」是**合法状态**，不应变成 500。
⑧ **平台侧写操作零审计（README §7.1 P0-17 在本页的具体化）**：安全策略变更**不写任何审计**；`sys_audit_log` 实测 **0 行** → 「谁在什么时候把平台安全基线改成了什么」**事后不可还原**。建议：按「时间 + 主体 + 来源 IP + 变更项 + 前后值 + 结果」落审计（README §1.3 红线③）。

⑮ **`message.loading(..., 0)` 永不关闭**：`:231`「正在保存安全策略...」→ 提示条**永久停留**（本组 62502-62505 四页同款，建议**组件级收口**）。
⑯ **`sys_config` 孤儿表里还有第三份安全语义**：`system.passwordPolicy = "minLength=8,...,requireDigit=1"`（**字符串拼装，非结构化**）、`system.sessionTimeout = 3600`、`system.loginLockCount = 5` → **同一语义三处重复、无一被证实生效**（§1.2、§7.3）。
