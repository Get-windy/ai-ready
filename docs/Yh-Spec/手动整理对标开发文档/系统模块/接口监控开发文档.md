## 1. 页面概述

接口监控页**本应**是平台运营方的「对外接口健康状况看板」：展示系统状态（CPU/内存/磁盘）、服务健康计数、24 小时告警（总数/未确认/严重/警告）、接口性能（平均响应时间/吞吐/错误率），并按端点分组列出 API 目录。

**一句话结论：这页是一张从未接线的占位页（死页），且带"假绿"——"系统状态 = 正常"是前端写死的常量。** 它唯一的两个数据源 `GET /api/monitor/dashboard`、`GET /api/monitor/info` 在后端**穷尽检索后零命中**，必然 404；404 被 `catch { /* ignore */ }` 静默吞掉，页面永久展示全 0 加上绿色的「正常」。

> **⚠️ 本页与《交易 → API 监控》（90107）是两套完全不同的实现**，详见 §1.3 与 §6.4 —— **本页的能力应当复用后者，而不是另起炉灶**（README §4「系统 → 交易」接线点的结论）。

### 8.1 业界叫法

**Actuator `/actuator/httpexchanges`（最近 HTTP 交换）+ `/metrics`**；PostgreSQL **`pg_stat_statements`**；SAP **HANA Cockpit 的 Expensive Statements / Statements Monitor / SQL Plan Cache / Workload Analyzer**。

### 8.2 业界做法要点

1. **HTTP 层面官方就给了「最近 N 次请求-响应」**：`httpexchanges`「显示 HTTP 交换信息（默认最近 100 次请求-响应）」，需要 `HttpExchangeRepository` bean。**这是最省事的"接口监控"数据源。**
2. **慢 SQL 用官方扩展，不要自己抓**：`pg_stat_statements`「跟踪服务器上所有 SQL 语句的规划与执行统计」，需要 `shared_preload_libraries` 预加载 + `compute_query_id`。
3. **关键列（官方原文列名）**：`calls`、`total_exec_time`、`min_exec_time`、`max_exec_time`、`mean_exec_time`、`stddev_exec_time`、`rows`、`shared_blks_hit`、`shared_blks_read`、`wal_bytes`、`queryid`、`query`；计划相关列（`plans`、`total_plan_time` 等）**仅在 `pg_stat_statements.track_planning` 开启时非零**。
4. **常量会被参数化**：文本中的常量被替换为 `$1`，`IN` 列表会被压缩为 `SELECT * FROM test WHERE a IN ($1 /*, ... */)` —— **按 SQL 文本聚合时要意识到这一点**。
5. **配置参数与默认值**：`pg_stat_statements.max` 默认 **5000**（超出丢弃最少执行的条目，**仅能在服务器启动时设置**）、`track` 默认 `top`（可选 `all`/`none`，**仅超级用户可改**）、`track_utility` 默认 `on`、`track_planning` 默认 `off`（「可能带来明显性能开销」）、`save` 默认 `on`。
6. **重置要有粒度与权限**：`pg_stat_statements_reset(userid, dbid, queryid, minmax_only)`，「默认仅超级用户可执行，可用 `GRANT` 授权」；`minmax_only=true` 时**只重置 min/max 时间** —— 这对「保留历史均值但清掉一次尖刺」很有用。
7. **隐私边界**：`pg_stat_statements(showtext := false)` 时 `query` 列返回 NULL，「供外部工具缓存首次文本以降低 I/O」—— **平台级看板面向运营方，仍需注意 SQL 文本中可能含租户敏感数据**。
8. **SAP 的对应能力名可直接借用为页面 Tab 名**：Expensive Statements（超阈值单条 SQL）、Statements Monitor（当前最关键的运行中语句）、SQL Plan Cache、Workload Analyzer（基于线程采样的 Top SQL）。

### 8.4 明确不借鉴

- **SAP HANA Cockpit 的四层下钻（Workload Analyzer → SQL Plan Cache → Expensive Statements）** —— 本系统当前只有 PostgreSQL 单库 + 单一应用进程，**不引入 HANA 特有的对象模型**；只借用「单条语句级下钻」这一条交互原则。

- **`pg_stat_statements` 的 `track_planning=on`** —— 官方明确「可能带来明显性能开销」，**默认保持 `off`**。
- **在平台级看板里直出 SQL 原文** —— 可能含租户敏感数据；**若未来接入，须评估 `showtext` 与脱敏**。
