## 1. 页面概述

性能监控页是**平台运营方的运行时性能看板**：展示 core-api 进程的 **CPU 使用率、内存使用率、GC 时间占比、活跃线程数**四个核心指标，外加 **CPU 详情、GC 详情表、性能瓶颈分析列表、类加载、编译信息**五块下钻内容，30 秒自动轮询。

**一句话结论：数据是真的，但用户看不到。** 四个指标卡与所有下钻内容都来自 JDK MXBean 的**实算值**（无写死、无随机数），但承载它们的 `cn.aiedge.monitor` 包**未装配**，6 个端点运行期全部 404（§6.5）。此外「系统CPU使用率 / 进程CPU使用率」两行存在**二次 ×100** 的显示放大（§9.2-2）。

| 指标 | 阈值 | 后端行 |

**🔴 不一致（如实登记）**：

1. **后端 `WARNING` 阈值（CPU 80 / 内存 85 / GC 10）与 `CRITICAL` 阈值（CPU 95 / 内存 95 / GC 20）是两套数**，但**前端只在瓶颈列表显示 `CRITICAL` 侧文案**（`:179`）→ 用户看到「阈值 CPU 80%」却不知道 80~95 会怎样。
2. **前端顶卡三值（`HEALTHY`/`WARNING`/其它）与后端三值（`HEALTHY`/`WARNING`/`CRITICAL`）对得上** ✅（其它分支恰好接住 `CRITICAL`）。
3. **GC 阈值单位是「时间占比 %」（10/20），而 `/`jvm` 页（《服务状态》）关注的是堆占用 %** —— 两页对「内存」的关注点不同，**不是缺陷**，但文档需写清口径差异。

> **本页在 ql361 无对应页**（§2）。本章只写**业界能力对标**，逐条标来源与可信度级别。**凡底稿标 D 级的方案，本文件一律写「本系统设计」而非「业界标准」。**

### 8.1 业界叫法

**Actuator `/actuator/metrics`（+ `/actuator/prometheus`）**；**HikariCP 连接池旋钮**；PostgreSQL **`pg_stat_activity` / `pg_stat_database`**；SAP **SAP HANA Cockpit**（Performance Monitor、Threads、Sessions）。

### 8.2 业界做法要点

1. **指标要能「按指标名下钻」**：Actuator `/metrics` 的定位是「显示应用的指标信息，**用于诊断已记录的指标**」—— 不是给一个总览数字，而是可查询单个指标。
2. **对外抓取用 `/actuator/prometheus`**：「以 Prometheus 服务器可抓取的格式暴露指标」，需要 `micrometer-registry-prometheus` 依赖。
3. **线程与堆要有出口**：`/actuator/threaddump`（执行线程转储）、`/actuator/heapdump`（返回堆转储文件，HotSpot 返回 HPROF、OpenJ9 返回 PHD）。
4. **连接池旋钮与默认值（官方 README 原文级）**：`maximumPoolSize`=10、`minimumIdle`（默认同 max，官方建议**不要设**、「instead allowing HikariCP to act as a *fixed size* connection pool」）、`connectionTimeout`=30000ms、`validationTimeout`=5000ms、`idleTimeout`=600000ms（仅在 `minimumIdle < maximumPoolSize` 时生效）、`maxLifetime`=1800000ms、`keepaliveTime`=120000ms、`leakDetectionThreshold`=0（关闭，开启最小 2000ms）、`connectionTestQuery`（**JDBC4 驱动不要设置**）、`poolName`（日志与 JMX 用）、`connectionInitSql`。
5. **池大小不是越大越好（官方原文）**：「too many connections have a clear and demonstrable *negative* impact on performance」（Oracle 演示中出现 50 倍差距）。
6. **数据库侧要有实时会话视图**：`pg_stat_activity` 的 `state` 是**7 值枚举**：`starting / active / idle / idle in transaction / idle in transaction (aborted) / fastpath function call / disabled`（`disabled` 表示该后端关闭了 `track_activities`）；`wait_event_type` 与 `wait_event` 独立于 `state` ——「`active` 状态 + 非空 `wait_event` 表示查询在执行但被阻塞」。**「长事务 + idle in transaction」是性能页必须独立告警的一类。**
7. **库级汇总**：`pg_stat_database` 的 `numbackends`（当前连接数，**该视图唯一反映当前状态的列**）、`xact_commit`/`xact_rollback`、`blks_read`/`blks_hit`、`deadlocks`、`temp_files`（「所有临时文件都被计数，无论为何创建」）。
8. **注意统计的可见性边界**：超级用户与 `pg_read_all_stats` 成员才能看全部会话；普通用户只看自己的；`stats_fetch_consistency` 默认 `cache`（事务内缓存），且**非干净关闭（崩溃/基础备份/PITR）会重置所有统计计数器**。

> **前置**：本模块**尚无 E2E**。落地脚本建议命名 `tools/e2e-system.cjs`（接口 + 直连 DB 对账 + 写库后复原 + Playwright UI 截屏）。

### 10.1 接口验收（23 项）

**包装配与可达性（①–③）**

① 修复 `scanBasePackages` 后重启，`GET /api/monitor/performance/realtime`（带 `admin` Bearer）**期望 200**；未修复时**期望 404** —— 两种结果都记录，404 即证明 P0-1 未修。
② 同批断言 `GET /api/monitor/performance/bottleneck`、`/aggregate`、`/trend/cpu`、`/predict/cpu`、`/compare` **6 个端点全部非 404**（逐个记录状态码）。
③ 断言不带 Authorization 调 `/realtime` 返回 **401/403**（类级 `@SaCheckLogin`，`PerformanceMetricsController.java:27`）。

**指标字段与数值（④–⑫）**

④ `/realtime` 返回体断言含 6 个顶层键：`cpu`、`memory`、`gc`、`threads`、`classLoading`、`compilation`。
⑤ `cpu` 子对象断言含 `usage`、`systemUsage`、`processUsage`；**断言三者的数量级一致**（都在 0~100 量级）—— 若 `systemUsage`/`processUsage` 恒为 `usage` 的 100 倍，**即证明 P0-2 的重复缩放发生在后端交付值上**（后端已 ×100）。
⑥ 🔴 **CPU 显示值断言（P0-2 的可执行证据）**：构造一个可预期的负载（例如持续 10 秒 100% 占用的 HTTP 压测），然后：
   - 记录 `/realtime` 返回的 `cpu.systemUsage`（期望落在 `0~100`）；
   - **断言页面上「系统CPU使用率」的显示值 = `cpu.systemUsage × 100`**（即 `performance/index.vue:290` 的二次乘法）→ **显示值会是 4~5 位数（如 1250）**。**这是"显示放大 100 倍"的端到端证据**；修复后改断言显示值 ≈ `cpu.systemUsage`。
⑦ 同型断言「进程CPU使用率」（`:291`）。
⑧ 对照组：断言同一页的 `cpuUsage`（CPU 使用率卡，`:287`）**未做二次乘法**（显示值 ≈ `/realtime` 的 `cpu.usage`）→ 佐证 ⑥ 是**前端局部缺陷**而非全局口径。
⑨ `memory` 子对象断言含使用率字段；`used <= max`；使用率落在 `[0,100]`。
⑩ `gc` 断言为**数组**或含各收集器项；每项含 `name` / `count` / `time`；`count` 与 `time` 均 ≥ 0。
⑪ `threads` 断言含线程数；**断言死锁检测字段存在**（后端 `:441` 用 `ThreadMXBean`）→ 死锁场景：`CRITICAL`（`:282`）。
⑫ `classLoading`（3 项）与 `compilation`（2 项）断言字段齐全（对应页面 `a-descriptions` 的 3 项与 2 项，`:196-209`、`:217-227`）。

**瓶颈分析（⑬–⑯）**

⑬ `/bottleneck` 返回体断言含 `bottlenecks[]` 与 `overallStatus`；`overallStatus` 值域断言为 `HEALTHY|WARNING|CRITICAL`（`:292-293`）。
