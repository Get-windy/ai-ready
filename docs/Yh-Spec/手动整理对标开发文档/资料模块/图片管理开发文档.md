## 页面概述

图片管理用于**商品图片**的检索/上传/匹配维护。对标系统为**多Tab组合页**，含 2 个子标签：**商品图片列表**（默认）、**图片空间**。**不属于主图/详情图/缩略图分类表**，而是「按商品维度维护图片」+「图片库自动匹配」形态。

| 子标签 | 说明 |
|--------|------|
| 商品图片列表 | 商品分类树 + 商品筛选 + 商品图片数据表（按行选择图片） |
| 图片空间 | 图片库上传/自动匹配/删除/搬移（图片网格视图） |

菜单：资料 → 商品管理 → 图片管理。

## 业务规范说明

- **图片单一口径（P0 红线）**：商品图片素材为全局基础数据（商品/营销/商城统一引用），仅 **一张表 `erp_product_image`** 承载「商品图片 + 图片空间素材」——`product_id` 为空即图片空间未匹配素材，非空即已关联该商品的图片，**严禁另建重复图片表**。
- **图片维度**：对标以「商品」为维度维护图片（商品图片列表）+「图片空间」做库内上传/自动匹配（按名称/货号匹配命名），并非主图/详情图/缩略图分类表。
- **自动匹配闭环**：素材文件名 → 去掉 `-N` 序号后缀得 `match_key` → 按「名称」匹配 `erp_product.product_name`，或按「货号」匹配 `product_code_alias`/`product_code`；命中唯一商品即回填 `product_id`，命中多个（歧义）与未命中分别计数返回。
- **主图**：一个商品最多一张主图（`is_main=1`），设主图时同步回写 `erp_product.image_url` 供商品主数据/商城引用。

### 实现差异（与对标形态的取舍，已确认可接受）

1. **列配置弹窗内部列**：对标为「序号 | 上级 | 列名 | 显示名 | 显示 + 上移/下移/恢复默认/保存」，本系统复用通用组件的「序号 | 显示 | 列名 | 显示名 | 宽度 + 拖拽排序 + 恢复默认」。差异点：多「宽度」列、拖拽替代上移/下移按钮、改动即时生效（等价「保存」），**入口位置与两 Tab 语义一致**。
2. **图片空间无列配置**：与对标一致（网格视图不提供列配置）。
3. **存储落盘**：图片统一落 `storage.local.base-path/product-image/{tenantId}/yyyy/MM/dd/{uuid}.ext`（与平台文件访问同根目录）。当前后端默认 local 存储；**接入 MinIO 需先把存储抽象下沉到 `core-base`**（`erp-*` 业务模块无法编译期依赖 `core-api` 的 storage 包），属遗留项。
4. **图片目录面板操作按钮**：对标「图片目录」标题栏有 `✕ ➕ «` 三个按钮（疑似 ql361 左侧 dock 面板的通用「关闭/新建/折叠」，点开后为图片分组管理）。本系统仅保留 `«` 折叠（由 `CategoryListLayout` 提供）；**未实现图片目录（分组）CRUD**——无实测交互依据且需新增目录表，避免臆造功能。
5. **分类树商品数量后缀**：`CategoryListLayout` 默认在分类名后渲染 `(N)`（该分类商品数），对标分类树无此后缀；属资料模块通用骨架的既定形态，保留以保持模块内一致。
6. **表格空行补齐 / 「表格展开显示」**：对标表格按数据行渲染、无空行，本系统 `BillDetailTable` 默认 `minRows=20` 补 `__ghost` 空行并带底部展开按钮；属明细表格通用组件行为（商品条码等资料页同款），保留。
7. **图片空间分页**：对标有 100+ 页故显示页码；本系统数据量小于一页时 antd 仅渲染 `‹ ›`，数据量增大后自动显示页码，形态语义一致。

### 缺陷修复（2026-09-12，线上反馈驱动）

| 级别 | 现象 | 根因 | 修复 |
|---|---|---|---|
| **P0** | 上传商品图片 `POST /erp/md/image/upload` 返回 **500「系统异常」** | 项目从未配置 `spring.servlet.multipart`，Spring Boot 默认单文件上限 **1MB**，而前端校验放行到 10MB → `MaxUploadSizeExceededException` 被全局兜底成 500（实测 70B 成功、2MB 必失败） | `application.yml` 增 `spring.servlet.multipart.max-file-size: 10MB` / `max-request-size: 50MB`，与前端 10MB 对齐（**全平台所有上传接口受益**，含 Excel 导入） |
| **P0** | 商品列表 / 图片管理页图片 **404** 刷屏，Sentry 报 `Resource load failed` | `erp_product.image_url` **残留指向已删除图片**：旧 `deleteImages` 只在 `isMain=1` 时回退主图，而 `move` 会把图片 `isMain` 置 0 却不清 `image_url` → 之后删除该图判定 `wasMain=false`，链接永久残留 | `ProductImageServiceImpl` 新增 `refreshProductMainImage(productId)`：按「图片归属过的商品」重算主图（取剩余图片排序最前一张，无图则清空）。`deleteImages` 改为按归属商品重算（不再只看 isMain），`move` / `bind` 在图片离开原商品时同步重算原商品 |
| P2 | 图片失效时页面破图并持续上报 Sentry | `<img>` 无加载失败兜底 | 图片管理页三处 `<img>` 增加 `@error` 兜底，降级为「图片失效」占位（防重复触发） |
| P2 | 「图片」筛选**多租户口径不严**（实测 SQL 子查询无 `tenant_id`，仅靠雪花 ID 全局唯一侥幸正确，且扫全表） | `QueryWrapper.inSql()` 内的 SQL **不会被多租户插件改写** | 子查询显式拼 `tenant_id = ?`（`Long` 类型无注入风险），命中 `idx_epi_tenant`；同时删掉与 `@TableLogic` 重复的手写 `deleted = 0` |
| P2 | `view/{id}` 返回上传内容存在 **SVG 存储型 XSS** 面（SVG 可内嵌脚本，直接打开该地址即同源执行） | 响应只有 `Content-Type` | 增加 `X-Content-Type-Options: nosniff` + `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`（对 `<img>` 嵌入无副作用） |
| P2 | 超长文件名写库报错 | `image_name` 为 `VARCHAR(255)`，原样存原始文件名 | `upload` 落库前截断到 255（保留扩展名）；同时修正 `source` 注释为实际取值 `UPLOAD/AUTO_MATCH/BIND/MOVE` |

> 历史残留数据修正（一次性 SQL）：把 `image_url` 指向已删图片的商品回退到其剩余图片（无则置 NULL）——
> `UPDATE erp_product p SET image_url = (SELECT '/api/erp/md/image/view/'||i.id FROM erp_product_image i WHERE i.deleted=0 AND i.product_id=p.id ORDER BY i.is_main DESC, i.sort_no ASC, i.id ASC LIMIT 1) WHERE p.image_url LIKE '/api/erp/md/image/view/%' AND NOT EXISTS (SELECT 1 FROM erp_product_image i WHERE i.deleted=0 AND '/api/erp/md/image/view/'||i.id = p.image_url);`

### 部署注意（多实例）

`storage.local.base-path` 默认 `./uploads` 是**相对进程工作目录**的路径：不同工作目录启动的后端实例（本机并行会话常见）会各自落到不同 `uploads/`，导致 A 实例上传的图片在 B 实例 `view/{id}` 返回 404。**单实例部署无此问题**；多实例/多会话验证时需统一工作目录或显式配置同一 `storage.local.base-path`。本次已把验证实例的 `product-image/` 文件补齐到共享实例目录，使其恢复 200。

## 开发原则（通用）
- **页面组件优先复用**、**功能/模块不重复开发**、**阶段结束前回写开发文档**。
