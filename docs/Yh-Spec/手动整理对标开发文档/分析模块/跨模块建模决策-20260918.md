## 1. 提成链路缺生产者

**问题**：`erp_commission_record` 无任何写入代码，且无 `rule_id` 关联提成方案，导致「提成方案名称/类型/规则/描述」四列永远为空。

**业界结论**：
- 共识是三层：`plan(方案头) + rule/tier(规则行)` → `statement/settlement(结算批次)` → `line(明细)`。批次层**是否必要取决于要不要锁历史/审批/冲销**，纯报表可砍。
- 两个极端：**Odoo 企业版提成不落表**（两个 `_auto=False` 的 SQL 视图读时求值 —— 天然不重复计，但无锁定、无审计、不碰总账）；**SAP 走条件技术 + 应计 + 结算凭证 + 反向冲销单据**。
- ★ 关键原则：**业绩归属(credit) 与 算多少钱(incentive) 必须是两组字段**（Oracle Incentive Compensation 把 crediting / rollup / calculation 列为独立过程）。
- 粒度用**源单据行级**；产生时机用**混合**：事件驱动落"待结算"行 + 期间批处理冻结为"已结算"行；已结算行**不可变，修正只新增负向冲销行**（SAP reversal document / NetSuite reversing entry 一致）。
- 幂等靠 DB 三件套即可（源单据唯一索引 + 批次业务唯一键 + 已结算行不可变约束），**不需要 HTTP 幂等中间件**。

**裁决**：**分两期，本期只做"能落地且不造假"的部分。**
- 一期（**等有规则再做**）：`erp_commission_record` 加 `rule_id` / `source_type` / `source_id` / `reversal_of_id` 四个列 + 一个 `WHERE deleted=0` 的 partial unique index；四列展示侧**零改造**，`LEFT JOIN erp_commission_rule` 即可取到（`rule_name` / `commission_type` / `calc_basis+calc_method+commission_value` / `remark`）；"当时费率"用现有 `commission_rate`，它天然就是快照。
- 落库时机：妥投时（`dms/sign` 的 DELIVERING→SIGNED）落 DRAFT 行，按规则优先级**取第一条命中即停**，**匹配不到就不落行**；结算复用**已存在**的 `/analytics/settle`。
- **为什么现在不做**：`erp_commission_rule` **0 行**。没有规则就没有"算多少钱"的依据，现在写生产者只能产出 0 或编造值。
- **明确不做**（YAGNI）：条件技术元数据引擎、独立结算单/审批流/statement 表、目标与达成率主数据（对标六 Tab 实抓均无此列，四大厂也无此主数据）、自建复式账本、事件溯源、多币种税率引擎、**按毛利提成**（`dms_task` 无成本口径列，做了就是编数）。

## 2. 商城无登录/访问埋点（交易分析、商城客户列表）

**问题**：`登录客户数 / 下单客户数 / 下单转化率` 与 `访问次数 / 成交数量 / 成交率` 取不到值。

**业界结论（Odoo 源码直读）**：
- 归因三段各落一表，用**来源维度 id**（source/medium/campaign）串，**不是**用"点击 id"串。触点表冗余 campaign_id；访问表按访客键唯一去重；业务表（`crm.lead` / `sale.order`）经 `utm.mixin` 从 cookie 落同一组维度 id。
- ⚠️ 常被做错的地方：`link.tracker.click` **没有订单外键**。Odoo 默认是**末触**（31 天 cookie 每次覆盖）；要首触就不能覆盖 → 建议**注册存首触、订单存末触，两列分开**。
- 访问采集**不需要 session 表**：`website.visitor`（唯一键 = 已登录则客户 id，匿名则 `sha1(IP+UA+session)[:32]`）+ `website.track` 明细（同页 30 分钟去重）；`visit_count` 在"距上次连接 > 8h"时 +1；匿名访客 60 天后 cron 直接删除。**明细只喂聚合，页面读按日汇总表**。
- 指标口径（**分母必须写进字段名**）：下单转化率 = 下单客户数 ÷ 登录客户数（分母是 **User** 不是 Session）；金蝶官方口径：转化率 = 订单数 ÷ 浏览人次，订单**不含代客下单/已取消/待确认**；GA4 明确区分 Session / User 两种转化率。除零返回 `null`。
- ⚠️「成交数量」在业界存在**笔数 vs 件数**的歧义，**必须先由业务定死**。

**裁决**：**现阶段继续如实留空（`null` → `-`），不建表。**
- 依据：本模块已经用"不填 0 冒充"的纪律处理了这三列，**这是正确的**。而实测 `shop_user` **0 行**、商城订单 **0 行** —— 就算今天把埋点表和 visitor_key 全建上，产出的依然是 0；建成的是"空转的基础设施"。
- 等有真实商城流量时再做的**最小落地**（已定方案，届时直接实施）：
  - 新增 2 表：`mall_track_event`（明细，保留 90 天）、`mall_track_daily`（按日汇总，永久，**页面直读**）
  - 加 3 列打通归因：`mkt_share_record.share_code + landing_url`（现在分享链接带不了 share_id，**链路第一环就断**）、`shop_user.reg_share_id + reg_visitor_key`（一列点亮"新客注册"）、`erp_sale_order.visitor_key`
  - 写入点**必须在后端**：visitor_key 服务端签发、utm 服务端落 cookie，**绝不信任前端提交的 share_id**（一旦用于推广提成即成攻击面）
- **明确不做**（YAGNI）：多触点归因、跨设备合并、广告 click-id、独立 session 表、实时看板；**不要复活 `erp_share_relation`**（实测 dev 库该表根本不存在）。

## 3. 四张余额表无"收付日期"列 → 往来余额表的期初/本期

**问题**：往来余额表要做四象限 `期初 / 本期发生 / 期末`，但四张余额表都没有发生日期列，本期发生额只能取 `期末 − 期初`。

**业界结论**：
- 两条生产级路线：**Odoo 不存期初**，靠报表换查询区间实时算；**SAP / 金蝶 / 用友 落"科目×期间"快照**（`FAGLFLEXT` 的期初列 + `HSL01..16` 分期间 / 金蝶 `T_GL_BALANCE` / 用友 `GL_accsum`），由结转程序写期初。
- ★ 三条铁律：
  1. **期间归属一律按记账/过账日期**（SAP 原文 "The posting date determines the posting period."）；
  2. **发生额必须同时存借方、贷方两个流量列**，**禁用"期末 − 期初"反推**；
  3. **期初必须是显式结转记录或另一段区间的聚合**，不能拿当前剩余额按单据日期切两刀。
- 追溯调整靠重跑结转 / 反结账 / 调整期级联重算。

**裁决**：**往来余额表应改凭证口径**（这是本清单里技术价值最高的一条），但**它是行为变更**，需先决策再动：
- 理由（实测支撑）：本项目**已有完整快照链** —— `LedgerServiceImpl.postToLedger()` 过账写 `finance_ledger`（**21 行，在写**），`closePeriod()` 实现了跨期/跨年结转但**无调用方**；而往来余额表**绕开了整条链**，直接读业务表的 `remaining_amount`。后果：期初低估、**漏计"本期新增且本期结清"的单据**，而 `期末 = 期初 + 本期` 恒真，所以**这个等式本来就构不成验证**。
- 落地口径（已定）：复用既有 `AuxBalanceMapper` 模式，按 `aux_unit` + 科目 1122/2202 + `fiscal_period` 聚合；**本期发生额改借贷两列**；预收/预付象限先用已有的 `receipt_date` / `payment_date`；补科目 1123/2203/2221。
- **状态**：**待决策**。改的是已验收页面的数字口径，且会动 `erp-finance`，需要业务确认"往来余额表以业务单据为准还是以凭证为准"。**在决策前保持现状，并把口径差异写进页面文档，不静默改数。**
- **明确不做**（YAGNI）：不新建余额表、不接 `closePeriod`、不做账龄分桶与历史时点回算（**无核销明细表**）。

## 4. 发票统计的进销项与税额符号

**问题**：对标 17 列要分 `销项开票` / `取得进项专票` 两组，但本系统 `InvoiceType` 把**方向/票种/用途塌成一个枚举**，且 `invoice` 表 0 行。

**业界结论**：
- 进销项在数据层要**独立成列**：`direction(SALE/PURCHASE)`；`invoice_kind` 走字典表；`deductible` + `deduct_status` **独立于票种**（用途类不可抵扣无法由票种推出）。
- 正负号：**存正数 + `is_credit_note` 标记，聚合时显式取负**；**税额列同样要做符号处理**（这一点最常被漏）。
- 「取得进项专票」的"必须是专票才可抵扣"要在数据层能表达。

**已实施（本次）**：**修了税额符号缺陷。**
- 证据：`InvoiceStatsServiceImpl` 同一段 SQL 里，**金额列做了符号处理**（`spAmt − ABS(snAmt)`），**税额与价税合计列却没做**（`SUM(tax_amount) FILTER (WHERE 销售)` 把红冲票**加了进去**）→ 一旦有红字发票，销项税额与应交税额会**虚高**。同一段 SQL 里两种口径并存，属实现自相矛盾，不是"业务选择"。
- 修法：`sTotal` / `sTax` / `pTotal` / `pTax` 四处改为 `SUM(CASE WHEN is_credit_note THEN -金额 ELSE 金额 END)`，与金额列口径对齐。合计行由逐行值重算，**自动继承修复**。
- 该缺陷当前是**潜伏态**（`invoice` 0 行），修在爆之前。

**待决策**：`direction` / `invoice_kind` 列与 `InvoiceType` 重构。
- **迁移窗口**：发票域 8 张表**全是 0 行**，是成本最低的迁移时点 —— 一旦有数据，改枚举语义就要写数据迁移。
- **不做**（YAGNI）：重构 `InvoiceType`、红字改存负金额。
- **附带规范化**：`invoice.tenant_id` 是 `varchar(50)`（全库其它表都是 `bigint`）、软删用 `is_deleted boolean`（全库用 `deleted integer`）。业界（SAP `MANDT`、Odoo `company_id`）的共性做法是**类型固定 + 过滤交给框架**，所以应**改数据为主、代码适配为辅**，并加一个扫 `information_schema` 的 CI 守门人。同样趁 0 行时改。

## 5. 配送指标缺列（最优路线 / 配送毛利 / 包装分档 / 退货赠品）

**问题**：业绩概览/明细要的 `最优路线(Km)`、`配送毛利总额`、`小/中/大包装`、`退货数量/金额`、`赠品数量`、`换算关系/换算结果` 都取不到。

**业界结论**：
- **两条线不可混**：UoM 线管换算（Odoo `uom.factor`、SAP `UMREZ/UMREN` 分子分母、金蝶计量单位组）；**packaging 线管实物**（Odoo `product.packaging` 含 `qty` + 唯一 `barcode`）。Odoo 另开一张表的理由是：UoM 是 category 级**通用**单位、packaging 是**产品专有**，且条码只在 packaging 上。
- **退货**：主流 = 独立单据类型 + **正向数量** + 挂回原单；**负数只在财务层**（负数量会破坏"数量 > 0"不变式）。
- **赠品**：主流 = **行级标志 + 单价 0**；**不能靠 `price_unit = 0` 反推**（0 价也可能来自整单免单）。
- **配送毛利**：收入 1 项 − 成本 N 项（结算运费 + 油耗 + 人工 + 维保）；行业占比：人工 43.8% / 燃油 21.3% / 折旧 16.7%。**无源分项必须 NULL** —— 0 是"测得的零"，NULL 是"未知"；填 0 会让毛利虚高、每公里成本虚低，**须同时输出成本覆盖率**。
- **最优路线距离**：业内是**派单时记录规划快照** + 事后用轨迹回填实际值，**不可事后重算**。

**裁决**：
- **包装分档不新建表**：本系统 `erp_product_unit.unit_type(SMALL/MEDIUM/LARGE)` + `conversion_rate` 就是 UoM 线，**join 即可**。（本次已按此修 业绩概览/明细 的取数链路。）
- ⚠️ **反面教训（必须记住）**：库里 **19 张表的 `small/mid/big_pack`、15 张表的 `conversion_result` 实测 0 行有值 —— 全是死列**。**不要照抄这个失败模式**（即不要为了"列齐"再新增冗余打包列）。
- **退货/赠品**：先查上游单据明细有无对应标志列，有则接、无则**如实留空**。
- **最优路线 / 配送毛利**：`dms_task` 无成本口径列、无规划快照列 → **如实留空**，不拿已有距离字段硬套、不用 `estimated_distance` 兜底出数。若将来要接，成本可从 `dms_vehicle_energy_log`（实测 128 行真实油耗）起步。
- **本次顺带修的真实缺陷**：业绩概览/明细原本 `FROM dms_task_item`，而该表 `product_id` 实测 **0/30 非空**，且配送域存在**口径分流**（有上游单据的任务不写明细）→ 主链路恒空。已改为 `dms_task → dms_task_doc → 上游单据明细`，`dms_task_item` 降为兜底。

## 6. 方法论沉淀（比上面任何一条都重要）

1. **先分清"缺字段"和"缺数据"**：本次 6 条里，`invoice` 0 行、`shop_user` 0 行、`erp_commission_rule` 0 行 —— **一半的"缺口"其实是"没有数据"**。对这些先建基础设施是**净负债**（空转的表 + 要维护的写入点）。
2. **先定口径再建表**：`下单转化率` 的分母到底是 User 还是 Session、`成交数量` 是笔数还是件数 —— 口径没定死就建表，等于把歧义固化进 schema。
3. **NULL ≠ 0**：无源必须 `null`（前端 `-`）。填 0 会让"毛利虚高 / 每公里成本虚低 / 转化率变成 0%"这类**看起来正常的错数**。
4. **同一段 SQL 里口径自相矛盾 = 缺陷信号**：本次的税额符号 bug 就是这么发现的（金额做了符号处理、税额没做）。
5. **死列是负债**：`small/mid/big_pack` 这类"为了列齐"加的列，19 张表全 0 行。**加列前先问"谁写它"**。
6. **不要为 0 行数据做破坏性重构**：反过来说，**0 行正是最佳迁移窗口** —— 发票域的字段规范化就应趁现在做。
