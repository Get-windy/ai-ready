## 1. 页面概述与业务口径（重要）

**配送员（原「骑手」）有两类来源**，这是本模块的核心业务口径：

| 类型 | 后端枚举 | 关联 | 说明 |
|------|---------|------|------|
| **企业员工** | `OWN_STAFF(1)` | `userId`（系统用户） | 自有配送员，走企业内部考勤/绩效 |
| 众包兼职 | `CROWD_SOURCE(2)` | — | 社会运力，按单结算 |
| **外部平台配送员** | `PLATFORM_RIDER(3)` | `channelId`（运力渠道） | 达达/美团/顺丰等第三方平台，资质由**渠道方背书** |
| 社会车辆司机 | `SOCIAL_DRIVER(4)` | — | 自带车辆的社会司机 |

## 3. 金标准目标设计

### 3.1 页面结构（金标准）

`CategoryListLayout` + `BillTableList`（序号齿轮列配置，`storage-key` = `dms-rider-columns`）+ `PageConfigPanel`（查询条件 / 功能按钮）。

- **列**：配送员编号、姓名、手机号、**类型**（企业员工/众包/外部平台/社会车辆）、**归属**（员工→系统账号；外部平台→渠道名称）、状态、审核状态、**资质到期**、评分、累计/今日单量、准时率、当前车辆、在线状态、最近上报时间、备注、创建时间、操作。
- **查询**：姓名/手机、类型（多选）、归属渠道、状态、审核状态、资质到期提醒、创建时间范围。
- **功能按钮**：新增、批量审核、**批量启停**、**同步外部运力**（跳《渠道管理》）、导入/导出、刷新。

### 3.2 表单（按类型差异化）

| 类型 | 必填字段 |
|------|---------|
| 企业员工 | 姓名、手机、**关联系统账号**、所属部门、入职日期 |
| 外部平台配送员 | 姓名、手机、**归属渠道**、平台骑手 ID、**渠道背书有效期** |
| 众包/社会车辆 | 姓名、手机、身份证、**车辆**（社会车辆必填）、结算方式 |

> 统一的**资质区**（见《实名认证》）：身份证、驾驶证、健康证、证照有效期与审核状态。

### 3.3 后端接口（金标准）

| 接口 | 说明 |
|------|------|
| `GET /api/dms/rider/page` | 多条件分页（补类型/渠道/资质到期/在线状态；联查渠道名称与车辆） |
| `POST/PUT /api/dms/rider` | 新增/修改（按类型校验必填） |
| `PUT /api/dms/rider/{id}/status` | **方法统一**（建议 PUT + body），状态机校验 |
| `POST /api/dms/rider/{id}/approve` | 审核（`verifyStatus` + `remark`，**参数形式与前端统一**） |
| `DELETE /api/dms/rider/{id}` | 删除（**前端改调此接口**，替换假删除） |
| `POST /api/dms/rider/location` | 位置上报（**路径与参数统一**，供配送员端调用） |
| `GET /api/dms/rider/options` | 选择器数据源（调度指派/车辆绑定/线路共用） |
| `POST /api/dms/rider/batch-approve` / `batch-status` | 批量审核 / 批量启停 |

### 3.4 业界生产级实践要点

1. **两类运力同池可比**：企业员工与外部平台配送员在调度侧**同权比较**（评分/负载/准时率），差异只在结算与资质来源。
2. **资质门控**：`verifyStatus` + 证照有效期不通过 → **不可被指派/接单**（联动《调度任务》《订单池》）。
3. **状态机**：离线 ⇄ 在线 → 忙碌 → 休息；在线判定优先用**轨迹上报心跳**（见《实时跟踪》），人工状态作为补充。
4. **绩效口径**：累计单量、准时率、评分、投诉数统一口径，供《智能调度》评分优先策略使用。
5. **合规**：身份证脱敏、外部平台只存背书结果（见《实名认证》）。
6. **选择器统一**：任何需要"选配送员"的地方（查询、指派、车辆绑定）一律走 `/rider/options`，禁止手输 ID。

## 6. 表单形态选型（2026-09-13 二次优化）

**问题**：初版表单直接套用 `BillFormPage` 的 `basicInfoFields` + `.info-flow`（`display:flex; flex-wrap:wrap; gap:8px`，每列 `min-width:120px`），22 个字段被挤成 6–7 行密排的窄列，观感"像在数据表里填字"。

**根因（组件选型错误）**：`BillFormPage` 的 info-flow 是**单据表头快速录单**布局（客户/仓库/经手人/日期一行扫过，字段少、横排、紧凑）；配送员是**档案（主数据）**（字段多、语义分组明确、编辑频率低）。

**对标依据**：
- 项目内先例——同属「人车管理」的 `views/dms/vehicle/form.vue` 已按此结论重写（"车辆是档案而非单据 → 四分区两列栅格，不再用 BillFormPage 的 inline flow"），源头是《资料模块》金标准 `views/md/logistics/form.vue`；
- 业界生产级（运力/HR 后台的骑手·员工档案）：分区卡片 + 2~3 列栅格 + 行内校验 + 到期日提示 + 底部固定操作条。

**落地形态（五分区两列栅格）**：

| 分区 | 字段 | 说明 |
|------|------|------|
| ① 基本信息 | 配送员编号 / 姓名* / 手机号* / 配送员类型* / 接单状态 / 头像地址 | 编号留空按 PSY 号段生成 |
| ② 归属与组织 | 按类型切换：企业员工（关联系统账号*/所属部门/入职日期）、外部平台（归属渠道*/平台骑手ID*）、众包·社会车辆（结算方式 / 社会车辆另需车牌*） | 分区提示语随类型变化 |
| ③ 资格与证件 | 身份证号 / 资质到期日期（外部平台显示为"渠道背书有效期"）/ 驾驶证号 / 健康证号 | 日期旁实时提示"剩 N 天 / 已过期，不可接单" |
| ④ 运力与排班 | 车辆类型 / 车牌号 / 服务半径 / 最大并行单数 / 上下班时间 / 保证金 | 供调度按评分·负载·半径选人 |
| ⑤ 备注 | 备注 | 500 字计数 |

页头（返回 + 标题 + 编号 tag + 审核状态 tag + 类型 tag）＋ 底部固定操作条（返回 / 保存 Ctrl+S）。校验改为 `a-form` **行内红字**（按类型动态 rules，与后端 `validateByType` 一致），保存前按类型裁剪 payload，避免把其它类型的专属字段写库。

**验收**：`tools/e2e-dms-rider.cjs` 118/118（含"切换外部平台后出现归属渠道/平台骑手ID/渠道背书有效期""表单必填校验拦截（行内红字）""表单保存后真实落库"）。
