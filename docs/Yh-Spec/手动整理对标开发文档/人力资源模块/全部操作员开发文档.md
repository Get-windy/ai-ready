## 1. 页面概述

「全部操作员」表面上是**系统账号（操作员）台账页**：分页查询 `sys_user`，并支持新增 / 编辑 / 启停 / 删除。

| 页面 | 地址 | 组件 | 行数 | 菜单挂载 | 说明 |
|------|------|------|:----:|:--------:|------|
| 全部操作员 | `md/staff-all` | `views/md/staff-all/index.vue` | 325 | ✅ `80532` | `ARReportPage`（路线 B）承载的账号 CRUD：2 项查询 / 10 列 / 7 字段弹窗 |

### 1.1 🔴 本页是**账号治理**页，不是 HR 页（必须先读）

| 维度 | 实情 | 判读 |
|------|------|------|
| 数据表 | **`sys_user`**（30 列） | **系统级账号表**，不是 HR 员工表 |
| 后端 | `SysUserController`（`cn.aiedge.base.controller`），前缀 `/api/user` | `core-base` 系统管理域 |
| 权限码 | `system:user:list` / `detail` / `create` / `update` / `delete` / `update-status` / `export` / `reset-password` / `assign-role` | **`system:` 前缀** —— 权威地说明这是系统管理能力 |
| `menu_code` | `md:staff-all` | `md:` = 资料 / 主数据域 |
| `component` | `views/md/staff-all/index.vue` | 物理落在 `views/md/` |
| 挂载位置 | 父 `61405 职员管理`（父 `60014 人力资源`） | **挂在人力资源下** |

四项证据（表 / 后端 / 权限码 / 路径）**全部指向系统管理域**，唯独菜单挂载在 HR。

**来源**：`V6.22.0__Fill_Mega_Menu_All_Columns.sql:250-255`（建在**「资料 > 职员权限 (61105)」**下）→ `V9.6.0__Menu_Consolidation.sql:154-155`（`UPDATE sys_menu SET parent_id = 61405`）→ `V9.18.0__Fix_All_Remaining_Placeholder_Paths.sql:26`（换真实组件）。被搬空的 `61105` 行**在库中已不存在**。

> **⚠️ 命名与定位问题（P1）**：「操作员」这个称谓在本系统里**只出现在这一个页面**。真实语义是 **`sys_user` 系统账号**（含登录账号、密码、`is_super_admin` / `is_tenant_admin` / `data_scope` / `last_login_time` 等**运维与安全字段**）。
> **收敛建议**：
> ① 菜单**改名**为「系统账号」或「用户账号」；
> ② **优先方案** —— 把菜单 `component` 改指 `views/system/user/index.vue`（**918 行**，同用 `userApi`），本页（325 行）废弃（详见 §5.5）。
> **本页的存在本身暴露一个更大的问题**：`sys_user` 是**系统管理**的账号，把它挂在「人力资源」下，会让 HR 使用者接触到**越权风险很高**的操作（重置密码、分配角色、启停账号）。

## 5. 业务规范

### 5.1 🔴 状态语义三处冲突（P0，必读）

`sys_user.status` 的语义在**同一个系统的三个位置**有三种说法：

| # | 位置 | 说法 | 证据 |
|:-:|------|------|------|
| 1 | 实体注释 | **`0-正常 1-禁用 2-锁定`** | `entity/SysUser.java:83` `/** 状态（0-正常 1-禁用 2-锁定） */` |
| 2 | 登录校验 | **`1` 才允许登录**（故 `0` 与 `1` 之外全部视为禁用/锁定） | `SysUserServiceImpl.java:69-71`：`if (user.getStatus() != 1) throw new BusinessException(403, "用户已禁用或锁定")` |
| 3 | 状态更新守卫 | **`0` = 禁用**（故「超管不可禁用」= 不允许把 status 改成非 0） | `SysUserServiceImpl.java:360-365`：`if (isSuperAdmin && status != 0) throw "超级管理员不可禁用"`（租户管理员同） |
| 4 | **新建用户** | **写死 `0`** | `SysUserServiceImpl.java:144`：`user.setStatus(0)` |
| 5 | 前端（本页） | **`1` = 启用（绿 tag）、`0` = 禁用（灰 tag）**；按钮写 `record.status === 1 ? 0 : 1` | `index.vue:25-26`、`:49`、`:183-186`、`:303-312` |

**推导结论**：

- ②③⑤ **互相一致**（`1` = 正常/启用，`0` = 禁用），**①（实体注释）是错的**。
- **④ 与 ② 冲突**：`createUser` 把新账号写成 `status = 0`，而登录校验要求 `status == 1`
  → **刚创建的操作员：既在列表里显示为「禁用」（灰 tag），也登录不了**。必须由管理员再点一次「启用」把状态改成 1 才能用。
- devdb 实测分布印证该口径：**`status = 0` 共 30 行，`status = 1` 共 41 行**（`sys_user` 合计 71 行）。
- 另外 `1` 语义下，值域里的 **`2 锁定` 在登录校验中与 `0` 同效**，但**页面上无法表达**（tag 只会显示「禁用」，行按钮只会在 `0/1` 之间切换）→ **被锁定的账号一旦被点「启用」就变成 `1`，直接解锁**。

> **⚠️ 裁定建议（P0）**：
> ① 以 **`0 = 禁用 / 1 = 正常`** 为准（②③⑤ 已一致），**订正 `SysUser.java:83` 注释**；
> ② **`createUser` 的 `setStatus(0)` 必须改** —— 要么改为 `1`（新建即可登录），要么改为显式的「新建后待启用」并**在前端提示管理员**；
> ③ 若确实需要 `2 锁定`（如密码错误次数超限），须**前端 tag / 按钮 / 查询选项三处同步支持**，否则该状态不可运维；
> ④ **不得**用 `ALTER TABLE ... SET DEFAULT` 订正存量（PostgreSQL 会回填既有行 → 语义翻转，参见《_开发指南-金标准》陷阱 17）；应写 Flyway **显式 UPDATE** 并按旧值逐行映射。

### 5.4 🔴 跨租户数据泄漏（P0，本页最严重）

`GET /api/user/page` 的租户过滤**完全依赖调用方传 `tenantId`**，而前端**从不传**：

| 环节 | 实际值 | 证据 |
|------|--------|------|
| 前端调用 | `userApi.getPage(params)`，`params` 只含 `pageNum/pageSize/username?/status?` | `index.vue:206-208`；`ARReportPage.vue:245-268` |

| Service | 原样透传给 Mapper | `SysUserServiceImpl.java:247-250` |
| Mapper XML | `SELECT * FROM sys_user WHERE deleted = 0` + **`<if test="tenantId != null"> AND tenant_id = #{tenantId} </if>`** | `SysUserMapper.xml:76-92` |
| **`sys_user` 是否被多租户拦截器忽略** | ✅ **被忽略** | `MyBatisPlusConfig.IGNORE_TENANT_TABLES` 含 `"sys_user"`（`MyBatisPlusConfig.java:41`，注释：「用户表（登录时需要无租户过滤查询）」） |

**→ 三道防线全部落空**：前端不传 `tenantId` → `<if>` 不生效 → 租户拦截器**恰好在 `sys_user` 上被关闭** → **返回全库所有租户的用户**。

| 项 | 值 |
|----|-----|
| `sys_user` 总行数 | **71** |
| `tenant_id = 1` | **68** |
| **`tenant_id = 0`（平台/无租户）** | **3** |

→ 以租户 1 的管理员登录本页，**会看到 71 行，其中 3 行不属于租户 1**。

> **⚠️ 修法（P0，三选一，建议 ①+③ 同时做）**：
> ① **后端强制**：`SysUserController.pageUsers` 忽略前端入参，改用 `SecurityUtils.getCurrentTenantId()`；仅当当前用户是平台超管（`is_super_admin = true`）时才允许跨租户（此时应提供显式租户筛选控件）。
> ② **前端补参数**：`userApi.getPage` 注入 `tenantId: userStore.tenantId` —— **但前端参数可被篡改，不能作为唯一防线**。
> ③ **`sys_user` 的忽略理由需细化**：现有注释的理由是「登录时需要无租户过滤查询」。**正确做法是把 `ignoreTable` 粗粒度开关改为"仅登录路径走无租户查询"**（登录用自定义 SQL / 临时租户上下文），而不是让全表在整个运行期都不隔离。
> **注意**：`sys_user` 的忽略**不可直接移除** —— 登录流程（`SysUserServiceImpl.login`）在**尚未建立 Sa-Token 会话时**查用户，移除会导致登录挂掉。必须**按调用路径**区分，见 `MyBatisPlusConfig.setTempTenantId` 的既有机制。

| 项 | 事实 |
|----|------|
| 索引 | 实测仅 **3 个**（`pg_indexes`）：`sys_user_pkey` + **`uk_super_admin`** + **`uk_tenant_admin`**（后两个对应实体注释里的「数据库唯一约束，最多一个 true」）。**无 `username` / `tenant_id` / `dept_id` / `status` 索引** —— 用户名唯一性**纯靠代码校验**（`selectByUsername`），71 行尚可，账号规模上千后分页会慢 |

| 逻辑删 | `@TableLogic`（`SysUser.java`）✅ |
| 乐观锁 | `version` + `@Version` ✅ |

## 8. 业界对标（SAP / 金蝶 / 用友 / Odoo）

> 本页在 ql361 **无对应页**（该对标系统**无人力资源模块**）。以下为业界标准做法与本系统的差距。
> **参考来源：** Odoo 18 HR `https://www.odoo.com/documentation/18.0/`（章节待补充）；SAP SuccessFactors RBP / Position Management `https://help.sap.com/`（章节待补充）；金蝶 s-HR `https://vip.kingdee.com/`（章节待补充）；用友 DHR `https://success.yonyou.com/`（章节待补充）。
> 本模块已核验的调研底稿：《人力资源-业界做法调研.md》（同目录），本节引用其 §1.2 / §1.3 / §2.1 / §2.6。

| # | 能力 | 业界做法 | 本系统当前 | 差距与建议 |
|:-:|------|---------|-----------|-----------|
| 1 | **账号生命周期（User Provisioning / Deprovisioning）** | 业界标准是「**入职开号、离职封号**」的**自动化**：HR 系统与账号目录（AD / LDAP / IAM / SAP IAS）集成，入职事件 → 自动建号 + 按岗位赋角色；离职事件 → 立即封号 + 回收权限 + 转移数据 | `hr_employee` 实测 **29 列，没有 `user_id`** → **员工与账号零关联**；本页只做手工 CRUD；**无任何入职/离职事件钩子** | **P0（架构）**：这是本模块最贵的缺口。最小可行改造：① `hr_employee` 补 `user_id`（+ `hr_employee_history` 或复用员工状态）；② 员工 `status` 变为「离职」时自动 `PUT /api/user/{id}/status` + **强制下线**（同一事务）。**不需要**先建 IAM 集成，先把「离职必封号」做成硬约束 |
| 2 | **禁用/改密后必须踢会话** | 所有生产系统的标配：账号被禁用 / 密码被重置 → **立即失效所有活动会话** | `updateUserStatus` / `resetPassword` **只改 DB**（`SysUserServiceImpl.java:355-372`、`:211-231`），**不调用 `StpUtil.kickout`** → **被禁用/改密的用户，其现有 token 依然可用**（Sa-Token 会话默认长期有效） | **P0（安全）**：在 `updateUserStatus`（`status != 1` 时）与 `resetPassword` / `changePassword` 中调用 `StpUtil.kickout(userId)`，并补一个显式的「强制下线」按钮 |
| 3 | **返回给前端的账号对象必须脱敏** | 厂商系统与自研系统**一致遵守**：密码/凭证字段**永不出接口** | `GET /api/user/page`、`/list`、`/{id}` 返回**裸 `SysUser` 实体**，`password` 字段**无 `@JsonIgnore`**（`entity/SysUser.java:40`）→ **BCrypt 哈希随 JSON 返回** | **P0（安全）**：改返回 VO（推荐），或至少 `@JsonIgnore`/`@JsonProperty(access = WRITE_ONLY)`。**BCrypt 是慢哈希，泄露不等于立刻可逆，但属于不可接受的信息暴露**（可离线爆破 + 暴露算法与成本因子） |
| 4 | **账号 ↔ 角色 ↔ 权限的分层** | SAP RBP：**Permission Roles（权限集合）× Permission Groups（谁被授予）× Target Populations（对谁生效）**；官方建议先建组再建角色 | 本系统 `用户 ↔ 角色 ↔ 菜单/权限` 经典 RBAC（`sys_user_role` + `sys_role_permission` + `sys_role_menu`）；**无"目标人群"维度** | **P2**：本系统的 `sys_user.data_scope`（`ALL/DEPT/DEPT_CHILD/SELF`）+ `DataScopeInterceptor` ≈ SAP 的 Target Populations，**已存在但未与角色绑定、且无 UI** → 建议补「角色 + 数据范围」的联合配置（而不是新增一套模型） |
| 5 | **账号与员工不是同一实体** | 业界把「人员（HR）」「编制岗位（HR）」「账号（IT）」分开，靠映射连接；SAP 用 `pos2jobInfo` 把职位信息同步进员工任职信息 | 本系统把「操作员」直接等同于 `sys_user`；`hr_employee` 是**另一套人事档案**且**无 `user_id`** → 同一个人存在两份互不相干的记录 | **P0**：见第 1 条。**建议**：以 `sys_user` 为唯一账号主数据，`hr_employee.user_id` 单向指向它；**不要**在两边各存一份姓名/手机号（当前已各存一份，会不一致） |
| 6 | **登录审计与异常检测** | 业界标配：登录历史、失败次数、异地/异常登录告警、密码过期强制改密、MFA | ✅ 有 `password_update_time` + 90 天策略 + 登录时算 `passwordExpired`；✅ 有 `last_login_time` / `last_login_ip`；❌ `sys_login_log` 表存在但**未接线**；❌ `login_count` **恒 0**；❌ 无失败次数 / 无锁定 / 无 MFA / 无异地告警 | **P1**：接线 `sys_login_log`；`login_count` 自增；补失败计数与自动锁定（`status = 2` 才有意义，见 §5.1） |
| 7 | **批量账号操作与导入** | 业界标配：批量导入（HR 主数据同步）、批量分配角色、批量停用 | 端点齐备（`/batch`、`/batch-assign-roles`、`/list`），**前端全无入口**；**无导入端点** | **P1**：接线已有端点；批量导入可复用本系统已有的「CSV 两步向导」模式（参见《CRM模块/客户开发文档》§5.5） |
| 8 | **账号数据隔离** | 多租户系统必须**服务端**强制隔离；跨租户查看须显式授权 | ❌ **跨租户泄漏**：`sys_user` 被排除在租户拦截器外 + 前端不传 `tenantId` → 返回全部 71 行（含 3 行 `tenant_id = 0`） | **P0**：见 §5.4 修法 |
| 9 | **账号启用状态语义** | 值域必须**单一权威定义**并贯穿前后端 | **三处冲突**：实体注释 `0-正常/1-禁用` vs 登录校验 `1=可登录` vs `createUser` 写 `0` → **新建账号默认登录不了** | **P0**：见 §5.1 裁定 |

**明确不借鉴**：SAP 的多公司/多国法定账号矩阵（本系统无多公司场景）；MFA / SSO / SCIM 等企业 IAM 全套（属独立基础设施，不在本页范围）；业界界面的视觉样式。

## 10. 验收标准（目标）

> 本模块**尚无 E2E 脚本**。以下为按金标准制定的验收清单，建议并入 `tools/e2e-hr-staff.cjs`。
> **前置条件（关键，且带风险）**：`sys_user` 有 **71 行真实账号**（含 3 行 `tenant_id = 0`、1 个超管 `admin`）。
> **本页验收必须在"只读 + 可完全复原"的前提下进行**：新增的测试账号用**唯一前缀**（如 `e2e_op_<ts>`）标识，收尾**必须删除**；**严禁**在本页对既有账号执行「禁用」「删除」「重置密码」—— 会影响并行会话（参见《按进程名杀进程会并行会话误杀》《共享db E2E 断言必须加作用域》）。

### 10.1 接口验收（目标 ≥ 18 项）

1. `GET /api/user/page` 默认查询 200，`total` 与直查 DB（`deleted = 0`）**逐值一致**。
2. `pageNum` / `pageSize` 生效：`pageSize=1` 时 `records.length === 1`。
3. **租户隔离断言（P0-2 回归）**：以租户 1 管理员请求，`records` 中**不应出现 `tenant_id = 0` 的行** —— **当前会失败**（总数 71 而非 68），这是跨租户泄漏的直接证据。
4. `username`（`LIKE`）/ `status`（`=`）逐个生效（造数验证）。
5. `deptId` **后端支持但前端未接** —— 接口层验证可用。
6. **响应体脱敏断言（P0-1 回归）**：`records[0]` **不含 `password` 字段**（或值为 `null`）—— **当前会失败**。

  | `SysUserServiceImpl.pageUsers` | 新增 `resolveScopedTenantId()`：超管沿用调用方传入值（null = 不限制），其余**忽略**传入值、强制用 `SecurityUtils.getCurrentTenantId()`；取不到会话租户且非超管 → 403 |
  | `SysUserController` | 新增 `assertSameTenant(id)`，作用于 `GET /{id}`、`PUT /{id}`、`DELETE /{id}`、`DELETE /batch`（逐个校验）、`PUT /{id}/password/reset`、`POST /{id}/roles`；`PUT /{id}/password/change` 另加「仅限本人（超管除外）」 |
  | `UserServiceOptimizedImpl.pageList`（`/api/v2/user/page`） | 非超管追加 `eq(SysUser::getTenantId, 会话租户)` |
  | **故意未改** | `getUserDetail` —— 它被 `SecurityContext` / `PermissionUtils` / `DataPermissionServiceImpl` 等**框架内部**逐请求调用，越权校验只能放 HTTP 边界，不能进这个方法 |

  **为什么用 `SecurityUtils.getCurrentTenantId()`**：它读 Sa-Token Session 里的 `tenantId`，
  因此超管「切换租户」后立即生效，无需额外适配。超管判定沿用 `SUPER_ADMIN` 角色码（与 `SysMenuServiceImpl` 同源，不新造第二套）。

  **验证（E2E 第 9 节，7 项断言全绿）**：
  - 超管查列表 → 仍能看到租户 2 的账号（**豁免生效，admin 行为与修复前一致**）
  - 非超管租户管理员查列表 → **看不到**租户 2 的账号
  - 非超管**显式传** `?tenantId=2` → **同样被忽略**（参数不可用来越权）
  - 非超管按 id 读租户 2 账号详情 → **403**
  - 超管按 id 读任意租户账号 → 仍可

  > ⚠️ **验证经验**：**用 `admin` 是断言不出租户隔离的** —— 超管本就该看到全部。
  > 必须专造一个**非超管**租户管理员（本仓库 `e2e_hr_ta`，角色 `SYSTEM_ADMIN`）
  > + 一个**第二租户**的靶子账号（`e2e_hr_t2`），见 `tools/e2e-hr-user.sql`。

  #### ✅ 彻底收口：`sys_user` 已移出全局忽略表（2026-09-18 第二轮）

  按 RuoYi 上游做法改为「**登录链路局部放开**」，常规路径由拦截器**自动**带租户条件，不再逐处补：

  | 位置 | 改动 |
  |---|---|
  | `MyBatisPlusConfig.IGNORE_TENANT_TABLES` | **移除 `sys_user`**（原是「用户表（登录时需要无租户过滤查询）」） |
  | `AiReadyTenantLineInnerInterceptor.shouldSkip()` | 由「租户不可解析」扩展为「租户不可解析 **或** 当前会话整体豁免」 |
  | `MyBatisPlusConfig.isTenantScopeExempt()` | 新增：读 Sa-Token Session 的 `tenantScopeExempt` 标记 |
  | `SysUserServiceImpl.login` | 登录时写入该标记（平台超管 = true） |

  **为什么登录链路无需特判**：登录发生在认证之前，此时既无 Sa-Token 会话、也无临时租户上下文，
  `shouldSkip()` 天然返回 true → `selectByUsername` / `selectByPhone` / `selectByEmail` 与注册（`TenantRegistrationService`）
  照常跨租户可查。**认证之后**的常规查询则自动带上 `tenant_id`。
  （已逐个核对三个 `selectByUsername` 调用点：登录、`PasswordResetRunner` 启动任务、租户注册 —— 全在认证前。）

  🔴 **两个必须记住的坑（都实踩过）**

  1. **绝不能在拦截器里实时算角色** → `StpUtil.hasRole(...)` 会查角色 → 那条 SQL 又过拦截器 → 再次判定 → **无限递归**。
     实测症状：登录直接 `java.lang.StackOverflowError`、前端只看到「系统异常」。
     原代码注释「将租户ID存入 Sa-Token Session，**避免多租户拦截器递归查询**」说的就是这件事。
     正解：豁免标记**登录时算好写进 Session**，拦截器只做一次 Session 读取（`isTenantScopeExempt()`）。
     **副作用**：改动前已签发的旧 token 没有该标记，会被当作「不豁免」而按会话租户收敛 —— **重新登录一次**即可恢复。
  2. **超管必须整体豁免**：拦截器不认识「超管」，一旦给表开了自动注入，`admin` 也会被收敛到会话租户。
     故 `shouldSkip()` 里加了 `isTenantScopeExempt()`，与 `resolveScopedTenantId` / `assertSameTenant` 三处口径同源。

#### 附：业界生产级系统怎么处理「平台账号 vs 租户账号」（2026-09-18 调研）

> 调研问题：① 平台运营方（厂商）账号与租户账号是否同表？② 租户管理员的「用户管理」列表里会不会看到平台/厂商账号？③ 主流框架的既有约定是什么？

**结论一：成熟系统把「平台运营」与「租户应用」拆成两个平面（plane），平台账号根本不进租户的列表。**
AWS《SaaS Architecture Fundamentals》原文：
> "the control plane and its services **are not actually multi-tenant**. …These services are **global to all tenants**."
> "You'll also notice that we show a **separate administration application**. This represents the application … that might be used by **a SaaS provider** to manage their multi-tenant environment."

即：**租户管理/租户用户管理属于控制平面**，控制平面本身**不是多租户的**、对全部租户是全局的，
且厂商用**单独的管理应用**去操作它 —— 租户管理员的应用平面里**没有**厂商账号这个概念。

**结论二：跨租户能力表达为「身份上的角色/属性」，而不是「一个魔法 tenant_id」。**
- PostgreSQL 官方：`BYPASSRLS` 角色属性是官方定义的跨租户绕过手段（"superusers and roles with the `BYPASSRLS` attribute always bypass the row security system"）；Supabase 的 `service_role` 即走此路，且**绝不允许暴露给面向用户的代码**。
- Microsoft Entra ID：外部账号以 `UserType = Guest` 入目录，**默认只能读自己的对象**，与 Member 的权限差一大截（Member 可枚举全部用户/公共属性）。
- Keycloak：`master` realm 的 `admin` / `create-realm` 是**全局角色**，官方明确建议 *"use the master realm only to create and manage other realms"*，**不要**在 master realm 里放应用用户。每个租户有独立 Admin Console。

**结论三：「保留系统租户 ID」是真实存在的约定，但要点是「保护」而非「共用」。**
- **RuoYi-Vue-Plus（本代码库的直接上游同族）**：保留 `tenant_id = '000000'` 作默认系统管理租户；`checkTenantAllowed` 对该租户直接抛 `不允许操作管理租户`；**只有超管能切换租户**；多租户忽略表通过 `tenant.excludes` 配置，另提供 `TenantHelper.ignore(…)` **局部**放开。
- NodeDB：把 slot `0` 留给 `system`、`1` 留给 `bootstrap`，自动分配的租户 ID **从 2 起**，且**删除后永不复用**。

  ⚠️ 本条**不适用于本代码库**：本库 `SYSTEM_TENANT_ID = 1L`，而 `sys_tenant.id = 0` 是一条遗留测试租户。**不要**照搬「把 0 当管理租户」的写法。

**结论四：厂商/支持人员如需进入租户，用「限时 + 被授权 + 留痕」的模拟登录，而不是在租户里放一个常驻账号。**
Salesforce 的 **Login Access / Login-As**：由 **org 管理员**授权、**限时**、经 SAML assertion 完成，不需要交换凭据；
其 support user class 对应用元数据仅**只读**。官方同时提醒该能力要强制 MFA、并可关闭「管理员可登录为任意用户」。

**对本站的裁定建议（依据上述四条 + 上游同款做法）**

> ⚠️ **务必不要「一刀切」按当前租户收口** —— 这一条是本页文档初稿的缺陷，2026-09-18 订正：
> **平台超级管理员必须豁免**。实测本库 `admin` 满足 `is_super_admin = true` 且角色为 `SUPER_ADMIN`（`tenant_id = 1`），
> 而 `tenant 1 = 系统租户` 即平台自身；RuoYi 上游也明确「**只有超管支持切换租户**」。
> 若不加豁免，超管登录后会**看不到别的租户数据**，「用 admin 验证开发」这条主路径当场断掉 —— 而且那种"数据凭空少了"的现象
> 极难被识别为权限问题。**正确规则是「超管不受限 / 可切租户，普通租户管理员限本租户」**，不是「所有人限本租户」。

| 项 | 建议 |
|---|---|
| `pageList` 缺少租户条件 | **按缺陷修，但带超管豁免**：非超管调用时显式 `eq(SysUser::getTenantId, 当前租户)`；超管保持现状（全局可见 / 可切租户） |
| 超管判定用什么 | 与本库既有口径一致即可：`SecurityUtils.hasRole("SUPER_ADMIN")`（或 `SysUser.isSuperAdmin`）；**不要**新造一套判定 |
| 当前租户取什么 | `SecurityUtils.getCurrentTenantId()` —— 它读的是 **Sa-Token Session 里的 `tenantId`**，因此天然支持「超管切换租户」后立即生效，无需额外适配 |
| 更彻底的收口 | 参照上游：`sys_user` 不进全局忽略表，改为**登录查询处局部 `ignore`**，让常规查询自动带租户条件 |
| `tenant_id = 0` 那行 | 属**遗留测试数据**（停用租户 + `apitest_*` 账号），应清理，而不是为它设计可见性规则 |
| 平台运营账号（若将来需要） | 放**控制平面**：独立管理端 + 独立账号体系；确需进入租户时用**限时模拟登录 + 审计**，不要在租户用户表里放常驻厂商账号 |
| 验证「租户隔离真的生效了」 | 需要一个**非超管**的租户管理员账号来断言；**用 `admin` 是断言不出来的**（超管本就该看到全部）。E2E 要用专用账号，不要复用超管 |
