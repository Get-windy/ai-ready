## 1. 页面概述

本页是外勤拜访的第一段（Plan）：把「谁、何时、去哪、做什么」登记成**拜访计划**，供执行段认领、检视段统计覆盖率。

| 页面 | 地址 | 组件 | 行数 | 说明 |
|------|------|------|:----:|------|
| **拜访规划（本页）** | `sales/visit-plan` | `views/sales/visit-plan/index.vue` | 387 | 10 列台账 + 新建/编辑弹窗 + 取消/删除；**无统计卡** |
| 拜访执行 | `sales/visit-exec` | `views/sales/visit-exec/index.vue` | 442 | 签到打卡，可关联本页计划并**联动置为已完成** |
| 拜访检视 | `sales/visit-review` | `views/sales/visit-review/index.vue` | 140 | 只读检视 + 7 张统计卡 |

### 1.1 三页构成「计划-执行-检视」闭环（方向正确，应肯定）

```
crm_visit_plan ──planId──▶ crm_visit_record ──聚合──▶ 统计/检视
  计划(status 0..3)          执行记录(result 1..3)      覆盖率/结果分布
```

| 环节 | 载体 | 关键联动 |
|------|------|---------|
| 计划 Plan | `crm_visit_plan`（19 列） | 本页创建，`status = 0 待执行` |
| 执行 Do | `crm_visit_record`（20 列） | 执行页打卡写入；**`planId` 非空时后端把计划置为 `2 已完成`**（`VisitRecordServiceImpl.java:50-56`） |
| 检视 Review | 无独立表 | 检视页算 `coverage = 已完成计划 / 计划总数`（`VisitRecordServiceImpl.java:117-128`） |

> **结论**：三段**共享同一条主记录链**（`plan_id` 关联 + 状态回写），与业界标准一致 —— 这是本模块**最值得肯定的设计**，不是三张互不相干的表。

### 1.2 菜单归属「名实不符」（必须如实登记）

| 维度 | 实际值 | 应然 |
|------|--------|------|
| 菜单挂载 | `CRM(60007) → 外勤拜访(60101) → 拜访规划(70001)` | ✅ CRM |
| `menu_code` | **`sales:visit-plan`** | ❌ 前缀是 `sales` |
| 路由 / 组件目录 | **`sales/visit-plan`** / `views/sales/...` | ❌ 不在 `crm/` 下 |
| 接口前缀 | `/api/crm/visit/plan/*` | ✅ crm |

即：**菜单在 CRM、代码在 sales、接口在 crm**。

> **收敛建议**：三页 `menu_code` 改为 `crm:visit-plan` / `crm:visit-exec` / `crm:visit-review`（路由/组件目录若一并搬迁需另裁定）。
> **安全性已核实**：`menu_code` 仅被 `SysMenuServiceImpl.checkMenuCodeExists`（`:237-244`，按 `tenant_id=0` 做唯一性检查）与 `SysMenuMapper.xml:116`（`WHERE menu_code = #{menuCode}`）使用；**角色授权按 `menu_id`** 关联 `sys_role_menu`（列实测为 `id/role_id/menu_id/tenant_id/create_time/deleted`）→ **改 `menu_code` 不影响已下发权限**。

### 1.3 拜访对象取的是 CRM 客户，不是 ERP 客户

「客户」下拉走 `crmCustomerApi.dropdown`（`api/crm.ts:414-427`）→ `GET /api/customer/dropdown`，即 `crm_customer`。外勤拜访属**客户服务与维护**，未必已成交 → 取 CRM 客户**正确**；本页与 ERP `biz_party` 无关，也不产出任何 ERP 单据。

> ⚠️ **边界缺口**：若拜访对象是已成交客户（存在于 ERP），CRM 侧靠 `crm_customer.md_partner_id` / `crm_erp_customer_mapping` 建映射，但**该映射全模块未接线**（README §4）→ 从 ERP 客户出发找不到对应拜访计划。

> ✅ **设计要点**：后端**按实体原样保存**（`VisitController.java:45-56`），两个**冗余快照列**由前端回填，省掉后端二次查询。
> ⚠️ **副作用（P2）**：`resolveNames()` 依赖「下拉能查到该项」。下拉加载失败（`:367-369` 只 `console.warn`）或客户不在**前 200 条**内时 `find` 返回 `undefined` → `updateById` 的 `NOT_NULL` 策略跳过该列 → **快照列停留旧值**（改名后列表仍显示旧客户名）。另：CRM 客户改名后历史计划的 `customer_name` 不同步（快照语义，需明确）。

`openEdit`（`:287-299`）只回填 7 个可编辑字段，**不回填** `planNo`/`status`/名称列。

## 5. 业务规范

### 5.1 状态值域与迁移（唯一真源在后端）

| 字段 | 值域 | 前端 | 后端 |
|------|------|------|------|
| `status` | `0 待执行 / 1 执行中 / 2 已完成 / 3 已取消` | `STATUS_MAP`（`:178-183`）+ 由它反推的 `statusOptions` | 实体注释（`VisitPlan.java:9-12`）+ 参数说明（`VisitController.java:34`）+ 建表默认 `0` |

| 迁移 | 触发 | 后端 |
|------|------|------|
| `0` → `1` | **无任何入口** | ⚠️ 见下 |
| 任意（非 2） → `2` | 执行页打卡且 `planId` 非空 | `VisitRecordServiceImpl.java:50-56` |
| `0/1` → `3` | 本页「取消计划」 | `VisitPlanServiceImpl.java:53-64`（`status == 2` 时**拒绝**返回 `false`） |
| `2` → 其他 | 不允许 | ✅（后端拦，前端隐藏按钮） |

> ⚠️ **P1：`1 执行中` 是死状态。** 全仓仅三处写 `crm_visit_plan.status`：`setStatus(0)` 默认、`setStatus(2)` 完成、`setStatus(3)` 取消 —— **没有任何代码写 `1`**。而前端却在查询下拉、tag 配色、超期判定里都把它当正常值。业务上「执行中」应有明确动作（如「出发/开始拜访」），否则应删除；**两者选一**。

### 5.2 编号规则（`plan_no`）

`VisitPlanServiceImpl.java:45-50`：`"VP-" + yyyyMMdd + String.format("%04d", selectCount(null) + 1)`。生成时机 `VisitController.java:48-50`（仅当请求体 `planNo` 为空/空串）。唯一约束 **`uk_crm_visit_plan_no` UNIQUE(plan_no)**（devdb 实测）。前端表单**不采集** `planNo`（`:259-267` 无该键）→ 用户不可见、不可改。

> 🔴 **P0：生成器可撞号 → 新建计划 500。** 复现（无需并发）：① 今天已建 `VP-202609180011`（未删计划数 11）；② `DELETE /plan/{id}` 逻辑删该条 → `selectCount(null)` 回到 10；③ 再新建 → 又是 `VP-202609180011` → **唯一索引冲突（PG 23505）→「保存失败」**。原因：唯一索引**不含 `deleted` 条件**，逻辑删的行仍占位；且**无锁、无序列**，并发创建同样必撞。
> **修法**：改用本系统既有**号段服务（`next-no`）**；唯一索引改「租户内唯一」（当前全局唯一，多租户会跨租户互相占号）。附带缺陷：序号是**全局流水**非当日序号（跨天不重置），`selectCount` 又天然不含已删行，与「流水号」语义不符。

### 5.3 关键业务规则

| 规则 | 当前 | 评估 |
|------|------|------|
| 计划日期可早于今天 | ✅ 允许（无校验），超期仅红字提示 | 新建时应二次确认或默认拒绝（业界建议） |
| 计划时间 | **自由文本** | 无格式校验、无法排序、无法与执行记录时间比对 |

| 计划 → 执行 | `planId` 关联，**一计划可被多条记录关联**（无唯一约束、`checkIn` 不判重） | 覆盖率虚高（详见执行页文档 §5） |

## 7. 数据模型

### 7.1 `crm_visit_plan`（**19 列**，devdb 实测 2026-09-18）

```
id, tenant_id, plan_no, customer_id, customer_name, sales_person_id, sales_person_name,
plan_date, plan_time, purpose, address, status, remark,
created_by, created_at, updated_by, updated_at, deleted, version
```

| 列 | 类型 | 可空 | 默认 | 说明 |
|----|------|:----:|------|------|
| `id` | `bigint` | NO | `nextval('crm_visit_plan_id_seq')` | **自增**（`@TableId(IdType.AUTO)`，`VisitPlan.java:17-18`）→ 前端 `number` 传 id 安全（**不涉及**雪花 ID 精度陷阱） |
| `tenant_id` | `bigint` | YES | null | 由 `MetaObjectHandler` 注入（`MyBatisPlusConfig.java:173-185`） |
| `plan_no` | `varchar` | **NO** | null | `uk_crm_visit_plan_no`（**全局唯一，未按租户**） |
| `status` | `integer` | **NO** | **0** | 建表已保证非空 ✅ |
| `deleted` | `integer` | NO | 0 | `@TableLogic`（`VisitPlan.java:56-57`） |
| `version` | `integer` | NO | 0 | `@Version`（`:59-60`）→ 乐观锁列存在 |
| `created_at` / `updated_at` | `timestamp` | YES | `CURRENT_TIMESTAMP` | 见 §7.2 |

**索引（实测）**：`pkey(id)`、`uk_crm_visit_plan_no(plan_no)` UNIQUE、`idx_..._customer(customer_id)`、`idx_..._sales_person(sales_person_id)`、`idx_..._date(plan_date)`、`idx_..._status(status)` → 本页 4 个查询条件**全部有索引覆盖** ✅。

### 7.2 审计列的三处实测缺陷（P1）

`VisitPlan.java:44-54` 用 `@TableField(fill = FieldFill.INSERT/UPDATE)` 标注 `createdBy`/`createdAt`/`updatedBy`/`updatedAt`；而全仓唯一填充器（`MyBatisPlusConfig.java:166-193`）**只填两个字段名**：`insertFill` → `createTime` + `updateTime` + `tenantId`；`updateFill` → `updateTime`。

| 列 | 实测结论 |
|----|---------|
| `created_at` | ⚠️ 填充器**不填** `createdAt`，靠列默认 `CURRENT_TIMESTAMP` 兜住 → 有值但非应用层写入 |
| `updated_at` | 🔴 **永不刷新**：填充器填的是 `updateTime`（本实体无此字段），`updateById` 的 `NOT_NULL` 策略又把 `updatedAt=null` 从 SET 剔除 → **停在 INSERT 时刻** |
| `created_by` / `updated_by` | 🔴 **永远为 NULL**（填充器不含这两个字段名，前端也不传） |
| `version` | ⚠️ `updatePlan` 用请求体 + `setId(id)`（`VisitController.java:60-64`），**请求体不含 version**（前端表单无此键）→ MP 在版本值为 null 时**不加版本条件** → **实际无并发保护** |

> **对照**：`crm_visit_record` 用的是 `create_time`/`update_time`（**正好命中填充器名单**）→ 那个表的 `update_time` **是**被正确刷新的。同模块两表因命名不同，一个能刷新、一个不能。
> **修法（二选一）**：① 实体改名（破坏性，需迁移列名）；② 在 `MetaObjectHandler` 补填 `createdAt`/`updatedAt`/`createdBy`/`updatedBy`（推荐，非破坏性，但需评估其他模块同名字段影响面）。

### 7.3 当前数据现状

`select count(*) from crm_visit_plan` → **0**；`crm_visit_record` → **0**。本页当前呈现空态 `暂无拜访计划数据`（`:11`）。**验收前必须先造数据**（建议 ≥ 8 条，覆盖 `status 0/1/2/3` × 超期/未超期 × 多客户多负责人）。

## 10. 验收标准（目标）

> 本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下**不存在** `e2e-crm*.cjs`，已实测）。落地脚本命名 `tools/e2e-crm.cjs`（界面 + 接口 + 直连 DB 对账 + 写库后复原）。

### 10.1 接口验收（建议 ≥ 14 项）

① `GET /plan/page` 默认 200，`total` 与直查 DB（`deleted = 0` + 租户条件）一致；② `page`/`size` 生效（`size=1` → `records.length === 1`），`pageNum`/`pageSize` **同样生效**（后端双风格兼容）；③ `customerId`/`salesPersonId`/`status`/`planDateStart`/`planDateEnd` **五参数逐个生效**；④ `planDateStart`+`planDateEnd` 为**闭区间**（`ge`/`le`，`VisitPlanServiceImpl.java:35-40`）→ 边界日期应被包含；⑤ 排序为 `planDate DESC`（`:41`）；⑥ 不传 `planNo` → DB `plan_no` 形如 `VP-yyyyMMddNNNN` 且非空，`status` 落 `0`；⑦ **主动传** `planNo` → 后端**不覆盖**（`VisitController.java:48-50`）；⑧ 🔴 **撞号回归**：创建 → 删除该条 → 再创建，新号**不得与已有（含已逻辑删）行冲突**（当前预期 500，修复后断言成功且唯一）；⑨ `PUT /plan/{id}` 改名后回读一致，且**未传字段保持原值**（`NOT_NULL` 局部更新）；⑩ `cancel`：`status=0/1` → DB `3` 且返回 `true`；`status=2` → 返回 **`false` 且 DB 不变**；⑪ `DELETE` → DB `deleted=1`，列表与 `total` 不再出现；⑫ `GET /api/customer/dropdown` 只返回启用客户且 **≤ 200 条**；⑬ 无 token 访问本域端点 → 401（当前**无接口级鉴权注解**，须实测全局 Sa-Token 兜底）；⑭ **写库隔离**：写断言按原值**复原**或使用专用测试计划。

> 2026-09-18 更新：⑧ 撞号**已修**（`CrmDocNo.next` 取当日同前缀最大号 +1，取号 SQL 刻意不含 `deleted`）→ 断言改为「必成功且唯一」，可直接回归；③④⑤⑨⑩⑪⑭ 口径未变。

### 10.2 UI 验收（建议 ≥ 18 项）

① 菜单 `CRM → 外勤拜访 → 拜访规划`（`70001`）点开落在 `sales/visit-plan`，**无配对标签页**（`display_mode=0`、`tag_label=null`、`list_path=null`）；② 标题「拜访规划」，**无统计卡**；③ 查询区 4 项渲染（客户/负责人/状态 3 个 select **有可见 label**，计划日期区间**无可见 label** —— 当前行为，改版后同步改断言）；④ 表格 10 列，状态列显示**中文 tag**（待执行橙/执行中蓝/已完成绿/已取消红），非法值回退 `-` + 灰 tag；⑤ `planDate` 早于今天且 `status ∈ {0,1}` → **红字 `#ff4d4f`**，`status = 2/3` 同日期行**不红**；⑥ 客户下拉有值、支持中文过滤；负责人 label = `nickname || username`；⑦ 查询 4 项**逐个生效**（含只填 `planDateStart` 的**单边区间**）；⑧ 重置清空 4 项、日期控件视觉也清空、回第 1 页；⑨ 分页请求参数为 **`page`/`size`**；⑩ 导出 `拜访规划_*.csv`、UTF-8 BOM、**表头 9 列**（不含「操作」）、`status` 当前导出为**数字**（登记为已知行为或随修复改断言）；⑪ `新建计划` → 标题「新建拜访计划」→ 不填直接确定 → 四条必填文案**逐字**出现：`请选择客户`/`请选择负责人`/`请选择计划日期`/`请输入拜访目的`；⑫ 完整填写 → 确定 → 提示「拜访计划创建成功」→ 列表出现新行且**客户/负责人显示中文名称**（快照回填生效），**断言网络无 4xx**；⑬ 编辑 → 标题「编辑拜访计划」→ 7 个字段**逐字段回填正确** → 保存提示「拜访计划更新成功」；⑭ 「取消计划」在 `status ∈ {0,1}` 可见、`{2,3}` 不可见；确认框文案逐字为 `确认取消该拜访计划？`/ok `取消计划`/cancel `返回`；确认后状态列变「已取消」；⑮ 「删除」确认框逐字为 `确认删除该拜访计划？`/ok `删除`/cancel `取消`；确认后行消失；⑯ **端到端闭环**：本页建计划 → 执行页打卡关联 → 回本页该计划变「已完成」且**不再红字**；⑰ 页面控制台**无 error**（含 `ReferenceError` —— 参见《重构搬迁后必须做运行时验证》）；⑱ **断言网络无 4xx**。

> 2026-09-18 更新：③ 计划日期区间**已有可见 label**（查询区改横向网格）→ 改断言；⑩ 导出**已套 `STATUS_MAP` 中文**（`status` 不再导出数字）→ 改断言；另需扩充断言集：表头齿轮列配置、页面配置弹窗（4 查询 + 4 按钮）、经典分页栏、`createdAt` 列（默认隐藏）、「打印(F8)」。⑪⑭⑮ popconfirm 与校验文案未变。

## 12. 剩余缺口（不阻塞，如实登记）

1. **`plan_no` 撞号**（P0）—— 删除后重建必复现。
2. **`1 执行中` 是死状态** —— 需业务裁定「补动作」还是「删值域」，**本页最需要产品决策的一点**。

4. **无批量生成/批量派单**。
5. **拜访目的无字典**；**计划时间无结构**（自由文本）。
6. **无提醒/无通知** —— 超期只在列表红字。
7. **无数据权限、无权限码**。
8. **审计列失效**（`updated_at` 不刷新、`created_by`/`updated_by` 恒 NULL、`version` 无实际保护）。
9. **路线排程未复用配送模块能力** —— 建议复用，**不新建**。
10. **与跟进记录（`crm_customer_follow_up`）无联动** —— 建议拜访完成后同步写一条 `follow_up_type = 2 拜访`。
11. **菜单名实不符**（`sales:*` 挂在 CRM 下），收敛建议见 §1.2。
12. **外壳为路线 B**，整体未达金标准。
13. **客户/负责人下拉上限 200 且客户端过滤**。
14. **无模块级 E2E、无验收截图资产**。
