## 1. 页面概述

业绩提成中心是**提成结算工作台**（复合页：统计分析 + 结算操作）：同一份提成数据按六种视角呈现，其中 `配送员 / 每月提成` 为人员 × 12 个月的**年度矩阵**（带跨年切换），`提成构成 / 方案汇总提成` 为**方案维度的拆解与汇总**，`业绩概览 / 业绩明细` 为**业绩指标的汇总与单据级明细**。核心操作是工具栏的 **`批量结算`**，其前置硬约束由页面提示条明示：**「若存在某月份提成未结算，此后月份提成将不显示」** —— 结算必须按月份顺序连续推进。

|------|------|------|
| 业绩提成中心 | 分析 → 提成分析 → 业绩提成中心 | 单入口复合页（**6 个视图 Tab**，逐 Tab 独立列配置） |

单入口：分析 → 提成分析 → 业绩提成中心。

- 实测实据（2026-09-15）：**6 个 Tab 记录数全部为 0**（`snapshot.record` 均为 `共 0 条记录`），因此本页仅有**表头与查询区实据**，**无数据行实据**。
- 页内 Tab 栏实测（`.png`，深灰底色条）：`配送员`（激活）｜`每月提成`｜`提成构成`｜`方案汇总提成`｜`业绩概览`｜`业绩明细`。

  - `配送员 / 每月提成`：`刷新`、`提成方案`、**`批量结算`**、`打印(F8)`、`导出`；
  - `提成构成 / 方案汇总提成`：`刷新`、`提成方案`、`打印(F8)`、`导出`（**无批量结算**）；

### 口径说明

- **矩阵列 vs 配置列**：`配送员 / 每月提成 / 方案汇总提成 / 业绩概览 / 业绩明细` 五 Tab 的表头实据末尾均出现**拼接串**（如 `合计0000000000`），说明对标表头存在**合并单元格（分组表头）**；其中 `1月`~`12月`、`合计` 属**运行期生成的矩阵列 / 固定合计列**，不参与列配置 —— 这正是基准文档「14 列」与本表 `columnConfig`「2 列」差异的来源。
- **`业绩明细` 与 `业绩概览` 均为 21 列**（列池相同量级），但**默认可见数不同**（10 vs 15）：`业绩明细` 是**单据级明细**（司机/商品/单位/数量/金额/换算/毛利），默认只留最常用的 10 列；`业绩概览` 是**人员级汇总**（单量/里程/装箱/金额/毛利/点位），默认 15 列。两者共用同一批包装/重量/体积明细列的隐藏项。
- **`提成构成` 是 `方案汇总提成` 的「加人员维度」版**：前者多 `配送员 / 职务` 两列（7 = 5 + 2），其余 5 列完全同名同序 —— 构成 = 逐人 × 逐方案，汇总 = 逐方案。
- **`不显示为零数据项`**：`提成构成 / 方案汇总提成` 两 Tab 的勾选项，勾选后隐藏金额为 0 的项；旁边口径提示「列表仅显示已产生业绩数据的方案提成数据」说明**默认只显示已产生业绩的方案项**。

## 4. 业务规范

### 统计口径与数据关系

- **年度矩阵**：人员 × 12 个月，单元格为该月提成金额（`配送员` / `每月提成` 两 Tab）；年度可切 `去年 / 本年` 与具体年份（实测 `2026年`）。
- **结算顺序硬约束**：**「若存在某月份提成未结算，此后月份提成将不显示」**（页面提示条实据，逐字）。即提成必须**按月顺序结算**，未结算月份会**截断其后所有月份的显示**，保证核算连续性 —— 这是本页最核心的业务规则。
- **批量结算**：对选中范围批量执行结算，**结算后锁定**（基准文档口径，弹窗细节**待复核**）。
- **六视图分工**：

| 视图 | 粒度 | 作用 |
|---|---|---|
| `配送员` / `每月提成` | 人员 × 月份 | 年度矩阵总览（结算操作台） |
| `提成构成` | 人员 × 方案 | 单月/单期提成的方案项拆分 |
| `方案汇总提成` | 方案 | 按提成方案汇总提成金额 |
| `业绩概览` | 人员 | 配送业绩指标总览（单量/里程/装箱/体积/毛利/点位） |
| `业绩明细` | 人员 × 商品 | 单据级业绩明细（发货/退货/赠品/换算/毛利） |

- **人员角色维度**：`配送员角色`（默认 `全部`）为人员范围过滤；基准文档记「按人员角色（配送员/业务员等）切换提成口径，角色由提成方案覆盖范围决定」，其中**角色枚举与切换后查询项是否变化待复核**。
- **`业绩明细` 的日期口径**：`日期类型 = 指定配送日期`（实测），即按**配送日期**而非单据日期过滤；其他可选值**待复核**。

### 与其他页面关系

- **取数**：`业务员提成`（销售提成计算）、`回款统计`（回款侧口径）+ 配送计件/配送业绩（`业绩概览`/`业绩明细` 的配送指标）+ `提成方案` 规则。
- **下游**：提成结算 → 工资 / 费用发放（财务域）；批量结算回写结算状态。
- **状态机（本系统侧可确认）**：`erp_commission_record.status` = `DRAFT`（待确认）/ `CONFIRMED`（已确认）/**`PAID`（已结算）**/ `CANCELLED`（已取消）；「已结 = `PAID`，未结 = `DRAFT` + `CONFIRMED`」（`views/analytics/commission-center/index.vue:61-66`、`backend/.../mapper/CommissionRecordMapper.java:27-33`）。**对标侧的月份锁定语义本系统后端没有对应实现**。

### 业绩概览 / 业绩明细的行源（2026-09-18 二次修正）

> **修正原因**：两个视图原先分别以 `dms_task`（概览）/ `dms_task_item`（明细）为行源。配送域实行
> **「口径分流」**（见 `backend/dms/.../task/service/TaskService.java` 的「口径分流」注释）：
> ① 有来源上游单据（销售出库单等）的配送单，表头数量/金额/重量/体积一律由上游单据聚合，
> **商品明细不写 `dms_task_item`**，查看时穿透上游单据；② 只有**无来源单据的临时配送单**才保留本单商品明细。
> 实测 `dms_task_item` 的 `product_id` 全为 NULL，故「只读 `dms_task_item`」在主流场景**恒为空集** —— 不是缺列问题，是**数据源选错**。

**修正后的行源**（`dms_task → dms_task_doc → 上游单据明细`，按 `doc_type` 分派）：

| `dms_task_doc.doc_type` | 上游单据 | 明细表 | 取数列 |
|---|---|---|---|
| `1` | 销售出库单 | `erp_sale_outbound` → `erp_sale_outbound_item` | `outbound_quantity` / `line_amount` / `cost_price` / `gift` |
| `2` | 销售退货单 | `erp_sale_return_doc` → `erp_sale_return_doc_item` | `return_quantity` / `line_amount` / `ref_cost_price` / `is_gift` |
| `3` | 调拨单 | `erp_stock_transfer` → `erp_stock_transfer_item` | `quantity` / `line_amount` / `unit_cost` |

- **上游关联键**：优先 `doc_id`（上游主键），`doc_id` 为空时退回 `doc_no`（实测多数行 `doc_id` 为空、仅少数行有值，两条路都要留）。
- **`dms_task_item` 作兜底**：仅当该配送单**没有任何有效 `dms_task_doc`**（临时配送形态）时才使用，两条链路都能出数，不因分派写死而丢掉另一种任务形态。
- **上游单据不按 status 过滤**：配送单已妥投即证明货已发出，上游单据状态只反映其自身流程进度。
- **妥投过滤必须落在两条链路内部**（`t.status IN (5,6)`）—— 只写在最外层会把配送中/异常单据算进业绩。

### 剩余缺口与无源登记

| # | 项 | 处置 |
|---|---|---|
| 1 | `提成构成` 的「提成方案名称 / 提成类型 / 提成规则 / 方案描述」四列；`方案汇总提成` 的同名四列 | **无数据源**：已核实 `erp_commission_record` **全部列**，**无 `rule_id`（无任何指向 `erp_commission_rule` 的关联列）**，且全库**无提成记录生产者**（`erp_commission_record` 0 行）。列名与列位如实保留，取值返回 `null`（前端 `-`），**不填 0 冒充**。 |

| 4 | `业绩概览`「小/中/大包装」三列 | **已接线（2026-09-18）**：join `erp_product_unit.unit_type`（`SMALL`/`MEDIUM`/`LARGE`），口径 = Σ(数量 × 该档位换算率)；`UNIT_4` 兜底大包装、`unit_type` 为 NULL 且换算率 > 1 的「无名档位」兜底中包装、无 SMALL 时退回基本单位。**不新建包装表、不加冗余打包列**（库里 19 张明细表的 `small/mid/big_pack` 实测 0 行有值，是死列，勿复制该失败模式）。商品未维护档位 → 该列 `null`（未知），**不填 0**。 |

| 6 | `业绩明细`「换算关系 / 换算结果 / 小包装 / 中包装 / 大包装」 | **已接线（2026-09-18）**：由 `erp_product_unit.conversion_rate` **查询期现算、不落库**（换算率 < 1 的脏档位不参与拼接，实测 `LARGE` 存在换算率 1 的行）；换算关系形如 `1盒=12瓶`，换算结果 = 数量 × 该换算率。`小单位` 取 `erp_product.small_unit`，为空时退回 `erp_product_unit` 基本单位名。 |
| 7 | `业绩明细`「商品毛利」 | **已接线（2026-09-18）**：原实现是 `发货金额 − 数量 × COALESCE(erp_product.cost_price, 0)`，因 `dms_task_item.product_id` 全 NULL 导致成本恒算 0、**毛利虚高成「等于发货金额」**。现改为取上游明细自带 `cost_price/cost_amount`（兜底链路取 `erp_product.cost_price`），**分组内任一行成本未知 → 整列 `null`**（成本算少了会让毛利虚高）。 |
| 8 | `配送里程(km)` | 取 `dms_task.estimated_distance` 合计（**预估里程口径**；`dms_tracking` 只有原始点位、无距离列），已登记 |

| 10 | `业绩概览` 查询条件 | 对标 `head` 未捕获 → 本系统按 `配送员` / `角色` /（年度区间）提供，页面已标注 |

   - 包装/换算列要求该商品在 `erp_product_unit` 维护了 `SMALL/MEDIUM/LARGE` 档位，且上游单据明细行的 `product_id` 非空；
   - 退货/赠品列要求该行来自销售退货单或带 `gift` 标志的销售出库明细行（调拨、临时配送无此语义 → 如实 `null`）。
   - 实测 dev 库中已妥投配送单能连到的上游出库明细（`E2E-XSCKD-0001/0002`）`product_id` 为空，故包装类列当前仍显示 `-`；这是**源数据未维护**而非取数口径缺失，商品档案与上游单据补齐后即自动出数。
