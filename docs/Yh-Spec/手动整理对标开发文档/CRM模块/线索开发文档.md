## 1. 页面概述

线索（Lead）是 CRM 全生命周期的**入口实体**：尚未确认意向、尚未建档的机会点统一先落线索池，经跟进、评分、分配后**转化为客户**（并可继续创建商机）。

| 页面 | 地址 | 组件 | 说明 |
|------|------|------|------|
| 线索列表页 | `crm/lead/index` | `views/crm/lead/index.vue`（1290 行） | 线索台账：单列表视图 + 4 张统计卡 + **内嵌表单弹窗** |
| 线索表单页 | `crm/lead/form` | `views/crm/lead/form.vue`（90 行） | 新增/编辑线索（`BillFormPage` + `useBasicForm`） |

> **⚠️ 双入口方向提醒**：菜单主 `path` 指向**列表页**，标签 `添加` 指向**表单页** —— 与「报价单 / 发票」两页方向相反，勿照抄。

### 1.1 线索在本模块中的位置

```
线索(Lead, crm_customer_lead) ──convert──▶ CRM 客户(crm_customer) ──▶ 商机/报价/合同
        │                                          │
        └── 跟进记录(crm_customer_follow_up)        └── 商机(crm_customer_opportunity)
```

- 线索转客户由 `POST /api/crm/lead/{id}/convert` 完成（`CustomerLeadController.java:86-89`）。
- **不产出商机**：转化 Service 内**没有任何** `CustomerOpportunity` 的写入（`CustomerLeadServiceImpl.convertToCustomer`，全方法体 94-137 行）。
- CRM 客户 ≠ ERP 客户，红线见《客户开发文档》§1.1。

### 1.2 「线索」与「线索转化」两个菜单页的关系

| | 线索（本页，`80210`） | 线索转化（`70311`） |
|---|---|---|
| 定位 | 线索**台账维护**（增删改查 + 分配） | 线索**转化工作台**（筛选待转化线索 + 4 步转化向导） |
| 组件 | `views/crm/lead/index.vue` | `views/crm/lead-convert/index.vue` |
| 转化入口 | 行内「转化为客户」+ 简易确认弹窗 | 行内「转化」+ **4 步向导弹窗** |
| 详见 | 本文 | [线索转化开发文档](./线索转化开发文档.md) |

> **⚠️ 两页共用同一后端端点**（`/api/crm/lead/*`）与**同一实体**，但**字段名读取口径不同**：转化页读 `record.status`，本页也读 `record.status`，而后端实体字段是 `leadStatus` —— 两页都受影响，见 §9.2。

> **⚠️ 运行期缺陷一（P0，全模块共性）**：列 `formatter` 写成 **vxe 对象解构** `({ row })` / `({ cellValue })`，而 `BillTableList` 会把列交给 `BillDetailTable`（`BillTableList.vue:176-202`，`:view-mode="true"`），后者在查看态对**每一格**调用 `col.formatter(raw, record)`（**位置参数**，`components/BillFormPage/BillDetailTable/index.vue:1410-1430`）。语义实测（node 复现）：
> - `({ row }) => row.name || ''` 被以 `('北京某公司')` 调用 → **抛 `TypeError: Cannot read properties of undefined (reading 'name')`**；
> - `({ cellValue }) => …` 被调用时 `cellValue` 恒 `undefined` → **返回 `undefined`**，单元格空白。
>
> 后果：本页第 1/2/3 列（`name`/`companyName`/`phone`）在**有任何数据**时即抛错，错误会冒泡到 `ErrorBoundary`（`components/ErrorBoundary/ErrorBoundary.vue:132-169` 的 `onErrorCaptured`，`return false` 阻断向上传播）→ **整页切成「页面出现异常」错误态**；第 4/5 列（来源渠道、评分）静默空白。
> **devdb 实测 `crm_customer_lead` 现有 0 行**，所以该缺陷**从未在真机上暴露**。验收第 1 项应当是「造 1 条线索后打开列表页并断言无 error」，见 §10.2。
> 修法：改为位置参数，例如 `(raw: any, row: any) => row.name || ''`、`(raw: any) => sourceTextMap[raw] || raw`。

> **⚠️ 运行期缺陷二（P0）**：插槽列**必须**写 `type: 'slot'`。`BillDetailTable` 的分支顺序是 `type==='action'` → `type==='slot'` → `isViewMode` → 编辑态（`index.vue:160-231`），只写 `slotName` 不写 `type` 会落到 `getCellDisplayValue` 分支 → 插槽**永不渲染**。本页 `status` 列（:699）只写了 `slotName: 'statusCell'` → `#statusCell`（:367-371）实际不生效（同时 `record.status` 亦不存在，见 §3.4）。
> **⚠️ 运行期缺陷三（P0）**：操作列的插槽回退名是 `col.slotName || 'actionCell'`（`BillDetailTable/index.vue:197`），而本页 action 列未传 `slotName`（:701）、页面提供的是 `#action`（:284）→ 按当前组件实现**操作列取不到插槽**。金标准写法是 `{ key:'action', title:'操作', type:'action', slotName:'actionCell', … }` + `<template #actionCell="{ record, column }">`（参照 `views/mall/keyword-bank/index.vue:136,288`）。CRM 全模块（客户/合同/线索/线索转化/商机）均为 `field + #action` 老写法，**须一并对齐**。

**目标规格（全量列，按 `crm_customer_lead` 32 列 + 业界 CRM 通用列整理；★ 为本系统已具备数据源但未上列的列）**：

### 5.2 编码规则

- **后端生成**：`POST /api/crm/lead` 时由 `generateLeadCode()` 生成（`CustomerLeadController.java:50`），格式 **`LEAD-yyyyMMdd` + 4 位序号**（`CustomerLeadServiceImpl.java:140-144`）。

- **唯一约束**：`uk_crm_lead_code`（`V9.11.0:97`）。

> **⚠️ 缺陷（P1）**：① 逻辑删的行仍占唯一索引（逻辑删只置 `deleted=1`，`CustomerLead.java:79-80`），而 `selectCount` 受 `@TableLogic` 影响不计删除行 → **删一条就会让下一条新线索撞码**；② 并发新增会取到同一序号（无号段/无重试）。
> **目标规格**：统一走**号段服务（`next-no` 体系）**，规则形如 `XSOL + yyyyMM + 4 位序号`，租户内唯一、并发安全；同时把 `uk_crm_lead_code` 的冲突转为友好提示而不是 500。

## 7. 数据模型（`crm_customer_lead`，**32 列**）

**建表来源**：`backend/core/api/core-api/src/main/resources/db/migration/V9.11.0__Create_CRM_Core_Tables.sql:63-96`（唯一一处定义，全仓无后续 `ALTER`）；devdb `information_schema` 实测 **32 列，与 DDL 完全一致**（2026-09-18）。

```
industry_type, lead_source, lead_status, lead_status_desc, lead_level, estimated_amount,
province, city, address, requirement, remark,
sales_person_id, sales_person_name, department_id, department_name,
expected_close_date, actual_close_date,
converted_customer_id, converted_time,
created_by, created_at, updated_by, updated_at, deleted, version
```

| 约束 / 索引 | 内容 | 位置 |
|-------------|------|------|
| 主键 | `id BIGSERIAL PRIMARY KEY` | :64 |
| **非空列** | `lead_code`（:65）、**`lead_name`**（:66）、`deleted`（:93）、`version`（:94） | — |
| 默认值 | `lead_status DEFAULT 0`（:71）、`estimated_amount DEFAULT 0`（:75）、`created_at/updated_at DEFAULT CURRENT_TIMESTAMP`（:86、:88） | — |
| 唯一索引 | `uk_crm_lead_code(lead_code)` | :97 |
| 普通索引 | `idx_crm_lead_sales(sales_person_id)`、`idx_crm_lead_converted(converted_customer_id)` | :98-99 |

> **⚠️ 无 `tenant_id` 列（P0 级风险，需真机探针确认）**：同文件其他 CRM 表（`crm_customer_pool` :178、`crm_contract` :219、`crm_quotation` :466 等）**都有** `tenant_id`，**唯独 `crm_customer` / `crm_customer_lead` / `crm_customer_opportunity` / `crm_customer_follow_up` 四张早期表没有**（devdb 实测：`crm_customer` 53 列**含** `tenant_id`（后续迁移补的），`crm_customer_lead` 32 列 / `crm_customer_opportunity` 33 列 / `crm_customer_follow_up` 29 列**均不含**）。
> 而多租户拦截器的 `ignoreTable` 只跳过固定白名单 + 「表名无下划线」的表（`core-base/.../MyBatisPlusConfig.java:32-66、137-141`），**这四张表都不在白名单里**；登录态下租户可解析 → 拦截器会注入 `AND tenant_id = ?`。同型先例已实证会造成 500：`shop_template` 因无该列被注入 → `/template/list`、`/template/library` 双双 500（`MyBatisPlusConfig.java:60-65` 注释记载）。
> **结论**：按同型先例推断，登录态下本页 `/page`、`/{id}`、`/convert` 等**读路径预期报「字段 tenant_id 不存在」→ 500**；而 devdb 中 `crm_customer_lead` 现有 **0 行**、全模块**从未跑过端到端验收**（README §3.2-7），该问题一直未被触发/发现。
> **处置（二选一，先做探针再定）**：① 出迁移补 `tenant_id BIGINT`（**无 DEFAULT 新增**，并按需回填现有行）→ 真正租户隔离；② 把这四张表加入 `IGNORE_TENANT_TABLES`（语义 = 平台级共享，与 CRM 业务语义不符，**不推荐**）。验收第 1 项必须先用一条 `GET /api/crm/lead/page` 探针确认实际状态，再决定改哪边（见 §10.1）。

> **⚠️ 表缺列（与前端强相关）**：前端列表/表单使用的 `score`（评分）、`mobile`（手机号码）、`phone`、`email`、`source` **在表中均无对应列**（32 列已逐列核对）。其中 `score` 对应「高分线索」卡片与 slider 录入，属**功能级缺失**；`mobile/phone/email/source` 属字段名映射问题（应分别落到 `contact_phone` / `contact_email` / `lead_source`）。

## 10. 验收标准（目标）

> 本模块**尚无 E2E**（`tools/` 下无 `e2e-crm*.cjs`）。落地脚本命名 `tools/e2e-crm.cjs`：接口 + 直连 DB 对账 + 写后复原 + UI 断言 + 控制台无 error。

### 10.1 接口验收（线索部分 ≥ 12 项）

1. **先跑探针**：`GET /api/crm/lead/page`（登录态）返回 200 —— 若报「字段 tenant_id 不存在」则先按 §7 处置租户列/白名单，**该探针是本页第一优先项**。
   > 2026-09-18 更新：`tenant_id` 已由 `V11.379.0` 补列，登录态探针预期直接 200。
2. `GET /page` 默认查询 `total` 与直查 `select count(*) from crm_customer_lead where deleted=0` 一致。
3. `pageNum/pageSize` 生效；`pageSize=1` 时 `records.length === 1`。
4. `keyword` 命中 `lead_name` / `company_name` / `contact_name` 三列（各造 1 条验证）。
5. `leadStatus` / `leadLevel` / `salesPersonId` 三个过滤参数逐个生效。
6. `POST /api/crm/lead` 用**实体字段名**（`leadName/companyName/contactPhone/contactEmail/leadSource/leadStatus/leadLevel/estimatedAmount`）创建成功，返回 `leadCode` 非空且形如 `LEAD-YYYYMMDDNNNN`；DB 可查回。
7. `PUT /{id}` 改 `leadName` 后三级回读（DB / 详情 / 列表）一致。
8. `DELETE /{id}` 后列表不出现（`deleted=1`）；`DELETE /batch` 批量删。
9. `GET /export` 条数与 `page` 的 `total` 一致。
10. `GET /code/{leadCode}` 命中；`GET /salesPerson/{id}` 命中。
11. `POST /{id}/convert`：生成 `crm_customer` 行、`customer_name = 线索公司名`、`crm_customer_lead.lead_status/ converted_customer_id / converted_time / actual_close_date` 被回写；**再次调用返回 400「线索已转化」**（幂等断言）。
12. `POST /batch-convert`（补齐后）：混合入参（1 条未转化 + 1 条已转化）→ 断言未转化的成功、已转化的被跳过且**不产生第二条客户**。
   > 2026-09-18 更新：端点已补齐（逐条独立事务、返回 `successCount/failCount/failures`），本项可直接执行。
13. 写入端点回归后**删除自产数据**（脚本自带清理）。

### 10.2 UI 验收（≥ 15 项）

1. 菜单 `CRM → 线索管理 → 线索` 落在**列表页**；标签 `添加` 跳到**表单页**（双入口方向校验）。
2. **造 1 条线索后打开列表页**：断言控制台**无 error**、未出现 `ErrorBoundary` 的「页面出现异常」态（对应 §9.2 P0 formatter 缺陷）。
   > 2026-09-18 更新：formatter 签名与插槽均已修复（见 §9.0），本项由「缺陷复现」转为常规回归断言。
3. 8 列渲染，公司/联系人列显示 `公司 / 联系人`，来源渠道列显示中文标签（不是 `website`）。
4. 状态列显示中文标签（不是空白、不是「未知」）。
5. 行操作按钮**可见且可点**（对应 §9.2 P0 插槽缺陷）；`转化为客户` 对未转化行可见、对已转化行不可见。
6. 4 张统计卡数值 = 当前页聚合（或改服务端口径后 = 全量）。
7. 筛选面板：线索名称 / 来源渠道 / 状态**逐个生效**（造数验证，含负例）。
8. 搜索框关键字生效。
9. 表头齿轮可改列显隐/顺序，**刷新后个人配置保留**（需先补 `storage-key`）。
   > 2026-09-18 更新：`storage-key` / `global-config-key` 已接线（`crm-lead-table-columns`）。
10. `Ctrl+N` 打开新增表单；`F5` 刷新；`Esc`/关闭时脏数据二次确认。
11. 新增（填线索名称+公司名称）→ 保存 → 列表出现新行，**断言网络无 4xx/5xx**（对应 §9.2 P0 字段映射缺陷）。
12. 编辑「线索名称」→ 保存 → 列表名称变更生效。
13. 删除 → 确认 → 行消失；批量删除按钮点击有响应。
   > 2026-09-18 更新：批量删除入口已随改造移除（原按钮本就无监听），本断言改为「页面不提供批量删除」。
14. 导入线索：能选 CSV、能映射字段、导入后可查回（补齐后）。
   > 2026-09-18 更新：仍未闭环 —— 后端暂无线索导入端点，页面点击后为如实缺口提示，本项保持待办。
15. 批量分配：选择 2 行 → 分配 → 断言网络请求发出且 `sales_person_id` 落库。
16. 分配候选人为**真实人员列表**，不含硬编码「张三/李四/王五」。

## 12. 剩余缺口（不阻塞，如实登记）

1. **租户列缺失未闭环**（`crm_customer_lead` 等四张表无 `tenant_id`）—— 需真机探针后再定"补列"或"白名单"，**这是本页能否打开的前提**。
2. **线索评分无落库列** —— 前端有 slider 与「高分线索」卡片，数据库无 `score` 列。
3. **线索池 / 分配规则 / 自动回收未实现** —— 后端无线索池表（客户域已有 `crm_customer_pool` 10 端点在前端不可达，线索域则连表都没有）。
4. **转化不创建商机** —— 转化向导 Step2 的勾选项无后端支撑（见《线索转化开发文档》）。
5. **7 处桩按钮未接线**（导入、批量分配、分配确认、批量转化、查看详情、添加跟进、跟进记录）。
6. **权限码未落库** 与 **`crm_customer_lead` 无导入端点**。
7. **无模块级 E2E、无验收截图**；`crm_customer_lead` 表当前 **0 行**，任何"已验证"的说法都缺运行时证据。
8. **遗留冗余**：`handleDelete` / `getScoreColor` / `getAvatarColor` / `sourceColorMap` / `handleRefresh` 死代码；`Lead` 接口同时声明两套字段名（`name`/`leadName`、`phone`/`contactPhone`、`status`/`leadStatus`，`api/crm.ts:10-39`）掩盖了 §9.2 的字段错配。
