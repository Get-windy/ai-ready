# AI-Ready 项目架构治理集成方案

## 背景

基于 **2026-05-05 紧急制动教训**，项目中发现严重的架构方向错误和目录结构混乱问题：

1. **目录结构混乱**：
   - `backend\erp\erp-purchase` 模块存在
   - `backend\infrastructure\deploy\erp-modules\erp-purchase-exchange` 模块也存在
   - 多个位置存在重复/冲突的ERP模块目录

2. **架构方向不统一**：
   - 缺乏清晰的模块边界和职责划分
   - 目录结构显示混乱的模块组织结构
   - 缺乏统一的技术规范和开发标准

3. **任务与架构不匹配**：
   - 多个agent正在执行P0核心功能开发任务
   - 但底层目录结构混乱，存在重复开发风险
   - 缺乏统一的模块设计和代码组织

## 问题根源分析

### 核心问题
**缺乏自动化流程约束导致架构问题在开发过程中不断积累**

### 反思日志要点
1. **缺乏架构治理**：项目启动时没有建立清晰的架构规范
2. **模块设计混乱**：ERP模块分散在多个目录，缺乏统一管理
3. **开发标准缺失**：没有强制执行统一的技术标准和目录结构
4. **监督不足**：coordinator未能及时发现架构问题

## 解决方案：CI/CD流水线架构治理集成

### 目标
在CI/CD流水线中集成架构治理检查机制，确保所有代码提交、构建和部署过程都自动执行架构合规性检查，从流程上保障架构规范的落地执行。

### 实施架构

```
ERP CI/CD流水线（增强版）
├── 阶段1: 架构治理检查
│   ├── 目录结构合规性检查
│   ├── 模块边界检查
│   ├── 依赖关系检查
│   └── 架构规范检查
├── 阶段2: 代码质量检查
├── 阶段3: 构建和推送镜像
├── 阶段4: 安全扫描
├── 阶段5: 部署前架构治理门禁
└── 阶段6: 多环境部署
    ├── 开发环境
    ├── 测试环境
    ├── 预发环境
    └── 生产环境
```

### 关键组件

#### 1. 架构治理检查脚本
**文件路径**: `.github/workflows/architectural-governance-check.sh`

**检查项目**:
1. **目录结构合规性检查**
   - 检查重复的ERP模块目录
   - 检查模块命名规范
   - 检查目录深度合规性

2. **模块边界检查**
   - 检查跨模块的Java包引用
   - 检查循环依赖风险
   - 检查模块职责单一性

3. **依赖关系检查**
   - 检查pom.xml中的依赖版本一致性
   - 检查循环依赖
   - 检查依赖兼容性

4. **架构规范检查**
   - 检查API路径规范（必须以 `/api/erp/` 开头）
   - 检查包命名规范（必须使用 `cn.aiedge.erp.{module}`）
   - 检查DTO/Entity/VO命名规范

#### 2. CI/CD流水线集成
**主流水线**: `.github/workflows/erp-ci-cd-pipeline.yml`

**新增的关键Job**:
1. **architecture-governance-check**（架构治理检查）
   - 位置：代码质量检查之前
   - 作用：防止不符合架构规范的代码进入构建流程
   - 失败处理：流水线立即停止，开发者必须修复架构问题

2. **architecture-deployment-gate**（部署前架构治理门禁）
   - 位置：所有部署阶段之前
   - 作用：确保部署的代码已经通过所有架构检查
   - 依赖：需要架构治理检查和安全扫描都通过

#### 3. 独立架构治理工作流
**文件路径**: `.github/workflows/architecture-governance-integration.yml`

**功能**:
- 提供独立的架构治理检查工作流
- 生成架构健康报告
- 提供架构治理门禁机制
- 支持团队协作和可视化

### 实施效果

#### 1. 预防架构问题积累
- **早期发现**：在代码提交阶段就发现架构问题
- **自动化检查**：减少人工审查的工作量和主观性
- **标准化约束**：强制执行统一的架构规范

#### 2. 提升开发效率
- **减少重构成本**：避免后期大规模重构
- **清晰指导**：为开发者提供明确的架构指导
- **持续改进**：通过自动化检查持续提升架构质量

#### 3. 保障架构稳定性
- **门禁机制**：防止不符合架构规范的代码进入生产环境
- **健康报告**：提供可视化的架构健康状况
- **趋势分析**：追踪架构质量的演变趋势

### 检查规则详细说明

#### 目录结构检查规则
```bash
# 规则1：禁止重复的ERP模块目录
❌ backend/erp/erp-purchase/
❌ backend/infrastructure/deploy/erp-modules/erp-purchase-exchange/
✅ backend/erp-modules/purchase/

# 规则2：统一的目录深度
❌ backend/erp/purchase/domain/repository/impl/
✅ backend/erp-modules/purchase/domain/

# 规则3：一致的命名规范
❌ backend/purchase-module/
✅ backend/erp-modules/purchase/
```

#### 模块边界检查规则
```java
// 规则1：禁止过度的跨模块依赖
❌ erp-purchase模块 import erp-sales模块的内部实现类
✅ erp-purchase模块 import erp-sales模块的API接口

// 规则2：禁止循环依赖
❌ erp-purchase → erp-sales → erp-purchase
✅ erp-purchase → common-utils ← erp-sales
```

#### 架构规范检查规则
```java
// 规则1：API路径规范
❌ @GetMapping("/purchase/orders")
✅ @GetMapping("/api/erp/purchase/orders")

// 规则2：包命名规范
❌ package com.aiedge.purchase;
✅ package cn.aiedge.erp.purchase;

// 规则3：类命名规范
❌ class OrderData
✅ class OrderDTO 或 OrderEntity
```
