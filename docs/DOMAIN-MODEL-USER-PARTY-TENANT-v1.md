# 用户 / 往来单位 / 租户 — 领域模型设计（v1）

> **状态**：讨论稿 v1（2026-09-22）。文中 ✅ = 已认同；带「**建议**」= 我给的倾向但尚未拍板；
> 带「**待定**」= 需要你给答案才能动手。
> **范围**：`自然人` / `往来单位` / `租户` 三个主体的建模，它们之间的四条关系边，
> 以及由此派生的「跨租户单据协同」。
> **不含**：接口清单、前端改造、税务/清算口径、权限码体系（那是 E-01 那条线）。

## 一、要解决的真实场景（需求源头，逐条可验）

| # | 场景 | 它压出来的模型约束 |
|---|---|---|
| **S1** | A 是往来单位 **B、C** 的员工；在**租户 E** 处分别为 B、C 下单 | 一人可属多单位；同一家店可代不同主体 |
| **S2** | A 在**租户 F** 处为**自己**下单 | 自然人可作"个人主体"，不代表任何单位 |
| **S3** | A 在**租户 F** 处为 **C** 下单 | 能代谁 ≠ 该单位在这家店是客户 |
| **S4** | 单位 **B 自己也是租户**，吸引客户 C 到自己店里下单 | "单位"与"租户"是两条可并存的边，不是一种东西 |
| **S5** | 客户 **C 在 E 下单后觉得好，自助申请开店**成为租户 | 开店主体是**单位**；走申请-审批；"客户"与"租户"可叠加 |
| **S6** | 租户 **B 与 F 互为客户与供应商**（B 卖鸡米花给 F、F 卖面包给 B） | 关系是**双向**的、角色**可并存**；**方向由单据决定** |
| **S7** | **代销/一件代发**：F 自己没有大豆油，与 B 协商**把 B 的货挂在自己店里卖**；客户在 F 店下单后**订单穿透到 B**，由 **B 实际交付**，F 赚**佣金或差价** | **销售方 ≠ 履约方**；商品可**跨租户挂载**；需要**分账/佣金结算**；货权在卖出前属供货方 |
| **S8** | **厂家推单给经销商**：客户 A 向厂家 G 下单，G 在山东、A 在甘肃，**租户 F 是 G 的经销商且手上有货** ⇒ G 把订单**推送**到 F，由 F 完成最终交付 | 与 S7 **同构、方向相反**；还隐含**区域授权/就近履约**（为什么是 F） |
| **S9** | **经销中转**：客户下单给 F ⇒ **F 向 B 下采购单** ⇒ **B 向 F 供货** ⇒ **F 向客户供货** | **交易链与 S7 完全相同**（客户→F、F→B），差别只在**货要经过 F** ⇒ 需要"**履约路径**"这一独立维度，且**两段运输**、**货权中途转移** |

> 这六条里没有一条是"特例"。它们共同指向同一件事：
> **自然人、往来单位是"系统级主体"，租户是"做生意的场所"，主体之间/主体与场所之间全是"关系"。**

## 二、现状与病根（都有实测证据）

### 2.1 三个主体的现状

| 主体 | 本仓现状 | 病 |
|---|---|---|
| **自然人**（谁在操作） | `sys_user`（员工，**带 `tenant_id`**）· `shop_user`（商城顾客）· `hr_employee`（0 行，`tenant_id` + `user_id`） | 同一个真人在系统里有 **2~3 个互不认识的账号** |
| **往来单位**（替谁做事 / 谁和我做生意） | `biz_party`（**152 行，带 `tenant_id`**） | 被切成"**每个租户一份**"：同一真单位在 E、F 是两条互不相识的记录 |
| **租户**（在哪做生意） | `sys_tenant` | 与往来单位**没有任何关联** ⇒ S4「B 自己也是租户」无处表达 |

### 2.2 四条"混在一起"的证据（不是推测）

| 证据 | 说明 |
|---|---|
| `biz_party.tenant_id` | 把"关系"压成了"**归属**"。同一单位无法跨租户识别，S6「互为买卖」更无从建立 |
| `biz_party.party_level = 'MEMBER'` + `member_card_no` / `points` / `member_level` / `member_name` | **个人会员被当成了一条往来单位** —— 自然人混进了单位表 |

## 三、目标模型

### 3.1 三个主体

| 主体 | 目标 | 是否租户内数据 |
|---|---|---|
| **自然人** `person` | 真人身份 + 登录凭据（唯一身份） | ❌ 系统级 |
| **往来单位** `party` | 业务主体（公司/个体户/个人会员） | ❌ 系统级 |
| **租户** `tenant` | 做生意的场所（一套独立的数据空间） | — 它自己就是边界 |

### 3.2 四条边 + 一个维度

| 边 | 含义 | 现状 | 目标 |
|---|---|---|---|
| **R1** 自然人 × 往来单位 | 任职 / 可代表（员工、法人、采购、财务…），**多对多 + 审批 + 角色集合** | `shop_user_party_link` | 升级为通用 `person_party` |
| **R2** 往来单位 × 租户 | **双向贸易关系**：这个主体在我店里是客户 / 供应商（**角色可并存**）+ 等级/信用/账期 | 被 `biz_party.tenant_id` 压成归属 | 拆成 `party_tenant` |
| **R3** 自然人 × 租户 | 这个人在**这家店**注册过（+ 审核） | `shop_user_tenant`（V11.484.0） | 保留，语义正确 |
| **R4** 租户 × 往来单位 | 这家店属于哪个主体（**可自助申请**产生） | ❌ 不存在 | 新建 `tenant_owner` |
| **维度** | 单据上的「**代谁**」= `acting_party_id`（空 = 个人自购） | ❌ 无 | 单据加列 |

### 3.2a 自然人 vs 企业：**注册与开店口径的不对称**（2026-09-22 用户裁定）

> **用户原话**：「**1 个自然人可以注册多个账号，不需要审批，私人事务不干预。**
> **企业（租户）理论上只允许有 1 个，注册多个需要所有人（法人同意）同时平台审核，避免越权违法。**」

这条的不对称**不是随意定的，而是对应现实法律的两套逻辑**：

| | **自然人** | **企业（租户 / 开店主体）** |
|---|---|---|
| 能否多个 | ✅ **可注册多个账号** | ⚠️ **原则上只允许 1 家店**（同一统一社会信用代码） |
| 是否要审批 | ❌ **不需要**，私人事务**平台不干预** | ✅ **要**：**法人（所有人）同意 + 平台审核** |
| 为什么 | **私人事务，风险自担**；平台没有正当理由干预 | **涉及公司主体与第三人利益，存在越权违法风险**（非授权人拿公司执照开店） |
| 唯一的硬约束 | **合并**需核验 + 同意（㊹，且不强制） | **开户/开分店**需**法人授权**（本条） |

**落地要点**：

| # | 要求 | 说明 |
|---|---|---|
| 1 | **`person` 不设身份证唯一约束** | 多账号**是合法状态**，不是脏数据；**不做任何自动关联/自动去重** |
| 2 | **同名同证只作"疑似"标记，不作判定** | 仅在**发起合并**时作为**核验依据**（㊹：核验 + 双方同意，不强制） |
| 3 | **`tenant_owner` 按统一社会信用代码去重**：同一执照默认**只能对应 1 个租户** | 与 ⑥「一店一照」一致 |
| 4 | **开第 2 家店的双重前置**：**法人（或经授权的代表）同意** + **平台审核** | 二者缺一不可；授权凭证与审核记录**必须留痕**（举证用） |
| 5 | **目的写清楚：防越权违法** | 不是"防多开赚钱"，而是**防止无授权者以公司名义开店** —— 这决定审核看的是"授权链"而不是"数量" |

> ⚠️ 注意与 ㊹ 的**层次区别**：**租户内的客户档案**重复了，由**租户自己合并**（不涉他租户利益）；
> **平台上的开店主体**重复了，必须**法人与平台**共同把关（涉及公司主体与第三人）。
> 两者都叫"重复"，但**风险性质完全不同**，不要用同一套规则处理。

### 3.2b 主体在交易中的「角色」：**逐笔确定，不是身份属性**（2026-09-22 用户裁定）

> **用户原话**：「现在客户通过**租户商城**成交，交易是发生在**租户和其客户之间**，**平台只是提供了交易场所**。
> 以后客户通过**平台自己自营的平台级商城**成交以后，**平台给客户开票，租户给平台开票**！
> **物流是租户或者平台委托的第三方服务**，是为了帮助租户或者平台达成交易的**第三方服务单位**。」

**同一家店、同一个平台，在不同交易里扮演的角色不同** ⇒ 角色必须**逐笔**记，不能挂在主体档案上：

| 角色 | 含义 | 谁在扮演（例） | 是否交易当事人 |
|---|---|---|---|
| **卖方** SELLER | 承担销售合同、开票、收款责任的**当事人** | 租户商城里 = 租户；平台自营里 = **平台** | ✅ 是 |
| **买方** BUYER | 承担付款、收货责任的**当事人** | 客户；平台自营里平台向租户采购时 = **平台** | ✅ 是 |
| **交易场所/平台服务方** PLATFORM | **只提供交易场所与技术服务的平台经营者** | 租户商城里的平台 | ❌ **不是当事人** |
| **辅助服务方** SERVICE | 帮某一方达成交易的第三方（物流、快递、安装、维修、检测…） | 第三方物流公司（本身也是"往来单位"） | ❌ 不是当事人 |

**两条关键结论**：

**① 平台在两种场景下的法律身份完全不同，不能混**：

| | 租户商城成交 | 平台自营商城成交 |
|---|---|---|
| 交易发生在 | **租户 ↔ 客户** | **平台 ↔ 客户**（+ 平台 ↔ 租户的采购） |
| 平台身份 | **场所/服务提供者**（电子商务平台经营者） | **交易当事人（卖方）** |
| 合同/发票/资金 | 全在"租户 ↔ 客户"之间，**平台不在三流里** | 平台在"平台↔客户"的三流里；租户在"租户↔平台"的三流里 |
| 平台怎么赚钱 | **场所与技术服务费**（订阅/抽成/增值，§3.4.4e）—— **不是差价** | **进销差价**（+ 可能的通道费） |
| 平台的责任 | **法定的治理义务**（入驻审核、纠纷处理、特定情形先行赔付）—— 电商法对"平台经营者"的要求，**不是合同义务** | 交易当事人的**合同义务**（质量、交付、售后） |

> ⇒ 这解释了为什么 §3.4.4e 的"平台收入"与 §3.4.4c 的"佣金/分账"是**两套账**：
> **前者是场所方收服务费（平台不在交易里），后者是当事人之间的分账（平台在交易里）。**

**② 物流要区分三个不同的东西**（这是"货损找谁赔"的判据）：

| 概念 | 含义 | 例 |
|---|---|---|
| **发货方** `ship_from` | 货从**谁的仓/店**发出 | 租户仓 / 平台仓 / 供货方 B 的仓 |
| **承运方** `carrier` | 实际运输的**第三方服务单位** | 顺丰、某区域物流商（本身是往来单位） |
| **委托方** `consignor` | **谁与承运方签运输合同** | 租户委托 / 平台委托 —— **决定在途货损赔谁** |

⇒ 补上了 §7.5 **T2-3** 的建模缺口：**运费由谁承担**看协议条款（已定），
**货损找谁赔**看**运输合同的委托方**（本条新增）—— 两者是不同的问题。

```sql
-- 交易参与方与角色（逐笔）
trade_party_role(
  id BIGINT PK,
  doc_type VARCHAR(32), doc_id BIGINT,      -- 哪张单据（订单/供货单…）
  participant_kind VARCHAR(16),             -- TENANT 租户 / PARTY 往来单位 / PLATFORM 平台
  participant_id BIGINT,
  role VARCHAR(24) NOT NULL,                -- SELLER / BUYER / PLATFORM / CARRIER / INSTALLER / …
  consignor_kind VARCHAR(16),               -- 仅辅助服务方用：谁委托的（决定责任相对方）
  consignor_id BIGINT,
  responsibility_note VARCHAR(255),
  UNIQUE (doc_type, doc_id, participant_kind, participant_id, role) WHERE deleted = 0
)
```

### 3.2c 「第三方服务」是**一类主体**，不是物流一种（2026-09-22 用户裁定）

> **用户原话**：「我们只是举了**物流**这一特殊的第三方，**以后还有安装、检测、培训等很多的第三方**，
> 他们只是**提供了服务**，**没有提供商品交换**罢了。」

⇒ 模型里的"辅助服务方"必须泛化成**可扩展的一类**，**绝不能把物流写死在表结构或代码分支里**。

**常见服务类型（示例，不是穷举 —— 由平台配置）**：
物流 / 安装 / 检测 / 培训 / 维修 / 保养 / 巡检 / 租赁 / 设计 / 咨询 / 计量校准 …

**"服务方"在系统里的身份**：**本身就是一个主体**——可以是**租户**（专业服务商），
也可以是**往来单位**（含个人师傅）。**通过"角色"参与交易，而不是靠新的主体类型。**

#### 3.2c-1 商品 vs 服务：**两类交付物，不能共用一套单据语义**

| 维度 | **商品** | **服务** |
|---|---|---|
| 交付物 | 实体货品 | 服务行为 / 结果 |
| 库存 | 有（数量、批次、库位） | **无库存**！有的是 **产能 / 排期 / 服务人员与资质** |
| 履约动作 | 发货 → 运输 → **签收** | 派单 → 上门/在线 → **完成确认 / 验收** |
| 逆向 | 退货 / 退款 | **不可"退"**，但有 **返工 / 重做 / 减免** |
| 质量责任 | 三包、质量问题 | **服务质量**（安装损坏、检测误判、培训无效…） |
| 计费 | 数量 × 单价 | **按次 / 按量 / 按期 / 按里程 / 按工时**（更多样） |
| 准入资质 | 类目资质（食品、药品…） | **服务资质**（安装资质、检测 CMA/CNAS、办学许可…） |
| 发票 | **货物类**发票 | **服务类**发票（**税率与类目不同**） |

⇒ 所以**服务单**与**商品单据**要分开建模（可挂在同一笔交易下）：

```sql
-- 服务类型字典（**平台可扩展**，物流只是其中一条；不写死在代码里）
service_type(
  code VARCHAR(32), name VARCHAR(64),
  billing_base VARCHAR(24),        -- PER_TASK 按次 / PER_QTY 按量 / PER_PERIOD 按期 /
                                   -- PER_MILEAGE 按里程 / PER_HOUR 按工时
  qualification_required BOOLEAN,  -- 是否需要资质（要则须先审核通过）
  default_liability VARCHAR(64),   -- 默认责任口径（真值仍以协议条款为准）
  status INT, ...
)

-- 服务单（与商品行并列的"交付物"）
service_order(
  id BIGINT PK, doc_type VARCHAR(32), doc_id BIGINT,   -- 挂在哪笔交易下
  service_type_code VARCHAR(32),
  provider_kind VARCHAR(16), provider_id BIGINT,       -- 服务方：TENANT / PARTY（含个人）
  consignor_kind VARCHAR(16), consignor_id BIGINT,     -- **谁委托的**（责任相对方，同 §3.2b）
  payer_kind VARCHAR(16),    payer_id BIGINT,          -- **谁付服务费**（委托方/买方/平台，三方都可能）
  billing_base VARCHAR(24), base_qty NUMERIC(18,4), unit_price NUMERIC(18,2), amount NUMERIC(18,2),
  -- 服务没有"收货"，只有"完成确认"
  status VARCHAR(16),                                  -- 待派单 / 服务中 / 待验收 / 已完成 / 返工中
  accept_by BIGINT, accept_time TIMESTAMP, accept_evidence VARCHAR(255),  -- 验收留痕（举证用）
  ...
)
```

**三条与商品共通的规则仍然适用**（不必为服务另造机制）：
① **责任划分进协议**（⑳/㉖）—— 服务质量谁赔、返工谁出钱，都是条款；
② **委托方决定责任相对方**（§3.2b）—— 安装损坏找谁，看是谁委托的安装；
③ **单方承诺不可传递**（第四条原则）—— 平台对客户承诺"包安装"，不等于服务商免费做。

**⚠️ 对 §7.5 缺口清单的修正**：**T3 里"服务类交易"不能算"可延后"** ——
用户的"以后还有很多第三方"意味着**现在的表结构就不能把物流写死**；
"服务单"的**完整实现**可以延后，但**模型留位（service_type + service_order + 角色字典）现在就要做**。

### 3.3 唯一一条授权推导规则

> **一个人在某租户能代表哪个主体 =（他所属的主体 R1）∩（该租户的客户 R2）**
> 个人自购不受此约束（自然人本身就是主体）。

六个场景逐条验证：

| 场景 | 推导 | 结果 |
|---|---|---|
| S1 A 在 E 为 B / 为 C 下单 | A∈{B,C}；E 的客户含 {B,C} | ✅ 两者皆可 |
| S2 A 在 F 为自己下单 | 个人身份不经 R1/R2 | ✅ |
| S3 A 在 F 为 C 下单 | A∈{B,C}；F 的客户含 C（不含 B） | ✅ 只能选 C，**选不到 B** |
| S4 C 在 B 的店里下单 | B 是租户 ⇒ 它有自己的 R2（客户 C） | ✅ |
| S5 C 申请开店 | 走 R4 的"自助申请"分支 | ✅ 见 3.5 |
| S6 B 卖鸡米花给 F | 单据 `seller=P_B, buyer=P_F`；两侧各有一条 R2，角色集合都含 {客户, 供应商} | ✅ |

#### 3.4.2b 为什么「贸易档案」必须分方向（2026-09-22 用户裁定，本节优先级高于其它细节）

> **用户原话**：「**f 给客户 30 天账期，b 只给 f 了 10 天账期还是要求现结，这个是 2 个不同维度的问题，
> f 给客户的承诺不能变成 b 给 f 的承诺**」。

**这条一次性定了三件事**：

1. **账期 / 信用 / 价格体系是「有向边」的属性，不是「无向关系」的属性。**
   F 对客户的 30 天，是 **F→客户** 这条边上的商务条件；
   B 对 F 的 10 天（或现结），是 **B→F** 这条边上的商务条件。
   两者**互不影响、不可传递、不可转嫁**——F 承诺客户 30 天，**不构成**对 B 的任何请求。

2. **所以 `party_tenant` 必须带 `direction`（SALE / PURCHASE），一行只放一个方向。**
   一对主体之间最多两行（互为买卖时各一行），正好对应 S6。
   ⚠️ 本文件早先版本把 `roles={CUSTOMER,SUPPLIER}` 与**单值** `credit_limit`/`settlement_days`
   塞在同一行，**是自相矛盾的**（两个方向的账期无处安放）—— 现按本条修正。

3. **一张客户订单会产生「两条互相独立的应收应付」，绝不能合并**：

```
客户订单（F 店，客户欠 F 的钱）
  ├─ F 的**应收**：客户 → F，**30 天**（F 对客户的承诺；挂在 F→客户 那条边）
  └─ F 的**应付**：F → B，**10 天**（B 对 F 的要求；挂在 B→F 那条边）
         ↑ 时间差 20 天 = **F 自己垫资的 20 天**，这是它的商业模式与风险，不是系统的 bug
```

**由此派生（现实且重要）**：
* **资金占用/垫资**由中间商自担 —— 这正是经销商生意的核心成本，系统要能**如实呈现**，
  而不是"顺手"把两边账期对齐（对齐就等于替客户改商业模式，是错的）。
* **信用额度**是**卖方对买方**的赊销额度 ⇒ 只在 SALE 方向那行有意义（`credit_limit`）。
  "B 要求 F 现结"就是 `direction=PURCHASE` 那行 `settlement_type=现结 / settlement_days=0`。
* **超额度怎么办**（挂起、要求预付、走审批）属**信控规则**，落在"这条边 + 规则配置"上。
* 将来要做**保理 / 供应链金融**（拿应收账款融资），入口也在这里 —— 留口子，不在 v1 实现。

#### 3.4.4b 商品跨租户挂载 + 订单路由（S7 / S8 的核心，**复用 S6 的推单机制**）

**先给结论**：S7 与 S8 在数据上**不是新机制**，而是"推单"的同构复用 ——
> F 店的客户订单，在 F 与 B 之间**触发一张 `F ← B` 的采购/供货单**（B 是 seller、F 是 buyer），
> 用同一条 `inter_tenant_doc_link` 把"客户订单 ↔ 供货单"串起来。
> 一句话：**卖给你的那个店不一定有货；有货的那个店是你的供应商。**

> **⚠️ 分两层，因为"取消谁承担 / 退货怎么退 / 运费谁出"这类问题，答案不在系统规则里，而在协议里。**
> 用户裁定（2026-09-22）：「**客户取消一张已经推给 B 且 B 已备货的单，这个就要求 F 和 B 达成代销合作的时候确定**」。
> ⇒ 系统**不做全局规则**，只负责"**如实执行协议条款**"。这也顺带解决了 G8/G9/G10。

**⚠️ 关键区分：S7 与 S9 的"交易链"一模一样，差别只在"履约路径"**

用户给出的三个变体（S7 / S8 / S9）里，**钱的流向**其实只有两种，而**货的流向**有三种：

| | **S7 直发（一件代发）** | **S9 经销中转** | **S8 厂家推单** |
|---|---|---|---|
| 交易链（钱） | 客户→F；F 结算给 B | **与 S7 完全相同**：客户→F；F→B | 客户→G；G 结算给 F |
| 履约路径（货） | **B → 客户**（跳过 F） | **B → F → 客户**（经停 F） | G → F → 客户（F 有货时 F→客户） |
| F 的库存 | **不动**（F 不持货） | **先增后减**（B 发来入库 → 发给客户出库） | 减少（F 自己已有的货） |
| F 的成本 | 佣金 / 差价（近服务费） | 采购成本（进销差价） | 采购成本 |
| 货运段数 | **1 段** | **2 段**（B→F、F→客户） | 1~2 段 |
| 货权 | 全程不过 F 的账 | **到 F 时转移给 F**（采购完成） | F 已有货权 |

⇒ 结论：**「履约路径」是与「交易链」正交的第三个维度**，必须单独建，不能塞进 `product_distribution.mode` 里
（同一份分销协议，可能两种履约方式都用：同城直发、异地中转）。

```sql

--    TRANSIT_STOCK 中转：供货方先发给成交店铺（货权转移），再由其发给客户
--    PICKUP        自提：客户到某租户处自提

  ship_from_tenant_id BIGINT, -- 本段发货方（B / F / G）
  ship_from_party_id  BIGINT,
  ship_to_kind VARCHAR(16),   -- CUSTOMER 终端客户 / TENANT 下一个租户（中转）

  ...
```

**链条**（S7 例：客户在 F 店买大豆油，货实际在 B）：

```
客户 ──下单──> F 的店铺（seller=F，价格=F 的售价）
                 │  命中 product_distribution ⇒ 判定无货/需穿透
                 ▼
        inter_tenant_doc_link（F 的客户订单 ↔ B 的供货单）
                 ▼
        B 侧生成供货单/销售单（seller=B, buyer=F, 价格=B 给 F 的价）
                 ▼
        B 发货给**终端客户**（收件人仍是客户，但发货方是 B）
                 ▼
        按协议结算：F 留佣金/差价，余款结给 B（见 3.4.4c）
```

#### 3.4.4b-2 可售量：**额度 + 供货方真实库存的双重校验**（2026-09-22 用户裁定）

> **用户原话**：「⑳a 这条选 b，但**如果供货方没有可用库存的时候 b 不可用**。**要保证无货发单情况**（即：不得出现"无货发单"）。」

⇒ "额度"**不是可以脱离供货方库存的独立数字**，规则是：

```
可下单 ⇔ (F 的额度剩余 ≥ 需求量)  且  (供货方当前可用库存 ≥ 需求量)
```

| 校验项 | 作用 |
|---|---|
| **额度** | 决定"F 最多能卖多少"（控制 B 的授信，且不暴露 B 的具体库存） |
| **供货方可用库存** | 决定"现在到底有没有货"（**防止无货发单**） |
| **两者都要过** | 缺一不可；**下单即锁**（供方锁库存 + 扣减 F 的额度余量），释放规则按协议条款 |

**这条真正要解决的矛盾：既"不暴露 B 的库存"，又"不能无货发单"** ⇒ 折中做法：
* **服务端**做真实校验（能拿到 B 的真实可用量）；
* **对外只暴露可售状态**，不给数字 —— 建议三档：**充足 / 少量 / 无货**；
* 并发场景下跨租户锁库存**必须走事件投递**（§4.3 三条铁律：不许跨租户直写）。

#### 3.4.4d0 **最高约束：所有协议不得违法**（2026-09-22 用户裁定）

> **用户原话**：「**我们所有的协议不能违法《消费者权益保护法》等相关法律法规。**」

这一条**优先级最高**，它给前面所有"双方约定"划了**法律边界**：

| 前文的口径 | 本条加的边界 |
|---|---|
| ㉖ 责任划分由**双方协议**定，平台不干预 | ❌ **但"双方同意"不能突破法律** —— 违反《消法》的条款**在法律上直接无效**，不是"平台不认" |
| ㉞ 对消费者的承诺**只能加码不能缩水** | 这只是**其中一条**法定底线；还有**格式条款整体不得排除/限制消费者权利**（《消法》第 26 条）等 |

**法律依据（真实世界）**：
* **《消费者权益保护法》第 25 条**：网购**七日无理由退货**是消费者的**法定权利**（有除外清单）；
* **《消费者权益保护法》第 26 条**：经营者不得以**格式条款**作出**排除或者限制消费者权利、
  减轻或者免除经营者责任**等对消费者不公平、不合理的规定 —— **含有此类内容的，其内容无效**；
* **《民法典》第 496~498 条**：格式条款的**提示说明义务**；不合理免除或减轻责任的条款**无效**。

**由此推出平台角色的最后一块拼图**：
> 平台**不干预商业条款**（谁承担成本、账期多长、佣金多少 —— 双方自治）；
> 但平台**必须守住法律底线**。而平台既然"**提供选项字典**"，就同时承担了
> **"字典里不得出现违法选项"**的责任 —— 把违法选项摆出来供人选择，平台自己也有责任。

**三个校验点（都必须是硬校验，不能只写在文档里）**：

| # | 时点 | 校验什么 |
|---|---|---|
| 1 | **字典维护时** | 每个选项要经**法务审核**（`legal_review_status`）；发现违法的选项要能**禁用并留痕**（历史协议仍可举证） |
| 2 | **租户承诺时** | ≥ 法定/平台底线（㉞），且**不得含排除消费者法定权利的表述** |
| 3 | **协议签署/生效时** | 同上校验一遍；**通过才允许 ACTIVE** |

**违法条款被发现后的处置（与"未约定"要区分开）**：

| 情形 | 系统行为 |
|---|---|
| **未约定**（必填项没填） | **不自动执行**任何赔偿/扣款，挂人工（§3.4.4d1） |
| **约定了但违法** | **该约定无效** ⇒ **按法定规则回退执行**（例：约定"不支持七日无理由"无效 ⇒ 消费者仍享有 7 天） |

**一个必须做对的精细点：法定权利有"除外清单"，不能一刀切**

《消法》第 25 条本身有除外（定作、鲜活易腐、拆封的数字化商品、报刊等；
以及"根据商品性质并经**消费者在购买时确认**不宜退货的"）。
所以底线模型**不能写死"一律 7 天"**，否则反而**不符法**：

```sql
consumer_policy_floor(
  ...,
  policy_code      VARCHAR(32),   -- RETURN_WITHOUT_REASON_DAYS …
  floor_type       VARCHAR(16),   -- LAW / PLATFORM
  floor_value      VARCHAR(32),
  legal_basis      VARCHAR(255),  -- 法条出处（举证与说明用）
  -- **适用范围与除外**：法定除外清单（类目 + 条件），命中且消费者已确认的，不适用该底线
  exempt_categories JSONB,        -- 如 ["FRESH","CUSTOM_MADE","DIGITAL_UNSEALED"]
  requires_buyer_confirm BOOLEAN, -- 命中除外时，**必须留下"消费者购买时确认过"的证据**
  status INT, effective_from DATE, effective_to DATE, ...
)
```

#### 3.4.4d 协议条款必须是「结构化选项」，不是自由文本（2026-09-22 用户裁定）

> **用户原话**：「**责任划分由合作双方协商（协议）确定，平台不干预，但要提供选项供双方选择，
> 便于系统仲裁和司法仲裁等。**」

**这条把"平台不干预"和"平台必须做点什么"同时说清了**：

| 平台**不做** | 平台**必须做** |
|---|---|
| ❌ 不制定"谁赔谁"的规则 | ✅ 提供**枚举选项字典**（可选项 + 每项的明确语义）—— **但绝不提供"默认值"**（给了默认值就等于平台替双方做了决定，见下） |
| ❌ 不替双方决定 | ✅ **如实记录**谁在何时选了哪一项、哪一版协议 |
| ❌ 不在双方约定之外扣任何人的钱 | ✅ **系统仲裁**：交易发生时按选定的选项**自动执行**（该扣谁就扣谁） |
| | ✅ **司法仲裁**：条款结构化留存 + 双方确认痕迹 + 执行日志，**可导出为证据** |

**为什么必须是"枚举"而不是"自由文本"**（这是这段的关键）：
* 自由文本平台**无法自动执行** —— "乙方承担合理损耗"这种句子，系统判不了该扣谁的钱；
* 自由文本**举证弱** —— 司法上要的是"双方明确同意的那一条是什么"，而不是一段可各自解释的描述；
* 枚举 + 参数才能做到「**选的时候就知道系统会怎么执行**」。

```sql
-- 条款选项字典（平台维护；**只定义"有哪些选项、各自什么含义"，不规定"必须选哪个"**）
agreement_term_option(
  id BIGINT PK,
  term_code   VARCHAR(32),   -- CANCEL_POLICY / RETURN_POLICY / RETURN_FREIGHT / FREIGHT_POLICY / QUALITY_LIABILITY …
  option_code VARCHAR(32),   -- SUPPLIER / DISTRIBUTOR / SHARE / TO_SUPPLIER / PREPAID / COLLECT …
  option_label VARCHAR(64),  -- 中文名（双方看到的）
  -- **语义说明**：选择了它，系统会怎么执行 —— 这段文字是给双方的"条款说明书"，也是司法举证的要点
  semantics   TEXT,
  needs_param VARCHAR(32),   -- 需要附带参数时（如 SHARE 需要比例）填参数名，否则空
  -- **是否必填**：责任划分类条款一律 required=true（见下"未约定就不自动执行"）
  required    BOOLEAN NOT NULL DEFAULT false,
  -- ⚠️ 刻意**没有** default_option 字段：平台给默认值 = 平台替双方决定 = 干预
  sort INT, status INT, ...
  UNIQUE (term_code, option_code) WHERE deleted = 0
)

-- 协议上的条款 = 从字典里选的选项 + 参数 + **双方确认痕迹**
distribution_agreement_term(
  id BIGINT PK, agreement_id BIGINT,
  term_code VARCHAR(32), option_code VARCHAR(32), param_value VARCHAR(64),
  -- 双方确认（司法举证用）；电子签章/哈希存证留列位
  confirmed_by_supplier BIGINT, confirmed_by_distributor BIGINT,
  confirmed_at TIMESTAMP, sign_hash VARCHAR(128),
  status INT, ...
  UNIQUE (agreement_id, term_code) WHERE deleted = 0
)
```

**协议还要有版本与变更历史**（因为要判"交易发生时生效的是哪一版"）：
`agreement_version(agreement_id, version_no, snapshot_json, changed_by, changed_at, change_reason)`。

#### 3.4.4d1 「未约定」≠「按平台默认」：**未约定就不自动执行**（2026-09-22 用户裁定）

> **用户原话**：「**在途（已下单未完成）的责任算哪边，也是双方协议约定的啊！**」

这条纠正了我一个错误倾向：我曾想在 ㉜ 里给"在途订单适用哪版协议"**设一个默认**（"默认不影响已确认订单"）。
**只要平台给默认值，平台就实际上替双方做了决定** —— 与"平台不干预责任划分"直接冲突。

**正确的落地方式（三步，全部必须有）**：

| # | 做法 |
|---|---|
| 1 | 责任划分类条款在字典里标 **`required = true`**（必填），**平台不设默认值** |
| 2 | **协议生效前校验必填项**：必填条款没选完，协议**不能置为生效**（逼双方在签约时说清，这是唯一不越位的做法） |
| 3 | **交易生成时校验"当时生效版本"里该项是否已约定**；**未约定 ⇒ 不自动执行任何赔偿/扣款**（不扣谁的钱、挂为人工处理），而不是拿平台默认去判 |

**同理适用于**：在途订单适用哪一版协议、取消/退货/运费/质量责任、账期与结算方式 ——
**凡是"双方怎么分"的问题，平台一律只提供选项、不做默认、且要求必须约定。**

> 这条与 §3.4.4d 合起来才是完整的：
> **平台不制定规则（不给默认）+ 平台要求你必须把规则约定清楚（必填）+ 平台按你约定的自动执行（可仲裁）。**

#### 3.4.4d2 协议**不可单方变更**：变更 = 新版本 + 双方同意 + 快照留存（2026-09-22 用户裁定）

> **用户原话**：「**合作双方达成协议以后不能单方面中途改变协议，改变协议要双方同意，
> 并且平台要保留双方协议快照。**」

**四条规定**（都要落到表结构与状态机上，不能只是"注释里写一句"）：

| # | 规定 | 落地方式 |
|---|---|---|
| 1 | **已生效的协议版本只读**，谁都改不了 | `agreement_version` 一旦 `ACTIVE`，其 `snapshot_json` **禁止 UPDATE**；改协议只能**新建一个 DRAFT 版本** |
| 2 | **变更必须双方同意**，缺一不可 | 版本记录里**两方的确认痕迹分开存**（`supplier_confirmed_at` / `distributor_confirmed_at` + 各自签章哈希）；**两者都非空**才允许置 `ACTIVE` |
| 3 | **平台保留双方协议快照** | 每个版本存**完整条款快照**（`snapshot_json`）+ 双方签章哈希；**只追加、不修改**（司法举证用） |
| 4 | **变更不追溯** | 新版本生效**不改动任何已产生的单据与结算**；推单/结算时一律取"**下单时刻生效的那一版**" |

```sql
distribution_agreement(
  ...,
  current_version_id BIGINT,   -- **当前生效版本**（双方都确认过的那一版）
  status INT,                  -- DRAFT 洽谈中 / ACTIVE 生效 / SUSPENDED 暂停 / TERMINATED 终止
)

agreement_version(
  id BIGINT PK, agreement_id BIGINT, version_no INT,
  snapshot_json JSONB NOT NULL, -- **完整条款快照（不可变）**：条款选项 + 参数 + 价格 + 期限
  status VARCHAR(16),           -- DRAFT 待对方确认 / ACTIVE 生效 / SUPERSEDED 已被新版取代 / REJECTED 被否决
  -- ↓ 双方确认，缺一不可（这也是"不能单方改"的技术保证）
  supplier_confirmed_by BIGINT,    supplier_confirmed_at TIMESTAMP,    supplier_sign_hash VARCHAR(128),
  distributor_confirmed_by BIGINT, distributor_confirmed_at TIMESTAMP, distributor_sign_hash VARCHAR(128),
  effective_from TIMESTAMP, effective_to TIMESTAMP,
  change_reason VARCHAR(255), created_by BIGINT, created_at TIMESTAMP,
  UNIQUE (agreement_id, version_no)
)
```

**变更流程（与"单据变更走变更单"完全同构）**：

```
一方发起变更 ──> 生成 DRAFT 版本（**现行版本继续有效，交易照常**）
                   │
     对方同意 ─────┼──> 新版本 ACTIVE，旧版本置 SUPERSEDED（快照留存）
     对方拒绝 ─────┴──> DRAFT 置 REJECTED（**现行版本继续有效**）
```

> ⚠️ 最容易做错的点：**在变更谈成之前，交易必须仍按现行版本执行**。
> 若把协议改成"可编辑"，就会出现"一方偷偷改了佣金比例，对方还在按老条款发货"——
> 这既是商业纠纷，也是系统无法自证清白的举证失败。

#### 3.4.4d3 对消费者的承诺：**只能加码，不能缩水**（2026-09-22 用户裁定）

> **用户原话**：「租户为了更好的服务可以**扩大**自己的责任但**不能缩小**责任！
> 比如租户承诺 7 天无理由退货，为了服务好，自行承诺 **10 天**无理由退货。
> **平台不反对不限制，但你不能按 5 天无理由执行。**」

**这条与前几条不是一回事，要单独建**：
* 前面讨论的是「**双方之间**怎么分责任」⇒ 平台不干预，双方协议定（㉖）；
* 这一条是「**一方对第三方（消费者）的单方承诺**」⇒ 有**不可退让的底线**，且**只能往上、不能往下**。

**底线从哪来（三层，取最严者）**：

| 层级 | 例子 | 性质 |
|---|---|---|
| **法定底线** | **网购 7 天无理由退货**（《消费者权益保护法》第 25 条） | 法律强制，谁都不能低 |
| **平台规则底线** | 平台入驻规则里对全体的更高要求 | 平台可设，但仍是最低标准 |
| **协议约定** | F↔B 之间再额外的约定 | 只影响双方之间，不改变对消费者的底线 |

**三条实现规则**：

| # | 规则 | 落地 |
|---|---|---|
| 1 | **只加码、不缩水**（单向棘轮） | 租户对外承诺值 **必须 ≥ 底线值**；店铺设置保存时**校验并拒绝**低于底线的承诺（"7 天 → 5 天"直接不让存） |
| 2 | **执行按"实际承诺"，不按底线** | 租户承诺了 10 天，就必须按 **10 天**执行（那是它对消费者的公开承诺，构成义务）；底线**只用于校验合法性**，不用于执行 |
| 3 | **加码不需要平台审批** | "平台不反对不限制"——加码是租户单方对消费者的让利，平台无正当理由限制 |

```sql
-- 底线清单（平台维护；**法定的那一层不是平台"定"的，是平台"守"的**）
consumer_policy_floor(
  id BIGINT PK, policy_code VARCHAR(32),   -- RETURN_WITHOUT_REASON_DAYS / REFUND_ARRIVAL_DAYS / WARRANTY_MONTHS …
  floor_type  VARCHAR(16),                 -- LAW 法定 / PLATFORM 平台规则
  floor_value VARCHAR(32),                 -- 如 "7"
  legal_basis VARCHAR(255),                -- 如《消费者权益保护法》第25条（**举证与说明用**）
  status INT, effective_from DATE, effective_to DATE,
  UNIQUE (policy_code, floor_type) WHERE deleted = 0
)

-- 租户对外承诺（**执行以此为准**；只能 ≥ 底线）
tenant_consumer_policy(
  id BIGINT PK, tenant_id BIGINT, policy_code VARCHAR(32),
  committed_value VARCHAR(32),             -- 如 "10"
  public_note     VARCHAR(255),            -- 对消费者的公开说明（留档，构成承诺）
  status INT, effective_from DATE, effective_to DATE,
  ...
  UNIQUE (tenant_id, policy_code, effective_from) WHERE deleted = 0
)
```

**⚠️ 由此派生一条重要规则：加码的成本默认由加码方自担，不可转嫁**

F 对消费者承诺 10 天无理由，但 B 只认 7 天 —— 那么 **8~10 天那部分退货的成本由 F 自己承担**；
要让 B 也接受 10 天，必须在 **F↔B 的协议**里约定（㉖ 的枚举条款）。

> 这与 ⑲「F 给客户 30 天、B 只给 F 10 天，**F 给客户的承诺不能变成 B 给 F 的承诺**」是**同一条道理**：
> **一方单方面答应别人的事，不能自动变成第三方的义务。**（见 §六 第四条通用原则）

#### 3.4.4e 平台收入：**多种计费方式并存**（2026-09-22 用户裁定）

> **用户原话**：「**平台收入可以是固定租费类似于房租也可以是抽成，方式可以多种多样，结合真实世界真实交易。**」

**真实世界里平台怎么收钱**（对照本仓已有物）：

| 计费方式 | 现实例子 | 本仓现状 |
|---|---|---|
| **固定租费 / 订阅**（类比房租） | 年费、月租、按版本套餐 | ✅ **已有骨架**：`sys_tenant_module.purchase_type`（`permanent`/`auto_renew`/`manual`）+ `expireTime` + `status`；另有 `sys_tenant_package`（套餐）与 `sys_tenant.level/expire_time` |
| **交易抽成** | 按订单额百分比（外卖 15~20%） | ⬜ 新 |
| **按量计费** | 按订单数、按 GMV 阶梯、按用户数、按存储量 | ⬜ 新 |
| **增值服务** | 短信包、广告位、装修模板、数据服务 | ⬜ 新（仓里有 `mkt_sms_*` 等可作基础） |
| **保证金 / 入驻费** | 电商平台入驻保证金（可扣罚） | ⬜ 新 |
| **组合**（现实常态） | **基础订阅费 + 交易佣金 + 增值**（SaaS）；**入驻费/保证金 + 佣金 + 广告**（电商） | ⬜ 待建 |

⇒ 所以**不能用一个"费率字段"表达**（这也是我要撤回自己先前 ㉕ 那条"平台级费率"推荐的地方），
要建成**计费规则引擎**：多条规则**可同时生效**，结算时汇总成一张平台账单。

```sql
platform_billing_rule(
  id BIGINT PK,
  billing_type VARCHAR(32),   -- SUBSCRIPTION 周期订阅 / MODULE 模块订阅 / USAGE 按量 /
                              -- COMMISSION 交易抽成 / SERVICE 增值服务 / DEPOSIT 保证金 / AD 广告
  scope        VARCHAR(32),   -- TENANT 整体 / MODULE 模块 / CATEGORY 类目 / PRODUCT 商品
  scope_ref    VARCHAR(64),   -- 对应 scope 的标识（模块码 / 类目 id …）
  charge_base  VARCHAR(32),   -- TIME 按时间 / ORDER_AMOUNT 按订单金额 / ORDER_COUNT 按单量 / USER_COUNT 按人数
  rate         NUMERIC(9,4),  -- 比例（抽成）
  fixed_amount NUMERIC(18,2), -- 固定额（租费/保证金）
  tiers        JSONB,         -- 阶梯（GMV 档位 → 费率）
  settle_cycle VARCHAR(16),   -- 结算周期 MONTHLY / QUARTERLY / YEARLY / PER_ORDER
  payer        VARCHAR(16),   -- TENANT 向租户收 / BUYER 向买家收（现实里抽成可能转嫁）
  price_bearer VARCHAR(16),   -- 抽成由谁承担：MERCHANT / BUYER / SHARE（与 G14 同性质）
  effective_from DATE, effective_to DATE, status INT, ...
)

platform_invoice(            -- 平台账单（周期结算产物，也可能被 ⑫ 净额结算冲抵）
  id BIGINT PK, tenant_id BIGINT, period VARCHAR(16),
  subscription_amount NUMERIC(18,2), commission_amount NUMERIC(18,2),
  service_amount NUMERIC(18,2), deposit_amount NUMERIC(18,2),
  total_amount NUMERIC(18,2), status INT, due_date DATE, ...
)
```

**三个必须一起想的约束**：
1. **平台向谁收**：订阅费向**租户（商户）**收；交易抽成现实中**可能由商户承担、也可能转嫁给买家**
   （`price_bearer`）—— 这直接决定 S7 里那笔钱怎么分。
2. **平台抽成与"平台不干预责任划分"的关系**：平台只在**双方约定的条款**下动钱
   （例如协议约定"取消由 F 承担"，平台就按约执行），**不自行加罚**。
3. **保证金可被扣罚的性质**：扣罚依据同样必须来自**协议条款**或**平台规则（租户入驻时已同意）**，
   且要留痕 —— 与 §3.4.4d 的"司法仲裁可举证"是同一套要求。

#### 3.4.4f 资金流模式：**按「销售渠道」分派**，两种渠道并存（2026-09-22 用户裁定）

> **用户原话**：「资金流模式里面**基本以后平台开平台商城了，租户还是可以使用自己的租户商城**，
> 比如租户通过**自己的租户商城**销售的产品走**自己的直连收单**，
> 如果商品是通过**平台商城**出售的走**平台分账**。」

**这条把 G4 从"全局二选一"纠正为"按成交渠道分派"** —— 现实中两种渠道会**长期并存**：

| 成交渠道 `sales_channel` | 资金路径 | 资金流模式 |
|---|---|---|
| **租户商城** `TENANT_MALL` | 客户 → **直达商户（该租户）** | `DIRECT` 直连收单 |
| **平台商城** `PLATFORM_MALL` | 客户 → **平台**（平台**自营**：先向租户采购、再销售给客户） | 平台收款（**是平台自己的销售收入**，不是"替商户代收"） |
| 其它渠道（线下 / 第三方平台…） | 按渠道单独配 | 预留 |

**四条落地要求**：

| # | 要求 | 说明 |
|---|---|---|
| 1 | **`fund_flow_mode` 配在「渠道」上，不是全局一个值** | 一张 `sales_channel_config(channel_code, fund_flow_mode, …)`；**两种渠道同时有效** |
| 2 | **订单必须记 `sales_channel`** | 资金/分账/开票**一律按"这笔单在哪个渠道成交"分派**，不由"商品来源"决定 |
| 3 | **默认（今天）**：租户商城走 `DIRECT` ⇒ 平台不经手资金，**只出分账指令/账单** | 规避"二清"；平台抽成通过**账单**向租户收（§3.4.4e），而不是从交易资金里扣 |
| 4 | **将来开平台商城** ⇒ 该渠道走 `ESCROW` | 前置条件：**支付牌照或持牌机构合作**（平台成为资金流当事人，分账/对账/退款/开票归属需重定义） |

**🔑 由此得到一个重要同构：平台商城 ≈ 一个特殊的「租户商城」**

平台商城卖的是**各租户的货**，这在模型上与 S7「F 挂 B 的货卖」**完全同构** ——
只是把 `seller_tenant` 换成"平台"：

```
平台商城成交（客户买租户 T 的货，货在 T 处）
  seller   = 平台（对消费者负责、给消费者开票的那一方）
  supplier = 租户 T（实际供货方）
  ⇒ distribution_agreement 把 T 的货挂到"平台店铺"（T 是 supplier，平台是 seller）
  ⇒ inter_tenant_doc_link 串"客户订单 ↔ T 的供货单"
  ⇒ commission_settlement 做平台抽成 + 结给 T
资金：ESCROW（钱先进平台，扣抽成后分给 T）
```

⇒ **结论：不需要为"平台商城"另造一套机制**，它是 §3.4.4b / §3.4.4c 那套推单 + 分账的**渠道变体**；
唯一不同的是**资金模式**（该渠道配 `ESCROW`）与**平台自身的双重角色**
（既是治理方，又是该渠道的交易当事人 —— 届时要写清"平台以什么身份参与"，避免角色混同；
平台自营销售对消费者开票的责任也随之落到平台身上）。

**🔑「自营」与「代收代付」是两种法律形态，绝不能混 —— 三流一致就卡在这里**（2026-09-22 用户裁定）

> **用户原话**：「平台代收的模式，只是以后平台有了**自己自营的平台级商城**以后！
> 到时候**平台给客户开票，租户给平台开票**。这个我认为没有问题啊。」

**用户是对的** —— 因为这不是"代收"，而是**平台自营（买断）**。两种形态对比：

| | ❌ 代收代付 / 撮合（三流不一致，有虚开风险） | ✅ **平台自营（买断）**（用户选的形态） |
|---|---|---|
| 平台的角色 | **代收方**（钱只是路过平台，平台不是销售方） | **销售方**（平台先买后卖） |
| 合同流 | 客户 ↔ **商户** | 客户 ↔ **平台**；平台 ↔ **租户**（采购） |
| 资金流 | 客户 → 平台(代收) → 商户 | 客户 → **平台**（平台自己的收入）；平台 → 租户（采购付款） |
| **发票流** | 商户 → 客户（**资金流经平台但发票不经平台 ⇒ 不一致**） | **平台 → 客户**；**租户 → 平台**（**双向闭环，三流一致 ✅**） |
| 平台赚什么 | 佣金/服务费 | **进销差价**（+ 可能的通道费） |

⇒ **所以平台商城走"自营口径"没有三流问题**，用户的口径把 T1-1 直接闭环了。

**但它带来两条模型要求（必须落，否则实现会走偏）**：

1. **平台与租户之间存在「采购关系」** —— 平台是 **buyer**、租户是 **seller**
   ⇒ 用 `party_tenant` 的 **PURCHASE 方向** 表达（平台视角）；
   ⇒ 平台在此场景下的收入是**进销差价**，**不是佣金** ——
   所以 `commission_settlement` 在自营场景下退化为**普通购销结算**，
   "抽成"只在**撮合/代销**形态下才存在。**两者不要混用同一张表语义。**
2. **物流仍可"租户直发"**（drop-ship by supplier），**不影响交易链** ——
   这正是 §3.4.4b 提炼的「**交易链 vs 履约路径正交**」的又一次验证：
   **法律上平台是卖方，物流上由租户直接发给消费者**，两者互不矛盾（现实中的厂商直发就是这样）。

**将来若真要做"撮合/代收"形态**（平台只做代收、由商户对客户开票），那才需要单独解决三流一致
（通常落成"**委托代收代付**"架构 + 平台只收通道费、不对客户承担销售责任）—— 属**另一种平台形态**，v1 不做。

## 四、跨租户单据协同（S6 的直接后果）

### 4.1 本仓的硬约束

`AiReadyTenantLineInnerInterceptor` 会按会话租户给所有租户表查询注入 `tenant_id` 条件
（仅超管豁免）。因此**在 F 的会话里读 B 的销售单，必然返回 0 行**。
结论：跨租户协同**不能靠会话上下文**，必须是**显式、受控、可审计**的通道。

### 4.2 四种候选形态与取舍

### 4.2.1 先讲清楚「推单」和「镜像」是什么（大白话）

**镜像（mirror）= 一本账，两个人同时写。**
两边的"同一笔生意"是**同一张单据**：F 建了采购单，B 那边自动出现一张一模一样的销售单；
F 改数量，B 那边跟着变；B 改价格，F 这边也变。像两个人**同时编辑同一个在线文档**。
问题：谁说了算？B 想改价时 F 已经打印盖章了怎么办？两边财务一个记 100、一个记 95 时永远扯不清。
而且技术上要跨租户共享同一行数据 —— 本仓的租户隔离**直接不允许**。

**推单（push / 传票）= 两本账，互相抄送，各自负责。**
两边是**两张独立的单据**，中间有一条"这是同一笔生意"的连线：
F 建自己的采购单 → **发一份**给对方（投递）→ B 那边**生成自己的销售单**（可以改、可以拒）；
B 改了自己的销售单 → **回一份**过去 → F 的采购单上出现"对方已确认，价格改为 X"，
但 F 的采购单**仍然是 F 自己的单据**，要不要接受是 F 的动作。像**两家公司各自记账 + 互发传真**。

**一句话区别**：镜像 = 一本账两人同写；推单 = 两本账互抄，各写各的。

**为什么推单才是"真实世界"**：现实里买方有**采购合同/采购订单**、卖方有**销售合同/销售订单**，
本来就是**两份独立的商业文件**，只是指向同一笔交易；发票更是各开各的。**没人"共用一张订单"。**

### 4.2.2 四种候选形态与取舍

| 形态 | 可行性 | 评价 |
|---|---|---|
| 在 F 的会话里直接读/写 B 的单据 | ❌ | 绕过租户隔离 = 把多租户拆掉 |
| 双方**共用同一张单据行**（= 镜像） | ❌ | 两侧账都不自洽；权限、审计、变更都无解 |
| **各自独立单据 + 关联表 + 状态单向驱动**（= 推单） | ✅ | **推荐**（本文件 3.4.4）—— 与真实世界的两份合同同构 |
| 服务间调用（内部 API）在对侧建单 | ✅（辅） | 推单的**投递手段**；但**必须补验签** —— 本仓现有回调（`ErpCallback**`、`/api/wms/erp`）**没有任何验签**，不可照抄 |

### 4.3 推荐形态

```
F 的采购单 PO ──┐
                ├── inter_tenant_doc_link（主体对 + 租户对 + 两张单据 + state）
B 的销售单 SO ──┘
状态传播（卖方确认制）：
  F 提交 PO      ──投递──> B 侧生成 SO 草稿（B 可拒/可改）
  B 确认 SO      ──回写──> F 的 PO = 已确认（此后 F 只能走变更单）
  B 发货         ──回写──> F 的 PO = 已发货 / 生成 F 的收货单
  B 开票         ──回写──> F 的应付、B 的应收
```

**三条铁律**：
1. **各侧单据是各租户自己的账**，必须独立存在、独立审计；关联表只是"这是同一笔生意"的映射。
2. **写操作绝不跨租户直写**，一律"事件投递 + 对侧消费"。
3. **投递必须验签**（服务令牌或 HMAC + 时间戳 + nonce），否则等于给库存/金额开了匿名写入口。

### 4.4 可见性边界

F 只能看到"我这单在 B 那边的**进度摘要**"（状态 / 交期 / 发货 / 发票），
**看不到** B 的完整销售单（其它客户、成本、库存、毛利）。摘要是白名单字段，不是整单脱敏。

### 4.5 与现有模块的接口（别从零造）

| 现成物 | 能借什么 | 要注意 |
|---|---|---|
| `erp-supplier-portal`（供应商门户） | "供应商看买方单据"的**界面与流程雏形** | 它现在是**同一租户内**的员工会话（已核实），**不是**跨租户 —— 正好是要升级的那一步 |
| `purchase_contract`（V11.439.0 新建） | **框架协议**：B↔F 先签框架，采购单挂框架下 | 没有框架就"谁都能给谁推单"，需拍板是否强制 |
| `crm_erp_customer_mapping` | **同构先例**：两套系统间同一实体的映射 | 照它的形状做跨租户单据映射 |
| `wms_event_outbox` / `InventoryChangeEvent` | 事件投递的表结构与消费模式 | **要补验签**（现有链路没有） |

### 6.5 租户编号口径：**0 = 默认共享租户，1 = 系统平台租户**（2026-09-23 用户裁定）

> **用户原话**：「**0 号租户是默认共享租户，1 号租户才是系统平台租户**」

**这是一条"地基级"口径**，因为它决定"某一行数据归谁看得见"这件事怎么表达。真库现状与之一致：
`sys_tenant` 里**没有 0 号行**（只有 `1 = 系统租户 / SYSTEM`）—— 0 是**共享层的哨兵值，不是一个真实租户**。

| 编号 | 是什么 | 数据长什么样 | 谁能看见 |
|---|---|---|---|
| **0** | **默认共享租户**（共享层） | 不属于任何单个租户的**公共数据**：平台字段字典（`agreement_setting_def` 22 行 `tenant_id=0`）、平台级配置默认值、散客/公共往来档案（`biz_party` 现有 4 行 `tenant_id=0`） | **各租户都可见**（这正是"共享"的含义） |
| **1** | **系统平台租户**（`SYSTEM`） | 平台自己的数据与**平台专属能力**：`system:*` 权限、系统模块（V11.455.0 只开给它） | 平台侧 |

**四条推论（照此判，不许再各说各话）**：

1. **`tenant_id=0` 不等于"平台专属"**。把 0 读成"平台"会把共享数据当成平台私有 ⇒ 该看见的看不见。
2. **平台专属能力归租户 1**（不是 0）：`system:*` 权限码、「系统」模块、平台协议写权限等。
   本轮落地的 `agreement:platform:*`（前缀归「系统」模块 ⇒ 按 V11.455.0 只开给系统租户）
   就是这条的**现成实现**，后续平台能力照抄它，别再造第二套。
3. **普通租户看得见 `tenant_id=0` 的数据**（MASTER_TODO §4 第 2 条的答案）。
   真正要防的是"看见**别的租户**的数据"，与 0 无关；把 0 一并挡掉属于额外收紧，需单独论证。
4. **本文件里所有"系统级/平台级对象"的表述，按本条重新读**：
   例如协议主档 `tenant_id` 恒 0（裁定⑥）—— 准确说法是「协议是**共享层**对象，
   行不属于任何单个租户，故租户拦截器不介入；可见性由两端租户**显式判定**」。
   同理，登记进 `IGNORE_TENANT_TABLES` 的表**不等于**"平台私有表"，
   而是「**共享层表**：行不按租户切分，行级过滤对它们无意义」。

| G4 | 平台代收货款的"二清"合规风险 | 资金是否过平台账户 / 直连收单 —— **法律问题，决定资金模型与牌照** | ⬜ **建议早定** |

| G7 | 保理 / 供应链金融（拿应收融资） | 留口子，v1 不做 | ⬜ 留口子 |

### 7.4 一句话总结这一节

> 我们把「**货怎么走、单怎么开**」想得比较透（甚至想到了履约路径这种正交维度），
> 但「**钱怎么走、退怎么退**」还停在最表层。
> 而现实里，**经销商模式赚的恰恰就是"钱的时间差"** —— 漏掉资金维度，
> 这套模型就只能算"能下单"，不能算"能做生意"。

### 7.6 第三轮自检（2026-09-22，按"**主体会变、单据要认当时的账**"这条线重走）

> 方法：不再逐条补功能，而是问三个"命门"问题 ——
> ① **主体会变吗**（改名/换法人/被收购/重复注册）？② **单据记的是"当时"还是"现在"**？③ **跨租户的钱怎么收付与对账**？
> 结论：**发现两个地基级缺口（U1/U2）** —— 它们**不推翻任何已定方案**，
> 但**决定"所有表要不要带快照列、要不要别名表"**，属**动手前必须定**。

#### ✅ U1 主数据的「变更」与「合并」（2026-09-22 用户裁定 —— 已闭环）

> **用户原话**（三条，逐条决定）：
> ① 「同一自然人在同一店注册两次…**除非是确凿证据证明比如身份证号**！
>   而且**账号合并也不能平台强制合并，需要通过核验、账户所有人同意**等，否则可能会出现冒用
>   （比如用户 a 的手机 c 不用了，用户 b 用手机 c 又重新注册，怎么确定？**这个合并有非常大的风险**）。
>   建议是**系统及平台不强制合并，只保留合规合并的选项**。」
> ② 「同一个公司被录了 2 套档案，相当于**租户内的档案处理**，**如果不涉及到其他租户的利益，应该由租户自己确定**。」
> ③ 「企业改名/迁址/换法人/被收购…**应该跟着工商系统的资料走**，
>   只要是 **2 个单位的社会统一信用代码是一样的，就应该是一个单位**，支持改名、迁址、换法人、被收购等操作。
>   只要**保留快照**就可以了。但如果是**被收购，是否需要建新档由租户所属用户自己决定**，
>   **平台提供合规接口但不干预**。」

**⇒ 三条铁律（与我先前"自动去重"的倾向相反，特此更正）**：

| # | 铁律 | 落地 |
|---|---|---|
| 1 | **不强制合并**：平台/系统**没有自动合并**，只有 **"申请 → 核验 → 双方同意 → 执行"** 的**合规合并选项** | 模型里不写任何"自动判定同一人/同一企业就合并"的逻辑 |
| 2 | **识别键分层**：**自然人 = 身份证号**（唯一确凿证据）；**企业 = 统一社会信用代码** | **手机号/邮箱/名称一律不作为合并依据**（正是用户举的"手机号被他人重新注册"的冒用场景） |
| 3 | **合并的授权范围分层**：**租户内档案 → 租户自主**（不涉他租户利益）；**跨租户 / 系统级主档 → 涉及多方利益，须谨慎，平台只提供合规接口** | 与 ㉖"平台不干预"一致：平台**给能力**，不**替人决定** |

```sql
-- 曾用名 / 别名（改名、迁址等历史值；**历史单据靠快照回溯，别名仅辅助检索**）
party_alias(id, party_id, alias_type,  -- NAME 曾用名 / LICENSE 曾用执照号 / ADDRESS 旧址 / LEGAL_PERSON 原法人
            alias_value, changed_at, change_source, evidence, ...)

-- 主体变更历史（改名/迁址/换法人：**只追加**，同第三条原则）
party_change_log(id, party_id, change_type, before_json, after_json,
                 change_source,      -- INDUSTRY_REG 工商登记 / MANUAL 人工登记（接口留位对接工商核验）
                 evidence, effective_from, operator_id, created_at, ...)

-- 主体关系（被收购/合并/分立 —— 代码不变 vs 代码变的两种情形）
party_relation(id, from_kind, from_id, to_kind, to_id,
               relation VARCHAR(24),   -- PREDECESSOR 前身 / SUCCESSOR 承继 / MERGED_INTO 并入 / SPLIT_FROM 分立
               uscc_before, uscc_after,  -- 统一社会信用代码是否变化（不变=仅变更；变=需新档或建承继关系）
               status INT, evidence, effective_from, ...)

-- 合并申请（**全流程留痕 + 双方同意**；没有任何自动路径）
merge_request(id,
  scope VARCHAR(16),            -- PERSON 自然人 / PARTY_TENANT 租户内档案 / PARTY_SYSTEM 系统级主档
  source_kind, source_id, target_kind, target_id,
  key_type VARCHAR(16),         -- ID_CARD 身份证号 / USCC 统一社会信用代码（**唯二**可作依据）
  verify_status VARCHAR(16),    -- 核验结果
  consent_source, consent_target,  -- **双方同意**（自然人须本人；企业须授权人）
  status INT, reject_reason, operator_id, created_at, ...)
```

**企业"被收购"的两种情形要分开**（用户说"是否建新档由租户自己决定"，正是这两种）：
* **统一社会信用代码不变**（股权收购、仅换法人）⇒ 走**变更**（`party_change_log`）+ 快照即可；
* **代码变化**（吸收/新设合并，被收购方代码注销）⇒ 需**建新档**或建**承继关系**（`party_relation`），
  由**租户自己决定**要不要建新档 —— 平台只提供接口，不替租户决定。

#### ✅ U2 单据的「时点快照」制度化 + 业务日期（2026-09-22 用户裁定 —— 已闭环）

> **用户选 (b) 推荐集**：主体名称 + 统一社会信用代码/身份证号 + **价格、税率、客户等级、协议版本号、收货地址与联系人**；
> **业务日期**按推荐采纳（补录/跨期入账需要）。

| 问题 | 现状 | 缺什么 |
|---|---|---|
| 改了主数据，**历史单据会不会跟着变**？ | 本仓**已有部分快照习惯**（`erp_purchase_order` 带 `supplier_name`/`buyer_name`/`purchaser_name`）✔ | **没有制度化**：应明确"哪些字段**必须快照**"（主体名称/税号/地址/联系人、价格、税率、等级、协议版本），并写进建表规范 |
| **业务日期 vs 系统日期** | 只有 create_time | ✅ **已定（按推荐采纳）**：补**业务发生日**（财务按业务日入账，不是录入日） |
| **税率变更**（如 13%→11%） | 发票无税率快照 | 税率是**时点属性**，发票必须存**开票当时的税率** |

⇒ **一票否决级**：凡是"已生效"的实体（协议、订单、发票、结算），**引用的外部信息必须快照**，
不能只存 id —— 否则**历史无法复现，对账与举证全会输**（与第三条原则同源）。

#### ✅ U3 跨租户的收付款与对账（**已裁定**，2026-09-22 —— 见 §7.7，**净额结算本批不做**）

**更正我上一轮的说法**：收付款单据**并不缺** —— 仓库里有
`erp_receipt`（收款）/`erp_payment`（付款）/`erp_pre_receipt`（预收）/`erp_pre_payment`（预付）/
`payment_reconciliation`（对账）/`erp_sale_order_settlement`（订单结算）。
缺的是**跨租户时的口径**：
* 平台自营时，**谁给谁收付款**（客户→平台、平台→租户），两张收付款单如何**关联成同一笔**；
* **对账单由谁出、对方怎么确认**（双方确认痕迹，同 ㉛ 的快照逻辑）；
* **对账不平**时的差异处理与争议升级（与 T1-4 状态补偿衔接）。

**✅ 裁定（2026-09-22）：选"各记各的 + 关联表"（选项 A），本批不做净额结算** —— 详见 **§7.7**：
* 两侧**各记各的账**（F 记"付给 B"、B 记"收到 F"），用 `inter_tenant_payment_link` 把两张单**串成同一笔**；
* 形态与 §4.3 已裁定的**跨租户推单同构**（各侧独立账 + 关联表 + 事件投递 + **验签**），**不引入第二套机制**；
* 对账单的"双方确认 + 快照"**复用协议模块的双签机制**（`sign_hash`），不另造；
* ❌ **明确不做"平台做对账中心"** —— 平台不是交易当事人（§6.3），做对账中心即越位；
* ⚠️ **决策 ⑫ 的"净额结算"部分本次收窄**：先只做**对账（关联 + 双方确认）**，净额结算**延后**为独立功能项（见 §6.1 的 ⑫ 注记）。

#### 🟠 U4 「项目 / 成本中心」维度缺失

B2B 现实：大客户的采购常挂在**项目**下（工程、装修、集成、专项采购），
结算与成本要**按项目归集**。仓库里**没有业务项目表**（`sys_project_config` 是配置，不是项目）。
⇒ 单据需要可选的项目维度（可与 §3.4.3 的"四主体"并列，作为第五个归属维度）。

#### 🟡 U5 平台治理的完整闭环（与 T2-2 配对）

电商法给"平台经营者"的义务是**一整套**，不是一个"清退权"：
**入驻资质审核** → **信息公示**（执照/许可证挂在店铺页）→ **知识产权保护**（通知-删除）→
**违规判罚**（扣分/降权/下架/扣保证金/清退）→ **申诉** → **纠纷处理** → **特定情形先行赔付**（T2-6）。
现状：只有零散的清退权（㉝）与保证金扣罚（㉙）。

#### 🟡 U6 特殊交易形态

仓库已有：`erp_marketing_gift`（营销赠品）、`erp_sale_exchange`/`erp_purchase_exchange`（换货）、
`erp_group_buy_activity`（拼团）、`mkt_presale`（预售）、`erp_payment`（付款）。
**仍缺**：**样品**（不走收入但走库存，B2B 常态）、**以货易货 barter**（与"互为买卖 + 净额结算"相关但不同）、
**竞价/拍卖**、**赠品对库存与成本的处理规则**（赠品不是收入，但货真的出去了）。

#### 🟡 U7 税率与发票要素进模型

货物与服务**税率不同**（且随政策变），发票需要**税率、税额、价税分离**，
且税率是**时点属性**（U2）。目前 `invoice*` 表在，但没有"税率随类目/时点"的口径。

#### 第三轮的诚实结论

**不可能有"绝对完整"的模型**（真实世界没有边界）。判断标准只能是**地基对不对**。六项地基：

| 地基 | 状态 |
|---|---|
| 主体（自然人/往来单位/租户） | ✅ |
| 关系（R1~R4 + 代谁 + 角色） | ✅ |
| 责任（进协议 + 法定底线） | ✅ |
| 资金（渠道分派 + 分账 + 净额） | ✅ |
| 合规（消法/三流/隐私） | ✅ 主干 |
| 时点（U2） | ✅ **已闭环**（快照清单选 (b) 推荐集 + 补业务日期） |
| 主数据变更/合并（U1） | ✅ **已闭环**（2026-09-22 用户裁定，见上） |

⇒ **最该在动手前定的，是 U1 + U2**（决定全表结构）；U3/U4/U5/U6/U7 都可以"边做边加"。

### 7.7 四条主干缺口的裁定（2026-09-22 用户裁定 —— **定表之前必须照此**）

> 这四条不是"以后再说"的细化，而是**已经开始施工的路线上还没定的地基**：
> G13 不定，协议签署永远答不出"凭什么代表"；G12 不定，阶段 5 的单据主体字段**建完就得返工**。

#### G13 · R1 授权范围与限额 → **结构化授权（分两步）**

| 选项 | 内容 | 结论 |
|---|---|---|
| A | 只加金额限制（单笔 + 日累计） | **采用，作为第一步** |
| **B** | **结构化授权**：范围（可代做哪些动作）+ 限额（金额/账期）+ 有效期 + 是否需二级审批 | ✅ **采用（目标形态）** |
| C | 不做限制，只在单据留痕"代谁" | ❌ 与"超过 50 万要审批"直接矛盾 |
| D | 在 A 之上加超限触发对方审批流 | 其能力**并入 B 的 `approval_threshold` 字段**，不单列方案 |

**落地分两步**：先落 **A 级金额限制**让风控尽快生效，再补「范围」维度。
**载体**：`person_party` 加列，或新表 `person_party_authorization`（**倾向后者** —— 一条授权有独立有效期与审批阈值）。
**闭环点**：协议签署的 `authority_basis` **引用**这条授权 ⇒ 补上 §13.6 现在答不出的「**他有没有越权**」。

#### G12 · 单据的四个主体 → **从属表为主 + 高频两列冗余**

| 选项 | 内容 | 结论 |
|---|---|---|
| A | 单据主表放四列（签约/收货/结算/开票） | 部分采用：**只把「收货方」「开票方」两列冗余到主表**（便于查询与索引） |
| **B** | **从属表 `doc_party_role`**（单据 × 角色 × 主体，多行） | ✅ **采用为主** |
| C | 只加收货方 + 开票方 | ❌ 结算方、报关方仍缺 |
| D | 不动，靠 `acting_party_id` 加备注 | ❌ "三单不一致"是 B2B **常态**，等于没建模 |

**关键**：该从属表**就是阶段 5 已规划的 `trade_party_role`**，不是新增设计 ⇒ 本条等于**把阶段 5 的表提前定下来**。
**为什么"为主"是 B 而不是 A**：用户已裁定「**角色逐笔确定，不是身份属性**」（§3.2b），从属表正是它的技术形态；
且角色**不止四个**（还会有报关方、保险受益人、承运委托方），固定列迟早要加列。

#### G11 · 直发时终端客户信息的暴露范围 → **写进协议，并对"明文"设硬底线**

| 选项 | 内容 | 结论 |
|---|---|---|
| A | 隐私号面单（虚拟号 + 脱敏地址） | 作为**协议可选值之一** |
| B | 只给区级地址，面单由系统代打 | 作为**协议可选值之一** |
| C | 走 F 的中转仓，由 F 发客户 | 作为**协议可选值之一** |
| D | 明文给 B + 协议约束 | ⚠️ **只在"同一集团 / 自营物流"这类特定关系下允许** |
| **E** | **把选择权写进协议**（`customer_info_exposure` 条款） | ✅ **采用为机制** |

**理由**：与「**责任划分进协议、不进全局规则**」（第二条原则）完全一致；且不同供应商能力不同，一刀切不现实。
**但**「协议自治有边界」（第五条原则）⇒ **D 不得无条件可选**，否则违反个保法的"最小必要"。
**首个消费方**：`inter_tenant_doc_link` 的**可见性矩阵（T1-3）** —— 这是 §4.4「只给对方白名单字段」的**第一个真实用例**。

#### U3 · 跨租户收付款与对账 → **选 A「各记各的 + 关联表」**

| 选项 | 内容 | 结论 |
|---|---|---|
| **A** | **各记各的 + 关联表**（F 记"付给 B"、B 记"收到 F"，用关联表串成同一笔） | ✅ **采用** |
| B | A 之上再加净额结算（多笔轧差） | ⏸ **本批不做**（决策 ⑫ 相应收窄） |
| C | 平台做对账中心 | ❌ **平台越位** —— 平台不是交易当事人（§6.3） |
| D | 不做，双方线下对 | ❌ 与已裁定的 ⑫ 矛盾 |

**形态**：两侧独立记账 + `inter_tenant_payment_link` ⇒ 与 §4.3 的**跨租户推单同构**
（各侧独立账 + 关联表 + 事件投递 + **验签**），**不引入第二套机制**；
对账单的「双方确认 + 快照」**复用协议模块的双签机制**（`sign_hash`），不另造。

#### 7.7 附：本次逼出来的「**三层结算口径**」问题（2026-09-22 一并裁定）

**实测发现**：`biz_party` **已有** `settlement_type` / `settlement_days` / `credit_days` / `payment_days` /
`fixed_payment_day` / `settlement_day` / `credit_limit` —— 而 `AgreementCreditTermProvider` **一个都没读**
（只读协议里的 `AR_CREDIT_DAYS`）⇒ 现在**三套结算口径并存且互不知情**：
档案（`biz_party`）、协议（`SETTLEMENT_TYPE`，待建）、采购/销售**硬编码的 30 天**。

**裁定（2026-09-22，用户采纳推荐）—— 按"是不是跨租户"分层**：

| 场景 | 用哪层口径 | 为什么 |
|---|---|---|
| **跨租户 + 有协议有约定** | **协议** | 双方约定，最高 |
| **跨租户 + 无协议 / 协议到期 / 协议未约定结算方式** | **现款现结**（无账期） | 见 §13.3 补充口径 3：低风险缺省 |
| **租户内交易**（客户就是我自己的客户） | **`biz_party.settlement_type`**（租户自己的信用政策） | 账期是**租户单方给客户的信用**，不涉及对方约定 ⇒ 与第四条原则「单方承诺不传导」**不冲突**（它本来就不传导） |
| 档案也没设 | **现款现结** | 兜底，同上 |

⚠️ **连带**：`PLATFORM_DEFAULT_CREDIT_DAYS = 30`（采购/销售硬编码）**在任何一层都不成立** —— 见 §13.3 ⑤。

### 8.1 两处带附加条件的裁决（实施时必须照做）

**① ★G4 资金流：按成交渠道分派，两种渠道并存** —— 见 §3.4.4f
· **租户商城**（`TENANT_MALL`）→ `DIRECT` 直连收单：钱直达商户，平台不经手，规避"二清"；
· **平台商城**（`PLATFORM_MALL`）→ `ESCROW` 平台分账：钱先进平台，扣抽成后分给供货租户；
· `fund_flow_mode` **配在「渠道」上**（`sales_channel_config`），**不是全局一个值**；订单必须记 `sales_channel`，资金一律按成交渠道分派；
· 切 `ESCROW` 的前置条件：**支付牌照或持牌机构合作**，且平台成为资金流当事人（分账/对账/退款/开票归属需重定义）；
· **平台商城不需要另造机制**：它与租户商城同构（平台＝特殊 seller、租户＝supplier），复用推单 + 分账那套。

**② ⑳a 可售量：额度 + 供货方真实库存，双重校验** —— 见 §3.4.4b-2
· 额度决定"F 最多能卖多少"，**供货方可用库存决定"现在有没有货"**，两者都要过；
· **硬要求：不得出现"无货发单"**；
· 折中：服务端真实校验，**对外只暴露"充足 / 少量 / 无货"**，不暴露 B 的库存数字；
· 跨租户锁库存走**事件投递**（§4.3 铁律，不许跨租户直写）。

### 11.6 单据快照规范（**阶段 2** · U2 的落地形态，2026-09-22 制定）

> **一句话**：单据一旦**已生效**，它引用的**外部信息必须同时落一份"当时的副本"**。
> 缺了它，历史无法复现、对账与举证全会输（U2 的"一票否决级"结论，与第三条通用原则同源）。
> 它是**唯一"晚做就要全表回填"的事**，所以排在阶段 2、在动任何单据表之前先定。

#### 11.6.1 与旧规「禁止冗余名称字段」的关系（**唯一判据**，必须写下来免得两条规则打架）

| 旧规（2026-07-13 开发技术规范） | 新规（U2，2026-09-22） |
|---|---|
| 禁止冗余名称字段，只存 ID，名称靠 JOIN | 已生效单据**必须**存名称等外部信息的快照 |

**两者不矛盾**，因为判据不同：

> **判据 = 这个值会不会随时间变，且历史单据必须认"当时"的账？**
> · **会变**（主体名称/税号/地址/联系人/价格/税率/等级/**协议版本**）⇒ **必须快照**；
> · **不会变、或只用于当下展示**（如仓库 id、分类 id）⇒ **仍然只存 ID、JOIN 取**。

⚠️ **快照是"列举式白名单"，不是"把主档搬过来"**：只冗余 §11.6.2 那几列，
**白名单之外一律只存 ID**（否则"快照"就成了绕开 ≤25 列红线的借口，旧规的初衷会被架空）。

#### 11.6.2 必快照清单（U2 (b) 推荐集 → **规范列名**，一律沿用既有惯例，不另造一套）

| 语义 | **规范列名** | 来源主档 | 现状（2026-09-22 真库实测） |
|---|---|---|---|
| 主体名称 | `<role>_name`（`customer_name`/`supplier_name`/`seller_name`/`buyer_name`） | `biz_party.party_name` | ✅ 已普及：38 张含 `customer_id` 的表有 **32** 张有；29 张含 `supplier_id` 的有 **26** 张有 |
| 主体编码 | `<role>_code` | `biz_party.party_code` | 🔶 部分（`erp_sale_outbound.customer_code` 有） |
| **税号**（企业=统一社会信用代码，自然人=身份证号） | **`tax_no`**（沿用多数派 11 处，**不要**另叫 `_unified_code`） | `biz_party.unified_code` | 🔶 11 处已有；`erp_purchase_inbound` **缺** |
| 客户/供应商等级 | `<role>_level` + `<role>_grade_code` + `<role>_grade_name` | `biz_party.party_level` / `CustomerGrade` | 🔶 仅销售侧（`sale_order`/`sale_outbound`）有 |
| **对方档案**上的联系人 | `contact_name` / `contact_phone` / `contact_address` | `biz_party_contact` | 🔶 2 张伴生快照表为此形态 |
| **本单收货**信息（≠ 对方档案的联系人，**必须分开**） | `receiver_name` / `receiver_phone` / `receiver_address` | 单据自身 | 🔶 `erp_sale_outbound` 有 `receiver_*`，但地址还叫 `shipping_address`（**历史别名，新表一律用 `receiver_address`**） |
| 银行 | `bank_name` / `bank_account` | `biz_party` | ✅ 2 张伴生快照表有 |
| **税率**（**时点属性**：开票当时是多少就是多少） | `tax_rate`（明细行粒度优先） | 商品/协议 | ❌ **两张主单据都缺**（只有 `tax_amount`/`total_amount_with_tax`，算不出当时税率） |
| **协议版本号**（回答"当时按哪一版"） | `agreement_id` + `agreement_version_no` | 协议模块 | ❌ **全新**（㉛ 要求：只记"当时生效的那一版"，**不许记 `current_version_id`**） |
| **业务发生日** | 域内既有语义名，见 §11.6.4 | 单据自身 | ✅ 基本都有 |

#### 11.6.3 表形态：**两种，二选一，不许第三种**

| 形态 | 何时用 | 依据 |
|---|---|---|
| **① 行内列**（默认） | 快照字段能放进主表（守"主表 ≤25 列"红线） | 现实里 38 张含 `customer_id` 的表，**32 张**已经这么做 ⇒ **规范的正名，而不是另起一套** |
| **② 1:1 伴生表** `<bill>_partner_snapshot` | 快照字段多到会击穿 25 列红线时 | 仓里已有 **2 例**：`erp_sale_order_partner_snapshot` / `erp_purchase_order_partner_snapshot`（列：`*_name`/`*_code`/`contact_*`/`bank_*`/`tax_no`/`region`） |

❌ **禁止第三种：拿一个 JSON 大字段兜底"几个字段的快照"**。
`agreement_version.snapshot_json` 那种大字段是**"一整份文件"的整版快照**（它的语义就是"这一版协议长什么样"），
与"单据上几个外部字段的时点副本"不是一回事，**不要混用**。

#### 11.6.4 业务发生日（业务日期 ≠ 系统日期）

- 单据**必须**有业务日期列；**列名沿用各域既有语义名**（`order_date`/`outbound_date`/`inbound_date`/
  `invoice_date`/`payment_date`/`apply_date`…）—— **刻意不做全表改名**，那本身就是一次全表回填。
- ⚠️ **业务日期 ≠ 凭证日期**：补录、跨期调整时两者不同，拿 `voucher_date` 当起算基准会把账算到错的月份
  （协议账期已按此实现：`CreditTermResult#dueDateFrom` 只认业务日期）。
- ⚠️ **同一张单上会有多个日期列，别认错**：`erp_sale_outbound` 上还有 `payment_date`/`reconciliation_date`，
  它们是"收款/对账"日期，**不是**本单的业务发生日（本单是 `outbound_date`）。
- **跨模块传递**（业财记账）统一用字段名 **`business_date`**（既有 `BusinessAccountingRequest.businessDate`）。

#### 11.6.5 何时写、写完能不能改

- **写**：单据**生效/过账那一刻**写一次，与单据状态变更**同一事务**（拿不到外部值就如实留空，**不许编**）。
- **之后**：**只读**，随单据一起不可变（第三条通用原则）——**改主数据、改协议一律不回写历史单**。
- 因此快照**不在更新接口里维护**：单据一旦生效，快照列的任何写入都是 bug。

#### 11.6.6 存量处置：**不回改** + 两张清单（豁免表 / 存量缺口），都只许缩不许涨

**（一）豁免表：不是"已生效单据"，故 R1/R2/R3 不适用**（`tools/audit-snapshot-spec.cjs` 的 `EXEMPT`）

实测（2026-09-22）：全库含 `customer_id` 的 **38** 张里 32 张有 `customer_name`（84%）、
含 `supplier_id` 的 **29** 张里 26 张有（90%）。**逐张看过缺的那几张，全部不是"已生效单据"**：

| 表 | 是什么 | 结论 |
|---|---|---|
| `erp_balance_log` | 余额变动台账 | 台账，豁免 |
| `erp_customer_product_price` | 客户商品价格档案 | 档案，豁免 |
| `erp_price_memory` | 比价记忆（含 `order_no`/`order_date`） | 过程记录，豁免 |
| `erp_group_buy_participant` | 拼团参与记录（子表） | 父单承载快照，豁免 |
| `invoice_payment_record` | 发票×付款核销关联表 | 关联表，豁免 |
| `mkt_presale_order` | 预售单↔商城单↔客户**关联**（真正单据是它指向的商城订单） | 关联表，豁免 |
| `erp_supplier_performance` / `erp_supplier_points_record` | 供应商绩效/积分台账 | 台账，豁免 |
| `erp_delivery_rating` / `erp_supplier_notification` | 评分记录 / 通知消息 | 非单据，豁免 |
| `batch_number` / `batch_flow_record` | 批次主档 / 流转记录 | 主数据 + 台账，豁免 |

⇒ **在 §11.6.8 登记的"单据主表"上，主体名称快照覆盖率是 100%**（不是"若干处违规"）。
**真正缺的是 U2 里那几类"还没人做过的时点字段"**：**税率**、**协议版本号**、等级/税号在采购侧的缺失。

**（二）存量已知缺口（棘轮基线，**只许缩不许涨**）**
收敛掉一条就从这里删一条；**新增一条 = 放宽规范，必须先在本表写下理由**。

| 表 | 规则 | 缺口 |
|---|---|---|
| `dms_ship_order` | R2 | 配送发货单：只有 `create_time`，无业务发生日（配送域遗留） |
| `dms_settlement` | R2 | 配送结算单：同上 |
| `erp_sale_order` | R3 | 有 `tax_amount` 无 `tax_rate`（税率是时点属性） |
| `erp_purchase_order` | R3 | 同上 |
| `erp_purchase_inbound` | R3 | 同上 |
| `erp_purchase_return` | R3 | 同上 |
| `finance_tax_declaration` | R3 | 纳税申报表：有税额无税率（申报口径，待定） |

#### 11.6.7 可执行检查（规范不是纸面的）

`tools/audit-snapshot-spec.cjs` —— 扫**真库** `information_schema`，输出
① R1 主体名称快照覆盖（全库）+ 豁免清单、② R2 业务日期缺口、③ R3 税率缺口、④ R4 协议版本号覆盖，
并以**退出码**守棘轮：**只有出现清单之外的新违规才 exit 1**（已知存量缺口不算）。

**为什么用"登记制"而不是自动猜"哪些是单据"**：第一版按"有 `_no` 列"自动判定，真库上判出 **80+ 张** ——
明细表 / 台账 / 缓存 / 日志全被卷进来（`wms_pick_detail`、`serial_status_cache`…）。
**一条 80% 误报的检查比没有检查更糟**（会训练所有人忽略它）⇒ 受约束的表**由人显式登记**（§11.6.8）。

⚠️ **写这类脚本必踩的坑**：`tools/sql.cjs` 有**硬上限 500 行且静默截断**。
第一版想"一次把全库 表→列 拉回来"，14146 行被截成前 500 行 ⇒ 只看到 29 张表（真实 568 张）
**而且不报错**，"覆盖率 100%"是假的。⇒ 查询必须收窄，且**命中上限要直接抛错**，绝不静默用截断结果下结论。

#### 11.6.8 受本规范约束的**单据主表**（登记制，新增单据主表必须登记进来）

判据（人判）：**这张表是"一笔业务发生后要留痕、要认当时账"的单据主表**。
明细表 / 台账 / 关联表 / 档案 / 现势表**不登记**（登记了只会制造误报）。

- **销售**：`erp_sale_order` · `erp_sale_outbound` · `erp_sale_return` · `erp_sale_return_doc` · `erp_sale_exchange` · `erp_sale_pre_order` · `erp_retail_order`
- **采购**：`erp_purchase_order` · `erp_purchase_inbound` · `erp_purchase_return` · `erp_purchase_exchange`
- **资金**：`erp_receipt` · `erp_payment` · `erp_pre_receipt` · `erp_pre_payment` · `erp_ar_ap_adjust` · `erp_write_off` · `erp_offset` · `erp_cash_transfer` · `erp_expense_doc`
- **库存**：`erp_stock_in` · `erp_stock_out` · `erp_stock_transfer` · `erp_stock_damage` · `erp_stock_overflow` · `erp_stock_take` · `erp_stock_assemble` · `erp_stock_split`
- **配送**：`dms_ship_order` · `dms_settlement`
- **合同 / 报价**：`crm_contract` · `crm_quotation`

⚠️ **协议（`agreement`）不在此登记表内**：它是**契约**不是单据 —— 它的"时点"是
`effective_from/to` 的**有效期区间**（§13.7），它的快照是一整版
`agreement_version.snapshot_json`（§11.6.3 的第三种形态），与"单据的业务发生日 + 字段快照"不是一回事。

## 十二、协议模块（2026-09-22 用户指令 + 五条落地裁定）

> **用户原话**：「我们应该建立一个**协议模块**，专门处理**租户之间**和**租户与平台之间**的相互协议关系。」
>
> **本节定位**：§3.4.4b~d3 已经裁定过协议的**语义与表结构**（㉑㉒㉓㉖㉘㉛㉜㉝㊲ 等 20 余条），
> 但那些 DDL 一直**停留在文档里、没有模块载体**（零表、零代码、零菜单）。
> 本节是「**把那一层模块化**」的落地方案，不推翻任何既有裁定，只做三处收敛（见 12.2）。

### 12.1 三类协议与"两端"（本节的核心收敛）

| 类 | `agreement_type` | 两端（对称记法） | 依据 |
|---|---|---|---|
| **平台 ↔ 租户**（入驻/服务协议） | `PLATFORM_SERVICE` | （平台主体 + 系统租户 1）↔（租户主体 + 该租户） | §3.4.4e、㉝ 清退权、保证金 |
| **租户 ↔ 租户**（代销/分销/购销框架） | `DISTRIBUTION` / `GOODS_FRAMEWORK` | （party_a, tenant_a）↔（party_b, tenant_b） | §3.4.4b、㉓ |
| **租户 ↔ 消费者**（单方承诺，只能加码） | `CONSUMER_PROMISE` | （租户）↔（不特定消费者） | §3.4.4d3 |

**裁定①（主档统一）** ── **一张 `agreement` 主档 + `agreement_type`**，版本/条款/双签三张子表**全类型共用**。
> 不按类型分表的理由：分表会让「版本不可变」「双签缺一不可」「必填校验」三套不变量各写一遍，
> 而这三条恰恰是㉛/㉜ 里**最贵、最不能各写一遍**的东西。
> 与㉓ 不冲突：㉓ 的真实意思是「**别把三种商务混进 `purchase_contract` 一张业务表**」，
> 统一主档 + 类型化条款正是它的正确形态。
> **连带结论**：`purchase_contract`（V11.439.0 新建）应成为 `GOODS_FRAMEWORK` 的**一种**，
> 而不是并列的第 4 套 —— 归入**阶段 D**（并存期 → 迁移）。

**裁定②（两端对称）** ── 协议两端一律记 `(party_id, tenant_id)` **两列**，取代 §3.4.4b 原 DDL 里
`supplier_party_id` + `distributor_tenant_id` 的**不对称**写法（一端主体、一端租户）。
> 理由：平台协议里甲方是"平台主体 + 系统租户 1"，只有对称结构才能让三类协议**共用一张表**；
> 且司法举证时「**谁代表哪个主体、在哪家店签的**」必须无歧义。

**裁定③（双签形式）** ── v1 = **确认人 + 内容哈希 `sign_hash` + 时间**，**双方痕迹分开存**，
两者都非空才允许 `ACTIVE`（这是"不能单方改"的**技术**保证，不是流程约定）。
第三方电子签章**只留列位、不接**；仓里 `erp_signature_record` 的形态可复用。

**裁定④（推单默认关闭）** ── **不强制先签协议**，但**跨租户推单能力默认关闭**：
只有存在覆盖双方且 `ACTIVE` 的协议时才放行（**fail-closed**）。
协议**未约定**某条款时**不自动执行任何赔偿/扣款**、挂人工 —— 不给平台默认值（㉜/§3.4.4d1）。

**裁定⑤（模块层级）** ── `agreement`（协议）为**租户级**模块，租户可开关；
其中**平台协议**那部分的写权限用 `agreement:platform:*` 隔离并归入「**系统**」模块
（按 V11.455.0，「系统」只开给系统租户）⇒ 平台协议**天然只有平台侧能用**，不必另造机制。

**裁定⑥（主档是系统级，可见性按两端判定）** ── ⚠️ **这条不是新选择，是①+②的必然推论，写下来是因为漏了会让整个模块没意义**：
协议主档 `agreement` 的 `tenant_id` 恒为 **0**（系统级），并登记进 `MyBatisPlusConfig.IGNORE_TENANT_TABLES`；
**谁能看到一份协议，由两端的 `party_a_tenant_id` / `party_b_tenant_id` 显式判定**，
而不是靠租户拦截器自动注入。
> **为什么必须这样**：协议天然跨租户。若给 `agreement.tenant_id` 存"创建方租户"，那么
> 乙方（B 租户）按会话租户过滤后**一行也查不到** —— 一份只有一方看得见的协议，
> 既无法双签、也无法共同执行，模块就白做了。
> **代价与防线**：自动租户隔离在这张表上**不生效**，可见性变成"要自己写对"的东西。
> ⇒ 必须把可见性条件**收敛到一处**（服务层统一的查询构造 / Mapper 统一条件），
> 并在验证脚本里**钉死"第三方租户查不到别人的协议"**这一条。
> 这与设计文档「主体是系统级、租户内只有关系」的立场一致：协议是**主体之间的契约**，
> 租户只是"哪一端的店"。

### 12.2 表（沿用 §3.4.4b~d3 已定名，只做三处收敛）

```
agreement               主档：两端 party+tenant（裁定②）· agreement_type（裁定①）· status
                        · current_version_id · effective_from/to · 平台终止留痕（㉝）
agreement_version       版本快照：snapshot_json NOT NULL，status ∈ DRAFT/ACTIVE/SUPERSEDED/REJECTED
                        ⚠️ 一旦 ACTIVE ⇒ snapshot_json 禁止 UPDATE；改协议只能新建 DRAFT 版本（㉛）
                        双方确认痕迹分开存，两者都非空才允许 ACTIVE（§3.4.4d2）
agreement_term          条款 = 从字典选的选项 + 参数 + 双签（UNIQUE(agreement_id, term_code)）
agreement_term_option   平台字典：term_code / option_code / semantics / required
                        ⚠️ 刻意**没有** default_option —— 平台给默认值就是替双方决定（㉜）
agreement_item          协议下商品：commission_rate / seller_price / price_floor / stock_mode
agreement_quota         额度（stock_mode = ALLOCATED 时用）
```

**三处收敛（相对 §3.4.4b~d3 的 DDL）**：
1. `distribution_agreement` → **`agreement`**（主档统一），`distribution_agreement_term` → `agreement_term`；
2. 两端由不对称改为**对称** `(party_id, tenant_id)` 四列（裁定②）；
3. `agreement_version` 采纳 §3.4.4d2 的 `supplier_confirmed_*` / `distributor_confirmed_*` 命名精神，
   但按对称口径改名为 `party_a_confirmed_*` / `party_b_confirmed_*`。

**三条不变量落到结构上（不是注释里写一句）**：
已生效版本只读 · 双签缺一不可 · 必填条款没选完不许 `ACTIVE`。

### 12.3 模块载体（**用户 2026-09-22 裁定：独立成模块**）

> **用户原话**：「协议还是**独立成模块**吧！」
> —— 于是协议**不在 `core-api` 里开一个包**，而是作为**独立 Maven 模块** `backend/agreement`
> （`groupId cn.aiedge.agreement` / `artifactId agreement` / 根包 `cn.aiedge.agreement`），
> 与 `crm` / `wms` / `dms` / `hr` 同构。
>
> **独立成模块要多接四处线，缺一处就是"没装配"**：
> ① 根 `backend/pom.xml` 的 `<modules>` 加 `<module>agreement</module>`；
> ② 根 pom 的 `<dependencyManagement>` 加该模块条目（版本用 `${project.version}`，子模块不写版本）；
> ③ `core/api/core-api/pom.xml` 声明依赖（不写版本，由父管理）；
> ④ `AiReadyApplication.scanBasePackages` 加 `cn.aiedge.agreement`
> （⚠️ 漏了第 ④ 条的症状是"页面空白 / 端点 404"，本仓实踩过）。
>
> 另外：`tools/build-backend.sh` 的 `MODULES` 默认只含核心三模块，
> **改了 `agreement` 就必须显式把它写进 `MODULES`**，否则 core-api 打包会从本地仓库取到旧 jar。

**菜单挂载点（用户 2026-09-22 裁定）** ── 「**租户级的协议从设置-协议契约分组进，系统级的协议从系统-协议契约分组进**」，
**后端独立模块与前端分组并不矛盾**。

> **这条澄清了一件我先前混在一起的事**：
> **模块（Maven 模块 / 权益边界）≠ 菜单挂载位置（导航边界）**。前者决定"代码住哪、按模块开关"，
> 后者决定"用户从哪点进去"。两者可以不一致，而且在本仓**本来就不一致**（`erp-stock` 里装的是
> `/api/erp/product/*`、`/api/erp/md/*` 的控制器）。
>
> **落地方式**（不新建一级菜单）：

| 谁 | 挂在哪 | 分组 | 叶子 | `client_type` |
|---|---|---|---|---|
| **租户级**协议（租户↔租户 / 租户↔消费者） | 「设置」(60012) | 「协议契约」 | 协议列表 | `tenant-admin` |
| **平台级**协议（平台↔租户）+ 条款字典维护 | 「系统」(60013) | 「协议契约」 | 平台协议 / 条款字典维护 | `system-admin` |

> **⚠️ 为什么 `client_type` 这两行是硬隔离**：`SysMenuServiceImpl#getAllMenusForSystemAdmin()`
> 查的是 `client_type IN ('tenant-admin','system-admin')` ⇒ **超管同时看到两棵树，普通租户只看 `tenant-admin` 那棵**。
> 也就是 `client_type` **本身就是"平台 / 租户"的分隔机制**，比单靠 `agreement:platform:*` 权限码更硬
> —— 平台协议页由此拿到**两道独立的门**（树的分流 + 码的归属）。
>
> **⚠️ 命名随树而不同**：目录层 menu_code 在「设置」树是 `mega:set:*`、在「系统」树是 `mega:sys:*`
> （**不是** `mega:system:*`）。

## 十三、协议模块（二）：成立过程、可执行内核、生命周期与维权边界

> **本节与 §十二 的关系**：§十二 定的是**地基**（主档 / 版本不可变 / 双签 / 条款字典 / 模块与菜单载体）；
> 本节定的是**契约怎么成立、怎么影响生意、怎么结束、出事谁来管**。
> 触发：用户 2026-09-22 三轮口述 ——
> ①「发起契约 → 通过二维码或连接**保证另一方唯一收到** → 对方确认/修改/签署 → **多轮协商** → 签署后形成版本；
>   有有效期与违约责任；还要有**维权、终止（单方终止执行但不代表不违约）、阶段修改**」；
> ②「契约既有**文字版**，又有通过设定**改变双方物流、钱流、货流**的**字段设定版**」；
> ③「维权：平台**只根据双方设定的、可以通过程序的部分自动执行**；产生纠纷**只提供双方协议及交易记录**，
>   超出平台能力的**他们通过司法自行解决**；平台**合规抽查读权限需要有**（避免非法交易）」；
> ④「履约方式双方**也可以通过协议订**，协议可以约定**不同的履约方式并存**，这才是真实交易」。

### 13.1 契约有两条腿，而第二条腿是**运行时配置**，不是文档

| | 是什么 | 系统怎么对待它 | 举例 |
|---|---|---|---|
| **字段设定版** | **可执行的运营内核** | **被下游链路直接消费**（订单路由 / 发货 / 库存 / 定价 / 结算 / 开票 / 风控） | 履约方式、库存模式与额度、授权区域、结算周期与账期、佣金率、售价与底线价、抽成承担方、开票方、信用额度 |
| **文字版** | 权责与举证 | **不解析、不自动执行**，只双方确认 + 哈希留痕 | 争议解决与管辖、保密、不可抗力、特别约定、违约责任的具体文字表述 |

> ⚠️ **这是本节最容易做错的地方**：把"字段设定版"当文档存下来就结束了 —— 那样的契约**不发生任何作用**，
> 只是又一份 Word。字段设定版**必须被下游消费**才成立（§13.3 的"字段 → 消费方"表与断言就是为它立的）。

### 13.2 字段设定版的**三种消费时机**

| 类 | 何时被消费 | 字段 | 消费方 |
|---|---|---|---|
| **运营设定** | 下单 / 发货 / 结算**每次** | 履约方式**集合**、库存模式与额度、授权区域、结算周期、账期（**有向**）、佣金率、售价与底线价、抽成承担方、开票方、信用额度 | 订单路由、发货单生成、库存扣减点、可售量校验、定价引擎、应收应付到期日、结算分账、发票生成、下单风控 |
| **后果设定** | **出事时**才消费 | 取消承担与费率、退货路径与退货运费、正向运费承担、质量责任归属、**违约金比例与上限** | 取消 / 退货 / 理赔流程、保证金扣罚。**每一条执行都必须引用"当时生效版本"里的该字段**；**未约定 ⇒ 不自动执行、挂人工**（㉜） |
| **文字条款** | **永不自动执行** | 争议解决与管辖、保密、不可抗力、特别约定、违约责任文字 | **无消费方** —— 只做双方确认 + 哈希留痕，供举证。⚠️ 界面必须**显式告知**"此类条款系统不会自动执行，需人工处理"，否则用户以为系统会按它扣钱 |

### 13.3 `AgreementRuntime`：读取生效设定的**唯一入口**

```
AgreementRuntime.resolve(卖方主体, 买方主体, 租户对, 业务时点) → 该时点生效那一版的设定集
```

- **必须带业务时点**（㉛ 定的是"下单时刻生效的那一版"）—— 不许读"当前版本"了事，
  否则改协议会**篡改已发生交易的口径**。
- 某个字段**未约定**时 ⇒ 返回"**未约定**"而**不是默认值**；下游据此**拦下并明确报错**
  （例：「本协议未约定账期，无法生成应收到期日」）。这就是㉜「未约定就不自动执行」落到**字段级**。
- ⚠️ **每个字段必须有消费方**。要有一张「**字段 → 消费方**」表（落成脚本可断言的形式）。
  > **为什么单列这一条**：本仓最贵的历史包袱恰恰是"配置界面能勾、勾了不生效" ——
  > 游客浏览开关的两个字段零消费、`sys_user_data_scope` 配了不生效、`sys_permission.api_path` 只填一半……
  > **没有消费方的字段不许进设定版。**

**§13.3 的三条补充口径（2026-09-22 实施时确定；第 3 条为用户裁定）**：

1. **时点挑选必须把"曾生效"算进去**（`ACTIVE` **与** `SUPERSEDED` 都算曾生效，`DRAFT`/`REJECTED` 排除）。
   > 只认 `ACTIVE` 会有一个反效果的 bug：新版本生效时旧版本被置 `SUPERSEDED`（唯一索引只容一行 ACTIVE），
   > 于是**回看历史时取不到当时那一版** —— 恰好违反 ㉛「不许篡改已发生交易的口径」。
   > 这是**加强**而不是放松：区间内优先 ACTIVE，再取版本号最大。
2. **「必填设定」不阻断签署，阻断的是「使用」**。
   > 责任划分类的**必填条款**（`agreement_term_option.required`）没选完**不许 ACTIVE**（㉜，已实现）。
   > 但**设定字段**的 `required` **不设成生效硬门**：某类协议未必用得到某个设定，
   > 强制在签署前填反而变成"平台替双方决定要先约定什么"。
   > 正确的落点是**消费时拦下**：`AgreementRuntime.require(key, usage)` 在该字段为
   > `UNDECLARED` 时抛中文业务异常（例：「本协议未约定账期，无法生成应收到期日」）。
   > ⇒ 口径一句话：**签得下来，但用不了；要能用，先约定。**

3. **⚠️ 「结算方式」决定有没有账期这回事；账期天数是它的**条件必填****（2026-09-22 用户四轮裁定 —— **第 4 轮点明前几轮说的是两层，不是互相推翻**）

   > **用户原话（第 1 轮）**：「协议不约定账期应该就**提交不了**才对！走**无协议无特定客户模式**才对。」
   > **用户原话（第 2 轮）**：「**无协议或者协议到期**走无协议无特定客户模式」
   > **用户原话（第 3 轮）**：「**有协议有约定走协议模式，无协议或者协议到期，或者协议无约定的走无协议无特定客户模式**」
   > **用户原话（第 4 轮，纠正我把两层混成一层）**：「**我说的是 2 个事情**，如果协议约定是**账期结账模式**，
   > 不约定账期肯定就**提交不了**！如果协议约定是**现金**就没有账期的事情啊！如果约定的是**滚结**也没有账期问题啊！」

   ⚠️ **三轮的关系（关键 —— 误读会做出两个都错的实现）**：前两轮**不是互相推翻**，而是**各说了两层中的一层**：

   | 轮次 | 实际说的是哪一层 | 结论 |
   |---|---|---|
   | 第 1 轮「不约定账期 ⇒ 提交不了」 | **第 2 层**：已约定「账期结算」，但没填天数 | **提交不了**（条件必填缺失）✔ 成立 |
   | 第 2 / 3 轮「无协议 / 到期 / 无约定 ⇒ 走无协议模式」 | **第 1 层**：连「结算方式」都没约定，或压根没协议、协议到期 | 走无协议无特定客户模式 ✔ 成立 |
   | 第 4 轮「我说的是 2 个事情」 | 点明上面两行**是两层、不是互相推翻** | 统一为「先判第 1 层、再判第 2 层」 |

   ⇒ **它们是"先判第 1 层、再判第 2 层"的关系**。v3.10 曾据此把第一轮整体作废，**本条予以恢复**：
   第一轮在"账期结算但缺天数"这一格上是对的。

   **⚠️ 本仓现状（实测，这就是病根）**：字段字典 `agreement_setting_def` 里**根本没有「结算方式」这个字段** ——
   现有的是 `SETTLEMENT_CYCLE`(结算周期, DURATION) / `AR_CREDIT_DAYS`(账期天数, NUMBER) /
   `AR_CREDIT_PROVIDER`(账期方向, ENUM) / `CREDIT_LIMIT`(信用额度, NUMBER)。
   而 `AgreementCreditTermProvider` **一上来就问 `AR_CREDIT_DAYS`** ⇒
   **协议约定"现金结算"时它照样报"未约定账期"**。这正是用户第三轮指出的毛病。

   **判定表（唯一口径，逐层判）**

   **第 1 层 —— 这份单据按哪套口径走？**

   | # | 情形 | 走哪套 | 状态 |
   |---|---|---|---|
   | 1 | **无协议**（散客 / 有客户但双方之间没有协议） | 无协议无特定客户模式 —— **默认现金 / 现款现结** | `NO_AGREEMENT` |
   | 2 | **协议已到期**（业务时点超出 `effective_to`） | 无协议无特定客户模式 —— **默认现金 / 现款现结** | `NO_AGREEMENT` |
   | 3 | **有协议但没约定「结算方式」** | 无协议无特定客户模式 —— **默认现金 / 现款现结** | `NO_AGREEMENT` |
   | 4 | **有协议且约定了「结算方式」** | **协议模式** ⇒ 进第 2 层 | — |

   > ⚠️ **「没约定结算方式 ⇒ 默认现金 / 现款现结」的依据**（用户第 5、6 轮补充）：
   > 第 5 轮：「如果协议没有约定结算方式，**默认肯定是走现金或者现款现结的无特定客户模式**了。」
   > 第 6 轮：「**无协议、无特定客户的模式肯定是走现款现结的低风险模式了，这就是真实生意的情况**。」
   >
   > **为什么这个默认成立、且不违反 ㉜**（三条）：
   > ① **现款现结是风险最低的结算方式** —— 钱货两清、**零信用敞口**；
   >    而赊销（账期）是**主动承担信用风险的特殊安排**。所以"没有约定"时退回到**风险最低**的那一端，
   >    是**自然的缺省**，不是平台替双方做商业决定。
   > ② **这是真实生意的常态**（用户原话："这就是真实生意的情况"）：一手交钱一手交货是商业的**基本盘**，
   >    有协议、有账期反而是**少数与特殊**。㉜ 真正禁的是**平台替双方编商业条款**（例如凭空给 30 天账期）——
   >    那才是"替双方决定"；而「不约定 ⇒ 不赊账」是把默认落在**无需任何参数、无任何信用敞口**的一端，
   >    性质完全不同。
   > ③ 因此 **无协议 / 协议到期 / 有协议但没约定结算方式 ⇒ 一律现款现结**，
   >    到期日 = 业务日（**当天结清，不产生应收账款账期**）。

   **第 2 层 ——（仅第 4 行进入）约定的结算方式是哪一种？**

   | 结算方式 | 账期天数 | 结果 |
   |---|---|---|
   | **现款现货 · 先款后货** | **不需要** | 放行；**款在发货前收**（对卖方零风险）⇒ 通常**不产生应收** |
   | **现款现货 · 现款现结** | **不需要** | 放行；钱货同时 ⇒ **到期日 = 业务日** |
   | **现款现货 · 货到付款** | **不需要** | 放行；货先到、款后付 ⇒ **到期日 = 到货日**（可能晚于业务日） |
   | **滚结**（滚动结算） | **不需要**（无固定账期） | 放行；按滚结规则处理 |
   | **账期结算** | **必须约定** | 约定了 ⇒ 到期日 = **业务日 + N 天** |
   | **账期结算** | **没约定** | ⚠️ **提交不了**（条件必填缺失 —— 第一轮说的就是这一格） |

   > ⚠️ **「现款现货」不是一种，而是三种**（用户第 7 轮）：
   > 「**现款现货也有好几种，先款后货，现款现结，货到付款**。」
   >
   > 三者**都属于"无账期"**（因此都不需要填账期天数），但**资金与货物的先后不同**，
   > 对**流程**与**到期日**的含义也不同 —— **不许把它们压成一个笼统的"现金"**：
   >
   > | 方式 | 资金 / 货物先后 | 到期日 | 风控含义 |
   > |---|---|---|---|
   > | **先款后货** | 款在发货**前** | 通常**不产生应收** | 对卖方**零风险** |
   > | **现款现结** | 钱货**同时** | **业务日** | 最常见的零售形态 |
   > | **货到付款** | 货在付款**前** | **到货日** | 卖方承担**极短期**在途敞口 |
   >
   > 压成一个值会同时丢掉两样东西：**"货到付款"算不出到货日**、**丢失风控含义**。

   > **一句话**：**先看有没有约定「结算方式」；现金与滚结压根不问账期天数；只有「账期结算」才要求填天数，缺了就不许提交。**

   **三条铁律**：

   - **① 「结算方式」是账期的前置字段**。没有它，系统不知道这笔账按现金、滚结还是账期走 ——
     **不许跳过它直接问"账期天数"**（现行 `AgreementCreditTermProvider` 就是这么错的）。
   - **② 账期天数是**条件必填**：仅当结算方式 = 账期结算时必填，缺 ⇒ 拦在提交处**。
     这是第一轮"提交不了"的准确含义，**不是**"任何字段没约定都按无协议模式放行"。
   - **③ 四种情形必须可分辨**：「从无协议」「协议到期」「有协议但没约定结算方式」「约定了账期却没填天数」
     是**四种不同情形** —— 前三种走无协议模式，**第四种拒单**。不许用一个含糊 fallback 全接住。

   **对实现的直接要求**：

   - **① 字段字典要新增「结算方式」**（`agreement_setting_def`）：建议 key `SETTLEMENT_TYPE`、
     `value_type=ENUM`。**选项至少五项**（用户第 7 轮把"现款现货"拆成三种）：
     `CASH_PREPAY`(现款现货·先款后货) · `CASH_SPOT`(现款现货·现款现结) · `CASH_ON_DELIVERY`(现款现货·货到付款)
     · `CREDIT`(账期结算) · `ROLLING`(滚结)。
     ⚠️ **本节建议保持"扁平枚举"**（一次下拉选到底），把"是否需要账期天数 / 是否现款类"
     **写在枚举的语义上**供第 2 层判定直接读取；**不要为了体现层次而拆成两个字段** ——
     拆了会让"没选第二个"变成一种**新的"未约定"态**，又得再定一遍它归哪层。
     **现有 21 项里没有它**，不加则第 1 层无从判定。
   - **② `AgreementCreditTermProvider` 的判定顺序要改**：**先取「结算方式」，再决定是否取「账期天数」**。
     · 无协议 / 已到期 / 结算方式未约定 ⇒ `NO_AGREEMENT` ⇒ 走无协议模式
     · 结算方式 = 现金 / 滚结 ⇒ **不再去问账期天数**，返回"本笔无账期"的结论（到期日 = 业务日）
     · 结算方式 = 账期 ⇒ 再取 `AR_CREDIT_DAYS` + `AR_CREDIT_PROVIDER`；**天数缺 ⇒ 拒单**
       （**不是** `UNDECLARED` 放行、**不是**留空挂人工）
   - **③ `CreditTermResult` 需要能表达"本笔没有账期这回事"**（现金 / 滚结）——
     它与"协议未约定账期"**不是一回事**：前者是**正常的业务结论**，后者是**配置缺项、要拒单**。
     现行三态（`AGREED` / `NO_AGREEMENT` / `UNDECLARED`）**不够用**，需按此扩充；
     如何命名由实现定，但**语义必须在枚举上写死**、且**不许用 null 代替状态**。
   - **④ `BusinessAccountingServiceImpl`**：`UNDECLARED`（账期结算缺天数）的处置**既不是"留空挂人工"、
     也不是"走无协议模式"**，而是**拒绝这笔单据提交** —— 这是第一轮的准确含义。
   - **⑤ 无协议无特定客户模式的默认口径 = 现金 / 现款现结**（用户第 5 轮裁定）⇒
     **无账期**（到期日 = 业务日，不赊账）。
     ⚠️ **这与现行 `PLATFORM_DEFAULT_CREDIT_DAYS = 30`（默认 30 天账期）直接冲突** ——
     采购 / 销售两处的 30 天是协议模块之前的历史行为，按本条口径**应改为"现金 / 现款现结、无账期"**；
     若因存量影响大而暂留，必须在代码里显式写明"与 §13.3 第 1 层默认口径冲突"并登记待办，
     **不得默认视为合规**。该常量**绝不覆盖协议模式下的任何结论**（包括"现金 ⇒ 无账期"）。
   - 单据**最终提交处**要保证：**四种情形都能得出结果**（要么协议、要么标准口径），
     **不存在"因为协议缺项所以提交不了"这条路径**。

   ⚠️ **需要一并改的现有验收口径**（实施方注意：别拿旧断言把新行为判成红的）：

   - `tools/verify-credit-term.cjs` 第 **⑤** 组现断言「有协议但未约定账期天数 ⇒ 到期日**留空**、单据照开」——
     按本口径要**拆成两种情形分别断言**：
     · **结算方式未约定** ⇒ 走无协议模式口径，**单据照开**
     · **结算方式 = 账期、但天数没填** ⇒ **提交被拒**
   - `erp-finance` 的 `CreditTermDueDateWiringTest#undeclaredLeavesDueDateEmptyAndDoesNotBlock`
     （断言 `assertNull` + `assertDoesNotThrow`）要改 —— 它现在把"账期结算缺天数"当成了"不阻断"。
   - **缺三组新断言**（目前一个都没有）：
     · **协议到期后**单据仍能提交、且走无协议模式口径
     · **结算方式 = 现金 / 滚结** ⇒ 单据正常提交、**且不报"未约定账期"**（用户第三轮点名的毛病）
     · **结算方式 = 账期、天数没填** ⇒ **提交被拒**

| **多轮协商** | 一串 DRAFT 版本 = **协商时间线** | 现行生效版本在协商期间**继续有效**（㉛：谈成之前交易照常） |

### 13.5 **唯一送达**（"保证另一方唯一收到"的技术形态）

`agreement_invite` 的 token 绑定五件事：**目标主体 + 目标租户 + 目标文稿版本 + 时效 + 一次性**。

- 打开链接的人**必须先登录**；其**会话租户**与**所代表主体**与目标**匹配**才放行，
  否则给明确提示「**这份契约不是发给你的**」；
- **转发给别人打不开** —— 这正是"唯一收到"的落地；
- 留痕：谁、何时、通过哪个渠道（二维码/链接）领取或查看了它；
- 过期 / 被发起方撤回 / 已使用 ⇒ 立即失效。

> ⚠️ 仓里**没有**可复用的邀请机制（实测：`mkt_share_record` 是营销分享、`erp_signature_record` 是签名台账，
> 语义都不对）⇒ 这一层必须新建，**不要**拿营销分享表凑。

### 13.6 签署：**自然人代表主体**

签署记录必须是「**谁**（自然人）· **代表哪个主体** · **在哪个租户** · **凭什么代表**（授权依据）· 签了哪一版 · 何时 · 签章哈希」。

> 只记一个 `tenant_id` 或账号 ID 是不够的：司法上要回答的是"**谁签的、凭什么代表这家公司**"。
> 这条接 R1（自然人×往来单位）与你已定的 ㉟ 授权范围与限额（G13）。

### 13.7 有效期、阶段修改、终止

- **有效期**：`effective_from` / `effective_to` + 到期提醒 + 续签（续签 = 又一次签署动作）。
- **阶段修改**（履约中变更）：只能"**新版本 + 双方签署**"，且**不追溯**已发生的单据与结算（第三条通用原则）。
- **终止**：五种来源 —— **协商一致 / 自然到期 / 单方终止 / 因对方违约 / 平台清退**（㉝）。
  ⚠️ **终止 ≠ 免责**（用户强调）：单方终止只记录「**停止履行**」这个**事实**；
  系统**不自动结清、不自动免责**，是否违约、赔多少走 §13.8。
  **数据上要能反证**：终止记录里**不得有任何**"责任已了结"语义的字段。

### 13.8 维权边界：**平台不裁判**

| 平台**做** | 平台**不做** |
|---|---|
| 按双方**设定的、程序可执行的部分自动执行**（扣保证金 / 计违约金 / 冻结额度） | ❌ **不认定"谁违约"** |
| 提供**双方协议快照 + 交易记录**作为证据（可导出、可举证） | ❌ **不判赔多少** |
| 超出平台能力的 ⇒ 标记「**需司法解决**」并留痕、不阻断其余流程 | ❌ 不替双方调解 / 裁决 |

> **推论（很重要）**：本模块**不需要"判责引擎"**。需要的是
> ①**可执行条款的自动执行**（依据**必须**来自双方设定，不得由平台自创规则）
> ②**证据包的完整可导出**（全部版本快照 + 相关交易记录）。
> ⚠️ 这条同时是**责任边界**：平台一旦开始"认定违约"，就从"提供工具"变成了"做裁判"，
> 既越位（与 §6.3 平台角色三句话冲突），也把自己拖进本该由司法解决的事里。

**⚠️ 但要保留「平台内裁决」这个能力（用户 2026-09-22 补充）**：
> 「原则上是维权我们平台不参与，但如果**司法要求平台履行平台监管责任**，估计也可能**平台内裁决**，
> **要保留这个能力**。」

设计口径 = **留口子，但默认不越位**（同 §7.1 G7 保理"留口子、v1 不做"）：

| 要点 | 落地方式 |
|---|---|
| 默认**只有**两条路 | 争议记录的 `resolution_channel` ∈ `SELF_NEGOTIATION`（双方自商）/ `JUDICIAL`（司法）；**默认只能是这两条** |
| `PLATFORM_RULING` **不默认可用** | 必须由平台侧**显式启用**（开关 / 授权动作），且**必须填写触发依据**（司法或监管要求：文书 / 工单 / 监管函编号）⇒ **没有依据就开不了这张口子** |
| 裁决依据**仍不是平台自创** | 裁决书必须标明依据来源：`AGREEMENT_TERM`（双方约定）/ `PLATFORM_RULE`（入驻时已同意的规则，㉝）/ `STATUTE`（法定规则） |
| 裁决**可申诉** | 与㉝ 平台清退权同口径：留痕 + 可申诉 |
| **执行通道只有一条** | 自动执行仍然只执行"双方设定的、程序可执行的部分"；裁决产生的执行走**同一个执行通道**，但依据字段不同（`ruling_id` 而非 `setting_key`）⇒ **"谁让它扣的这笔钱"永远可追溯** |

> **为什么这样留口子**：把平台裁决做成**外挂的、默认关闭的、依据可追溯的**能力 ——
> 将来司法/监管真要求时能立刻启用；而在此之前，平台**不主动**判定任何人违约，责任边界不破。
> ⚠️ 实现时**不要**为了"留口子"提前把裁决逻辑写进自动执行链路里（那等于默认越位）。

### 13.9 契约模板

- **平台模板**（全员可选）与**租户模板**（本租户内可选）；
- **平台拥有合规抽查读权限**（用户 2026-09-22 明确需要，目的：**避免非法交易**）；
  ✅ **2026-09-22 已落地**（`V11.493.0`）：**独立权限码 `agreement:platform:compliance:read`**
  （前缀 `agreement:platform:` 归「系统」模块 ⇒ 按 V11.455.0 **天然只有平台侧能拿**），
  端点 `GET /api/agreement/platform/compliance/page` 与 `/{id}`，各带 `@OperLog` **留痕**。
  ⚠️ 它**不是**租户级 `agreement:view` 的复用：协议正本是**任意两个租户之间的商业契约**，
  与"平台模板"敏感级别完全不同。放宽可见性的那一句仍然只写在
  `AgreementVisibility#applyPlatformCompliance`（"唯一构造处"的纪律不破）。
- 模板是**显式选择的起点**，**不是自动套用的默认值**（否则等于平台替双方定商业条款，㉜）；
  模板可预填，但 `required=true` 的条款**仍必须由双方在"本次这一版"上显式确认**；
- 版本快照**记录模板来源**（"基于模板 X"）⇒ 司法可追溯；
- 模板**同样过合法审核**（㊲，`legal_review_status`），违法条款无效；
- ⚠️ **绝不允许**"模板里有 ⇒ 视为已约定"。**约定只以双方签署的那一版为准。**

### 13.10 履约方式：协议可约定**多种并存**

`fulfillment_mode` 落在**协议**上，且是**集合**（同一份合作协议可以同城直发、异地中转并存 —— 用户明确要求）。
下单时在该集合内确定具体方式（订单行粒度），并记录**是谁定的**（规则 / 人工）。
