## 1. 页面概述

本页是**商机阶段推进工作台**：把区域内的商机按阶段排开，让销售/主管**就地推进阶段、判赢单、判输单**。它**不是**阶段字典维护页（见 §1.1）。

| 页面 | 地址 | 组件 | 行数 | 说明 |
|------|------|------|:----:|------|
| 商机阶段（本页） | `crm/opportunity-stage` | `views/crm/opportunity-stage/index.vue` | 282 | 11 列表格 + 3 个行内动作（推进/赢单/输单）+ 赢单/输单两个弹窗 |
| 商机（兄弟页） | `crm/opportunity/index` ↔ `crm/opportunity/form` | `views/crm/opportunity/{index,form}.vue` | — | 商机台账：管道/列表/统计**三视图**，含拖拽改阶段、新增商机 |

> **双入口方向提醒**：本页是**单入口**（`display_mode = 0`、`list_path = null`、`tag_label = null`），**没有配对标签页**。这与「客户/线索/商机/合同」（主 path 指向列表页、标签指向表单页）以及「报价单/发票」（主 path 指向表单页、标签指向列表页）**都不同 —— 本页两者皆无**。

### 1.1 「商机阶段」不是阶段字典维护页（重要定性）

| 期望职责（按菜单名） | 实际实现 |
|---|---|
| 维护阶段主数据：阶段名、序号、赢单概率、是否成交阶段 | ❌ **完全没有**。阶段与概率**硬编码在前端**（`:137-145`）与**后端 switch**（`CustomerOpportunityServiceImpl.java:221-241`） |
| 配置阶段级规则（推进条件、必填项、审批要求） | ❌ 无 |
| 阶段推进 / 赢单 / 输单 | ✅ **本页唯一真实能力**（3 个行内动作全部真实接口，**零桩**） |

**配置表不存在**：全库 `crm%` 表实测 22 张（`crm_contract`、`crm_contract_attachment`、`crm_contract_change`、`crm_contract_clause`、`crm_contract_payment`、`crm_customer`、`crm_customer_follow_up`、`crm_customer_lead`、`crm_customer_opportunity`、`crm_customer_pool`、`crm_erp_customer_mapping`、`crm_marketing_campaign`、`crm_marketing_channel`、`crm_marketing_content`、`crm_marketing_execution`、`crm_marketing_target`、`crm_quotation`、`crm_quotation_item`、`crm_quotation_template`、`crm_quotation_template_item`、`crm_visit_plan`、`crm_visit_record`）—— **没有 `crm_opportunity_stage`**，即阶段字典**无任何持久化载体**。

> **业界对照**：Odoo `crm.stage` 是可维护主数据（`sequence` 排序 / `probability` 赢率 / `is_won` 是否成交阶段 / `fold` 管道折叠），由管理员维护，销售管道直接读取。「商机阶段」这个菜单名**正是它应有的挂载点**，当前只做了「推进工作台」。

### 1.2 阶段值域在本模块内**有三套**（P0）

| 来源 | 值域 | 证据 |
|------|------|------|
| **本页** | **数字 1–5**：初步接触/需求确认/方案报价/商务谈判/成交 | `opportunity-stage/index.vue:137-145` |
| **商机列表页** | **字符串 key**：`lead / qualification / proposal / negotiation / closing / won / lost` | `opportunity/index.vue:1076,1114-1118,1146` |
| **商机表单页** | **数字 1–6**：1–4 同上，**5 赢单 / 6 输单** | `opportunity/form.vue:44-53` |

**后端只有一套**：`CustomerOpportunity.opportunityStage` 是 `Integer`，`getStageDesc` 为 `1 初步接触 / 2 需求确认 / 3 方案报价 / 4 商务谈判 / 5 成交`（`CustomerOpportunityServiceImpl.java:221-230`）—— **与「本页」一致**。

**后果**：① 本页传数字 → 后端正确过滤 ✅；② 商机列表页传字符串 key → 后端 `Integer opportunityStage` 反序列化失败或 `opportunity_stage = 'qualification'` 类型不匹配 → **查询报错或恒空**；③ 商机表单页把 `5` 标成「赢单」、`6` 标成「输单」，而本页与后端把 `5` 理解为「成交」、赢单/输单走 **`status` 字段**（2/3）→ **表单页把「赢单/输单」错当成阶段值**。

## 4. 表单页配置

> 本页**没有独立表单页**。等价形态是 **1 个二次确认（推进）+ 2 个动作弹窗（赢单/输单）**。三个动作的对象都是**已存在的商机**，**没有新增场景**（新增在兄弟页 `crm/opportunity/form`）。

### 4.1 推进（`Modal.confirm`）

| 项 | 实现 | 证据 |
|----|------|------|
| 触发 | 行「推进」 | `:36-43` |
| 禁用 | `!isActive(record) \|\| (record.opportunityStage ?? 0) >= 5` | `:39` |
| 标题 | `推进商机阶段` | `:209` |
| 内容 | `` `确定将商机「${record.opportunityName}」推进到下一阶段（${STAGE_TEXT[(record.opportunityStage ?? 0) + 1]}）吗？` `` | `:210` |
| 按钮 | ok `确定` / cancel `取消` | `:211-212` |
| 调用 | `opportunityStageApi.advance(record.id)` | `:215` |
| 成功 | `message.success('商机阶段已推进')` → `reportRef.value?.reload()` | `:216-217` |
| 失败 | `message.error(e?.message \|\| '推进失败')` | `:218-220` |

`isActive(record) = record.status !== 2 && record.status !== 3`（`:166-168`）→ **赢单/输单后的商机不能再推进**。

> **文案缺陷（P2）**：确认文案的「下一阶段」由前端 `STAGE_TEXT[(stage ?? 0) + 1]` 自行推算。`stage = 5` 时取 `STAGE_TEXT[6]` = `undefined`（但按钮已被 `>= 5` 禁用，不可达）；`stage = 4` → `STAGE_TEXT[5] = '成交'` ✅；`stage = null` → `STAGE_TEXT[1] = '初步接触'` ✅。**结论：可达路径上正确，但依赖了「阶段非空」这一未强制前提** —— 后端并不保证非空（§7.1）。

### 5.1 阶段与状态值域（本页口径，与后端一致）

### 5.2 阶段推进规则

| 规则 | 实现 | 证据 |
|------|------|------|
| 只能逐级 `+1`，不能跳级 | `nextStage = currentStage + 1` | `:114` |
| 到顶拦截 | `currentStage >= 5` → 400「商机已处于最终阶段」 | `:110-112` |
| 概率自动联动 | `10 / 30 / 50 / 70 / 100` | `:232-241` |
| 阶段说明同步 | `opportunityStageDesc = getStageDesc(nextStage)` | `:116` |
| 已删除商机不可推进 | `getDeleted() == 1` → `notFound` | `:105-107` |

> **`deleted` 空值风险（P1）**：`opportunity.getDeleted() == 1` 是 `Integer` 的 **`==` 拆箱比较**；`crm_customer_opportunity.deleted` 实测 `is_nullable = YES`（默认 `0`，历史行可能 `NULL`）→ **为 `NULL` 时 NPE → 接口 500**（`:105,130,151` 三处同型）。
> **`opportunity_stage` 空值风险（P1）**：`int currentStage = opportunity.getOpportunityStage();`（`:109`）是**强转 int**；该列实测 `is_nullable = YES`、`column_default = null` → **阶段为空的商机点「推进」必 500**。而前端禁用条件 `(record.opportunityStage ?? 0) >= 5` 在 `null` 时判为**可点**（`0 >= 5` 为假）→ **前端禁用逻辑与后端强转假设不匹配**。

### 5.3 赢单 / 输单规则

| 规则 | 赢单 | 输单 |
|------|------|------|
| 前置状态 | 无（`isActive` 即 status ∉ {2,3}） | 同左 |
| `status` / `statusDesc` | `2` / `赢单` | `3` / `输单` |
| `opportunity_stage` | 强制 `5` | **不改** |
| `probability` | `100` | `0` |
| `actual_close_date` | 今天 | 今天 |
| 业务字段 | `actual_amount = actualAmount` | `lose_reason = loseReason` |
| 幂等性 | ✅ 实际不可逆（输单后 `status=3` → `isActive` 为假 → 按钮禁用） | 同左 |
| 并发保护 | 实体有 `@Version private Integer version`（`entity/CustomerOpportunity.java:69-70`），`advanceStage` 传的是 `selectById` 的整实体 → **乐观锁生效** ✅ | 同左 |

> **⚠️ 口径不一致（P1）**：赢单把 `opportunity_stage` 推到 `5 成交`（`:134-135`），而**输单不动阶段**（`:149-164`，只改 status/probability）→ 输单商机仍停留原阶段（如「方案报价」），**按阶段统计时仍被算作该阶段商机**。业界做法是把输单移出管道（Odoo 用 `Lost` + `fold`）。需在阶段统计口径里**显式排除 `status in (2,3)`**。
> **赢单/输单无二次业务校验**：不校验「是否已有合同/报价」，不要求赢单原因。相比 SAP「Loss reason 必填 + 竞争对手必填」偏松。

### 5.4 三套阶段字典（P0，见 §1.2）

**裁定建议**：① 以**后端 `opportunity_stage` 的 `Integer 1–5` 为唯一真源**；② 商机列表页的字符串 key 字典（`lead`/`qualification`/…）**改为数字**，管道视图阶段键一并改；③ 商机表单页的 `1–6` 字典**去掉 5 赢单 / 6 输单**，只保留 `1–5`，赢单/输单改由 `status` 表达；④ 三处字典**抽成共享常量模块**（如 `@/constants/crm`），禁止再各自复制。

### 5.5 权限

**本页无任何 `v-permission`**（对比报价单页有 10 处）。3 个行内动作对**任何能打开本页的用户**均可见可点。

> **业界口径**：赢单/输单通常是**主管级动作**（涉及金额确认与商机关闭），不应与「推进阶段」同级开放。建议补权限码（`crm:opportunity:advance` / `:win` / `:lose`）。

## 7. 数据模型

### 7.1 `crm_customer_opportunity`（**33 列**，devdb 实测 2026-09-18）

```
id, opportunity_code, opportunity_name, customer_id, customer_name, lead_id,
opportunity_stage, opportunity_stage_desc, estimated_amount, actual_amount, probability,
opportunity_type, opportunity_source, product_interest, requirement, competitor,

```

**关键实测**：

| 列 | 类型 / 约束 | 说明 |
|----|------------|------|
| `opportunity_stage` | `integer`，`is_nullable = YES`，`column_default = null` | **可空** → 后端强转 int NPE（§5.2） |
| `status` | `is_nullable = YES`，`column_default = 0` | 默认 `0`，**但 `0` 不在本页值域 `1/2/3` 内** → `oppStatusText` 回退 `OPP_STATUS_TEXT[0]` = `undefined` → 再回退 `'跟进中'`（`:161`）；颜色回退 `'default'` |
| `deleted` | `is_nullable = YES`，`column_default = 0` | 实体 `@TableLogic`；业务代码又 `getDeleted() == 1` 显式比较（双保险 + NPE 风险） |
| `version` | `is_nullable = YES`，`column_default = 0` | 实体 `@Version`，乐观锁 |
| **无** `create_by`/`update_by` | — | 实体用 `created_by`（`String`）/`updated_by`（`String`），**不是** `BaseEntity` 的 `createBy`（`Long`） |

**实体**（`customer/entity/CustomerOpportunity.java`）：`@TableId(type = IdType.AUTO)` → **自增 ID（非雪花）**，故前端用 `number` 传 `id` 安全（不涉及《_开发指南-金标准》陷阱 12 的 `Number()` 精度问题）｜`@TableLogic deleted`｜`@Version version`。

> **审计列命名与模块内不一致（P2）**：本表用 `created_by/created_at/updated_by/updated_at`（`created_by` 是 `String`），而 `Quotation` 用 `create_by/create_time/update_by/update_time`（`create_by` 是 `Long`）。**本表没有 `create_by`/`update_by`/`version` 三列中的前两者** → 实体**不能** `extends BaseEntity`（否则 MP 无条件 SELECT 不存在的列，见陷阱 14）；现状未继承，**正确**。

### 7.2 当前数据现状

`select opportunity_stage, status, count(*) from crm_customer_opportunity where deleted=0 group by 1,2` → **0 行**（**表内无数据**）。故本页当前呈现 `ARReportPage` 默认空态 `暂无数据`（`ARReportPage.vue:198`）。**验收前必须先造商机数据**（建议 ≥ 6 条覆盖 stage 1–5 × status 1–3 组合）。

### 7.3 缺失的阶段字典表

**`crm_opportunity_stage` 不存在**（§1.1 全库 22 张 `crm%` 表中无此项）→ 阶段硬编码无从配置。

## 10. 验收标准（目标）

> 本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下不存在 `e2e-crm*.cjs`）。落地脚本命名 `tools/e2e-crm.cjs`（界面 + 接口 + 直连 DB 对账 + 写库后复原）。

### 10.1 接口验收（建议 ≥ 16 项）

① `GET /api/crm/opportunity/page` 默认 200，`total` 与直查 DB（含 `deleted=0` 与租户条件）一致；② `pageNum`/`pageSize` 生效（`pageSize=1` → `records.length===1`）；③ `keyword` **同时命中**商机名称与客户名称；④ `opportunityStage` **逐值 1–5 过滤**（各造一条，逐个断言）；⑤ `status` 逐值 1–3 过滤；⑥ `POST /{id}/advance`：`stage=1` → DB `opportunity_stage=2`、`desc='需求确认'`、`probability=30`；⑦ `advance` 在 `stage=5` 时 400「商机已处于最终阶段」；⑧ **`advance` 在 `opportunity_stage` 为 `NULL` 时的行为**（当前预期 500，修复后改断言 400/正常推进）；⑨ `POST /{id}/win?actualAmount=1000` → DB `status=2`、`status_desc='赢单'`、`opportunity_stage=5`、`actual_amount=1000`、`actual_close_date=今天`、`probability=100`；⑩ `win` **不带 `actualAmount`** → 400（`@RequestParam` 必填）；⑪ `POST /{id}/lose?loseReason=预算不足` → DB `status=3`、`status_desc='输单'`、`lose_reason='预算不足'`、`probability=0`、**`opportunity_stage` 不变**；⑫ `lose` **不带 `loseReason`** → 400；⑬ `GET /statistics` 返回 7 个键；⑭ **`/statistics` 在「无赢单无输单但有商机」时不 500**（当前预期 500，修复后断言 `winRate=0`）；⑮ `GET /export` 条数与 `page.total` 一致；⑯ **写库隔离**：写断言后**按原值复原**，或使用专用测试商机。

> 2026-09-18 更新：⑧（`opportunity_stage` 为 NULL 时 `advance` 拆箱 NPE）与 ⑭（`/statistics` 除零）**均未修**，断言维持现状；⑬ 仍返回 7 个键；其余各项端点均已存在、可直接执行。

### 10.2 UI 验收（建议 ≥ 17 项）

① 菜单 `CRM → 商机管理 → 商机阶段`（`70321`）点开落在 `crm/opportunity-stage`，**该菜单无配对标签页**（`tag_label=null`、`list_path=null`）；② 查询区 3 项渲染（`阶段`/`状态` 有可见 label，`关键字` 只有 placeholder —— 与《查询区必须横向网格》偏好冲突，改版后需同步改断言）；③ 表格 11 列渲染，阶段/状态显示**中文 tag**，概率渲染 `a-progress` 且 `>= 70` 绿色 `#52c41a`、否则 `#1890ff`；④ 金额列有值显示 `1,234.56`，空值显示 `-`；⑤ 阶段筛选生效；⑥ 状态筛选生效；⑦ 关键字回车即查；⑧ 重置后三项清空并回第 1 页；⑨ 分页切页/改 `pageSize` 后请求参数为 `pageNum`/`pageSize`（**不是** `page`/`size`）；⑩ 导出下载 `商机阶段_*.csv`，UTF-8 BOM（Excel 中文不乱码），**表头 10 列（不含「操作」）**；⑪ 推进 → 确认框含商机名与**下一阶段中文名**（非 `undefined`）→ 确定 → 成功提示 → 列表刷新且阶段前进一格；⑫ 推进按钮在 `status ∈ {2,3}` 或 `stage >= 5` 时**禁用**；⑬ 赢单 → 弹窗「商机赢单」→ 成交金额**预填预计金额** → 清空后确定 → 提示 `请输入成交金额` 且**无网络请求**；填值确定 → `已标记为赢单` → 列表刷新（阶段「成交」、状态「赢单」）；⑭ 输单 → 不填原因确定 → `请输入输单原因`；填值（含首尾空格）确定 → `已标记为输单`，**DB 中 `lose_reason` 已 trim**；⑮ 赢单/输单后该行三个按钮**全部禁用**；⑯ **断言网络无 4xx**（本页 4 个端点全部 200）；⑰ 页面控制台**无 error**（含 `ReferenceError` —— 参见《重构搬迁后必须做运行时验证》）。

> 2026-09-18 更新：② 查询区已改横向网格、5 项（关键字/阶段/状态/客户/负责人）均带可见 label；⑩ 导出已改后端 `/export` 全量、12 列中文映射；⑫ 推进按钮禁用条件在 `opportunityStage` 为空时一并禁用；⑯ 本页 4 个端点均已存在，可断言全部 200。
