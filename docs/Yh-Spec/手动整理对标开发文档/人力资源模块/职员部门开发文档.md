### 1.1 🔴 菜单归属反常（名实不符，必须先读）

本页存在**三重错位**，是本模块最需要先裁定的事项：

| 维度 | 实情 | 反常点 |
|------|------|--------|
| `menu_code` 前缀 | `md:staff-dept` | `md:` = **主数据 / 资料模块**域，不是 HR 域（HR 页用 `hr:employee`、`hr:attendance`） |
| `component` 路径 | `views/md/staff-dept/index.vue` | 物理落在 **`views/md/`**（资料模块目录），不是 `views/hr/` |
| 菜单挂载位置 | 父 `61405 职员管理`（父 `60014 人力资源`） | 挂在了**人力资源**下 —— 三者互相矛盾 |

**来源已取证**（这条错位是**一次性搬迁**造成的，不是设计）：

- 建菜单：`V6.22.0__Fill_Mega_Menu_All_Columns.sql:250-255` —— 三个叶子建在**「资料 > 职员权限 (61105)」**下，`component` 当时还是 `views/common/placeholder/index.vue`。
- 改挂：`V9.6.0__Menu_Consolidation.sql:147-157` —— `Step 7: 职员权限(61105) 叶子 → 人力资源·职员管理(61405)`，`UPDATE sys_menu SET parent_id = 61405 ...` 把 **80530/80531/80532 三行整体**搬到了 HR。
- 补组件：`V9.18.0__Fix_All_Remaining_Placeholder_Paths.sql:24` —— 把占位组件换成真实组件。
- 现状：`61105` 这一行**在库中已不存在**（`SELECT ... WHERE parent_id = 60011` 现存子节点仅 `61101/61102/61103/61104/61106/61107`）—— **整列组被搬空后未清理**。

> **⚠️ 结论**：「职员部门」概念上属**系统管理 / 组织架构**，与「人力资源」只是**语义相邻**（HR 也读部门），但**数据上并无 HR 专属逻辑**（表是 `sys_department`，接口是 `/api/department`，权限码是 `department:*`）。
> **收敛建议（P1）**：菜单**留在原地成本最低**（`V9.6.0` 已搬过一次，再搬会造成第二次菜单跳变），但必须在**「人力资源 → 职员管理」上加分组说明**，或把该目录重命名为「组织与账号」（如实反映其内容 = 部门 / 岗位 / 账号三件系统管理事务）。
> **若选择移回**：应挂到 `60013 系统管理` 下的 `61307` 平台管理支线，与 `views/system/department/index.vue`（**1138 行**）合并，删除本简化页（详见 §5.5）。

1. **清空不可用且行为不一致**：后端 `update`（`DepartmentServiceImpl.java:174-186`）对 `phone` / `email` / `leaderName` 用 `StringUtils.hasText()` **守卫**，但对 `remark` 是**无条件赋值**（`:186` `dept.setRemark(request.getDescription())`）。
   → 用户在弹窗里**把联系电话删空再保存，值不会变**（改不掉），而**描述删空会真的清空**。同一表单两套语义。
2. **循环引用可被造出**：`loadParentOptions()`（`index.vue:211-221`）只排除了**自己**（`.filter(d => d.id !== editingId.value)`），**未排除自己的后代**；后端 `update`（`DepartmentServiceImpl.java:145-190`）**也不校验**（只有 `move` 才调 `isDescendant`）。
   → 把「财务部」的上级改成自己的子部门「财务部-会计组」→ **组织树成环**，`getTree`（`:81-91` 递归 `buildTree`）将丢节点或无限递归。
3. **改上级不改路径**：`update` 即使改了 `parentId`，也**不重算 `ancestors`**（`DepartmentServiceImpl.java:165-167` 只 `setParentId`）→ `path`（= VO 的 `ancestors`）与实际层级**永久不一致**；只有 `move` 端点才重算（`:255,261`）。
4. **编辑不拉详情**：后端已有 `GET /api/department/{id}`（`DepartmentController.java:52-56`），但页面 `openEdit(record)`（`index.vue:258-272`）**直接用列表行**回填。列表列缺 `email`（列里没有邮箱列）→ 编辑任意部门**不改邮箱也会照原样回传**（本次不丢），但一旦后端列表列裁剪或加列，就会静默丢字段。**建议改为一律先 `getById` 再回填**。

## 5. 业务规范

### 5.1 状态与值域

| 字段 | 值域 | 当前实现 | 问题 |
|------|------|---------|------|
| `status` | `0 禁用 / 1 启用` | 前端 select `启用=1 / 禁用=0`（`index.vue:180-183`）；`a-tag` 判定 `1 → 绿`（`:25-26`）；DDL 默认 `0`（`V5.0.0:561`）；后端 `create` 默认 `1`（`DepartmentServiceImpl.java:123`）；后端 `listAll` 只取 `1`（`:73`） | ✅ 语义**全站一致**（本模块少见的干净项）；但 **DDL 默认 0 与后端默认 1 冲突**，任何绕过 Service 的写入（迁移 / 直连 DB）会得到禁用部门 |

### 5.2 编码规则

- **手工填写，无号段**：`departmentCode` 是普通 input，编辑时 lock（`index.vue:88`）。
- **唯一性**：后端 `create` / `update` 各自用 `eq(deptCode, ...)` 统计（`DepartmentServiceImpl.java:106-112`、`152-160`），**依赖多租户拦截器补 `tenant_id`**（`sys_department` **有** `tenant_id` 列且**不在** `IGNORE_TENANT_TABLES`，`MyBatisPlusConfig.java:32-71`）→ 租户内唯一 ✅。
- **目标规格**：改走**号段**（`next-no` 体系），规则形如 `D + 4 位序号`；存量 `D9001` / `D9002` 已符合该形态。

### 5.3 关键业务规则

| 规则 | 当前 | 目标 |
|------|------|------|
| 名称唯一性 | ❌ 无校验（只校验编码） | 同租户内 `dept_name` 唯一（或「同名同父」唯一） |
| 删除保护 —— 子部门 | ✅ `count(parent_id = id) > 0` 则拒绝（`DepartmentServiceImpl.java:196-200`） | 保留；**并提示子部门数量与名称** |
| 删除保护 —— 关联用户/岗位/员工 | ❌ **不校验** | **P0**：`sys_user.dept_id`、`sys_position.dept_id`、`hr_employee.dept_id` 均有引用，删除部门会产生**孤儿引用**（本系统其它模块已普遍采用「引用保护」，此处必须补） |
| 上级部门合法性 | ⚠️ `create` 校验父存在（`:128-131`），但**不校验父是否属于本租户**、**不校验禁用父** | 补租户一致性 + 状态校验 |
| 层级路径（`ancestors`） | ⚠️ `create` 写 `"0"`（`:134`）或 `父.ancestors + "," + 父.id`（`:132`）；`update` **不重算**；`move` 重算 | **统一由一处（Service）维护**；禁止 update 改 parentId 不重算 |
| 层级深度上限 | ❌ 无 | 建议 ≤ 10 层 |
| 排序 | ⚠️ `sort` 是自由整数，`getTree`/`pageList` 都按它排（`:58,73`） | 保留；但**排序值冲突无提示** |
| 负责人（`leader_id`/`leader_name`） | ❌ **无写入入口**（列表有列、表有字段、弹窗无项） → 该列**永远为 NULL/空** | 补「负责人」选择器（数据源 `sys_user` 或 `hr_employee`，二选一须先定口径，见 §8） |
| 部门合并 / 撤销 | ❌ 无 | 业界标配（组织调整），需后端补 |

### 5.4 种子数据的现实约束（验收必读）

devdb 实测 `sys_department` **仅 2 行**：

| id | tenant_id | parent_id | dept_code | dept_name | ancestors | status | deleted | version |
|----|:---------:|:---------:|-----------|-----------|-----------|:------:|:-------:|:-------:|
| 9001 | 1 | 0 | D9001 | 财务部 | **null** | **0** | 0 | 0 |
| 9002 | 1 | 0 | D9002 | 市场部 | **null** | **0** | 0 | 0 |

由此产生三个**必然现象**：

1. **所有「部门下拉」都是空的**。`DepartmentServiceImpl.listAll()` 硬过滤 `status = 1`（`:73`），而两条种子部门 `status = 0`。
   → 本页「上级部门」下拉**必然空**（无法新建子部门，只能建顶级）；
   → 「岗位权限」页的「所属部门」下拉、「全部操作员」页的「所属部门」下拉**同样必然空**（三页共用同一 `departmentApi.getList()`）。
2. **存量 `ancestors = null` 与新建值 `"0"` 不一致**：`convertToVO` 用 `ancestors.split(",").length` 算 `level`（`:358-362`），null 时走 `level = 0`；而新建顶级部门 `ancestors = "0"` → `level = 1`。**同级部门计算出不同层级**。
3. **`move` 会产生脏路径**：`move` 内 `target.getAncestors() + "," + target.getId()`（`:255`）对 `ancestors = null` 的目标部门会拼出 **`"null,9001"`** 这种字符串，写入 `ancestors`（`VARCHAR(500)`）后污染层级计算。

> **⚠️ 验收前置条件**：任何 UI 验收**必须先造数**（至少把一条部门的 `status` 改为 `1`，否则下拉全空），并在收尾时**复原现场**（参见《共享db E2E 断言必须加作用域》）。

> 本页在 ql361 **无对应页**（该对标系统**无人力资源模块**）。以下为业界标准做法与本系统的差距。
> **参考来源：** Odoo 18 HR `https://www.odoo.com/documentation/18.0/`（章节待补充）；SAP SuccessFactors / S·4HANA HCM `https://help.sap.com/`（章节待补充）；金蝶 s-HR `https://vip.kingdee.com/`（章节待补充）；用友 DHR `https://success.yonyou.com/`（章节待补充）。
> 本模块另有已核验的调研底稿：《人力资源-业界做法调研.md》（同目录），本节引用其 §1.2 / §2.1 / §2.6。

| # | 能力 | 业界做法 | 本系统当前 | 差距与建议 |
|:-:|------|---------|-----------|-----------|

## 10. 验收标准（目标）

> 本模块**尚无 E2E 脚本**（`tools/` 目录下无 `e2e-hr*.cjs`）。以下为按金标准制定的验收清单，建议脚本命名 `tools/e2e-hr-staff.cjs`。
> **前置条件（重要）**：`sys_department` 仅 2 行且 **`status` 全为 0** —— **下拉类断言必须先造数**（把一条部门改为 `status = 1`），并在收尾时**逐字段复原**（`status` 改回 0、删除本轮新建的部门）。

### 10.1 接口验收（目标 ≥ 15 项）

1. `GET /api/department/page` 默认查询 200，`total` 与直查 DB（`deleted = 0` + `tenant_id = 1`）**逐值一致**。
2. `pageNum` / `pageSize` 生效：`pageSize=1` 时 `records.length === 1`。
3. `departmentName`（`like`）/ `status`（`eq`）逐个生效（造数验证）。
4. `departmentCode` / `parentId` **后端支持但前端未接** —— 断言接口层面可用（作为前端补控件的依据）。
5. `POST /api/department` 新建后 `id` 非空、DB 可查回，且 **`ancestors` 为 `"0"`**（顶级）、`status` 默认 `1`。
6. `PUT /api/department/{id}` 改名后三级回读（DB / 详情 / 列表）一致。
7. **改 `parentId` 后 `ancestors` 是否重算** —— 当前应断言为**未重算**（记录 P0 缺陷证据），修复后改断言为已级联更新。
8. `PUT /api/department/{id}/status` 改状态后 DB 一致。
9. `DELETE /api/department/{id}`：**有子部门时**应 400「存在子部门，无法删除」。
10. `DELETE /api/department/{id}`：**有用户/岗位/员工引用时**（目标行为）应 400 并提示引用数（当前会静默删成功 → 作为 P0 证据）。
11. `DELETE /api/department/batch` 批量删（前端当前无入口，先验接口）。
12. `POST /api/department/{id}/move`：`position='inner'` 时移动成功且 `ancestors` 正确；**目标 `ancestors` 为 null 时**断言是否产出 `"null,..."` 脏值（P0 证据）。
13. `POST /api/department/{id}/move` 移动到自己的子部门应 400。
14. `GET /api/department/tree` 返回树形结构，**父子关系与 DB `parent_id` 一致**；断言顶层节点数 = `parent_id = 0` 的行数。
15. `GET /api/department/list` **只返回 `status = 1`**（当前为 0 条 → 这是 P0「下拉恒空」的直接证据）。
16. `GET /api/department/export` 返回的 CSV 行数 = `page` 的 `total`，且**首字节为 UTF-8 BOM**（当前应失败，记录缺陷）。
17. 未登录请求 `/api/department/page` 应 401；`/list`、`/tree` 的鉴权现状（当前仅要求登录）作为 P1 证据。

### 10.2 UI 验收（目标 ≥ 12 项）

1. 菜单 `人力资源 → 职员管理 → 职员部门` 点开落在本页，**页面不空白**（目录节点透传组件已就位）。
2. 页面**控制台无 error**（含 `ReferenceError` —— 参见《重构搬迁后必须做运行时验证》）。
3. **断言网络无 4xx**：`GET /api/department/page` 必须 200。
4. 表格 9 列渲染正确；状态列显示**中文标签**（启用/禁用）而非 `0`/`1`。
5. 查询区为**横向自适应网格**（不得纵向单列），2 项条件**逐个生效**。
6. 「上级部门」下拉**有真实选项**（造数后；当前为空 → P0 证据）。
7. 新增 → 保存 → 列表出现新行（**断言网络无 4xx**）；`departmentCode` 重复时应给出明确提示。
8. 编辑 → 保存 → 列表值更新；**断言未改动字段未被清空**。
9. 「禁用/启用」行按钮文案与状态联动，点击后状态 tag 变化。
10. 删除 → `a-popconfirm` → 确认 → 行消失。
11. 表头齿轮可改列显隐/顺序，刷新后**个人配置保留**（目标）。
12. 分页为**经典形态** `.classic-pagination`，页长选项 `[20,50,100]`（目标）；**打印判 N/A**（勿按模板硬加）。
13. 收尾：清理验收造出的部门行、`status` 复原，并复核现场已复原。
