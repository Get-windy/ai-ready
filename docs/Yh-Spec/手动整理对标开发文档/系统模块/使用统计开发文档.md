## 1. 页面概述

使用统计页意图是**平台运营方的一屏式用量看板**：「平台一共几个模块、几个活跃、服务多少租户、平均使用率多少」，以及一张**模块使用排行**表，用于判断**哪个模块值得继续投入、哪个模块可以下架**。它属于 `61302 模块管理` 组的第 4 页（`sort=400`）。

**但本页当前是「两张皮」**：
- **顶部 4 张统计卡是完全写死的常量**（`:90-95`：`12 / 10 / 48 / 78`），**后端也不返回这 4 个汇总值** → 这 4 个数字**在本系统中无任何数据来源**（其中「总模块数 12」「活跃模块 10」「总租户数 48」与库中实测 `6 / 5 / 3` **全对不上**）；
- **排行表走 `catch` 分支的 6 行写死假数据**（`:112-119`），而**后端侧还有 4 处硬编码**（§9.2），形成**同一列两种假法**的双重失真。

### 1.1 与相邻页的分工（`61302 模块管理` 组 4 页，本页是唯一「聚合视图」）

| 页面 | 菜单ID | 回答的问题 | 数据源 | 后端端点 | 可用性 |
|------|:-----:|-----------|--------|---------|:------:|
| **模块列表** | 62101 | 平台**有哪些模块**、启停/改描述 | `sys_module` | `GET /api/module/list` | ❌ 404 |
| **模块版本** | 62102 | 某模块**有哪些版本** | `sys_module_version` | `GET /api/module/versions` | ❌ 404 + 假数据 |
| **模块发布** | 62103 | 平台**发布了什么** | 复用 `sys_module_version` | `GET /api/module/releases` | ❌ 404 + 假数据 |
| **使用统计（本页）** | 62104 | 各模块**被用得多少**（**唯一做聚合的页**） | `sys_module` + `sys_audit_log` | `GET /api/module/usage` | ❌ 404 + 假数据 + **后端硬编码** |

> **一句话分工**：前三页是**台账**（清单 / 版本 / 发布），**本页是唯一的度量视图** —— 回答「哪个模块被用得最多，好决定投入或下架」。
> **⚠️ 本页与「租户管理 → 配额管理」（62005）分工**：本页是**平台资源视角**（模块维度）；配额管理是**租户权益视角**（租户 × 配额的授权数字）。二者口径应分离：**配额 = 有权用多少，用量 = 实际用了多少**（§8.2-1）。

### 3.2 🔴 统计卡（4 张，**完全写死**）

`moduleStats` 定义于 `:90-95`（`shallowRef<any[]>` 常量数组）：

| # | `name`（逐字） | `count`（写死） | 其它字段 | 图标 / 颜色 | 行 |
|:-:|---------------|:--------------:|---------|------------|----|
| 1 | `总模块数` | **12** | — | `AppstoreOutlined` / `#1890ff` | `:91` |
| 2 | `活跃模块` | **10** | — | `AppstoreOutlined` / `#52c41a` | `:92` |
| 3 | `总租户数` | **48** | `unit: '个'` | `TeamOutlined` / `#722ed1` | `:93` |
| 4 | `平均使用率` | **78** | 🔴 **`suffix: '%'`** | `AppstoreOutlined` / `#faad14` | `:94` |

**🔴 缺陷（P0）：这 4 个数字在本系统中没有任何数据来源**

| 断言 | 证据 |
|------|------|
| 前端无接口 | `moduleStats` 是**常量数组**，`fetchData`（`:106-123`）**从不给它赋值** |
| 后端不返回 | `getUsageStats()` 只**逐模块** put `rank/moduleName/moduleCode/tenantCount/usageRate/monthlyActive/callCount`（`ModuleServiceImpl.java:181-189`）—— **没有任何汇总值** |
| 所以 | **总模块数 / 活跃模块 / 总租户数 / 平均使用率四个卡片「在本系统中无任何数据来源」，属纯前端编造** |

**🔴 缺陷（P2）：`suffix: '%'` 从不被读取 → `%` 后缀不显示**

```
数据定义（:94）：{ name: '平均使用率', count: 78, suffix: '%', icon: AppstoreOutlined, color: '#faad14' }
模板绑定（:38）：:suffix="stat.unit || ''"
```

第 4 项声明的是 `suffix`，而模板读的是 `unit` → **`suffix` 字段从未被读取** → 「平均使用率」卡片显示 `78` 而**不显示 `%`**（第 3 项写的是 `unit: '个'`，因此「总租户数」的 `个` 能显示）。**修法：把 `suffix: '%'` 改成 `unit: '%'`，或让模板同时兜底 `stat.unit || stat.suffix || ''`。**

> **对照**：本项目已知的 `a-statistic` 字符串值陷阱（传「-」会被解析成 `-0`）在本页**不适用** —— 因为 4 张卡传的都是 **number**（`12/10/48/78`）。但一旦改成后端取值，**必须注意**：`count` 若来自 JSON 字符串会走同一陷阱 → **应统一走 `:formatter`**。


**🔴 本页统计的两条硬约束（当前 100% 命中「空数据分支」）**：

| 约束 | 事实 | 后果 |
|------|------|------|
| `sys_audit_log` **0 行** | devdb 实测：`SELECT count(*) FROM sys_audit_log` = **0**；`group by module` 结果集为空 | `activeUserMap` / `callCountMap` **全空** |
| `maxMonthlyActive` 的兜底 | `Map<...>::stream().mapToInt(Set::size).max().orElse(1)` → **空集合时返回 `1`** | `maxMonthlyActive = 1 > 0` → **不会**走 `else`（**注意**：源码写的 `math.max` 兜底是 `1` 而不是 `0`，见下） |

> ⚠️ **一处源码细节（如实登记）**：`ModuleServiceImpl.java:157` 是 `.max().orElse(1)`，**兜底值为 `1`** → 因此「`maxMonthlyActive > 0` 恒假」这一说法**需要修正**：当前实际是 **`maxMonthlyActive = 1`（恒真）** → 走的是**真分支**，于是 `usageRate = 0 / 1 * 100 = 0` → **所有模块使用率恒为 0**。
> **结论修正**：`sys_audit_log` 0 行时，**使用率恒为 `0`**（而不是「伪造 50/0」）—— **`ModuleServiceImpl.java:179` 的伪造分支只在 `activeUserMap` 的 max 兜底为 0 时才可能命中**；当前代码的 `.orElse(1)` 使其**实际上不可达**。这是**比"伪造 50"更隐蔽的一处**：**使用率恒 0 会让页面看起来"这个平台的模块根本没人用"**。
> **两种假法都要如实登记**：① 若兜底为 0 → 伪造 50/0（`:179`）；② 当前实际（`.orElse(1)`）→ **恒 0**。**验收时必须以实测值（0）为准**（§10.1-③）。

## 8. 业界对标

> **本页在 ql361 无对应页**（§2）。因此本章**不写 ql361 对标规格**，只写**业界能力对标**。所有来源按「标题 + URL + 章节 + 查阅日期 + 可信度级别」留痕；**凡底稿标 D 级的方案，本文件一律写「本系统设计」而非「业界标准」**。

### 8.1 业界叫法

**AWS 的 per-tenant 计量与消耗分析**（Well-Architected SaaS Lens 的 **SaaS COST 1 / SaaS OPS 2**）；SAP 侧对应**用量与成本监控**（目录功能「监控使用基于使用量的商业模式的合同的使用情况和成本」）；用友对应「**容量资源看板**」；金蝶对应「**调度整体看板**」。

### 8.2 业界做法要点

1. **按租户切分消耗是 Well-Architected 的正式最佳实践**：SaaS **COST 1** 问题原文「**How do you measure the resource consumption of individual tenants?**」，推荐手段为 **AWS CUR + 资源标签、CloudWatch**。→ 本系统**完全没有租户维度**（`tenantCount` 是常量 `1`，§3.6）。
2. **SaaS OPS 2 要求「捕获并呈现用于分析单个租户使用情况和消费趋势的指标数据」** —— **趋势比快照重要**。→ 本系统**只有近 30 天快照，无趋势**（§3.4）。
3. **用标签打通「实体 → 成本/用量」**：SAP 目录功能明确「监控使用基于使用量的商业模式的合同的使用情况和成本」。
4. **看板要给多角色多视角**：金蝶「调度中心」定位是「提供整体可视化看板以供多角色、多视角查看调度中心健康情况」（下有整体看板 / 执行服务器监控 / 任务分析 / 任务追踪四件套）。→ 本系统只有**一张表 + 4 张假卡**。
5. **tier 与用量计划绑定**：AWS Serverless SaaS 参考方案「通过 API Gateway 为每个租户层级（**basic、standard、premium、platinum**）设置用量计划」→ **用量统计直接服务限流与计费**；本系统用量**不服务任何下游**。

### 8.4 明确不借鉴

- **AWS CUR / CloudWatch / 资源标签体系** —— 那是**云资源级**计量（EC2 小时、S3 字节、Lambda 调用）；本系统的「用量」是**业务级**（用户数 / 单据数 / 模块活跃用户）→ **只借鉴「按租户切分 + 趋势」两条原则，不搬采集架构**。
- **SAP 的按使用量计费（usage-based billing）合同模型** —— 本系统无计费引擎，**不引入合同/账单概念**。
- **金蝶「调度中心」的四件套页面组织与界面样式**（README §5.3 口径：按能力模型建模，**不照搬界面**）。
- **AWS API Gateway 的 usage plan / throttle 机制** —— 本系统无网关限流层，**不套用**。
- **「用大量假数据撑满看板」的做法** —— 这是**本页当前的病灶**（§3.2 / §3.10），**必须消除而不是借鉴**。

## 10. 验收标准（目标）

> **前置**：本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下不存在 `e2e-system-*.cjs` / `e2e-admin-*.cjs`）。落地脚本建议命名 `tools/e2e-system.cjs`（接口 + 直连 DB 对账 + 写库后复原 + Playwright UI 截屏，参照 `tools/e2e-crm.cjs`）。
> **⚠️ 本页验收的三个最大前提**：
> 1. **P0-1（包未装配）不修，§10.1 的接口断言全部得到 404** → 建议顺序：**先修 `scanBasePackages` → 再拔掉兜底数组 → 再跑接口断言 → 最后跑 UI 断言**；
> 2. **必须先拔掉两处写死数据**：顶部 4 张卡（`:90-95`）与表尾兜底数组（`:112-119`）—— 否则任何断言都会被假数据「答对」，UI 断言全部失真（**硬性前置条件**）；
> 3. **`sys_audit_log` 实测 0 行**，因此**所有活跃类指标预期恒 0** → 断言「等于 0」是**当前的正确期望**，不要因为「看起来不对」而误判为失败（**先把数据灌进 `sys_audit_log` 才能断言非 0**）。
> **权限账号**：`admin`（`id=1`，`tenant_id=1`，SUPER_ADMIN）用作 **200 基线**（走 `UnifiedPermissionCacheService.java:82-88` 的 `*` 通配）；另需一个**非超管的平台运营账号**做 **403 对账**（因为 `system:module%` 权限码实测 0 行）。

### 10.1 接口验收（24 项）

**可达性（①–④）**

① 用 `admin` 登录（Bearer），`GET /api/module/usage` **期望 200**；**未修 `scanBasePackages` 时期望 404** —— **两种结果都要记录**，404 即证明 P0-1 未修。
② **断言 `/api/module/**` 全部 404**（逐条打 10 个 mapping：`/list` `/versions` `/releases` `/usage` `/{id}` `POST ""` `PUT /{id}` `DELETE /{id}` `PUT /{id}/status` `POST /{id}/publish`）—— 这是**修复前的基线**；**修复后本项应改为「全部非 404」**。
③ **在拔掉两处写死数据之后**再打开页面，断言卡片**显示 `0`（或 `-`）**而不是 `12/10/48/78`，且表格**渲染 `a-empty`（或 0 行）**并**出现可见错误提示**（当前无提示 → 登记 P0-3；修复后应改断言「提示 + 重试按钮」）。
④ 断言 `GET /api/module/usage` **不带 `Authorization`** 时返回 **401/403**（证明全局登录拦截生效）。

**数据一致性（⑤–⑫）**

⑤ 断言 `GET /api/module/usage` 返回的 `records` 条数 = **6**，且**直连 DB** `SELECT count(*) FROM sys_module WHERE deleted=0` = **6** → **两者相等**。
⑥ 🎯 **超管登录后本表能查到 ≥ 6 行**（专门断言，来自 README §1.3 红线②的验收纪律）：`GET /api/module/usage` 返回 `total >= 6`；同时断言 `SELECT count(*) FROM sys_module WHERE deleted=0` = **6**。

⑧ 🔴 **断言 `tenantCount` 恒为 `1`**：连续调 3 次（间隔 >30s），断言 6 行的 `tenantCount` **全部为 `1` 且完全不变** → **P0-4 的可执行证据**（对照前端假数据的 42/38/…）。
⑨ 🔴 **断言 `monthlyActive` 恒为 `0` 且 `usageRate` 恒为 `0`**（因 `sys_audit_log` 0 行）→ 与库中 `SELECT count(*) FROM sys_audit_log` = **0** 对账；**登记 P0-5**。修复数据源后改断言「与 `GROUP BY module` 的实测值一致」。
⑩ 断言排序：`records` 按 `monthlyActive` **降序**（`:163-169`），且 `rank` 从 **1 连续递增**；**当所有 `monthlyActive` 都是 0 时**，断言 `rank` 仍为 1..6（顺序退化为 `sys_module.sort_order` 的顺序）—— **记录此时的真实顺序**。
⑪ 断言 `callCount`（第 7 个键）**有返回但前端无列**：抓取接口响应确认该键存在，并断言页面 Network 之外的 DOM 中**不存在「调用次数」列** → 登记 P2-19。
⑫ 断言 `GET /api/module/usage` **无任何可传参数**：尝试 `?days=7` / `?tenantId=1` / `?moduleCode=sale` 均**被忽略**（返回结果与不传时逐字节相同）→ 登记 P1-6 与 P1-7。

**汇总值来源（⑬–⑮）**

⑬ 🔴 **断言 4 张卡的数字与任何接口都无关**：抓包确认页面**只发出 1 个请求**（`GET /api/module/usage`），**没有任何汇总请求**；同时断言该响应体**不含** `totalModules` / `activeModules` / `totalTenants` / `avgUsageRate` 之类的汇总键 → **证明这 4 个数字无数据来源**。

⑮ 断言 `GET /api/module/usage` 被调用前后 **`sys_module` / `sys_audit_log` / `sys_module_version` 行数完全不变**（证明本页只读）。

**后端缺口（⑯–⑲）**

⑯ **断言以下能力不存在**（逐个尝试，期望 404/405 或参数被忽略）：`GET /api/module/usage/summary`、`GET /api/module/usage/trend`、`GET /api/module/usage/tenants`、`GET /api/module/usage/export` → 与 §6.5 的 11 条后端缺口对账。

**权限与红线（⑳–㉔）**

⑳ 🎯 **超管登录后本表能查到 ≥ 6 行**（与 ⑥ 同一断言的重申，用于自动化脚本的显式检查点）：断言 `total >= 6` 且 `records.length >= 6`。
