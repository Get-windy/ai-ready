## 页面概述

支付记录是**在线支付逐笔流水**（支付回调落库的每笔成功/失败记录）查询页：只读展示渠道订单号、渠道交易号、支付渠道、支付金额、状态、回调时间、创建时间。（**无创建/编辑入口**——支付记录由支付渠道回调 `POST /api/payment/callback/{channel}` 自动落库。）**单入口，无子 Tab，无独立表单**。

| 页面 | 地址 | 说明 |
|------|------|------|
| 支付记录 | `payment/record` | 单视图列表页（统计卡片 + 4 查询字段 + 数据表） |

单入口：交易模块 → 支付管理 → 支付记录。

- 实测实据：数据表列配置 10（默认显示 7）、查询字段 4、列/页面配置弹窗 **有**（表头 rowNo 列齿轮列配置 + 独立页面配置面板）。
- 状态：列表/详情 Tag 仍为**二值展示**（`status===2` 成功，其余失败），但**筛选下拉已按后端真实字典取值**：成功=`2`、失败=`3`（修正前误用 `1`＝支付中）。

## 页面结构（含配置）

支付记录 = 单视图列表页（无子 Tab；列配置为表头 rowNo 列齿轮、页面配置为独立 `PageConfigPanel`）。含查询区（4 项）+ 统计卡片 + 数据表。

### 统计卡片（后端聚合 4 项）
成功（status 2）、失败（status ≠ 2）、成功金额（status=2 金额合计）、笔数（`total`）；走后端聚合 `GET /api/payment/record/stat?channel=`，**已随查询区「支付渠道」联动**（`loadStats()` 传 `channel`；`status`/时间条件后端聚合端点不支持，故不参与联动）。

### 查询条件字段（4 项，显隐可由页面配置弹窗控制）
- 渠道订单号（文本框，模糊）
- 支付渠道（下拉：全部渠道/支付宝/微信支付/银联支付/银行转账/现金+线下）
- 状态（下拉：成功=`2` / 失败=`3`，取值同 `payment_record.status` 真实字典）
- 支付时间（区间，含时分秒）
- 查询、重置（按钮）

### 功能按钮 / 行级操作
- 头部按钮：刷新、打印(F8)、导出。
- 行级操作：**详情**（抽屉：渠道订单号/渠道交易号/支付渠道/支付金额/状态/回调时间/创建时间）。

### 数据表列配置：共 10 列可配置（默认显示 7 / 默认隐藏 3：支付请求ID、错误码、错误信息）；固定列：序号、操作（详情）
默认显示：渠道订单号、渠道交易号、支付渠道（Tag）、支付金额（¥ 绿色）、状态（成功/失败 Tag）、回调时间、创建时间、操作（详情）。

## 业务规范说明

- **记录主线**：支付请求 → 渠道完成支付 → 渠道网关回调 `POST /api/payment/callback/{channel}` → 支付回调解码落 `payment_record`（渠道订单号/渠道交易号/金额/状态/回调数据）→ 本页可查。
- **状态口径**：`payment_record.status` 后端真实字典为 **0 待支付 / 1 支付中 / 2 成功 / 3 失败**；列表/详情 Tag 仍按 `status===2` 判定成功、其余失败（二值展示），**筛选下拉「失败」已修正为 `3`**（修正前为 `1`＝支付中，属口径错误）。`errorCode`/`errorMsg` 为列表**默认隐藏列**（详情抽屉亦展示）。
- **金额口径**：支付金额 = 本次回调成交金额。
- **与支付请求的关系**：一条支付请求（`payment_request`）可对应多条支付记录（`payment_record`，含多次回调/重试），通过 `requestId` 关联。
- **下游**：仅作审计/对账追溯，无写操作。

  **(1) 前端路径双前缀 → 4 个支付页的每一个请求都 404（最严重）**
  - **现象**：`frontend/apps/pc-admin/src/utils/request.ts:93` 的 axios 实例是 `baseURL: '/api'`，而 `src/api/payment/index.ts` 把路径写成 `'/api/payment/...'`、`'/api/refund/...'`、`'/api/reconciliation/...'` → 实际请求 `"/api" + "/api/payment/record/page"` = **`/api/api/payment/record/page`**。`vite.config.ts` 的 proxy（`/api/erp/mall`、`/api`）**没有 rewrite**，后端映射是 `/api/payment/**` →
    `{"code":404,"message":"接口不存在: api/api/payment/record/page"}`。**4 个页面在浏览器里全部不可用**。
  - **实测对照**：`/api/payment/record/page` → 200；`/api/api/payment/record/page` → 404（两条都真机跑过，见 `tool-results/e2e-trade/probe-after-fix.txt` 的负向对照行）。
  - **修复**：把 `api/payment/index.ts` 里 **20 处**调用的前导 `/api` 去掉（`/payment/...`、`/refund/...`、`/reconciliation/...`），与全仓其它 api 文件（如 `api/erp/mall.ts`、`api/trade/index.ts`）写法一致。**保留第 46/60 行注释里描述后端完整路径的 `/api/config/list`**（那是说明文字，不是调用）。
  - **验证**：修复后 4 页的 6 个分页 + 4 个统计 + `pending-dates` + `channels` **全部 200**（探针 33/33 PASS，退出码 0）。

  **(2) 不传时间区间时列表必 500（`endOfRange` 空指针）**
  - **现象**：`GET /api/payment/record/page`、`GET /api/refund/request/page` → **500**，
    `NullPointerException: Cannot invoke "java.time.LocalDateTime.toLocalTime()" because "to" is null`
    （`PaymentServiceImpl.endOfRange:291` / `RefundServiceImpl.endOfRange:186`）。
  - **根因**：调用方写的是 `wrapper.lt(to != null, PaymentRecord::getCallbackTime, endOfRange(to))` —— MyBatis-Plus 的 `lt(boolean, …)` 靠**条件**决定是否拼 SQL，但 **Java 会先求值实参**，所以 `to == null`（不筛结束时间，即页面默认查询）时 `endOfRange(null)` 照样被执行 → NPE。**默认查询必挂**，不是偶发。
  - **修复**：`endOfRange` 开头加 `if (to == null) return null;`（`null` 语义＝不设上界，与 `lt` 的条件一致）。两个文件同步修。

  **(3) 支付 5 张表缺 `BaseEntity` 审计列 → 这些实体的任何查询都 500**
  - **现象**：`GET /api/reconciliation/pending-dates` → **500**，
    `BadSqlGrammarException … PSQLException: 错误: 字段 "create_by" 不存在`，
    SQL 为 `SELECT id, …, create_time, update_time, create_by, update_by, deleted, version FROM payment_request …`
    （`ReconciliationServiceImpl.getPendingDates:338`）。
  - **根因（真库复核）**：`core-payment` 的 5 个实体**全部** `extends BaseEntity`（声明了 `createBy`/`updateBy`/`version`，见 `core-base/.../entity/BaseEntity.java` L40/L46/L58），但真库这 5 张表**都没有这三列**：

    | 表 | create_by | update_by | version | 列数 |
    |---|---|---|---|---|
    | `payment_request` | f | f | f | 18 |
    | `payment_record` | f | f | f | 15 |
    | `refund_request` | f | f | f | 17 |
    | `refund_record` | f | f | f | 14 |
    | `payment_reconciliation` | f | f | f | 17 |

    全仓也**没有 `MetaObjectHandler` 实现**（`grep "implements MetaObjectHandler"` 无命中）→ 这三列不会被自动填充，INSERT 时因 `FieldStrategy.NOT_NULL` 被忽略（写侥幸不报错），但 **SELECT 一定把它们列进列清单 → 每次查询必抛**。即**读路径必挂**。
  - **修复**：新增迁移 **`V11.367.0__Add_Payment_Tables_BaseEntity_Audit_Columns.sql`**，为这 5 张表补 `create_by BIGINT` / `update_by BIGINT` / `version INTEGER DEFAULT 0`（+ 列注释，幂等 `ADD COLUMN IF NOT EXISTS`）。**未改任何实体/服务代码**（把实体改成不继承 `BaseEntity` 会破坏全仓一致性）。
  - **`version` 这里可以给 DEFAULT 0（与 V11.365.0 的陷阱相反）**：`@Version` 乐观锁 UPDATE 的 WHERE 是 `version = ?`，NULL 会导致更新匹配不到任何行，且 `0`＝「初始版本」是正确语义、不翻转任何业务判定；而 V11.365.0 的 `reg_audit_required` 默认值会翻转审核判定，故那一列**不能**给默认值。
  - **真机应用**：启动日志 `Migrating schema "public" to version "11.367.0 - Add Payment Tables BaseEntity Audit Columns"` → `Successfully applied 1 migration … now at version v11.367.0`。

  **修复后整体验证**：接口探针 **33/33 PASS**（`tool-results/e2e-trade/probe-after-fix.txt`，退出码 0，含 3 条「双前缀必 404」负向对照）；`node tools/e2e-trade.cjs` **103/103 通过、退出码 0**（第八节 10 项即本节 5 张表的分页 total 与 4 个统计接口直查对账）。

### 明确不借鉴
- **业界界面视觉样式**（唯一不借鉴项）：不采用其配色、圆角、阴影、字体与组件外观；外观令牌一律取自本系统既有主题。
- **不照搬字段命名**：仅语义对齐，本系统字段名以库表与既有实体为准（如 `state` 对应本系统 `status`，`provider_reference` 对应 `channelTradeNo`/`channelOrderNo`，`state_message` 对应 `errorMsg`）。
- **`currency_id`（币种）**：本系统 `payment_record` 无币种列、按单一结算币种处理，借鉴该字段需先做多币种改造，超出本页范围。
- **`operation`（交易操作类型）**：Odoo 以单模型区分 payment/refund 等操作；本系统支付与退款为**两张独立表**（`payment_record` / `refund_record`），操作类型由表区分，无需再引入一列。
- **`payment_method_id` / `token_id`（支付方式与卡令牌）**：本系统**不存储卡令牌**、不进入 PCI 卡数据范围，渠道差异由 `PAYMENT_CHANNEL_MAP`（`api/payment/index.ts:5-11`）承载。
