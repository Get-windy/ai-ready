## 3. 金标准目标设计（改造前拟定的目标，已全部达成）

### 3.1 能力拆分（两块，分别落地）

**A. 人车核验（现状增强）**

- 人车绑定：绑定 / 解绑 / 交车，绑定期间一人一车唯一性校验。
- 巡检：出车前 / 收车后 / 抽检 / 定检，含**照片/里程/位置**凭证（现仅文本）。
- 预警：人车分离、异常滞留、绑定超时——**由后端定时任务产生**（修复 `detect*Anomaly` 无调用问题），并可推送《实时跟踪》。

**B. 实名认证 / 资质（新增，合规刚需）**

| 项 | 说明 |
|----|------|
| 身份认证 | 身份证 OCR + 实名核验（三要素/人脸核身），分自有员工与外部平台两类 |
| 证照管理 | 驾驶证、行驶证、健康证、从业资格证；**有效期到期提醒**（复用 `dms_vehicle_inspection` 的到期思路） |
| 背景审查 | 审查状态与结论留档（可选第三方） |
| 车辆合规 | 车辆证照（行驶证/营运证/保险/年检）与配送员资质**双向校验** |
| 审核流 | 提交 → 审核（通过/驳回）→ 生效；**未通过不可接单**（与《调度任务》指派联动） |
| 外部平台背书 | 外部平台配送员的资质由渠道方提供，系统记录**渠道背书结果 + 有效期**，不重复采集敏感信息 |

### 3.2 后端接口（金标准）

| 接口 | 说明 |
|------|------|
| `GET /api/dms/verification/binding/page` | 人车绑定分页（**分页参数与全站统一**） |
| `POST /api/dms/verification/binding/{id}/handover` | 交车（**方法/参数与前端对齐**） |
| `GET /api/dms/verification/binding/{id}` | 绑定详情（**补齐**） |
| `GET /api/dms/verification/alert/page` | 预警分页 |
| `PUT /api/dms/verification/alert/{id}/handle` | 处理预警（`handler` 从登录态取，**不要求前端传**） |
| `GET /api/dms/verification/inspection/page` | 巡检分页（**补齐**） |
| `PUT /api/dms/verification/inspection/{id}/review` | 审核（字段名对齐） |
| `POST /api/dms/verification/kyc/submit` | 提交实名/资质材料 |
| `POST /api/dms/verification/kyc/{id}/audit` | 资质审核 |
| `GET /api/dms/verification/kyc/page` | 资质台账（含到期提醒） |
| 定时任务 | `detect*Anomaly` + 证照到期扫描（**必须真实调度**） |

### 3.3 业界生产级实践要点

1. **无资质不接单**：指派/抢单前校验资质有效（`verifyStatus` + 证照有效期），与《调度任务》《订单池》联动。
2. **敏感信息最小化**：身份证号脱敏展示（前 3 后 4）、加密存储；外部平台配送员**只存背书结果**，不落原始证件。
3. **到期提醒**：证照/保险/年检到期前 N 天预警（可配置，《配送参数》）。
4. **审计留痕**：谁审核、谁修改、何时生效，全部留档（合规检查要求）。
5. **预警自动产生**：靠定时任务 + 轨迹/绑定数据计算，不能依赖人工触发（现状预警永不产生是硬伤）。

## 5. 已落地能力清单（对照 §3 目标设计）

**A. 人车核验**：人车绑定/解绑/交车（一人一车唯一性校验 + 交车凭证）、四类巡检（照片来源字段 + 里程 + 油量 + 定位）、三类预警（人车分离 / 异常滞留 / 绑定超时，全部由后端定时任务与核验流程真实产生，同一对象同类型未处理预警自动去重）。

**B. 实名认证 / 资质（KYC）**：

| 能力 | 落地口径 |
|------|---------|
| 身份认证 | `dms_rider_verification`（一人一条，25 列）；身份证号脱敏落库；证件影像存 URL（JSON），不重复采集原始证号 |
| 证照管理 | `dms_rider_certificate` 子表（驾驶证/行驶证/健康证/从业资格证/其他），整体替换保存；按有效期自动标记 有效/已过期 |
| 到期提醒 | 每日定时扫描，`kyc.cert.expire.warn.days`（默认 30 天）内到期或已过期 → 产生预警类型 7「证照/资质到期」；台账「到期预警」列 + 「仅看到期预警」筛选 |
| 审核流 | 待提交 → 待审核 →（通过/驳回）；驳回必填审核意见；通过写生效时间；**审核通过后不可直接改，需先驳回**（保证留痕唯一） |
| 外部平台背书 | 外部平台配送员记录渠道快照 + 背书机构 + 背书结论 + 有效期，不落内部证件细节 |
| 无资质不接单 | `KycService.assertEligible` 已接入《调度任务》指派/改派、《订单池》抢单；判定 = 认证已通过 + 背书未过期 + 证照未过期；由配送参数 `verification.eligibility.enforce` 控制（**默认关闭**，见 §6） |
| 与配送员档案一致性 | 审核结果回写 `dms_rider.verify_status`（0-待审核 / 1-已通过 / 2-已拒绝或失效），不新建重复状态列 |

**B2. 车辆检查内嵌出车/收车（2026-09-13 增补，业界 check-out / check-in 单证口径）**

用户的研判成立：**检查不该是独立台账，而是「出车」与「交车」两个动作的组成部分**——检查必须在车边、在交接瞬间完成，且两次检查是同一辆车的前后对照。落地如下：

| 环节 | 实现 |
|------|------|
| 出车登记 | 两步向导：①绑定信息（配送员/车辆/原因）②**出车前检查**（里程/油量/6 项车况/位置/照片）→ 落 `inspectionType=1` 检查单 → 检查通过才允许绑定，并把 `binding_id` **回写**到检查单（原实现该列永远为空，「关联巡检」恒 0，本次修复） |
| 交车 | 工具栏与行内双入口：①收车登记（交车里程默认=出车里程，**不得更小**；交车地点）②**收车后检查**（同结构，`inspectionType=2`）→ 同一事务内落检查单 + 交车 + 解绑 |
| 门控 | 出车/收车检查均**强制**（参数 `verification.departure.inspection.required` / `verification.return.inspection.required`，默认 `true`）；检查单必须属于所选车辆且不可重复使用 |
| 异常闭环 | 收车检查异常 → 车辆置**「维修中」(2)**（不回到空闲）并自动生成《车辆维护》**维修待办**（defect → work order，维保号走 `WB` 号段，内容含异常项与巡检单号）；出车检查异常 → 禁止出车并提示转《车辆维护》 |
| 抽检/定检 | 巡检台账保留为只读台账 + 审核 + 详情，**新增「抽检/定检」入口**（车管员发起，类型 3/4，不关联人车绑定）——这是唯一不能被合进绑定流程的类型 |
| 单一实现（红线） | 绑定/解绑**复用《车辆管理》页的 `VehicleService.bindRider/unbindRider`**（含一车一人唯一性、车辆状态 空闲⇄已出勤、绑定流水），本模块只叠加「检查门控 + 凭证 + 异常闭环」，不再重复造第二套绑定 |

## 8. 车辆补能（加油 / 充电 / 加气 / 换电）· P0 已落地（2026-09-13）

### 8.1 归属研判结论（为什么是 Tab 而不是菜单）

| 判断 | 依据 |
|------|------|
| 落「用车管理」的 Tab | 补能是一车/一人多条的**从属流水**，没有独立单据生命周期与单据号；使用者（车管员/站长）与用车登记、巡检完全重合；且补能数据只有在同屏与「巡检的油量快照、交/出车里程差、异常预警」交叉验证才有价值（业界把 fuel log 与 inspection/telematics 放同一视图正因如此） |
| 不给它独立菜单 | 有单据号/费用/供应商/下次保养推算的（如《车辆维护》`WB` 维保号）才独立成页；**流水做成 Tab，单据才独立成菜单** |
| 不落「结算收款」分组 | 边界：补能**只做成本台账**，不与《配送结算》重复做结算；放结算组会诱导两件事揉在一起，也误示"补能只是钱"（它同时是能耗与合规数据） |
| 归属模型「车/人二选一」 | 四轮车挂 `vehicle_id`（按仪表里程核算）；骑手两轮换电挂 `rider_id`（月租套餐按里程分摊）。一套表覆盖两类主体 |

### 8.2 数据模型

`dms_vehicle_energy_log`（**25 列**，贴合「单表 ≤ 25 列」规范；迁移 `V11.201.0`）：

`id / tenant_id / vehicle_id / rider_id / energy_type / pay_mode / quantity / unit_price / amount_yuan / odometer / mileage_since_last / unit_cost / station / occurred_at / card_no / voucher_url / abnormal_flag / abnormal_reason / remark` + 审计列（`deleted/create_time/update_time/create_by/update_by/version`）

- `energy_type`：1-汽油 2-柴油 3-充电 4-换电 5-加气；`pay_mode`：1-现金 2-油卡 3-电卡 4-月租套餐 5-平台代扣。
- **不给单号**：流水无独立生命周期（与《车辆维护》的 `WB` 号形成对照）。
- `card_no` 为 P1「一卡一车一人」稽核预留锚点。

### 8.3 派生口径（服务端自动，前端不传）

| 字段 | 口径 |
|------|------|
| `mileage_since_last` 区间里程 | 本次仪表里程 − **上次同主体**补能里程（按补能时间倒序取最近一条有里程的记录）；首条为空 |
| `unit_cost` 每公里成本 | 金额 ÷ 区间里程；无区间里程时**不臆造**（置空） |
| 百公里油耗 | 数量 × 100 ÷ 区间里程，**派生不落库**（可由两字段还原，避免冗余列）；仅燃油/燃气类计算 |
| 月租套餐分摊 | 骑手换电（`pay_mode=4`）填「当次里程」后同样按里程分摊出每公里成本——这正是横向比较油车与电车成本的公平口径 |

### 8.4 异常规则（阈值租户可配）

| 规则 | 参数 |
|------|------|
| 里程倒挂（本次里程 < 上次） | — |
| 本次里程与上次相同（无法核算区间成本） | — |
| 百公里油耗超阈值 | `energy.consumption.max.per100km`（默认 30 L/100km） |
| 每公里成本超阈值 | `energy.unit.cost.max`（默认 5 元/km） |
| 金额为空 / ≤0 | — |

命中即 `abnormal_flag=1` 并追加 `abnormal_reason`（多条以「；」连接）；列表「异常」列以 tag + tooltip 展示，支持「仅看异常」筛选。**未新建告警体系**（P1 若需推送再挂 `dms_verification_alert`）。

### 8.5 接口与页面

| 接口 | 说明 |
|------|------|
| `GET /api/dms/vehicle/energy/page` | 分页（主体类型/车辆/骑手/类型/支付方式/仅看异常/关键字(车牌·姓名·站点·卡号)/日期） |
| `GET /{id}` · `POST` · `PUT /{id}` · `DELETE /{id}` · `POST /batch-delete` | 详情 / 新增（自动派生+异常判定）/ 修改（重算）/ 删除 / 批量删除 |
| `GET /export` | 真实 xlsx（16 列） |

页面：用车管理 → **车辆补能** Tab（新增补能 / 刷新 / 打印(F8) / 导出 / 页面配置 + 表头齿轮列配置）；录入弹窗按「补能主体」二选一切换车辆或配送员选择器，`pay_mode=4` 时给出月租分摊提示；保存后直接回显「区间里程 / 每公里成本」或异常原因。

### 8.6 补能卡 / 套餐（P1 已落地）

`dms_vehicle_energy_card`（**22 列**，迁移 `V11.202.0`）：卡号/卡名称/卡类型（油卡·电卡·换电套餐·充电套餐·加气卡）/绑定主体/发卡方/月费/余额/额度/已用额度/生效·有效期/状态。

- **一卡一车一人（红线）**：卡只能绑定一个主体；绑定主体必须存在；卡号租户内唯一。
- **用卡稽核**（补能落流水时自动执行，命中即写 `abnormal_reason`）：
  1. 用卡主体 ≠ 卡绑定主体 → 「一卡一车一人校验失败」（防串用，业界 fuel card 风控核心）；
  2. 使用**已停用卡** / **已过期卡**（含补能日期早于生效日期）；
  3. **套餐额度超限**——按「除本笔以外的已用 + 本笔」判定（否则新增永远漏判），额度与已用额度均由服务端按有效期内流水汇总，**可重算**；
  4. 卡号**未建档** → 提示（不阻断，允许路边快修先用卡号记账）。
- **补能录入选卡联动**：在补能弹窗选卡后自动带出绑定主体与对应补能类型/支付方式，从源头避免稽核命中。
- 页面：用车管理 → **补能卡** Tab（卡档案 CRUD + 启停 + 额度使用率/到期着色）。

### 8.7 能耗报表（P2 已落地）

`GET /api/dms/vehicle/energy/stats`：汇总（记录数/金额/数量/有效里程/平均每公里成本/CO₂）+ **油电对比**（燃油燃气组 vs 电动组，各自每公里成本与 CO₂）+ 按能源类型分组 + 按主体（车/人）分组。

- **每公里成本是核心指标**——这是横向比较「油车 vs 电车」真实使用成本的公平口径（业界共识）。
- **CO₂ 折算**：汽油 2.30 kg/L、柴油 2.63 kg/L、加气 2.16、电 0.581 kg/kWh（用于绿色配送口径）。
- 页面：用车管理 → **能耗报表** Tab（4 张汇总卡 + 油电对比柱图 + 能源类型占比饼图 + 按主体分组表；复用 `ARReportChart`）。

### 8.8 司机端补能录入（P1 已落地）

司机端新增 `/energy`「补能登记」页（Vant）：主体默认「我（两轮车）」（有在途绑定时可切「所驾车辆」）、类型/金额/数量/里程/卡号/站点/时间/**凭证拍照上传**；提交后回显「区间里程 / 每公里成本」或异常原因。入口在「我的」页菜单。与 PC 用**同一套契约**（`POST /api/dms/vehicle/energy`）。

### 8.9 准入核验（P2 已落地）

`GET /api/dms/verification/onboarding/page`：把「人（KYC 状态/证照有效期）」×「车（当前绑定车辆状态 + 三证最早到期 + 最近一次出车前检查结果）」汇成一屏，给出**可否接单 / 可否出车**两层结论与阻塞原因（tooltip 展示）。
