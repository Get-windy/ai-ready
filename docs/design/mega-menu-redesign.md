# 菜单改造方案

## 概述

将现有树形侧边栏菜单改为「窄侧边栏 + 悬停弹出多列面板」的交互模式，借鉴截图 ERP 系统的设计。

**核心交互逻辑：**
- **一级**：鼠标悬停触发弹出面板，左侧红色竖条指示当前选中项
- **二级**：横向多列面板，按业务分组分列平铺展示
- **三级**：菜单项 = 新建表单入口；`[历史]` 按钮 = 列表查询入口

---

| 序号 | 菜单项 | 图标 | 说明 |
|------|--------|------|------|
| 1 | 销售 | 🏷 | 当前选中项，左侧红色竖条 |
| 2 | 采购 |  | |
| 3 | 仓储 | 📦 | |
| 4 | 配发收 | 🚚 | |
| 5 | 财务 | 💰 | |
| 6 | 营销 | 📣 | |
| 7 | 商城 | 🏪 | |
| 8 | 分析 | 📊 | |
| 9 | 资料 |  | |
| 10 | 设置 | ⚙ | |

**交互细节：**
- 侧边栏宽度：140px（图标+短文字横排）
- 菜单项高度：45px
- 菜单项文字字号：12px
- 悬停触发：鼠标移入 150ms 后弹出右侧面板
- 选中指示：左侧红色竖条（`border-left: 3px solid #ff4d4f`）
- 离开面板 300ms 后自动关闭

**布局规则（全屏不滚动）：**
- 整体布局占满浏览器窗口，页面级不滚动（`height: 100vh; overflow: hidden`）
- 侧边栏菜单项超出侧边栏高度时，仅侧边栏内部滚动（`overflow-y: auto`）
- 内容区整体不滚动
- 只有页面内部的表格区域和分类树内部可滚动

## 三、当前系统现状分析

### 3.1 现有菜单架构

```
后端API: GET /menu/user/client/pc-admin
    ↓
userStore.menus (MenuInfo[])  ← Pinia 存储原始菜单树
    ↓
dynamicRoutes.ts: transformMenuToRoute()  ← 菜单树→路由配置
    ↓
Vue Router 动态注册路由
    ↓
BasicLayout.vue 读取 userStore.menus 渲染侧边栏（a-menu 树形）
```

**侧边栏三种渲染模式：**
- `menuType=0 && displayGroup=1` → `a-menu-item-group`（纯分组标题）
- `menuType=0` → `a-sub-menu`（可展开目录）
- `menuType=1` → `a-menu-item`（叶子菜单项）

### 3.2 现有数据结构

### 5.4 可见性与权限控制方案

#### 第一层：「系统」菜单项的租户级可见性

**规则**：只有系统租户（`tenantId=1` 或 `isSystemTenant=true`）能看到「系统」菜单项。

**后端过滤逻辑**（`SysMenuServiceImpl.getUserClientMenus()`）：

```java
public List<SysMenu> getUserClientMenus(String clientType, Long userId, Long tenantId) {
    UserInfo user = userService.getById(userId);
    boolean isSystemTenant = tenantId.equals(SYSTEM_TENANT_ID);  // tenantId=1

    if (clientType.equals("pc-admin")) {
        if (isSystemTenant) {
            // 系统租户：返回所有菜单（menuLevel=0 + menuLevel=1）
            return buildMenuTree(getAllByClientType(clientType));
        } else {
            // 普通租户：只返回租户级菜单（menuLevel=0）
            return buildMenuTree(getByClientTypeAndLevel(clientType, 0));
        }
    }
    return buildMenuTree(getAllByClientType(clientType));
}
```

**效果**：
- 系统租户登录 → 侧边栏13项（含「系统」）
- 普通租户登录 → 侧边栏12项（无「系统」）
- 前端无需额外判断，后端已经过滤好了

#### 第二层：「系统」面板内菜单项的角色权限控制

**规则**：「系统」面板内的菜单项由**系统管理人员**通过角色权限授权给**系统租户内的工作人员**。

> 系统菜单的权限管理和租户菜单的权限管理使用相同的角色-菜单关联机制（`sys_role_menu`），区别在于管理主体不同：
> - **租户级菜单**：由租户管理员授权给租户内工作人员
> - **系统级菜单**：由系统管理人员授权给系统租户内的工作人员

**系统管理人员操作流程**：

```
1. 系统管理人员进入「系统 → 平台设置 → 角色管理」（或「设置 → 菜单配置」）
2. 创建/编辑系统级角色（如"运维管理员"、"开发管理员"等）
3. 为角色分配「系统」面板内的菜单项权限
4. 将角色分配给系统租户内的具体工作人员
```

**权限数据流**：

```
sys_menu（menuLevel=1 的系统级菜单项）
    ↓
sys_role_menu（角色-菜单关联表，系统管理人员配置）
    ↓
sys_user_role（用户-角色关联，系统管理人员分配）
    ↓
用户登录 → 获取角色 → 获取权限码列表
    ↓
userStore.permissions = ["system:tenant:list", "system:module:manage", ...]
    ↓
MegaMenuPanel 按 permissions 过滤显示
```

**前端渲染**：`MegaMenuPanel.vue` 中按权限过滤菜单项：

```vue
<!-- 计算属性：根据权限过滤可见菜单项 -->
const visibleItems = computed(() => {
  return items.filter(item => {
    if (!item.menuCode) return true  // 无权限标识的始终显示
    return userStore.hasPermission(item.menuCode)
  })
})
```

**授权示例**：

| 系统管理人员操作 | 角色 | 授权的系统菜单项 |
|----------------|------|-----------------|
| 创建角色+分配菜单+分配人员 | 超级管理员 | 系统面板全部44项 |
| 创建角色+分配菜单+分配人员 | 运维管理员 | 系统监控(9项) + 数据管理(7项) = 16项 |
| 创建角色+分配菜单+分配人员 | 开发管理员 | 开发工具(7项) + 模块管理(7项) = 14项 |

### 5.6 菜单授权体系

菜单权限分为**租户级菜单授权**和**系统级菜单授权**两条线，由不同的管理主体负责。

#### A. 租户级菜单授权（menuLevel=0 的菜单）

采用**两级授权**机制：

**第一级：平台级授权（系统管理员 → 租户）**

系统管理员或系统租户内有权限的工作人员，决定每个租户能使用哪些菜单。

```
操作入口：系统 → 租户管理 → 模块授权
控制粒度：按一级模块或具体菜单项授权
存储位置：sys_tenant_menu（租户-菜单授权表）
```

**效果**：租户登录时，只返回已授权的菜单项。

**第二级：租户内授权（租户管理员 → 内部角色）**

租户管理员在**已授权的菜单范围内**，进一步分配给内部角色。

```
操作入口：设置 → 菜单配置 → 分配角色
控制粒度：按角色分配菜单权限
存储位置：sys_role_menu（角色-菜单关联表）
```

**效果**：不同角色看到的菜单项不同，但不会超出系统授权的边界。

**租户级授权流程示意**：

```
系统管理员                    租户管理员                   普通员工
─────────                    ──────────                   ──────
授权「销售」模块 ──────────→  看到销售模块全部菜单
给租户A                                                  │
                                                         ├── 授权「销售订单」→ 销售员角色
                                                         ├── 授权「销售分析」→ 经理角色
                                                         └── 不授权「销售价格跟踪」→ 任何人看不到
```

#### B. 系统级菜单授权（menuLevel=1 的菜单）

系统菜单权限由**系统管理人员**直接授权给**系统租户内的工作人员**，只需一级授权。

```
操作入口：系统 → 平台设置 → 角色管理
控制粒度：按角色分配系统菜单权限
存储位置：sys_role_menu（角色-菜单关联表）
```

**系统级授权流程示意**：

```
系统管理人员                         系统租户内工作人员
──────────                         ──────────────
创建系统角色（运维管理员）
    │
    ├── 分配菜单：系统监控+数据管理 ──→  运维人员登录 → 看到系统监控+数据管理
    │
创建系统角色（开发管理员）
    │
    └── 分配菜单：开发工具+模块管理 ──→  开发人员登录 → 看到开发工具+模块管理
```

> **注意**：系统租户不需要 `sys_tenant_menu` 授权（系统租户默认拥有所有菜单），系统菜单的权限完全由 `sys_role_menu` 控制，由系统管理人员管理。

#### C. 后端统一查询逻辑

```java
public List<SysMenu> getUserClientMenus(String clientType, Long userId, Long tenantId) {
    // 1. 获取用户角色已授权的菜单ID集合（sys_role_menu）
    Set<Long> roleAuthorizedMenuIds = roleMenuService.getMenuIdsByUserId(userId);

    if (isSystemTenant(tenantId)) {
        // 系统租户：直接使用角色授权结果（系统菜单只需一级授权）
        return buildMenuTree(filterByIds(getAllByClientType(clientType), roleAuthorizedMenuIds));
    }

    // 2. 普通租户：还需检查租户级授权（sys_tenant_menu）
    Set<Long> tenantAuthorizedMenuIds = tenantMenuService.getAuthorizedMenuIds(tenantId);

    // 3. 取交集：必须同时通过两级授权
    Set<Long> finalMenuIds = intersection(tenantAuthorizedMenuIds, roleAuthorizedMenuIds);

    return buildMenuTree(filterByIds(getAllByClientType(clientType), finalMenuIds));
}
```

#### D. 与现有系统的关系

| 现有机制 | 适用对象 | 说明 |
|---------|---------|------|
| `validModuleCodes`（租户模块） | 普通租户 | 已有，粗粒度的模块级控制 |
| **新增 `sys_tenant_menu`** | 普通租户 | 新增，细粒度的菜单项级控制 |
| `sys_role_menu`（角色菜单关联） | 所有租户（含系统租户） | 已有，控制角色能看哪些菜单 |

> 现有 `validModuleCodes` 是模块级的粗粒度控制，新增 `sys_tenant_menu` 实现菜单项级的细粒度控制。系统租户不走 `sys_tenant_menu`，其系统菜单权限直接由 `sys_role_menu` 控制。

### 6.4 路由注册改造

`dynamicRoutes.ts` 的 `transformMenuToRoute()` 需要支持双路由注册：

```typescript
function transformMenuToRoute(menu: MenuItem, parentPath: string = ''): RouteRecordRaw[] {
  const routes: RouteRecordRaw[] = []
  
  // 主路由
  const mainRoute = buildRoute(menu, parentPath)
  routes.push(mainRoute)
  
  // 双入口：额外注册隐藏的列表页路由
  if (menu.displayMode === 1 && menu.listPath) {
    const listRoute = buildRoute({ ...menu, path: menu.listPath }, parentPath)
    listRoute.meta.hidden = true  // 不在菜单中显示，但可访问
    routes.push(listRoute)
  }
  
  return routes
}
```

### 9.5 结论与建议

#### 覆盖率统计

| 类别 | 数量 | 占比 |
|------|------|------|
| 当前已有页面总数 | ~120 | 100% |
| 改造方案已覆盖 | ~98 | **82%** |
| 改造方案中缺失 | ~22 | **18%** |

#### 缺失最严重的模块

1. **财务管理**：遗漏 7 个页面（对账、账龄、催收、核销、定金、付款审批、收付款记录）
2. **系统管理**：遗漏 4 个页面（角色、权限、数据导入、通知公告）
3. **资产管理**：遗漏 2 个页面（资产分类、资产采购）
4. **配送管理**：遗漏 2 个页面（仪表盘、实名认证）

#### 建议处理方案

1. **财务模块需补充**：在「财务」面板中增加以下菜单项：
   - 账务处理列增加：对账管理、收付款核销
   - 收款列增加：定金押金、收付款记录、催收记录
   - 付款列增加：付款审批
   - 分析→财务分析列增加：应收账龄分析

2. **系统管理需补充**：在「设置」面板中增加：
   - 系统配置列增加：角色管理、权限管理、通知公告、数据导入

3. **仓储模块需补充**：
   - 资料→仓库管理列增加：库位管理
   - 仓储→库存作业列增加：序列号管理、库内事件

4. **采购模块需补充**：
   - 采购→采购查询列增加：采购询价

5. **资料模块需补充**：
   - 商品管理列增加：定价审批、价格层级

6. **配送模块需补充**：
   - 增加：配送仪表盘、实名认证

7. **资产模块需补充**：
   - 资产管理列增加：资产分类、资产采购

8. **预算模块需补充**：
   - 增加：预算概览

9. **公共功能需确认归属**：
   - 工作台：建议作为登录后默认首页，或在分析模块增加「工作台」列
   - 图表：建议作为分析模块的子页面或公共功能
