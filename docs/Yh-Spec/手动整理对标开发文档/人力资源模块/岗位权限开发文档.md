## 1. 页面概述

### 1.1 🔴 名实不符：菜单叫「岗位权限」，实际是**岗位主数据 CRUD**

**本页与"权限"没有任何关系。** 它维护的是 `sys_position`（系统岗位主数据），且**不接触任何角色、菜单、权限码**。

页面自己已经**明说**了这一点 —— 页头有一条常驻 `a-alert`（`views/md/staff-role/index.vue:3-9`）：

```
message:      岗位权限页当前对接岗位主数据接口（/api/position）
description:  后端暂无岗位-权限/角色关联接口（仅有岗位对用户的分配接口），
              岗位的权限配置能力待后端补充端点后接入。
```

**逐项取证**：

| 证据 | 值 | 结论 |
|------|-----|------|
| 表格数据源 | `mdPositionApi.getPage(params)`（`index.vue:206-208`）→ `GET /api/position/page` | 岗位主数据 |
| 表格列（10 列） | `positionCode`/`positionName`/`deptName`/`level`/`userCount`/`sort`/`status`/`description`/`createTime`/`action`（`index.vue:188-199`） | **无任何权限列**（无角色、无菜单、无权限码） |
| 弹窗字段（7 项） | 岗位编码/名称/所属部门/级别/排序/状态/描述（`index.vue:88-159`） | **无任何权限项** |
| 导入的 API | 仅 `mdPositionApi`（`@/api/md`）与 `departmentApi`（`@/api/department`）（`index.vue:171-172`） | **未导入 `roleApi`**（`@/api/role`）、未导入任何权限 API |
| 全页关键字 | 无 `permission` / `role` / `menu` 字样（除页头 alert 文案） | **零权限能力** |

> **⚠️ 结论（P0 定位问题）**：菜单名「岗位权限」是**误导性命名**，会让使用者以为可以在这里给岗位配权限。
> **实际语义** = 系统岗位主数据维护（与「职员部门」「全部操作员」同属**系统管理**域）。
> **收敛建议（二选一，须先裁定）**：
> ① **改名**（最小成本）：菜单改名为「岗位管理」，`menu_code` 从 `md:staff-role` 改为 `md:staff-position`（`md:*:role` 后缀会让人误以为与角色有关）；
> ② **换实现**（推荐）：把菜单 `component` 直接指到 `views/system/position/index.vue`（**1301 行**，已用 `ErrorBoundary` + `PageContainer` + `BillTableList` + `FullScreenDetail`，`views/system/position/index.vue:517-539`），本页（316 行）降级废弃。
> **真正的「角色 / 权限」页面存在**，是 `views/system/role/index.vue`（**931 行**，用 `roleApi` + `menuApi` + `roleBillTypeApi` + `BillTableList`，`views/system/role/index.vue:412-424`）—— 但它**同样没有菜单**（`sys_menu` 中无任何行指向 `views/system/role`，见 §5.5），用户点不到。**若产品确实需要一个「权限配置」入口，应给 `views/system/role` 挂菜单，而不是把本页改名了事。**

### 5.2 编码规则

- **手工填写，无号段**：`positionCode` 是普通 input，编辑时 lock（`index.vue:95`）。

- **目标规格**：改走**号段**（`next-no` 体系），规则形如 `POS + 4 位序号`。

### 5.3 关键业务规则

### 5.4 🔴 `sys_user_position` 双重重伤（本页最严重的结构性缺陷）

`sys_user_position` 是「用户 ↔ 岗位」多对多关联表。devdb 实测其 **5 列**：

```
id (PK) | user_id | position_id | is_primary | create_time
```

**没有任何 `deleted` 列，也没有任何 `tenant_id` 列。** 但代码对它的使用**同时踩了两个坑**：

#### 坑 1：`@Select` 手写 SQL 写了不存在的 `deleted = 0`

`UserPositionMapper.java`（`core/api/core-api/src/main/java/cn/aiedge/position/mapper/UserPositionMapper.java`）三个方法**全部**带该条件：

| 行号 | 方法 | SQL |
|:----:|------|-----|
| `:23` | `selectPositionIdsByUserId` | `SELECT position_id FROM sys_user_position WHERE user_id = #{userId} AND deleted = 0` |
| `:29` | `selectUserIdsByPositionId` | `SELECT user_id FROM sys_user_position WHERE position_id = #{positionId} AND deleted = 0` |
| `:35` | `countUsersByPositionId` | `SELECT COUNT(*) FROM sys_user_position WHERE position_id = #{positionId} AND deleted = 0` |

→ 调用即抛　`column "deleted" does not exist`（PostgreSQL 语法/语义错误）。

> 注意：`UserPosition` **实体**也没有 `deleted` 字段（`entity/UserPosition.java` 只有 `id` / `userId` / `positionId` / `isPrimary` / `createTime`）—— 说明这是**手抄其它 Mapper 模板时留下的错误**，不是「表缺列」。

#### 坑 2（**文档首次登记，此前未被记录**）：表无 `tenant_id` 却未被多租户忽略

`MyBatisPlusConfig.IGNORE_TENANT_TABLES`（`core/base/core-base/src/main/java/cn/aiedge/base/config/MyBatisPlusConfig.java:32-71`）共 24 张表，**其中没有 `sys_user_position`**。

`ignoreTable()` 的判定是（`:141-146`）：

```java
return IGNORE_TENANT_TABLES.contains(tableName)
    || !tableName.contains("_");   // 无下划线的表名跳过
```

`sys_user_position` 含下划线且不在白名单 → **拦截器会为它的 SELECT / INSERT / UPDATE / DELETE 注入 `tenant_id`**（`AiReadyTenantLineInnerInterceptor` 只在「租户上下文不可解析」时跳过，正常登录请求**不跳过**，`:32-45`）。

→ 即使把 `deleted = 0` 删掉，仍会撞 `column "tenant_id" does not exist`。

> **⚠️ 两个坑是串联的（AND 关系）**：只修一个**不能**让表可用。修法必须**同时**：
> ① 删掉三个 `@Select` 里的 `AND deleted = 0`；
> ② 把 `sys_user_position` 加入 `MyBatisPlusConfig.IGNORE_TENANT_TABLES`（理由同 `shop_template` / `erp_group_buy_participant` 的既有先例 —— **表物理上就没有该列，不忽略不是"隔离得不好"，而是直接报错**）。

#### 受影响的调用链（全量）

| 调用方 | 行号 | 触发端点 | 后果 |
|--------|------|---------|------|
| `PositionServiceImpl.convertToVO` | `:296` | `GET /page`、`GET /list`、`GET /{id}`、`GET /dept/{deptId}`、`getByUserId` | **`GET /api/position/page` 500**（见 §9.2 P0-1） |
| `PositionServiceImpl.delete` | `:139` | `DELETE /{id}`、`DELETE /batch` | **删除 500** |
| `PositionServiceImpl.getUserIds` | `:268` | `GET /{id}/users` | 500 |
| `PositionServiceImpl.assignToUser` | `:241,249` | `POST /assign` | 500（`delete` + `insert` 双撞） |
| `PositionServiceImpl.removeFromUser` | `:261` | `DELETE /remove` | 500 |

> **⚠️ 最恶劣的一点 —— 缺陷当前是"潜伏"的，且会被"成功操作"激活**：
> `sys_position` 现有 **0 行**（devdb 实测）。`pageList` 只对**查出来的行**调 `convertToVO`（`PositionServiceImpl.java:71-73`）——**0 行 = 0 次调用 = 不报错**。
> 所以**现在打开本页是"正常"的空表**；但**用户一旦点「新增岗位」并保存成功**（create 路径不碰 `userPositionMapper`，会成功），紧接着的 `reload()` 就会 500，`ARReportPage` 弹「查询失败，请检查网络后重试」（`ARReportPage.vue:300-307`）→ **页面永久打不开，且用户会以为是自己刚才建的数据有问题**。

### 5.6 「岗位」概念在本系统里的**三套并存**（结构性缺陷）

同一个「岗位」，系统里存在**三个互不相通**的载体：

| # | 载体 | 位置 | 使用方 | 状态 |
|:-:|------|------|--------|------|
| 1 | **`hr_position`**（HR 岗位，**17 列**，含 `quota_count` 编制 / `current_count` 当前人数 / `position_level` / `responsibility`） | `hr/hr-base`，实体 `cn.aiedge.hr.organization.HrPosition` | `HrController` 的 `/hr/position/*`（**该控制器前缀缺 `/api` → 全部 404**，见《考勤记录开发文档》§6.2）、`HrServiceImpls.pagePositions` | ⚠️ **端点 404，前端无页** → 事实上未启用 |
| 2 | **`sys_position`**（系统岗位，**16 列**） | `core/api/core-api`，实体 `cn.aiedge.position.entity.Position` | 本页 + `views/system/position/index.vue` | ✅ 在用（唯一有页面的） |
| 3 | **`sys_user.post_id`**（用户身上的单个岗位列） | `core/base`，`SysUser.java` | `UserCreateRequest.postId` / `UserUpdateRequest.postId` → `SysUserController.convertToEntity`（`SysUserController.java:255,266`） | ⚠️ 列存在、DTO 有、**前端无任何页面传它**（`md/staff-all` 的弹窗不含岗位项） |

外加第 4 个载体 **`sys_user_position`**（用户↔岗位多对多 + `is_primary`），它**既没有可用的 SQL（§5.4），也没有任何 UI 入口**。

> **⚠️ 业务后果**：
> - 「一个用户有几个岗位」这个问题，**有三个互相矛盾的答案**（`sys_user.post_id` 是 1 个；`sys_user_position` 是 N 个带主岗标记；`hr_position` 是 HR 口径的编制岗位）。
> - 「岗位有多少编制」这个问题，**只有 `hr_position.quota_count` 能回答**，而它所属的模块端点 404。
> - **员工与账号完全无关联**：`hr_employee` 实测 **29 列**，**没有 `user_id`** —— 所以「某人是什么岗位」在 HR 侧（`hr_employee.position_id`）和在账号侧（`sys_position`）**是两条永远对不上的数据**。
>
> **裁决建议（P0，须产品先定）**：同一概念**只保留一套**主数据（《功能/模块不重复开发》原则）。
> 推荐收敛到 **`sys_position` 作唯一岗位主数据**，`hr_position` 通过外键或视图引用它（而不是并存两表），`sys_user.post_id` **废弃**（改用 `sys_user_position` 表达多岗 + 主岗）；`hr_employee` **补 `user_id`** 建立「员工 ↔ 账号」映射（这也是 HR 侧所有「当前登录人是谁的员工」能力的前置条件）。

## 8. 业界对标（Odoo / SAP / 金蝶 / 用友）

> 本页在 ql361 **无对应页**（该对标系统**无人力资源模块**）。以下为业界标准做法与本系统的差距。
> **参考来源：** Odoo 18 HR `https://www.odoo.com/documentation/18.0/`（章节待补充）；SAP SuccessFactors RBP / Position Management `https://help.sap.com/`（章节待补充）；金蝶 s-HR `https://vip.kingdee.com/`（章节待补充）；用友 DHR `https://success.yonyou.com/`（章节待补充）。
> 本模块已核验的调研底稿：《人力资源-业界做法调研.md》（同目录），本节引用其 §1.3 / §2.1 / §2.2 / §2.6。

| # | 能力 | 业界做法 | 本系统当前 | 差距与建议 |
|:-:|------|---------|-----------|-----------|
| 1 | **「岗位」的定位** | Odoo：`hr.job` **即招聘需求载体**（含 `no_of_recruitment` 计划招聘人数、`no_of_employee` 在岗数、`expected_employees` = 在岗 + 计划）；SAP：`Position` 是**独立 MDF 对象**（49 个标准字段），有 `targetFTE`、`positionControlled`、`vacant`、`parentPosition` | `sys_position` 只是**一张扁平字典表**（16 列，无编制、无在岗数、无职级体系、无层级） | **P1**：岗位必须能承载「编制 + 在岗 + 招聘计划」。本系统这三样分散在 `hr_position.quota_count` / `hr_position.current_count` / `hr_recruitment.headcount`，**且互不连通** |
| 2 | **岗位与角色/权限的关系** | SAP RBP 三要素：**Permission Roles（权限角色）× Permission Groups（权限组）× Target Populations（目标人群）** —— 官方明确「**先建组、再建角色**」，且带"代表他人操作"语义的角色**必须指定目标人群** | **本页（名为「岗位权限」）与权限零连线**；系统真实模型是 `用户 ↔ 角色 ↔ 菜单/权限` 经典 RBAC，**没有"目标人群 / 数据范围"维度** | **P1（命名）**：菜单名必须改（§1.1）。**P2（能力）**：SAP 的 Target Populations ≈ 本系统的 `dataScope`（`SysUser.dataScope` = `ALL/DEPT/DEPT_CHILD/SELF` + `DataScopeInterceptor`），**已存在但未与角色绑定**；**业界建议、本系统未实现**「角色 + 数据范围」的联合授权 |
| 3 | **岗位 ≠ 账号角色** | 业界把「编制岗位（HR 概念）」与「账号/角色（IT 概念）」**明确分离**，靠「人员-岗位-账号」映射连接；SAP 用 `pos2jobInfo` 同步把职位信息带入员工任职信息 | 本系统**三套岗位主数据并存**（`hr_position` / `sys_position` / `sys_user.post_id`），外加第 4 个坏掉的 `sys_user_position`；`hr_employee` **无 `user_id`** → 员工与账号**完全无关联** | **P0（架构）**：见 §5.6 收敛建议。这是本模块最贵的结构性缺口 |
| 4 | **编制管控（超编拦截）** | SAP：`positionControlled` 为真时，**分配人员会校验 `targetFTE`** 并触发稳定人头处理；金蝶/用友有**控编规则** | **无任何编制校验**：`sys_position` 无编制列；`hr_position` 有 `quota_count`/`current_count` 但端点 404；招聘 `headcount` 与二者**无关联** | **P2**：业界建议、本系统未实现。**注意 Odoo 也只能"算"不能"拦"**（`expected_employees` 是 compute 字段，无校验）—— 若要真拦，须落 Service 层校验 + 明确「编制挂在岗位还是部门」 |
| 5 | **多人在任 / 主岗** | SAP `multipleIncumbentsAllowed`（预交付标签 Mass Position）显式声明「同一职位可否多人」；`Incumbent` 字段启用 Position Management 时必须设为不可见 | `sys_user_position.is_primary` 表达「主岗」，**但表不可用且无 UI** → 该语义**从未生效** | **P1**：修表后可实现「一岗多人 + 每人一个主岗」 |
| 6 | **岗位层级** | SAP 有 `parentPosition`（**职位层级**，区别于员工汇报层级） | `sys_position` **无 `parent_id`**（注意：`sys_position_category` **有**，即"分类"是树、"岗位"不是） | **P2**：若需要职位层级须新增列；**但先确认业务是否真的需要**（多数 ERP 用「部门树 + 职级」已足够） |
| 7 | **职级 / 薪档** | SAP `payGrade` / `jobLevel` / `payRange` | `sys_position.level` 是**无字典的自由整数**（UI 1–20） | **P2**：`level` 应接字典（`dictItemApi` 已在本系统存在，`views/system/position/index.vue:540` 已在用） |
| 8 | **岗位说明书** | Odoo `hr.job` 有 `description`（富文本职责）+ `requirements`（纯文本任职要求），**且招聘需求直接复用它们** | `sys_position` 只有 `description VARCHAR(500)` 纯文本，**无 `requirements`** | **P1**：招聘侧 `hr_recruitment` 有 `description` + `requirements`（TEXT）两列 —— **岗位主数据反而比招聘需求弱**。建议岗位补 `requirements`，并让招聘需求引用岗位（见 §5.7） |

**明确不借鉴**：业界界面视觉样式；SAP 的多公司/多国/多币种岗位矩阵（本系统无多公司场景）；Odoo 的 `contract_type_id` / 招聘邮件模板等 Odoo 特有耦合。
