## 1. 页面概述

本页是外勤拜访的第三段（Review）：把「拜访执行」沉淀的记录做**只读检视** —— 顶部 7 张统计卡给总体口径，下方 9 列台账给明细，支持按「拜访结果」与「拜访日期」筛选。

| 页面 | 地址 | 组件 | 行数 | 说明 |
|------|------|------|:----:|------|
| 拜访规划 | `sales/visit-plan` | `views/sales/visit-plan/index.vue` | 387 | 计划台账 + 增改删 |
| 拜访执行 | `sales/visit-exec` | `views/sales/visit-exec/index.vue` | 442 | 签到打卡（本页数据来源） |
| **拜访检视（本页）** | `sales/visit-review` | `views/sales/visit-review/index.vue` | 140 | **纯只读**：7 张统计卡 + 9 列台账；**无行操作/无弹窗/无图表** |

### 1.1 本页是「报表页」，但当前仍未达金标准自检

《_开发指南-金标准》§一的三条路线中，**路线 B（`ARReportPage`）"仅用于纯报表"**。本页是**三兄弟页里唯一符合路线 B 适用范围的**：

| 判据 | 实情 | 结论 |
|------|------|------|
| 有写动作 / 弹窗 / 行操作 | ❌ 均无（9 列里**没有 `action` 列**，`:99-109`） | 纯只读 |
| 有行选择 / 有统计卡 | ❌ 无行选择（`ARReportPage.vue:199` 默认 false）；✅ **7 张统计卡**（`:68-76`） | 无批量动作；报表特征 |

> **两条硬缺口仍在**：① **无 `PageConfigPanel`**（查询条件/按钮显隐不可配）；② **无 `StandardPagination variant="classic"`**（分页是 `a-table` 内置形态）。按金标准自检第 4、5 项**仍未达标**，只是升级成本低于另两页。
> **本页真正的价值缺口不是外壳，而是"指标口径"** —— 见 §5.2、§8。

### 1.2 三页闭环中的位置

```
crm_visit_plan ──planId──▶ crm_visit_record ─┬─▶ GET /review/page  → summary + byDate + page
   （计划）                    （执行记录）      └─▶ GET /stats/summary → today/week/planTotal/planExecuted/coverage
```

**这是本页最需要说清的一点**：7 张统计卡**来自两个不同口径的端点** —— 3 张是**全局值**、4 张**随筛选变化**（§5.2）。

### 1.3 菜单归属「名实不符」（与另两页同源）

菜单挂在 `CRM → 外勤拜访`，但 `menu_code = sales:visit-review`、路由 `sales/visit-review`、组件在 `views/sales/` 下，**接口却是 `/api/crm/visit/*`** —— 即「菜单在 CRM、代码在 sales、接口在 crm」。

> **收敛建议**：`menu_code` 改 `crm:visit-review`。已核实（《拜访规划开发文档》§1.2）`menu_code` 仅用于唯一性检查（`SysMenuServiceImpl.checkMenuCodeExists`，`:237-244`）与按码查询（`SysMenuMapper.xml:116`）；**角色授权按 `menu_id`** 关联 `sys_role_menu` → 改码**不影响已下发权限**。

### 3.5 响应归一化（本页**自定义**，为的是拿到 `summary`）

`normalizeResponse`（`:116-123`）：

```ts
function normalizeResponse(res: VisitReviewResponse): ReportFetchResult {
  const page = res?.page
  return { list: page?.records || [], total: Number(page?.total) || 0, raw: res }  // ← raw 留住 summary/byDate
}
```

必须自定义，因为后端返回**嵌套 Map**：`{ summary, byDate, page: Page }`（`VisitRecordServiceImpl.java:94-98`），分页对象在 `page` 里而不在顶层，默认归一化（`ARReportPage.vue:281-289`，只认 `records`/`list`/`content`）拿不到。

`@loaded="handleLoaded"`（`:126-129`）：`reviewSummary.value = result.raw?.summary || null`，随后 `loadStats()`。

### 5.2 🔴 7 张统计卡的口径分裂（本页最需要说清的一件事）

`statCards`（`:68-76`）共 7 张，**来自两条不同的数据通道**：

| # | label | 取值 | 来源 | 是否随筛选变化 |
|:-:|-------|------|------|---------------|
| 1 | 今日拜访 | `stats.todayCount` | `GET /stats/summary` | ❌ **永远全局** |
| 2 | 本周拜访 | `stats.weekCount` | `GET /stats/summary` | ❌ **永远全局** |
| 3 | 计划覆盖率 | `Number(stats.coverage)`，`precision: 2`，suffix `%` | `GET /stats/summary` | ❌ **永远全局** |
| 4 | 拜访总数 | `reviewSummary.total` | `GET /review/page` 的 `summary` | ✅ 随**日期区间**变化 |
| 5 | 有意向 | `reviewSummary.interested` | 同上 | ✅ 随**日期区间**变化 |
| 6 | 一般 | `reviewSummary.normal` | 同上 | ✅ 随**日期区间**变化 |
| 7 | 无意向 | `reviewSummary.noIntention` | 同上 | ✅ 随**日期区间**变化 |

**两条因果链（须实测确认）**：

- `statsSummary()`（`VisitRecordServiceImpl.java:101-137`）**不接受任何参数**（`VisitController.java:132-136` 无 `@RequestParam`）→ 前 3 张卡**与用户选的日期区间/结果完全无关**。用户把日期改到 2020 年，第 1~3 张卡**纹丝不动**。
- `reviewPage` 的 `summary` **有意不受 `result` 过滤**：计数用的 wrapper 是 `buildWrapper(null, null, null, visitDateStart, visitDateEnd)`（`VisitRecordServiceImpl.java:64`）—— **第 3 个参数（result）硬编码为 null**。这是**正确设计**：若跟着 `result` 过滤，选了「有意向」后「一般/无意向」两张卡会恒为 0，分布卡就失去意义。
- 但 `summary` **受日期区间影响**（`:64` 日期参数透传）→ 第 4~7 张卡会随日期筛选变化，而第 1~3 张不变 → **同一条卡带上出现两种口径**，用户无从判断"为什么改了日期只有后面 4 张动"。

> **修法建议（二选一）**：① 给 `statsSummary` 加日期参数，让 7 张卡**同口径**；② 保持现状但**在 UI 标注口径**（如前 3 张卡加副标题「全局，不受筛选影响」）。**当前是无标注状态，属 P1。**

### 5.3 计划覆盖率（`coverage`）的真实口径

`VisitRecordServiceImpl.java:117-128`：`coverage = (status = 2 的计划数) * 100 / (全部未删计划数)`，`setScale(2, HALF_UP)`。

| 项 | 实情 |
|----|------|
| 分子 | `crm_visit_plan` 中 `status = 2 已完成` 且未逻辑删的计划数 |
| 分母 | **全部**未逻辑删计划数（⚠️ **包含 `status = 3 已取消`**） |
| 时间范围 | **全历史**（无日期条件） |
| 租户 / 除零 | 由多租户拦截器注入 `tenant_id`（该表有此列 ✅）；`planTotal == 0` → `ZERO`（**已防除零** ✅，对比商机 `/statistics` 的 `winRate` 除零缺陷，本处更健壮） |

> ⚠️ **P1 口径问题：已取消的计划计入分母。** 举例：10 个计划、5 个完成、3 个取消 → 覆盖率 50%；若排除取消的 3 个，应是 5/7 = 71.4%。**建议分母排除 `status = 3`。**
> ⚠️ **与业界「拜访覆盖率」不是同一个东西**：业界口径是**被拜访客户数 / 应拜访客户数**（客户维度）；本系统是**已完成计划 / 计划总数**（计划维度，实际更接近"计划完成率"）。**当前指标名（计划覆盖率）与实际口径（计划完成率）相符**，但与业界同名指标**不可比** —— UI 与文档都须写明。

### 5.4 其他计算口径

| 指标 | 实现 | 评估 |
|------|------|------|
| `todayCount` | `visit_time >= 今天00:00` **且** `< 明天00:00`（`:106-110`） | ✅ 闭区间日语义正确 |
| `weekCount` | `visit_time >= 本周一00:00`（`:112-115`），**无上界** | ⚠️ **无上界** → 若存在**未来日期**的 `visit_time`（系统允许手选未来时间，见执行页 §4.4）会被**算进本周**。建议补 `AND visit_time < 下周一00:00` |
| 周起始 | `today.with(DayOfWeek.MONDAY)`（`:104`） | ✅ ISO 周（周一起算），与中国习惯一致 |
| `summary.total` | `all.size()` —— 把**全部匹配记录拉到内存**再计数 | 🔴 见 §9.2 性能缺陷 |
| 结果分布 3 项 | `all.stream().filter(...).count()`（`:67-69`），Java 侧聚合 | 🔴 同上 |

### 5.5 权限与数据权限

前端**无任何 `v-permission`**；后端**无接口级鉴权注解**（依赖全局 Sa-Token 兜底，须实测）；**无数据权限** —— 默认查全部人的拜访记录，无「我的/下属」过滤，无行级脱敏。

> 「检视」在业界通常是**主管视角**（看全团队），所以"看全部"本身合理；但**销售也应能看自己的**，且**主管看下属**应有部门边界。当前是「任何能打开本页的人看全部」——**无边界的全可见**，需按角色区分（§8）。

## 6. 后端接口清单

### 6.1 本页调用的端点（2 个）

| 方法 | 路径 | 入参 | 返回 | 封装 | 证据 |
|------|------|------|------|------|------|
| GET | `/api/crm/visit/review/page` | `result`、`visitDateStart`、`visitDateEnd`、`page`、`size` | **裸 Map**：`{ summary, byDate, page }` | `visitReviewApi.reviewPage`（**`getRaw`**） | `api/crm.ts:691-693`；`VisitController.java:118-130` |
| GET | `/api/crm/visit/stats/summary` | **无参数** | **裸 Map**：`{ todayCount, weekCount, planTotal, planExecuted, coverage }` | `visitReviewApi.statsSummary`（**`getRaw`**） | `api/crm.ts:695-697`；`:132-136` |

**为什么两个端点都用 `getRaw`（原生 axios）而不是标准 `request`？** crm 后端**无统一响应包装**：`reviewPage` 返回 `Map<String,Object>`（`VisitRecordServiceImpl.java:94-98`），`summary` 子对象里**没有 `code` 字段** → 标准拦截器会按 `code` 判定成败而误判失败 → 故走 `getRaw`（`api/crm.ts:542-550`，**绝对路径** `CRM_BASE = '/api/crm'`（`:271`）+ 手写 `Authorization`（`:273-276`））。**有意为之，不要"修正"成相对路径。**

**响应契约（`api/crm.ts:664-687`）**：`VisitReviewSummary = { total, interested, normal, noIntention }`；`VisitReviewResponse = { summary, byDate: {visitDate, cnt}[], page }`（`byDate` **前端从未读取**）；`VisitStatsSummary = { todayCount, weekCount, planTotal, planExecuted, coverage }`，其中 `coverage` 注释为「覆盖率百分比数值（0-100，两位小数）」。

> ⚠️ **`planTotal`/`planExecuted` 返回了但一张卡都没用**（`:68-76` 只用了 `coverage`）→ 用户看到「计划覆盖率 50.00%」**看不到分子分母**，无法判断是「5/10」还是「1/2」。建议卡片副标题显示「已完成 N / 总数 M」（**无需新端点**，字段已返回）。
> ⚠️ **`byDate` 完全未使用** → 后端**每次都算了**（`VisitRecordServiceImpl.java:78-89` 一次 `GROUP BY visit_time::date` 查询）却白算。

### 6.2 拜访域全量端点（`VisitController`，前缀 `/api/crm/visit`，**共 11 个**）

`GET /plan/page`、`POST /plan`、`PUT /plan/{id}`、`DELETE /plan/{id}`、`PUT /plan/{id}/cancel`；`GET /record/page`、`POST /record`、`PUT /record/{id}`、`DELETE /record/{id}`；**`GET /review/page`、`GET /stats/summary`（本页用这 2 个）**。

### 6.3 `review/page` 内部做了什么（一次请求 = 4 次 DB 往返 + 1 次内存聚合）

`VisitRecordServiceImpl.reviewPage()`（`:61-99`）共 5 步、**4 次 DB 往返 + 1 次内存聚合**：

1. `countWrapper = buildWrapper(null, null, null, start, end)` + `select(VisitRecord::getResult)` → **`selectList` 把全部匹配行拉进内存**（`:64-66`）；
2. Java `stream().filter(...).count()` 算 `interested`/`normal`/`noIntention`，`summary.total = all.size()`（`:67-75`）；
3. `dateWrapper` 用**原生 SQL** `select("visit_time::date AS visitDate", "count(*) AS cnt")` + `GROUP BY visit_time::date` + `ORDER BY ... DESC` → `selectMaps`（`:78-89`）；
4. `pageList(null, null, result, start, end, page, size)` → 第 4 次查询（分页明细，`:92`）；
5. 组装 `{summary, byDate, page}` 返回（`:94-98`）。

> 🔴 **P1 性能缺陷（步 1-2）**：结果分布**不用 SQL 聚合**，而是把**整段日期内所有记录**拉到 JVM 再 `stream()` 计数。数据量上万时，**每次翻页都会全量传输 + 全量聚合**（翻页本身只取 20 条，计数却取全部）。**修法**：照步 3 的写法改 `GROUP BY result`，一次 SQL 出 3 个计数。
> ⚠️ **P2 契约风险（步 3 的别名）**：`AS visitDate` **未加双引号** → PostgreSQL 把标识符**折叠为小写**，`ResultSetMetaData.getColumnLabel` 极可能返回 **`visitdate`** 而非 `visitDate`；而前端类型声明的是 `visitDate`（`api/crm.ts:675`）。因**前端从未读取 `byDate`**，此问题至今未暴露。**落地趋势图前，必须先对真实响应核对 `byDate[0]` 的键名**（另注：crm 模块 `application.yml:21` 配了 `map-underscore-to-camel-case: true`，`visitdate` **无下划线，不会被自动转成 `visitDate`**）。

### 6.4 端点缺口

| 端点 | 用途 | 状态 |
|------|------|------|
| `review/page` 补 `customerId`/`salesPersonId` | 按客户/负责人筛选 | ❌ **Service 层已支持**（`buildWrapper` 收了这两个参数），**仅 Controller 未开参** → 补 2 行即可 |
| `stats/summary` 补日期/负责人参数 | 让前 3 张卡与筛选同口径 | ❌ 无参数 |
| 趋势/图表端点 | 按日/周趋势 | ❌ 无（但 `byDate` 已随 `review/page` 返回，**可直接用**） |

### 7.2 🔴 本页缺的两类指标**没有数据源**（不得发明）

| 业界指标 | 能否算 | 依据 |
|---------|-------|------|
| **平均拜访时长** | ❌ **不能** | `crm_visit_record` **无 `checkin_time`/`checkout_time`/`duration` 列**（20 列逐列核对）；且无「签退」动作 → **无数据源，禁止用 `visit_time` 与 `update_time` 之差伪造**（`update_time` 是任意编辑时间，语义完全不同） |

## 10. 验收标准（目标）

> 本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下**不存在** `e2e-crm*.cjs`）。落地脚本 `tools/e2e-crm.cjs`（界面 + 接口 + 直连 DB 对账 + 写库后复原）。

### 10.1 接口验收（建议 ≥ 15 项）

① `GET /review/page` 默认 200，返回体**含三个键** `summary`/`byDate`/`page`（`VisitRecordServiceImpl.java:94-98`）；② `page.total` 与直查 DB（`deleted = 0` + 租户条件）一致，`page.records.length = min(total, size)`；③ `page`/`size` 生效，`pageNum`/`pageSize` **同样生效**；④ `summary.total` = **同日期区间内**记录总数（**不受 `result` 影响**，`:64`）；⑤ `summary.interested + normal + noIntention` **≤** `summary.total`（**可能小于**，因 `result` 可空或为其它值 —— 必须断言「≤」而非「=」）；⑥ `result = 1` 时 `page.records` **全部** `result === 1`，而 `summary` 四项**与不传 `result` 时相同**（证明分布不受列表筛选影响）；⑦ `visitDateStart`/`visitDateEnd` **闭区间日语义**：`start = end = 今天` → 今天全天记录全部命中；⑧ 排序 `visit_time DESC`（`:38`）；⑨ `byDate` 为数组，每项含**日期与计数两键**；**逐项打印键名并核对是 `visitDate` 还是 `visitdate`**（§6.3，**接图表前必须确认**），并抽查「某日 cnt = 直查该日记录数」；⑩ `GET /stats/summary` 默认 200，返回 **5 个键**（`todayCount`/`weekCount`/`planTotal`/`planExecuted`/`coverage`）；⑪ `todayCount` 与直查「`visit_time` 落在今天 00:00~24:00」一致；⑫ `weekCount` 与直查「`visit_time >= 本周一 00:00`」一致（**注意当前无上界**，未来日期记录会被计入）；⑬ `planTotal` = `crm_visit_plan` 中 `deleted = 0` 总数；`planExecuted` = 其中 `status = 2` 数量；⑭ `coverage` 两处小数应符合 `setScale(2, HALF_UP)`；**`planTotal = 0` 时必须返回 `0` 而不是 500**；⑮ **口径交叉验证**：`status = 3 已取消` 的计划计入分母（当前行为）→ 断言覆盖率被稀释；修复后改为断言分母排除 `3`。

> 2026-09-18 更新：⑨ 按日**趋势已落地**（前端同时兜住 `visitDate`/`visitdate` 两种键名并按日期升序）→ 由「仅核键名」扩为「趋势柱计数与直查该日记录数一致」；⑮ 分母仍含 `status = 3`（后端未改）→ 仍按现状断言。

### 10.2 UI 验收（建议 ≥ 17 项）

① 菜单 `CRM → 外勤拜访 → 拜访检视`（`70003`）点开落在 `sales/visit-review`，**无配对标签页**；② 标题「拜访检视」，**统计卡 7 张**，label 逐字为「今日拜访 / 本周拜访 / 计划覆盖率 / 拜访总数 / 有意向 / 一般 / 无意向」；③ 卡片后缀：前 6 张为 `次`，「计划覆盖率」为 `%` 且**保留两位小数**（`precision: 2`）；④ 三张结果卡**颜色**分别为 `#52c41a`/`#faad14`/`#ff4d4f`；⑤ 表格 **9 列**，**无「操作」列**；方式 tag（上门蓝/电话青/其他灰）、结果 tag（有意向绿/一般橙/无意向红）文案正确，非法值回退 `-` + 灰 tag；⑥ 「打卡时间」列显示 `YYYY-MM-DD HH:mm`，空值 `-`；⑦ 查询区 2 项渲染（拜访结果 select **有可见 label**，拜访日期区间**无可见 label**）；⑧ **日期筛选生效**：改到「上月」→ 表格与**后 4 张卡**同步变化；⑨ **口径断言（当前行为，修复后改断言）**：日期改到「上月」→ **前 3 张卡（今日/本周/覆盖率）数值不变**；⑩ 「拜访结果」筛选生效：选「有意向」→ 表格**只剩有意向行**，而 **4 张分布卡数值不变**（有意为设计）；⑪ 重置后 2 项清空并回第 1 页；分页参数为 **`page`/`size`**；⑫ 导出 `拜访检视_*.csv`、UTF-8 BOM、**表头 9 列**；⑬ **当前卡片不可点击**（点击无反应、无下钻）—— 断言现状；修复后应断言「点『无意向』→ 查询条件带上 `result=3`」；⑭ 空库场景：7 张卡全 `0`、`coverage` 为 `0.00%`、表格显示 `暂无拜访检视数据`，**无任何报错/无 500**；⑮ **端到端闭环**：执行页打一次卡（关联一个计划）→ 本页「今日拜访」+1、`拜访总数` +1、对应结果卡 +1、对应日期趋势 +1；规划页确认该计划已变「已完成」→ 本页 `coverage` 上升；⑯ **断言网络无 4xx**（本页 2 个端点全部 200）；⑰ 页面控制台**无 error**（含 `ReferenceError` —— 参见《重构搬迁后必须做运行时验证》），并**登记 `onMounted` + `@loaded` 导致的 `/stats/summary` 双请求**（§9.2）。

> 2026-09-18 更新：⑦ 拜访日期区间**已有可见 label** → 改断言；⑰ **双请求已修**（改为 `fetchData()` 单链 + `onMounted` 各一次）→ 断言改为「`/stats/summary` 仅请求 1 次」；另需扩充断言集：按日趋势柱状图（可显隐、`localStorage` 记忆）、覆盖率分子分母、拜访转化率、口径标注条、表头齿轮 + 页面配置弹窗 + 经典分页栏、打印(F8)。⑬ 统计卡**仍不可下钻**（未修）→ 仍按现状断言。

## 12. 剩余缺口（不阻塞，如实登记）

1. **趋势图缺失** —— 后端 `byDate`（按日计数）**每次都在算、前端从不使用**，`#chart` 插槽闲置。**投入产出比最高的一项**（后端零改动），但**接图前必须先核对 `byDate` 键名是 `visitDate` 还是 `visitdate`**。
2. **7 张统计卡两种口径** —— 前 3 张不随任何筛选变化，且无 UI 标注。
3. **无法按客户/负责人筛选** —— Controller 未开参（Service 已支持）；**而前端类型已声明这两个参数**，接线顺序错了会变成"静默失效"。
4. **`coverage` 分母含已取消计划** → 覆盖率被稀释；且与业界「拜访覆盖率（客户维度）」不是同一指标，UI 与文档都需写明。
5. **`weekCount` 无上界** → 未来日期记录被计入本周。
6. **结果分布为内存聚合** —— 每次翻页全量传输记录再在 JVM 计数，数据量大时性能显著劣化。
7. **缺「拜访转化率」与「异常拜访」** —— 转化率数据已具备（`interested`/`total`），仅缺一张卡或一个百分数；异常中的「计划超期未执行」可算（无需新列），「地点不符」**无数据源**。
8. **缺「平均拜访时长」** —— `crm_visit_record` **无起止时间列**，**无数据源，不得伪造**（与执行页 §12-6 同一条）。
9. **统计卡不可下钻，且 `planTotal`/`planExecuted` 已返回却未展示** —— `ARStatCards` 已支持 `clickable`，`ARReportPage` 未透出；覆盖率看不到分子分母。
10. **挂载时 `/stats/summary` 双请求**（`onMounted` + `@loaded` 各一次）；**卡片 loading 与自身数据不同步**（先闪 `0`）。
11. **无数据权限、无权限码** —— 任何用户看全部；检视在业界通常是主管视角，应分角色。
12. **无「关联计划」列、无详情入口** → `plan_id` 不可见，`content`/`location` 被截断后无法完整查看。
13. **无 `PageConfigPanel`；分页非经典形态**（金标准自检第 4、5 项未过）；导出仅当前页且用原始值；两页枚举常量各写一份未抽共享常量；页面未传 `ref`。
14. **菜单名实不符**（`sales:*` 挂在 CRM 下）。
15. **无模块级 E2E、无验收截图资产**。
