## 1. 页面概述

支付配置页是设置模块的**支付渠道配置台**：上半部列出后端 JVM 内可用的支付渠道（含单笔限额与可用状态），并为每个渠道提供「参数配置」抽屉（APP ID / 商户号 / API 密钥 / 异步通知 URL / 是否启用）；下半部以两个 Tab 展示支付请求与支付记录台账。
**核心事实**：渠道参数的**保存是假的** —— 写走 `/api/config/save-value`（**只写缓存不落库**），读走 `/api/config/list`（**只返回内置 12 条**）→ **保存后重新打开抽屉永远为空**，却提示「保存成功」（README §7.1-10 已登记，本文档 §3.7 / §9 / §12 逐条取证）。

**1.1 与相邻页的分工**

| | **支付配置（本页，80623）** | **支付渠道（`md/payment-channel`，资料域）** | **支付方式（`md/payment-method`，80550）** | **在线支付对账单（财务域）** |
|---|---|---|---|---|
| 定位 | **渠道的商务参数**（APP ID / 商户号 / 密钥 / 回调 URL）+ 支付请求台账 | 渠道**档案**（`md_payment_channel` 表） | 支付**方式**字典（引用保护 + 默认唯一） | 渠道流水的**对账** |

> **分工结论（现状）**：本页的「渠道列表」**不是来自任何表**，而是来自 Spring 容器中的 `PaymentChannel` 实现类（`AlipayChannel` / `WechatChannel` / `UnionPayChannel` / `BankChannel` / `CashChannel`），限额硬编码在这些 Java 类里（`PaymentChannel.java:71,76` 接口 + 各实现的 `getMinAmount` / `getMaxAmount`）。资料域另有一张 `md_payment_channel`（15 列）**与本页无任何关系**。

**1.2 本页不提供的能力（如实登记）**

- ❌ 无页内 Tab 对应的 ql361 四个维度：**微信公众号配置 / 支付方式 / 场景配置 / 在线退款** 全部缺失（本页的 2 个 Tab 是「支付请求 / 支付记录」，是**台账**而非配置）

- ❌ 无「场景 × 支付方式」矩阵配置（ql361 场景配置 Tab）
- ❌ 无费率说明（ql361 场景配置 Tab 底部列了 6 条费率）

### 3.8 保存时的兜底校验不会触发（P2，注释与实现不符）

`api/payment/index.ts:59-74` 的注释称：

> 后端写接口 `/api/config/save-value` 返回 `{ success, message }`（无 `code` 字段），响应拦截器会将其误判为失败并 reject，因此保存后重新读取校验是否真实写入。

### 8.3 明确不借鉴

- **可以只靠已有载体完成的**：渠道参数（`appId` / `merchantNo` / `appSecret` / `notifyUrl` / `enabled`）**已在 `PaymentChannelParam` 接口声明**（`api/payment/index.ts:34-40`），只需换落库表 → 可用 `sys_config`（**已有 17 列**：`param_key` 唯一、`param_value` 文本）或 `sys_project_config`（**已在用的 KV**），**无需新增列/表**；也可落到 `md_payment_channel`（**已有 15 列**，若确认它是渠道档案的正式载体）。
- **需要新增配置键（不是新增列）的**：场景矩阵、费率、自动退款开关 —— 走现成 KV 的**新键**即可。

## 10. 验收标准（目标）

> 本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下不存在 `e2e-set-*.cjs` / `e2e-settings-*.cjs`）。落地脚本建议命名 `tools/e2e-settings.cjs`。

### 10.1 接口验收（≥ 20 项）

**渠道查询（①–④）**
① `GET /api/payment/channels?amount=100` → 200，断言返回渠道数 **≤ 5**（`ALIPAY`/`WECHAT`/`UNIONPAY`/`BANK`/`CASH` 中满足 min/max 的子集）。
② `amount=0.01` 与 `amount=99999999` → 断言返回集合**不同**（验证金额区间过滤真实生效）。
③ 断言每个渠道返回项含 `code` / `name` / `minAmount` / `maxAmount` / `available`（页面的 4 个渲染列所依赖的字段）。
④ 断言 `GET /api/payment/channels` **无权限注解**（用最小权限账号调用，**当前预期 200**，登记 P0-③）。

**台账分页（⑤–⑨）**
⑤ `GET /api/payment/request/page?pageNum=1&pageSize=20` → 200；直查 `SELECT count(*) FROM payment_request` → 断言**均为 0**。
⑥ `GET /api/payment/record/page?pageNum=1&pageSize=20` → 200；直查 `SELECT count(*) FROM payment_record` → 断言**均为 0**。
⑦ 断言 ⑤ 的封装**声明支持** `bizType` / `bizNo` / `channel` / `status` / `startTime` / `endTime` / `payerName` 七个过滤项（读 `payment/index.ts:192-203` 断言）。
⑧ **断言页面实际只传 `pageNum` / `pageSize`**（抓包 / 读源码断言，登记 P1）。
⑨ 断言 ⑥ 的封装声明支持 `channel` / `status` / `channelOrderNo` / `startTime` / `endTime` 五个过滤项（`payment/index.ts:227-235`）。

**渠道参数假保存（⑩–⑯，全部要求「改库 → 回读 → 按原值复原」）**
⑩ `POST /api/config/save-value`（`configKey=payment.channel.alipay`、`configValue={"appId":"E2E_APP","merchantNo":"E2E_MCH"}`）→ 200。
⑪ ⑩ 之后直查 `SELECT count(*) FROM sys_config WHERE param_key = 'payment.channel.alipay'` → **断言 0**（不落库，登记 P0-①）。
⑫ ⑪ 之后 `GET /api/config/list?configGroup=payment` → **断言返回中不含 `payment.channel.alipay`**（读不回，登记 P0-①）。
⑬ 直查 `SELECT count(*) FROM md_payment_channel WHERE ...`（按渠道码）→ 断言**渠道参数未写入该表**（登记 P0-②）。
⑭ 直查 `SELECT count(*) FROM sys_project_config WHERE config_key LIKE 'payment.channel%'` → 断言 **0**（亦未走真实 KV）。
⑮ 断言 `SystemConfigServiceImpl.BUILTIN_CONFIGS` 的 12 个键中**无任何以 `payment.` 开头**（读源码 / 调 `GET /api/config/list` 断言）。
⑯ 断言 `/config/save-value` **不带 `X-Tenant-Id`** 或带任意值时，写路径行为一致（因写只入缓存、读不查缓存）。

## 12. 剩余缺口（不阻塞，如实登记）

> ⚠️ **本节为施工前快照**：P0-①②③（假保存 / 无持久载体 / 零权限门控）与 P1-④–⑩**均已于本轮修复**。**仍然成立**的缺口见文末《实现收口》§④（场景清单来源、`config_key` 无唯一索引、按 §8.3/§8.4 明确不做的三项）。

> 级别口径与 README §7 一致：**P0** = 页面不可用 / 数据不落库 / 越权；**P1** = 与对标不符或能力缺失但页面能用；**P2** = 体验与一致性。

**P0**
① **渠道参数「假保存」**：`/config/save-value` 写缓存不落库，`/config/list` 只返回内置 12 条 → **保存后重新打开抽屉永远为空**，却提示「保存成功」（README §7.1-10 已登记）。
② **渠道参数无任何持久载体**：`sys_config`（8 行）、`md_payment_channel`（15 列）、`sys_project_config` **三者都不写**。
③ **零权限门控**：`/api/payment/*` 11 个端点**全部无权限注解**，前端无 `v-permission` → 任何登录用户可调用支付请求创建 / 取消 / 确认等端点。

**P1**
④ **形态完全不对标**：ql361 = 4 个配置 Tab（微信公众号配置 / 支付方式 / 场景配置 / 在线退款）；本系统 = 渠道列表 + 2 个台账 Tab。
⑤ 两个台账 Tab **恒空表**（`payment_request` 0 行、`payment_record` 0 行）。
⑥ 两 Tab **无任何查询条件**（后端与封装共支持 12 个过滤项）→ 台账页无法用。
⑦ 无场景矩阵、无费率说明、无「在线支付自动退款」开关、无「上传 API 证书」、无聚合支付申请流程。
⑧ 抽屉 5 个字段**无必填标记、无 `:rules`** → 可全空保存。
⑨ 未使用任何闲置端点：`/request` `/request/stat` `/request/{id}` `/cancel` `/confirm` `/record/stat` `/callback/{channel}`。
⑩ Tab 切换不重新加载；两 Tab 无独立 `storage-key`；无 `PageConfigPanel`、无表头齿轮、无 `StandardPagination`、无 `CategoryListLayout`。

**P2**
⑪ 源码注释与拦截器行为不符（称裸响应会被误判为失败，实际一律视为成功）→ 兜底校验分支**不会触发**。
⑫ 四处失败静默（渠道参数读取 / 渠道列表 / 支付请求 / 支付记录，均仅 `console.warn`）。
⑬ 渠道表 `row-key="code"`（与全站 `id` 惯例不一致，本表无 `id`，属合理妥协）。
⑭ 抽屉「是否启用」开关无文案标注。
⑮ 页面 alert 自述「暂存至系统参数」，与「存了读不回」的实际不符。
⑯ 「查询可用渠道」的金额是**过滤**（渠道会消失）而非「筛选提示」，语义易误解。
⑰ `payment_request`（21 列）/ `payment_record`（18 列）的**列清单未逐列核对**；后端支付状态值域未逐值核对；回调端点验签与防重放**未核对**（本文档均如实标注）。
⑱ **无本系统验收截图、无模块级 E2E**（`tools/` 下无 `e2e-set-*.cjs`）。

### ④ 仍存在的缺口（如实登记）

1. **场景清单来源不权威**：场景取自 `PaymentRequest` 实体注释登记的 3 个 `bizType`（`SALE_ORDER` / `TRADE_ORDER` / `DMS_DELIVERY`）。`payment_request` 表**实测 0 行**，源码中**无支付场景字典表**，`TRADE_ORDER` / `DMS_DELIVERY` 的中文名（"交易订单" / "配送单"）**是推定**，未找到权威字典 → 已在代码注释如实标注。
2. **`sys_project_config.config_key` 无唯一索引**：upsert 采用「先查后写」，并发首写理论上可能产生重复行（读取侧用 `orderByDesc(id) LIMIT 1` 兜底，取最新一行）。
3. **按 §8.3 / §8.4 明确不做的三项**：「上传 API 证书」（依赖文件上传能力）、聚合支付四态申请流程、费率数字 —— **均未实现，本轮也未承诺**。
4. **回调端点的验签与防重放未核对**（原 §12-⑰ 登记项）—— 本轮**未改动**，仍属实。
5. **`payment_request`（21 列）/ `payment_record`（18 列）列清单未逐列核对**：两表仍为 0 行，E2E 只做只读探针（`/request/page`、`/record/page` 返回 200），**未做行级断言**。
6. **场景配置的写接口未被 E2E 覆盖**：`POST /scenes/{sceneCode}` 会覆盖「场景↔渠道」勾选矩阵（属租户真实配置），E2E 刻意**只做只读断言**、不做破坏性写入。
