## 1. 页面概述

同步任务页是**平台运营方的数据同步台账**：列出跨数据源（源数据源 → 目标数据源）的同步任务（任务名称 / 源 / 目标 / 同步方式 / Cron 表达式 / 状态 / 上次执行），并提供「新增任务 / 编辑 / 删除 / 执行 / 启停」五个动作。它是 `61304 数据管理` 组的第 4 页（`sort=400`）。

**但本页当前是「表能建、点不动 + 执行是状态桩」的双重不可用状态**：①`cn.aiedge.datasource` 包漏配 `scanBasePackages` → 5 个端点运行期**全部 404**；②即使装配，「立即执行」也只把台账写成 `running`，**不做任何数据搬运**、与 `backend/sync-engine/` **零代码连线**。本文档的核心是把这两件事写透（§6、§9、§10、§12）。

### 8.2 业界做法要点（编号列表，保留底稿原文引用）

1. **三层模型（金蝶，B 级）**：**调度计划（schedule）→ 调度作业（job）→ 调度任务（task）**，并有「参数定义 vs 运行参数」的分离 —— 官方社区文档原文：「V6.0.1 升级后运行参数规范化，拆分为**参数定义**（开发人员定义参数名称、类型、默认值）与**运行参数**（运维人员选择参数、填写参数值）」。**这是「同步任务参数」页面的关键设计：定义权与填值权分离。** 另：金蝶有「cron 自定义执行周期」条目。
2. **要支持 cron 自定义周期**：Odoo 的 `ir.cron` 用的是**结构化字段**而非 cron 串：`interval_number`（Integer，默认 1，**SQL 约束 `CHECK(interval_number > 0)`**）+ `interval_type`（Selection，精确值 `('minutes','Minutes'), ('hours','Hours'), ('days','Days'), ('weeks','Weeks'), ('months','Months')`，默认 `'months'`）。
3. **失败与自动停用机制（Odoo 源码常量级，A 级）**：`MAX_FAIL_TIME = timedelta(hours=5)`（模块处于 `to %` 状态时，超 5 小时自动重置模块状态）；`MAX_BATCH_PER_CRON_JOB = 10`（单次 cron 最多循环处理 10 批）；`CONSECUTIVE_TIMEOUT_FOR_FAILURE = 3`（连续超时 3 次即判 FAILED）；`MIN_FAILURE_COUNT_BEFORE_DEACTIVATION = 5` **且** `MIN_DELTA_BEFORE_DEACTIVATION = timedelta(days=7)` —— **失败 ≥5 次且首次失败已超 7 天 → 自动置 `active=False` 并通知管理员**；`CompletionStatus`：`FULLY_DONE='fully done'` / `PARTIALLY_DONE='partially done'` / `FAILED='failed'` —— **三态而非二态：部分完成会立刻重排（`_reschedule_asap`），完全完成按间隔重排（`_reschedule_later`）**。
4. **并发安全用「抢占」而不是「锁等待」**：Odoo 用 `FOR NO KEY UPDATE SKIP LOCKED` 取任务，**多 worker 天然不重复执行**。
5. **失败指标要能人工看**：`failure_count`（成功自动重置）、`first_failure_date`（成功自动重置）、`priority`（默认 5，「0 为较高优先级，10 为较低优先级」，就绪排序为 `failure_count, priority, id`）。
6. **执行期可见性**：Odoo 有 `_notify_progress(done, remaining)` 与进度 API；金蝶有「调度任务追踪」「调度任务分析」「调度任务为什么一直处于运行中/计划中/终止」这类 FAQ —— **「为什么没跑」必须是能被回答的问题。**
7. **执行模式要支持分片**：金蝶有「广播分片和任务分片」；Odoo 有 batching（`MAX_BATCH_PER_CRON_JOB`）。
8. **Misfire（错过的触发）要有明确指令**：Quartz 官方教程原文「**A misfire occurs if a persistent trigger "misses" its firing time**」—— 原因是「持久化触发器因调度器关闭，或 Quartz 线程池没有可用线程执行任务」；调度器启动后会查找已 misfire 的持久化触发器，**按各自配置的 misfire 指令更新**，默认使用 **smart policy**，行为取决于触发器类型与配置。**⚠️ 具体常量（`MISFIRE_INSTRUCTION_SMART_POLICY` 等）该教程页并未展开（该页明确指向 JavaDoc）→ 底稿未取到 A 级依据，本页不引用未取证的常量名，该项显式标注「未取证」。**
9. **SAP 的后台作业是「作业名 + 优先级 + 目标服务器 + 步骤（ABAP 程序/外部程序/命令）+ 重复周期 + 作业链」**，且支持**事件触发**（SM62 建事件 → `BP_EVENT_RAISE` 触发 → SM36 里「After event」启动条件）（B 级）。
10. **并发策略的三种（底稿 §5.4 第 1 条）**：①禁止并发（前一次未结束则跳过本次）；②允许并发（可能重复处理）；③抢占式（`SKIP LOCKED`，Odoo 做法，多 worker 不重复）。**Odoo 的 `FOR NO KEY UPDATE SKIP LOCKED` 是可直接抄的并发模型。**
11. **失败重试与补偿（§5.4 第 3 条）**：Odoo **不重试、但重排** —— `PARTIALLY_DONE` → `_reschedule_asap`（立刻可再跑），`FAILED` → `_reschedule_later`（按间隔等下一次），并用 `failure_count` + `first_failure_date` 累计，达阈值自动停用并通知。**这是「避免无限重试打爆系统」的收敛设计。** 超时判定用 `CONSECUTIVE_TIMEOUT_FOR_FAILURE = 3`（§5.4 第 4 条）。
12. **单次执行要有界（§5.4 第 5 条）**：`MAX_BATCH_PER_CRON_JOB = 10` 循环上限 + 进度上报（`done`/`remaining`）—— **长任务必须能「跑一半让出」，否则会拖垮调度线程。**
13. **执行用户要显式指定（§5.4 第 6 条）**：Odoo `user_id`（`required=True`）+ `_allow_sudo_commands = False` 保护；金蝶也有「调度预置时执行作业的用户选不到管理员」FAQ —— **「定时任务以什么身份执行、有什么权限」是必须显式建模的字段。**

| 4 | **running 复位** | 无复位路径 | `last_run_status` 先置 `running` 作在途标记 → **无论成败立即改写为终态**（`dispatched` / `failed`）；超过 `inflight-timeout-seconds`（默认 600s）的历史 `running` 视为中断残留，允许重新执行，不会锁死 |
| 5 | **幂等** | 无 | 在途窗口内的重复调用直接拒绝（防双击 / 并发重复投递） |
| 6 | **状态语义厘清** | `execute` 把 `status` 置 `running` —— 等价于「执行一次＝把任务打开」 | `execute` **完全不写 `status`**。`status`（running/paused/stopped）是**启停开关**，由页面「启用/暂停」维护；执行结论走 `last_run_*` |
| 7 | **审计** | 零审计 | 新增/修改/删除/执行四端点补 `@OperationLog`（执行另加 `saveResponse=true`） |
| 8 | **租户隔离** | 读路径用请求头 | 服务层按 `tenant_id` 校验归属，跨租户访问拒绝并记日志 |

#### 新增列（迁移 `V11.409.0`）

`sys_sync_task` 16 → **19** 列：`last_run_time`、`last_run_status`、`last_run_message`（均落注释说明值域）。响应字段：`SyncTaskItem` 补 `lastRunTime` / `lastRunStatus` / `lastRunMessage`。

#### 本机实测与可预期行为

1. **迁移**：`BEGIN … ROLLBACK` 执行通过，`sys_sync_task` 列数 16→19，回滚后复原（无残留）。
2. **引擎未启动时的行为（实测环境即此状态）**：`triggerSync` 内部按 `java.net.ConnectException` 分支返回 `{success:false, message:"同步引擎未启动，请确认 sync-engine 正在运行"}` → 本实现把它转成 `last_run_status=failed` + **HTTP 200 但 `success:false`**，页面以错误提示弹出该原因。**这就是「宁可诚实报未实现，也不假成功」的落点。**
3. **引擎在线的行为（未实机验证，因不启动外部服务）**：投递成功 → `last_run_status=dispatched` + 回执「由引擎调度周期执行，本系统无法确认结果」。**未做**「投递后校验引擎日志/DB 真正确认搬运完成」的闭环 —— 见下。

#### 仍未闭环（明确登记）

| 级别 | 未闭环项 | 现状 |

#### 前端同步改动（只改文案与回读口径，**未改交互结构**）

- `views/admin/data/sync/index.vue`：顶部注释与警示条由「零连线 / 永停 running」改为「真实投递 + 为什么只报已投递」；新增 `LAST_RUN_MAP` 与 `lastRunMeta()`，在既有「上次执行」列内并列展示 `lastRunStatus` 标签（**未新增列**）；`executeTask` 改为只认回读到的 `last_run_*`，`dispatched` 提示明确写「不是数据已同步完成」，`failed` 提示写「未发生任何数据搬运」。
- `api/admin.ts`：`SyncTaskItem` 补 `lastRunTime` / `lastRunStatus` / `lastRunMessage`。

#### 判定说明（为什么这是「正确的降级」而不是「偷懒」）

任务要求「宁可诚实地报『未实现』并返回明确错误，也不要假成功」。本轮做到了：
① **有真实动作**（真的向引擎发 HTTP 请求，用的是既有通道）；
② **有真实结论**（成功=已投递、失败=引擎拒绝/无配置/在途，全部来自真实返回或真实查询）；
③ **有复位路径**（在途标记必然改写为终态 + 超时视为中断）；
④ **不越权承诺**（永不出现「同步完成」）。
唯一不能做的是「本系统自己把数据搬过去」—— 那需要表级映射与引擎配置映射两类字段，属于 §8.6 的 `sys_sync_job` 体系，**本轮不发明字段**。

## 10. 验收标准

> **前置（🔴 本页特有）**：本页**当前无法造数** —— 5 个端点运行期 404（§6.1）、`sys_sync_task` 0 行、`sys_data_source` 0 行。因此 **①–④ 是「现状断言」**（断言 404 与 200 对照组）而非功能断言；**⑤ 起的全部写链路断言在修 `scanBasePackages` 之前无法执行**，只能作为**修复后的目标断言**（执行时先记录「修复前结果」）。
> **权限账号**：`admin`（`SUPER_ADMIN`，`tenant_id=1`）用作 200 基线；另需**一个非超管账号**（建议持 `SYSTEM_ADMIN` 或 `DEPT_ADMIN`，二者均**无** `*` 通配）做 403 对账。
> **🔴 本页首要断言（P0-5 专用）**：**「立即执行」必须被证明"什么都没做"** —— 因 `execute` 是状态桩、"很容易假通过"，验收**必须包含「幂等」+「失败回滚」+「执行前后数据量对比」三类断言**（⑮–㉑ 组），并断言**无任何 HTTP 出站**到 `sync-engine`。建议落地 `tools/e2e-system.cjs`（接口 + 直连 DB 对账 + 写库后复原 + Playwright UI 截屏，参照 `tools/e2e-crm.cjs`）。

### 10.1 接口验收（**26 项**）

**可达性、基线与现状（①–⑥）**

① `GET /api/data-source/sync/list`（带 `admin` 的 `Authorization: Bearer <token>`）→ **当前期望 404**，响应体逐字含 `接口不存在: api/data-source/sync/list`（登记 P0-Ⅰ）。**修复 `scanBasePackages` 后改断言 200**。
② **阳性对照组**：同一 token 调 `GET /api/config/list` → **期望 200**（证明"404 不是环境不通"）。
③ **映射存在性对照组**：`GET /api/menu/tree`（不带参数）→ **期望 400 且 message 含 `缺少必要参数: tenantId`**（证明后端在跑、映射可用）。
④ **鉴权对照组**：不带 `Authorization` 调 ① → **期望 401**。
⑤ **超管数据可见性专项（红线②）**：修复装配后，`admin`（**必须重新登录一次**以拿到带 `tenantScopeExempt` 的新 token）调 ① → 断言 `total` **等于**直查 `select count(*) from sys_sync_task`（本轮实测 = **0**）→ **若直查有数据而接口为 0，即租户插件误注入**，按 §5.5 处置。
⑥ **`X-Tenant-Id` 语义断言**：带 `X-Tenant-Id: 1` 与不带该头各调一次 ① → 断言两者 `total` 相同 → **登记「该头目前无实际过滤效果」**。

**查询与分页、权限（⑦–⑩）**

⑦ `pageSize=1` 调 ① → 断言 `records.length ≤ 1`、`current === 1`、`size === 1`、`pages === ceil(total/1)`（`SyncTaskController.java:36-45` 内存切片）。
⑧ `page=999` 调 ① → 断言 `records === []` 且**无异常**（`fromIndex >= total` 分支，`:38`）。
⑨ **`pageSize` 无上限（登记 P2）**：`pageSize=100000` → **当前期望 200**；修复后改断言 400。
⑩ **鉴权断言**：用**非超管账号**调 `POST /`、`PUT /{id}`、`DELETE /{id}`、`POST /{id}/execute` → **期望 403**（5 个码在 `sys_permission` 中 0 行，psql 实测 `datasource:sync%` = 0）；同时断言 `select count(*) from sys_permission where permission_code like 'datasource:sync%'` = **0**（当前事实），补种子后改断言 ≥ 5。

**写链路 + 类型冲突专证（⑪–⑭）**

⑪ `POST /api/data-source/sync/`（`admin`）body 仅 `{taskName:"E2E_SYNC_TMP"}` → **修复装配后**断言 200；**直查** `select id,task_name,status,tenant_id,deleted from sys_sync_task where task_name='E2E_SYNC_TMP'` → 断言 `status='stopped'`（兜底，`SyncTaskServiceImpl.java:40`）、`deleted=0`。
⑫ **🔴 `deleted` 类型冲突专证（可执行证据）**：**只读探针** `select count(*) from sys_sync_task where deleted = false;` → **期望报错 `错误: 操作符不存在: integer = boolean`**（本轮已实测复现）；对照 `where deleted = 0` → 正常返回。→ 若 ⑪ 的 200 与"直查无行"同时出现，即命中该缺陷（端点抛错被全局兜底成 200 壳）。
⑬ **`update` 字段级语义**：先经 ⑪ 建行 → `PUT /{id}` 只传 `{status:"paused"}` → 断言 DB 中 `task_name`/`cron_expression` **保持不变**（逐字段判 null，`:49-55`）。
⑭ **`update` 对不存在 id**：`PUT /999999999` → **当前期望 HTTP 200 + `{"success":false,"message":"同步任务不存在"}`**（`SyncTaskController.java:71-73`）→ 登记「不存在也返回 200 壳」。

**🔴 幂等 / 失败回滚 / 数据量对比（⑮–㉑，本页硬要求）**

⑮ **幂等-1（连续两次执行）**：记录 `select count(*) from sys_sync_task`（记 N1）→ 连续两次 `POST /{id}/execute` → 断言两次均成功，且 **`sys_sync_task` 行数仍等于 N1**（执行不产生新行）。
⑯ **幂等-2（执行前后数据量对比 —— 目标库/目标表完全不变）**：断言 `select count(*) from sys_data_source` **执行前后完全相同**（本轮基线 = **0**）；断言 `sys_sync_task` 行数**执行前后完全相同**；并对比 `sys_sync_task` / `sys_data_source` / `scheduled_task` / `scheduled_task_log` 四表的**行数与 `max(update_time)`，执行前后必须一致** → 这是「**没有同步发生**」的正向证据。
⑰ **幂等-3（`last_sync_time` 变化 ≠ 数据搬运）**：断言执行后 `last_sync_time` **确实被刷新**（非空且递增），**同时**断言 ⑯ 的三组数据量**完全不变** → **「时间戳变了但没有任何数据搬运」**必须被同时记录。
⑱ **状态永不复位专证**：执行后直查 `status` → 断言 `= 'running'`；**等待（如 60s）后再次直查，断言仍然 `= 'running'`**；并作静态断言：grep `setStatus("stopped")` **仅命中 `SyncTaskServiceImpl.java:40` 的建单兜底**（无复位路径）→ **这是 P0-Ⅱ 的可执行证据**。
⑲ **无 HTTP 出站专证（sync-engine）**：启动本地探针（或直接用同步引擎访问日志 / `docker logs`）**监听 `http://127.0.0.1:9800`** → 调 `POST /{id}/execute` 与页面「执行」按钮 → 断言**探针 0 请求**；**对照断言**：调 `POST /api/v1/sync-config/{id}/sync`（数据导入页链路，**仅在明确允许时才执行**）在引擎未起时应返回失败文案含「同步引擎未启动，请确认 sync-engine 正在运行」（`SyncConfigServiceImpl.java:267`）→ 证明探针有效。
⑳ **失败回滚专证（脏引用）**：造一行 `source_id = 999999999`（**不存在的数据源**，本表无 FK）→ 调 `POST /{id}/execute` → 断言 **当前期望 200 且 `success=true`**（后端**无引用完整性校验**，`SyncTaskServiceImpl.java:72-80` 不读 `source_id`）；并断言**无任何回滚/补偿流水**（`select count(*) from sys_audit_log` 前后不变、无运行表新增）→ 登记「失败不会被识别，也没有回滚机制」。
㉑ **台账不得出现虚假成功（核心断言）**：对**同一行**连续执行 3 次 → 断言 `sys_sync_task` 仅该行的 `last_sync_time`/`update_time`/`status` 三个字段变化、**其余 13 列全部不变**（字段级 diff），且**不出现** `scheduled_task_log` 或任何运行流水表的新行 → **任何"成功搬运"的痕迹都不存在**。

**删除、复原与清理（㉒–㉖）**

㉒ `DELETE /{id}`（`admin`）→ 断言 200 + `{"success":true,"message":"删除成功"}`；**直查断言 `deleted=1`（逻辑删除，非物理删除）**，且 ① 的列表不再返回该行（`eq(getDeleted,false)`，`:25`）。
㉓ **删除的幂等性**：对同一 id 再 `DELETE` → 断言 `success=false` + `同步任务不存在`（`:66`）。
㉔ **「改库 → 回读 → 按原值复原」标准动作**：取一行记录原 `task_name`/`sync_type`/`status` → 经 `PUT` 改为 `E2E_SYNC_TMP2` → 经 ① 回读断言新值 → 再 `PUT` 改回原值 → 回读断言复原（**全程不得直改 DB**）。
㉕ **前端在调、后端不在的端点（本页 0 个）**：断言 6 个调用的**路径+方法**均能在后端找到 mapping；**唯一差异是"包未装配"** → 与《租户审批》（前缀不匹配）区分登记。
㉖ **清理自产数据**：⑪–㉔ 造出的行必须逐条清理（逻辑删除或物理清除测试行），完成后断言 `select count(*) from sys_sync_task where task_name like 'E2E_SYNC%'` = **0**，且 `select count(*) from sys_sync_task` 回到 **0**（本轮基线）。

> 口径见《对标开发技术参考文档》§5.6 四条落位通道：**① 环境变量 / ② core-api 的 Spring 配置（`application.yml` + profile yml）/ ③ 配置中心（数据库配置表）/ ④ 业务档案表字段**。
> **本页涉及「同步引擎地址 / cron 表达式 / 源与目标数据源凭据 / 并发策略」—— 每一项必须写明落在哪张表哪一列或哪个 yml key。**

### 11.2 落位缺口（登记）

| 缺口 | 建议 |
|------|------|
| **`sync-engine.api-url` 未在 yml 声明**（只靠 `@Value` 默认值 + 环境变量） | 补进 core-api `application.yml`（或 profile yml）并在《对标开发技术参考文档》§5.6.3 登记；**通道 1/2 的现状必须在文档里写明** |
| **Cron 有列无消费方** | 二选一：**接线**（复用 `cn.aiedge.scheduler` + `JobHandlerRegistry` 的 `job_key` 白名单）或**移除**；**不应保留"看起来能配"的假能力** |
| **并发/超时/失败阈值/执行身份 无落位** | ★需新增 `sys_sync_job` 列（**本系统设计**） |
| **运行流水无落位** | ★需新增 `sys_sync_job_run` 表（开始/结束/三态/处理条数/错误摘要/`parent_run_id`） |
| **审计开关无落位** | 建议通道 2（yml）默认开启、通道 3 支持运营关闭（但需审计「关审计」本身） |
| **平台级表豁免未以配置表达** | 见 §5.5 修法（`@InterceptorIgnore` + `setTempTenantId`）；**不得**依赖会话豁免（定时任务链路无会话上下文） |

## 12. 剩余缺口（P0 / P1 / P2）

> 口径与《系统模块/README.md》§7 对齐：**P0** = 页面不可用 / 数据不落库 / 越权 / 红线；**P1** = 与业界能力差距大但页面能开；**P2** = 体验与一致性。
> README §3.4 **P0-5**（同步任务「立即执行」状态桩、与 `sync-engine` 零连线）、§7.1 第 5 条、§7.2「数据管理 5 页无查询表单且全是前端分页」在本页的具体化见下。

### P0（8 条）

① **5 个端点运行期全部 404（README §7.1-P0-1/P0-2 的具体化）**：`cn.aiedge.datasource` 漏配 `scanBasePackages`（`AiReadyApplication.java:21-96` 不含该包），而 `:117` 的 `@MapperScan("cn.aiedge.**.mapper")` 通配 → **Mapper 注册、Service/Controller 不注册** → 「表能建、点不动」。建议：补包进扫描列表，**并逐个复核其余未列包**。
② **「立即执行」是状态桩（README §3.4 P0-5）**：`SyncTaskServiceImpl.java:72-80` 只写 `last_sync_time` + `status='running'`，**无任何数据搬运**；后端/前端却都报「同步任务已触发执行」（`SyncTaskController.java:88-94`、`sync/index.vue:321`）。建议：接通同步引擎（复用 `cn.aiedge.integration`）或**明确降级并改文案**，**不得谎报已触发**。
③ **与 `backend/sync-engine/` 零连线**：真正调引擎的代码在 `cn.aiedge.integration`（`SyncConfigServiceImpl.java:35/192/244`），由「数据导入」页消费（`views/system/data-import/index.vue:961/1096`）；全仓 grep `SyncTaskMapper|SyncTaskService` 在该包外**零命中**。建议：**写明两页分工**，避免重复开发。
④ **Cron 表达式完全不生效**：只落库，**全仓无消费方**（无解析、无调度注册、无 `next_sync_time` 计算）。建议：接线或删列。
⑤ **`status='running'` 永不复位**：无调度器、无超时/失败判定 → 任务**永久停在「运行中」**。建议：补执行流水与超时判定，或提供显式「停止/复位」动作。
⑥ **`deleted` 列类型冲突（integer vs Boolean）**：psql 探针两处复现 → **装配后读写都会在该列抛错**。建议：实体改 `Integer deleted`（与全仓 333 个文件一致）。
⑦ **本页写操作零审计（README §7.1-P0-17 的具体化）**：新增/编辑/删除/执行**不留任何流水**；`sys_audit_log` 实测 **0 行**。建议：按「时间 + 主体 + 来源 IP + 目标记录 + 操作 + 变更前后值 + 结果」落审计（README §1.3 红线③）。
⑧ **5 个权限码 0 行（README §7.1-P0-16 的同源）**：`datasource:sync:*` 在 `sys_permission`（共 264 行）中 **0 行**；前端又**零 `v-permission`** → 非超管「按钮可见但点了 403」（当前被 404 掩盖）。建议：补权限种子 + 前端补指令，并**统一命名域**（`datasource:sync:*` vs `system:datasource:*` 二选一）。

### P1（11 条）

⑨ **`fetchData` 静默吞错**（`sync/index.vue:356-358`）→ 失败时表格静默变空表（**404 的表现就是空表**）。
⑩ **数据源加载失败仅 `console.warn`**（`:368-370`）→ 下拉恒空无解释。
⑪ **0 查询条件**：无查询表单/搜索框/状态筛选；唯一过滤是前端分页（`:45-61`、`:244-247`）—— 与 README §7.2「数据管理 5 页无查询表单，同步任务 0 项」一致。
⑫ **前端分页 1000 条上限**：固定 `pageSize: 1000`（`:354`），`total` 用 `allRows.length`（`:239`）→ **第 1001 条起永远看不到，总数失真**。建议：改后端分页（后端已支持）。
⑬ **`next_sync_time` 死列**（`V6.14.0:259`；仅 `SyncTask.java:44/84/85` + `api/admin.ts:205` 定义）→ 接线或删列。
⑭ **状态机缺陷**：`stopped` 不可回退；「启用」从 `stopped` 直跳 `running`（`:329`、`SyncTaskServiceImpl.java:40`）。
⑮ **无业务校验**：无 Cron 格式校验、无「源 ≠ 目标」校验、无数据源存在性校验、无任务名重复校验（前后端均无）。
⑯ **未达金标准路线 A**：无 `ErrorBoundary`、无布局组件、无列配置齿轮、无 `PageConfigPanel`、无经典分页（`:2`、`:45-48`、`:63-114`、`:249-258`）。
⑰ **执行期零可见性**：无进度、无运行流水、无「为什么没跑」的解释入口（底稿 §4.4 第 6 条：**「为什么没跑」必须是能被回答的问题**）。
⑱ **无并发/超时/失败阈值/执行身份**（表无列、代码无逻辑）→ 对照 Odoo 四条策略（底稿 §4.4 第 3、4 条）差距最大的一项。
⑲ **平台级表未豁免多租户（红线②本体，README §7.1-P0-15）**：`sys_sync_task` 有 `tenant_id` 且不在白名单 → 非超管/旧 token 会被注入 `tenant_id` → **查回 0 行且不报错**（当前因表本身 0 行而看不出来）。建议：读全局用 `@InterceptorIgnore`，写目标租户行前 `setTempTenantId`；**不得依赖会话豁免**（定时任务链路无会话上下文）。
