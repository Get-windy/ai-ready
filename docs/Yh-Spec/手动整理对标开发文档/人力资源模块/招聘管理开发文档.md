### 1.1 🔴 P0：孤儿菜单 —— 用户**点不到**这个页面

**事实（devdb `sys_menu` 实测）**：

| 项 | 值 |
|----|-----|
| `SELECT id, parent_id FROM sys_menu WHERE id BETWEEN 900 AND 999` | **只有 1 行**：`id=907`，`parent_id=900` |
| `SELECT count(*) FROM sys_menu WHERE id = 900` | **0** |
| `907.parent_id` | **900（悬空）** |
| `907` 在菜单树中的位置 | 无 —— `buildMenuTree(menus, 0)` 以 `parentId === 0` 为根（`router/dynamicRoutes.ts:1048-1056`），`907.parentId = 900 ≠ 0` → **永不进入树** |

**根因（已定位到具体迁移行）**：

1. `V8.9.0__HR_Module_Tables_and_Menu.sql` 建了老 HR 菜单 `900 人力资源` 及其子节点 `901-906`。
2. `V9.6.1__Cleanup_Legacy_Menus.sql:12` 的注释写明：`900（人力资源）及子节点 901-906 → 已被 60014（人力资源 Mega Menu）替代`；`:24-28` 删除子节点时**只列了 `901, 902, 903, 904, 905, 906`**，`:31-32` 删除 `500, 700, 900`。
3. **`V11.36.0__HR_Recruitment_Tables.sql:149-156` 在其之后执行**，插入 `907` 时把 `parent_id` 写成 **`900`**（注释 `:144` 还写着 `目录：id=907, parent_id=900 (HR模块)`）—— 而 `900` 此时**已被删掉**。
4. `V11.36.0:159-183` 的三个按钮 `9071/9072/9073` 又把 `parent_id` 写成 `907` → 三个按钮**跟着孤儿一起悬空**。

> **⚠️ 后果（P0）**：`buildMenuTree` 从根 `parentId = 0` 递归（`dynamicRoutes.ts:1048-1056`），`907` 的父是 900、而 900 不存在 → **907 及其 3 个子按钮永远不会出现在侧边栏，也不会生成路由**。
> 用户**在 UI 上完全没有入口**；即使手工在地址栏输入 `/hr/recruitment`，也会命中兜底路由 `/:pathMatch(.*)*` 落 404 页（路由表由菜单驱动，`loadDynamicRoutes` → `transformMenuToRoutes`，`dynamicRoutes.ts:958-1046`）。
> **组件本身是好的**：`router/dynamicRoutes.ts:512` 已注册 `'hr/recruitment/list': () => import('@/views/hr/recruitment/list.vue')`，且 `transformMenuToRoutes:992` 会把 `views/hr/recruitment/list` 归一化为 `hr/recruitment/list` **正好命中**该 key（`.replace(/^views\//, '').replace(/\.vue$/, '')`）→ **只要把 `parent_id` 修对，页面立刻可达**。

#### 修法（二选一，推荐 ①）

| 方案 | 做法 | 说明 |
|:----:|------|------|
| **① 挂到既有分组（推荐，1 行 SQL）** | `UPDATE sys_menu SET parent_id = 61401 WHERE id = 907;` | `61401 员工管理` 是 HR 下已有的一级分组（`V9.5.0:39`，`menu_code = mega:hr:employee`）。**必须同时把 `sort` 调到一个不冲突的值**（`61401` 下现有 `90001 员工列表`，建议 `907.sort = 2`） |
| ② 新建分组 | 新建 `61406 招聘管理`（`menu_code = mega:hr:recruitment`，`parent_id = 60014`，`sort` 建议 600），再 `UPDATE sys_menu SET parent_id = 61406 WHERE id = 907` | 语义更清晰（招聘确实是独立业务域，与考勤/薪资/组织并列），但多一行菜单 |

**同批需一起做的收尾**：

- `9071/9072/9073` 的 `parent_id = 907` **无需改动**（父修好后自动入树）。
- `907.menu_level = 2`，而 HR 其它叶子（`80530-80532`）是 `3`、`90001` 是 `0` → **层级未正确回填**，建议随修法一并订正（参考《交易模块/_开发指南-金标准》对菜单层级的核对方式）。
- `907.path = '/hr/recruitment'` **带前导斜杠**，而 HR 其它页（`hr/employee`、`md/staff-dept`）不带 → `transformMenuToRoutes:963-965` 会把前导 `/` 剥掉，**功能上无害**，但口径不统一，建议顺手改为 `hr/recruitment`。
- `907.component = 'views/hr/recruitment/list'` **无 `.vue` 后缀** —— `transformMenuToRoutes:992` 已做 `.replace(/\.vue$/, '')`，**两种写法都能命中**，无需改。

### 3.2 🔴 请求层双重缺陷（**即使修好孤儿菜单，页面依然不可用**）

本页**绕过了自己的 API 封装文件**，直接调 `request`，同时踩了两个坑。

#### 缺陷 A：`/api` 双前缀 → 全部请求 404

| 环节 | 实际值 | 证据 |
|------|--------|------|
| 后端类级前缀 | `/api/hr/recruitment` | `HrRecruitmentController.java:23` |
| 前端 axios `baseURL` | `/api` | `utils/request.ts:93` |
| **本页写法** | `request.get('/api/hr/recruitment/page', ...)` | **`list.vue:292`** |
| 合成 URL | **`/api/api/hr/recruitment/page`** | `baseURL + url` |
| vite proxy | `'/api'` → `localhost:5655`，**无 `rewrite`** | `vite.config.ts:121-123` |
| servlet `context-path` | 各 profile 都是 `/`（无补正） | `application{,-local,-gateway,-docker-test}.yml` |

**受影响的 4 处调用**（全部在 `list.vue`）：

| 行号 | 调用 | 期望 URL | 实际 URL |
|:----:|------|---------|---------|
| `:292` | `request.get('/api/hr/recruitment/page', {params})` | `/api/hr/recruitment/page` | **`/api/api/hr/recruitment/page`** ❌ |
| `:368` | `request.put(\`/api/hr/recruitment/${id}\`, form)` | `/api/hr/recruitment/{id}` | **`/api/api/hr/recruitment/{id}`** ❌ |
| `:371` | `request.post('/api/hr/recruitment', form)` | `/api/hr/recruitment` | **`/api/api/hr/recruitment`** ❌ |
| `:383` | `request.delete(\`/api/hr/recruitment/${id}\`)` | `/api/hr/recruitment/{id}` | **`/api/api/hr/recruitment/{id}`** ❌ |

> **⚠️ 反直觉的关键点**：`api/hr/index.ts` 里的招聘封装**写法是对的** —— `request.get('/hr/recruitment/page')`（`:345-346`）等 6 个函数都是**相对路径**，实际发 `/api/hr/recruitment/page` **正好匹配后端**。
> **即：正确的封装已经写好了，本页却没用它。**
> **修法**：把 `list.vue` 的 4 处裸 `request` 调用**改调 `api/hr/index.ts` 的既有封装**（`getRecruitmentPage` / `createRecruitment` / `updateRecruitment` / `deleteRecruitment`），**一行都不用新增**。
> **切勿**在 `api/hr/index.ts` 里补 `/api` 前缀（会合成 `/api/api/hr/...`，参见《_开发指南-金标准》陷阱 11）。

#### 缺陷 B：响应体解析错位 → **表永远是空的**

`list.vue:302`：

```ts
const data = res.data?.data || res.data || {}
tableData.value = data.records || []
pagination.total = data.total || 0
```

但 `utils/request.ts` 的响应拦截器**已经把 wrapper 拆掉了**：

| 步骤 | 结果 |
|------|------|
| axios 原始响应体 | `ApiResponse<Page<HrRecruitment>>` = `{code, message, data: {records, total, current, size, ...}}` |
| 拦截器分支 | `utils/request.ts:203-205` 的「`records` + `total` 特例」**不命中**（外层是 wrapper）→ 走 `:207-221` wrapper 分支 → **`return data`** |
| `res` 实际值 | **`Page<HrRecruitment>` 对象** = `{records, total, current, size, pages, ...}` |
| `res.data` | `undefined`（`Page` 没有 `data` 字段） |
| **`data` 实际值** | `res.data?.data` → `undefined`；`res.data` → `undefined`；→ **`{}`** |
| **`tableData.value`** | **`[]`（永远空）** |
| **`pagination.total`** | **`0`（永远 0）** |

> **⚠️ 结论**：**缺陷 A 修好之后，页面会从「报错 + 空表」变成「不报错但依然空表」** —— 这是最容易误判为"已修复"的地方。
> **修法**：直接用 `res.records` / `res.total`（`res` 已是 `Page`），或改用 `ARReportPage` 的 `defaultNormalize` 那套兼容写法（`ARReportPage.vue:281-289` 兼容 `records` / `list` / `content` / 数组四种形态）。
> **两个缺陷必须同时修**，只修 A 会得到"看似正常的空页面"。

### 5.1 🔴 值域三处冲突（P0）

| 字段 | DDL 注释（`V11.36.0`） | Java 实体注释 | 前端 | 裁定建议 |

### 5.2 编码规则

- **招聘职位无编号**：`hr_recruitment` **没有 `recruitment_no` / `code` 类列**（28 列里无编号字段）。
- **候选人无编号**：`hr_candidate` 同样无编号列。
- **目标规格（业界建议）**：两个对象都应给**业务单号**（如 `ZP2026090001` / `CAND2026090001`），走本系统的号段服务（`next-no` 体系）。当前只能靠 `id`（雪花）。

### 5.3 关键业务规则

| 规则 | 当前 | 目标 |
|------|------|------|
| `position_name` 唯一 / 防重复发布 | ❌ 无 | 同租户内「岗位 + 发布中」唯一，或至少给**疑似重复提示** |

## 8. 业界对标（Odoo / SAP / 金蝶 / 用友 / Workday）

> 本页在 ql361 **无对应页**（该对标系统**无人力资源模块**）。以下为业界标准做法与本系统的差距。
> **参考来源：** Odoo 18 HR / Recruitment `https://www.odoo.com/documentation/18.0/`（章节待补充）；SAP SuccessFactors Recruiting `https://help.sap.com/`（章节待补充）；金蝶 s-HR `https://vip.kingdee.com/`（章节待补充）；用友 DHR `https://success.yonyou.com/`（章节待补充）。
> 本模块已核验的调研底稿：《人力资源-业界做法调研.md》（同目录），本节引用其 §1.8 / §2.7 / §5.5。

| # | 能力 | 业界做法 | 本系统当前 | 差距与建议 |
|:-:|------|---------|-----------|-----------|
| 1 | **招聘阶段（Stage）可配置** | **Odoo**：`hr.recruitment.stage` 是**独立可配置对象**（`name` / `sequence` / `job_ids` 可按岗位限定 / `template_id` 邮件模板 / `fold` 看板折叠 / `legend_*` 图例），并用 **`hired_stage` 标记"录用阶段"**（决定录用日期）；应聘者可**看板拖拽**推阶段 | **阶段硬编码在 `status` 枚举**（5 档 / 8 档），**无阶段配置对象、无看板、无图例、无阶段专属邮件模板**；改阶段只能改代码 + 发迁移 | **P1（架构）**：新增 `hr_recruitment_stage`（可排序、可按岗位限定、含 `is_hired_stage` 标记）；`hr_candidate.status` 改为 `stage_id` 外键。**这是本页与业界最大的建模差距** |

## 10. 验收标准（目标）

> 本模块**尚无 E2E 脚本**（`tools/` 下无 `e2e-hr*.cjs`）。以下为按金标准制定的验收清单，建议脚本命名 `tools/e2e-hr-recruitment.cjs`。
> **前置条件（关键）**：`hr_recruitment` = **0 行**、`hr_candidate` = **0 行**；且**本页当前不可达**（P0-1）。
> 故验收的第一条**不是**页面元素断言，而是**可达性 + 请求层**断言：**先证伪、再修复、再回归**。
> 收尾必须删除本轮造出的招聘职位与候选人，并复核两表行数回到 0。

### 10.1 接口验收（目标 ≥ 20 项）

1. `GET /api/hr/recruitment/page` 默认查询 200，`total` 与直查 DB（`deleted = 0` + `tenant_id`）**逐值一致**。
2. `pageNum` / `pageSize` 生效：`pageSize=1` 时 `records.length === 1`。
3. `positionName` / `channel` / `status` 三个过滤参数逐个生效（造数验证）。
4. **`startDate` / `endDate` 按 `publish_date` 区间生效**（后端已支持）；非法日期格式应返回明确错误（当前抛 `IllegalArgumentException`，确认 HTTP 状态与消息）。
5. **`urgency` 参数当前被静默忽略** —— 传 `urgency=3` 与不传结果一致（记录缺陷证据）。

## 12. 剩余缺口（不阻塞，如实登记）

1. **菜单孤儿**（`907.parent_id = 900` 悬空，`V9.6.1` 删了 900 而 `V11.36.0` 又指向它）→ **页面不可达**，一行 SQL 可修。

8. **无 Offer 对象**（无金额 / 发出时间 / 答复期限 / 接受与否）。
9. **候选人 = 一次应聘**（`recruitment_id NOT NULL`）→ 同一人多条孤立记录，**无"人"这一层**。
