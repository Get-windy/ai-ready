## 1. 页面概述

清理规则页是**平台运营方的数据保留策略台账**：以表格列出「清理规则」（规则名称 / 数据表 / 条件列 / 保留天数 / 执行周期 / 更新时间 / 启用 / 操作），并提供「新增规则 / 刷新 / 编辑 / 删除 / 立即执行」五个动作。它是 `61304 数据管理` 组的第 5 页（`sort=500`，组内最后一页）。

⚠️ **本页不是「清理器」，本页是「清理器的配置界面」** —— 当前**没有任何清理器存在**：全仓不存在按 `retention_days` 删除目标表数据的执行器，「立即执行」只改一行状态（§5.3、§9.2）。

**🔴 「启用」列插槽 JSX 语义（原文，`:63-67`）**：

```html
<a-switch
  :checked="record.status === 'running'"
  size="small"
  @change="(checked: boolean) => toggleRule(record as CleanupRuleItem, checked)"
/>
```

→ 用**字符串 `'running'`** 判断开关状态；而 DB 列 `status` 是 **`integer`**（实测 `data_type=integer`、`default=1`）→ `1 !== 'running'` → **开关恒为 `false`**；且切开关触发的 `PUT` 会因类型不匹配报错 → **死开关**（§5.1、§9.2）。

## 5. 业务规范

### 5.1 状态值域（**三方语义互不相容 —— 本页最重的缺陷**）

本页**无下拉选项**，`status` 值域体现在**开关判断**与 **update 载荷**：

| 值 | 含义 | 出处 |
|---|------|------|
| `running` | 启用（开关 on） | `cleanup/index.vue:64`（`:checked="record.status === 'running'"`）、`:255`（`const nextStatus = checked ? 'running' : 'paused'`） |
| `paused` | 停用（开关 off） | `cleanup/index.vue:255` |

**🔴 三方语义对照（P0）**：前端 = `running` / `paused`（`:64`、`:255`）；实体 = `private String status`，注释「状态: running/paused/**stopped**」（**三方**，比前端多 `stopped`，`datasource/model/CleanupRule.java:37-38`）；建单兜底 = `if (rule.getStatus() == null) rule.setStatus("stopped")`（`CleanupRuleServiceImpl.java:40`）；**DB = `status integer DEFAULT 1`**（DDL `V6.14.0__Complete_Admin_Management_Tables.sql:279`；`information_schema` 实测 `data_type=integer`、`column_default=1`）。

**psql 探针复现（事务内回滚，未留数据）**：

```sql
insert into sys_data_cleanup_rule(rule_name,target_table,status) values('__probe__','__probe__','running');
-- 错误: 无效的类型 integer 输入语法: "running"
```

→ **新增**（兜底写 `'stopped'`）、**启停**（写 `'running'`/`'paused'`）、**执行**（写 `'running'`）**三条写路径全部会因类型不匹配失败**。

**🔴 第二处类型冲突 —— `deleted`（P0）**：实体 `private Boolean deleted;`（`CleanupRule.java:59`）vs DB `deleted integer DEFAULT 0`（DDL `:286`；实测 `data_type=integer`）；探针报 `字段 "deleted" 的类型为 integer, 但表达式的类型为 boolean`。**全仓约定对照**：`private Integer deleted` **333 文件** vs `private Boolean deleted` **8 文件**（本模块占 3 个）；DB 中 `deleted` 列 **integer 387 个 / boolean 20 个**（boolean 那 20 张表属 budget/expense/fixed_asset/purchase_inquiry）→ **本模块违背仓库既有约定**。

**另注**：`status INT DEFAULT 1` 的 `1` 与实体注释的 `running/paused/stopped` **无语义对应关系**（既非布尔、也无枚举映射表）→ **建模本身就是错的**；因列参与前端开关判断，**即使能写入数字也永远不显示为「启用」**。

### 5.2 流转规则（本页动作）

```
（无）── 新增 POST / ──▶ status="stopped"（兜底）／DB 列 integer → 写入失败
status="running" ── 停用（开关 off / PUT）──▶ "paused"；"paused" ── 启用 ──▶ "running"（均因 DB 类型冲突失败）
任意状态 ── 执行 POST /{id}/execute ──▶ status="running" + updateTime；【无任何数据删除】
任意状态 ── 删除 DELETE /{id} ──▶ deleted=true（逻辑删除）
（无）── cron 触发 ──▶ 【不存在：全仓无调度器消费 sys_data_cleanup_rule】
```

| 动作 | 后端 | 前置校验 | 失败文案 | 副作用 | 行号 |
|------|------|:--------:|---------|--------|----|
| 新增 | `POST /api/data-source/cleanup/` | 无（后端**不校验**） | 无（恒返 `success:true`） | `createBy/updateBy/tenantId/deleted(false)` 兜底；`status` 空则补 `"stopped"` | `CleanupRuleServiceImpl.java:32-43` |
| 编辑 | `PUT /api/data-source/cleanup/{id}` | **有**：`selectById` + `deleted` 判空 | `清理规则不存在`（`success:false`） | 逐字段「非 null 才覆盖」+ `updateTime` | `:46-61`；`CleanupRuleController.java:70-74` |
| 删除 | `DELETE /api/data-source/cleanup/{id}` | **有**：同上 | `清理规则不存在` | **逻辑删除** `deleted=true` | `:64-70`；控制器 `:80-83` |
| **执行** | `POST /api/data-source/cleanup/{id}/execute` | **有**：同上 | `清理规则不存在` | **只写 `status="running"` + `updateTime`** | `:72-79`；控制器 `:85-94` |

**✅ 正确之处**：`update`（`:47-48`）/ `delete`（`:65-66`）/ `execute`（`:74-75`）**都先 `selectById` 并判 `deleted`** —— 与《租户列表开发文档》§9.2 登记的「`PUT`/`DELETE` 无存在性校验」相比，**本页这一点是对的**。
**⚠️ 但返回值口径不一致**：`update`/`delete`/`execute` 对不存在返回 `success:false` 但 **HTTP 仍 200**（`CleanupRuleController.java:72`、`:82`、`:92`）→ 前端因此**不会走 catch**，`executeRule` 会照常弹「清理任务已触发执行」（`:269`）→ **"不存在"也被报成"已触发"**。

### 5.3 取值口径（三个业务字段**只存不用**）

**🔴 P0-6「立即执行」不删任何数据** —— `CleanupRuleServiceImpl.java:72-79` 全文：

```java
@Override
public boolean execute(Long id) {
    CleanupRule rule = cleanupRuleMapper.selectById(id);
    if (rule == null || rule.getDeleted()) return false;
    rule.setStatus("running");
    rule.setUpdateTime(LocalDateTime.now());
    return cleanupRuleMapper.updateById(rule) > 0;
}
```

| 判定 | 实测结论 | 证据 |
|------|---------|------|

### 5.6 安全口径（🔴 必须登记为 P0）

**事实**：`target_table` 是 `VARCHAR(100) NOT NULL` 自由文本（DDL `:275`）；`condition_column` 同为自由文本（`:276`）；后端**只存不校验**（`CleanupRuleServiceImpl.java:32-43`、`:51`）—— 无表名白名单、无 `sys_` 前缀约束、无 SQL 标识符校验（无正则、无 `information_schema` 存在性检查、无关键字黑名单）；前端**无二次输入**（仅一次 popconfirm，`:71-76`）；5 个端点**零审计**。
**潜在后果**：一旦真接清理执行器，本页就是**任意表 `DELETE` 入口**（且条件列用户可控 → **SQL 注入面**）。

### 8.2 业界做法要点（A/B 级，逐一引用官方原文）

1. **大数据量删除的正确姿势是「删分区」而不是 `DELETE`**（**A**）—— PostgreSQL 官方原文级：「Bulk loads and deletes can be accomplished by adding or removing partitions... **Dropping an individual partition using `DROP TABLE`, or doing `ALTER TABLE DETACH PARTITION`, is far faster than a bulk operation. These commands also entirely avoid the `VACUUM` overhead caused by a bulk `DELETE`.**」；「`DROP TABLE measurement_y2006m02;` 能快速删除数百万行，因为『不必逐条删除每一条记录』」。
2. **先 DETACH 再删，可以保留数据做备份/聚合**（**A**）—— 官方建议「也可先 `DETACH PARTITION` 保留数据做备份/聚合/报表，再删除」。**这正是「清理规则」页面最该提供的交互：先归档，再清理。**
3. **加锁级别决定了能否在线操作**（**A**）—— `DETACH PARTITION` 默认需父表 `ACCESS EXCLUSIVE`；**加 `CONCURRENTLY` 后只需 `SHARE UPDATE EXCLUSIVE`**（有使用限制）；`ATTACH PARTITION` 只需 `SHARE UPDATE EXCLUSIVE`，而 `CREATE TABLE ... PARTITION OF` 需 `ACCESS EXCLUSIVE`。
4. **分区键要按「清理边界」设计**（**A**）—— 官方原文「设计时应尽量让要一次性删除的数据位于同一分区」→ **落地到本系统就是「按月份 / 按租户分区」二选一，取决于清理诉求。**
5. **三种分区法**（**A**）—— `RANGE`（区间，下界含、上界不含）、`LIST`（枚举）、`HASH`（`MODULUS`/`REMAINDER`）。
6. **WAL 保留有明确规则**（**A**，底稿 §4.3 第 10 条）—— 名称数值更小的归档 WAL 段可删、**建议保留多套备份集**、时间线历史文件适合**无限期保留**、**增量备份的依赖关系 PostgreSQL 没有内置机制，必须自行记录**。
7. **备份目录本身也要清理**（**B**）—— SAP 有专门的「Housekeeping for Backup Catalog and Backup Storage」，官方推荐用 **"Delete Older Backups..."** 动作，并列出「删除旧备份的前提条件」。
8. **保留期是可配策略而非硬编码**（**B**）—— 金蝶把「运行日志默认多久进行清理和归档」作为**独立 FAQ 条目**，说明这是客户常问、且产品里可配的项。

#### 分区 vs 分批 DELETE（本轮最关键的取舍，含 A 级依据）

- **官方口径**：PostgreSQL 对大表历史数据的推荐做法是 **`DETACH PARTITION` / `DROP PARTITION`**（元数据操作、近乎瞬时，且避免删除海量行带来的 WAL 膨胀与 autovacuum 回收压力）。本页 §8.4 / §8.5 已收录该结论为 **A 级**。
- **本系统实测（2026-09-19）**：`SELECT count(*) FROM pg_partitioned_table` = **0** —— 目标库**没有任何分区表**。因此 `DETACH/DROP PARTITION` 路径**当前无对象可用**；而在非分区表上模拟只能靠 `TRUNCATE`/`DROP`，那是整表级破坏，与「按保留期滚动删除」语义不符。
- **本轮决策**：首版用**分批 DELETE**（每批 1000 + 单次上限 5000）。这与 §8.6-3「首版先做归档+删除、分区留作二期」的既定建议一致。
- **代码中的固化**：`CleanupExecutor` 类注释写明该取舍；每次执行都会探测 `pg_partitioned_table` 并把 `partitioned` 结果随回执返回，便于判断何时可切换；若目标表是分区表，回执末尾会附「官方推荐用 DETACH/DROP PARTITION」提示。

## 10. 验收标准

> **🔴 安全前置（本页第一条，违反即作废）**：
> ① **对共享 `devdb` 只允许只读断言**（`select` / `count(*)` / `information_schema`）—— **严禁**在共享库上执行本页的写/删类断言；
> ② 所有**写库、删库、清理执行类断言**（§10.1-⑧~⑱）**只允许在一次性隔离库**（如丢弃库 **`devdb_cleanup_e2e`**）执行，跑完**整库丢弃**；
> ③ **即使端点通了，也不得对生产共享库触发 `POST /{id}/execute`**（一旦执行器落地，该动作会删数据）；
> ④ 隔离库的库名、连接串、构建方式须写进 E2E 脚本头部，**不得默认指向 `devdb`**。

> **前置**：本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下无 `e2e-system-*.cjs` / `e2e-admin-*.cjs`）。建议落地 `tools/e2e-system.cjs`（接口 + 直连 DB 对账 + 写库后复原 + Playwright UI 截屏，参照 `tools/e2e-crm.cjs`），脚本落位见 MEMORY「开发纪律：脚本落位+收尾关进程」。
> **权限账号**：`admin`（`SUPER_ADMIN`，`sys_user.is_super_admin=t`）用作 200 基线；另需一个**非超管账号**（建议持 `SYSTEM_ADMIN` 或 `DEPT_ADMIN` 角色，均**无** `*` 通配）做 403 对账。
> **前置事实（决定「断言会怎么失败」，必须写进脚本注释）**：端点**当前全部 404**（§6.3）、`status`/`deleted` **类型冲突致写操作必失败**（§5.1）、**表 0 行**（§7.1）→ 下面标 **「当前必然失败」** 的断言，**必须判定为 FAIL 而非 SKIP**（否则就是假通过）。

### 10.1 接口验收（**24 项**）

**可达性与基线（①–④）**

① `GET /api/data-source/cleanup/list`（带 `admin` 的 `Authorization: Bearer <token>` + `X-Tenant-Id: 1`）**期望 200**，返回体含键 `records`/`total`/`current`/`size`/`pages`（`CleanupRuleController.java:40-46`）。**当前必然失败** —— 实测 404 `{"code":404,"message":"接口不存在: api/data-source/cleanup/list"}`（§6.3）。
② **阳性对照**：`GET /api/config/list` → **期望 200**（证明 token 与后端可用）。**当前应通过**。
③ `GET /api/data-source/cleanup/list` **不带 `Authorization`** → **期望 401**（实测未挂 token 全部 401）。
④ **超管数据可见性专项**：断言接口 `total` **等于** `select count(*) from sys_data_cleanup_rule where deleted=0`（**本轮实测全表 0 行**）→ 断言 `total === 0` 且 `records.length === 0`。**若返回 0 行须区分两种原因**：① 表里确实没有规则（本轮事实）；② 租户插件误注入（README §1.3 红线②）。**判定法**：若直查 `select count(*) from sys_data_cleanup_rule` **也为 0** → 属原因①；若直查 > 0 而接口 `total=0` → **红线②复发**，立即登记 P0。

**查询与分页（⑤–⑦）**

⑤ **无查询条件专项**：断言 `list` 端点**不接受任何过滤入参** —— 传 `ruleName=X` / `status=running` **均被忽略**（返回结果不变）。**这是 §3.3 的可执行证据**。
⑥ 分页断言：`page=1&pageSize=1` → 断言 `records.length ≤ 1` 且 `current === 1`、`size === 1`、`pages === ceil(total/1)`。
⑦ **`pageSize` 无上限**（登记 P2）：传 `pageSize=100000` → **当前期望 200**（无校验）；修复后改断言 400。

**🔴 执行不删数据专项（⑧–⑫，本页硬要求；仅隔离库）**

> **前提**：以下 ⑧–⑫ **只允许在一次性隔离库 `devdb_cleanup_e2e` 执行**。隔离库内**先经接口造 1 条规则**，`targetTable` 指定为**隔离库中行数已知 > 0 的表**（建议直接建一张 `e2e_cleanup_target` 并插入 N 行，N 已知）。

⑧ **执行前后数据量对比（真查目标表行数）**：记录 `POST /{id}/execute` 之前的 `select count(*) from <targetTable>` = **N**，调用接口（**期望 200**），再查 `select count(*) from <targetTable>`。**断言：`count(*) === N - 期望清理行数`（即「期望减少 N 行」）** —— 当前实现**必然保持 `N` 不变** → **该断言在修复前必然 FAIL**。**脚本必须把它判为 FAIL 并打印两侧数值**（打印 `before=N, after=N, expected=<N-k>`）。这是本页**唯一能证明「清理真的发生了」的断言**，**不得写成「断言 count 不变」以求得通过**。
⑨ **幂等断言**：对同一 `id` **连续两次** `POST /{id}/execute`（每次之间重新查目标表行数）→ 断言**第二次相对第一次不再产生任何额外的数据变化**（`count_2 === count_1`），且两次均不报错（或因「已在运行中」返回明确业务错误）。**注意**：当前实现第二次会再次 `setStatus("running")` + 刷 `updateTime`（`CleanupRuleServiceImpl.java:76-77`）→ **`update_time` 会变**，所以幂等断言必须**同时**断言「目标表行数不变」**与**「`update_time` 不得再被刷新」（或把「会刷新」明确登记为已知非幂等）。
⑩ **失败回滚断言（非法表名）**：新增一条 `targetTable = 'no_such_table_e2e'` 的规则，调用 `POST /{id}/execute` → **断言「不得返回 `success=true`」**（即 `success:false` 或 HTTP 4xx/5xx）。**当前必然失败**：`execute` **不读 `targetTable`**（`:72-79`）→ 表名非法它**照样返回 `success:true`**；而它**想写** `status="running"` 时又会撞 `status` 的 `integer` 类型冲突（§5.1）→ **真正发生的是「报成功但状态没写进去」**（若端点已装配）。
⑪ **静态断言——零删除语句**：对**清理链路**（`cn.aiedge.datasource` 包内 `*CleanupRule*` / `*Cleanup*` 文件）做全仓 `grep`，断言 `DELETE` / `TRUNCATE` / `JdbcTemplate` / `executeUpdate` **命中数为 0**。**当前应通过**（这是对「当前实现真没有删数据」的正向确证）。
⑫ **静态断言——三个字段不被后端读取**：对 `CleanupRuleServiceImpl.java` + `CleanupRuleController.java` 断言 `getTargetTable()` / `getConditionColumn()` / `getRetentionDays()` 的**调用点数为 0**（只在 setter 侧出现）。**当前应通过**（§5.3）。

**写链路与类型冲突（⑬–⑱，仅隔离库）**

⑬ **新增会因类型冲突失败专项**：`POST /api/data-source/cleanup/` body 仅 `{ruleName:'E2E-T1', targetTable:'e2e_cleanup_target'}` → 断言**写库成功**且直查该行 **`deleted=0`**、`status` 为**兜底值**（`CleanupRuleServiceImpl.java:40` 写 `"stopped"`）。**当前预期**：HTTP 200 但**直查无此行**（`status` 的 `integer` 列拒绝 `"stopped"`）→ **当前必然失败**。
⑭ **启停会因类型冲突失败专项**：`PUT /{id}` body `{"status":"running"}` → 断言 DB `status` **被改为字符串枚举值**。**当前必然失败**（§5.1 探针）。
⑮ **期望的列型（修复后断言）**：断言 `select data_type from information_schema.columns where table_name='sys_data_cleanup_rule' and column_name='status'` **等于**修复后选定类型（`character varying` 或 `boolean`）；断言 `column_name='deleted'` 的 `data_type === 'integer'`（对齐仓库 333 文件约定）。**当前实测**：`status` = **`integer`**（default `1`）、`deleted` = **`integer`**（default `0`）。
⑯ **「改库 → 回读 → 按原值复原」标准动作**：取造出的规则行，记录原 `rule_name` / `retention_days` → 经 `PUT /{id}` 改名/改天数 → `GET /list` **回读断言新值** → 再经 `PUT` **改回原值** → `GET /list` **回读断言复原**（**全程不直改 DB**）。
⑰ **逻辑删除断言**：`DELETE /api/data-source/cleanup/{id}` → 断言 200；**直查断言 `deleted=1`（逻辑删除，非物理删除）**，且 `GET /list` 不再返回该行（服务层手写过滤 `.eq(CleanupRule::getDeleted, false)`，`CleanupRuleServiceImpl.java:25`）。
⑱ **删除幂等**：对同一 `id` 再 `DELETE` 一次 → 断言返回 `success:false` + `message:"清理规则不存在"`（`CleanupRuleController.java:82`；`CleanupRuleServiceImpl.java:66` 判 `deleted` 提前返回 false）。

**权限断言（⑲–㉑）**

⑲ 用 **`admin`（SUPER_ADMIN）** 调 `GET /list`、`POST /`、`PUT /{id}`、`DELETE /{id}`、`POST /{id}/execute` → **期望全部 200**（`*` 通配旁路，`UnifiedPermissionCacheService.java:86`）。
⑳ 用**非超管账号**（无 `*`）调**同上 5 个端点** → **期望全部 403**（5 个 `datasource:cleanup:*` 码在 `sys_permission` 中 **0 行**，devdb 实测）。
㉑ 断言 `select count(*) from sys_permission where permission_code like 'datasource:cleanup%'` **= 0**（当前事实）；补种子后改断言 ≥ 5。**同时**断言 `select count(*) from sys_permission where permission_code like 'system:datasource%'` = 0（同模块另一组码，登记 §9.2-P1）。

**清理自产数据与契约（㉒–㉔）**

㉒ **清理自产数据**：⑬–⑱ 造出的规则必须**按 id 逐条清理**；完成后断言隔离库中本页造的数据 **0 行**。（共享库 `sys_data_cleanup_rule` 仍应为 **0 行**。）
㉓ **响应契约一致性（登记 P2）**：断言 `list` 返回体**不含** `code` 键（裸 Map），而 `POST`/`PUT`/`DELETE`/`execute` 返回体**含** `success` 但**不含** `code` → **4 个写端点的 HTTP 状态恒 200**（含业务失败）。
㉔ **「不存在」的可执行证据**：`POST /api/data-source/cleanup/999999999/execute` → 断言 **HTTP 200** 且 body `{success:false, message:"清理规则不存在"}`；**并断言前端在该响应下仍会弹「清理任务已触发执行」**（`cleanup/index.vue:268-269` 不判 `success`）→ 登记为 P1。

## 12. 剩余缺口（P0 / P1 / P2）

> 口径与《系统模块/README.md》§7 对齐：**P0** = 页面不可用 / 数据不落库 / 越权 / 红线；**P1** = 与业界能力差距大但页面能开；**P2** = 体验与一致性。
> README **§3.4 P0-6**（清理规则「立即执行」不删任何数据）、**§7.2**「清理规则 `status`（DB `integer`）与本页/实体语义冲突，写操作注定失败」、**§7.1 P0-1/P0-2**（包未装配 → 404）、**§7.1 P0-17**（平台侧无审计）在本页的具体化见下。

### P0（7 条）

① **「立即执行」不删任何数据（README §3.4 P0-6 的本体）**：`execute` 只 `setStatus("running")` + `setUpdateTime`（`CleanupRuleServiceImpl.java:72-79`）；**全仓不存在按 `retention_days` 删除目标表数据的执行器**（包外 grep 零命中）；`targetTable`/`conditionColumn`/`retentionDays` **只存不用**；前端仍弹 `清理任务已触发执行`（`cleanup/index.vue:269`）—— **谎报**。建议：按 §8.6，首版做「**归档到历史表 + 删除**」，分区留二期；`execute` 改为**异步任务 + 可查询结果**，并在无执行器时**返回明确的「未实现」而非成功**。
② **`status` 列类型冲突（README §7.2 的本条）**：DB `integer DEFAULT 1`（DDL `:279`）vs 实体 `String`（`CleanupRule.java:38`）vs 前端 `'running'`/`'paused'`（`:64`、`:255`）—— **三方语义互不相容**；探针复现 `无效的类型 integer 输入语法: "running"` → **新增/启停/执行三条写路径全部注定失败；开关恒 false（死开关）**。建议：**改列型**（`varchar` 枚举 **或** `enabled boolean`），并同步改实体、前端与 `CleanupRuleServiceImpl.java:40` 的兜底值。
③ **`deleted` 列类型冲突**：DB `integer DEFAULT 0`（DDL `:286`）vs 实体 `Boolean`（`:59`）→ 探针报 `字段 "deleted" 的类型为 integer, 但表达式的类型为 boolean`；且**未标 `@TableLogic`**。全仓对照：`private Integer deleted` **333 文件** vs `Boolean` **8 文件**（本模块占 3 个）→ **违背仓库既有约定**。建议：改为 `Integer` + 补 `@TableLogic`。
④ **5 个端点运行期全部 404（README §7.1 P0-1/P0-2 的本页具体化）**：`cn.aiedge.datasource` **不在** `scanBasePackages`（`AiReadyApplication.java:21-96`，`grep` 命中 0），而 `@MapperScan("cn.aiedge.**.mapper")` **通配**（`:117`）→ 「**表能建、点不动**」；实测 `GET /api/data-source/cleanup/list` → **404**（对照组 `/api/config/list` → 200）。建议：补进 `scanBasePackages`。
⑤ **权限码未落库 → 非超管必然 403（README §7.1 P0-16 同源）**：`datasource:cleanup:*` 5 个码在 `sys_permission`（264 行）中 **0 行**；前端又**零 `v-permission`** → 「**按钮可见但点了 403**」。建议：补权限种子（迁移）+ 前端补指令；并**统一命名域**（P1-⑫）。
⑥ **写操作零审计（README §7.1 P0-17 的具体化）**：新增/编辑/删除/执行**都不留痕**（`sys_audit_log` 实测 0 行）。**清理是破坏性动作，无审计等于无法追责**。建议：按「时间 + 主体 + 来源 IP + 目标表 + 影响行数 + 操作 + 结果」落审计（SAP SAL 字段口径，README §1.3 红线③）。
⑦ **输入无安全校验（潜在任意表 DELETE 入口）**：`target_table` / `condition_column` 是**自由文本**，**无白名单、无 `sys_` 前缀约束、无 SQL 标识符校验**（DDL `:275-276`；`CleanupRuleServiceImpl.java:32-43`、`:51`）。**一旦真接清理执行器，本页就是任意表 `DELETE` 入口 + SQL 注入面**。建议：按 §5.6 八条加固。

### P1（10 条）

⑧ **`cron_expression` 无消费方** → 配了不生效，清理永不自动发生（§5.3、§11）。
⑨ **无查询条件（0 项）** 且后端 `list` **不支持任何过滤入参**（`CleanupRuleController.java:29-32`）—— 本组 5 页中唯一「既无查询表单也无 `#extra`」的页面（§3.3）。建议：后端补 `ruleName`/`status` 入参 + 前端补查询表单（**须走横向网格**，MEMORY「查询区必须横向网格」）。
⑩ **静默吞错**：`catch { allRows.value = [] }`（`:292-294`）**不区分「接口 404」与「列表为空」** → 后端未装配与空表在界面上**完全一致**。建议：补 `message.error` + `console.error`，404 时明确提示「后端服务不可用」。
⑪ **分页被绕过 + 静默截断**：前端硬编码 `pageSize: 1000`（`:290`），> 1000 条规则**静默丢失**；后端已有的真分页（`:34-38`）**被前端弃用**。建议：改走后端分页。
⑫ **命名域不一致**：本控制器 `datasource:cleanup:*`（`:27/50/62/78/86`）vs 同模块 `DataSourceController` 的 `system:datasource:*` → 两组码**库中均不存在**且**域不统一**。建议：统一到 `system:data:cleanup:*`（与 `menu_code=system:data:cleanup` 对齐）。
⑬ **placeholder 指向不存在的表**：`:121` 写 `如: sys_operation_log`，本库对应表是 **`sys_oper_log`**（README §3.5 实测 18 列 / 13474 行）→ **示例本身就是错的**。建议：改为 `sys_oper_log` 或改为**白名单下拉**。
⑭ **「不存在」被报成「已触发」**：`execute` 对不存在的 id 返回 `success:false` 但 **HTTP 200**（`CleanupRuleController.java:92`）→ 前端不判 `success`，仍弹成功文案（`:268-269`）。建议：改用 HTTP 404，或前端判 `success` 后再提示。
⑮ **无归档 / 无执行历史 / 无 dry-run**：14 列无相关列。建议：★新增 `archive_before_delete` / `last_run_time` / `last_run_result` 三列（§8.7）。
⑯ **未达金标准路线 A**：无 `ErrorBoundary`（页面级 0 处）、无 `CategoryListLayout`、无列配置齿轮、无 `PageConfigPanel`、无经典分页、无序号列（`:2`、`:45-48`、`:49-89`、`:186-195`）—— 与 README §7.2「30 页全部无 `PageConfigPanel` / 无 `storage-key` / 无经典分页 / 无列配置齿轮」一致。
⑰ **`tenantId` 走请求头而非会话**：「平台侧全局规则」实际落在 `tenant_id=1`（系统租户）名下，**平台运营视角下的全局清理规则无处安放**；且请求头缺失时服务层**不加过滤**（`:26`）→ 跨租户可见（§5.5）。建议：读全局用 `@InterceptorIgnore(tenantLine="true")`，写目标租户行前 `MyBatisPlusConfig.setTempTenantId(tid)`；**不得依赖会话豁免**（对定时任务/无会话链路无效）。

### P2（8 条）

⑱ **响应契约不统一**：`list` 返裸 `Map`（`:29`），4 个写端点返 `{success}` 且**无 `code`**（`:52/64/80/88`）→ 前端**必须两套解包**（`api/admin.ts:5-18` 注释）。建议：统一为 `Result` 包装。
⑲ **表单无 `:model` / `:rules`**：`required`（`:108`、`:117`）**只是视觉星号**，仅 2 条手写校验（`:234-235`）；`条件列`/`保留天数`/`Cron表达式`/`描述` **零校验**。建议：补 `:rules` + 行内校验。
⑳ **弹窗无 `destroy-on-close`**（`:93`）、`@cancel` 不重置表单（`:99`）。建议：对齐《租户套餐》弹窗。
㉑ **「更新时间」无格式化**：`updateTime` 直接原值输出 ISO 串（`:192`）。建议：补日期格式化。
㉒ **`pageSize` 无上限校验**（后端 `:31`）→ 可传 `pageSize=100000`。建议：`@Max` 或服务端钳制。
㉓ **无统计卡 / 无页内 Tab / 无导出 / 无打印 / 无快捷键 / 无行选择 / 无自动刷新**（全文）；⚠️ 统计卡落地前需先有**执行历史列**（P1-⑮），否则只能造**假指标**。
㉔ **`status` 的 `DEFAULT 1` 本身无语义**：既非布尔、也无枚举映射表，与实体注释 `running/paused/stopped` **无对应关系** → **建模本身就是错的**（§5.1）；即使能写入数字，开关也**永远不显示为「启用」**。建议：随 P0-② 一并在迁移中修正。
㉕ **无本系统验收截图、无模块级 E2E**（README §7.3 末条）；本页**尤其需要**在一次性隔离库（`devdb_cleanup_e2e`）建立**「执行前后数据量对比」**这条断言（§10.1-⑧），**否则「执行成功」永远是假通过**。
