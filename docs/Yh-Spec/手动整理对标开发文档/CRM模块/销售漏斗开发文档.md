### 3.2 数据源（**唯一的接口调用**）

```ts
async function loadData() {                            // :168-179
  loading.value = true
  try {
    const list = await opportunityStageApi.exportList() // GET /api/crm/opportunity/export
    opportunities.value = Array.isArray(list) ? list : []
  } catch (e) { opportunities.value = []; console.warn('[销售漏斗] 商机数据获取失败', e) }
  finally { loading.value = false }
}
onMounted(() => { loadData() })                        // :181-183
```

| 项 | 实情 |
|----|------|
| 端点 | `GET /api/crm/opportunity/export`（`api/crm.ts:497-499` → `CustomerOpportunityController.java:77-86`） |
| 入参 | `exportList(params?: { keyword?, customerId?, opportunityStage?, status?, salesPersonId? })` —— **本页不传任何参数**（`:171` 无参调用） |
| 返回 | **裸 `List<CustomerOpportunity>`**（无分页、无响应包装）；`request` 拦截器对裸数组**原样返回**（`utils/request.ts:198-200`） |
| 过滤 | 后端 `buildQueryWrapper` 只加 `deleted = 0`（`CustomerOpportunityServiceImpl.java:60`）+ 多租户插件注入 `tenant_id` |
| 规模风险 | **全量拉取**，无分页/无时间窗 → 商机量上万时**首屏 JSON 与前端聚合都会变慢**（P2） |

> **⚠️ 页面顶部 `a-alert` 的说明与实际原因不符（P2）**：文案写「后端商机统计接口（`/crm/opportunity/statistics`）返回**裸 Map 暂不可直接用**，本页由商机全量列表实时聚合」（`:8`）。但 `utils/request.ts:214-220` 对**无 `code` 字段的裸响应视为成功**并把整个对象返回给调用方 —— **裸 Map 是可用的**。
> **真正不能用的原因**见 §6.3-①：`getOpportunityStatistics` 在「有商机但无已关闭商机」时**除零**（`CustomerOpportunityServiceImpl.java:198-200`，`winCount + loseCount = 0`）→ 接口 **500**。**文档/宣传文案应如实改写**（否则后人会照字面理解成「Map 结构不可用」而做出错误的技术决策）。

### 3.3 统计卡（4 张，`statCards`，`:76-90`）

| # | 标题 | 计算 | 单位/样式 | 行 |
|:-:|------|------|-----------|----|
| 1 | 商机总数 | `list.length` | suffix `个` | `:85` |
| 2 | 预计总金额 | `Σ (Number(o.estimatedAmount) || 0)` | precision 2、prefix `¥` | `:80,86` |
| 3 | 赢单金额 | `Σ (Number(o.actualAmount) || 0)`，**仅 `status === 2`** | precision 2、prefix `¥`、绿色 `#52c41a` | `:78,81,87` |
| 4 | 赢单率 | `closedCount ? Math.round((winList.length / closedCount) * 1000) / 10 : 0` | precision 1、suffix `%` | `:82-83,88` |

其中 `winList = list.filter(o => o.status === 2)`（**赢单**）、`loseCount = list.filter(o => o.status === 3).length`（**输单**）、`closedCount = winList.length + loseCount`（`:78-83`）。

> **口径**：赢单率 = **赢单数 ÷（赢单数 + 输单数）**，即**只统计已关闭商机**（`status ∈ {2,3}`），未关闭的跟进中商机**不进分母** —— 与业界「Win Rate」口径一致 ✅。
> **⚠️ 但当 `closedCount = 0` 时值显示为 `0`**（`:83` 三元兜底），无法区分「赢单率 0%」与「无已关闭商机」（P2，业界通常显示 `-` 或 `--`）。
> **⚠️ 与后端 `/statistics` 的 `winRate` 公式完全一致**（`CustomerOpportunityServiceImpl.java:198-200` = `winCount * 100 / (winCount + loseCount)`，两位小数），仅**精度不同**（前端 1 位、后端 2 位）→ 同一指标两处实现，**应收敛为一处**（P2）。

### 3.5 阶段明细表（`stageColumns` + `stageRows`）

**列定义（4 列，`:130-135`）**：`stageName` 阶段 110｜`count` 商机数 90 right｜`amount` 预计金额 130 right｜`percent` 数量占比 100 right。`row-key="stage"`（`:33`，唯一 ✅）。

**行计算（`:146-160`）**：对 `STAGES` 逐阶段

```ts
count   = list.filter(o => o.opportunityStage === s.stage).length
amount  = 该阶段 Σ (Number(o.estimatedAmount) || 0)
percent = total ? (rows.length / total) * 100 : 0      // total = list.length（全部商机）
```

**渲染**：`stageName` 用 `a-tag :color="record.color"`（`:38-40`）｜`amount` 走 `formatMoney`（`:162-165`：空/NaN → `-`，否则 `zh-CN` 两位小数）｜`percent` 走 `record.percent.toFixed(1)%`（`:46`）。

> **⚠️ 本页没有计算阶段间转化率（P1）**：`percent` 是**「该阶段商机数 ÷ 全部商机数」的数量占比**，**不是**「该阶段 → 下一阶段的转化率」。Salesforce `Sales Funnel` 的核心指标是 **stage-to-stage conversion**（逐级转化率）——本页完全没有（§8）。
> **⚠️ `percent.toFixed(1)` 无空值兜底（P2）**：`stageRows` 恒产出数字（`:157` 有三元兜底），但模板直呼 `record.percent.toFixed(1)`，一旦未来改为异步/可空数据即 `TypeError` → **白屏**（叠加 §3.1 无 `ErrorBoundary`）。

|:-------:|------|------|--------------------------------|----------------|
| 1 | 初步接触 | `#91caff` | `case 1 → "初步接触"` | 10 |

## 4. 计算规则与值域

### 4.1 全部计算一览（本页无持久化、无写操作）

| 输出 | 公式 | 行 |
|------|------|----|
| 商机总数 | `list.length` | `:85` |
| 预计总金额 | `Σ estimatedAmount`（**不加权**） | `:80,86` |
| 赢单金额 | `Σ actualAmount WHERE status === 2` | `:81,87` |
| 赢单率 | `win / (win + lose) × 100`（保留 1 位） | `:82-83,88` |
| 漏斗各段值 | `count(opportunityStage === s)` | `:96-102` |
| 阶段预计金额 | `Σ estimatedAmount WHERE opportunityStage === s` | `:156` |
| 阶段数量占比 | `count(s) / list.length × 100` | `:157` |

### 4.2 口径边界（**如实登记，勿当成缺陷忽略**）

| 边界 | 事实 | 影响 |
|------|------|------|
| **只覆盖阶段 1–5** | 阶段不在 1–5（含 `NULL`）的商机**不进入任何段**，但仍计入「商机总数」 | **阶段明细 5 行之和 ≠ 商机总数**；差值即「未分阶段商机」 |
| **后端未给阶段兜底** | `CustomerOpportunity.opportunityStage` **无默认值**（`entity/CustomerOpportunity.java:27`），`POST /api/crm/opportunity` 也未赋值 | 若创建时未传阶段 → 该行为 `NULL` → **静默漏统计**；且后端 `advanceStage` 会 `int currentStage = getOpportunityStage()`（`CustomerOpportunityServiceImpl.java:109`）→ **NPE 500**（商机页问题，此处登记为跨页影响） |
| **含已关闭商机** | `win`（赢单）把阶段置 5（`:134-135`），`lose`（输单）**只改 `status`、不改阶段**（`:155-159`） | 漏斗图包含**已赢单与已输单**的商机 → 口径是「阶段分布」而非「在谈管道」；业界 Sales Funnel 通常只含 **open pipeline**，或至少可视化区分 |
| **金额不加权** | 无 `probability` 加权 | 「预计总金额」= 乐观上限（§3.6） |
| **无时间维度** | 无 `expectedCloseDate` / `actualCloseDate` 过滤 | 无法回答「本季度漏斗」「环比」 |

## 5. 业务规范

### 5.1 本页的角色

- **只读**：不写任何表（无 `POST`/`PUT`/`DELETE` 调用）。
- **无参数**：不传过滤条件，永远是「全租户全量商机」。
- **无下钻**：漏斗段与表格行都**不可点击**（`ARReportChart` 支持 `point-click` 事件、`ARStatCards` 支持 `card-click`，本页**都没接**，`:11-14,17-23`）→ 看到「某阶段积压 50 个」**无法跳到对应商机列表**。

> **裁定建议（P1）**：接 `@point-click` / `@card-click`，跳 `crm/opportunity?opportunityStage=N`（商机页查询条件已支持 `opportunityStage`，`CustomerOpportunityController.java:29`）。

### 5.2 与其它页面的口径一致性

| 指标 | 本页 | 其它页 | 一致？ |
|------|------|--------|:------:|
| 赢单率 | `win/(win+lose)` 保留 1 位 | 后端 `/statistics` 的 `winRate` 保留 2 位 | ⚠️ 精度不同 |
| 阶段名称/颜色 | 前端 `STAGES`（`:64-70`） | **四份实现各自硬编码**：`crm/opportunity/form.vue:46`、`crm/opportunity-stage/index.vue:138,144`、后端 `getStageDesc` 的 `switch` | ⚠️ 改一处不会同步（P2，应收敛为「商机阶段」页 `70321` 的主数据或共享常量） |
| 阶段赢率 `probability` | **未用** | 商机页可展示 | ❌ 本页缺 |

### 5.3 缺失能力（对照本系统已有数据）

| 能力 | 数据是否已就绪 | 本页 |

## 10. 验收标准（目标）

> 本模块**尚无 E2E**（`tools/` 下不存在 `e2e-crm*.cjs`）。落地脚本命名 `tools/e2e-crm.cjs`。

### 10.1 接口验收（建议 ≥ 12 项）

1. `GET /api/crm/opportunity/export` 默认 200，返回**裸数组**，条数与直查 DB（`deleted=0` + 租户）一致。
2. 造 5 个阶段各 1 条 → 数组长度 5，`opportunityStage` 覆盖 1–5。
3. `export?status=2` / `status=3` / `salesPersonId=x` **逐个生效**（当前页未传，但端点支持，为后续补筛选用）。
4. `export?opportunityStage=3` 只返回阶段 3。
5. `GET /statistics` **正常情况下**返回 `totalCount/winCount/loseCount/activeCount/totalEstimated/totalActual/winRate` 七个键。
6. **`GET /statistics` 在「有商机但无赢单无输单」时 → 断言当前 500（除零）**，修复后改断言 200 且 `winRate = 0`。
7. `GET /statistics?salesPersonId=` 过滤生效。
8. 造 1 条 `opportunityStage = null` 的商机 → **断言 `POST /{id}/advance` 500（NPE）**（登记缺陷）。
9. `POST /{id}/win?actualAmount=` 后：`status=2`、`opportunityStage=5`、`probability=100`、`actualAmount` 落库。
10. `POST /{id}/lose?loseReason=` 后：`status=3`、`opportunityStage` **不变**（断言现状，作为口径依据）。
11. `POST /{id}/advance` 阶段 < 5 时 `+1` 且 `probability` 与 `getProbabilityByStage` 一致；阶段 = 5 时 400「商机已处于最终阶段」。
12. **写库隔离**：所有造数用专用测试客户/商机并在断言后清理。

## 12. 剩余缺口（不阻塞，如实登记）

1. **无任何查询条件（P1）** —— 报表无法对比；后端 `export` 已支持 `status`/`salesPersonId`/`customerId`/`opportunityStage`，**只差前端查询区**。
2. **无阶段间转化率（P1）** —— Salesforce 式 `stage-to-stage conversion` 缺失，数据已就绪。
3. **金额口径不加权（P1）** —— `probability` 已落库却未用，预计金额系统性高估。
4. **漏斗只有数量口径（P1）** —— 缺「金额漏斗」切换。
5. **无下钻（P1）** —— 段/卡/行都不可点，看到问题无法定位。
6. **缺 `ErrorBoundary`（P1）** —— 渲染异常即白屏。
7. **`a-alert` 口径说明失真（P1）** —— 真因是后端 `/statistics` **除零 500**，不是「裸 Map 不可用」。
8. **无时间维度 / 无人员维度（P1）** —— `expected_close_date`/`sales_person_id` 列已存在。
9. **阶段口径含已赢/已输商机（P2）** —— 与业界「open pipeline」口径不同。
10. **`NULL` 阶段商机静默漏统计（P2）** —— 阶段明细之和 ≠ 商机总数；且该行 `advance` 必 NPE。
11. **阶段名/颜色/赢率分别在前端 3 处 + 后端 1 处硬编码（P2）** —— 应收口到「商机阶段」页（`70321`）。
12. **全量拉取无分页（P2）**；加载失败只有 console（P2）。
13. **无刷新/无导出/无刷新提示（P2）**。
14. **赢单率口径细节（P2）** —— 无已关闭商机时显示 `0` 而非 `-`；精度与后端不一致。
15. **无验收截图资产 / 无模块级 E2E（P2）**。
