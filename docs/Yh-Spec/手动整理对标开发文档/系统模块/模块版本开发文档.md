## 1. 页面概述

模块版本页是**平台运营方查看「每个模块有哪些版本、哪个版本已发布」的台账页**。它属于 `61302 模块管理` 组的第 2 页（`sort=200`），数据源只有一张表 `sys_module_version`，**不提供新增/编辑/删除**，只在行上提供「详情」「发布」两个动作 —— 而这两个动作**当前都是纯桩**（§3.4）。

### 1.1 与相邻页的分工（`61302 模块管理` 组 4 页极易混淆，必须写清）

| 页面 | 菜单ID | 回答的问题 | 数据源 | 后端端点 | 可用性 |
|------|:-----:|-----------|--------|---------|:------:|

| **模块版本（本页）** | 62102 | 某模块**有哪些版本**、哪些已发布（**版本←→已发布态**） | `sys_module_version` | `GET /api/module/versions` | ❌ 404 + **假数据兜底** |
| **模块发布** | 62103 | 平台**发布了什么**、能否回滚 | 复用 `sys_module_version`（**无独立发布表**） | `GET /api/module/releases` | ❌ 404 + **假数据兜底** |

### 3.9 🔴 排序缺陷（P1）：`release_time` 为 NULL 的行排在**最前**

## 5. 业务规范

### 5.1 状态值域（**三方不一致**，本页最典型的契约断裂）

| 来源 | 值域 | 证据 |
|------|------|------|
| **前端映射表** | `released`(已发布) / `beta`(测试版) / `draft`(草稿)；其它值走 `default` 色 + **原样输出** | `version/index.vue:33-34` |
| **后端实体 `@Schema` 声明** | `draft` / `released` / **`rolled_back`** | `SysModuleVersion.java:34`（原文 `@Schema(description = "发布状态: draft/released/rolled_back")`） |
| **库中实测** | `released`(9 行) / `beta`(2 行) / `draft`(1 行)；**无 `rolled_back`** | psql 实测 12 行 |

> 🔴 **差异结论**：前端**有 `beta`、无 `rolled_back`**；实体注释**有 `rolled_back`、无 `beta`** → **两边值域各缺一个**。库中真实存在 `beta`（2 行）说明**实体注释才是过时的那一方**；而 `rolled_back` 是「回滚」能力的状态位，**当前既无数据也无端点**（后端 10 个 mapping 中无 rollback，§6.2）。
> **建议**：① 以库中实际取值 + 「需新增的回滚能力」为准，把值域收敛为 `draft / beta / released / rolled_back` 四值，并**在后端定义枚举类**（当前是裸 `String`，无枚举、无 `CHECK` 约束）；② 前端映射表补齐 `rolled_back: '已回滚'`。

### 5.2 版本状态流转（当前**不存在任何流转实现**）

```
        ┌──────────────────────────────────────────────┐
        │  当前实际：无状态机、无端点、无校验            │
        └──────────────────────────────────────────────┘

  draft ──(前端假「发布」按钮：只改本地对象，不落库)──▶ released
     ▲                                                    │
     │                                                    │
     └────────── rolled_back（实体注释声明，无实现）◀──────┘
```

| 动作 | 后端端点 | 前置校验 | 失败文案 | 副作用 | 可用性 |
|------|---------|:--------:|---------|--------|:------:|
| **发布新版本** | `POST /{id}/publish`（`:124-140`） | `version` 非空 | **`版本号不能为空`**（`:133`）；模块不存在 → `模块不存在`（`:137`） | 插 `sys_module_version`（`release_status='released'`）+ 同步 `sys_module.version` | ⚠️ **端点存在但前端零调用** |
| **把已有 draft 改为 released** | **无端点** | — | — | — | ❌ |
| **回滚版本** | **无端点** | — | — | — | ❌ |

> ⚠️ **注意「发布」按钮的语义**：本页行内「发布」的目标是**已存在的某一版本行**（把它标成 released），而后端 `POST /{id}/publish` 的语义是**插入一条新版本记录**（`ModuleServiceImpl.java:107-118` 是 `new SysModuleVersion()` + `insert`）。**两者不是同一个业务动作** —— 接线时必须先裁定：是把「发布」改成「把该行标为已发布」（需新增端点），还是改成「基于该模块发布新版本」（复用现有端点，但 `:124` 的 `{id}` 是 **moduleId** 而非 versionId）。
> 🔴 这是一个**易踩的语义陷阱**：`POST /{id}/publish` 的 `{id}` 是**模块 ID**（`ModuleServiceImpl.java:100` 用它查 `sys_module`），而本页行内的 `record.id` 是**版本 ID** → 直接把 `record.id` 传进去会**给错误的模块发布版本**。

### 7.2 🔴 租户隔离红线（**平台级表未豁免多租户插件**）

| 项 | 事实 |
|---|---|
| 白名单 | `MyBatisPlusConfig.IGNORE_TENANT_TABLES`（`MyBatisPlusConfig.java:32-93`）**不含** `sys_module` / `sys_module_version`；而 **`sys_tenant`(`:33`) 与 `sys_menu`(`:35`) 在** |
| 注入条件 | `AiReadyTenantLineInnerInterceptor.shouldSkip()`（`:41-44`）= 「租户不可解析」**或** `MyBatisPlusConfig.isTenantScopeExempt()`（`:157-167`，只读 Session 缓存以避免递归） |

| ✅ 因此 | **新登录的超管会话下，租户插件对全部表整体跳过** → 本表**读得到、不会空白** |
| 🔴 但红线仍在 | **非超管的平台运营账号**（平台侧正确配置）其会话租户 ≠ 0 时，会被注入 `AND tenant_id = <会话租户>` → 本表数据全为 0 → **查询恒返回 0 行 → 页面空白而非报错** |
| 结论口径 | **当前被超管整体豁免「掩盖」，但配置脆弱、红线仍在** |

> **⚠️ 写作纠偏（如实记录）**：本项目取证文件中曾出现「`isTenantScopeExempt()` 无调用点」的判断，**该判断是错的** —— 调用点在 `AiReadyTenantLineInnerInterceptor.java:41-44`。本文件以源码为准。

## 8. 业界对标

> **本页在 ql361 无对应页**（§2）。因此本章**不写 ql361 对标规格**，只写**业界能力对标**。所有来源按「标题 + URL + 章节 + 查阅日期 + 可信度级别」留痕；**凡底稿标 D 级的方案，本文件一律写「本系统设计」而非「业界标准」**。

### 8.1 业界叫法

**Odoo 的模块版本三字段**（`installed_version` / `latest_version` / `published_version`）；SAP 侧对应**传输请求（Transport Request）+ SAP Note 补丁**；金蝶 / 用友**无独立的「模块版本」页**（版本随产品发版走）。

### 8.2 业界做法要点

1. **三个版本字段，且源码里有明确的「命名反义陷阱」**：Odoo 官方源码 `ir_module.py` 的代码注释指出命名与语义相反 ——
   - `installed_version` 实际表示**磁盘上的最新版本**（`fields.Char('Latest Version', compute='_get_latest_version')`）；
   - `latest_version` 实际表示**数据库中已安装的版本**（`fields.Char('Installed Version', readonly=True)`）；
   - `published_version` 表示**仓库可用版本**。
   → **这是「版本三态」的经典建模：当前安装 / 磁盘可达 / 远端可发布**。
   → **本系统要避免重蹈这个命名反义坑**：字段名必须与语义一一对应，并在实体 `@Schema` 里显式写清（参照 §7.3 的命名方案）。
2. **升级是「标记 + 由后台串行执行」，不是同步操作**：`button_upgrade` 的第一步是 `update_list()`（比较 manifest 与数据库记录、写入差异、返回 `[update, add]` 两个计数）→ 校验状态必须为**已安装或待升级**（否则报错）→ 把**依赖它的已安装模块**加入 `todo` → 写为 `to upgrade`（若目标是 `base` 模块，还会加入所有未选中的已安装模块，排除 `studio_customization`）→ 收集依赖中 `uninstalled` 的模块并调 `button_install()`。
3. **升级期间冻结定时任务**：`ir.cron._check_modules_state` —— 存在 `to %` 状态的模块且**有就绪任务**时，若最旧任务距今 **< `MAX_FAIL_TIME`（5 小时）** 抛 `BadModuleState`；**超过 5 小时**则调 `reset_modules_state`。
4. **版本变更触发自动备份**（Odoo.sh）：**合并的提交更新了模块版本（`__manifest__.py`）或 Python 依赖（`requirements.txt`）时，会触发自动备份（标记为 `Update` 类型）**。
5. **Odoo 的模块状态机（官方源码 `STATES` 精确取值）**：`uninstallable`（不可安装）/ `uninstalled`（未安装）/ `to install`（待安装）/ `installed`（已安装）/ `to upgrade`（待升级）/ `to remove`（待移除）；依赖状态额外有一个 `unknown`（`DEP_STATES = STATES + [('unknown','Unknown')]`）。**→ 本系统目前没有任何状态机**（§5.2）。

### 8.4 明确不借鉴

- **Odoo 的「模块 = Python 包」模型** —— Odoo 的模块是**可安装的代码包**（有 `__manifest__.py`、`requirements.txt`、依赖与互斥校验）；**本系统的「模块」= 菜单 + 权限 + 表结构的功能块**（`sys_module` 是纯元数据行，无代码载体）。因此 `button_install` / `button_uninstall` / 依赖树解析这一整套**不适用**。
- **SAP 的 ABAP 传输体系整体照搬**（SE09/SE10 / TMS / STMS / 传输路由）—— 本系统是单体部署 + Flyway 迁移，**没有多环境传输链**；只借鉴其「发布要有对象锁 / 要可回滚 / 要填结构化文档」三条**设计约束**（见《模块发布开发文档》§8）。
- **Odoo / SAP / 金蝶 / 用友的界面样式与字段命名**（README §5.3 口径：本模块按能力模型建模，**不照搬界面**）。
- **`published_version` → 远端仓库的自动发现**：Odoo 依赖 Odoo Apps Store；本系统**无模块市场**，该字段在本系统只能人工维护或由发布动作写入。

### 8.5 不发明字段承诺

本章建议涉及的所有新字段（`installed_version` / `available_version` / `published_version`）与唯一约束，**本系统当前均不存在**，已在 §7.3 标注 **「需新增」**。除此之外：
- 「版本详情抽屉」「发布弹窗」**不引入任何新字段** —— 复用 `SysModuleVersion` 已有的 11 个属性；
- 「回滚」所需的状态位**可由已有 `release_status` 列承载**（补 `rolled_back` 取值即可），**无需新增列**；
- 「发布人」列**无需新增字段** —— 库中 `publisher` 已有值（12 行全为「管理员」），只是**后端写死**（§11）与**前端未展示**（§3.5）。

## 10. 验收标准（目标）

> **前置**：本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下不存在 `e2e-system-*.cjs` / `e2e-admin-*.cjs`）。落地脚本建议命名 `tools/e2e-system.cjs`（接口 + 直连 DB 对账 + 写库后复原 + Playwright UI 截屏，参照 `tools/e2e-crm.cjs`）。
> **⚠️ 本页验收的两个最大前提**：
> 1. **P0-1（包未装配）不修，§10.1 的接口断言全部得到 404** → 建议顺序：**先修 `scanBasePackages` → 再拔掉兜底数组 → 再跑接口断言 → 最后跑 UI 断言**；
> 2. **必须先拔掉 `version/index.vue:86-91` 的 6 行兜底数组**（否则任何断言都会被假数据「答对」，UI 断言全部失真）—— 这是**硬性前置条件**。
> **权限账号**：`admin`（`id=1`，`tenant_id=1`，SUPER_ADMIN）用作 **200 基线**（走 `UnifiedPermissionCacheService.java:82-88` 的 `*` 通配）；另需一个**非超管的平台运营账号**做 **403 对账**（因为 `system:module%` 权限码实测 0 行）。

### 10.1 接口验收（22 项）

**可达性（①–④）**

① 用 `admin` 登录（Bearer），`GET /api/module/versions` **期望 200**；**未修 `scanBasePackages` 时期望 404** —— **两种结果都要记录**，404 即证明 P0-1 未修。
② **断言 `/api/module/**` 全部 404**（逐条打 10 个 mapping：`/list` `/versions` `/releases` `/usage` `/{id}` `POST ""` `PUT /{id}` `DELETE /{id}` `PUT /{id}/status` `POST /{id}/publish`）—— 这是**修复前的基线**；**修复后本项应改为「全部非 404」**。
③ **在拔掉兜底数组之后**再打开页面，断言表格**渲染 `a-empty`（或 0 行）**且**出现可见错误提示**（当前无提示 → 登记 P0-2；修复后应改断言「提示 + 重试按钮」）。
④ 断言 `GET /api/module/versions` **不带 `Authorization`** 时返回 **401/403**（证明全局登录拦截生效）。

**数据一致性（⑤–⑧）**

⑤ 🎯 **超管登录后本表能查到 ≥ 12 行**（专门断言，来自 README §1.3 红线②的验收纪律）：`GET /api/module/versions` 返回 `total >= 12`；同时**直连 DB** `SELECT count(*) FROM sys_module_version` = **12** → **两者相等**。
⑥ 断言返回体 `records` 每行的键集合 = {`id`,`moduleId`,`moduleName`,`version`,`changelog`,`releaseStatus`,`publisher`,`releaseTime`,`tenantId`,`createTime`,`updateTime`}（**11 个属性，与实体一致**，`SysModuleVersion.java:20-50`）。
⑦ 断言库里 **6 行完全重复**确实被原样返回（`module_id/version` 组合出现 2 次）→ **登记 P1-11 缺陷**；修复去重/约束后改断言「每个 (moduleId, version) 只出现 1 次」。
⑧ 断言排序：当前 `release_time` 为 NULL 的「客户关系 1.8.0」**排在首位**（PostgreSQL NULLS FIRST）→ **登记 P1-10**；修复后改断言「NULL 排在最后」。

**过滤与分页（⑨–⑪）**

⑨ 🤖 **`?moduleId=1` 过滤生效**：直接调 `GET /api/module/versions?moduleId=1` → 断言只返回 `moduleId=1` 的 6 行（销售管理 2.1.0 / 2.2.0-beta 各 2 条重复）；
⑩ 断言**前端未传 `moduleId`**：抓网络包，断言本页首屏请求为 `GET /api/module/versions`（**无 query**）→ **登记 P1-8**；修复后改断言「带 `moduleId`（当查询区选了模块时）」。
⑪ 断言本页**无分页请求**（无 `pageNum`/`pageSize`，且 UI 无分页器）→ **登记 P1-9**。

**发布链路（⑫–⑯）**

⑫ 🎯 **假发布可执行断言**：在页面上点某 `draft` 行的「发布」→ 抓网络包断言 **0 个请求**；断言数据库该行 `release_status` **仍为 `draft`**；**刷新页面后按钮重新出现**（本地对象被重置）→ 这是 **P0-3 的可执行证据**。
⑬ **后端真实端点可用性**：`POST /api/module/{moduleId}/publish`（body `{"version":"2.9.9-test","changelog":"E2E"}`）**期望 200 + `success:true`**；**`version` 为空时期望 `{"success":false,"message":"版本号不能为空"}`**（`ModuleController.java:132-134`）。
⑭ **改库 → 回读 → 按原值复原**：先记录 `SELECT id, version FROM sys_module WHERE id=1`（销售管理，`version='2.1.0'`）→ 调 ⑬ 的 publish（version=`2.9.9-test`）→ **回读断言 `sys_module.version` 已被同步为 `2.9.9-test`**（`ModuleServiceImpl.java:120-123`）+ `sys_module_version` 新增 1 行（`release_status='released'`）→ **最后手工执行反向 SQL 复原**：删掉新增的 `sys_module_version` 行 + 把 `sys_module.version` 回写为 `2.1.0`，并**回读断言复原成功**。
⑮ **断言 `publishVersion` 写死的两个值**：新增行的 `publisher` **恒为字符串 `admin`**（`ModuleServiceImpl.java:113`）、`tenant_id` **恒为 `1`**（`:115`）—— 即使当前登录人是别的账号、当前会话租户是别的值 → **登记 P0/P1（§11）**；修复后改断言「`publisher` = 当前登录用户名、`tenant_id` = 当前会话租户」。
⑯ 断言**前端的「发布」动作不产生任何 SQL**（网络无请求 + 库中无新行 + `sys_module.version` 不变）→ 与 ⑫ 互证。

**详情与缺口（⑰–⑲）**

⑰ 🎯 **断言「详情」不产生任何请求**：点击「详情」→ 网络面板**0 请求**，只有一条 `message.info`（`version/index.vue:70-72`）→ 登记 **P0-4**。
⑱ **断言以下端点不存在**（逐个调，期望 404/405）：`GET /api/module/versions/{id}`、`POST /api/module/versions`、`PUT /api/module/versions/{id}`、`DELETE /api/module/versions/{id}`，以及任何含 `rollback` 的路径 → 与 §6.4 的 8 条后端缺口对账。
⑲ **断言 `sys_module_version` 无 `deleted` 列、无 `status` 列**（`information_schema.columns` 直查）→ 与《模块发布开发文档》§5 的「`status` 恒空」缺陷对账。

**权限（⑳–㉒）**

⑳ `admin`（SUPER_ADMIN）调 `GET /api/module/versions` → **期望 200**（走 `*` 通配）。
㉑ 用**非超管的平台运营账号**（持有 `system:module:list` 的角色）调同一端点 → **期望 403**，因为 **`sys_permission` 中 `system:module%` = 0 行**（无法被授权）→ **登记 P1-6**；补权限种子后改断言 **200**。
㉒ 断言 `SELECT count(*) FROM sys_permission WHERE permission_code LIKE 'system:module%'` **= 0**（当前事实）→ 补种子后改断言 **≥ 4**（`list`/`create`/`update`/`delete`）。
