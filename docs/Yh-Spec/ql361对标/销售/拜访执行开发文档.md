## 业务规范说明

### 状态流转与特殊交互

- 日期与职员均为必填（标红*），两者确定后查询该职员当日外勤轨迹
- 轨迹数据来源为移动端（外勤 APP）上报的 GPS 点位，需有定位上报机制支撑；地图服务商（截图样式疑似高德/腾讯系 Web 地图）待复核
- 本系统技术栈已定高德地图 Web API（见根 AGENTS.md），对标实现时采用高德地图

### 与其他页面关系

- 外勤拜访三步流程：**1.拜访规划**（定计划）→ **2.拜访执行**（本页，查轨迹/定位）→ 3.拜访检视（统计完成率）
- 本页轨迹数据是拜访检视中"异常拜访次数"等统计的佐证数据来源（推断，具体口径待复核）
- 拜访执行依赖移动端签到/定位上报，与 PDA/移动端的签到功能联动

### 架构师红线（Ponytail六步过滤网）

动手前必过六关：①此功能业务真需要？②标准库/原生API能搞定？③现有依赖能否复用？④能否一行代码干净解决？⑤能否复用已有组件？⑥通通走不通才写最小可用闭环。**Lazy, not negligent**——跨边界防注入、容灾、安全防御代码不准省。

### 业务逻辑要求

对标 Odoo、SAP、金蝶、用友、管家婆等生产级系统的业务逻辑和交互逻辑，溯源字段真实所属实体，实现真正的生产级数据闭环。轨迹点位必须来自真实定位上报，禁止伪造轨迹数据。

## 验收标准

- 没有桩（Stub）与模拟（Mock）数据：代码中不得出现 TODO、FIXME、stub、模拟、mock、假数据、临时、演示、示例、占位、placeholder，确保使用真实数据
- 日期*、职员* 必填校验真实生效，缺任一条件不得发起查询
- 地图真实加载并渲染所选职员当日的轨迹点位/轨迹线（来自真实定位上报记录）
- 职员轨迹 / 职员定位两个子标签可切换，各自查询逻辑真实可用
- 与拜访规划、拜访检视页的数据口径一致（执行记录可回溯到计划）
