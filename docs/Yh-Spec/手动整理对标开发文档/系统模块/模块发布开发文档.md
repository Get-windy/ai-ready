## 1. 页面概述

模块发布页意图是**平台运营方管理「模块发版/发布」动作的台账页** —— 谁在什么时候发布了哪个版本、发得成功还是失败、失败或不满意时能不能回滚。它属于 `61302 模块管理` 组的第 3 页（`sort=300`）。

**但本页当前是一张「结构完整的空壳」**：3 个按钮（新建发布 / 详情 / 回滚）**全是纯桩**；数据表**只有一张复用的 `sys_module_version`**（**不存在 `sys_module_release`**）；表格的「状态」列绑定的字段（`status`）**后端根本不返回**；值域（`success/pending/failed/rolling`）**与后端（`released/beta/draft`）完全不交集** → **即便接口接通，状态列恒空、「回滚」按钮将永不可见**。

### 1.1 与相邻页的分工（`61302 模块管理` 组 4 页，本页与 62102 最易混）

| 页面 | 菜单ID | 回答的问题 | 数据源 | 后端端点 | 可用性 |
|------|:-----:|-----------|--------|---------|:------:|
| **模块列表** | 62101 | 平台**有哪些模块**、启停/改描述 | `sys_module` | `GET /api/module/list` | ❌ 404 |
| **模块版本** | 62102 | 某模块**有哪些版本**、哪些已发布 | `sys_module_version` | `GET /api/module/versions` | ❌ 404 + 假数据 |
| **模块发布（本页）** | 62103 | 平台**发布了什么**、能否回滚 | 🔴 **同上（复用）** | `GET /api/module/releases` | ❌ 404 + 假数据 |
| **使用统计** | 62104 | 各模块**被用得多少** | `sys_module` + `sys_audit_log` | `GET /api/module/usage` | ❌ 404 + 假数据 |

> 🔴 **两页的数据源是同一张表** —— 后端 `GET /api/module/releases`（`ModuleController.java:50-62`）**逐行等价于** `GET /api/module/versions`（`:36-48`）：两者都调 `moduleService.getVersionList()`（`:55` / `:41` → `ModuleServiceImpl.java:92-96`），都做同一个 `moduleId` 过滤分支，都返回 `Map.of("records", versions, "total", versions.size())`。**`/releases` 没有任何独立业务逻辑**：既没有「发布批次」概念，也没有本页期望的 `status` 字段。
> **一句话分工（目标态）**：**模块版本（62102）看「版本清单」**；**模块发布（62103）看「发布单」** —— 每张发布单有发布单号、目标模块、版本、变更清单、影响菜单、回滚方案、发布人、审批人、窗口期、结果。**该「发布单」实体在本系统中尚不存在**（§7.2）。

## 8. 业界对标

> **本页在 ql361 无对应页**（§2）。因此本章**不写 ql361 对标规格**，只写**业界能力对标**。所有来源按「标题 + URL + 章节 + 查阅日期 + 可信度级别」留痕；**凡底稿标 D 级的方案，本文件一律写「本系统设计」而非「业界标准」**。

### 8.1 业界叫法

**SAP 的传输请求（Transport Request）/ 变更请求 + 任务**，工具是 **Transport Organizer（SE09/SE10）+ TMS（STMS）**；金蝶侧对应**调度计划导入导出**（在「调度中心」专题里作为独立条目）；Odoo 侧对应 **Odoo.sh 的分支 + 构建（build）**（代码即产物，**无独立发布包**）；**jeecg / RuoYi 无发布概念**（单体部署）。

### 8.2 业界做法要点

1. **发布单元是「请求」而不是「版本号」**：SAP 的 Transport Organizer「**记录并文档化 Repository 对象（ABAP Dictionary、程序、屏幕、接口定义、文档模块）和 Customizing 对象的变更**」，通过**变更请求（change request）+ 任务（task）**管理；官方原文：「支持开发团队直至变更请求释放；之后由 Transport Management System (TMS) 负责将请求导入目标系统」。
   → **本系统的对应物应是「发布单」**，而不是「版本行」（§7.2）。
2. **发布必须有对象锁**：官方原文「**提供对象锁定机制，防止未协调的并行修改**」—— **同一对象不能被两个请求同时改**。
3. **发布必须可回滚**：官方原文「**提供版本管理，支持比较和恢复历史版本**」。
4. **释放请求必须填结构化文档**：官方原文「**释放任务时要求开发者填写结构化文档**」。→ **这一条直接对应本页「新建发布」的必填字段设计**（§7.2 的 `changelog` / `affected_menus` / `rollback_plan`）。
5. **导入有独立队列与监控**：TMS 通过 **STMS** 启动，用于「组织、执行和监控 SAP 系统间的传输」，有**导入队列**与**导入监控**（SAP Library 目录列出「传输执行、导入队列管理、导入监控、传输工作流、QA 审批流程」）。
6. **环境分层**：TMS 配置**传输路由（transport routes）**时定义系统组，即 **dev → QA → prod** 的路径。
7. **灰度用「分支 + 净化副本」**：Odoo.sh 的 staging 分支使用生产数据库的**净化副本（sanitized copy）** —— 「净化会**禁用计划动作、外发邮件、IAP 服务、支付提供商和配送连接器**」；升级测试**始终使用前一晚自动备份**且**无法更改此行为**。→ **「预发环境要关外发副作用」这条工程闭环非常值得抄**。

### 8.4 明确不借鉴

- **SAP 的 ABAP 传输体系整体照搬**（SE09/SE10 / TMS / STMS / 传输域 / 传输路由 / 传输层）—— 本系统是**单体部署 + Flyway 迁移**，**没有可传输的对象清单**（代码在 Git、表结构在 Flyway），整套 TMS 架构**不适用**。只借鉴其**四条设计约束**：发布单元是请求、要有对象锁、要可回滚、释放要填结构化文档。
- **Odoo.sh 的「分支 + 构建」模型** —— 本系统**无多分支部署**（无 staging/production 双分支链），代码即产物的前提不成立。
- **Odoo 的「模块 = Python 包」** —— 本系统的「模块」= **菜单 + 权限 + 表结构的功能块**（`sys_module` 是纯元数据行），无安装包 / 无依赖树 / 无 `__manifest__.py`。
- **vendor 的界面样式与字段命名**（README §5.3 口径：按能力模型建模，**不照搬界面**）。
- **「灰度 = 环境级」的直接套用** —— 本系统单环境，SAP 式环境级灰度**无落点**；若要做灰度，只能走 **D 级自建的租户级方案**（见 8.3 末行）。

### 8.5 不发明字段承诺

- 本章建议的 **发布单全部字段**（§7.2 的 14 项）与本系统的 `sys_module_release` 表**均不存在**，已明确标注 **「需新增」**。
- **「新建发布」弹窗**不引入任何新字段即可复用现有的 `POST /{moduleId}/publish`（`ModuleController.java:124-140`，只吃 `version` + `changelog`）—— 但那样只能覆盖**路线 ②**（无审批、无窗口期、无回滚方案），**是否够用须先裁定**（§4）。
- **「回滚」不一定要新增列**：可复用 `sys_module_version.release_status` 的 `rolled_back` 取值（实体注释已有该值，`SysModuleVersion.java:34`），**但库中 0 行、且后端无端点**。
- **`status` 字段**：本页当前期望的 4 值（`success`/`pending`/`failed`/`rolling`）在本系统**无任何落点**，若走「发布单」路线则由新表承载；若走「版本行」路线则**必须删掉这 4 值**，改读 `releaseStatus`。

## 10. 验收标准（目标）

> **前置**：本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下不存在 `e2e-system-*.cjs` / `e2e-admin-*.cjs`）。落地脚本建议命名 `tools/e2e-system.cjs`（接口 + 直连 DB 对账 + 写库后复原 + Playwright UI 截屏，参照 `tools/e2e-crm.cjs`）。
> **⚠️ 本页验收的两个最大前提**：
> 1. **P0-1（包未装配）不修，§10.1 的接口断言全部得到 404** → 建议顺序：**先修 `scanBasePackages` → 再拔掉兜底数组 → 再跑接口断言 → 最后跑 UI 断言**；
> 2. **必须先拔掉 `release/index.vue:109-113` 的 5 行兜底数组**（否则任何断言都会被假数据「答对」，UI 断言全部失真）—— 这是**硬性前置条件**。
> **权限账号**：`admin`（`id=1`，`tenant_id=1`，SUPER_ADMIN）用作 **200 基线**（走 `UnifiedPermissionCacheService.java:82-88` 的 `*` 通配）；另需一个**非超管的平台运营账号**做 **403 对账**（因为 `system:module%` 权限码实测 0 行）。

### 10.1 接口验收（23 项）

**可达性（①–④）**

① 用 `admin` 登录（Bearer），`GET /api/module/releases` **期望 200**；**未修 `scanBasePackages` 时期望 404** —— **两种结果都要记录**，404 即证明 P0-1 未修。
② **断言 `/api/module/**` 全部 404**（逐条打 10 个 mapping：`/list` `/versions` `/releases` `/usage` `/{id}` `POST ""` `PUT /{id}` `DELETE /{id}` `PUT /{id}/status` `POST /{id}/publish`）—— 这是**修复前的基线**；**修复后本项应改为「全部非 404」**。
③ **在拔掉兜底数组之后**再打开页面，断言表格**渲染 `a-empty`（或 0 行）**且**出现可见错误提示**（当前无提示 → 登记 P0-2；修复后应改断言「提示 + 重试按钮」）。
④ 断言 `GET /api/module/releases` **不带 `Authorization`** 时返回 **401/403**（证明全局登录拦截生效）。

**数据一致性（⑤–⑨）**

⑤ 🎯 **超管登录后本表能查到 ≥ 12 行**（专门断言，来自 README §1.3 红线②的验收纪律）：`GET /api/module/releases` 返回 `total >= 12`；同时**直连 DB** `SELECT count(*) FROM sys_module_version` = **12** → **两者相等**。
⑥ 断言 `/releases` 与 `/versions` 的返回体**逐行相同**（`diff` 两个 JSON 的 `records`）→ **这是 P1-8 的可执行证据**（`ModuleController.java:50-62` 复用 `getVersionList()`）。
⑦ 断言返回体 `records` 每行的键集合 = {`id`,`moduleId`,`moduleName`,`version`,`changelog`,`releaseStatus`,`publisher`,`releaseTime`,`tenantId`,`createTime`,`updateTime`}（**11 个属性**）—— **并显式断言其中不存在 `status` 键**（登记 P0-3 的根因）。
⑧ 断言库里 **6 行完全重复**确实被原样返回（`module_id/version` 组合出现 2 次）→ **登记 P1-16**；修复后改断言「每个 (moduleId, version) 只出现 1 次」。
⑨ 断言 `/releases` 返回行中 `publisher` **全部为「管理员」**（12/12），**断言不存在「运维」「开发」** → 与假数据（`:111`、`:113`）对账，**证明页面展示的是伪造数据**。

**发布链路（⑩–⑮）**

⑩ 🎯 **假回滚可执行断言**：在页面点某 `success` 行的「回滚」→ 抓网络包断言 **0 个请求**；断言数据库 **无任何行被修改**；断言**页面上该行的状态 tag 也不变**（连本地对象都没改，`:98-100`）→ **P0-4 的可执行证据**。

## 12. 剩余缺口（P0 / P1 / P2）

> 口径与《系统模块/README.md》§7 保持一致。README §7.1 **P0-1**（包漏配 `scanBasePackages`）、**P0-15**（平台级表未豁免多租户）、以及 §7.2 的「**模块版本/发布/使用统计写死假数据且发布链路零接线**」在本页的具体化见下。

### P0（7 条）

① **包未装配（README §7.1 P0-1 的具体化）**：`cn.aiedge.module` 不在 `scanBasePackages`（`AiReadyApplication.java:21-97`，`grep` 命中 **0**）→ **本页唯一端点 `/releases` 运行期 404**；同组另 3 页共 9 个 mapping 同因。现象：`GET /api/module/releases -> 404 {"code":404,"message":"接口不存在: api/module/releases"}`。建议：补包 + 重新构建 + 重启，并按 §10.1-①② 复验。
② **写死假数据兜底且静默**：`release/index.vue:108-114`（5 条在 `:109-113`），**任何异常都触发**、**无 `message.error`** → 页面 100% 展示假数据；🔴 **假数据里的发布人「运维」「开发」在库中根本不存在**（库中 12 行全是「管理员」）→ **这是在伪造审计信息**。建议：**删除兜底数组**，改空数组 + 可见错误提示 + 重试；**验收必须先拔掉兜底**。
③ **状态列字段名 + 值域双重不匹配**：列绑 `status`（`:86`）而后端返回 `releaseStatus`（`ModuleController.java:55`）→ **恒为空白**；值域 `success/pending/failed/rolling`（`:45-46`）与库中 `released/beta/draft` **零交集**。建议：裁定「发布单」或「版本行」路线后收敛。
④ **「回滚」是假回滚且后端无端点**：`release/index.vue:98-100` 只弹 `message.success('版本回滚中: …')`；`ModuleController.java` 的 10 个 mapping **无 rollback**。**UI 在无能力时谎报「回滚中」**。
⑤ **「回滚」按钮接真数据后永不可见**：`v-if="record.status === 'success'"`（`:57`）在 `status` 恒 `undefined` 时恒假；当前可见**只因假数据里有 `status`**（`:109-112`）。
⑥ **「新建发布」自报「功能开发中」**：`release/index.vue:90-92`，无弹窗、无表单、无接口、无表。
⑦ **「详情」是纯桩**：`release/index.vue:94-96`，只弹 `message.info`，且 `GET /releases/{id}` 端点不存在。

### P1（10 条）

⑧ **`/releases` 无独立业务逻辑**：`ModuleController.java:50-62` 与 `:36-48` **逐行等价**（同一个 `getVersionList()`）→ 与 `/versions` 返回完全相同的数据，既无「发布批次」也无 `status`。
⑨ **无 `sys_module_release` 表**：全库 `%module%` 仅 3 张表 → **发布单元无落点**；「发布编号」列只能用版本表主键冒充（`:81`）。
⑩ **无 `changelog` 列**：发布页**看不到本次发布了什么**（数据就在 `sys_module_version.changelog`，库里 6 行都有值）。
⑪ **平台级表未豁免多租户（README §7.1 P0-15 的具体化）**：`sys_module_version` 不在白名单（`MyBatisPlusConfig.java:32-93`），数据 `tenant_id` 全 0 而超管会话租户为 1 → **非超管平台账号查询恒 0 行，页面空白而非报错**；当前被超管整体豁免掩盖（`SysUserServiceImpl.java:88` + `AiReadyTenantLineInnerInterceptor.java:41-44` + `MyBatisPlusConfig.java:157-167`），**但配置脆弱、红线仍在**。建议：读全局加 `@InterceptorIgnore(tenantLine="true")`；写目标租户行前 `setTempTenantId(tid)`。
⑫ **权限码 0 行**：`sys_permission` 中 `system:module%` = **0 行** → 非超管对 `/api/module/**` 全部 403。建议：补 `system:module:list` / `:create` / `:update` / `:delete` 种子。
⑬ **`moduleId` 过滤未接线 + `moduleApi` 缺 `releases` 方法**（后端支持 `:53-60`；`api/admin.ts:304-321` 无该封装）。
⑭ **无分页**（前端 `:pagination="false"` + 后端返回全量）。
⑮ **排序 NULLS FIRST**：`release_time` 为 NULL 的行排最前（`ModuleServiceImpl.java:94`）。
⑯ **库中 6 行完全重复且无唯一约束** → 展示 12 行。
⑰ **未达金标准路线 A**：无 `ErrorBoundary`、无 `CategoryListLayout`、无列配置齿轮、无 `PageConfigPanel`、无 `storage-key`、无经典分页 —— **与 README §7.2「30 页全部无 `PageConfigPanel` / 无 `storage-key` / 无经典分页 / 无列配置齿轮」一致**。

### P2（6 条）

⑱ **无 `releaseStatus` 列**：表格标题叫「状态」但绑的 key 后端不存在（`:86`）。
⑲ **无刷新按钮**（header 右侧只有「新建发布」，`:19-30`）→ 加载失败后**用户无法重试**（需整页刷新浏览器）。
⑳ **状态文案未中文化**：`|| record.status` 会原样输出英文（`:46`）—— **对照《模块版本》页 `:34` 的正确写法**。
㉑ **「发布编号」语义错**：列标题与绑定字段不符（`:81`）。
㉒ **裸调 `request` 而非 `moduleApi`**（且该封装也没有 `releases`）：`release/index.vue:75,105`。
㉓ **无本系统验收截图、无模块级 E2E**（README §7.3 末条；`tools/` 下无 `e2e-system-*.cjs`）。
