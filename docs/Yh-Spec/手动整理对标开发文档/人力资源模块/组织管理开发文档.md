## 1. 页面概述

「组织管理」在本系统是一个**不存在菜单的孤儿页面**，内容为「**左：部门结构树 + 右：该部门下的职位列表**」，是本系统里**唯一一处把部门与岗位放在同一屏联动**的实现。

| 页面 | 路由 / 组件 | 行数 | 菜单挂载 | 说明 |
|------|------------|:----:|:--------:|------|
| 组织架构（**本文档主角**） | `hr/organization/index` → `views/hr/organization/index.vue` | 273 | ❌ **无菜单** | 左部门树 + 右岗位表；含「新增部门」「新增岗位」两个弹窗 |
| 职位管理（有菜单的平级页） | `hr/organization/position` → `views/hr/organization/position-list.vue` | 222 | ✅ `90006` | 纯岗位单表，**无部门树**（详见《职位管理开发文档》） |

> **⚠️ 本页是「更完整的那个」，但用户看不到**
> `index.vue` 比 `position-list.vue` **多出**：`ErrorBoundary` 外壳、`PageContainer` 容器、部门树、按部门过滤岗位、部门新增。
> 而 `sys_menu` 只有一行把 `component` 指向 `position-list.vue`（菜单 `90006`「职位管理」，父 `61404 组织管理`）。路由表由菜单驱动（`transformMenuToRoutes`，`dynamicRoutes.ts:958`；组件 key 由 `menu.component` 去 `views/` 与 `.vue` 得到，`:992`），故 `hr/organization/index` 虽在路由映射表中，**没有任何菜单会导航到它**。
> 这与《考勤记录开发文档》§1、《请假管理开发文档》§1 的「**功能更完整的伴生页用户看不到**」是同一种病，本页是最严重的一例（**整页不可达**）。

### 1.1 部门主数据的真正归属（红线，必须先读）

**HR 模块自身不维护部门**。部门是**系统级主数据**，HR 只是**引用方**：

| | 部门（本页左树的数据来源） | HR 模块 |
|---|---|---|
| 表 | **`sys_department`**（19 列） | `hr_employee.dept_id` / `hr_position.dept_id` / `hr_recruitment.dept_id`（**仅引用**） |
| 后端 | **`cn.aiedge.department.controller.DepartmentController`**，类级 `/api/department`（**前缀正确**） | **无任何部门写接口** |
| 前端 api | `api/department.ts` 的 `departmentApi`（11 个方法） | 复用同一个 `departmentApi` |
| 外键 / 权限码 | ❌ 无任何外键约束 / ✅ `department:create·delete·edit·list·manage·query`（**6 条已登记**） | ❌ 无外键 / ❌ `hr:*` 权限码 **0 条** |

> **⚠️ 结论**：写「组织架构 / 部门」的任何功能，**后端一律改 `DepartmentController` + `sys_department`**，**不要在 HR 模块里另起一套部门表或部门 Service**。
> HR 侧唯一该做的是**消费方**：补 `deptId` 选择器（当前《职位管理开发文档》§4.2 记录 `hr_position.dept_id` **恒 NULL**）、补 `deptName` join 回填列。

### 1.3 本页与「岗位权限」的关系（方向不要搞反）

菜单 `80531`「**岗位权限**」对应的 `views/md/staff-role/index.vue` **并不是「岗位 → 权限」的配置页** —— 该页**自身在顶部挂了一条 `a-alert`**（`:4-9`）自认：「后端暂无岗位-权限/角色关联接口（仅有岗位对用户的分配接口），岗位的权限配置能力待后端补充端点后接入」。即该页实际是**岗位主数据列表页**，权限能力**尚未实现**。

> **⚠️ 与《职位管理开发文档》§8-6 呼应**：业界（SAP RBP）是「**权限组 × 权限角色 × 目标人群**」三元授权，**不存在「岗位 → 权限」直连**。因此「岗位权限」这个名字本身就有误导性；后续若要落地权限，应让**岗位成为「目标人群」的筛选条件之一**，而不是权限的宿主表。

### 3.2 左：部门树（`a-tree`，L6-22 / L125-158）

| 项 | 实现 | 说明 |
|----|------|------|
| 数据源 | `loadDeptTree()` → `departmentApi.getList()` → `GET /api/department/list` | **不是** `getTree()` |
| 返回值解包 | `Array.isArray(res) ? res : res?.data \|\| []`（L127-128） | 冗余兼容写法 —— `request.ts` 其实已解包 `ApiResponse.data` |

| 节点字段 | `title: d.departmentName`、`key: d.id`、`value: d.id`（L137） | 同一节点兼顾 `a-tree` 与 `a-tree-select` |
| 交互 | `@select="onDeptSelect"`（L16）→ `selectedDeptId` → `loadPositions()`；`default-expand-all` | — |
| 空态 | `catch { deptTree.value = [] }`（L130） | **失败静默为空树，不提示用户** |

> **🔴 缺陷（P0 业务）：部门树在现状下必然为空**
> `listAll()` **硬编码 `wrapper.eq(Department::getStatus, 1)`**（`DepartmentServiceImpl.java:71-78`）→ **只返回启用部门**；而 `sys_department` 现有 2 行种子（`id=9001 财务部 D9001` / `id=9002 市场部 D9002`，均 `tenant_id=1`、`parent_id=0`、`ancestors=null`）**`status` 全部为 `0`（禁用）**（devdb 实测）。
> ⇒ **打开本页，左部门树必然为空**，右表只能是「全部岗位」；**树-表联动能力完全无法被验证**。
> 修法二选一：① 种子改为 `status = 1`；② 树改用 `departmentApi.getTree()`（**不做 status 过滤**）。

### 3.3 左：部门树的交互缺陷

| 缺陷 | 位置 | 说明 |
|------|------|------|
| **选中名只查根节点** | `index.vue:152` | `deptTree.value` 是**根数组**，`.find` **不递归** → 选中**任何非根部门**时 `selectedDeptName` 为 `''`，右侧标题回落成「**全部岗位**」（L27），**但数据已被 `deptId` 过滤** → 标题与数据不一致（最典型的"看着是全部，实际是一个部门"） |

## 5. 业务规范（部门，`sys_department`）

> 本章描述**后端 `DepartmentController` 的真实行为**（部门是系统级主数据，HR 只是消费方）。行号引用 `DepartmentServiceImpl.java`。

### 5.1 状态与值域

| 字段 | 值域 | 当前实现 | 问题 |
|------|------|---------|------|
| `status` | `0 禁用 / 1 启用`（DB **默认 `0`**，`V5.0.0:561`） | `create` 默认 `1`（`:123`） | ⚠️ **DB 默认 0 与 Service 默认 1 不一致** → SQL 直插得「禁用」、接口建得「启用」；**且 2 行种子都是 `status = 0`** |
| `level` | 整数（层级） | **非库列** —— `convertToVO` 由 `ancestors` 推导：`ancestors.split(",").length`，`ancestors == null` 时为 `0`（`:357-362`） | ⚠️ **计算列** |
| `path` | 字符串（祖级路径） | **非库列** —— `vo.setPath(dept.getAncestors())`（`:354`） | ⚠️ **别名列**（`path` ↔ `ancestors`） |
| `description` | 字符串 | **非库列** —— `vo.setDescription(dept.getRemark())`（`:355`） | ⚠️ **别名列**（`description` ↔ `remark`） |

> **⚠️ `api/department.ts` 类型声明的真实情况（修正一处常见误读）**
> `DepartmentInfo` 声明了 `parentId` / `level` / `path` / `children` 四个字段：**`parentId` / `children` 是后端 VO 的真实字段**（`getTree()` 会填 `children`）；**`level` / `path` / `description` 是 VO 层的"计算 / 别名"字段，库表里都不存在**（分别由 `ancestors` 推导、别名 `ancestors`、别名 `remark`）。
> 即：**不能按前端类型去给 `sys_department` 建列或写 SQL**。

### 5.2 编码规则

- **无号段、无自动生成**：`dept_code` 手填、**可留空**（本页弹窗无 required；`md/staff-dept` 页**有**）。
- **有应用层唯一性校验**：`create` / `update` 都查 `dept_code` 重复并抛「部门编码已存在」（`:105-112` / `:151-160`），**但仅当编码非空时才校验**；**无 DB 唯一约束**（`sys_department` 只有 `id` 主键，`V5.0.0:545`）。
- **目标规格**：走号段（`next-no`），或至少补 `UNIQUE (tenant_id, dept_code) WHERE deleted = 0`。

### 5.3 树模型与移动

| 规则 | 当前实现 | 问题 / 目标 |
|------|---------|------------|
| 树模型 | **`parent_id` + `ancestors`（祖级路径，如 `0,1,2`）** | 业界把 `ancestors` 称 `parent_path` 物化路径（Odoo `parent_path` **带索引**）；本表 `ancestors` **无索引** → 子树查询需全表扫 |
| 建树 | `getTree()`：按 `parentId` 分组（null 归 `0L`）后 `buildTree(0L, …)`（`:80-91, 328-345`） | ⚠️ **只看 `parent_id`、不看 `ancestors`** → 两字段可能互相矛盾 |
| 新增时 `ancestors` | `parentId > 0` → `parent.getAncestors() + "," + parent.getId()`；否则 `"0"`（`:126-134`） | ⚠️ 父级 `ancestors` 为 `null` 时拼出 `"null,9001"` |
| **移动 `POST /{id}/move`** | `inner` → `setParentId(targetId)` + `setAncestors(target.getAncestors() + "," + target.getId())`；`before/after` → `setParentId(target.getParentId())` + `setAncestors(target.getAncestors())`（`:251-267`） | 🔴 **两处硬缺陷**（见下） |
| 循环检测 / 批量删除 | 仅在 `inner` 时调 `isDescendant` 防环（`:245-249, 270-284`）；`batchDelete` 循环调 `delete(id)`（`:210-215`） | ✅ 有防环但 **`before/after` 不检测**；批量删已删的不回滚 |
| **编辑不重算路径 / 删除保护** | `update()` 改名称/父/负责人/电话/邮箱/排序/状态/备注后**完全不动 `ancestors`**（`:145-192`）；`delete()` **只查子部门**（`:200-208`），**不查员工/岗位/用户引用** | 🔴 改父后 `level`/`path` 失真；删掉被 `hr_employee.dept_id` 引用的部门 → 引用悬空 |
| 租户 / 逻辑删 | 有 `tenant_id` 且**不在**忽略表（`:32-77` 已核）→ 拦截器自动注入 ✅；`Department extends BaseEntity`（`@TableLogic` + `@Version`）列齐备 ✅ | 保持；**勿加入忽略表** |

> **🔴 `move` 的两个硬缺陷**
> 1. **不级联更新子孙的 `ancestors`**：只改被移动节点自己（`:254-266`）→ **一次移动把整棵子树的路径搞脏**。
> 2. **`before` / `after` 的 `ancestors` 赋值是错的**：`dept.setAncestors(target.getAncestors())` 把**目标节点的祖先路径**直接套给被移动节点；当两者父级不同时路径必然错误。
> 且注释声称「同级移动，调整排序」（`:257-259`），但**整段 switch 没有任何 `setSort(...)`** → **排序根本没被调整**，`before`/`after` 与 `inner` 实际都只改了父级。
> **结论**：`move` 的 `before` / `after` **不可用**；`inner` 也只能移动单节点。

### 5.4 跨模块联动

| 方向 | 联动 | 状态 |
|------|------|------|
| 部门 → 员工 / 岗位 / 招聘 | `hr_employee.dept_id` / `hr_position.dept_id` / `hr_recruitment.dept_id` → `sys_department.id` | ⚠️ 列在、**均无外键**；员工页**无部门选择器**（《员工列表开发文档》§3.2）、岗位弹窗**无部门字段**（§4.3） |
| 部门 → 用户（系统） | `views/system/department/index.vue` 用 `userApi` 关联成员（`:629,664` 调 `getTree`） | ⚠️ **该页无菜单，用户不可达** |
| 部门 → 岗位（系统） | `sys_position.dept_id` + `sys_user_position` | 🔴 **`sys_user_position` 查询/写入必抛 SQL 异常**（§6.3） |
| 部门 → 统计 | 部门人数 / 编制 / 缺口 | ❌ **无任何统计端点** |

### 6.3 🔴 P0：`sys_user_position` 查询/写入必然失败（**两处独立的硬错误**）

`assign` / `remove` / `{id}/users`，以及 `PositionServiceImpl.pageList` / `getDetail` / `delete`（**每行 `convertToVO` 都会调 `countUsersByPositionId`**）全部依赖 `sys_user_position`。**该表当前不可用**：

| 错误 | 证据 | 影响 |
|------|------|------|
| **① `deleted` 列不存在** | `UserPositionMapper.java:23,29,35` 三个 `@Select` 都写了 `AND deleted = 0`；而真库实测该表**只有 5 列**（`id / user_id / position_id / is_primary / create_time`，`V9.34.0:1073-1079`）→ **无 `deleted` 列** | 三处 `@Select` 调用即 `column "deleted" does not exist` |
| **② `tenant_id` 列不存在（拦截器注入）** | 该表**无 `tenant_id` 列**（同上实测），且**不在** `MyBatisPlusConfig.IGNORE_TENANT_TABLES`（`:32-77` 已核）→ 拦截器注入 `tenant_id = ?` | 对该表的 **SELECT / INSERT / DELETE 全部报 `column "tenant_id" does not exist`**（与《_开发指南-金标准》陷阱 15 的 `shop_template` / `erp_group_buy_participant` 完全同型） |

**受影响面**：`DELETE /api/position/{id}`、`/batch`、`POST /api/position/assign`、`DELETE /api/position/remove` **全部 500**；
🔴 **`GET /api/position/page` 与 `GET /{id}` 也会 500** —— 因为 `convertToVO` **无条件**调 `countUsersByPositionId`（不是只有写操作才挂）。

> **修法（二选一）**：① 给 `sys_user_position` **补 `deleted INTEGER DEFAULT 0` 列**并**加入 `IGNORE_TENANT_TABLES`**（该表是用户-岗位关联，`sys_user` 已在忽略表中，语义一致）—— **推荐**；
> ② 去掉三处 `@Select` 的 `AND deleted = 0` 并加忽略表（但 `assignToUser` 的物理 `delete` 会变成真删除，需一并改）。
> **注意**：这不是「隔离得不好」，而是**直接报错**（参见《_开发指南-金标准》陷阱 15 原话）。

### 6.4 🔴 P0：HR 侧前缀不一致 → 本页「岗位区」全部 404

| 同模块其他控制器 | `/api/hr/recruitment`、`/api/hr/candidate` | `HrRecruitmentController.java:23`、`HrCandidateController.java:23` |
| 前端 `baseURL` / api 写法 | `/api` + `request.get('/hr/positions/page')` | `utils/request.ts:93`、`api/hr/index.ts:23` |
| 实际发出的 URL | **`/api/hr/positions/page`** | `baseURL + url` |
| 前缀补正机制 | **三处均无**：servlet `context-path` 各 profile 都是 `/`；`HealthCheckConfig.configurePathMatch` 为空实现；全仓裸前缀控制器**只有 `HrController` 一个** | 逐项已核 |

### 6.5 🔴 P0：`hr-base` 无 mapper XML → 10 个自定义方法无 SQL 绑定

- `hr-base` 的 `src/main/resources` **不存在**（`ls backend/hr/hr-base/src/main` 只有 `java/`）；**全仓 mapper XML 0 个**（`find backend/hr -name '*.xml'` 无结果）；`HrPositionMapper.selectByDeptId`（`HrPositionMapper.java:11`）**无 `@Select`** → 调用即抛 `Invalid bound statement (not found)`。
- **受影响方法（共 10 个）**：`HrPositionMapper.selectByDeptId`、`HrEmployeeMapper.selectByDeptId/selectByEmployeeNo/updateStatus`、`HrContractMapper.selectByEmployeeId`、`HrAttendanceMapper.selectByEmployeeAndMonth`、`HrLeaveRequestMapper.selectByEmployeeId`、`HrSalaryStructureMapper.selectEffectiveByEmployeeId`、`HrSalaryPaymentMapper.selectByEmployeeId`、`HrPerformanceMapper.selectByEmployeeId`。
- **与本页的关系**：`selectByDeptId` 经 `HrPositionService.getByDeptId` 暴露，**但 `HrController` 无对应端点** → 本页「按部门查岗位」走 `page(deptId=…)`，**当前不触发**；一旦接上该端点（推荐做法）即 500。
- **修法**：补 `hr-base/src/main/resources/mapper/*.xml` 并配 `mybatis-plus.mapper-locations`；或改 `@Select`（**手写 SQL 不会被多租户插件改写，须自己拼 `tenant_id` 与 `deleted = 0`**，参见《inSql/apply 手写SQL不带租户条件》）。

### 6.6 缺失（全 HR 模块共性）与端点缺口

> 1. **无 DTO / VO / 校验（仅 HR 侧）**：`HrController` 直收发实体 `HrPosition`，无 `@Valid`。对比：`DepartmentController` 用 `DepartmentQueryRequest` + `DepartmentVO`；`PositionController` 用 5 个 DTO + `@Valid`。**系统侧有，HR 侧没有**。
> 2. **无鉴权注解**：`HrController` 类与方法级**均无** `@SaCheckLogin` / `@RequiresPermission`（对比 `DepartmentController` 每个写方法都有）。
> 3. **无审计人**：`MetaObjectHandler.insertFill` **只填 `createTime` / `updateTime` / `tenantId`**（`MyBatisPlusConfig.java:175-190`），**没有 `createBy` / `updateBy`** → 所有 HR 表与 `sys_department` 的这两列**永远为 NULL**。
> 4. **权限码**：`sys_permission` 全表 **169 行**，前缀只有 `crm / department / erp / finance / log / permission / position / purchase / role / sale / stock / system / tenant / user` —— **HR 侧 `hr:*` 0 条**；`department:*` **6 条**、`position:*` **7 条**（均已登记）。

**待新增端点**：`GET /api/department/{id}/stats`（部门人数/编制/缺口/岗位数，**P0 业务**）、`GET /{id}/members`（成员下钻，P1）、`GET /api/department/org-chart`（组织结构图，P1）、`POST /{id}/batch-move`（组织批量调整，P2）、`GET /api/department/change-log` + `/{id}/history` + `PUT /{id}/effective`（变动明细/历史版本/生效日期，P2）。

## 7. 数据模型

### 7.1 `sys_department`（19 列，devdb 实测）

建表：`V5.0.0__Consolidate_DDL_And_Seed_Data.sql:544-564`

```
id BIGINT PK, tenant_id BIGINT DEFAULT 0, parent_id BIGINT DEFAULT 0,
deleted INTEGER NOT NULL DEFAULT 0,                 -- @TableLogic
create_time / update_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
create_by BIGINT, update_by BIGINT,                 -- ⚠️ 无填充器 → 恒 NULL
dept_code VARCHAR(100),                             -- ⚠️ 无 UNIQUE
dept_name VARCHAR(200) NOT NULL,
ancestors VARCHAR(500),                             -- 祖级路径（如 0,1,2），⚠️ 无索引
leader_id BIGINT, leader_name VARCHAR(100),         -- ⚠️ 本页无控件
phone VARCHAR(50), email VARCHAR(200),
sort INTEGER DEFAULT 0,
status INTEGER DEFAULT 0,                           -- ⚠️ DB 默认 0，Service 默认 1
remark VARCHAR(500),                                -- 对外别名 description
version INTEGER DEFAULT 0                           -- @Version
```

**无 `level` 列、无 `path` 列**（§5.1）。**索引**：建表语句**未创建任何索引**（除主键）→ `parent_id` / `dept_code` / `ancestors` **全无索引**。
**当前行数**：**2 行**（`id=9001 财务部 D9001 sort=1 status=0`、`id=9002 市场部 D9002 sort=2 status=0`；`tenant_id` 均 `1`，`parent_id` 均 `0`，**`ancestors` 均为 `null`**）。
**逻辑删 / 乐观锁 / 租户**：`Department extends BaseEntity` → `@TableLogic` + `@Version` 列齐备；`tenant_id` 存在且**不在**忽略表 → 拦截器生效 ✅。

> **⚠️ 验收前提**：这 2 行**都是 `status = 0`（禁用）**，而 `getList()` 只返回 `status = 1` → **本页部门树在现状下必然为空**。任何 UI 验收**必须先造数或把种子行改为启用**。

## 10. 验收标准（目标）

> 本模块**尚无 E2E 脚本**（`tools/` 下无任何 `e2e-hr*.cjs`）。
> **前置条件（重要）**：`hr_*` 表**全部 0 行**；`sys_department` 仅 2 行且**均 `status = 0`**；`sys_position` / `sys_position_category` / `sys_user_position` 均 0 行。任何验收**必须先造数**，并**在收尾时清理自产数据**（参见《共享db E2E 断言必须加作用域》）。

### 10.1 接口验收（目标 ≥ 18 项）

1. `GET /api/department/list` 返回 200，条数与直查 DB（`deleted = 0` + `tenant_id` + **`status = 1`**）一致 —— **此项即 P0「树为空」的回归断言**。
2. `GET /api/department/tree` 返回嵌套结构，根节点数 = DB 中 `parent_id = 0` 的行数。
3. `GET /api/department/page` 的 `departmentCode` / `departmentName` / `parentId` / `status` **逐个生效**（造数验证）。
4. `POST /api/department` 新建后 DB 可查回；`dept_code` 重复时报「部门编码已存在」（非 500）；新建后 `ancestors` **不含 `"null"` 字样**（P1 回归断言）。
5. `PUT /api/department/{id}` 改名后三级回读（DB / 详情 / 列表）一致；`PUT /{id}/status` 改状态后 DB 一致。
6. **改父后 `ancestors` / `level` 正确**（当前不重算 —— 目标行为，此项即 P0 的回归断言）。
7. `POST /api/department/{id}/move`：`inner` → 父级变更且**整棵子树 `ancestors` 同步更新**（移动含 3 层子树的部门后逐层校验前缀）；`before` / `after` → **`sort` 真的被调整**（当前完全没调 —— 此项即 P0 的回归断言）。
8. `move` 防环：把父部门移到自己子部门下 → 业务错误。
9. `DELETE /api/department/{id}`：有子部门 → 拒绝；**被 `hr_employee` / `hr_position` 引用 → 拒绝**（目标行为）。
10. `GET /api/department/export` 返回 CSV，条数与 `page` 的 `total` 一致。
11. `GET /api/hr/positions/page`（按 `deptId` 过滤）返回 200（**当前 404 —— 此项即 P0 前缀的回归断言**）。
12. `POST /api/hr/positions` 提交 `deptId` 后，DB `hr_position.dept_id` **非空**（**当前 UI 无该字段 —— 此项即 P0 的回归断言**）。
13. `GET /api/position/page` 返回 200（**当前因 `sys_user_position` 缺列必 500 —— 此项即 P0 的回归断言**）；`POST /assign` + `GET /{id}/users` 闭环、`is_primary` 正确（**目标行为**）；`GET /api/position/category/tree` 返回分类树。
14. 越权：未带 token 请求 `HrController` 端点应 401（**当前无鉴权注解，此项预期失败**，作为 P1 证据）。

### 10.2 UI 验收（目标 ≥ 10 项）

1. **本页可达性**：按 §9.3 方案落地后菜单能打开组织架构页、**页面不空白**；收敛前本页应**如实记为不可达**。
2. 页面**控制台无 error**（含 `ReferenceError` —— 参见《重构搬迁后必须做运行时验证》）；**断言网络无 4xx**（`GET /api/hr/positions/page` 与 `GET /api/department/*` 均必须 200）。
3. **左部门树有数据**（种子 `status` 改为 1 后）；**选中非根部门时标题正确显示该部门名**（当前回落成「全部岗位」）。
4. **部门树-表联动**：切换部门后右表按 `deptId` 过滤、标题与过滤条件一致，且**按该部门新建的岗位能立刻在右表出现**（验证 `dept_id` 已落库）。
5. 部门弹窗：新建成功；**编辑成功**（当前编辑分支是死代码）；上级部门下拉**有可选项**（当前因禁用被过滤而为空）。
6. 岗位弹窗：必填校验生效（`positionName`）。
7. 表头齿轮可改列显隐/顺序，刷新后**个人配置保留**（目标）。
8. 分页为**经典形态** `.classic-pagination`，页长选项 `[20,50,100]`（目标）；**打印判 N/A**（勿按模板硬加）。
9. 按钮按权限码显隐：无 `department:create` 的账号**看不到「新增部门」**（当前一律展示）。
10. 收尾：清理验收造出的 `sys_department` / `hr_position` / `sys_user_position` 行，并复核现场已复原。

## 12. 剩余缺口（不阻塞，如实登记）

1. **本页是孤儿页面**（`sys_menu` 无对应行），用户不可达；处置建议见 §9.3。**最高优先**。
2. **`views/system/department/index.vue`（1138 行，功能最全）与 `views/system/position/index.vue`（1301 行）也都没有菜单** —— 「部门 / 岗位」前端**共 6 个页面，只有 2 个可达**（`md/staff-dept`、`md/staff-role`，且都是 `ARReportPage` 路线 B）。
3. **部门树为空**（种子 `status = 0` vs `getList()` 硬编码 `status = 1`）；**岗位弹窗无「所属部门」** → `hr_position.dept_id` 恒 NULL，本页核心联动语义失效。
4. **`move` 的 `before` / `after` 不可用**（不调 `setSort`、`ancestors` 赋值错）；`inner` 不级联更新子树路径；`update()` 改父不重算路径；**删除部门不检查引用**。
5. **`sys_user_position` 双重结构硬伤**（缺 `deleted` + 缺 `tenant_id` 且未加忽略表）→ `PositionController` 的 `page` / `assign` / `remove` / `users` 全 500。
6. **整个 HR 模块端点 404**（`HrController` 前缀缺 `/api`）+ **`hr-base` 无 mapper XML**（10 个自定义方法无绑定）。
7. **无生效日期 / 无历史版本 / 无组织调整申请**（业界 Effective Dating 口径）。
8. **组织不参与权限判定**（无数据级可见范围；菜单名「岗位权限」实际是岗位主数据页，其 `a-alert` 已自认权限能力未实现）。
9. **无组织/岗位统计端点**（部门人数 / 编制数 / 缺口数 / 满编率）；**无组织结构图**。
10. **HR 权限码 0 条**、`HrController` 无鉴权注解；**`create_by` / `update_by` 恒 NULL**。
11. **`sys_department` 除主键外无任何索引**，`dept_code` 无唯一约束，`status` DB 默认与 Service 默认不一致；**无模块级 E2E、无验收截图**。
