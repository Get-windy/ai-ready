## 1. 页面概述

存储配置页是**平台运营方的文件存储接入台账**（本地目录 / 对象存储二选一，共 5 种存储方式）：**上下两张卡片**（上 `a-card title="文件存储配置"` 内一个随 `storageType` **条件渲染字段块**的表单；下 `a-card title="存储概览"` 内 **3 个 `a-statistic`**）+ **2 个按钮**（`保存配置` / `测试连接`）。它属于 `61306 平台设置` 组的第 4 页（`sort=400`）。

### 1.2 `/api/storage` 这个前缀到底有什么（**必须辨析：前缀存在 ≠ 本页能用**）

| 控制器 | 类前缀 | 端点 | 与本页的关系 |
|--------|--------|------|-------------|
| `cn.aiedge.platform.controller.StorageConfigController` | **`/api/storage-config`** | `GET /config`（`:25`）、`POST /config`（`:34`）、`POST /test`（`:44`） | ✅ **本页真正需要的后端**（但前端一个都没调到） |
| `cn.aiedge.storage.controller.FileStorageController` | **`/api/storage`** | `POST /upload`（`:44`）、`GET /download/{fileId}`（`:72`）、`GET /info/{fileId}`（`:95`）、`GET /preview/{fileId}`（`:107`）、`DELETE /{fileId}`（`:121`）、`DELETE /batch`（`:133`）、`GET /url/{fileId}`（`:142`）、`GET /presigned-url/{fileId}`（`:154`） | ❌ **与"配置"无关**（这是文件读写 API）。**注意**：`/api/storage/config`、`/api/storage/test` **不在其中**（方法 + 层级都不匹配，不会被 `DELETE /{fileId}` 之类吞掉） |
| `cn.aiedge.storage.chunk.ChunkUploadController` | **`/api/storage/chunk`** | 分片上传相关 | ❌ 无关 |

> **结论**：**`/api/storage` 前缀是"活的"，但活的是文件读写 API，不是配置 API** —— 这是一个**极强的误导**：开发/测试时看到 `/api/storage/*` 有响应，会误以为"前缀没问题"；**实际本页需要的 `/config`、`/test` 两个子路径在该前缀下根本不存在**（全仓 `grep storage/config`、`storage/test` 于 `--include=*.java` → **0 命中**）。

### 7.4 租户拦截器与 `Map.of` NPE 的耦合（**修好路径 + 装配后立刻会遇到**）

```text
GET /api/storage-config/config
  └─ StorageConfigController:30  storageConfigService.getConfig(tenantId)
       └─ StorageConfigServiceImpl:20-33
            ├─ selectOne(... eq(tenant_id, <会话租户>))   ← 租户插件自动注入
            └─ 兜底 selectOne(... .last("LIMIT 1"))        ← 插件同样注入 → 等价于第一次
  └─ StorageConfigController:31  return ResponseEntity.ok(Map.of("code", 200, "data", config, "message", "ok"))
       └─ JDK Map.of 对 null value 抛 NullPointerException → 500
```

| 会话情形 | 结果 |
|---|---|
| **超管（重登后）** | `AiReadyTenantLineInnerInterceptor.shouldSkip()`（`:41-44`）= `isTenantScopeExempt()` 为真 → **整体跳过注入** → 能查到 `tenant_id=0` 的第一条 → **正常 200**（**注意：因无 `tenant_id` 过滤，返回的可能是 `tenant_id=0` 的行而不是 `tenant_id=1` 的真实行**） |
| **超管但用旧 token** | 未豁免 → 注入 `tenant_id=1` → 主查能查到 **id=3**（该行恰为 tenant 1）→ **可能 200**；若会话租户是**其它值**（如 `2`）→ 主查/兜底均 null → **`Map.of` NPE → 500** |
| **非超管账号（会话租户 = 1）** | 注入 `tenant_id=1` → 主查命中 **id=3** → **可能 200** |
| **非超管账号（会话租户 ∉ {0,1}）** | 主查/兜底均 null → **500** |

> 口径依据：README §1.3 红线②（**已订正**）：写入点 `SysUserServiceImpl.java:88`、读取点 `AiReadyTenantLineInnerInterceptor.java:41-44` + `MyBatisPlusConfig.java:157-166`。
> **本页的特殊性**：**3 行里恰好有 1 行 `tenant_id=1`**，所以「超管旧 token / 非超管（会话租户=1）」**可能反而读得到数据** —— 这让"读不到"的现象**更不稳定**，验收时必须**写死账号 + 会话租户 + 是否重登**。

**修法（推荐显式声明，不依赖会话豁免）**：读全局用 `@InterceptorIgnore(tenantLine = "true")`；写目标租户行前 `MyBatisPlusConfig.setTempTenantId(tid)`。**另**：`Map.of` 用法应改为 `HashMap`（允许 null）或先做空值判断，否则「无配置行」这一合法状态会变成 500。

## 10. 验收标准（目标）

> **前置**：本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下不存在 `e2e-system-*.cjs` / `e2e-admin-*.cjs`）。脚本建议命名 `tools/e2e-system.cjs`（接口 + 直连 DB 对账 + 写库后复原 + Playwright UI 截屏，参照 `tools/e2e-crm.cjs`）。
> **🔴 本页验收的四条硬纪律（务必先读）**：
> 1. **绝对不要改动 `sys_storage_config.local_path` 的值** —— **`id=3` 的 `I:\AI-Ready-file` 是本机真实运行依赖的路径**，改坏会导致**上传/读取文件失败**；写断言**一律不得触碰 `local_path` / `local_url_prefix` 两列**；
> 2. **绝对不要改动 `access_key` / `access_secret` 列**（当前为空串，不要写任何值进去）；
> 3. **绝不真实执行"存储迁移"**（本页无该能力，但要防止有人手写脚本去搬文件）；
> 4. **写库断言必须「改库 → 回读 → 按原值复原」**：建议只动 `id=1`（种子行）的**非路径列**（如 `endpoint`），并**先记录原值**。
> **⚠️ 本页验收的最大特点**：**当前 3 个请求全部 404（路径不匹配）**；**修好路径之后仍是 404**（包未装配）。因此断言要**三段式**：`【现状】` → `【仅改路径】` → `【路径+装配都修好】`。

### 11.1 必须写清的「通道判别」事实（《对标开发技术参考文档》§5.6.2 硬规则）

1. **模块自带 yml 不生效**：若把 `storage.local.*` 写进 `storage` 模块或任何**模块自带**的 `src/main/resources/*.yml`（位于嵌套 jar 内），**core-api 启动时不会加载**（Spring Boot 只读 classpath 根那一份）→ **必须写到 core-api 的 `application.yml` / `application-dev.yml`**（或启动参数 / 外部化文件）。
   **本页现状**：`storage.local.base-path` **已在 core-api `application-dev.yml`**（§5.6.3 已登记）→ ✅ 这一点是对的；**但 DB 里的 `sys_storage_config.local_path` 与它无任何连线** → **两条真源并存**。
2. **前端 `VITE_*` 是构建期注入**：本页**未使用** → 无需 CI 注入；代价是**任何前端改动（三卡、路径、校验、loading 缺陷）都属前端改动 → 必须 rebuild 才生效**。
3. **密钥优先不入库**：`sys_storage_config.access_key` / `access_secret` 是明文列 —— 能用环境变量/Secret 的**绝不写进表**；确需页面维护的，按通道 ④ 落库，并遵循「**脱敏展示 + 仅授权角色可见 + 日志不打印**」（本页日志侧**已做到不打印**，其余两项**均未做到**）。
   **⚠️ 另需注意**：`local_path` **本身也是敏感信息**（服务器文件系统结构）→ 应按「仅授权角色可见」处理（当前**明文展示给所有能看到本页的人**）。
4. **必须有降级**：配置缺失时**不得阻塞业务**。当前 `storage.local.*` 缺失 → 上传文件跨实例 404（**明确失败**）；**本页不可作为兜底**（未接线）→ 表现为「用户在页面上配了也没用」。
   **⚠️ 特别提醒**：**`local_path` 改成相对路径 = 静默漂移**（不报错但文件写到别处）→ 属"**不报错的降级**"，比 404 更危险；校验必须做「是否绝对路径」。
5. **换配置要能生效**：本页**当前无生效方式**（无消费方 + 404）。目标形态**须先裁定**：
   - **路线 A（推荐，底稿 §6.4 口径）**：保持 `storage.local.*` 为唯一真源 → 本页改成**只读诊断页**（显示当前生效的存储方式 / 根路径 / 访问前缀 + **根路径与容量校验**，**不回显凭据明文**，参照 `GET /api/dms/route/config` 的 `keySource` 口径）；**不做运行期切换**（**高风险：牵动已上传文件迁移**）。
   - **路线 B**：让 `LocalStorageStrategy` 改读 `sys_storage_config`（热生效）→ 需补**缓存失效机制**（保存后发领域事件 + 消费方失效本地缓存，多实例 TTL 兜底），并**显式豁免租户插件**（§11.1-6）；**且必须先解决"切换时的文件迁移"**。
6. **多租户读全局默认行**：`sys_storage_config` 有 3 行（`tenant_id` 为 `0/0/1`）→ 读它**必须** `@InterceptorIgnore(tenantLine = "true")`（读全局）或明确按会话租户读；否则被租户插件注入条件 → **3 行里只能看到 1 行（或 null → `Map.of` NPE → 500）**（§7.4）。
