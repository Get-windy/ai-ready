## 4. 业务规范

- **促销规则模型（同构实据归纳）**：
  - 作用层级：按整单门槛生效——整单金额/数量满 N 触发减/赠/折；落点为销售订单摘要结账面板「促销优惠、优惠金额(−)」。
  - 与商品促销的分工（列结构同构实据）：商品促销按「订单单个促销商品」触发（行级）；整单促销按整单汇总门槛触发；两页查询区与 13 列完全一致，说明共用同一套促销活动模型，仅促销方式不同。
  - 定向维度：促销商品、促销客户、使用范围三维定向（列实据）。
  - 组合促销：是否可与其他活动叠加的标记（列实据），行级取值待复核。
  - 生命周期：新增 → 时间窗内生效 → 过期/作废；「显示已过期/已作废活动」默认隐藏（基准文档勾选项实据）。
- **与其他页面关系**：与《商品促销开发文档》互补（单级 vs 行级；叠加规则由「组合促销」列控制）；销售开单联动（整单优惠在销售订单摘要面板体现）；商城侧「我要推广」可推广促销活动；本系统落地对应 `/api/sale/promotion`。

| 命中判定 | 活动状态 `published` + 时间覆盖 + 使用范围（线下/商城）匹配 + 促销客户（空＝全部，雪花 id 按字符串比对） | — |
| 优先级 | `priority` 降序，**同优先级按 id 升序兜底** | SAP 明确要求避免同优先级（否则随机选择） |
| 叠加/互斥 | `stack_policy=STACK` 继续算；`EXCLUSIVE` 命中即停（更低优先级不再参与） | SAP 独占/非独占规则组 |
| 条目消耗 | 同一商品行只被**一个行级**活动（商品促销/特价）消耗，高优先级先占 | SAP Order Entry Consumption |
| 折扣计算 | 打折＝匹配行金额×(1−折扣率)；满减＝达门槛减固定额；特价＝Σ(行成交价−特价单价)×数量；满赠＝0（只登记赠品） | Odoo Reward 类型 |
| 封顶 | `max_discount_amount` 限制单条活动在本单的优惠上限 | SAP Caps |
| 分摊 | 行级优惠摊到命中行；整单级优惠按**各行金额占比**摊到每一行（末行吃舍入残差，保证合计=优惠额） | SAP / Commerce Layer 分摊法 |
| 券校验 | 状态 UNUSED + 未过期 + 属本客户 + 通道开关 + 门槛（`use_rule`） | — |
| 次数 | 试算**不累加**；只有落单才 `quota_used + 1` | — |

### 顺带修掉的既有缺陷（跨模块，与本轮改动无关但阻断验证）

`biz_party_grade_relation`（客户等级关系）**无 `tenant_id` 列**却未登记 `IGNORE_TENANT_TABLES` →
多租户拦截器注入 `AND tenant_id = 1` → 该查询在 `getCustomerGradeCode` 的 try 里被 catch 吞掉，
但 **PostgreSQL 已把整个事务标记为 aborted** → 其后所有语句报「当前事务被终止，事务块结束之前的查询被忽略」→
**销售订单创建整体 500（整单不可用）**。
已按「同类一次收口」把资料域无 `tenant_id` 的 5 张表一并登记：
`biz_party_grade_relation`、`biz_party_address`、`biz_party_role`、`biz_party_transaction`、
`biz_customer_grade_price`（外加 `biz_migration_log`）。
