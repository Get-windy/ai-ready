## 页面概述

退款管理是**在线支付退款请求的统一审批中心**：查询退款请求（申请金额、退款原因、申请人、状态、渠道退款号、创建时间），对待处理（status 0）的退款单做批准/拒绝（单条或批量），并通过渠道回调 `POST /api/refund/callback/{channel}` 结果更新为已退款/已拒绝。（**无创建入口**——退款请求由业务侧 `POST /api/refund/request` 发起，本页做审批。）**单入口，双 Tab（Tab1「按退款单」/ Tab2「按退款明细」），无独立表单**。

| 页面 | 地址 | 说明 |
|------|------|------|
| 退款管理 | `payment/refund` | 双 Tab 列表页（Tab1「按退款单」/ Tab2「按退款明细」；统计卡片 + 数据表 + 审批流） |

单入口：交易模块 → 支付管理 → 退款管理。

- 实测实据：数据表列配置 Tab1 **11** / Tab2 **8**（默认显示 7 / 6）、查询字段 4、列/页面配置弹窗 **有**（表头 rowNo 列齿轮列配置 + 独立页面配置面板，逐 Tab 独立）。
- 状态机（`REFUND_STATUS_MAP`）：0 待处理 / 1 处理中 / 2 已退款 / 3 已拒绝。

- 行级操作：**详情**（抽屉）、**批准**、**拒绝**（仅 `status===0` 时显示；Modal 确认后 `/request/{id}/approve?approved=1|0`）。

## 业务规范说明

- **退款主线**：支付成功（`payment_record`）→ 业务侧发起退款 `POST /api/refund/request`（paymentId+金额+原因）→ 本页审批（批准走在线退款流程，拒绝则结束）→ 渠道回调 `POST /api/refund/callback/{channel}` 落退款结果 → 状态 待处理/处理中/已退款/已拒绝。
- **金额口径**：退款金额 ≥0 且 ≤ 支付可退金额（对外发起）；页面以 ¥ 红色展示。
- **审批**：待处理（status 0）可批准/拒绝；单条或批量。审批后为处理中（status 1）→ 回调成功 已退款（2）/失败 已拒绝（3）。
- **审批人留痕**：`approverId`/`approveRemark`（后端）；前端详情抽屉已展示「审批人」（`approverName || approverId`）与「审批备注」。
- **与支付请求的关系**：`paymentId` 关联支付请求/支付记录；渠道退款号 `channelRefundNo` 对应第三方退款单号。
- **下游客商**：ql361 参照「设置→支付配置→在线退款」的自动退款说明：有处理中的在线退款时不能再次提交退款，在线退款处理完成后方可发起（本系统需在审批侧取值）。

### 后端改动（本轮）
- `RefundController`（`cn.aiedge.payment.controller`，`@RequestMapping("/api/refund")`）
  - `GET /request/page` **扩参**：pageNum、pageSize、status、refundNo(渠道退款号/支付请求ID)、startTime、endTime、channel
    - `refundNo` 纯数字时 = `channel_refund_no` 模糊 **OR** `payment_id` 等值；非数字仅按渠道退款号模糊
    - `channel`：`refund_request` 无渠道列 → 先取该渠道的 `payment_request.id` 集合，再 `in(payment_id)`（集合为空直接返回空页）
    - 退款日期口径 = 申请创建时间 `create_time`（非 `refunded_time`）
  - `GET /request/stat?channel=` — **新增**，后端聚合返回 `total / pendingCount(status=0) / approvedCount(status 1+2) / rejectedCount(status=3) / totalAmount`
  - `POST /request/{id}/approve?approved=&remark=` — 审批留痕：`approver_id` 取当前登录用户（`StpUtil`，无登录上下文时留空、不阻断审批）、`approve_remark` 落库；**拒绝时写 `process_time`**（批准 → status=1 处理中，不写 `process_time`；回调成功 → status=2，写 `refunded_time`）
  - 其他已有：`POST /request`、`GET /request/{id}`、`POST /callback/{channel}`、`GET /record/page?channel=`（仅 pageNum/pageSize/channel）
- Flyway 迁移：`V11.361.2__Add_Refund_Request_Process_Time.sql`（新增列 `refund_request.process_time` TIMESTAMP，注释「处理时间（审批完成时间）」）、`V11.361.4__Add_Refund_Request_Approver_Name.sql`（新增列 `refund_request.approver_name` VARCHAR(100)，审批时按 `approver_id` 关联 `sys_user.real_name`/`nickname`/`username` 回写）
- **审批人姓名已闭环**：`refund_request.approver_name` 列 + 实体字段已补，`RefundServiceImpl` 审批时回写姓名；前端抽屉 `approverName || approverId` 与列表「审批人ID」列不再退化为数字 ID。
- 其他模块本轮改动（与本页无关）：新增 `ExternalOrderController`（含 `/stat`、`/{id}/retry`）；`ChannelConfigController` 补 `/stat`；`InventorySyncController` 补 `/stat`、`/{id}/retry`；迁移 `V11.361.1`（对账 `handle_method`）、`V11.361.3`（交易模块金标准字段）

### 明确不借鉴
- **业界界面视觉样式**（唯一不借鉴项）：不采用其配色、圆角、阴影、字体与组件外观；外观令牌一律取自本系统既有主题。
- **不照搬字段命名**：仅语义对齐，本系统字段名以库表与既有实体为准（如 SAP `Pending Settlement` 对应 `status=0/1`、`Settled` 对应 `status=2`、`Failed` 对应新增失败态；Odoo `source_transaction_id` 对应本系统 `paymentId`）。
- **退款过账到原应收科目（SAP：退款金额 post 到原应收科目并生成反向凭证）**：本系统 `core-payment` 为**支付中台，不产生记账凭证**，退款与财务凭证/科目自动过账的打通属财务域职责，超出本页范围 → 不借鉴（如后续需要，另立财务域文档）。
- **冲正（`Reversed`）的「能力」本身**：依赖渠道撤销接口与会计凭证体系，本系统 `PaymentChannel` 未提供撤销退款方法、`core-payment` 不产凭证 → **能力待复核**，不预设字段名。
  > ✅ **已修正（2026-09-15 复盘）**：原条目把**「跳转查看反向日记账」这一下钻交互**一并排除，属**误判**——下钻交互应借鉴（已上移为「关联单据下钻」一行与「冲正/撤销的交互入口」一行）。此处**仅保留"能力前提未就绪"**这一客观限制。
- **卡授权/令牌化相关口径**：SAP F7326 面向**卡支付**授权，本系统涵盖支付宝/微信/银联/银行转账/现金（`PAYMENT_CHANNEL_MAP`，`api/payment/index.ts:5-11`），渠道口径更宽，不引入卡授权语义。
- **币种字段（Odoo `currency_id`）**：本系统 `refund_request` 无币种列、按单一结算币种处理 → 不借鉴（若将来做多币种，此项转为可借鉴）。
