## 1. 页面概述

合同审批页是 CRM 模块的**审批工作台**：把「待审批」的合同集中处理（通过 / 驳回），并允许把「草稿」直接提交审批。它与《合同开发文档》的列表页**共用同一批后端端点**（`/api/crm/contract`），但**独立菜单、独立页面、独立统计口径**。

| 项 | 值 | 证据 |
|----|-----|------|
| 页面 | `crm/contract-approval`（单入口） | `sys_menu.id=70341`，`display_mode=0`，`list_path=null` |
| 组件 | `views/crm/contract-approval/index.vue`（**313 行**） | 同上游菜单 `component=views/crm/contract-approval/index.vue` |
| 路由 | `crm/contract-approval` 与 `crm/contract-approval/index` 均指向该组件 | `router/dynamicRoutes.ts:492-493` |
| 外壳 | **`ARReportPage`（路线 B，报表页）** + 2 个 `a-modal` | `index.vue:3-13,60-116` |
| 后端 | 复用 `ContractController`（前缀 `/api/crm/contract`，40 个端点） | 见《合同开发文档》§6.1 |

**1.1 与合同列表页的分工**

| | 合同列表页（`80230`） | 本页（`70341`） |
|---|---|---|
| 外壳 | `PageContainer` + `ErrorBoundary` + `BillTableList` | `ARReportPage`（内部 `ErrorBoundary > PageContainer > ARStatCards + a-table`） |
| 行操作 | 查看/打印/编辑/审批/签订/更多 | **仅**「通过 / 驳回 / 提交审批」三态分流 |
| 审批意见 | **不收集**（`approve(id)` 的 `note` 恒 `undefined`，见《合同开发文档》§3.4） | **可填**（通过弹窗 `approveNote`，非必填） |
| 统计口径 | **当前页**聚合（4 张卡） | **全量**聚合（走 `/crm/contract/export`） |
| 列定义 | 10 列（vxeColumns + 插槽） | 10 列（`a-table` columns，**无列配置齿轮**） |

**1.2 本页不提供的能力（如实登记）**：无审批记录/审批历史、无批量审批、无审批意见模板、无合同内容预览（金额以外的明细/条款/附件一律看不到）、无审批耗时与超时提醒、无多级审批、无电子签。**门槛**：本页只做「单级 + 单人」的审批动作。

3. **源码注释的前提与现状不符（P2，静态核对结论）**：`index.vue:194-195` 注释称「`/crm/contract/statistics` 为裸 Map 会被拦截器误判，故改用 `/crm/contract/export` 聚合」。核对 `utils/request.ts:207-221`：拦截器对**无 `code` 键**的裸响应判定为成功（`hasCode === false → isOk = true`），返回 `data !== undefined ? data : resData`，因此**裸 Map 本不会被误判**。该注释可能反映早期拦截器版本的行为，或另有隐情 → **建议运行期复核一次 `/crm/contract/statistics`**，确认后再决定是否切回后端聚合（后端 `/statistics` 亦存在「循环 11 次 COUNT」「金额只统计 5 态」两个问题，见《合同开发文档》§6.2）。

## 4. 表单页配置

**本页无表单页**：菜单 `display_mode = 0`（单入口）、`list_path = null`（devdb 实测），本页自身即全部界面。页内的两个 `a-modal`（审批通过 / 审批驳回）为**动作确认弹窗**，字段清单见 §3.7 —— 共 5 个字段位：合同（只读）、合同金额（只读）、审批意见（textarea 非必填）、合同（只读）、驳回原因（textarea 必填）。

> **不发明字段**：上述 ★ 项均指向 `crm_contract` **已有列**（§7）或纯 UI 约束，无需新增字段。唯一需要新增实体的是**审批记录表**（见 §8）。

## 5. 业务规范

### 5.1 状态值域（本页 **11/11 完整**）

`CONTRACT_STATUS_OPTIONS`（`:128-140`）、`STATUS_TEXT`（`:141-144`）、`STATUS_COLOR`（`:145-148`）三处均为 **11 项**，与后端 `ContractStatus`（`enums/ContractStatus.java:4-14`）逐字一致：`0 草稿 / 1 待审批 / 2 已审批 / 3 待签署 / 4 已签署 / 5 生效中 / 6 执行中 / 7 已完成 / 8 已终止 / 9 已过期 / 10 已取消`。
> 对比：合同列表页的筛选下拉只有 **8/11**（缺 6/9/10），表单页 `status` 只有 4 值且语义不同（见《合同开发文档》§5.1）。**本页是全 CRM 合同域状态映射最完整的一处**。

### 5.2 审批链路（后端唯一真源，**单级**）

```
0 草稿 ── submit（仅 0）──▶ 1 待审批 ── approve（仅 1）──▶ 2 已审批  （写 approved_by/approved_time/approved_note）
                              └─ reject（仅 1）──▶ 0 草稿  （⚠️ 驳回人与原因均不落库）
```

| 动作 | 后端 | 前置校验 | 失败文案 | 副作用 | 行 |
|------|------|:--------:|---------|--------|----|
| 提交审批 | `POST /{id}/submit` | `status == 0` | 只有草稿状态的合同可以提交审批 | 状态 → 1 | `ContractServiceImpl.java:179-190` |
| 审批通过 | `POST /{id}/approve?note=` | `status == 1` | 只有待审批状态的合同可以审批 | 状态 → 2；`approved_by` = `StpUtil.getLoginIdAsLong()`（`ContractController.java:132`）；`approved_time` = now；`approved_note` = note | `:194-208` |
| 审批驳回 | `POST /{id}/reject?reason=` | `status == 1` | 只有待审批状态的合同可以拒绝 | 状态 → **0**；**`rejecterId`/`reason` 未写入任何字段** | `:212-223` |

**🔴 单级审批的三个结构性缺陷**：
1. **无审批记录表**：devdb 实测 `crm_%` 共 16 张表，**不存在 `crm_contract_approval`**；审批结果只体现为合同行上的 3 个列（`approved_by`/`approved_time`/`approved_note`）→ **只能保留"最后一次通过"的痕迹**；驳回则**什么都不留**。
2. **无多级/分支**：`submitForApproval` 只有一条路径（0→1），`approve` 只有一条（1→2）。**无金额阈值、无部门/角色分支、无会签**。
3. **该链路不经过工作流引擎**：`ContractServiceImpl` 仅注入 4 个 Mapper（`:36-39`），**无任何 `workflow_*` / 审批流调用**；系统内已存在 `workflow_definition`/`workflow_node`/`workflow_instance`/`workflow_task` 四表（`MyBatisPlusConfig.java:56-59` 有登记），**合同审批未接线**。

### 5.3 审批人取值与「自审」问题

审批人一律取当前登录人（`StpUtil.getLoginIdAsLong()`），**不做任何校验**：既未校验审批人是否拥有审批权限（后端无权限注解），**也未校验审批人 ≠ 提交人 / 制单人**。→ 同一用户可以「建合同 → 提交 → 自己审批通过」一条龙（`create_by` 与 `approved_by` 会是同一人，`crm_contract` 两列均在，可用于事后审计，但**系统不拦截**）。
> 对比业界：SAP Release Strategy 会按审批策略解析出审批人集合；用友审批流节点可配置"审批人不得为提交人"。本系统属**能力缺失**，如实登记为缺口（§9.2 / §12）。

### 5.4 「审批上下文」不足

弹窗只展示 **合同名称 / 合同编号 / 合同金额** 三项（`:72-77`）。审批人**看不到**：合同条款（子表 `crm_contract_clause` 未接）、附件（`crm_contract_attachment` 未接）、付款计划（`crm_contract_payment` 未接）、风险等级与备注（`risk_level`/`risk_note` 已有列未展示）、执行/已收金额（`execution_amount`/`paid_amount` 已有列未展示）。→ 审批决策**信息严重不足**（P1）。

### 5.5 与合同列表页的审批口径不一致

| | 合同列表页行「审批」 | 本页「通过」 |
|---|---|---|
| 意见 | **不收集**（`note` 恒 `undefined`，`index.vue:1094`） | 可填（非必填） |
| 二次确认 | `Modal.confirm`（标题「确认审批」，内容「确定要审批合同 "X" 吗？」） | 独立 a-modal + `确定通过` |
| 失败提示 | `message.error('审批失败')`（**吞掉后端原因**，`index.vue:1095`） | `message.error(e?.message \|\| '审批失败')`（**保留后端原因**） |
| 请求 | `contractApi.approve` → 标准 `request` | `contractApprovalApi.approve` → `postRaw`（原生 axios） |

→ **同一动作两个入口、两套交互、两套错误处理**（P1）。且列表页 `catch` 后只给固定文案，用户看不到「只有待审批状态的合同可以审批」这类关键原因。

### 5.6 分页与请求参数

`page-param-style="pageNum"`（`:10`）→ `buildParams` 发 `pageNum`/`pageSize`（`ARReportPage.vue:247-249`），后端 `@RequestParam(defaultValue = "1") int pageNum` / `pageSize=**10**`（`ContractController.java:45-46`）→ **前后端分页参数一致** ✅。
`fetcher` = `contractApi.page(params)`（`:190-192`，标准 `request`，`api/crm.ts:176-178`）；响应为 MyBatis-Plus `Page<ContractVO>`（裸对象，含 `records`/`total`）→ `ARReportPage` 的 `defaultNormalize`（`ARReportPage.vue:281-289`）取 `data.records || data.list || data.content` + `data.total` → **归一化正确** ✅（`utils/request.ts:202-205` 亦对 `records + total` 直接透传）。
`row-key="id"`（`:12`）= 默认值（`ARReportPage.vue:192`）；因 `id` 是**雪花值且被 `JacksonConfig` 序列化为字符串**，`row-key` 按字符串比对是**安全**的（勿做 `Number()`，见《合同开发文档》§5.8）。

### 5.7 三个变更类端点的调用方式（与查询类不同）

`contractApprovalApi`（`api/crm.ts:516-533`）中 `submit`/`approve`/`reject` 走 `postRaw`（`:294-302`），即**原生 `axios` + 手工 `Authorization: Bearer <token>`**（`authHeaders()`，`:273-276`），**不经过 `request` 实例**，因此：
- ✅ 适配后端「裸实体、无 `code` 包装」的返回（`unwrapRaw` 判定：HTTP 200 即成功，带数值 `code ≠ 200` 才算业务错误，`:278-287`）；
- ⚠️ **不享受 `request` 实例的拦截器能力**（无 401 自动刷新 Token 重试、无 NProgress、无慢请求埋点）—— 这是 `api/crm.ts:262-269` 已注明的既定口径，但会带来「Token 恰好过期时审批动作直接失败」的用户体验差异（P2）；
- 请求地址是 `${CRM_BASE}/contract/{id}/submit`，而 `CRM_BASE = '/api/crm'`（`:271`）→ 因用的是**裸 axios（未设 baseURL）**，绝对路径 `/api/crm/...` 才能命中后端 **`/api/crm/contract`**；此处**不是**双前缀错误（该陷阱只针对 `request` 实例，见《_开发指南-金标准》陷阱 11）。

## 10. 验收标准（目标）

> 本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下不存在 `e2e-crm*.cjs`）。落地脚本命名 `tools/e2e-crm.cjs`（界面 + 接口 + 直连 DB 对账 + 写库后复原）。
> **前置提醒**：`crm_contract` 当前 **0 行** → 本页表格为空、4 卡恒 0、三个动作按钮无法触达。**造数前必须先修合同页的 P0（`contractType` 字符串 → 新建必 400）**，否则无法产生「待审批」数据。
> **2026-09-18 更新**：造数阻塞已解除（合同页 `contractType` 已改整数，见《合同开发文档》§9.0）；**权限断言口径已反转** —— §10.1-⑯（无权限账号调用三端点「当前预期 200」）与 §10.2-⑭（另一账号「仍然可见可点」）本轮已加鉴权，验收时改断言 **403 / 按钮隐藏**；其余条目（`reject` 不落库、无审批记录表、无 SoD、审批记录表不存在等）仍按原样断言。

### 10.1 接口验收（建议 ≥ 20 项）

**查询（①–④）**：① `GET /page`（本页参数 `pageNum`/`pageSize`/`keyword`/`status`）默认 200，`total` 与直查 DB（`deleted=0` + 租户）一致；② **`status` 用 Integer 逐值 0–10 过滤均生效**（本页传参方式正确）；③ **`keyword` 命中 `contract_no`/`contract_name`/`customer_name`** 三类（`ContractServiceImpl.java:70-74`）；④ `GET /export` 返回条数与 `page.total` 一致，**断言返回体无 `statusDesc`**（裸实体，本页统计卡不依赖它）。

**审批链路（⑤–⑫）**：⑤ `POST /{id}/submit`：0→1；**非 0（1/2/4/8）→ 400「只有草稿状态的合同可以提交审批」**；⑥ `POST /{id}/approve?note=X`：1→2 且 `approved_by` = 当前登录人 ID、`approved_time` 非空、`approved_note` = `X`；非 1 → 400「只有待审批状态的合同可以审批」；⑦ `POST /{id}/approve`（**不带 note**）→ 200 且 `approved_note` 为 `null`（断言空值语义）；⑧ `POST /{id}/reject?reason=Y`：1→**0**；不带 `reason` → 400（缺必填参数）；⑨ **断言 `reject` 后 DB 中 `approved_by`/`approved_time`/`approved_note` 均未被改写，且无任何字段记录 `Y`**（登记 P0 缺陷；修复后改断言有值）；⑩ **断言 `crm_contract` 无 `rejecter_id`/`reject_reason`/`rejected_time` 列**；⑪ **断言数据库不存在 `crm_contract_approval` 表**；⑫ 审批人取值断言：用账号 A 登录调 `approve` 后 `approved_by` = A 的用户 ID；**并断言「同一账号可对自己创建的合同审批通过」（当前无 SoD 校验，登记缺陷）**。

**统计与刷新（⑬–⑯）**：⑬ `/export` 全量聚合的 4 项指标与直查 DB 的 `GROUP BY status` 一致（`count(status=1)`、`count(status=0)`、`count(*)`、`Σ contract_amount WHERE status IN (5,6)`）；⑭ **断言 `/statistics` 端点当前是否可被 `request` 正常解析**（复核 §3.2-3 的注释前提，记录结论）；⑮ 每次审批动作后**断言发出 2 个请求**（`/page` + `/export`，登记 P1 性能缺陷）；⑯ **权限断言**：用无审批权限的账号调用 `approve`/`reject`/`submit`，**当前预期仍为 200**（登记 P0 缺陷；修复后改为 403）。

**写库隔离（⑰–⑳）**：⑰ 所有写断言后**按原值复原**（记录原 `status`/`approved_*` 后回写）或使用专用测试合同并清理；⑱ 造数须经由**后端接口**而非直插 DB（以覆盖 `createContract` 的强制字段）；⑲ 断言审批动作**不产生**任何子表行（条款/附件/付款/变更）；⑳ 断言 `GET /{id}` 的 `statusDesc` 在 0→1→2→0（驳回）各阶段均正确回显。

### 10.2 UI 验收（建议 ≥ 15 项）

① 菜单 `CRM → 合同管理 → 合同审批`（`70341`）点开直达本页（**单入口**，无标签跳转）；② 4 张统计卡渲染，数值与 §10.1-⑬ 的聚合一致（含 `¥` 与 `份` 后缀、待审批卡橙色 `#fa8c16`）；③ 表格 10 列渲染，**「状态」列显示中文 tag**（`statusDesc` 优先）；④ **「合同金额」列显示 `¥` 金额**，空值显示 `-`；⑤ 查询 2 项生效（`keyword` 三类命中 + `status` 11 值逐个筛选）；⑥ `重置` 清空条件并回到第 1 页；⑦ 造一条 `status=0` 数据 → 行显示**只有**「提交审批」；点击 → `Modal.confirm` 文案为 `确定将合同「X」提交审批吗？` → 成功提示 `已提交审批` → **行变为「通过 / 驳回」**；⑧ 造一条 `status=1` 数据 → 行显示「通过 / 驳回」；点「通过」→ 弹窗显示「合同名称（合同编号）」与 `¥ 金额`，**审批意见非必填** → `确定通过` → 提示 `审批已通过` → 状态变「已审批」；⑨ 点「驳回」→ **不填原因直接点 `确定驳回` → 提示 `请输入驳回原因` 且弹窗不关闭**；填原因后提交 → 提示 `已驳回` → **状态回到「草稿」**；⑩ **断言驳回后重新打开该合同，看不到任何驳回原因/驳回人**（登记 P0）；⑪ 造一条 `status=2`（或 5/8）数据 → 操作列显示灰色 `—`；⑫ `刷新` 按钮重新拉取；`导出` 生成 `合同审批_YYYYMMDD_HHmmss.csv` 且**仅含当前页**；⑬ 分页切换/每页条数切换重新请求且参数为 `pageNum`/`pageSize`；⑭ 用**另一个账号**（非审批权限）登录，确认「通过 / 驳回 / 提交审批」**仍然可见可点**（登记 P0 权限缺陷；修复后改为不可见或 403）；⑮ 页面控制台**无 error**（含 `TypeError`/`ReferenceError` —— 参见《重构搬迁后必须做运行时验证》）。

## 12. 剩余缺口（不阻塞，如实登记）

**P0**：① **驳回原因与人永不落库**（后端 `reject()` 不写、表无列），前端却强制必填 —— 语义闭环断裂；② **无审批记录载体**（无 `crm_contract_approval` 表），通过只留最后一次、驳回零痕迹；③ **零权限控制**（前端无指令 + 后端三端点无注解）→ 任何登录用户可审批任意合同；④ **无职责分离校验**（提交人可自审，`create_by` 与 `approved_by` 可为同一人）。

**P1**：⑤ 审批上下文严重不足（弹窗仅名称/编号/金额，条款/附件/付款计划/风险/已收金额均不可见，而相关列与端点均已具备）；⑥ 统计卡每次进页与每次动作都**全表拉 `/export`**（无分页无上限）；⑦ 统计口径与合同列表页不一致（`5||6` vs `>=5&&<8`）；⑧ 与列表页的审批交互**双轨**（有无意见/不同确认/不同错误文案/不同 axios 通道）；⑨ 未达金标准路线 A（`ARReportPage` 属路线 B，无 `CategoryListLayout`、无列配置、无页面配置）；⑩ 未使用任何与本页职责相关的闲置端点（`/effective`、`/complete`、`/cancel`、`/renew`、`/progress`、`/expiring`、`/statistics`）。

**P2**：⑪ 状态颜色与列表页 2 处不一致（`3`、`9`）；⑫ 源码注释前提与拦截器现状不符（裸 Map 本不会被误判，待运行期复核）；⑬ 审批意见 `undefined` 落 `null`，无法区分「未填/填空」，且无意见模板；⑭ `postRaw` 不经 `request` 实例（无 Token 自动刷新与埋点）；⑮ 无快捷键、无自动刷新、无「新单提醒」、无审批超时升级；⑯ 导出仅当前页；⑰ 无批量审批（端点与 UI 均无）；⑱ 无审批意见附件/佐证材料；⑲ 无验收截图资产 / 无模块级 E2E。
