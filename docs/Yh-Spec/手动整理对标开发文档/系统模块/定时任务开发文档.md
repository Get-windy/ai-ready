## 1. 页面概述
定时任务页是**平台运营方的调度控制台**：以一张表格列出全部定时任务（任务名称 / 任务处理器 / Cron 表达式 / 启用开关 / 运行状态 / 上次执行 / 成功失败计数），提供「新增 / 编辑 / 删除 / 启用停用 / 立即执行 / 查看执行日志」六个动作，并以抽屉展示每个任务的 `scheduled_task_log` 执行流水。**它是本系统唯一「真跑得起来」的调度界面** —— 后端是自研 Spring 调度引擎（`ThreadPoolTaskScheduler`），执行目标经 `JobHandler` 白名单 SPI 解析，执行流水真实落 `scheduled_task_log`（见 §9.1 正向样板）。

> **★ 结论（必须写进规格，否则会重复开发）**：业界（金蝶云·苍穹「调度中心」）把「同步任务」与「定时任务」做成**同一能力的两套界面**（**业务视角 vs 技术视角**），文档必须明确**二者共用同一后端对象**。
> **本系统的实况是：二者不共用。** 定时任务 = `scheduled_task` ＋ `JobHandler` SPI 白名单（`scheduler` 包）；同步任务 = `sys_sync_task` ＋ 与 `sync-engine` 零连线（`datasource` 包）。两个包之间**零交叉引用**（全仓 grep：`datasource` 包内无 `scheduler`/`ScheduledTask` 命中，`scheduler` 包内无 `sync` 命中）。
> **目标规格**：本页应作为**统一的「平台级调度视图」**，把同步任务也纳入同一「任务目录 ＋ 执行流水」模型（即业界的三层：**调度计划 / 调度作业 / 调度任务**）；**当前未做，属 P1 缺口**（§8、§12）。

## 2. 页面截图
**N/A —— 本模块无对标系统截图。**

**原因（本模块的通用前提，本页严格遵守）**：ql361（来肯企汇 v2.2，`22stable.ql361.com`）是**租户级进销存产品**，它对客户暴露的只有「设置」域（`client_type = tenant-admin`）。本页属于**平台控制台**（`client_type = system-admin`）——「平台方怎么管所有租户的定时作业」——**任何厂商都不会把自己的 SaaS 控制台给客户看**。因此：

- ql361 中**不存在**「定时任务」这个页面（`client_type='system-admin'` 的行不会出现在租户登录的菜单树中），**无可对标截图**；
- **不使用 Odoo / SAP / 金蝶 / 用友的界面截图**（口径见《系统模块/README.md》§5.3：本模块按业界**能力模型**建模，**不照搬任何一家的界面**）；
- §8 只写**业界能力对标**，逐条标来源与可信度级别。

**本系统截图**：当前无本系统验收截图（`tools/` 与 `tools/acceptance/` 下不存在 `e2e-system-*.cjs` / `e2e-admin-*.cjs`）→ **P2 缺口**（README §7.3）。

**数据现状（devdb 实测 2026-09-18）**：

```
scheduled_task      : 23 列 / 16 行     scheduled_task_log : 14 列 / 15 行
  其中 enabled=1 的行 = 0 行（全部停用）  其中 execute_status 去重值 = SUCCESS（15 行）
  其中 job_key 非空的行 = 4 行            create_time 全部落在 2026-09-14
```

- **本页是本模块唯一的正向样板**：`scheduled_task_log` 里有 **2026-09-14 的真实执行记录 15 条**，含「演练（未落库）」的业务摘要与「跳过：另一实例正在执行（锁 `dms:job:lock:dms.dispatch.escalateOverdue` 被占用）」——**证明多实例 Redis 互斥锁真的生效过**（样例行见 §7.2）；
- 但 **`enabled=1` 的行数为 0** → 当前**没有任何任务在跑**；要让它「动起来」必须先启用某个任务（**属写操作，本次未执行**，见 §10.1 的谨慎断言口径）。表格另有 12 行「历史演示数据」：行 `1-12` 的 `job_key` 为空、`status='STOPPED'`、`success_count/fail_count` 为种子演示值（如 `9980/20`），已由迁移统一停用并追加描述（§7.1）。

### 5.2 流转规则
```
（无）── 新增 POST /api/scheduler/task ──▶ enabled=0（默认停用）＋ status 由后端落库
enabled=0 ── 开关打开 POST /{id}/enable ──▶ enabled=1 → TaskExecutor.scheduleTask() → status=RUNNING
enabled=1 ── 开关关闭 POST /{id}/disable ─▶ enabled=0 → cancelTask() → status=STOPPED
enabled=1 ── 调度注册失败（Cron 非法等）──▶ status=ERROR（TaskExecutor.java:100-104）
enabled=1 ── 到点触发 ──▶ 写 scheduled_task_log(RUNNING) ──▶ SUCCESS / FAILURE
（后端另有 pause / resume / log retry / batch-execute，本页未接，见 §6.3）
```

| 动作 | 后端 | 前置校验 | 失败文案 | 副作用 |
|------|------|:--------:|---------|--------|
| 新增 | `POST /api/scheduler/task`（`:58-63`） | **`job_key` 必须在白名单内**：`validateJobKey`（`ScheduledTaskServiceImpl.java:97-107`）→ 非法则 `BusinessException(400, "未注册的任务处理器: …（可选：…）")` | 后端 400 文案 | 落 `scheduled_task` 一行 |

### 8.2 业界的口径 —— 首先必须写清「与《同步任务》的关系」
底稿 §5.4 原文：「**本页与 4.4『同步任务』是同一能力的两套界面（业务视角 vs 技术视角），文档里必须明确二者共用同一后端对象，否则会重复开发。**」

- **业界口径**：金蝶云·苍穹把「调度计划 / 调度作业 / 调度任务」做成**一套对象**，业务侧看「同步了什么」，技术侧看「怎么排、跑没跑」——**同一后端对象、两套视图**。
- **本系统实况（实测）**：**二者不共用**。定时任务 = `scheduled_task` ＋ `JobHandler` SPI（`cn.aiedge.scheduler` 包）；同步任务 = `sys_sync_task` ＋ `cn.aiedge.datasource` 包（且该包**未装配，端点全 404**）。两包**零交叉引用**（§1.1）。
- **落地建议**：本页应作为**统一的平台级调度视图**，把同步任务纳入同一「任务目录 ＋ 执行流水」模型（即业界三层）；**当前未做（P1）**。

### 8.3 业界做法要点（补充 §4.4 未覆盖的「并发策略 / misfire / 失败重试与补偿」）
1. **并发策略的业界三种**：①禁止并发（前一次未结束则跳过本次）；②允许并发（可能重复处理）；③抢占式（`SKIP LOCKED`，Odoo 做法，多 worker 不重复）。**Odoo 的 `FOR NO KEY UPDATE SKIP LOCKED` 是可直接抄的并发模型。**
2. **misfire 的官方定义与默认策略**：Quartz 原文「**A misfire occurs if a persistent trigger "misses" its firing time**」，默认使用 **smart policy**；调度器启动后**会查找已 misfire 的持久化触发器并按各自配置的指令更新**。**⚠️ 具体指令常量未在该教程页展开（该页明确指向 JavaDoc），因此「各 misfire 指令的精确语义」底稿未取得 A 级依据（§9.1 第 12 条）→ 本页不引用任何未取证的常量名，此点显式标注「未取证」。**
3. **失败重试与补偿**：Odoo 的做法是**不重试、但重排** —— `PARTIALLY_DONE` → `_reschedule_asap`（立刻可再跑），`FAILED` → `_reschedule_later`（按间隔等下一次），并用 `failure_count` ＋ `first_failure_date` 累计，达阈值自动停用并通知。**这是「避免无限重试打爆系统」的收敛设计。**
4. **超时要能被判定**：`CONSECUTIVE_TIMEOUT_FOR_FAILURE = 3` —— 连续 3 次超时判失败。
5. **单次执行要有界**：`MAX_BATCH_PER_CRON_JOB = 10` 循环上限 ＋ 进度上报（`done`/`remaining`）——**长任务必须能「跑一半让出」，否则会拖垮调度线程。**
6. **执行用户要显式指定**：Odoo `user_id`（`required=True`），并有专门的 `_allow_sudo_commands = False` 保护；金蝶也有「调度预置时执行作业的用户选不到管理员」FAQ —— **「定时任务以什么身份执行、有什么权限」是必须显式建模的字段。**
7. **优先级**：Odoo `priority` 默认 5，「0 为较高优先级，10 为较低优先级」，就绪排序 `failure_count, priority, id`（**先跑失败多的，再跑优先级高的**）。
8. **SAP 侧补充**：后台作业有**作业链（job chain）**与事件触发（SM62 建事件 → `BP_EVENT_RAISE` → SM36 启动条件选 "After event"）。
9. **Odoo 的字段级细节（与 `ir_cron.py` 源码对齐）**：`interval_number`（Integer，默认 1，**SQL 约束 `CHECK(interval_number > 0)`**）＋ `interval_type`（Selection：`('minutes','Minutes')` / `('hours','Hours')` / `('days','Days')` / `('weeks','Weeks')` / `('months','Months')`，默认 `'months'`）；`MAX_FAIL_TIME = timedelta(hours=5)`；`MIN_FAILURE_COUNT_BEFORE_DEACTIVATION = 5` **且** `MIN_DELTA_BEFORE_DEACTIVATION = timedelta(days=7)`（**失败 ≥5 次且首次失败已超 7 天 → 自动置 `active=False` 并通知管理员**）。

## 12. 剩余缺口（P0 / P1 / P2）
> 口径与《系统模块/README.md》§7 对齐：**P0** = 页面不可用 / 数据不落库 / 越权 / 红线；**P1** = 与业界能力差距大但页面能开；**P2** = 体验与一致性。
> **★ 本页的特殊性**：README §7.1-P0-10 的两半中，**「15 端点无权限注解」经运行态复核不成立**（§9.3），**「前端硬编码筛选分页」成立且是本页唯一 P0**。

### P0（**1 条**）
① **前端硬编码筛选与分页，绕过后端已支持的筛选能力（README §7.1-P0-10 的成立部分）**：列表请求写死 `{ current: 1, size: 100 }`（`scheduler/index.vue:401`）→ 恒为「第一页 100 条」；页面**没有任何查询条件**（无搜索框/状态下拉/日期范围/`#filter`）；表格 `:pagination="false"`（`:74`）→ 无页码、无总数、无每页条数，**`total > 100` 的任务永久不可见**。**证据**：`index.vue:401`、`:74`、`:45-119`；**后端其实支持** `page(current,size,taskName,status)`（`ScheduledTaskController.java:87-97`，`:91-94` 为 4 个 `@RequestParam`）。**建议处置**：① 补查询区（`taskName` ＋ `status`，选项取 §5.1 四态）；② 换 `StandardPagination variant="classic"` 并接后端 `total`/`current`/`size`（**后端无需改动**）；③ 后端补 `pageSize` 上限（`:92`）。**可执行证据**：§10.1-⑦⑧⑨⑪、§10.2-⑥。

### P1（**14 条**）
② **后端权限注解实际齐全，但前端零权限控制**（§9.3，**口径差异**）：后端 15 端点全部有 `@SaCheckPermission`、码已落库 5 条并授权超管；**缺的是前端 `v-permission`**（按钮人人可见，点了才知道 403）→ 补前端指令。
③ **「15 个端点全部无权限注解」的 README 口径与实测不符**（§9.3-1）→ **README 由上级维护，本篇只登记差异**；建议订正为「后端注解已齐全，P0 实为前端硬编码筛选分页」。
④ **`timeout` 列存在但完全不生效**（`ScheduledTask.java:72`；`TaskExecutor` 无读取点）→ 任务可无限期运行，无法判定超时（对标 `CONSECUTIVE_TIMEOUT_FOR_FAILURE = 3`）。
⑤ **失败无收敛（自动停用 / 告警缺失）**：失败只累加 `fail_count`（`TaskExecutor.java:184`），**永不自动停用、永不通知**（对标 Odoo 的 5 次 / 7 天自动停用）。
⑥ **重试是同步阻塞且可能 NPE**：`Thread.sleep(retryInterval * 1000L)`（`TaskExecutor.java:159`）发生在**持有调度线程**期间 → 拖住线程池（`poolSize=10`）；`retryInterval` 为 `null` 时直接拆箱 → **NPE 风险**（`:159`）。
⑦ **引擎层无并发策略**：互斥完全依赖各 `JobHandler` 内部的 Redis 锁（`DmsDispatchEscalateJob.java:49` 等）→ **新处理器漏加锁即多实例重复执行**，引擎不做兜底。
⑧ **无 misfire 处理**：`ThreadPoolTaskScheduler` 为内存态、trigger 不持久化（`SchedulerConfig.java:15-24`）→ **停机期间的触发直接丢失**。**⚠️ misfire 各指令的精确语义未取证（底稿 §9.1 第 12 条），本页不引用任何未取证的常量名。**
⑨ **6 个后端端点闲置**（`GET /{id}`、`pause`、`resume`、`log/{logId}/retry`、`/{id}/statistics`、`batch-execute`，§6.3）→ 补 UI，且 `pause`/`resume` 与启停开关**语义需区分**（暂停 = 保留状态等恢复；停用 = 不参与调度）。
⑩ **三处 `catch` 静默**（`index.vue:404-406`、`:382-383`、`:393-395`）→ 接口失败只表现为空表，**无任何提示**。
⑪ **页头计数会失真**：`enabledCount`/`disabledCount`（`:243-244`）基于内存 `list`（上限硬编码 100）→ 任务数 > 100 时计数错误。
