# 物流发货 / 发货 · 业界成熟做法调研

> **起因**：2026-09-13 复核《物流发货》时提出两个质疑——
> ① 「物流发货」点开就是「订单处理中心 → 2.拣货/发货」（销售订单列表），像复制了一个销售订单列表页；
> ② 「发货」一键完成，物流单号只在「物流备注」弹窗里手输。
> 本文调研 SAP / Oracle NetSuite / Odoo / 金蝶云星空 / 用友 U8 / 旺店通·聚水潭 及 WMS·TMS 边界设计，回答「业界怎么处理这件事」。
> 调研日期：2026-09-14。**本文只做结论与建议，不改代码。**

---

## 0. 结论摘要

1. **「发货」与「物流发货」在成熟系统里是两层，不是两个按钮**：
   `销售订单 → 发货单/发货通知 → 出库过账(动库存) → 运单/包裹(带承运商+运单号) →（可选）ASN 提前发货通知`。
   「物流信息」不属于发货动作，属于**运单/包裹这一层**。
2. **运单号挂在「包裹」上，不挂在订单表头**：一个发货单支持 **N 个包裹 = N 个运单号**（SAP handling unit、NetSuite `package`、Odoo multipack 都是这个模型）。
3. **承运商（物流公司）是档案实体**，不是自由文本：金蝶「物流公司是基础资料」、用友 U8「承运商档案 + 运费计费规则」、TMS 里承运商池/合同价。
4. **运费要能对账**：U8 有「运费维护 → 生成费用单 → 分摊到销货单」，TMS 侧是「运单 → 计费 → FreightBill → 与承运商对账」。运费是钱，必须有单据。
5. **电商 ERP 的运单号来自「电子面单接口」，不是手输**：聚水潭/旺店通流程 = 审单 → 获取电子面单(取号) → 打单拣货 → 验货 → 发货回传平台。手输只是**兜底**。
6. **系统边界**：库存/出库单归 WMS，运单/在途/签收归 TMS，运费归 TMS+BMS/ERP，订单与凭证归 ERP；跨系统靠**单据号关联**，不复制单据。

> 对照结论：ql361 把「承运商 / 运单号」退化成了**订单表头上的两个文本字段 + 一个批量维护弹窗**，
> 既没有运单/包裹实体，也没有承运商档案与运费对账 —— 相比成熟模型**确实是简化**。
> 但其定位是中小商贸进销存（以自有配送为主、少量第三方物流、不做多包裹/面单/运费对账），**属"够用即止"，不算错**。
> 本系统按对标复刻原则照做无过；**可按下面的分档建议按需增强**。
>
> 🔎 **但本系统比 ql361 走得远**：我们**已经建好了**业界模型的物流子表 `erp_sale_order_logistics`（1:N）——
> 后端 entity/mapper/DTO/写入/清理全都有，**只差前端接线**（表里 0 行）。
> 所以下面的 P0 本质是**"接线"而不是"造轮子"**。详见 §6。

## 1. 业界主流单据分层

| 层 | 单据 | 干什么 | 权威系统 | 动库存 |
|---|------|--------|---------|:-----:|
| 1 | 销售订单 | 承诺 | ERP/OMS | — |
| 2 | **发货单 / 发货通知单**（Delivery / DO / 发货通知单） | 确定发什么、发多少、发到哪 | ERP | — |
| 3 | **出库单**（Goods Issue / 销售出库单） | 过账出库 | WMS/ERP | ✅ |
| 4 | **运单 / 包裹**（Shipment / Package / Handling Unit） | 谁运、单号、件数重量 | TMS/承运商 | — |
| 5 | **ASN**（提前发货通知，EDI DESADV / X12 856） | 告知客户/仓库"货在路上" | ERP/TMS | — |

- SAP SD：`Delivery(VL01N) → Picking → Packing(HU) → Post Goods Issue(601, VL02N) → Carrier + freight bill(VL03N 承运商/运单号) → 输出 Delivery Note / Packing List / ASN`。**运单号是承运商伙伴 + freight bill 号**，录在 Delivery 抬头/运输层，不在销售订单上。
- Infor LN：`Release Outbound Advice → Freeze/Confirm Shipment/Load → Confirm Outbound ASN`，ASN 确认后即成为收货方单据，差异回 RDN（收货差异通知）。
- D365：Load/Shipment 状态为 **Shipped** 后才允许 **Send ASN**（`WHSShipConfirmClass.sendASN()`），且仅对「Generate ASN = Yes」的客户生成。

**要点**：成熟系统的「发货」不是终点，「**发出去 + 谁承运 + 单号是多少 + 运费多少**」才闭环。

## 2. 运单号归属：包裹层（一单多包）

- **Odoo**：Delivery Order 可拆成多个 Pack（`Put in Pack`），Validate 后**自动带出 carrier Tracking ref**，标签与面单在 Delivery 历史里；Portal 可查多个 tracking number。
- **NetSuite**：Item Fulfillment 的 **Packages** 子页签存 `packageTrackingNumber` + 重量；承运商专用包（FedEx/UPS/USPS）是另一种 package 类型；一个 fulfillment 支持多包裹（同步到 Shopify/Amazon 时多单号/单号限制各不同）。
- **SAP**：Handling Unit（HU）— 托盘/箱层级 + SSCC 标签，一个 Delivery 多 HU。

**要点**：**"一个运单号"是中小场景的简化**。一旦出现拆包、多箱、部分发货，就必须有包裹层，否则对账与追踪都对不上。

## 3. 承运商：档案 + 计费规则 + 对账

- **金蝶云星空**：物流公司是**基础资料**（分配型，可按库存组织/地区/配送区域/物料范围配置），拣配环节自动匹配最优物流公司 → 获取电子面单 → 打印物流单；发货后上传物流公司/物流单号；与金蝶物流模块集成可回传物流轨迹；销售出库单有 `FCarriageNO`（运输单号）字段。
- **用友 U8**：承运商=**供应商档案**（运输管理插件）；「物流管理 → 单据处理」选销货单 → **输入运单号 + 物流结算方式 → 确认发货 → 生成发货单**；「运费维护」按运单号录运费 → 生成费用单 → **分摊到销货单**；结算方式（现结-寄付/垫付、月结-寄付）决定是否自动分摊。
- **TMS**：运单确认发运后按**合同价**自动算运费 → 推 ERP 生成应付；签收后触发应收；对账时运单与物流结算单**逐条比对、差异标红**；有 TMS 走「运单→采购订单→与承运商结算」，无 TMS 走「销售订单计提运费→线下核对→冲减计提」。

## 4. 电商 ERP 的打单发货（运单号来自接口）

聚水潭标准四步（**不可跳过**）：

1. **审单**：校验付款/库存/地址，异常转异常单；
2. **配货 / 打单拣货**：勾选已审未配货 → **获取电子面单**（调快递接口取号）→ 打印面单 → 拣货扫码绑定；
3. **验货**：核对实物与 SKU/规格/数量，未通过不得发货；
4. **发货确认**：确认快递公司+单号 → **回传平台**（订单变"已发货"，不可逆）+ 打印交接单。

旺店通同类，另强调**波次拣货**（如 30 单一个波次，面单与拣货单一起出）、多仓、拆合单、权限分工。
**手工填写单号只是电子面单未开通时的兜底**（且必须准确，否则上传报错）。

## 5. 系统边界（WMS / TMS / ERP）

| 数据域 · 单据 | 权威系统 | 交接点 |
|---|---|---|
| 库存、仓内作业、**出库单** | WMS | 出库完成 / 装车确认 |
| **运单**、承运商、在途、签收 | TMS | 承运商揽收 / 签收 |
| **运费与结算** | TMS + BMS/ERP | 签收回传 / 对账 |
| 订单、应收应付、凭证 | ERP/OMS | — |

边界三原则：**数据域单点维护、单据按归属流转、交接点明确定义**；跨系统只传**关联键**（如 ERP 订单号为主键，携带下游运单号/出库单号），不两边各维护一份。
边界不清的典型症状：重复维护、状态割裂（WMS 已出库而 TMS 无运单）、出库件数/运单件数/账单件数三者对不上（对账只能人翻）。

## 6. 本系统现状与差距

> ⚠️ **2026-09-14 核查中的两个关键发现（改变了结论）**：
> 1. **系统里已经建好了业界模型的物流子表** —— `erp_sale_order_logistics`（`order_id` 1:N），
>    字段：`logistics_type / delivery_method / delivery_route(_id) / driver_id·driver_name / delivery_vehicle /
>    logistics_company / logistics_no / waybill_no / freight_payer / shipping_fee / cod_amount`。
>    后端 entity + mapper + `SaleOrderDTO.LogisticsInfo` + `saveSubTables` 写入 + `deleteSubTables` 清理**全都写了**，
>    订单处理中心的「按线路汇总」也在读它（`orderCenterGroupByRoute`）——**但前端没有任何页面写它，表里 0 行**。
>    → 这是**半成品/断头链路**：模型是对的，差最后一根接线。
> 2. **承运商双口径**：物流公司档案存在（`erp_partner_logistics_ext`，挂在往来单位上，即《资料 → 物流公司》页），
>    而拣货/发货页与物流备注弹窗用的是**主表自由文本** `erp_sale_order.logistics_company`。

| 能力 | 业界成熟做法 | 本系统现状 |
|------|-------------|-----------|
| 发货动作 | 一键发货（生成出库单） | ✅ 一致（`POST /erp/sale/order/{id}/ship` → `XSCKD-`） |
| 发货单/发货通知 | 独立单据 | ⚠️ 无独立发货单（拣货/发货阶段视图 + 出库单） |
| **运单/物流信息载体** | **子表（一单多条：承运商+运单号+运费）** | ⚠️ **子表 `erp_sale_order_logistics` 已存在但前端未接线（0 行）**；页面实际读写主表扁平列 |
| 运单号 | 包裹层，一单多号 | ⚠️ 主表单字段 `waybill_no`（单号） |
| 承运商 | 档案 + 计费规则 | ⚠️ 主表自由文本 `logistics_company`（档案另有一套，未引用） |
| 运费 | 运单计费 + 对账 | ⚠️ 子表已预留 `shipping_fee / freight_payer / cod_amount`，但无计费规则、无对账 |
| 电子面单 | 承运商接口自动取号 | ❌ 无（手输运单号） |
| ASN / 发货通知 | 出库后外发 | ⚠️ 有 `dms_event_outbox` 事件出口，未发发货通知 |
| 轨迹回传 | 承运商轨迹写回 | ⚠️ DMS 有《实时跟踪》但未与第三方承运商对接 |

**两个扎眼的问题**（都是"同一份数据两个口径"，正是业界警告的"重复维护"）：① 物流信息有子表也有主表扁平列；② 物流公司有档案也有自由文本。

## 7. 建议（分档，按投入排序）

> **实施状态（2026-09-14）：P0 / P1 / P2 已全部落地**，见《物流发货开发文档》**§6**。
> 迁移 `V11.340.0`（子表补 承运商档案ID/包裹层/运费对账列 + 新建 `erp_freight_rule`、`erp_shipment_notify`）、
> `V11.341.0`（新增菜单 `70162 物流运费对账`）；E2E `tools/e2e-sale-logistics.cjs`。
> 下面保留原始建议文本作为设计依据。

### P0 · 低成本、把已有能力接上（建议做）

1. **物流备注改读/写子表 `erp_sale_order_logistics`**（而不是主表扁平列），并**回写主表 `logistics_company`/`waybill_no` 作为列表展示快照**。
   - 收益：接上已有半成品，一次写入两处口径一致（列表仍能显示）；后续运费对账直接有载体。
   - 成本：改 `batchUpdateLogistics` 落点 + 列表展示取数（或写时同步），**无需新表**。
2. **「物流公司」改档案引用**：弹窗的物流公司改为选择《资料 → 物流公司》档案（下拉可搜），落库 `logistics_company` 存名称快照（子表可加 `logistics_company_id`），保留手输兜底兼容历史值。
   - 与金蝶「物流公司是基础资料」一致；为运费计费提供承运商主键。

### P1 · 能力补齐（按业务需要）

3. **一单多包 / 部分发货**：把子表按「包裹」语义使用（一条 = 一个包裹/运单），支持拆包与部分发货；发货时按包裹录入并打印面单。
   - 子表结构已具备（承运商 + 运单号 + 运费 + 代收货款），无需改表即可先支持"一个订单 N 条物流记录"。

### P2 · 生产级（有第三方物流规模再做）

4. **承运商运费规则 + 运费对账**：按 承运商 × 线路 × 重量/件数 计费（对齐 U8「运费维护/分摊」与 TMS「FreightBill 对账」），用子表的 `shipping_fee/freight_payer` 落账并生成应付。
5. **电子面单接口取号**：接主流快递开放平台（顺丰/中通/菜鸟等），自动取号 + 打面单；手输退化为兜底。
6. **ASN / 发货通知外发**：出库后经 `dms_event_outbox` 外发发货通知（复用《配送模块》事件底座）。

> **不做也不错**：ql361 的简化模型覆盖"自有配送 + 少量三方物流"的中小场景是够用的。
> 但只要出现**多承运商 / 多包裹 / 运费要跟承运商对账**中任意一条，P1/P2 就必须上。
> 而本系统 **P0 几乎是"接线"而非"造轮子"** —— 子表和 DTO 都已就位。
