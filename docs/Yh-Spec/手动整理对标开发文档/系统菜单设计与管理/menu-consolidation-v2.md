> **版本：** V2.0

## 一、变更背景

V1.0 完成 Mega Menu 改造后，一级菜单从 13 个扩展到 17 个（V9.5.0 新增 HR/交易/质量/支付）。  
经评审，17 个一级菜单过于分散，存在以下结构性问题：

| 问题 | 说明 |
|------|------|
| **配发收 × 配送重叠** | 两者同属物流链路，配发收是执行层，配送是调度层，割裂了完整闭环 |
| **商城独立一级菜单过重** | 商城本质是销售渠道之一，与交易天然一体，不应单独成模块 |
| **质量模块过于单薄** | 质检/标准/缺陷是仓储作业的约束层，3 列独占一级菜单不合理 |
| **支付独立一级菜单混淆了主数据与流水** | 支付配置是主数据（资料），支付流水是交易记录（交易） |
| **职员权限放在资料模块语义错位** | 职员属于"人"，归属人力资源更合理 |

**目标：** 17 个一级菜单 → **13 个**，保持足够信息密度的同时消除结构冗余。

---

## 二、第一性原理分析

### 2.1 配发收 vs 配送：合并为「配送」

从物流链路的本质追问：

```
调度 → 发车 → 在途 → 送达收货
(配送)  (配发收·发货)  (配送·跟踪) (配发收·收货)
```

- **配发收** = 配货发出 + 收货确认（物流执行层）
- **配送** = 路线/车辆/骑手/调度/跟踪（物流调度层）

两者是同一配送流程的切面，拆成两个一级菜单是人为割裂了"调度-执行-签收"完整闭环。

**结论：合并，配发收的 3 个列组整体并入配送。**

### 2.2 商城：保留在「交易」内

商城是一个销售渠道，POS 是另一个销售渠道，交易的本质是"订单从哪来、怎么处理"。  
商城订单与 POS 订单在业务流上同构：下单 → 支付 → 履约 → 售后。

**结论：商城保留在交易内，不单独拆分。**

### 2.3 质量：3 列合并为 1 列归入「仓储」

质检发生在仓储作业的各环节：
- 采购入库时 → 收货质检
- 在库期间 → 库存质量巡检
- 出库前 → 发货质检

质量管理不是独立业务流，而是仓储作业的质量保障层。但仓储已有 10 列，3 个独立列组过于膨胀，合并为 1 列「质量管理」。

**结论：质量 3 列合并为 1 列放入仓储。**

### 2.4 支付：拆分为主数据 + 流水两部分

- 支付方式/渠道/账户 → **主数据/配置**，与仓库、费用类型、银行账户性质相同 → 归「资料」
- 支付请求/记录/退款/对账 → **交易流水**，是交易的支付环节 → 归「交易」

**结论：支付流水部分归交易（新建支付结算列），支付配置部分归资料（新建支付管理列）。**

### 2.5 职员权限：独立列归入「人力资源」

职员权限（职员部门、岗位权限、全部操作员）管理的是"谁能操作什么"。  
组织管理（职位管理）管理的是"组织架构长什么样"。

| 维度 | 组织管理 | 职员管理 |
|------|----------|----------|
| 关注点 | 骨架——部门、职位、编制 | 血肉——具体的人+权限 |
| 语义 | 公司结构 | 人员权限配置 |

两者相关但概念独立，合并会导致"组织+人员+权限"概念模糊。

**结论：在人力资源下新建「职员管理」列组（61405），不混入组织管理。**

## 十、注意事项

1. **client_type 一致性**：新插入的列组/叶子统一使用 `client_type = 'tenant-admin'`，与现有租户级菜单保持一致。

2. **sys_tenant_menu 授权同步**：硬删除一级菜单时，必须同步删除 `sys_tenant_menu` 中引用这些 ID 的授权记录，防止孤儿数据；新建列组需要为已授权原模块的租户自动授权。

3. **前端路由兼容**：叶子菜单的 `path` 和 `component` 不变，仅 `parent_id` 变更，路由注册不受影响。

## 开发原则（通用）

- **页面组件优先复用**：页面开发优先使用已有的页面组件，除非当前页面组件不满足业务需求；确无对应组件，则优先开发合适的通用组件。
- **功能/模块不重复开发**：已开发过的业务功能、单据、通用能力在全系统范围内只实现一次；其它模块直接复用，不重复开发。
- **Service 接口签名变更需同步测试**：修改 Service 接口签名（方法名/参数/返回值）时，必须同步更新对应测试类，否则会阻塞整模块的 `test-compile`。
- **阶段结束前回写开发文档**：当前阶段工作完成后、结束前，必须更新开发文档的「已完成」与「待完善」章节，使其反映当前代码的实际实现情况。
