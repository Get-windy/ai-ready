# 人力资源模块 · 业界成熟做法调研

> **起因**：本系统「人力资源模块」共 10 个页面（员工列表 / 考勤记录 / 请假管理 / 薪资管理 / 绩效考核 / 职位管理 / 职员部门 / 岗位权限 / 全部操作员 / 招聘管理），
> 但对标系统**来肯企汇 ql361 没有人力资源模块**，无法"照抄"。
> 因此必须按**业界成熟生产级 HR 系统**（Odoo 18、SAP SuccessFactors / S/4HANA HCM、金蝶 s-HR / 星瀚 HR、用友 YonSuite 人力云，并引 Workday / BambooHR）的**标准能力**建模。
>
> **本文只回答"业界怎么做 + 出处"，不写任何针对本系统的实现建议。**
> 调研日期：**2026-09-18**。
>
> **证据分级**（全文每一条结论均标注）：
> - **A** = 厂商官方产品文档 / 官方源码（含官方文档源文件、官方 OpenAPI/SDK 文档）
> - **B** = 厂商官方社区 / 官网解决方案文章 / 授权服务商
> - **C** = 第三方教程 / 博客
> - **D** = 推论或未证实（本文尽量不用，凡出现必显式标注）
>
> **取数方式说明**：`help.sap.com`、`doc.workday.com`、`club.kdcloud.com`、`success.yonyou.com` 等站点为前端 SPA，
> 纯 HTTP 抓取只能得到导航壳；本文对应条目均以**真实渲染后的页面正文**取证（页面标题已逐条核对）。
> Odoo 部分除官方文档外，另取 **Odoo 官方源码**（`odoo/odoo` 18.0 分支模型定义）作为字段级证据。

## 0. 结论摘要（10 条）

1. **员工主档的"三层模型"是分水岭**：SAP / Workday 把「**职务 Job（职类）→ 职位 Position（编制单元）→ 员工 Employee（在编人）**」拆成三个对象；Odoo 则只有「岗位 `hr.job` + 员工 `hr.employee`」两层，**没有 Position 这一层**（出处：SAP、Workday，A）。
2. **编制（Headcount）在成熟系统里是"职位上的 FTE 容量 + 校验规则"**，不是员工表上的一个数字：SAP 用 `targetFTE` + `positionControlled` 做**超编拦截**；用友/金蝶用「组织编制 / 维度编制 / 控编方式(允许/不允许超编)」做**事前＋事中管控**（出处：SAP、用友、金蝶，A/B）。
3. **人事异动（入职/转正/调岗/调薪/晋升/离职/退休）是被建模成一等公民的**：SAP 叫 **Personnel Action（人事措施）**，一个动作=一组预定义 infotype 的连续维护，并写入 `Actions infotype (0000)`；用友叫「变动类型 + 变动原因 + 生效日期 + 申请单 → 审批 → 回写任职记录」；金蝶叫「人事快速异动」并区分入职/转正/调动三类业务开关（出处：SAP A、用友 B、金蝶 A）。
4. **"生效日期 + 历史版本"是 HR 数据的通用底座**：SAP EC 的 MDF 对象带 `effectiveStartDate` / `effectiveEndDate` / `mdfSystemVersionId`；用友调动单必须选**生效日期**；金蝶对人员档案提供**修订（Revise）**与历史版本查询（出处：SAP A、用友 B、金蝶 A）。
5. **考勤是"打卡明细 + 异常清单"两件事**：Odoo 的考勤错误定义为**签到后 24 小时内未签退**或**单次签到超过 16 小时**，异常条目在列表/甘特视图标红，必须由有权限者**修改或删除**后才能真正进入薪资（出处：Odoo A）。
6. **加班在 Odoo 里带审批状态**：`overtime_hours`（Worked Extra Hours）→ `overtime_status`（To Approve / …）→ `validated_overtime_hours`（Validated Extra Hours），即「加班申报 → 审批 → 计入」（出处：Odoo A，源码）。
7. **假期额度是"三件套"：额度分配(Allocation) + 累积计划(Accrual) + 审批方式(Validation)**。Odoo 的累积计划明确区分「结转时点（年初 / 分配日）」「是否按工时累积」「结转规则（不结转=归零 / 结转上限 / 上限封顶）」；SAP 的 2006 明确区分「**有效期**」与「**扣减期**」两个不同区间，并支持**负额度**（出处：Odoo A、SAP A）。
8. **薪资的通行架构是"结构类型 → 结构 → 规则 → 参数 → 输入项"**，规则带**类别（基本/津贴/扣款/社保/个税）、序号、条件、计算方式（固定额 / 百分比 / 他项输入 / Python 表达式）**，并把**借贷科目**直接挂在规则上；**各国差异由本地化包承载**，而不是在规则里写死（出处：Odoo A）。
9. **SAP 的薪资发放有一个"控制记录"闸门**：`Payroll Control Record` 持有 `Payroll area / Payroll status / Payroll Period / Retroactive Accounting Limit / Last change`，状态按 `Release Payroll → Check Payroll Results → Release for Correction → Exit Payroll` 流转；发布时**期间号 +1 并锁住影响过去/现在的主数据**（未来数据仍可改），出错人员进 **Matchcode W** 只做**更正运行**且**期间不变**（出处：SAP A）。
10. **薪资保密与数据脱敏是显式配置项**：Odoo 用**字段级 `groups=`** 把私密字段（`private_*`、证件号、银行账户）限制给 `hr.group_hr_user`；金蝶提供 `desensitize_enable`（脱敏开关）配置（出处：Odoo A 源码、金蝶 A）。

> **要点**：Odoo 的 `expected_employees = 在岗 + 计划招聘`，是**"目标编制"的轻量替身**——
> 它只能"算出来"，**不能"拦下来"**（没有超编校验）。真正能拦的是 SAP 的 `positionControlled` 与用友/金蝶的控编规则（见 §2.2、§3、§4）。

| 能力 | 业界做法（SAP） | 关键对象 / 字段 |
|---|---|---|

| **② Run Payroll（运行）** | 调用**国家特定**的薪资程序；从控制记录取当前期间；通常作为**后台作业**执行 | 同上 |

### 2.6 权限：Role-Based Permissions（RBP）

| 能力 | 业界做法（SAP） | 关键对象 |
|---|---|---|
| **三要素** | **Permission Groups（权限组）+ Permission Roles（权限角色）+ Target Populations（目标人群）** | 官方原文：*Role-based permissions contain three main elements: permission groups, permission roles, and target populations.* |
| 权限组 | "共享某些属性（如 City 或 Job Code）且需要访问一组相似任务"的员工集合；可分为**动态组**（按条件自动更新）与**静态组**（导入固定名单） | Permission Groups（dynamic / static） |
| 权限角色 | "一组权限"的集合，授予某个权限组；若该角色要求的权限是**代表他人执行操作**，则必须同时指定**目标人群** | Permission Roles |
| 目标人群 | 当授予的权限需要"代表其他员工执行"时，为权限组指定其作用对象人群 | Target Populations |
| 顺序建议 | 官方建议**先建组、再建角色**，因为建角色时要选授予给哪个组，且需要目标人群的角色也依赖已定义的组 | 官方文档 § Tip |
| 适用范围 | RBP 应用于 SAP SuccessFactors HCM 套件的绝大多数产品；官方称**支持最多 1,500,000 名员工**的组织 | 官方文档 § note |

> **与"岗位→权限"的关键差别**：RBP **不是**把权限挂在一张"岗位权限表"上，
> 而是「**角色（权限集合）× 组（谁被授予）× 目标人群（对谁生效）**」的三元授权，
> 且"谁"可以由**动态条件**（部门/国家/职务代码）自动圈定。

**出处**：SAP Help Portal《What Are Role-Based Permissions?》§（三要素 / Permission Groups / Permission Roles）（A）。
