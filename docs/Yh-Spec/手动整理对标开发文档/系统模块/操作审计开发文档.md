## 1. 页面概述

操作审计页是**平台运营方的安全审计台账**：按审计类型 / 模块 / 时间范围筛选 `sys_audit_log` 的审计记录，展示审计日志总数 / 成功操作 / 失败操作三个统计，表格列出日志 ID / 审计类型 / 操作模块 / 操作用户 / 操作时间 / 状态 / IP 地址，点「详情」打开只读弹窗。

**一句话结论：本页的前后端都是真的（8 个端点全部实现、8 个端点全部有权限注解、前端解包写法正确），但它读的表是空的（`sys_audit_log` 实测 0 行），而且一旦有数据，每一行都会显示红色「失败」。**

> **⚠️ 这是本模块"红线③（平台侧写操作必须有审计）"落地情况的直接体现**：`sys_audit_log` **24 列 / 0 行** —— **平台侧目前等于无审计**（README §1.3 红线③、§3.4 P0-17）。

## 8. 业界对标

> **本页在 ql361 无对应页**（§2）。本章只写**业界能力对标**，逐条标来源与可信度级别。**凡底稿标 D 级的方案，本文件一律写「本系统设计」而非「业界标准」。**
> **⚠️ 特别注意底稿 §9.1 第 18 条**：「**OpenTelemetry 通用属性不能兜底『谁改了什么』，审计模型必须自建**」—— 引用 OTel 时必须写清这一点。

### 8.1 业界叫法

**SAP Security Audit Log（SAL）**；Odoo **无独立审计模块**，但 **ACL 拒绝会产出结构化日志文本**（`ir.model.access` → `Access Denied by ACLs for operation: %s, uid: %s, model: %s`）；金蝶有「权限报告」（`Permission Report`）；RuoYi/jeecg 有 `sys_oper_log` 表（**C 级佐证**，见底稿 §9.3）。

### 8.2 业界做法要点

1. **审计必须覆盖「失败」**：SAP SAL 记录「**对话框登录成功/失败、RFC 登录尝试、RFC 调用、用户主记录变更、事务启动、审计配置变更**」—— **6 类事件中 3 类是安全敏感事件，不是业务操作**。
2. **Odoo 的 ACL 拒绝消息给出了「审计最小字段集」的模板**：`Access Denied by ACLs for operation: %s, uid: %s, model: %s`（= **操作 + 主体 + 模型**），错误正文还会带上「This operation is allowed for the following groups:\n%(groups_list)s」和「Contact your administrator to request access if necessary.」—— **即"谁、对什么、想做什么、被哪条策略拒绝、该找谁"**。
3. **审计要有「选择槽（selection slots）」概念**：SAP 参数 `rsau/selection_slots`（默认建议 10）—— 即**可同时启用的审计过滤器数量有限**，这是性能与可运维性的权衡。
4. **区分「全局规则」与「分组规则」的组合语义**（Odoo `ir.rule` 官方原文）：「**Global rules intersect**」「**Group rules unify**」「**The global and group rulesets intersect**」，并警告「**Creating multiple global rules is risky**」（可能形成互不重叠的规则集，导致所有访问被移除）。**做平台级数据权限时要引以为戒。**
5. **权限判定是累加的**：Odoo 官方原文「Access rights are additive」「a user's accesses are the union of the accesses they get through all their groups」；且「**an empty group_id means the ACL is granted to every user**」（空组 = 全员）。
6. **字段级权限是独立一档**：Odoo 字段可设 `groups` 属性，效果是「restricted fields are automatically removed from requested views」「removed from `fields_get` responses」「attempts to explicitly read from or write to restricted fields results in an access error」。
7. ⚠️ **OpenTelemetry 通用属性不能兜底审计字段**：OTel 通用属性页**只有** `client.address`（「Client address - domain name if available without reverse DNS lookup; otherwise, IP address or UNIX domain socket name」）、`network.peer.address`（「Peer address of the network connection」）、`server.address`；**没有** `enduser.id` / `enduser.role` / `user_agent.original` / `service.name` / `error.type` / `url.full`。→ **「谁、从哪个 IP、改了什么」里的「谁」与「改了什么」，OTel 通用属性并不覆盖，必须自建审计模型。**

## 10. 验收标准

> **前置**：本模块**尚无 E2E**。落地脚本建议命名 `tools/e2e-system.cjs`（接口 + 直连 DB 对账 + 写库后复原 + Playwright UI 截屏）。
> **⚠️ 本页验收的特殊性**：`sys_audit_log` **当前 0 行** → **大部分"字段错配"缺陷在空表下不可见**。因此验收**必须先造数**（经 `POST /api/audit/record`，**不要直插 DB**，以覆盖实体的 `@TableField(fill=INSERT)` 逻辑），**断言完成后再清理造的数据**。
> **权限账号**：`admin`（id=1，`tenant_id=1`，SUPER_ADMIN，**持有全部 6 个 `log:audit:*` 码**）作 200 基线；另用一个 `SYSTEM_ADMIN` 角色账号 → **当前预期 403**。
> **⚠️ 写库断言必须"改库 → 回读 → 按原值复原"** —— 本页有 `DELETE /api/audit/clean` 与 `POST /api/audit/record`，**测试后必须清理自产数据**。

### 10.1 接口验收（24 项）

**写数据（造数，前置）**

① `POST /api/audit/record`（带 `admin` Bearer，body 含 `auditType` / `module` / `action` / `targetType` / `targetId` / `targetName` / `userId` / `username` / `operIp` / `operTime` / `result`）→ **期望 200**，返回 `{success: true, logId: …}`（`AuditLogController.java:33-39`）。
② 🔴 **直查 DB 对账**：`SELECT count(*) FROM sys_audit_log` 从 **0** 变为 **≥1**；断言该行的 `tenant_id` / `result` / `oper_ip` / `username` 与提交值一致。
③ **断言 `create_time` 由 `@TableField(fill=INSERT)` 自动填充，而 `oper_time` 由请求体决定**（`AuditLog.java:138` vs `:82`）→ **这就是「操作时间列语义错位」的接口级证据**。
④ **造一条 `result='FAILURE'` 与一条 `result='SUCCESS'` 的记录**（各 1 条），供后续统计断言。

**查询与字段（⑤–⑫）**

⑤ `GET /api/audit/query?page=1&pageSize=20` → 期望 200，返回裸 `Map`（`total`/`page`/`pageSize`/`records`）。
⑥ 🔴 **断言返回的 `records[0]` 含字段 `username` / `operIp` / `operTime` / `result`**，**且不含** `userName` / `ipAddress` / `status` / `createTime`（或 `createTime` 存在但非业务时间）→ **这是 4 处字段错配的接口级证据**。
⑦ 🔴 **状态列逻辑断言**：断言 `records[0].status === undefined` → **证明前端 `record.status === 'SUCCESS'` 恒 false → 每行显示红色「失败」**（即使 `result='SUCCESS'`）。
⑧ `GET /query?auditType=<小写 code>`（如 `login`）→ 断言能过滤；`GET /query?auditType=LOGIN`（**大写**）→ 断言**过滤为 0 行** → **复现 §5.1 的大小写失配**（**登记结论：真实落库值是小写**）。
⑨ `GET /query?module=<某模块>` → 断言与 `WHERE module = ?` 一致。
⑩ `GET /query?userId=<id>`（后端支持，`:44`；**前端未传**）→ 断言与 `WHERE user_id = ?` 一致 → 登记"前端未使用该筛选"。
⑪ `GET /query?startTime=...&endTime=...`（正确格式 `yyyy-MM-dd HH:mm:ss`）→ 断言生效；**后端按 `oper_time` 过滤与排序**（`AuditLogServiceImpl.java:54-57`）。
⑫ `GET /api/audit/detail/{logId}`（取 ① 的 logId；**前端未调**）→ **期望 200**，返回完整 `AuditLog`；**断言含 `beforeData`/`afterData`/`errorMsg`/`duration`/`operLocation`/`targetType` 等 16 个 UI 未使用的列** → 登记 P1-9。

**统计（⑬–⑮）**

⑬ `GET /api/audit/statistics` → 断言返回键为 `total` / `successCount` / **`failureCount`** / `typeStats` / `moduleStats` / `userStats`（`AuditLogServiceImpl.java:101-119`）。
⑭ 🔴 **断言响应中不存在 `failCount` 键**（只有 `failureCount`）→ **这是「失败操作卡恒 0」的接口级证据**（页面 `:304` 读 `failCount`）。
⑮ 🔴 **断言 `/statistics` 不带筛选参数时是全量口径**：造 2 条记录（1 成功 1 失败）后，断言 `total >= 2`、`successCount >= 1`、`failureCount >= 1`；再带 `startTime`/`endTime` 调用，断言结果随之变化（**证明后端支持筛选而前端不传**，P1-11）。

**权限（⑯–⑲）**

⑯ 🔴 **超管 200 断言**：用 `admin` 调 8 个端点 → **期望全部 200**（超管持全部 6 码 + `*` 通配）。
⑰ 🔴 **SYSTEM_ADMIN 403 断言**：用 `SYSTEM_ADMIN` 角色账号调 `/query`（要求 `log:audit:list`）与 `/statistics`（要求 `log:audit:stats`）→ **当前预期 403** → **登记 P1-13**（该角色无任何 `log:audit:*` 码）。修复后改断言 200。
⑱ **权限码存在性与归属断言**：`SELECT permission_code FROM sys_permission WHERE permission_code LIKE 'log:audit%'` → 断言 **6 行**；`SELECT role_id, count(*) FROM sys_role_permission rp JOIN sys_permission p ON p.id=rp.permission_id WHERE p.permission_code LIKE 'log:audit%' GROUP BY role_id` → 断言**当前只有 `role_id=1`**（登记 P1-13）。
⑲ **未带 Token 断言**：不带 Authorization 调 `/query` → **期望 401/403**（全局拦截，`SaTokenConfig.java:70-71`）。

**租户豁免（⑳，红线②专用）**

⑳ 🔴 **超管可见性 + 租户豁免断言**（**"改库 → 回读 → 按原值复原"的标准动作**）：① 断言 `IGNORE_TENANT_TABLES`（`MyBatisPlusConfig.java:32-93`）**不含 `sys_audit_log`**（逐项核对）、**含 `sys_login_log`**（`:50`，作"逐表显式登记"的对照）；② 经 `POST /api/audit/record` **插入一行 `tenantId=0` 的测试记录**（`module='E2E_TENANT_SCOPE_TEST'`）；③ **回读**：断言超管 `/query` **能否查到这一行**，记录结论（预期**查不到** → 红线②未落地）；④ **按 `logId` 精确删除该行复原**。

⑪ 🔴 **详情弹窗断言**：点行内「详情」→ 弹窗打开（`:174`）→ **打开 Network 面板断言未发出 `/api/audit/detail/*` 请求** → 证明**纯前端**。

⑬ 🔴 **缺失信息断言**：断言弹窗中**没有「变更前值 / 变更后值 / 错误信息 / 耗时 / 请求 URL / 目标对象」** 任何一项（24 列只用 8 个字段）→ 登记 P1-⑧。
⑭ **刷新按钮与无防抖断言**：连点 3 次「刷新」→ 断言发出 3 组请求（无防抖）；**并断言本页无自动刷新**（静置 60 秒无新请求）。

⑱ **控制台与泄漏断言**：断言页面控制台**无 `error`（含 `TypeError`）/ 无未捕获 Promise rejection**（**注意**：SYSTEM_ADMIN 场景下预期会出现 unhandled rejection，需显式记录）；断言**无 `setInterval` / `addEventListener` 注册**（本页无轮询，`onUnmounted` 未导入属合规）；**反复进出 10 次断言无任何资源增长**。

## 12. 剩余缺口（P0 / P1 / P2）

> 与《系统模块/README.md》§7 口径一致。README §1.3 红线③（平台侧写操作必须有审计）、§3.4 P0-9（操作审计 4 处字段错配）、§3.4 P0-17（平台侧无审计）、§7.1 P0-9 在本页的具体化见下。

### P0（6 条）

① **4 处字段名与实体错配（README §7.1 P0-9 的具体化）**：`userName`←`username`（`:251` vs `AuditLog.java:67`）、`status`←`result`（`:253` vs `:87`）、`ipAddress`←`operIp`（`:254` vs `:72`）、`createTime`←`operTime`（`:252` vs `:82`，语义错位）。**后果：有数据时每行都显示红色「失败」；操作用户与 IP 恒空；操作时间不是业务时间。** 建议：逐处改 key。
② **「失败操作」统计卡恒 0**：前端读 `failCount`（`:304`），后端返回 **`failureCount`**（`AuditLogServiceImpl.java:107`）。建议：改读 `failureCount`。
③ **表为空且无写入方（README §1.3 红线③ 的具体化）**：`sys_audit_log` **24 列 / 0 行**；全仓 grep **无生产代码调用** `auditLogService.record(...)`。→ **「谁在什么时候从哪个 IP 给哪个租户开了哪个模块」目前无迹可查**（README §3.4 P0-17）。建议：在平台侧写操作处调用 `record(...)`。
④ **平台级审计表未豁免多租户（红线②）**：`sys_audit_log` **不在 `IGNORE_TENANT_TABLES`**（`MyBatisPlusConfig.java:32-93` 逐项核对）；底稿 §3.5 明确要求「平台运营方自己的操作 `tenant_id` 应为 **0/NULL**，且该表**必须豁免多租户过滤**，否则平台运营方的操作审计自己看不到」。建议：读全局用 `@InterceptorIgnore(tenantLine="true")`；按 §10.1-⑳ 专断言。
⑤ **权限码只挂超管**：6 条 `log:audit:*` **全部 `role_id=1`**；`SYSTEM_ADMIN` **一条都没有**（devdb 实测）→ 该角色登录本页**两接口全 403**。建议：按最小权限授予 `log:audit:list` / `log:audit:stats`。
⑥ **`fetchData` 无 `catch`**（`:281-309`）→ 接口 403/500 时**表格保持旧数据或空、无任何用户提示**；叠加 ⑤，**非超管看到的是"空白页面且无解释"**。建议：补 `catch` + 可见提示。

### P1（7 条）

⑦ **6 个后端端点无 UI 入口**：`/detail/{logId}`（`AuditLogController.java:59`）、`/user/{userId}/history`（`:67`）、`/object/{targetType}/{targetId}/history`（`:76`）、`/export`（`:97`）、`/clean`（`:109`）、`/record`（`:33`）—— **后端全实现、全有权限，前端只用了 2 个**。
⑧ **详情弹窗是纯前端**（`:270-273` 不调 `/api/audit/detail/{logId}`）；且 **24 列中 16 列在 UI 上无出口**，含审计最核心的 `result` / `before_data` / `after_data` / `action` / `target_*` / `error_msg` / `duration` / `oper_location` / `request_*` / `response_data` / `data_snapshot` —— **"改了什么"完全看不到**。
⑨ **统计接口不带筛选条件**（`:300`）→ 顶部统计恒全量，与列表口径不一致（后端支持 `startTime`/`endTime`，`:88-93`）。
⑩ **两个下拉硬编码且与后端枚举大小写不一致**（前端大写 5 项 vs 后端小写 10 项；模块 4 项硬编码）→ **筛选恒 0 行、tag 恒灰**。
⑪ **`/statistics` 全表扫描**（`AuditLogServiceImpl.java:93-119` 的 `selectList` + 内存 `groupingBy` ×3）与 **`/export` 无条数上限**（`AuditLogController.java:97-107`）。
⑫ **未达金标准路线 A**：无 `ErrorBoundary`、无布局组件、**裸 `a-table`**、无列配置齿轮、无 `PageConfigPanel`；查询区 `layout="inline"` **非横向网格**（`:37`）—— 与 README §7.2 一致（「30 页全部无 PageConfigPanel / 无 storage-key / 无经典分页 / 无列配置齿轮」）。
⑬ **无登录日志页**：`sys_login_log`（**16 列 / 6238 行**）有真实数据却没有页面（README §3.6、§7.2）；而 SAP SAL 的审计重点正是**登录失败 / RFC 登录 / 用户主记录变更**（B 级）。

### P2（4 条）

⑭ **无自动刷新**（无轮询、无 SSE）→ 新审计事件不会自动出现；与《系统日志》页有 30 秒刷新形成不一致。
⑮ **弹窗第 8 项 `v-if="detailItem?.detail"` 永不显示**（实体/DB 无 `detail` 列，`:206-211`）。
⑯ **刷新按钮无防抖**（`:19-30` 直接绑定 `fetchData`）；全局事件/定时器体系上，`onUnmounted` **未导入**（本页无定时器，属合规，但与同组其它页写法不一致）。
