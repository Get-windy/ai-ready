## 页面概述

缺陷记录用于登记质检不合格项的处置（退货/返工/报废/特采等），由质检单「不合格处理」入口创建，本页做查询与处置。模块含一个页面：

| 页面 | 地址 | 说明 |
|------|------|------|
| 缺陷记录列表页 | `quality/defect/list` | 单一列表页，查询 + 处置弹窗 |

### 配置功能说明（每个页面都有）

- **页面配置**（页面顶部齿轮图标）：管理页面级字段的显示、隐藏和排序。
- **列配置**（数据表右上角表头单元格内齿轮图标）：管理数据表列字段的显示、隐藏、排序、宽度调整及左右冻结。
- ⚠️ **当前实现说明**：本页当前采用轻量 `ARReportPage` + `a-modal` 弹窗实现，**暂未接入页面配置/列配置弹窗**，该能力列入「实现差异说明 → 待完善」。

### 查询条件

| 查询条件 | 控件 | 说明 |
|---------|------|------|
| 检验记录 ID | input | inspectionId（⚠️ 后端 page 不接收，待补） |

| # | 列名 | dataIndex | 说明 |

| 4 | 缺陷描述 | defectDesc | ellipsis |

| 8 | 处理人 | handlerName | |
| 9 | 状态 | status | Tag（0 或 'PENDING'→待处理 warning，否则已处理 success） |

### 处置弹窗字段

| 字段 | 控件 | 必填 | 说明 |
|------|------|------|------|
| 来源单号 | a-input | 否 | disabled，仅记录有 bizNo 时显示 |
| 处理方式 | a-select | 是 | RETURN 退货 / CONCESSION 让步接收 / REWORK 返工 / SCRAP 报废 / SPECIAL_RELEASE 特采（默认 REWORK） |
| 处理数量 | a-input-number | 是 | handleQuantity（默认取 defectQuantity） |
| 处理结果 | a-textarea | **是** | handleResult |

## 业务规范说明

- 缺陷来源：由质检单「不合格处理」入口创建（`POST /api/quality/defect`，body inspectionId/defectType/defectDesc/defectQuantity）。
- 处置流转：待处理(status=0) → 已处理(status=1)；`handle` 写 handleType/handleQuantity/handleResult/handlerName/handleTime。
- 处理方式：RETURN 退货 / REWORK 返工 / SCRAP 报废 / SPECIAL_RELEASE 特采（⚠️ 前端弹窗另含 CONCESSION 让步接收，后端实体注释无，待补）。
- **架构师红线**：对标 Odoo/SAP/金蝶/用友/管家婆等生产级系统的业务与交互逻辑；动手前过六关，仅最小可用闭环，防注入/容灾/安全防御代码不准省。
- **验收标准**：无桩（Stub）与模拟（mock|todo|fixme|占位|placeholder），确保真实数据。
- **对标系统**：ql361（`22stable.ql361.com`），质量模块无此页，本页为设计新增。

## 实现差异说明

**实现文件**：
- 前端：`frontend/apps/pc-admin/src/views/quality/defect/list.vue`、`frontend/apps/pc-admin/src/api/quality/index.ts`（`qualityDefectHandleApi`）
- 后端：`backend/core/base/core-base/src/main/java/cn/aiedge/quality/` — `entity/QualityDefectHandle.java`、`controller/QualityDefectHandleController.java`、`service/impl/QualityDefectHandleServiceImpl.java`
- 表：`quality_defect_handle`（V8.13.0 建表，含 tenant_id，无 version/create_by/update_by）
- 菜单：90203（缺陷记录），`quality:defect`，组件 `quality/defect/list`

### 页面对齐（已建成）
- **列表页**：`CategoryListLayout` + `BillTableList` + **列配置弹窗** + **页面配置弹窗**（列/查询字段/功能按钮显隐，localStorage 持久化）+ 6 项查询（来源单号/检验记录ID/缺陷类型/状态/处理人/创建日期区间）+ a-modal 处置弹窗，查询/处置闭环。**「缺陷数量/来源单号/处理人」三列真实数据已补齐**（见下节）。
- **API**：`page`(GET `/api/quality/defect/page`)、`handle`(POST `/{id}/handle`)、`create`(POST `/api/quality/defect`)、`pending`(GET `/pending`)。

### 已补齐（本次开发）
1. **缺陷数量/来源单号/审计列真实数据**：建表缺 `defect_quantity`/`biz_no` 列、实体缺字段，前端列/API/create 引用后一直为空，且 `create` 曾将缺陷数量错写入 `handle_quantity`。迁移 `V11.67.0` 补 `defect_quantity`/`biz_no` 两列；**`V11.68.0` 补 BaseEntity 审计列 `create_by`/`update_by`/`version`**（缺陷实体继承 `BaseEntity` 由 `MetaObjectHandler` 自动填充，V8.13.0 建表缺失三列导致 `insert` 报 BadSqlGrammar）；实体补 `defectQuantity`/`bizNo`；`create` 改存 `defect_quantity` 并带出质检单 `biz_no`（经 `QualityInspectionMapper.selectBizNoById` 仅查单列，规避质检单表同样缺失 BaseEntity 列导致的全列查询报错）；`handle` 补齐 `handlerId`/`handlerName`（取当前登录用户真实姓名）。
2. **状态筛选类型冲突修复**：后端 `page` 的 `status` 改为 `String` 接收并映射 `PENDING→0`、`HANDLED→1`（兼容数字），类型转换 400 消除。
3. **查询条件后端接收**：后端 `page` 新增 `inspectionId`/`defectType` 查询参数（`inspectionId` 做非法值兜底），前端 select/input 提交不再被忽略。
4. **枚举一致**：后端实体/迁移注释补充 `CONCESSION`（让步接收），与前端弹窗枚举对齐。
5. **处置校验**：处置弹窗「处理数量」设为必填并在提交前校验，避免空值触发后端 `handle` NPE。
6. **前端金标准升级**：列表页由轻量 `ARReportPage` 升级为金标准三件套（`CategoryListLayout` + `BillTableList`，对齐同模块 `quality/standard/list.vue` 与报损/报溢通用列表页标配），接入**列配置弹窗**（显隐/排序/宽度/冻结）与**页面配置弹窗**（查询字段/功能按钮显隐）；查询区扩充来源单号/处理人/创建日期区间，后端 `page` 相应支持 `bizNo`/`handlerName` 模糊与 `createTimeStart`/`createTimeEnd` 区间过滤；导出保留前端 CSV。未接入「按单据/按明细」双Tab、新增表单页/双入口、编号/审批/库存回写等单据特有能力（缺陷记录为扁平"记录+处置"，记录由质检单写入，不适用）。
7. **模块内业务闭环**（对应跨模块检查问题本页负责项，页面级已完成）：
   - **缺陷等级(S/Ma/Mi)**：`defect_level` 字段 + 列表列/查询/导出；后端 `page` 支持 `defectLevel` 过滤（迁移 V11.73.0）。
   - **处理历史/多步处置**：新增 `quality_defect_handle_history` 处理历史表，`handle` 每次处置写一条历史，前端详情弹窗展示处理历史。
   - **缺陷回查质检单/标准**：缺陷详情弹窗按 `inspectionId` 回查质检单信息、按 `inspectionType` 回查质检标准。
   - **联动基建**：`QualityDefectHandledEvent` 事件（core-base 发布）+ `linkDownstream` 回填 `returnNo`/`damageNo` 字段；处置弹窗按 RETURN/SCRAP 显示联动提示。

## 开发原则（通用）

- **页面组件优先复用**：页面开发优先使用已有的页面组件，除非当前页面组件不满足业务需求；确无对应组件，则优先开发合适的通用组件。
- **功能/模块不重复开发**：已开发过的业务功能、单据、通用能力在全系统范围内只实现一次；其它模块直接复用，不重复开发。
- **Service 接口签名变更需同步测试**：修改 Service 接口签名（方法名/参数/返回值）时，必须同步更新对应测试类，否则会阻塞整模块的 `test-compile`。
- **阶段结束前回写开发文档**：当前阶段工作完成后、结束前，必须更新开发文档的「已完成」与「待完善」章节，使其反映当前代码的实际实现情况。
