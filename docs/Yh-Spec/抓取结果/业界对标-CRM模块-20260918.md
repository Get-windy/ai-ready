## 一、Odoo 17 / 18（CRM + Sales + Subscriptions + Sign）

### 1.1 线索(Lead) / 商机(Opportunity) / 客户(Partner) 的转化模型

| 能力 | 业界做法（Odoo） | 关键字段/对象名 |
|---|---|---|
| 线索与商机是否同表 | **是。** 二者共用同一模型 `crm.lead`，用 `type` 选择字段（`lead` / `opportunity`）区分；`type` 决定可见视图与可用阶段，`stage_id` 决定漏斗位置 | 模型 `crm.lead`；字段 `type`(Selection)、`stage_id` |
| 启用线索 | `CRM → Configuration → Settings` 勾选 **Leads**，为所有销售团队激活线索功能；也可在单个销售团队中单独禁用 | 设置项 Leads |
| 「Convert to Opportunity」做什么 | 打开线索 → 左上角 **Convert to Opportunity** → 弹窗中选 **Conversion Action**：`Convert to opportunity`（直接转化）或 `Merge with existing opportunities`（与已存在的相似线索/商机合并）→ 在 **Customer** 分组选择「创建新客户 / 关联现有客户 / 不关联客户」→ 指定销售人员和团队 → **Create Opportunity**。转化本质是把记录的 `type` 从 lead 改为 opportunity | 按钮 Convert to Opportunity；弹窗字段 Conversion Action、Customer |
| 合并的优先规则 | Odoo **优先保留创建最早的记录**；合并「线索 + 商机」时结果记录一律称为 **opportunity**（无论谁先创建） | — |
| 转商机向导的字段演进（开发相关） | 有一份 Odoo 主分支 PR 重构了转化逻辑：单选转化不再打开向导；批量转化取消了 `action` 字段、以 `lead_tomerge_ids`(M2M) 取代 `lead_id`；`user_id` 改为 `user_ids`；`commercial_partner_id` 被移除；`user_ids` / `team_id` / `partner_id` 默认均为 False（留空则不修改） | `lead_tomerge_ids`、`user_ids` |
| 客户对象 | Odoo 的「客户」是 `res.partner`（Partner 即客户/供应商/联系人统一档案），商机通过外键关联 Partner | `res.partner`；`crm.lead.partner_id` |

### 1.2 去重 / 相似记录合并（Deduplicate）

| 能力 | 业界做法（Odoo） | 关键字段/对象名 |
|---|---|---|
| 自动检测重复 | Odoo **自动检测** CRM 中的相似线索与商机，方式是比对**关联联系人的电子邮件与电话号码**；命中后记录顶部出现 **「相似销售线索」(Similar Leads) 智能按钮** | 智能按钮 Similar Leads |

| Lead Mining | **本次检索未获取到 Odoo 18.0 官方「Lead Mining」独立文档页**，故不对其机制下结论。Odoo 语境下的去重由上述「相似线索合并」+「Data Cleaning 去重规则」两套机制承担 | — |

### 1.3 销售管道(Pipeline)与 `crm.stage` 阶段模型

| 能力 | 业界做法（Odoo） | 关键字段/对象名 |
|---|---|---|
| 阶段字段全集 | 阶段是 `crm.stage` 模型，核心字段如下 | `name`(名称，必填)、`sequence`(排序，越小越靠前)、`probability`(该阶段成功概率%)、`is_won`(是否赢单阶段)、`fold`(管道中折叠)、`requirements`(内部要求)、`team_id`(指定使用该阶段的销售团队) |
| `requirements` 的真实行为 | 原生**仅作提示文本**：填写后鼠标悬停阶段名称时以 **tooltip** 显示。**原生不做强制校验**；如需「字段为空不允许进入下一阶段」需第三方模块（如 `crm_stage_requirements`）或二次开发 | `requirements` |
| `fold` 的作用 | 当该阶段**没有记录时**，看板视图中该列折叠 | `fold` |
| 阶段推荐数量 | Odoo 建议管道阶段**不超过 6 列**，可拖放重排顺序 | — |
| 「自动更新概率」 | 阶段上勾选 **Change Probability Automatically** 后，机会移动到该阶段时概率**自动调整**；建议赢单阶段 = 100%、丢单阶段 = 0% | 选项 Change Probability Automatically |
| 阶段状态语义（源码内文档） | Odoo 源码 `addons/crm/doc/stage_status.rst` 定义：`new` = `stage_id.sequence = 1`；`won` = `probability = 100` 且 `on_change = True`；`lost` = `probability = 0` 且 `on_change = True` 且 `sequence != 1`。默认新建线索处于 `sequence = 1` 的阶段 | 源码文档 `stage_status.rst` |
| 看板拖拽 | 阶段管理通过看板视图或可点击的状态栏完成，**不再使用按钮**；拖拽卡片即推进阶段 | — |
| 「停滞 / rotten」提醒 | **存在信息冲突，需谨慎**：一方称 rotten 是 **Odoo 19 才引入**（基于 `mail.tracking.duration.mixin` 计算 `is_rotting` / `rotting_days`，18/17/16 均无此功能）；另一方（第三方教程类）称可在 **CRM → Configuration → Stages** 为每阶段设 "Days to rot"，且 CRM 设置中可启用 Rotting Days 使停滞交易标红。**Odoo 18.0 官方文档中未检索到专门的 rotting 章节**，故本项标记为「未取得官方文档佐证」 | `is_rotting`、`rotting_days` |
| 官方认可的「停滞商机」替代做法 | Odoo 18 官方文档给出 **Unattended Leads Report（未处理线索报告）**：定义为「有逾期或已过期计划活动的线索/商机」；做法是在 **Pipeline Analysis** 中清除默认过滤器，再加自定义过滤：Activities > Due Date ≤ 今天；Salesperson is set；可选 Sales Team in [团队]。销售经理每天拉取该报告识别需立即关注的商机 | 报表 Unattended Leads Report；过滤条件 Activities ▸ Due Date |
| 常见实务阈值（第三方经验，非官方） | 新建商机 3 天无活动→审查；资格阶段 7 天无活动→经理关注；提案阶段 10 天无跟进→需跟进；谈判阶段 14 天无活动→升级/审查（第三方治理文章的建议值） | — |

### 1.6 预测与统计（Expected / Prorated Revenue、Pipeline 分析）

| 能力 | 业界做法（Odoo） | 关键字段/对象名 |
|---|---|---|
| 预期收入 | **Expected Revenue = 销售价格 × 数量** | 字段 Expected Revenue |
| 按概率折算收入 | **Prorated Revenue = Expected Revenue × Probability**。官方示例：商机 A「Global Solutions」预期收入 $3,800 × 90% = **$3,420**；商机 B「600 把椅子的报价」$22,500 × 20% = **$4,500**；当月合计**$7,920**，显示在该月柱状列顶部、进度条右侧 | 字段 Prorated Revenue |
| Forecast 报表 | `CRM → Reporting → Forecast`；**按「预计成交日期」的月份分组**，可**拖拽看板卡**调整成交日期；默认时间范围为「月」，可通过 Group By → Expected Closing 改为 年/季/月/周/日；支持 **Kanban / Graph / Pivot / List** 四种视图；列会随商机移动**自动更新** | 报表 Forecast；分组 Expected Closing |
| Pipeline 分析 | `CRM → Reporting → Pipeline` 打开 Pipeline Analysis 仪表盘；`Measures → Expected Revenue`，常用过滤：Expected closing date is set + is between；Salesperson is set（排除未指派线索）；Sales Team is in（可选）。视图含 **Graph（柱/线/饼）、Pivot、List** | 报表 Pipeline Analysis |
| 常用度量(Measures) | 第三方资料列出的度量集：**Days to Assign、Days to Close、Expected Revenue、Expected Closing Days、Expected MRR、Prorated MRR、Prorated Revenue**；Pivot 可同时选多个度量，按月与商机阶段交叉分析 | 上述 Measures |
| 产品级预测 | OCA 社区模块 `crm_lead_product` 允许把多个产品/类别/模板挂到线索上，行上有 `expected revenue` 与 `prorated revenue` 两个计算字段，菜单 `CRM > Reporting > Pipeline by Product`，支持 Pivot/Graph | 模块 `crm_lead_product`（第三方/OCA，非官方） |

### 1.7 报价单（Quotation / Sale Order）

| 能力 | 业界做法（Odoo） | 关键字段/对象名 |
|---|---|---|

### 2.5 合同管理：框架协议（Outline Agreement）

SAP 的合同体系在**采购侧**与**销售侧**都存在，采购侧分类最清晰，销售侧在 S/4HANA 的 Sales Documents 官文中与「合同(Contracts)、计划协议(Scheduling Agreements)」并列为一类销售凭证。

| 能力 | 业界做法（SAP） | 关键字段/事务码 |
|---|---|---|
| 框架协议两种形态 | 框架协议 = 与供应商/客户的长期约定，在开单前先锁定条款。两种形态：**合同(Contract)** 与 **计划协议(Scheduling Agreement)** | Outline Agreement |
| 合同：不带交货日期 | 合同是**不含交货日期**的长期协议，分两类 | — |
| **数量合同 Quantity Contract** | 以**约定总数量**交付完成为履约完毕。**目标数量在行项目级维护**；当所有 release order 的累计数量达到约定数量即视为完成 | 类型 **MK**；事务码 **ME31K** |
| **价值合同 Value Contract** | 以**约定总价值**交付完成为履约完毕，**与数量无关**。**目标价值在抬头级维护**（行项目的目标数量可选填） | 类型 **WK**；事务码 **ME31K** |
| 合同的其他特征 | 必须有**有效期结束日期**；货物通过**参照合同的 release order（采购订单）**叫料（如 ME21N，凭证类型 NB）；**Release order documentation** 跟踪全部订单活动、单笔采购订单、累计数量与订单价值，并自动更新用于合同监控（ME3L）；**累计值：数量合同在行级更新，价值合同在抬头级更新**；适合**需求不规律/不可预测**但价格已谈定的场景 | Release Order；ME3L |
| **计划协议 Scheduling Agreement** | 供应商按**已传达的交货计划（含固定交货日期）**供货。协议类型 **LP（无 release documentation）**、**LPA（有 release documentation）**。交货日期由**计划行(schedule lines)**控制（ME38 维护，或由 MRP 自动生成）；**不需要逐次下采购订单**。计划行含 **Firm（固定）、Trade-off（权衡）、Forecast（预测）** 三个区段；可与 **MRP** 紧密集成，适合重复制造/批量生产；适合**规律、可预测的供应** | 类型 LP/LPA；事务码 ME31L；ME38 |
| 对比要点 | 交货日期是否已知 = 核心分野：**时间未知用合同，时间已知用计划协议**；合同每次交货有一张 PO，计划协议没有 | — |
| 销售侧的框架协议 | S/4HANA 的销售凭证类别中「框架协议」含**合同与计划协议**；并有专门文档《Document Flow for a Unit Price Contract》（单价合同凭证流） | 销售合同 / 计划协议 |
| 合同监控 | 通过 release order documentation 与累计值实现合同履约监控 | 报表 ME3L |

### 4.8 销售漏斗转化率口径（stage-to-stage vs 整体赢单率）

| 能力 | 业界做法 | 关键字段或对象名 |
|---|---|---|
| 转化率定义 | **Conversion Rate = Conversions ÷ Total Opportunities × 100**；团队应**在每个漏斗阶段分别跟踪一个比率**，而不仅是最终值 | Conversion Rate |
| 赢单率定义 | **Win Rate = closed-won ÷ (closed-won + closed-lost)**。必须先确定「**无决策 / 不合格(disqualified)**」是否计入输单，这会显著改变数值；以**全部创建的机会**为分母算出的赢单率，会比以**已合格机会**为分母的难看 | Win Rate / Close Rate |
| 阶段转化率定义 | **Stage Conversion = 到达第 N+1 阶段数 ÷ 进入第 N 阶段数**；**应做队列化(cohort-based)** 计算——按**进入时间分组**，而不是取某个时点的快照，以避免在途机会扭曲 | Cohort |
| 比率相乘原理 | 阶段比率**连乘**：五个阶段各 50% 的漏斗整体转化约 **3%**；把某一阶段从 50% 提到 60%，整体提升约五分之一。端到端 MQL-to-customer 率 = 各阶段率之积 | — |
| 基准数据（第三方，仅供参考） | **Optifai（939 家 B2B，2025Q2–2026Q1）**：Discovery → Qualification **40%**；Qualification → Proposal **55%**（最大流失点，-20pt）；Proposal → Negotiation **70%**；Negotiation → Closed-Won **85%**；**整体 13%**（100 单 → 13 单）。**Grou（1,400 笔 B2B SaaS，2024–2026）**：整体 Discovery→Closed Won **18–25%**（中型市场更高、企业级更低）；Discovery→Qualified 62%；Qualified→Demo 78%；**Demo→Proposal 48%（成交阵亡点）**；Proposal→Verbal 55%；Verbal→Closed 82% | 上述百分比 |
| 更细的漏斗基准（第三方） | Tomba（B2B SaaS 漏斗地图）：访客→线索 <1.5% / 3–5% / 8%+；线索→MQL <10% / 20–30% / 40%+；MQL→SQL <8% / 13% / 25%+；SQL→商机 <12% / 20–25% / 35%+；商机→成交 <15% / 20% / 30%+（弱/中位/强三档） | 上述区间 |
| 口径陷阱（重要） | 必须钉死三件事：**被计数的动作是什么、能执行该动作的总体是谁、时间窗多长**——改任何一个，数字就会在业务没变的情况下变动。**队列完整性**：用「本月成交 ÷ 本月新线索」会混人群；在 90 天周期业务中，这会**在增长期低估、在衰退期高估**转化率。**基准只用于体检，不用于定目标**——自己最近 90 天的滚动值才是更好的基线。**必须按 ACV 分层**：SMB 转化更快（平均阶段推进率 75%），企业级更慢（55%），周期 90–180 天 | — |

## 结语：对 16 个 CRM 页面覆盖度自检

| CRM 页面 | 已取得业界做法 + 出处 | 主要证据缺口 |
|---|---|---|
| 客户 | Odoo `res.partner` + Partner Levels；用友客户 360；Salesforce Account 360；SAP BP | — |
| 客户跟进 | Odoo `mail.activity` + Activity Plans；SAP Activity Management；用友行动管理 | — |
| 客户分级 | Odoo Partner Level/Weight；金蝶客户优先级 1–99 + 四维分级 + 信用等级；用友客户评测/客户价值模型 | 金蝶分级为第三方归纳 |
| 拜访规划 | SAP Visits + Route；纷享排线/路线；用友拜访推荐规则 | — |
| 拜访执行 | 用友行动类型签到签退；简道云定位拍照；SAP 拜访执行 | 金蝶外勤签到无官方佐证 |
| 拜访检视 | 简道云轨迹/覆盖率；畅捷通完成率/下单率/超期预警；SAP 产品审核+报告 | — |
| 线索 | Odoo `crm.lead` type=lead；SAP Lead；Dynamics Lead；用友线索池 | — |
| 线索转化 | Odoo Convert to Opportunity（Conversion Action / 合并）；Dynamics Qualify（Account+Contact+Opp，最多 5 个）；SAP 线索转化查重 | — |
| 商机 | Odoo `crm.lead` type=opportunity；SAP Opportunity；用友商机准入/分配 | — |
| 商机阶段 | Odoo `crm.stage`（sequence/probability/is_won/fold/requirements）；SAP Sales Phase（Days in Phase、On Track/Slow/Stalled）；金蝶阶段推进+成功概率；用友阶段属性+赢单率%+持续时间；Salesforce Stage+Forecast Category | — |
| 报价单 | Odoo Quotation（Validity Date / 模板）；SAP Sales Quote Version（Group ID / Active-Inactive）；用友销售报价（三方式/两类型/变更历史） | Odoo 报价版本对象无官方佐证 |
| 合同 | SAP Outline Agreement（MK/WK/LP/LPA）；Odoo Subscriptions Renewal；用友销售合同下推链 | Odoo 独立 Contracts 应用无官方佐证 |
| 合同审批 | 用友协同审批流程设计器（固定流/自由流/参与人/分支）；金蝶合同中心（电子签章） | — |
| 发票 | Odoo Credit Note（Reverse / Reverse and Create）；SAP Billing Plan + Billing Document；用友合同→订单→出库→发票 | — |
| 销售漏斗 | SAP Forecast/Pipeline；Odoo Prorated Revenue + Forecast/Pipeline 报表；金蝶销售漏斗报表；用友 CRM-决策分析-销售漏斗；通用转化率口径与基准 | — |
| 客户分析 | RFM 模型（Klaviyo / 阿里云 / Oracle Unity / Omnisend）；客户健康度（Pricefx / Churnkey / 专利）；Einstein Opportunity Scoring | Salesforce 官方 "Customer Health Score" 文档无佐证 |
