## 1. 页面概述

备份管理页是**平台运营方的数据库备份台账 + 备份动作入口**：4 张由真实记录聚合的统计卡 + 一张「备份记录」表格（备份名称 / 数据源 / 备份类型 / 大小 / 状态 / 开始时间 / 操作）+「创建备份 / 恢复 / 删除」三个动作。它是 `61304 数据管理` 组的第 3 页（`sort=300`）。

**一句话结论（本页最重要的事实）**：**本页当前双层不可用** —— ① **端点层**：`cn.aiedge.datasource` 包漏配 `scanBasePackages`，4 个端点运行期全部 404；② **能力层**：即便装配好，「创建备份」也只往台账插一条 `status='running'` 的行，**不做任何 dump、不落任何文件、状态永不推进**（`BackupServiceImpl.java:31-44`），「恢复」是**空实现且谎报成功**（`:46-51`）。→ 本页是 README §3.2 登记的「**核心能力桩**」页。

## 2. 页面截图

**N/A —— 本模块无对标系统截图。**

**原因（本模块的通用前提，本页严格遵守）**：ql361（来肯企汇 v2.2，`22stable.ql361.com`）是**租户级进销存产品**，对客户暴露的只有「设置」域（`client_type = tenant-admin`）。本页属于**平台控制台**（`client_type = system-admin`）——「平台方怎么管所有租户的数据基础设施」——**任何厂商都不会把自己的 SaaS 控制台给客户看**。因此：ql361 中**不存在**本页（`client_type='system-admin'` 的行不在租户菜单树里）；**不使用 Odoo / SAP / 金蝶 / 用友的界面截图**（口径见 README §5.3：按业界**能力模型**建模，**不照搬任何一家的界面**）；§8 只写**业界能力对标**并逐条标来源与级别。

**本系统截图**：当前无本系统验收截图（`tools/` 与 `tools/acceptance/` 下不存在 `e2e-system-*.cjs` / `e2e-admin-*.cjs`）→ **P2 缺口**（README §7.3）。

**数据现状（devdb 实测 2026-09-18）**：

```
select count(*) from sys_backup_record;   → 0        （列数实测 13）
select count(*) from sys_data_source;     → 0        （列数实测 16）
```

- **`sys_backup_record` 0 行** → 表格**恒空**（渲染 `a-empty`）；4 张统计卡（备份总数/总备份大小/失败备份/最近备份时间）**全部由 `allRows` 聚合**（`:223-234`，无写死指标）→ 在 0 行下**恒为 `0 份` / `0 B` / `0 份` / `-`**（`:229-232`）；
- **`sys_data_source` 0 行** → 卡片右上角「全部数据源」下拉与弹窗「数据源」下拉**均无选项**；`openCreate` 预填的 `dataSources.value[0]?.id` 为 `undefined`（`:267`）→ **即使端点装配好，点「确定」也只会弹「请选择数据源」**（`:274`）；

- 因此本页**写类验收必须先造数**（须经接口或直连，见 §10.1 安全前置）。

**🔴 值域五方不一致（P1，须逐条对照）**：

| 来源 | 合法值 | 证据 |
|------|-------|------|

**后果**：① **`pending` 会直出原值**（手工插入用列默认值的行 → 表格显示裸字符串 `pending`，灰 tag）；② **`failed` 是死值** —— `errorMessage` 列（`V6.14.0:240`）与 `failed` 状态**全仓无写入路径** → 统计卡「失败备份」（`:226`）**恒为 0**（假健康信号）；③ **`success` 不可达** —— 见 §3.6，`create` 只写 `running`，无代码推进 → 「恢复」门槛永假。

**`backupType` 值域（四处口径一致 ✅）**：弹窗下拉 `full`→全量备份／`incremental`→增量备份（`:163-170`）；列表 tag `full`→全量备份（`blue`）／`incremental`→增量备份（`cyan`）／其余直出原值（`:92-93`）；DDL 默认 `'full'` 且注释 `full/incremental`（`V6.14.0:234/246`）；后端兜底 `backupType != null ? ... : "full"`（`BackupController.java:68`）。

### 5.2 流转规则（本页动作）

```
（无）── POST /create ──▶ status='running'（唯一可达状态；file_path/file_size/end_time 全不写）
running ──（全仓无改写路径：无定时任务、无引擎、无补偿）──▶ success / failed   【不可达】
running ── 前端恢复门槛 status==='success' ──▶ 永久为假 → 「恢复」按钮永久灰
任意行 ── DELETE /{id} ──▶ 物理删除（本表无 deleted 列）
```

| 动作 | 后端 | 前置校验 | 失败文案 | 副作用 | 行号 |
|------|------|:--------:|---------|--------|----|
| 创建 | `POST /create` | **仅校验 `dataSourceId != null`**（`:62-64`）；**不校验数据源是否存在** | `{"success":false,"message":"请提供数据源ID"}`（HTTP **200**） | `insert` 1 行台账；**无文件、无进程、无 IO** | `BackupController.java:50-73`；`BackupServiceImpl.java:31-44` |
| 恢复 | `POST /{id}/restore` | 记录须存在且 `status === 'success'` | `{"success":false,"message":"备份记录不存在或状态无效"}`（HTTP **200**） | **无**（空实现） | `BackupController.java:75-84`；`BackupServiceImpl.java:46-51` |
| 删除 | `DELETE /{id}` | 无（`deleteById` 返 0 行即 `false`） | `{"success":false,"message":"备份记录不存在"}`（HTTP **200**） | **物理删除**（非逻辑删除） | `BackupController.java:86-92`；`BackupServiceImpl.java:53-56` |

**🔴 P1-③：三个写动作全部用 HTTP 200 承载失败** —— 4 个端点**没有一处返回 4xx/5xx**，失败一律 `200 + {"success": false}`。后果：前端 `restoreBackup`（`:292-301`）与 `deleteBackup`（`:303-311`）**都不检查 `res.success`**，只要 HTTP 200 就弹「恢复操作已启动」/「备份已删除」→ **失败也提示成功**；E2E 断言不能只看状态码（§10 已按此设计）。**对比**同模块其它控制器存在 `Result.fail(404, …)` 的做法，本控制器**口径不一致**。
**🔴 P1-④：`create` 不校验数据源存在性** —— 只判非空（`:62`）后直接 `Long.valueOf(...)`（`:66`）→ 传 `dataSourceId=999999999` 也能成功插台账；且 `Long.valueOf` 遇非数字会抛 `NumberFormatException` → **预期落全局异常处理返回 500 而非 400**（**该分支未实测**）。
**🔴 P1-⑤：删除是物理删除且无引用保护** —— `deleteById`（`BackupServiceImpl.java:55`）；本表**无 `deleted` 列**（13 列实测、无 `@TableLogic`）→ **删了就是真删**，台账与（未来的）备份文件之间**无一致性保障**：删记录不删文件，反之亦然。

### 5.3 取值口径（4 张统计卡怎么算的）

`statCards` 是 `computed`（`:223-234`），**全部由 `allRows`（当前筛选下的全量，最多 1000 条）聚合，无写死指标**：

| 卡 | label（逐字） | 算法 | 行号 |
|:--:|--------------|------|------|
| 1 | `备份总数` | `rows.length`，后缀 `份` | `:229` |
| 2 | `备份总大小` | `rows.reduce((s, r) => s + (Number(r.fileSize) \|\| 0), 0)` 后过 `formatSize` | `:225`、`:230` |
| 3 | `失败备份` | `rows.filter(r => r.status === 'failed').length`，后缀 `份`；非 0 时 `valueStyle.color = '#ff4d4f'` | `:226`、`:231` |
| 4 | `最近备份时间` | `rows.map(r => r.startTime \|\| r.createTime \|\| '').filter(Boolean).sort().pop()`，空则 `'-'` | `:227`、`:232` |

**口径问题（P1）**：① **受筛选影响** —— 卡上注释自认「基于当前数据源过滤后的全量记录计算」（`:52`），但 label **无「本数据源」字样** → 易被读成全平台合计；② **受 1000 条截断** → 超限时 4 张卡**全部偏小**；③ **`失败备份` 恒 0**（`failed` 是死值，§5.1）→ 假健康信号；④ **`最近备份时间` 用字符串 `.sort()` 无比较器** —— 当前返回 ISO 串时字典序 = 时间序（**恰好正确**），换本地化格式即失效（P2 隐患）。

### 8.2 业界做法要点（逐条给级，保留底稿原文）

1. **逻辑备份与物理备份是两套东西，用途不同**：官方明确「`pg_dump` / `pg_dumpall` 是**逻辑**转储，**不包含 WAL 重放所需的信息**」，**不能用于 PITR**。（**A**）
2. **`pg_dump` 的格式选择有硬约束**：`-F p`（纯文本，默认）/ `c`（自定义，**最灵活、默认压缩，可选择性恢复**）/ `d`（目录，**唯一支持并行转储**，默认 gzip）/ `t`（tar，**不支持压缩**，且表数据项相对顺序恢复时不可更改）。并行 `-j njobs` **只能配目录格式**，且「pg_dump 将打开 njobs+1 个数据库连接」（需注意 `max_connections`）。（**A**）
3. **并行转储的一致性依赖同步快照**：需要同步快照，否则「不同的 worker 作业无法保证在每个连接中看到相同的数据，这可能导致备份不一致」；可用 `--snapshot=snapshotname` 指定。（**A**）
4. **压缩方法**：`-Z` 支持 `gzip`/`lz4`/`zstd`/`none`；`zstd` 的 `long` 模式提高压缩比但增加内存。示例 `pg_dump -Fc -Z zstd:level=9 mydb > mydb.dump`。（**A**）
5. **`pg_dump` 不是集群级一致快照**：官方原文「pg_dump 只转储单个数据库。要导出整个集群，或导出集群中所有数据库共有的全局对象（如角色和表空间），请使用 `pg_dumpall`」。**本系统若一个 PostgreSQL 实例承载多租户多库，备份策略必须明确是「整集群」还是「单库」。**（**A**）
6. **官方还给了「不要用 pg_dump 做定期备份」的警告**：原文「请注意，除非在简单情况下，`pg_dump` 通常不是对生产数据库进行定期备份的正确选择」→ **生产备份应用 PITR。**（**A**）
7. **PITR 三要素（官方原文级）**：`wal_level`（≥replica，**只能在服务器启动时更改**）、`archive_mode = on`、`archive_command`（或 `archive_library`）；`archive_command` 用 `%p`（完整路径）与 `%f`（文件名）占位，**必须「成功才返回 0」**，且「应设计为拒绝覆盖任何已存在的归档文件」；`archive_timeout` 强制段切换（「一分钟左右的设置通常是合理的」）；**归档持续失败会填满 `pg_wal/`，该文件系统写满会导致 PostgreSQL PANIC 关闭**。（**A**）
8. **基础备份与恢复**：`pg_basebackup`（可输出普通文件或 tar 归档）；低阶 API 是 `pg_backup_start(label, fast)` → 复制文件 → `pg_backup_stop(wait_for_archive)`（返回 3 个值，第 2 个写 `backup_label`、第 3 个写 `tablespace_map`）；恢复时需要 `restore_command`，并**创建 `recovery.signal`**（或 `standby.signal`）文件。（**A**）
9. **恢复目标（PITR 停在哪）**：`recovery_target_time` / `recovery_target_name` / `recovery_target_xid`，以及 `recovery_target_timeline`；约束是「停点必须在基础备份结束时间之后」。官方还提示「截至撰写时只有日期/时间和命名恢复点选项非常可用，因为**没有工具能帮你准确识别该用哪个事务 ID**」。（**A**）
10. **保留策略原文（直接决定「备份管理」页的默认值）**：「所有名称数值更小的归档 WAL 段……不再需要，可以删除。**然而，你应考虑保留多套备份集，以绝对确定能恢复数据。**」「由于必须保留回到最近一次基础备份为止的所有归档 WAL 文件，基础备份之间的间隔通常应根据你想在归档 WAL 文件上花费多少存储来选择。」「时间线历史文件……很便宜，适合无限期保留（不像段文件那么大）。」「增量备份……**PostgreSQL 没有内置机制来判断哪些备份仍是恢复后续增量备份所必需的。你必须自行记录全量与增量备份之间的关系。**」（**A**）
11. **Odoo.sh 的保留策略可直接作为产品默认值**：生产环境「每天自动备份，保留 **7 个每日备份、4 个每周备份和 3 个每月备份**。每个备份包含数据库转储、filestore（附件和二进制字段）、日志和会话」；暂存/开发环境**不自动备份**；手动备份保留 7 天、每天限 5 次。（**B**）
12. **Odoo 的源码级 API（A 级）**：`odoo/service/db.py` 的 `dump_db(db_name, stream, backup_format='zip')`、`restore_db(db, dump_file, copy=False, neutralize_database=False)`、`exp_duplicate_database`、`exp_drop`、`exp_rename`、`exp_create_database(db_name, demo, lang, user_password, login, country_code, phone)`。（**A**）

### 8.5 明确不借鉴与不发明字段承诺

| 不借鉴 | 理由 |
|--------|------|
| **把 `pg_dump` 当作生产定期备份的主要手段** | 官方明确警告「除非在简单情况下，`pg_dump` 通常不是对生产数据库进行定期备份的正确选择」（§8.2-6，**A**）→ **本系统设计**：`pg_dump` 只作**首版可落地的逻辑备份**，物理备份/PITR 走 §11 的实例级配置，二者用 `method` 列区分 |
| **把「恢复」做成单按钮无二次确认的操作** | 「恢复到某个时间点」是**高风险破坏性动作**（§8.2-9），必须权限码 + 二次输入 + 审计（**本系统设计**） |
| **把 PITR 的 `recovery_target_xid` 暴露到 UI** | 官方原文「**没有工具能帮你准确识别该用哪个事务 ID**」（§8.2-9，**A**）→ 只提供时间点与命名恢复点 |
| **照搬任何一家的界面样式**（HANA Cockpit 备份卡 / Odoo 数据库管理器） | 本模块口径：只学**能力模型**，**不照搬界面**（README §5.3） |
| **在页面上直接编辑 `archive_command` / `wal_level`** | 属数据库**实例级**且「`wal_level` 只能在服务器启动时更改」（§8.2-7，**A**）→ 页面最多**只读展示** |

**不发明字段承诺**：① **可由现有列/能力支撑（无需迁移）** —— `data_source_id` 校验、`status` 值域与 DDL 注释对齐（把 `pending` 收敛或补进前端 `STATUS_MAP`）、`start_time`/`end_time`/`error_message`/`file_path`/`file_size` 真实落库、`create_by` 取真实登录主体、**调度复用既有 `scheduled_task` + `JobHandler` SPI**；② **必须新增字段/表（★ 显式标注）** —— §8.4-① 的全部 ★ 项 **+ 一份保留策略配置**（§11 建议落位）；③ **本页 §7 实测 `sys_backup_record` 仅 13 列**，**不含**上述任何 ★ 项，**全部建议须走迁移**；④ **本轮不改任何代码**（§9.0），以上全部为**规格建议**，不得当作已实现引用。

## 10. 验收标准

> **前置**：本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下无 `e2e-system-*.cjs` / `e2e-admin-*.cjs`）。建议落地 `tools/e2e-system.cjs`（接口 + 直连 DB 对账 + 写库后复原 + Playwright UI 截屏，参照 `tools/e2e-crm.cjs`）。
> **权限账号**：`admin`（`SUPER_ADMIN`，`tenant_id=1`）作 200 基线；另需一个**非超管账号**（持 `SYSTEM_ADMIN` 或 `DEPT_ADMIN`，二者均**无** `*` 通配）做 403 对账。
> **🔴 红线②专项**：**超管（重登后）登录时本表能查到 ≥ 实测行数的记录**（当前 0 行 → 先造数）；**若造数后仍返回 0 行，即为租户插件误注入（页面空白而非报错）**，立即按 §5.5 修法处置。
> **🔴🔴 安全前置（本页最硬的一条纪律）**：本页写动作为**创建备份 / 恢复 / 删除**，其中「恢复」在真实实现后会**覆盖目标库当前数据**。故：① **对共享 devdb（`:5432/devdb`）只允许读类断言**（所有 `GET` + `psql` 只读 `SELECT`）；**严禁**在共享环境验证「恢复」的真实落库效果；② **写得像真的恢复只能在一次性隔离环境执行**（单独 PG 实例 + 丢弃库 `devdb_backup_e2e`，用完即毁）；③ 共享环境允许的写类断言**只有**「造数 → 回读 → 按原值复原 → 清理自产行」这一组，且**必须逐条清理**；④ 「无 `pg_dump` 子进程 / 无文件落盘」类断言**只读进程表与目录 mtime，不得 kill 任何进程**。

### 10.1 接口验收（**30 项**）

**A. 可达性与基线（①–⑤）**

① `GET /api/data-source/backup/list`（带 `admin` token）**当前期望 404** + `{"code":404,"message":"接口不存在: api/data-source/backup/list"}`（本轮实测值，即「包未装配」的可执行证据）。
② **阳性对照**：同一 token 调 `GET /api/config/list` → **期望 200**（排除「整个后端挂了」这一替代解释）。
③ **401 ≠ 端点存在**：不带 token 调 ① → **期望 401**；再调一个**确定不存在**的路径（如 `/api/__no_such_path__`）→ **同为 401** → 断言两者状态码相同，从而固化「必须带 token 才 404」的判定口径。
④ `GET /api/data-source/list` → **当前期望 404**；`psql` 直查 `select count(*) from sys_data_source` = **0** → 断言**两处数据源下拉必然无选项**。
⑤ `GET /api/menu/tree`（不带 `tenantId`）→ **期望 400「缺少必要参数: tenantId」**（证明映射存在，与 ① 的 404 形成对照）。

**B. 装配修复后的读写基线（⑥–⑫，在 P0-① 修复后执行）**

⑥ 重跑 ① → **期望 200**，返回体含键 `records`/`total`/`current`/`size`/`pages`（`BackupController.java:41-47`，**裸 Map 非 `Result` 包装**）；断言 `records` 是数组、`total` 是数字。
⑦ **DB 直查对账**：`select count(*) from sys_backup_record` = **T** → **期望 `total == T`**（基线 T=0）。
⑧ `?page=1&pageSize=1` → 断言 `records.length <= 1`、`size===1`、`current===1`、`pages===Math.ceil(T/1)`。
⑨ **`pageSize` 无上限（登记 P1）**：`?pageSize=100000` → **当前期望 200**；修复后改断言 400。
⑩ `?page=99999` → 期望 200 且 `records===[]`（`fromIndex >= total` 分支，`:39`），**不是 500**。
⑪ **`dataSourceId` 过滤**：先造 2 行（`data_source_id=101` / `102`）→ `?dataSourceId=101` → 断言**仅返回 101 的行且 `total` 与之相等**（`BackupServiceImpl.java:25`）。
⑫ **`X-Tenant-Id` 头的作用**：同 token 分别带 `X-Tenant-Id: 1` 与 `: 999` 调 `?dataSourceId=101` → 断言两次结果**不同**（999 时 0 行）→ 固化「归属来源是请求头」这一**当前事实**（§5.5 缺陷的可执行证据）。

**C. 创建链路 + 幂等 + 落盘对账（⑬–㉒）**

⑬ `POST /api/data-source/backup/create` body `{dataSourceId:101}` → **当前期望 404**；修复后 **期望 200** + `success:true`/`data`/`message`（`:72`）。
⑭ 缺参：body `{}` → 断言 HTTP **200** + `{"success":false,"message":"请提供数据源ID"}`（**当前是 200 不是 400**，§9.2-P1 证据）。
⑮ **数据源不存在也成功（登记 P1）**：body `{dataSourceId:999999999}` → **当前期望 200 + `success:true`** 且 DB 新增 1 行；修复后改断言 404。
⑯ **兜底**：body `{dataSourceId:101}`（不传名称/类型）→ 断言 `backup_name` **以 `手动备份_` 开头**（`:67`）、`backup_type=='full'`（`:68`）。
⑰ **🔴 状态与死列专项（当前事实）**：直查刚插入行 → 断言 **`status=='running'`**、`start_time IS NOT NULL`，且 **`file_path`/`file_size`(除默认 0)/`end_time`/`error_message` 全为 NULL/0**（`BackupServiceImpl.java:33-41` 从不 set 这 4 列）→ 「只记台账无 dump」的可执行证据。
⑱ **🔴 状态推进（当前必失败，修复后必通过）**：插入后等待 ≥ 60s 再直查同一行 → **当前断言仍为 `'running'`**（全仓无改写路径）；**修复后断言必须为 `success` 或 `failed`**。
⑲ **🔴 幂等断言**：连续两次 `POST /create` 且 body **完全相同** → 断言**产生 2 行台账**（当前**无幂等键**，`BackupController` 无去重）→ **两条口径二选一并在实现前定死写入 §4**：(a) 允许重复 → 断言 2 行；(b) 要求幂等 → 断言「第 2 次返回既有记录、台账仍 1 行」，此时须新增幂等键（`backup_no` 或 `dataSourceId+backupName+日期` 唯一约束）。**同时断言此刻台账可区分**：两行 `id` 不同、`create_time` 不同，但**无任何字段能表明「哪一行是重复请求」** → 登记缺口。**🔴 关键（修复后）**：连续两次 `POST /create` **不得产生第二个真实的备份文件** —— 断言备份目录文件数增量为 **0 或 1**（取决于幂等口径），增量 > 1 即幂等失效。
⑳ **🔴 无子进程 / 无落盘断言**：一次 `POST /create` 的**前/中/后**三次采样（间隔 200ms，共约 5s）—— **进程侧**断言进程树中**不存在** `pg_dump`/`pg_restore`/`mysqldump` 子进程（Windows：`Get-CimInstance Win32_Process` 或 `wmic process where "name like '%pg_%'" get ProcessId,ParentProcessId`；**只读**）；**文件侧**记录候选备份目录的文件数与最大 mtime（`find <dir> -newermt '<起点>' -type f | wc -l`）。**当前断言：进程 0 个 + 文件 0 个** —— **与「已成功创建备份」的提示语直接矛盾**（核心能力桩的铁证）；修复后断言**进程出现且文件增量为 1**。
㉑ **🔴 执行前后数据量对比**：`POST /create` 前后各执行 `select count(*) from sys_backup_record;` 与 `select count(*) from pg_stat_activity where datname = current_database();` → 断言**台账行数 +1**，且 **`pg_stat_activity` 连接数增量 ≤ 1**（PG 官方 §8.2-2 提示并行 `pg_dump` 会开 `njobs+1` 个连接；当前无 dump 故为 0，**修复后按实际 `-j` 值放宽并写明**）。
㉒ **🔴 失败不留 `running`**：制造一次**必然失败**的创建（`dataSourceId` 指向不可连通的数据源，或令备份目录不可写）→ ① 断言 HTTP 响应**不得**为 `success:true`（`BackupController.java:72` 当前**无条件**返回 `true`，故**当前必失败**）；② 断言**不存在**「创建后 60s `status` 仍为 `running` 且 `error_message` 为空」的行（失败必须落 `failed` + `error_message`）。**当前期望：因状态永不推进，该断言当前必失败** → 登记 P0 的可执行证据。

**D. 恢复链路 + 目标库数据量不变断言（㉓–㉗）**

㉓ `POST /api/data-source/backup/{id}/restore`（`admin`）→ **当前期望 404**；修复后 **期望 200**。
㉔ 对不存在的 id：`POST …/999999999/restore` → 断言 HTTP **200** + `{"success":false,"message":"备份记录不存在或状态无效"}`（`BackupServiceImpl.java:49` + `BackupController.java:82`）→ 登记「失败用 200 承载」。
㉕ **🔴🔴 恢复前后目标库数据量完全不变（只在隔离环境执行）**：前置 —— 在丢弃库 `devdb_backup_e2e` 中于恢复前后各做一次全库表行数快照（`select relname, n_live_tup from pg_stat_user_tables order by relname;`，或逐表 `select count(*)`）→ 断言 **`POST /{id}/restore` 后所有表行数快照完全一致**（逐表 diff 为空）；同时断言 `pg_database_size(current_database())` **变化量在噪声阈值内**。**⚠️ 当前「恢复」是空实现 → 自然满足「不变」→ 这正是本页最容易「假通过」的地方**：因此本断言**必须与 ㉖ 联合判定**（只断言「不变」会把空实现判为通过）。
㉖ **🔴 恢复的真实性反证（防假通过）**：与 ㉕ 同时执行 —— 在隔离环境中，把某个备份**之后**写入的一条测试数据留在目标库，然后执行恢复：若「恢复」是**真实实现** → 断言该测试数据**消失**（回滚到备份点）；若是**空实现**（当前） → 断言该测试数据**仍在** → **即判定为 `success:true` 但无任何效果的谎报**，登记 P0。**判定规则：㉕「不变」只有在 ㉖ 显示「确实回滚过」时，才是正确的「无副作用」证据；两者同时满足「不变 + 该变而没变」= 空实现。**
㉗ **🔴 恢复无子进程 / 无状态改写**：`restore` 前后各直查该行 → **当前断言 `status` 未变（仍 `running`）、`end_time` 与 `error_message` 仍为 NULL**（`BackupServiceImpl.java:46-51` 不 touch 任何列）；同时断言进程侧**无 `pg_restore`/`psql` 子进程**、文件侧**无新文件**。
㉘ **🔴 「改库 → 回读 → 按原值复原」标准动作（本页适用）**：取一行记录，记录其 `backup_name` 原值 → 经接口或直连改为 `E2E_BKP_TMP` → 回读断言新值 → 再改回原值 → 回读断言复原；**若走直连改库，必须用 `UPDATE` 精确到 `id` 并在结束时复原**（本表无 `update_time`，无法靠时间戳自查，**故必须记录原值**）。

**E. 删除与清理（㉙–㉚）**

㉙ `DELETE /api/data-source/backup/{id}` → **当前期望 404**；修复后 **期望 200 + `success:true`**；**直查断言该行物理消失**（`select count(*) … where id=<id>` = 0，**因本表无 `deleted` 列**，不是逻辑删除）。**幂等性**：对同一 id 再 `DELETE` → 断言 HTTP **200** + `{"success":false,"message":"备份记录不存在"}`（`BackupServiceImpl.java:55` 返 0 行 → `BackupController.java:91`）。
㉚ **权限断言（写清账号 + 期望码）**：① 用 **`admin`（SUPER_ADMIN）** 调 `list`/`create`/`restore`/`delete` → **期望 200**（`*` 通配旁路，`UnifiedPermissionCacheService.java:84-88`）；② 用**非超管账号**（无 `*`）调同 4 个端点 → **期望 403**（4 个码在 `sys_permission` 中 **0 行**，实测）；③ 断言 `select count(*) from sys_permission where permission_code like 'datasource:backup%'` = **0**（当前事实），补种子后改断言 ≥ 4。**🔴 清理自产数据 + 行数复原**：⑪/⑬–⑲/㉘ 造出的**所有**测试行必须逐条 `DELETE`（或按 id 精确物理删除）→ 结束时断言 `select count(*) from sys_backup_record` **回到造数前的基线值（当前 = 0）**，且**备份目录文件数回到 ⑳ 观测到的基线**（测试产物不得残留 —— 见记忆中的「共享 db E2E 断言必须加作用域」）。

## 12. 剩余缺口（P0 / P1 / P2）

> 口径与《系统模块/README.md》§7 对齐：**P0** = 页面不可用 / 数据不落库 / 越权 / 红线；**P1** = 与业界能力差距大但页面能开；**P2** = 体验与一致性。README §3.4 **P0-7**（备份管理核心能力缺失）、§7.1 第 **7** 条（「恢复」空实现且谎报成功）、**P0-1/P0-2**（数据管理 22 端点全 404）、**P0-15/P0-16/P0-17** 在本页的具体化 —— 证据与修法见 §9.2。

### P0（5 条）

① **端点全 404（README P0-1 / P0-2 的具体化）**：`cn.aiedge.datasource` 漏配 `scanBasePackages`（`AiReadyApplication.java:21-96`），`@MapperScan` 通配（`:117`）→ Mapper 注册而 Service/Controller 不注册 → 本页 4 端点 + 数据源下拉 1 端点**全 404**（运行态实测：本页 404 / `/api/config/list` 200）。
② **「创建备份」只记台账、无 dump、状态永不推进（README P0-7 前半）**：`BackupServiceImpl.java:31-44`；`status` 固定 `running` 且**包外零引用**；4 个死列（`file_path`/`file_size`/`end_time`/`error_message`）；全仓 `pg_dump|pg_restore|mysqldump|ProcessBuilder` **零命中**。
③ **「恢复」空实现且谎报成功（README P0-7 后半 / §7.1 第 7 条）**：`BackupServiceImpl.java:46-51` 仅做状态字符串比较；`BackupController.java:80-83` **无条件**返回 `success:true`；前端弹成功且不检查 `res.success`。
④ **「恢复」按钮永久不可达**：门槛 `status !== 'success'`（`:293`）恒真 + `pointer-events:none`（`:115`、`:342-345`）→ 「按钮存在但永远不可达」的典型，**同时构成对 ③ 的双层掩盖**。
⑤ **零权限 + 零审计（P0-16 / P0-17 的具体化）**：前端无 `v-permission`；4 个码 `datasource:backup:*` 在 `sys_permission`（264 行）中 **0 行** → 非超管必然 403；创建/恢复/删除**零流水**，`sys_audit_log` 实测 **0 行**（红线③）。

⑥ **失败用 HTTP 200 承载 + 前端不检查 `res.success`** → 404/失败也提示成功（`BackupController.java:62-64/80-83/91`；`backup/index.vue:292-311`）。⑦ **`create` 不校验数据源存在性**（`:62-66`），非数字入参预期 500（**未实测**）。⑧ **4 个死列 → 3 处恒空/恒 0**。⑨ **状态值域三方不一致 + `failed` 是死值**（`V6.14.0:237/247` vs `BackupRecord.java:37` vs `:186-190`）。⑩ **前端分页 + 1000 条静默截断**；后端 `list` 亦为「全查 + 内存 `subList`」且 `pageSize` 无上限。
