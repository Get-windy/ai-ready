# ERP供应商协同门户跨模块集成架构方案

## 1. 概述

### 1.1 项目背景
ERP供应商协同门户涉及多个核心模块的集成，包括：
- 批次管理模块（已初步建立）
- 价格策略模块（开发中）
- 供应商管理模块（规划中）
- 协同流程模块（待开发）
- AI智能客服系统（规划中）

### 1.2 集成目标
1. 实现模块间数据无缝流转
2. 建立统一的服务治理机制
3. 确保系统可扩展性和可维护性
4. 支持分布式事务和数据一致性
5. 提供统一的监控和日志体系

### 2.2 模块间关系
```
批次管理 → 价格策略：批次信息用于价格计算
价格策略 → 供应商管理：供应商特定价格策略
供应商管理 → 协同流程：供应商协同工作流
协同流程 → 批次管理：流程触发批次操作
所有模块 → AI客服：智能咨询和辅助决策
```

## 3. 技术实现方案

### 3.1 微服务集成架构

#### 3.1.1 服务发现与注册
- 使用 **Consul** 或 **Nacos** 作为服务注册中心
- 支持动态服务发现和健康检查
- 实现服务熔断和降级机制

#### 3.1.2 API 网关设计
- 统一入口点：所有外部请求通过API网关
- 身份认证和授权统一处理
- 请求限流和熔断保护
- 请求/响应日志记录
- 跨域资源共享(CORS)支持

#### 3.1.3 服务间通信
- **同步通信**：RESTful API（80%场景）
- **异步通信**：消息队列（复杂业务流程）
- **协议规范**：
  - 使用OpenAPI 3.0规范定义接口
  - 统一错误码和响应格式
  - 版本控制策略：URL路径版本化

### 3.2 数据库集成方案

#### 3.2.1 数据一致性策略
```
方案1：分布式事务（适用于强一致性场景）
  批次创建 → 价格计算 → 供应商通知 → 事务提交/回滚
  技术选型：Seata分布式事务框架

方案2：最终一致性（适用于大多数业务场景）
  批次创建 → 发送领域事件 → 价格策略服务消费事件 → 更新价格
  技术选型：RabbitMQ + 事件溯源

方案3：Saga模式（适用于长事务流程）
  拆分为多个本地事务，每个事务都有补偿操作
  技术选型：Camunda工作流引擎
```

#### 3.2.2 共享数据层设计
```
┌─────────────────────────────────────────────┐
│          共享数据模型 (Shared Models)        │
├─────────────────────────────────────────────┤
│ 1. 供应商主数据                             │
│    - 供应商基本信息                         │
│    - 资质信息                              │
│    - 联系人信息                            │
│                                             │
│ 2. 批次主数据                               │
│    - 批次标识信息                           │
│    - 批次状态                               │
│    - 批次关联关系                           │
│                                             │
│ 3. 价格策略数据                             │
│    - 价格规则定义                           │
│    - 折扣策略                               │
│    - 价格历史                               │
└─────────────────────────────────────────────┘
```

### 3.3 缓存策略

#### 3.3.1 缓存层级设计
```
L1 缓存：本地缓存 (Caffeine)
  - 有效期：5分钟
  - 容量：1000条
  - 用途：频繁访问的配置数据

L2 缓存：分布式缓存 (Redis Cluster)
  - 有效期：30分钟
  - 容量：10000条
  - 用途：共享数据、会话数据

L3 缓存：数据库缓存
  - 查询缓存：高频查询结果缓存
  - 二级缓存：MyBatis/Redis二级缓存
```

#### 3.3.2 缓存一致性方案
- 写策略：先更新数据库，后删除缓存
- 读策略：先读缓存，缓存不存在则查库并写入缓存
- 失效策略：基于TTL自动过期 + 主动失效
- 并发控制：使用Redis分布式锁

### 3.4 消息队列集成

#### 3.4.1 消息主题设计
```
topic.supplier.batch.created     # 批次创建事件
topic.supplier.price.calculated  # 价格计算事件  
topic.supplier.workflow.triggered # 工作流触发事件
topic.supplier.ai.assistant     # AI助手请求事件
topic.supplier.notification     # 通知事件
```

#### 3.4.2 消息处理保障
- **可靠性**：持久化存储 + 确认机制
- **顺序性**：分区键保证同一业务顺序
- **去重**：消息ID去重机制
- **监控**：消息堆积告警

## 4. 接口规范

### 4.1 统一接口标准

#### 4.1.1 RESTful API 规范
```json
// 请求格式
{
  "requestId": "uuid-v4",
  "timestamp": "2024-01-01T00:00:00Z",
  "version": "v1",
  "data": {}
}

// 响应格式
{
  "success": true,
  "code": "SUCCESS",
  "message": "操作成功",
  "data": {},
  "timestamp": "2024-01-01T00:00:00Z",
  "requestId": "uuid-v4"
}

// 错误响应
{
  "success": false,
  "code": "ERROR_CODE",
  "message": "错误描述",
  "detail": "详细错误信息",
  "timestamp": "2024-01-01T00:00:00Z",
  "requestId": "uuid-v4"
}
```

#### 4.1.2 接口版本管理
- URL路径版本：`/api/v1/suppliers`
- 请求头版本：`X-API-Version: v1`
- 弃用策略：新版本发布后，旧版本保持6个月支持期

### 4.2 核心接口定义

#### 4.2.1 批次管理接口
```yaml
/batch-management/v1/batches:
  POST: 创建批次
  GET:  查询批次列表
  /{batchId}:
    GET:    获取批次详情
    PUT:    更新批次信息
    DELETE: 删除批次
```

#### 4.2.2 价格策略接口
```yaml
/price-strategy/v1/policies:
  POST: 创建价格策略
  GET:  查询价格策略列表
  /calculate:
    POST: 计算批次价格
```

#### 4.2.3 供应商管理接口
```yaml
/supplier-management/v1/suppliers:
  POST: 创建供应商
  GET:  查询供应商列表
  /{supplierId}:
    GET:    获取供应商详情
    PUT:    更新供应商信息
    PATCH:  部分更新供应商
```

```sql
-- 批次-价格数据一致性验证
SELECT 
  b.batch_id,
  b.status,
  p.price,
  p.calculated_at
FROM batches b
LEFT JOIN prices p ON b.batch_id = p.batch_id
WHERE p.price IS NULL AND b.status = 'ACTIVE';
```

### 6.2 监控告警

#### 6.2.1 监控指标
- **应用指标**：QPS, 响应时间, 错误率
- **系统指标**：CPU, 内存, 磁盘, 网络
- **业务指标**：批次创建量, 价格计算成功率
- **集成指标**：服务间调用成功率, 消息延迟

#### 6.2.2 告警策略
```
级别    条件                     响应时间
P0    服务不可用                5分钟内
P1    性能严重下降              15分钟内  
P2    数据不一致                30分钟内
P3    资源使用率高              1小时内
```

### 6.3 故障处理

#### 6.3.1 故障分类
- **A类故障**：核心功能不可用，立即处理
- **B类故障**：非核心功能异常，4小时内处理
- **C类故障**：轻微问题，24小时内处理

#### 6.3.2 应急预案
- 数据库故障：主从切换，数据恢复
- 服务故障：服务降级，流量切换
- 网络故障：多区域部署，DNS切换
- 集成故障：消息重试，补偿事务

### 7.2 风险识别与应对

#### 7.2.1 技术风险
```
风险项：服务间通信延迟过高
影响：业务流程响应时间增加
应对：优化网络架构，增加缓存，异步处理

风险项：数据一致性难以保证
影响：业务数据不准确
应对：引入分布式事务，加强监控告警

风险项：系统复杂性增加
影响：维护成本提高
应对：统一技术栈，标准化开发规范
```

#### 7.2.2 管理风险
```
风险项：团队协作效率低
影响：集成进度延迟
应对：建立每日站会，明确接口规范，使用协作工具

风险项：需求变更频繁
影响：集成方案不稳定
应对：建立需求变更流程，版本化管理接口

风险项：测试覆盖不足
影响：上线后问题频发
应对：建立自动化测试体系，持续集成
```
