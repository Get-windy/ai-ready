## 1. 页面概述

租户列表页是**平台运营方的租户台账**：以分页表格列出全平台租户（编码 / 名称 / 联系人 / 电话 / 状态 / 到期时间），并提供「新增租户 / 编辑 / 删除」三个写动作。它是 `61301 租户管理` 组的第 1 页（`sort=100`），是「平台方怎么管所有租户」这条链路的入口页。

**1.1 与相邻页的分工（`61301 租户管理` 组 5 页极易混淆）**

| 页面 | 菜单ID | 回答的问题 | 后端前缀 | 本页与其关系 |
|------|:-----:|-----------|---------|-------------|
| **租户列表（本页）** | 62001 | 「平台上一共有哪些租户、什么状态、什么时候到期」+ 平台**代建**租户 | `/api/tenant` | 本页 |
| 租户审批 | 62002 | 「哪些租户在等审批」——**审批流转**（通过/驳回） | `/api/tenant-registration` | 同表 `sys_tenant` 的**另一视角**；本页 `status` 字段是审批的结果 |
| 租户套餐 | 62003 | 「平台上有哪几档套餐、多少钱」——**权益模板** | `/api/tenant-package` | 本页 `level` 字段语义上对应套餐编码（`basic/professional/enterprise`），但**当前无外键关联**（见 §5.3） |
| 模块授权 | 62004 | 「某个租户能开哪些模块」——**权益分配记录** | `/api/tenant-menu` | 本页选中租户后的下游操作 |
| 配额管理 | 62005 | 「某个租户的用量上限」——**配额账本** | `/api/tenant-quota` | 同上 |

> **一句话分工**：本页是**租户主数据的读写界面**；审批（62002）决定租户**能不能进**，套餐（62003）决定**给什么**，模块授权（62004）/配额（62005）决定**给多少**。
> **本页与《租户审批》共用同一张表**：本页的「新增租户」是**平台代建**（`POST /api/tenant`，直接落 `sys_tenant`），**不经过**审批链路的 `POST /api/tenant-registration/register`（该端点由登录页 `views/login/tenant-register.vue:375` 使用，本页不涉及）。

## 2. 页面截图

**N/A —— 本模块无对标系统截图。**

**原因（本模块的通用前提，本页严格遵守）**：ql361（来肯企汇 v2.2，`22stable.ql361.com`）是**租户级进销存产品**，它对客户暴露的只有「设置」域（`client_type = tenant-admin`）。本页属于**平台控制台**（`client_type = system-admin`）——「平台方怎么管所有租户」——**任何厂商都不会把自己的 SaaS 控制台给客户看**。因此：

- ql361 中**不存在**「租户列表」这个页面（`sys_menu` 里 `client_type='system-admin'` 的行不会出现在租户登录的菜单树中），**无可对标截图**；
- **不使用 Odoo / SAP / 金蝶 / 用友的界面截图**（口径见《系统模块/README.md》§5.3：本模块按业界**能力模型**建模，**不照搬任何一家的界面**）；
- §8 只写**业界能力对标**，逐条标来源与可信度级别。

**本系统截图**：当前无本系统验收截图（`tools/` 与 `tools/acceptance/` 下不存在 `e2e-system-*.cjs` / `e2e-admin-*.cjs`）→ **P2 缺口**（README §7.3）。

**数据现状（devdb 实测 2026-09-18）**：

```
表内 3 行（select id,tenant_name,tenant_code,status,deleted from sys_tenant order by id）：
  0 | tenant_mqd4cr9h租户 | tenant_mqd4cr9h | status=0 | deleted=1（已逻辑删除，列表不显示）
  1 | 系统租户           | SYSTEM          | status=1 | deleted=0
```

### 3.8 数据获取与错误处理（`fetchData`，`:233-242`）

```ts
async function fetchData() {

  try {

    list.value = res.data.records || []
    pagination.value = { current: res.data.current, pageSize: res.data.size, total: res.data.total }
```

**🔴 缺陷 P1-④：`fetchData` 无 `catch`**（`:233-242` 只有 `try/finally`）→ 接口 4xx/5xx 时**本页无任何自身提示**，`loading` 被复位、表格保持上一次数据或空表；错误只能靠全局 `request` 拦截器（`utils/request.ts`）提示。**本页 3 个写动作都有 `catch`（`:294`、`:310`），唯独查询没有** —— 口径不一致。

## 5. 业务规范

### 5.1 状态值域

| 场景 | 选项（名 / 值） | 位置 |
|------|----------------|------|
| 查询条件「状态」下拉 | `1` = 正常；`0` = 禁用 | `list/index.vue:54-59` |
| 表格状态 Tag | `status === 1` → 「正常」+ `green`；否则「禁用」+ `red` | `list/index.vue:91-93` |
| 新增默认状态 | `status = 1` | `resetModalForm`，`list/index.vue:262` |
| 后端创建兜底 | `if (tenant.getStatus() == null) tenant.setStatus(1);` | `TenantController.java:85-87` |
| 租户等级下拉 | `basic` 基础版 / `professional` 专业版 / `enterprise` 企业版 | `list/index.vue:182-190` |
| DB 实测 `status` 分布 | `1` → 2 行（id=1 / id=2）；`0` → 1 行（id=0，且 `deleted=1`） | devdb 实测 |

**⚠️ 值域只有 2 值，与业务需要不符（P1）**：真实租户生命周期至少有「待审 / 试用 / 正式 / 停用 / 到期 / 注销」六态（业界实证见 §8）；本系统 `status` 只有 `0/1` 二值，**且「待审」被复用为 `status=0`**（`TenantRegistrationService.java:117`）→ **「未审批」与「已禁用」在数据上完全无法区分**（详见《租户审批开发文档》§5.1）。
**⚠️ 与《租户套餐》的状态语义冲突（P2）**：套餐表 `status` 也是 `1=启用 / 0=停用`（`SysTenantPackage.java:43-44`），但那是**产品档位是否可售**，与租户是否可用**不是同一个概念**，两处共用同一组数字容易误读。

### 5.2 流转规则（本页动作）

```
（无）── 平台代建 POST /api/tenant ──▶ status=1 正式（直接可用，不经审批）
status=1 ── 编辑（PUT /{id}）──▶ status 可被改写成 0/1（前端弹窗无此字段，仅能通过接口改）
status=1 ── 删除（DELETE /{id}）──▶ deleted=1 逻辑删除（不可逆，无回收站）
（后端有 PATCH /{id}/status，本页未接）
```

| 动作 | 后端 | 前置校验 | 失败文案 | 副作用 | 行号 |
|------|------|:--------:|---------|--------|----|
| 新增 | `POST /api/tenant` | 无（前端仅查非空） | 后端无 | `deleted=0`；`status` 空则补 `1` | `TenantController.java:80-90` |
| 编辑 | `PUT /api/tenant/{id}` | 无（**不校验 id 是否存在**） | 无（`Result.ok(rows>0)`，改 0 行也返回 true 语义） | `updateById`（MyBatis-Plus **忽略 null 字段**） | `:95-102` |
| 删除 | `DELETE /api/tenant/{id}` | 无 | 无 | 逻辑删除 `deleted=1` | `:107-113` |

**🔴 缺陷 P1-⑤：`PUT` 与 `DELETE` 不做存在性校验** —— `update` 直接 `tenantMapper.updateById(tenant)`（`:100`），`delete` 直接 `deleteById(id)`（`:111`），**都不先 `selectById`**。→ ①对不存在的 id 调用 `PUT` 会返回 `Result.ok(false)`（rows=0）但 HTTP 200，前端会提示「更新成功」；②对比 `GET /{id}`（`:71`）与 `GET /{id}/config`（`:146-149`）**都做了 `tenant == null || deleted == 1` 检查**，同一控制器内口径不一致。

**🔴 缺陷 P1-⑥：`updateById` 忽略 null → 「清空字段」不可实现**：MyBatis-Plus 默认 `update-strategy=NOT_NULL`，`PUT /{id}` 传 `{"remark": null}` **不会**把备注清空（`SysTenant` 未覆盖该策略）。→ 用户以为清空了，实际原值仍在（属通用陷阱，见记忆中的「MyBatis 两个静默陷阱」）。

### 5.3 取值口径（`level` 与套餐的关系）

- 本页 `level` 三值与《租户套餐》`package_code` 三值**字面完全一致**：`basic` / `professional` / `enterprise`（`list/index.vue:182-190` vs `sys_tenant_package.package_code` 实测 `basic/professional/enterprise`）。
- **但 `sys_tenant` 无套餐外键、无 `package_id` 列**（15 列实测），`sys_tenant_package` 也无任何指向租户的分配记录表（`sys_tenant_entitlement` 之类的表**不存在**）。
- → **「租户持有哪个套餐」当前只能靠 `level` 字符串猜**，且**套餐改价/改配额不会影响任何租户**（因为根本没有绑定关系）。这是 §8「套餐 = 模板，租户持有的是分配记录」这条业界口径的**结构性缺失**（P1，详见《租户套餐开发文档》§5.4、§12）。

### 5.5 多租户口径（本模块红线②，必须逐页写清）

**实测复核（2026-09-18，以本轮源码核对为准）**：

| 事实 | 证据 |
|------|------|
| `sys_tenant` **在** `IGNORE_TENANT_TABLES` 白名单内，且该表**没有 `tenant_id` 列**（15 列实测无此列） | `MyBatisPlusConfig.java:33`；devdb `information_schema.columns` |
| 同组《租户套餐》的 `sys_tenant_package`、**以及** `sys_tenant_menu` / `sys_module` / `sys_module_version` / `sys_tenant_quota` **均不在**白名单（`:32-93` 逐项核对无命中） | `MyBatisPlusConfig.java:32-93` |
| **超管整体豁免已接线并生效** | 登录时写 Session：`StpUtil.getSession().set("tenantScopeExempt", StpUtil.hasRole("SUPER_ADMIN"))`（`SysUserServiceImpl.java:88`）；拦截器 `shouldSkip()` = 「租户不可解析」**或** `isTenantScopeExempt()`（`AiReadyTenantLineInnerInterceptor.java:41-44`）；`isTenantScopeExempt()` 只读 Session 缓存（`MyBatisPlusConfig.java:157-167`，注释明确说明「实时算角色会经 SQL 造成无限递归」） |
| → **新登录的超管会话下，租户插件对全部表整体跳过**，上述平台表**读得到、不会空白** | 同上 |
| ⚠️ **红线本体仍在**：**非超管的平台运营账号**（平台侧正确配置角色的运营人员，其会话租户 ≠ 0）**仍会被注入 `tenant_id = <会话租户>`** | 拦截器仅豁免「不可解析」与「SUPER_ADMIN」两种；`getCurrentTenantIdValue()`（`:115-134`）对普通登录用户返回其 `tenant_id` |
| 表现形态 | **页面空白 / 查不到数据，而不是报错** —— 这是本模块最危险的失败模式（README §1.3 红线②） |
| 副作用（须知悉） | 改动前**已签发**的旧 token 无 `tenantScopeExempt` 标记 → 需**重新登录一次**才恢复全局视野（`MyBatisPlusConfig.java:150-152`） |

**结论（写入口径）**：本页如实写成「**当前被超管整体豁免掩盖，但配置脆弱、红线仍在**」。
**修法（两条）**：① 读全局数据用 `@InterceptorIgnore(tenantLine = "true")`；② 写目标租户行前 `MyBatisPlusConfig.setTempTenantId(tid)`（`MyBatisPlusConfig.java:101-103`）。**不得**把平台级表加进 `IGNORE_TENANT_TABLES` 了事（`sys_tenant_package` 有 `tenant_id` 列，白名单化会让**所有**租户看到所有套餐）。

### 8.2 业界做法要点（逐条给级）

1. **平台层与租户层必须物理/逻辑分离** —— jeecg 官方原话：「系统用户、系统角色菜单，这个是给超级管理员用的，**不做租户隔离**」。即平台侧数据不能落在租户过滤范围内。**这是本模块最关键的一条红线**（与本系统 §5.5 对应）。**A**
2. **租户列表要能一眼看出「谁能用、用了多少、什么时候到期」** —— SAP 的账户导航器把「**标签（Labels）**」做成可筛选维度，且**标签可继承**（查看子账户时同时显示父目录的标签）；每个实体**最多 10 个标签**，同名标签不能重复添加。**A**
3. **层级不是一个平面** —— SAP 允许「目录 → 目录 → … → 子账户」，**最深 7 层**（最高全局账户、最低子账户，中间最多 5 层目录）；这给了「集团-子公司-工厂」式建模能力。**A**
4. **标签体系优于硬编码分类** —— SAP 明确标签**替代了**旧「自定义属性（custom properties）」，且支持单值标签 / 多值标签 / 无值标签。**A**
5. **删租户是破坏性动作** —— SAP 删除租用后「**所有与多租户应用程序相关的数据都将在相应子账户中删除**」；即**业界的删除是真删**。→ 本系统若要保留客户数据，**必须显式设计冷静期/软删除**，并在文档里写清与业界的差异。**A**

## 10. 验收标准

> **前置**：本模块**尚无 E2E**（`tools/` 与 `tools/acceptance/` 下无 `e2e-system-*.cjs` / `e2e-admin-*.cjs`）。建议落地 `tools/e2e-system.cjs`（接口 + 直连 DB 对账 + 写库后复原 + Playwright UI 截屏，参照 `tools/e2e-crm.cjs`）。
> **权限账号**：`admin`（`SUPER_ADMIN`，`tenant_id=1`，`sys_user.is_super_admin=t`）用作 200 基线；另需一个**非超管账号**（建议持 `SYSTEM_ADMIN` 或 `DEPT_ADMIN` 角色，二者均**无** `*` 通配）做 403 对账。
> **🔴 本页验收的首要断言（红线②专用）**：**超管登录后本表能查到数据** —— 直查 `sys_tenant` 共 **3 行**（其中 id=0 已逻辑删除）→ `GET /page` **预期 ≥ 2 行**。**若返回 0 行，即为租户插件误注入（页面空白而非报错）**，必须立即按 §5.5 修法处置。
> **数据前置**：`contact_person` / `contact_phone` / `expire_time` 现网全空 → **§10.1 的字段类断言须先经接口造数**（造数后须清理）。

### 10.1 接口验收（**24 项**）

**可达性与基线（①–④）**

① `GET /api/tenant/page`（带 `admin` 的 `Authorization: Bearer <token>`）**期望 200**，返回体含键 `records` / `total` / `current` / `size` / `pages`（`TenantController.java:53-59`）。
② **超管数据可见性专项**：断言 `total ≥ 2`（直查 `select count(*) from sys_tenant where deleted=0` = **2**）；**同时断言返回的 `records[].id` 不含 `0`**（`@TableLogic` 生效，`SysTenant.java:60-61`）。
③ `GET /api/tenant/page` **不带 `Authorization`** → **期望 401/403**（类级 `@SaCheckLogin`，`TenantController.java:24`）。
④ 用**非超管账号**调 `GET /page` → **期望 200**（`/page` 无权限注解，仅要求登录）→ 记录结论（这是「读端点无权限码」的显式登记）。

**查询与分页（⑤–⑨）**

⑤ `tenantName` 模糊查询：传部分名称，断言返回行数 ≤ 全量且**每行 `tenantName` 均含该子串**（`like`，`TenantController.java:46`）。
⑥ `status=1` 过滤 → 断言所有返回行 `status === 1`；`status=0` → 断言返回行数 = 直查 `select count(*) from sys_tenant where status=0 and deleted=0`（**本轮实测 = 0**：全表仅 id=0 一行 `status=0`，而它 `deleted=1` 被逻辑删除过滤）→ **`status=0` 过滤预期 0 行**。**注意区分**：`select count(*) from sys_tenant where status=0`（**不带** `deleted`）= **1**。
⑦ **`tenantCode` 后端可用但前端未接**：直接调 `GET /page?tenantCode=SYSTEM` → **期望 200 且命中 id=1 行**（证明后端参数可用，登记前端缺输入项）。
⑧ 分页断言：`pageSize=1` → 断言 `records.length === 1` 且 `total ≥ 2`、`current === 1`、`size === 1`。
⑨ **`pageSize` 无上限**（登记 P2 缺陷）：传 `pageSize=100000` → **当前期望 200**（无校验）；修复后改断言 400。

**写链路（⑩–⑮）**

⑩ `POST /api/tenant`（`admin`）body 仅 `{tenantCode, tenantName}` → **期望 200**；断言 DB 新增 1 行且 `deleted=0`、**`status=1`**（兜底逻辑 `TenantController.java:85-87`）。
⑪ **字段静默丢弃专项（P1 缺陷的可执行证据）**：`POST` body 额外带 `{"contactName":"张三","expireDate":"2030-01-01","maxUsers":50,"description":"备注X"}` → 断言 HTTP 200，但**直查 DB 该行 `contact_person` / `expire_time` / `remark` 全为 NULL**（且表中无 `max_users` 列）。
⑫ **唯一性缺失专项（P1 缺陷）**：用**同一 `tenantCode` 再 POST 一次** → **当前期望 200（重复创建成功）**；修复后改断言 400/409。
⑬ `PUT /api/tenant/{id}` 改 `tenantName` → 断言 200 且 DB 值已变、`update_time` 已刷新；**再断言可回读**（`GET /page?tenantName=<新值>`）。
⑭ **`PUT` 改不存在的 id**（如 `999999999`）→ **当前期望 HTTP 200**（`Result.ok(false)`，登记 P1 缺陷）；修复后改断言 404。
⑮ **`updateById` 忽略 null 专项（P2 陷阱）**：先给某行写 `remark='R1'`，再 `PUT` 传 `{"remark": null}` → **断言 DB 中 `remark` 仍为 `'R1'`**（未被清空）；如需清空须用空串或 `UpdateWrapper.set(null)`。

**删除与复原（⑯–⑲）**

⑯ `DELETE /api/tenant/{id}` → 断言 200；**直查断言 `deleted=1`（逻辑删除，非物理删除）**，且 `GET /page` 不再返回该行。
⑰ **删除的幂等性**：对同一 id 再 `DELETE` 一次 → 记录返回值（当前 `deleteById` 对已删行返回 0 行，`Result.ok(false)`）。
⑱ **「改库 → 回读 → 按原值复原」标准动作**：取 id=2 行，记录原 `tenant_name` / `status` → 经接口改名为 `E2E_LIST_TMP` → `GET /page` 回读断言新值 → 再改回原值 → `GET /page` 回读断言复原（**全程不得直改 DB**）。
⑲ **清理自产数据**：⑩–⑰ 造出的租户必须**按 id 逐条清理**（删除或物理清除测试行），完成后断言 `select count(*) from sys_tenant where deleted=0` 回到 **2**。

**权限断言（⑳–㉒）**

⑳ 用 `admin`（SUPER_ADMIN）调 `POST` / `PUT` / `DELETE` → **期望 200**（`*` 通配旁路，`UnifiedPermissionCacheService.java:86`）。
㉑ 用**非超管账号**（无 `*`）调 `POST` / `PUT` / `DELETE` → **期望 403**（`system:tenant:create/update/delete` 在 `sys_permission` 中 **0 行**，实测）。**这是当前缺陷的显式登记**（修复权限种子后应改为 200）。
㉒ 断言 `select count(*) from sys_permission where permission_code like 'system:tenant%'` = **0**（当前事实）；补种子后改断言 ≥ 4（list/create/update/delete）。

**未用端点与缺口（㉓–㉔）**

㉓ `GET /api/tenant/{id}`（前端未接）→ 断言 200 且含 `contactPerson` / `expireTime` / `remark` 键；对不存在的 id → 断言 404（`Result.fail(404, "租户不存在")`，`:72`）。
㉔ **405 专项**：按**前端写法**发 `PUT /api/tenant/{id}/status?status=0` → **期望 405**（后端是 `@PatchMapping`）；改用 `PATCH` → **期望 200** 且 DB `status` 已变。**这是 §6.3-③ 的可执行证据。**

## 12. 剩余缺口（P0 / P1 / P2）

> 口径与《系统模块/README.md》§7 对齐：**P0** = 页面不可用 / 数据不落库 / 越权 / 红线；**P1** = 与业界能力差距大但页面能开；**P2** = 体验与一致性。
> README §7.1-P0-15（平台级表未豁免多租户）、P0-17（平台侧无审计）、§7.2「租户列表字段名错位」在本页的具体化见下。

### P0（3 条）

① **权限码未落库导致非超管必然 403（README §7.1-P0-16 同源）**：`system:tenant:create/update/delete` 在 `sys_permission`（共 264 行）中 **0 行**；前端又**零 `v-permission`** → 「按钮可见但点了 403」。建议：补权限种子（迁移）+ 前端补指令，并统一到 `system:tenant:*` 命名域。
② **平台侧写操作零审计（README §7.1-P0-17 的具体化）**：新增/编辑/删除租户**不留任何流水**；`sys_audit_log` 实测 **0 行**。后果：「谁在什么时候从哪个 IP 给哪个租户建了账号」，**事后无法从业务表还原**。建议：按「时间 + 主体 + 来源 IP + 目标记录 + 操作 + 变更前后值 + 结果」落审计（SAP SAL 字段口径，README §1.3 红线③）。
③ **平台级表未豁免多租户插件（README §7.1-P0-15 的红线本体）**：`sys_tenant_package` / `sys_tenant_menu` / `sys_module` / `sys_module_version` / `sys_tenant_quota` 均不在 `IGNORE_TENANT_TABLES`（`MyBatisPlusConfig.java:32-93`），数据 `tenant_id=0` 而运营侧会话租户可为非 0 → **页面空白而非报错**。**当前被超管整体豁免掩盖**（`SysUserServiceImpl.java:88` + `AiReadyTenantLineInnerInterceptor.java:41-44`），**但配置脆弱**。建议：读全局用 `@InterceptorIgnore(tenantLine="true")`；写目标租户行前 `MyBatisPlusConfig.setTempTenantId(tid)`；**不要把平台表整体加进白名单**。**验收必须专门断言「超管登录后本表能查到 ≥2 行」**（§10.1-②）。

### P1（9 条）

④ **「联系人」列恒空**（`contactName` ↔ `contactPerson`，`:226`）—— 列配置错位，改一行即可。
⑤ **「到期时间」列恒空**（`expireDate` ↔ `expireTime`，`:229`）—— 同上，且缺日期格式化。
⑥ **弹窗 4 字段静默丢弃不落库**（`contactName` / `expireDate` / `maxUsers` / `description`；实体无 `maxUsers` / 无 `description`）→ 用户以为保存了，实际丢了。
